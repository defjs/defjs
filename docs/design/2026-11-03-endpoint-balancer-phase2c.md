## 1. 要解决的问题

1. **恢复冲击。** 现在摘除到期的端点立即回到候选，按正常份额接收流量。现场 60 个并发 `pick` 里有 20 个立刻选中刚恢复的副本。副本若仍未恢复，这一波请求会先失败，要再积累连续失败才会重新摘除；POST 不会换台，失败直接到用户。
2. **p2c 在途数起点过早。** 在途数在 `pick` 时加一，而 `pick` 发生在构建请求与拦截器之前。拦截器前后各等 80 毫秒时，所有端点的在途数被一起抬高，p2c 的平均收益只剩约 1.45%。

## 2. 半开试探与慢启动

### 2.1 选项

加在健康过滤的选项 `OutlierDetectionOptions` 上，三个内置工厂的 `outlierDetection` 选项与 `outlierDetection(child, options)` 共用：

| 选项                        | 类型                | 默认   | 说明                                     |
| --------------------------- | ------------------- | ------ | ---------------------------------------- |
| `halfOpen`                  | `boolean`           | `true` | 摘除到期后先只放行一次试探               |
| `probeTimeoutMs`            | 有限正数            | `5000` | 试探多久没有结果就视为通过               |
| `slowStartWindowMs`         | 非负有限数          | `0`    | 恢复后逐步放量的时长，`0` 表示不做慢启动 |
| `slowStartMinWeightPercent` | `(0, 100]` 的有限数 | `10`   | 慢启动开始时的最低放行比例               |

取值不合法时按现有选项错误处理，调用得到 `REQ_OPTIONS_INVALID`。

`halfOpen` 默认开启，这是对规格第 5 节与 gRFC A50 的有意偏离：现场证据表明到期即全量会把失败集中推给刚恢复的端点。`slowStartWindowMs` 默认关闭，与 Envoy 的慢启动默认不开一致。

### 2.2 端点状态

健康过滤里每个端点在原有状态之外，多出两个阶段：

1. **试探中。** 摘除到期、且 `halfOpen` 为 `true` 时进入。
2. **慢启动中。** 试探通过、且 `slowStartWindowMs` 大于 0 时进入，持续 `slowStartWindowMs`。

`halfOpen` 为 `false` 时，到期后跳过试探：`slowStartWindowMs` 大于 0 就直接进入慢启动，否则直接恢复正常，与第二期乙的行为相同。

### 2.3 试探中

- 候选计算时，试探中的端点只在「没有未结束的试探」时进入候选。一旦有一次 `pick` 选中了它，这次尝试就是试探，之后在它结束前，其他 `pick` 的候选都不含这个端点。
- 内层策略可能选不到它，例如轮询转到了别的端点。没被选中时，试探名额仍然空着，下一次 `pick` 继续提供。
- 试探的 `done`：
  - 非失败样本：试探通过。进入慢启动，或直接恢复正常。
  - 失败样本：立即重新摘除，倍数照第 5.6 节加一，不需要再积累连续失败。名额规则照旧，名额不足时视为试探未通过但不摘除，端点留在试探中。
  - `attempted` 为 `false`：只释放试探名额，状态不变。
- 试探的 `pick` 之后过了 `probeTimeoutMs` 还没有 `done`，视为试探通过。这主要针对 SSE 与 WebSocket：它们的 `done` 要到连接结束才来，健康的长连接不应让端点一直卡在试探中。判断在之后的 `pick` 与 `done` 里按 `Date.now()` 进行，不创建计时器。之后那次试探的 `done` 再到达时，按普通样本记账。
- 试探中的端点计入「已摘除」吗：不计。名额与「最后一个可用端点」照第 5.6 节，只看摘除期内的端点。
- 候选为空时的兜底照第 5.3 节第 3 条。兜底选中的试探中端点，同样算作这次试探。

### 2.4 慢启动中

- 候选计算时，慢启动中的端点以概率 `p` 进入候选，`p = max(minWeight, elapsed / slowStartWindowMs)`，其中 `minWeight = slowStartMinWeightPercent / 100`，`elapsed` 是距离进入慢启动的毫秒数。随机数用 `Math.random()`，测试用 `vi.spyOn(Math, "random")` 固定。
- 这样做与内层策略无关，轮询、p2c 与自定义策略都适用。它是按候选资格放量，不是按权重；文档要说明这一点和 Envoy 按权重放量的差别。
- 窗口结束后恢复正常。慢启动期间的失败照常计入连续失败与失败百分比，达到阈值照常摘除。
- 如果这次计算让候选变空，按第 5.3 节第 3 条兜底。

### 2.5 对 `pickFirstBalancer` 的影响

`pickFirstBalancer` 默认不启用健康过滤。启用时同样适用以上规则。`failbackMs` 的试探与这里的半开试探是两件事：前者是粘滞策略回到第一台，后者是健康过滤放行一个刚到期的端点。两者都开时，各自的规则独立生效，测试要覆盖两者同时对第一台生效的情况。

## 3. p2c 在途数从传输层起算

### 3.1 新回调

`EndpointPickResult` 增加可选的 `start?(): void`。

- 运行时在这次尝试真正交给传输层时同步调用它，至多一次：HTTP 在调用 `fetch` 之前；SSE 在调用 `fetch` 之前；WebSocket 在构造套接字之前。时机与第二期甲 `durationMs` 的计时起点相同。
- 构建失败、拦截器短路、`makeResponse`、调用方已取消等没有到达传输层的出口，不调用 `start`，但照常调用 `done`。
- `start` 抛出或返回 thenable 时，与 `done` 相同处理：吞掉异常，接住拒绝，不影响这次尝试。
- 运行时的包装负责「至多一次」，与 `done` 的包装同一处实现。
- 健康过滤把 `start` 原样转给内层。

### 3.2 p2c

- `pick` 时不再加在途数。`start` 时在途数加一。
- `done` 时，只有这次 `pick` 调用过 `start`，在途数才减一，不低于 0。没有 `start` 的 `done` 不减。
- 延迟样本规则不变，照第二期乙说明第 3.2 节。
- 单端点时也照此计数。
