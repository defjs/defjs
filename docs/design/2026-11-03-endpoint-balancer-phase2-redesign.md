# 端点负载均衡第二期：按现场验证修订设计

- 状态：第 7 节六个决定已于 2026-11-03 全部确认，作为规格 `docs/design/2026-11-02-endpoint-balancer.md` 第七稿第 2.3 节。
- 依据：五个领域的现场验证，汇总见 `/tmp/lbexp/field/SUMMARY.md`，各领域报告在 `/tmp/lbexp/field/<领域>/REPORT.md`。
- 第一期已实现，尚未提交。本文只改第二期及以后，以及第一期里还没发布的类型。

## 1. 结论

现场验证暴露的问题，大多数确实出在设计上：第一期把「选台」做对了，但把「这次调用失败」完全留给了用户。浏览器拒连场景里，手写的「失败就试下一台」只有几行，用户可见失败是 0/12，Defjs 默认是 3/12。规格第 11 节把「同一次 HTTP 调用里换一台再试」列为不做，这是这次修订要推翻的核心决定。

另有两项是刻意的取舍，保留；两项是客户端均衡本身做不到的，写进文档。

## 2. 逐条判定

| 现场暴露的限制                                                   | 判定                 | 处理                                 |
| ---------------------------------------------------------------- | -------------------- | ------------------------------------ |

## 3. 提案

### P1 同一次 HTTP 调用内换台

**现状。** 失败的调用直接返回给用户，下一次调用才换台。规格第 11 节明确不做。

**证据。** 浏览器拒连：Defjs 3/12 失败，手写回退 0/12。主区不响应：Defjs 15/15 超时，手写回退 15/15 成功。滚动重启：轮询聚合请求失败 55.42%，加上只针对连接失败的重试降到 6.46%。

**提议。** 新增客户端选项 `withEndpointFailover(options)`，与均衡器分开，均衡器只负责选台。这与 golib 调研的结论一致：均衡与重试是两层，go-kit 用 `lb.Retry` 显式组合，Envoy 把重试放在路由策略里。

```ts
interface EndpointFailoverOptions {
  /** 一次调用最多额外尝试几次。默认 1，上限为候选数减一。 */
  readonly attempts?: number;
  /** 哪些结果触发换台。默认 ["connect-failure"]。 */
  readonly retryOn?: readonly (
    "connect-failure" | "gateway-error" | "attempt-timeout"
  )[];
  /** 允许换台的方法。默认 RFC 9110 的安全方法：GET、HEAD、OPTIONS、TRACE。 */
  readonly methods?: readonly string[];
  /** 单次尝试的超时，见 P3。默认不设。 */
  readonly attemptTimeoutMs?: number;
}
```

规则：

1. 只用于 HTTP。SSE 与 WebSocket 已有重连，重连本身会重新选台。
2. 每次尝试各自 `pick`、各自 `done`。换台时排除这次调用已经试过的端点；候选用完就停。
3. 每次尝试从拦截器链最外层重新开始，`builder` 也重新运行。这样鉴权和链路追踪拿到的是这次尝试的端点，不会把发给 A 的凭据带到 B。`builder` 是同步纯函数，重跑没有副作用。
4. 请求体是 `ReadableStream` 时不换台，因为它只能读一次。
5. 调用方的截止时间覆盖整个调用，不按尝试重置。
6. 连接失败 `connect-failure` 指 `NET_UNREACHABLE`。网关错误 `gateway-error` 指状态码 502、503、504，取自 Envoy 的同名重试条件。不包括 500：那通常是应用错误，换台也一样失败。
7. 用户最终拿到的元组，是最后一次尝试的结果。

**默认值，待确认。** 推荐默认启用，只对安全方法、只在连接失败时、最多额外一次。理由是：安全方法按 RFC 9110 定义可以重发；浏览器里连接被拒绝时，请求不可能已被服务器处理。gRPC 的透明重试同样默认开启，也只限于请求肯定没有送达的情况。

**代价。** 安全方法如果被应用误用于有副作用的操作，会被重发一次。可以用 `methods: []` 关闭。

### P2 pick_first 在网关错误时也换台

**现状。** 只有 `NET_UNREACHABLE` 换台，502 和 503 各 15/15 不换台。

**提议。** pick_first 的前进条件改为：`NET_UNREACHABLE`，或状态码 502、503、504。500 与其他 5xx 不前进，理由同 P1 第 6 条。与 P1 一起配置 `gateway-error` 时，这次调用还能当场换到下一台。

### P3 单次尝试超时与握手超时

**现状。** 只有调用方的整体截止时间。到期后整个调用失败，不会去试下一台。WebSocket 和 SSE 没有握手超时。

**提议。**

- HTTP：P1 的 `attemptTimeoutMs`。到期只中止这一次尝试，`done` 收到 `{ attempted: true, code: "NET_TIMEOUT" }`。`retryOn` 含 `attempt-timeout` 时换台，否则把超时返回给用户。
- SSE 与 WebSocket：重连选项增加 `connectTimeoutMs`，从发起连接到收到响应头或 `open` 为止。到期视为这次尝试连接失败，`done` 收到 `{ attempted: true, code: "NET_UNREACHABLE" }`，按重连规则重新选台。会话建立之后不再受它约束，所以不会像整体截止时间那样把正常的长连接杀掉。

### P4 本机离线时不归因

**现状。** 浏览器断网时 `fetch` 同样报 `NET_UNREACHABLE`，健康的主区被换成备用区。

**提议。** 一次尝试以 `NET_UNREACHABLE` 结束时，如果 `globalThis.navigator?.onLine === false`，`done` 收到 `{ attempted: false }`，P1 也不换台。只认严格等于 `false`：`true` 不能证明网络可用，服务端运行时通常没有这个字段。没有 `navigator` 的环境行为不变。

### P5 用 `failbackMs` 回切

**现状。** 原稿的 `failback` 必须同时配置健康过滤，主区恢复后要等 30 秒摘除期结束。现场 30/30 次仍走备用区，每次多约 120 毫秒。

**提议。** 改为 `pickFirstBalancer({ failbackMs })`。离开第一台之后，经过 `failbackMs`，下一次 `pick` 先试第一台一次。成功就留在第一台；以 `NET_UNREACHABLE` 失败就前进，并重新计时。时刻在 `pick` 里用 `Date.now()` 判断，不创建计时器。不再依赖健康过滤。配合 P1，这次试探失败时用户也看不到。默认不开启。

### P6 轮询与 p2c 默认启用健康过滤

**现状。** 健康过滤要显式配置。没有它时，滚动重启期间轮询会反复打到已下线的副本。

**提议。** `roundRobinBalancer` 与 `p2cBalancer` 默认带健康过滤，使用第 5 节的默认判据，`outlierDetection: false` 可以关闭。pick_first 不需要，它自己会换台。

**依据与代价。** Envoy 和 gRPC 默认都不开启被动摘除，这一条偏离业界。偏离的理由是现场数据：服务端副本池正是轮询和 p2c 的场景，而在这个场景下不摘除，滚动重启的聚合失败率是 55.42%。代价是多一层状态和每次 `pick` 的过滤开销。

### P7 p2c 的延迟在传输边界测量

**现状。** 第二期原稿用 `pick` 到 `done` 的时间作为延迟样本。现场测得，前后各 80 毫秒的拦截器会把一次几乎为零的请求记成 163 到 169 毫秒，重试也会被混进去。

**提议。** `EndpointDoneInfo` 增加可选字段 `durationMs`：只对 HTTP，从结果被采用的那次尝试调用传输层开始，到收到响应头为止。p2c 只用这个字段，没有它就不产生延迟样本。这和 tower 的 PeakEwma 一致，它测的也是到响应开始返回为止。

## 4. 保留的取舍

**打开后被异常断开，不算端点不可达。** WebSocket 关闭码 1006、SSE 读体中断，都可能来自良性原因：负载均衡器的空闲超时、单条连接被回收、移动网络切换。如果把它们当作端点故障，pick_first 会在几个健康节点之间来回漂移。现场测得的代价是多一次很快失败的尝试，WebSocket 约多 23 毫秒。P3 的握手超时能保证这次尝试不会卡住。

**SSE 正常结束不重连。** 这是 SSE 现有的契约，与选台无关。写进 SSE 指南：长期订阅的应用要监听 `closed`，带着游标重新调用。

## 5. 客户端做不到的

**长连接的再平衡。** 每个客户端只在自己的连接断开时重新选台，不知道其他客户端的分布。现场 50 个 WebSocket 客户端经过一轮按轮询顺序的滚动部署，最后全部落在同一台。业界在服务端解决这个问题，例如 gRPC 的 `MaxConnectionAge`：服务端定期让连接自然到期，客户端重连时重新分布。文档写明这一点，并建议服务端设置连接最长寿命。

## 6. 修订后的分期

| 期   | 内容                                                                                 |
| ---- | ------------------------------------------------------------------------------------ |
| 二甲 | P1 换台、P2 网关错误、P3 两种超时、P4 离线、P5 `failbackMs`、P7 的 `durationMs` 字段 |
| 二乙 | 健康过滤（第 5 节）、P6 默认值、`p2cBalancer`（用 P7 的样本）                        |
| 三   | 照原计划：`ringHashBalancer`、`XXH64`、`RequestOptions.hashKey`                      |

先做二甲：它直接消除现场最常见的用户可见失败，而且不需要健康过滤的状态机。

## 7. 需要确认的决定

1. 推翻规格第 11 节「同一次 HTTP 调用里不换台」，采用 P1。
2. P1 默认启用：只对安全方法、只在连接失败时、最多额外一次。
3. P6 让轮询与 p2c 默认启用健康过滤，偏离 Envoy 和 gRPC 的默认值。
4. P2 的 pick_first 前进条件加入 502、503、504。
5. P5 用 `failbackMs` 取代原稿必须配合健康过滤的 `failback: true`。
6. 分期改为二甲、二乙、三。
