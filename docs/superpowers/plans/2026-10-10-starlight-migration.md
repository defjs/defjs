# Starlight Migration Implementation Plan

> Superseded by the [Fumadocs implementation plan](2026-10-10-fumadocs-migration.md). Do not execute the Starlight tasks in this document.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. If the user chooses subtask execution, then use superpowers:subagent-driven-development. The checkboxes below track implementation progress; this round does not execute application development.

**Goal:** Keep the existing documentation content in 11 languages, migrate the site to Starlight, build an API module that centrally presents type information, and unify repository-wide Bun type checking.

**Architecture:** Use Starlight's native documentation capabilities, Sidebar Topics, and the LLM plugin; reuse the existing API inventory, link checking, and recipe tests. Documentation code blocks are checked by Bun in independent temporary files, and library declaration files continue to be generated by the existing tsdown/TS7 pipeline.

**Tech Stack:** Bun 1.4.3, TypeScript 7.0.2, Astro 7.3.8, Starlight 0.42.6, Sidebar Topics 0.9.0, starlight-llms-txt 0.12.0, and the existing Oxlint/Oxfmt/Vitest/Playwright.

**Spec:** [Development specification](../specs/2026-10-10-starlight-migration-design.md). Read both the specification and this plan before execution.

## Global Constraints

- Repository-wide type checking uses Bun uniformly, covering each package, tests, scripts, configuration, and compilable documentation TS/TSX examples.
- Development, checking, and build runtimes require at least Bun 1.4.3; continue using the existing Bun lockfile and CI.
- Remove documentation Twoslash and its TS6 dependency. The current library build still depends on TS7 to generate `.d.ts`; this effort does not change the declaration generation approach.
- Deploy only at the root path of the official primary domain. Old URLs, `.html` paths, old anchors, and subpath deployments have no compatibility requirements; internal links on the new site must be valid.
- The 385 source documents, 11 languages, 162 API catalog display entries, and existing example semantics must each have a complete destination.
- The status of the Q1 domain and the Q2 template-check boundary follows the specification; unanswered items must not be treated as approved without authorization.
- Do not automatically commit, push, create a PR, publish packages, or deploy. After the user authorizes development, choose an isolated workspace according to the worktree skill; do not create the application project during the preparation phase.

## Review Focus

| Input/condition most easily missed                                                                       | Expected behavior and owning task                                                                                                |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Multi-file examples, hidden declarations, and duplicate filenames in the source                          | Each example keeps an independent context; displayed content and checked content correspond correctly. Tasks 2/3.                |
| Generic angle brackets, backticks, code inside MDX Tabs, and translation differences                     | Extracted code is preserved verbatim; divergent versions must not be incorrectly deduplicated. Task 2.                           |
| Multiple API entries sharing one original anchor, slug conflicts, or missing translations                | Every entry can reach a complete description, shared content is not lost, and existing translations do not regress. Task 4.      |
| Language switching, RTL, no JS, keyboard operation, and empty search results                             | Base content is readable, interactions have labels and feedback, and links stay in the target language. Tasks 3/4/7.             |
| Type checking missing files, empty input, a missing official domain, or a changed build output directory | Checks fail explicitly or report the missing condition, and do not produce false passes or incorrect public URLs. Tasks 1/2/5/6. |

## Task 2: Implement documentation example extraction and Bun type checking

**Files:** Create `doc/scripts/code-examples.ts`, `doc/scripts/check-examples.ts`, `doc/test/code-examples.test.ts`, and the necessary example-context data; modify `doc/package.json` and `doc/src/content.config.ts`.

**Interfaces:** `readCodeBlocks(source: string): CodeBlock[]` returns `language`, `code`, `info`, and `line`; `collectExampleProjects(path: string, source: string): ExampleProject[]` returns the original page location, language, relative filename, and content. A non-zero exit from the CLI `bun scripts/check-examples.ts` means an example error, empty input, or a missing classification.

- [ ] Write assertions for the following regression scenarios and observe them fail: `<>&` inside generics and strings is preserved as-is; triple/quadruple backticks and tilde fences are correct; code inside MDX Tabs is extracted; the original fence info is not lost.
- [ ] Write assertions for independent blocks, two independent examples with the same filename, a relative import from `users-sdk.ts` to `app.ts`, and hidden Vue `App.vue.d.ts` context: file grouping is correct, and displayed content does not mix in helper declarations.
- [ ] Implement extraction from the existing source code, and do not let the displayed example and the checked example become two independently handwritten copies. The implementer may choose the parser; prefer native Bun capabilities, and the known missing complete info-string must be supplied.
- [ ] For complete TS/TSX examples, construct temporary projects, reference workspace library source through `paths`, deduplicate by context, and call `bun check`; do not depend on a pre-generated `dist`. Confine temporary directories to directories created for this run, clean them up afterward, and map diagnostics back to the page and code block.
- [ ] Explicitly classify API signature sketches and context fragments; complete examples enter checking by default. Any skip must have a specific source and reason, and must not use `noCheck` or a wildcard exclusion to skip all APIs.
- [ ] Add CLI negative cases: correct TS/TSX exits 0; assigning a number to a string exits non-zero and locates the original page; an error that appears only in a different translation also fails; an empty document collection fails.
- [ ] Run `bun test doc/test/code-examples.test.ts`. Handle the 33 Vue code blocks according to the plan confirmed by Q2; before confirmation, do not mark them as having completed static checking.

## Task 4: Build the API index and detail experience

**Files:** Migrate/extend `doc/src/data/api-catalog.ts`; create API components, `doc/src/scripts/api-filter.ts`, `doc/test/api-catalog.test.ts`, and per-language API index and detail content.

**Interfaces:** `ApiEntry` contains `package`, `name`, `kind`, `slug`, and `related`; `filterApiEntries(entries: readonly ApiEntry[], query: string, packageName: string, kind: string): ApiEntry[]` uses an empty string to mean no filter. The catalog keeps the identity of the 162 display entries and does not use the old anchor as the sole identity.

- [ ] Write failing tests for case-insensitive queries, combined package/kind filters, no results, and duplicate slugs; assert that a combined filter returns the intersection.
- [ ] Check public exports and fill the catalog with real kinds. Keep existing packages and entries; old shared anchors must be mapped explicitly to a new detail or a shared description in the migration map.
- [ ] Create a catalog and details that can be read statically; client-side filtering uses only browser TS. Inputs have accessible names, result changes have perceivable feedback, and query strings are not concatenated into `innerHTML`.
- [ ] Organize handwritten API content into details, keep shared descriptions and related guides, and make type references navigable. Supplemental metadata may be checked against source, but do not invent descriptions or batch-generate translations automatically.
- [ ] Add catalog/content consistency tests: all 162 entries have non-empty destination content, destinations in every language resolve, `related` references exist, and routes do not conflict.
- [ ] Bun unit tests read ordinary TS catalog data and source content files, and do not directly import Astro's `astro:content` runtime virtual module.
- [ ] Run `bun test doc/test/api-catalog.test.ts`; after the actual build, verify one example each of `createClient`, `ClientOption`, `struct.parse`, and the React/Vue exports.
