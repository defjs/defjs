# OpenTelemetry server

中间件插件：以 Core 拦截器对每次操作调用及其 HTTP / SSE / WebSocket 传输做出站插桩。它**不会**初始化 OpenTelemetry SDK，也**不是**入站服务端插桩。

见 [OpenTelemetry server 指南](/zh-Hans/docs/integrations/opentelemetry-server)。

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

提供 `tracer`、`meter` 或 `logger` 时先追加一个操作拦截器，再为每种启用的传输追加一个拦截器，顺序为 HTTP、SSE、WebSocket。在 `createClient` 时应用，每个 Client 一次。`options` 必填；传 `{}` 会安装只做上下文传播的传输拦截器。

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`、`meter` 和 `logger` 都是可选的。不传 `propagator` → W3C Trace Context + Baggage。

每次操作调用都会从调用开始观察到它的元组：一个名为 `defjs.operation.name`（例如 `GET /orders/:id`）的 `INTERNAL` 操作 Span，失败时其 `error.type` 为 Fault 代码；一条 `defjs.client.operation.duration` 样本；失败时一条 `WARN` 日志。每次 HTTP 尝试以及每个 SSE 或 WebSocket 连接，都会在它之下得到一个 `CLIENT` 传输 Span。没有活跃父 Span 的调用会开启自己的 trace；保留哪些由 SDK 的采样器决定。

省略 `tracer` 时，插件不创建本地 span，不调用 `trace.getTracer(...)`、`startSpanHook`、`requestHook` 或 `responseHook`。传入的 `meter` 和 `logger` 独立工作。上下文传播仍转发提取后的父 context；WebSocket 的 `queryPropagation` 仍默认为 `false`。

HTTP、SSE、WebSocket 默认开。某个传输传 `{ enabled: false }` 就跳过。

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| 字段                      | 默认值                      | 作用                                                                     |
| ------------------------- | --------------------------- | ------------------------------------------------------------------------ |
| `tracer`                  | 无                          | 不传就没有本地 span，也没有 span hook。                                  |
| `meter`                   | 无                          | 不传就不记录该包的指标。                                                 |
| `logger`                  | 无                          | 来自 `@opentelemetry/api-logs` 的 `Logger`。不传就不发出诊断 LogRecord。 |
| `propagator`              | W3C Trace Context + Baggage | 提取父 context，并注入出站 context。                                     |
| `includeErrorDiagnostics` | `false`                     | 在失败的 span、`exception` 事件和失败日志上导出错误消息和堆栈。          |
| `http`                    | `{}`                        | HTTP 传输选项。                                                          |
| `sse`                     | `{}`                        | SSE 传输选项。                                                           |
| `webSocket`               | `{}`                        | WebSocket 传输选项。                                                     |

`enabled` 默认为 `true`；只有 `enabled: false` 才会关闭某个传输，同时关闭该传输上各次调用的操作遥测。

仅在传入 `tracer` 时运行 Span Hook。`startSpanHook` 在为对应 HTTP、SSE 或 WebSocket 传输创建 Span 前同步运行。返回的属性在内置属性之后应用，因此应用可以覆盖 `url.full` 或其他初始值。如果它抛出异常，Defjs 会用内置属性创建 Span 并继续请求；`requestHook` 与 `responseHook` 在 Span 创建之后运行。两者都不会被 await：抛出或 reject 不会阻塞或使操作失败。

Hook 作用于传输 Span；操作 Span 没有 Hook。`span.isRecording()` 为 true 时，Hook 失败会记录 `defjs.otel.hook.error` 与 `exception` 事件。`exception` 事件只携带 `exception.type`（类名，不是 Defjs 的 Fault 代码），除非开启 `includeErrorDiagnostics`，否则不携带 `exception.message` 或 `exception.stacktrace`，因为运行时错误文本可能包含完整请求 URL 或响应 body 片段；传输失败时记录的 `exception` 事件也遵循同一规则。Span 未 recording（已结束或未采样）时，失败通过 `diag.error` 交给 OpenTelemetry 诊断 logger。应用必须用 `@opentelemetry/api` 的 `diag.setLogger(...)` 配置接收通道；默认不会自动输出。本包不初始化 SDK，这个诊断也不是独立的 SDK `LogRecord`。

`responseHook` 接收传输返回的内容：HTTP 为 `HttpResponse`，SSE 为启动成功后的流句柄，WebSocket 为打开后的会话。它的第三个参数是原始请求。

默认情况下，`url.full` 只把 `request.endpoint` 相对可选的 `request.baseEndpoint` 解析，不追加 `request.query`。这条边界不是查询脱敏。按照 OpenTelemetry 语义约定的要求，端点 userinfo 中的凭据会被替换为 `REDACTED:REDACTED`，默认敏感查询键（`sig`、`Signature`、`AWSAccessKeyId`、`X-Amz-Signature`、`X-Amz-Credential`、`X-Amz-Security-Token`、`X-Goog-Signature`）的值会被替换为 `REDACTED`，但包内没有其他内置脱敏器或敏感键策略。`startSpanHook` 返回的 `url.full` 会以同样方式脱敏，但应用通过 `requestHook` 或 `responseHook` 中的 `Span` 对象写入的 URL 不会被拦截，因此请显式构造，并按需脱敏：

</include>

`webSocket.queryPropagation`（仅 WebSocket）默认 `false`。只有接受把 trace context 放进 WebSocket URL 时才打开。

## Logger 诊断

顶层 `logger?: Logger` 使用 `@opentelemetry/api-logs` 接口，而不是应用日志记录器。它可选，也可单独使用。Defjs 从不获取全局 logger，也不管理其 provider。每个失败的操作调用发出一条 `WARN` `LogRecord`（严重级别 13），每个打开后失败的 SSE 流或 WebSocket 会话也发出一条，消息均固定：

| 结果                                                       | 事件                                                              | 属性                                                                                                                |
| ---------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 操作调用以 `NET_ABORTED` 之外的 Fault resolve              | `defjs.client.operation.exception`                                | `defjs.operation.name`、`error.type`（Fault 代码）、`exception.type`、`defjs.meta.*`                                |
| SSE 流或 WebSocket 会话以错误结束，包括 `closed` 被 reject | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address`、`server.port`、`exception.type`、`defjs.meta.*`、`defjs.sse.fault.code` 或 `websocket.close.code` |

成功、被后续尝试恢复的重试尝试、正常关闭、EOF、服务器发来的 WebSocket 关闭帧（无论 code 是什么）以及调用方取消都不产生 LogRecord。没有关闭帧的 WebSocket 突然断开（1006）会在每个运行时上以 error 结束会话，并记录一次。操作记录在操作 Span 的上下文中发出。

开启 `includeErrorDiagnostics: true` 后，每条记录还会携带 `exception.message` 和 `exception.stacktrace`；对于操作调用，它们是 Fault 的 `message` 和 `stack`。错误的 cause 链和可枚举字段从不导出，但消息本身不会被过滤：Fault 的消息往往就是其 cause 的消息，平台错误文本也可能引用请求 URL。过滤、exporter、flush 与 shutdown 由应用负责。

完整的日志和第三方日志库案例见 [OpenTelemetry 指南](/zh-Hans/docs/integrations/opentelemetry-server#logs-and-third-party-loggers)。
