<ApiReference identity="@defjs/core:withSSEReconnect" />

```ts
function withSSEReconnect(options: ClientSSEOptions['reconnect']): ClientOption
```

配置 SSE 流失败后的自动重连。重连是可选开启的：没有这个 option，失败的流不会重试。传入 `undefined` 会清除之前的设置。

```ts
type SSEReconnect = {
  attempts?: number
  delayMs?: number
  factor?: number
  jitter?: number
  maxDelayMs?: number
  shouldReconnect?: (context: {
    attempt: number
    cause?: unknown
    lastEventId: string
    method: string
    open?: { response: { status: number; statusText: string; url: string }; url: string }
  }) => boolean | Promise<boolean>
}
```

- `attempts` 是每次连接中断的重试预算。设了 `reconnect` 时默认为 `3`，`0` 表示禁用重试。成功握手后会重置预算、回调中的 `attempt` 和退避指数。省略它并不表示单次中断期间可以无限重试。反复成功打开后立刻遇到可重试的流失败，会按当前基础延迟持续重连（受 jitter 和上限约束），因为每次打开都会重置预算；用 `shouldReconnect` 停止它们。正常 EOF 仍然是终止性的。
- 未提供 `shouldReconnect` 时，只有 `GET`、`HEAD`、`OPTIONS`、`PUT` 和 `DELETE` 请求会重连。提供后，所有请求方法是否重连都由回调的返回结果决定，包括 `POST`；上下文中的 `method` 用来区分端点。返回 `false` 即停止针对本次失败的重试。该回调在检查重试次数上限之前运行。
- 请求体为 `ReadableStream` 的请求不会重连，也不会调用 `shouldReconnect`。
- `delayMs`、`factor`、`jitter`（0 到 1）和 `maxDelayMs` 决定退避延迟。`factor` 默认为 `1`，`jitter` 默认为 `0`。`maxDelayMs` 限制抖动和取整后的最终延迟。未配置上限时，仍受平台计时器上限 `2_147_483_647` 毫秒约束。基础延迟为零时始终为零；有效数字在计算中溢出时会被限制在这些上限。
- `delayMs` 只是起始的基础延迟（默认 `1000`）。服务器发来的 `retry:` 字段（仅限数字，单位毫秒）会在之后的尝试中取代它。
- 最后一个事件 ID 会在下一次尝试中以 UTF-8 字节写入 `Last-Event-ID` 再次发送。空的 `id:` 会清除它；包含 NUL 的 ID 会被忽略。
- 重连选项在 interceptor 或 Fetch 运行前校验：`attempts` 必须是非负安全整数；`delayMs` 和显式提供的 `maxDelayMs` 必须是非负有限数；`factor` 必须是正的有限数；`jitter` 必须是 0–1 范围内的有限数。无效值会在执行时返回 `REQ_OPTIONS_INVALID`。
