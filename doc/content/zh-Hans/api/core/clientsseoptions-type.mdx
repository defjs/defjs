<ApiReference identity="@defjs/core:ClientSSEOptions" />

```ts
interface ClientSSEOptions {
  handle?: FetchHandle
  onInvalidEvent?: (context: {
    reason: 'missing-struct' | 'validation-failed'
    message: { id: string; event: string; data: string }
    cause?: unknown
    signal: AbortSignal
  }) => unknown
  reconnect?: {
    attempts?: number
    delayMs?: number
    factor?: number
    jitter?: number
    maxDelayMs?: number
    shouldReconnect?: (context: {
      attempt: number
      cause?: unknown
      lastEventId: string
      method: string
      open?: { response: { status: number; statusText: string; url: string }; url: string }
    }) => boolean | Promise<boolean>
  }
}
```

- **handle** — 打开流的 fetch 实现。自定义 handle 收到的是一个 `Request`。
- **onInvalidEvent** — 事件没有匹配的 struct 且没有 `default` struct（`'missing-struct'`），或事件数据校验失败（`'validation-failed'`）时调用。该事件会被跳过。hook 抛出的错误不会关闭流。
- **reconnect** — 需主动开启。不设置则流永远不会重连。`attempts` 默认为 **3**；`attempts: 0` 表示禁用重试，省略 `attempts` 并不是无限次。`delayMs` 是第一次的延迟，默认 1000，服务器发来的 `retry:` 值会取代它。`factor` 在每次尝试后乘到延迟上，默认为 1。`jitter` 是 0-1 的乘性因子，与 WebSocket 相同，默认为 0。`maxDelayMs` 默认不设上限。未提供 `shouldReconnect` 时，只有 `GET`、`HEAD`、`OPTIONS`、`PUT` 和 `DELETE` 请求会重连；提供后，所有请求方法是否重连都由回调的返回结果决定，回调上下文中包含 `method`。请求体为 `ReadableStream` 的请求不会重连。一旦收到过事件 id，之后每次重连都会在 `Last-Event-ID` header 里带上它。

用 `withSSEHandle`、`withSSEOnInvalidEvent` 和 `withSSEReconnect` 设置这些选项。不使用 `withSSEReconnect` 就不会重试。
