# 错误

操作会把可判别的 `Fault` 放在元组第一项——声明过的失败不抛出异常。

## FaultCode

<ApiSignature name="FaultCode" />

一个封闭集合。第一个 `_` 之前的部分是类别；没有单独的 `kind` 字段。集合保持封闭，`switch (fault.code)` 才能穷尽——扩展通过 `cause` 报告自己的细节，而不是新增代码。

## FaultClass

<ApiSignature name="FaultClass" />

`FaultClass<FaultCode>` 是 `'CAP' | 'ENV' | 'EXT' | 'HTTP' | 'NET' | 'REQ' | 'RES'`。

## Fault

<ApiSignature name="Fault" />

对 `fault.code` 做 switch。

### FaultOf

<ApiSignature name="FaultOf, Fault" />

`FaultOf` 就是 `Fault`，只是用解码后的错误 body 类型表示，而不是用产生它的 struct。`HttpAwaitResult` 和各 `Fault` 工厂处理解码后的值，所以使用这种形式。

每个变体都是名为 `DefjsFault` 的原生 `Error`，所以 `String(fault)` 给出 `DefjsFault: <message>`。`code` 和各变体元数据——`status`、`response`、`data`——都是可枚举的自有属性。原生 `cause` 链不可枚举。

默认 struct 消息使用 `received <kind>`，从不包含接收到的值，例如 `Expected number at email, received string`。`RES_DECODE_FAILED` 底层的 JSON `SyntaxError` 会给出消息 `Response body could not be decoded`。issue 路径是结构性的，并保留 record 键：`struct.record(...)` 可能产生 `Expected number at alice@example.com, received string`，因此键在默认消息、`prettify()` 和 `String(fault)` 中仍可能敏感。原始 `StructIssue.received` 和解析器 cause 仍然敏感；自定义 `errorMap` 与扩展消息按原样使用，记录日志前需要审查。

只有在把 `fault.cause` 收窄到 `StructError` 之后，才能调用 `format()`、`flatten()` 或 `prettify()`；这些辅助函数不会被复制到 `Fault` 上。

### HttpStatusFault

<ApiSignature name="HttpStatusFaultOf, HttpStatusFault" />

任何非 2xx 状态。定义声明了 `error` 且 body 解码成功时，`data` 就是该 body，`response` 也携带它。省略 `error` 时 body 从不读取，因此 `data` 为 `undefined`，`response` 只有元数据。

### DecodeFault

<ApiSignature name="DecodeFaultCode, DecodeFault" />

响应到达了，但无法按声明读取。`response` 只有元数据：body 是解码后的值，而失败的是解码，所以没有 `body` 字段可用。细节在 `cause` 上——struct 不匹配时是 `StructError`，表示形式不可读时是解析器失败。

### PreflightFault

<ApiSignature name="PreflightFaultCode, PreflightFault" />

所有可能在响应存在之前就失败的情况：`REQ_*`、`NET_*`、`EXT_*`、`CAP_*`、`ENV_UNSUPPORTED`。传输层有元数据可报之前，`response` 是 `undefined`，比如下载中途被截断的 body。

无效的 `withRetry` 选项会在 HTTP 传输开始之前返回 `REQ_OPTIONS_INVALID`，消息为 `Invalid retry options`。这包括非对象的策略、不是至少为 1 的安全整数的 `maxAttempts`，以及无效的条件、方法、超时、退避或预算设置。省略 `withRetry` 会关闭重试。`withRetry()` 与 `withRetry(undefined)` 的行为与 `withRetry({})` 相同。`withRetry({ maxAttempts: 1 })` 会在启用之后关闭重试。

### AnyFault

<ApiSignature name="AnyFault" />

任何 `Fault`，不论其解码后的错误 body 是什么类型。用于只做分类、不关心是哪个操作产生的处理函数；body 类型重要时优先使用 `Fault<typeof yourErrorStruct>`。

## createPreflightFault()

<ApiSignature name="createHttpStatusFault, createUndecodedHttpStatusFault, createDecodeFault, createNetworkFault, createPreflightFault" />

`createHttpStatusFault` 接收一个已经携带解码后 body 的响应；`createUndecodedHttpStatusFault` 只接收元数据，用于未声明 `error` 的定义。

`createNetworkFault` 用 [`isAbortCause`](/zh-Hans/api/core/isabortcause) 判断 `NET_ABORTED`，用 [`isTimeoutCause`](/zh-Hans/api/core/istimeoutcause) 判断 `NET_TIMEOUT`：两者都能识别来自任意 Core 副本的带标记哨兵；`isAbortCause` 还能识别名为 `AbortError` 的 `DOMException`，`isTimeoutCause` 还能识别名为 `TimeoutError` 的 `DOMException` 或 `Error`。其他情况都映射到 `NET_UNREACHABLE`。`createPreflightFault` 直接接收代码；没有 `cause` 时，代码成为消息。

所有工厂都返回带上述结构化字段的原生 `Error` 实例；它们不造普通对象错误，`String(fault)` 也不需要适配器。

## 哨兵

## ERR_ABORTED

## ERR_TIMEOUT

<ApiSignature name="ERR_ABORTED, ERR_TIMEOUT" />

abort 和 timeout 共享的 `Error` 哨兵对象，用作 `cause`。从 HTTP 拦截器中抛出其中一个，调用会以 `NET_ABORTED` 或 `NET_TIMEOUT` 结算。SSE 和 WebSocket 拦截器会把任何抛出（包括这两个）都报告为 `EXT_INTERCEPTOR_FAILED`。

这些哨兵带有不可枚举的 `Symbol.for('defjs.cause.aborted')` 和 `Symbol.for('defjs.cause.timeout')` 标记。分类不依赖哨兵的对象身份，也不受之前无关执行的影响。

## 原因检查

<ApiSignature name="isAbortCause, isTimeoutCause" />

[`isAbortCause`](/zh-Hans/api/core/isabortcause) 识别带中止标记的 `Error` 或名为 `AbortError` 的 `DOMException`。[`isTimeoutCause`](/zh-Hans/api/core/istimeoutcause) 识别带超时标记的 `Error`，或名为 `TimeoutError` 的 `DOMException` / `Error`。传入 `fault.cause` 来分类底层值；这些函数不会解包 fault，也能识别另一份 Core 的哨兵。

## ERR_NO_CANDIDATE

## isNoCandidateCause

<ApiSignature name="ERR_NO_CANDIDATE, isNoCandidateCause" />

没有候选端点可选时，`ERR_NO_CANDIDATE` 只作为 `REQ_BUILD_FAILED` 的 `cause` 出现。它不新增 `FaultCode`。这个哨兵带有不可枚举的 `Symbol.for('defjs.cause.no-endpoint')` 标记。[`isNoCandidateCause`](/zh-Hans/api/core/isnocandidatecause) 能识别另一份 Core 副本上的该标记，方式与 [`isAbortCause`](/zh-Hans/api/core/isabortcause) 识别中止相同。传入 `fault.cause`。它不会解包 fault。

见 [错误指南](/zh-Hans/docs/errors)。
