# HTTP

声明一个带类型的请求，再用 Client 和 input 调用该操作。

## defineRequest()

<ApiSignature name="defineRequest" />

- **definition** — `method`、`path`，可选 `input` struct，可选 `output` 和 `error` struct，可选 `operation`。声明了 `input` 就始终需要显式 `builder`。`input` 只定义参数；位置完全由 `builder` 决定。只有没有 `input` 的定义可以省略 `builder`。这些 `definition` 成员记录在 [`RequestDefinition`](/zh-Hans/api/core/requestdefinition-type)。`builder` 恰好在声明 `input` 时必填。
- **返回** 一个操作。调用方式是 `getOrder(client, input)`；未声明 input 时是 `health(client)`。整个 input struct 可选时，可以省略 input 参数。调用它即开始请求。没有第三个选项参数。

<include cwd>examples/api/define-request.ts#example</include>

`output` 是 2xx body 的单一 struct；`error` 是每个非 2xx body 的单一 struct。两者都不按状态码分键。省略哪个，那个 body 就根本不会被读——见
[声明即断言](/zh-Hans/docs/design-decisions#declaration-is-an-assertion)。

调用该操作会返回一个 promise，其值是 [`HttpAwaitResult`](/zh-Hans/api/core/httpawaitresult-type) 描述的元组。单次调用选项通过从 [`RequestOptions`](/zh-Hans/api/core/requestoptions-type) 派生 Client 传入。HTTP 读取 `signal`、`retry` 和进度回调，忽略其他字段。

未声明 `error` struct，或声明的 `error` body 能解码时，非 2xx 状态为 `HTTP_STATUS`。声明过 `error` 时，Fault 的 `data` 是解码后的错误 body，否则为 `undefined`。如果声明的 `error` body 无法读取（媒体类型错误、JSON 无效）或与 struct 不匹配，Fault 改为 `RES_MEDIA_TYPE_INVALID`、`RES_DECODE_FAILED` 或 `RES_STRUCT_MISMATCH`，响应状态仍记录在其元数据中。失败时元组第三项为 `undefined`；响应元数据由 Fault 携带。

## fetchHandler()

<ApiSignature name="fetchHandler" />

默认 HTTP 传输。`fetchImpl` 默认是在发送时解析的全局 `fetch`；`withHTTPHandle` 可提供其他实现。未被替换的平台 Fetch 收到 `(url, init)`，被替换的全局实现或自定义句柄收到 `Request`。没有响应到达 Client，或读取声明的 body 失败时，它会 reject，而不是解析为合成响应。

## makeResponse()

<ApiSignature name="makeResponse" />

不发起网络调用即可构造 `HttpResponse`（用于拦截器或测试）。默认 status 为 `0`。2xx 时 `ok` 为 true。返回值会经过与网络响应相同的媒体类型检查和声明 struct；不存在可信短路。

## HttpExecuteOptions

<ApiSignature name="HttpExecuteOptions" />

`HttpExecuteOptions` 是 [`RequestOptions`](/zh-Hans/api/core/requestoptions-type) 的 HTTP 部分：[`UseRequestConfig`](/zh-Hans/api/core/userequestconfig-type)，即 `signal` 加上 `onDownloadProgress`、`onUploadProgress` 和 `retry`。没有 `timeout` 或 `abort` 字段。期限是 `signal: AbortSignal.timeout(ms)`，归类为 `NET_TIMEOUT`。手动中止是 `NET_ABORTED`。`signal` 是本次调用的 signal；要组合 signal，在应用代码中使用 `AbortSignal.any`。没有 Client 级默认期限。其他请求字段（例如 `heartbeat`）会被忽略。

## 类型

### RequestDefinition

`method`、`path`，可选 `input`、`output`、`error`、`operation` 和 `builder`。声明 body 的读取方式由 struct 类型决定。声明了 `input` 就始终需要显式 `builder`。`input` 只定义参数；位置完全由 `builder` 决定。只有没有 `input` 的定义可以省略 `builder`。

### HttpAwaitResult

<ApiSignature name="HttpAwaitResult" />

成功时，只有声明过 `output`，第三项才携带 `body`。失败时它仍是 `undefined`——Fault 已经持有当时存在的响应元数据。

### HttpRequest

规范化后的出站请求：`method`、`endpoint`、`headers`、`body`、`signal`、`operation`、`withCredentials`、`finalizeHeaders`、`downloadProgress` / `uploadProgress`、`baseEndpoint` 和 `query`。拦截器看到它时，`body` 已经是网络值——JSON 时是 JSON 文本字符串——因此 HMAC 和摘要要针对它来签，而不是针对 struct 输入。`query` 是请求发送的唯一查询，类型为 `URLSearchParams`：拦截器可以就地修改它，也可以把替换值传给 `next()`。`builder` 返回 `URLSearchParams` 时，会复制该实例；`withQuerySerializer` 函数返回的字符串会被解析进它。线上形式是 `query.toString()`，即 URL Standard 的 application/x-www-form-urlencoded 序列化，因此空格是 `+`，空的 `query` 不会添加 `?`。`responseType` 和 `errorResponseType` 是只读的：它们由声明的 `output` 与 `error` struct 类型推导而来，不能修改。

### HttpMeta

<ApiSignature name="HttpMeta" />

响应元数据，只要有响应到达 Client 就可用。它**不**带 `body`：只有声明过的 struct 解码出 body 之后，body 才存在。

### DecodedResponse

<ApiSignature name="DecodedResponse" />

body 已按声明的 struct 解码成功的响应。持有这个类型就证明解码确实发生过——这也是解码失败时只报告 `HttpMeta` 的原因。

### HttpResponse

<ApiSignature name="HttpResponse" />

响应没有 body 时，`body` 是 `undefined`；JSON `null` 仍是 `null`。该类型带品牌标记，因此请用 `makeResponse` 构造，不要用对象字面量。这是传输层产出、拦截器看到的网络形态：`body` 是文本或已解析的 JSON，不是解码后的值。对于 JSON 表示，字符串是 JSON 字符串根，不会再次解析；字节和 blob 是原始数据，只解析一次。到达调用方的是 `DecodedResponse`。

### HttpProgressEvent

### HttpProgressFn

`loaded`、`total`、`lengthComputable`。回调可以异步执行。`onDownloadProgress` 或 `onUploadProgress` 抛出异常时，调用会以 `EXT_OBSERVER_FAILED` 失败，抛出的值作为 `cause`；取消仍报告 `NET_ABORTED`，中止原因是超时时报告 `NET_TIMEOUT`。
上传进度只在请求 body 是你传入的 `ReadableStream` 时才会报告。其他任何 body（`Blob`、`File`、`ArrayBuffer`、`FormData`、字符串、`URLSearchParams`）都按构建结果发送，并且在每个运行时上都不会调用 `onUploadProgress`；库从不把 body 转成流。`ReadableStream` body 遵循 Fetch 对流式请求体的规则，无论有没有 `onUploadProgress`：Chromium 和 WebKit 只在 HTTP/2 及以上接受它（HTTP/1.1 上为 `NET_UNREACHABLE`；WebKit 只在 27.2 上做过人工检查；Node.js 和 Bun 接受 HTTP/1.1）；Firefox 不能流式发送请求体（`ENV_UNSUPPORTED`）；在浏览器中，跨源请求需要 CORS 预检，除非浏览器持有缓存的预检结果，因此服务端必须应答 `OPTIONS`；301、302、307 或 308 重定向会在 body 发送一次之后失败，而 303 会变成 GET 并成功。浏览器不发送 `Content-Length`。`fetch` 把这些失败，以及 `fetch` 读取时抛出的源 `ReadableStream`，报告成与不可达端点相同的网络错误，因此负载均衡器对它们收到 `{ attempted: false }`，对抛出异常的进度回调（`EXT_OBSERVER_FAILED`）也一样。因此仅靠流式上传无法发现已宕机的端点，被拒绝的流式上传也从不重试：`ReadableStream` body 会在询问 `shouldRetry` 之前结束重试流程。

流式 body 没有已知长度：除非有效的显式 `Content-Length` 请求头设定了它（浏览器不会发送该请求头），报告的总量未知。`loaded` 统计流中的字节，不代表服务端确认。带非 identity `Content-Encoding` 的下载报告 `total: 0` 和 `lengthComputable: false`；其流字节可能已经解压。

见 [HTTP 指南](/zh-Hans/docs/http) 和 [Client](/zh-Hans/docs/client)。

## RequestEndpoint

`defineRequest` 的返回值。第一个参数是 [`Client`](/zh-Hans/api/core/client-type)。其余参数只是 input。

## BuilderInput

`builder` 看到的、解析后的操作 input。对象节点携带产生它的 struct，因此别名、`Date` 和 `bigint` 编码跟随该值。

## HttpRequestShape

<ApiSignature name="HttpRequestShape" />

四个字段都可选。`query` 是 `URLSearchParams` 或 record；嵌套对象在运行时需要 `withQuerySerializer`。`headers` 是 `HeadersInit`，或由标量、标量数组组成的 record。`path` 为每个 `:name` 片段提供一个标量。

`GET` 和 `HEAD` 的 `body` 是 `never`。其他方法下，它可以是网络值（`string`、`Blob`、`ArrayBuffer`、类型化数组或 `DataView`、`FormData`、`URLSearchParams` 或 `ReadableStream<Uint8Array>`），也可以是 JSON 数据（`number`、`boolean`、`bigint`、`Date`、`null`、数组，或键为字符串的对象）。

## UseRequestConfig

`signal`，加上可选的 `onDownloadProgress`、`onUploadProgress` 和 `retry`。`HttpExecuteOptions` 就是这个切片。没有 `timeout` 或 `abort` 字段。

## RequestSuccessData

从声明的 `output` struct 推出来的成功 body；没声明时是 `undefined`。

## RequestErrorData

从声明的 `error` struct 推出来的错误 body；没声明时是 `undefined`。

## HttpResponseType

`'arraybuffer' | 'blob' | 'json' | 'text'`

由声明的 struct 类型选出（`string` → `text`，`blob` / `file` → `blob`，`arrayBuffer` → `arraybuffer`，其他 → `json`）。不是 `defineRequest` 上的字段。

## MakeResponseOptions

给 `makeResponse` 的字段：`status`、`statusText`、`url`、`headers`、`body`、`request`。
