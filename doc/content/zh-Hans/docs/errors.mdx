# 错误处理

Defjs 遇到入参校验失败、网络异常或响应解码失败时，**不会在调用处 `throw` 异常**。每个操作都会返回一个错误优先的元组 `[err, ...]`：其中 `err` 要么是 `null`，要么是一个带 `code` 判别字段的 `Fault`（本身也是原生 `Error` 实例）。建议统一把错误变量命名为 `err`，像 Go 语言那样在调用后第一时间判断处理。

唯一会直接 reject 抛出 `TypeError` 的情况，是调用方式本身连 TypeScript 类型检查都通不过（例如根本没传 `Client`、或者传入的 `signal` 不是合法的 `AbortSignal`）——这类非法调用不在契约保障范围内。

### 为什么 HTTP 请求失败时 `err` 上也挂着 `response`？

HTTP 请求失败时返回的元组是 `[err, undefined, undefined]`。为了让排查日志或上层错误处理仍然看得到状态码和响应头，Defjs 把拿到的响应元数据（`status`、`statusText`、`headers`、`url`）直接挂在了 `err.response` 上——把 `err` 往外传递时上下文不会丢。

### 推荐做法：每个错误只处理一次

建议把 `[err, data]` 当作 Go 语言的 `(T, error)` 来写，逻辑最清爽：

- **紧接着 `if (err)` 提前返回**：调用完立刻写 `if (err)`，并在 `if` 块内 `return`（后续成功路径不用缩进一层），具体状态码或 `err.code` 分支全部写在 `if (err)` 里面，不要在正常代码流里写 `err?.code`。
- **处理和返回二选一**：一个错误要么在这里消化掉（打日志、弹提示、走兜底），要么包装后向上返回，切忌“既打了一遍日志又往上抛”导致告警重复。通常只在应用顶层（如 `main`、UI 事件处理器、测试断言）打印或弹窗；下层业务 helper 统一返回 `Promise<[Error, undefined] | [null, T]>`，不要靠返回 `undefined`、`null` 或 `false` 暗示失败。
- **单步透传、多步包装**：如果 helper 只调一次 Defjs 操作，可以直接原样 `return [err, undefined]`；如果连续调了好几步，请按步骤命名每个错误变量（如 `putErr`、`listErr`），并用 `new Error("put object", { cause: putErr })` 保留根因。只有像 TanStack Query `queryFn` 这种明确要求 Promise reject 的第三方适配边界，才主动 `throw err`。

## 2. Fault 七大分类与错误码速查

`err.code` 第一个 `_` 前面的前缀代表出错环节（`HTTP`、`REQ`、`NET`、`RES`、`EXT`、`CAP`、`ENV`），所有错误码组成封闭联合类型，方便做完备的 `switch`：

| 类别   | 错误码                                                                 | 什么时候发生与怎么处理                                                                                                                               |
| ------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HTTP` | `HTTP_STATUS`                                                          | 服务端返回非 `2xx` 状态码（`3xx`/`4xx`/`5xx`）；如果操作定义了 `error` struct，解码结果在 `err.data`                                                 |
| `REQ`  | `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`                                | 入参没过 `input` schema、`builder` 抛错、路径非法或 `Request` 构造失败（body 流已被消耗、方法非法、`GET`/`HEAD` 带了 body、带账密 URL 等）。不可重试 |
| `RES`  | `RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED`, `RES_STRUCT_MISMATCH`   | 响应 `Content-Type` 不对、JSON 读取/语法解析失败，或返回字段和声明的 `struct` 对不上                                                                 |
| `NET`  | `NET_ABORTED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `NET_BODY_INCOMPLETE` | 主动取消（`NET_ABORTED`）、等待超时（`NET_TIMEOUT`）、连不上服务（`NET_UNREACHABLE`）或响应流半路断掉（`NET_BODY_INCOMPLETE`）                       |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`     | 自定义拦截器（如传了非法的 `signal` 给 `next()`）、`shouldRetry` 等钩子，或进度/状态观察者回调里抛了错                                               |
| `CAP`  | `CAP_BUFFER_EXCEEDED`                                                  | SSE 帧缓冲区超出允许上限                                                                                                                             |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | 当前运行环境缺少所需 Web API（例如在 Firefox 下流式上传请求体）                                                                                      |

**错误码归因原则（按故障本质归类，不按来源背锅）**：

- 对 HTTP 来说，只要平台构造 `Request` 失败，一律归为 `REQ_BUILD_FAILED`，不管这个非法值来自 `builder`、Client 配置还是拦截器。
- SSE 首次建连与每次重连对非法头、无效 URL 及带账密 URL 同样报 `REQ_BUILD_FAILED`（因为 Bun 会直接放行带账密 URL，所以 Defjs 做了统一前置拦截）。
- 对于库本身不提前拦截、交由运行环境拒绝的情况（如 SSE 用了非法方法、WebSocket 用带账密 URL/无效子协议/不支持的协议），平台拒收后会统一报成 `NET_UNREACHABLE`，原始异常放在 `err.cause`；若换到直接放行的环境（例如 Bun 上的非法 SSE 方法）则会照常发出。
- `EXT_INTERCEPTOR_FAILED` 专指拦截器自己的问题——要么它抛出了异常，要么传给 `next()` 的 `signal` 不是合法 `AbortSignal`。

### 不同错误码上能读到哪些属性

| 错误码        | `status` | `response`                                    | `data`                                 | `cause`                    |
| ------------- | -------- | --------------------------------------------- | -------------------------------------- | -------------------------- |
| `HTTP_STATUS` | `number` | `DecodedResponse<TErr>` 或 `HttpMeta`         | 解码后的 `error` struct 或 `undefined` | 底层原因（如果有）         |
| `RES_*`       | `number` | `HttpMeta`（**绝不会带 `body` 属性**）        | 不存在                                 | `StructError` 或解析器异常 |
| 其他错误码    | 不存在   | 已拿到响应头时是 `HttpMeta`，否则 `undefined` | 不存在                                 | 底层 `Error` 或中止原因    |

## 4. SSE 与 WebSocket 的建连错误 vs. 运行中错误

对于长连接来说，函数返回值里的元组只反映**初始握手有没有成功**；连接打开之后中途出问题，由流/会话对象接管报告：

| 协议          | 启动期失败（直接在元组 `err` 返回）                                                                                         | 打开连接后的失败（返回流/会话之后）                                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **HTTP**      | 全部都在这一次调用的元组里一次性返回                                                                                        | 不适用                                                                                                                                                 |
| **SSE**       | 非 `2xx`（`HTTP_STATUS`，若声明 `error` 且解码失败则是对应解码 Fault），或 `2xx` 但媒体类型不对（`RES_MEDIA_TYPE_INVALID`） | `for await` 异步迭代器直接 reject；`stream.closed` 返回 `{ kind: 'error', code }`                                                                      |
| **WebSocket** | 握手前连不上、构造函数报错或握手期被信号中止                                                                                | 单条消息解析失败只触发 `session.onRuntimeError`（不断线）；致命故障让 `session.receive` reject 并将 `session.closed` 结束为 `{ kind: 'error', cause }` |

## 5. 安全地记日志与排查 `err.cause`

每个 `Fault` 都是标准 `Error`（`err instanceof Error === true`），并带有可枚举的 `code` 属性。其它字段按错误码有无有所不同：只有 `HTTP_STATUS` 同时带 `status`、`response` 和 `data`；`RES_*` 带 `status` 和 `response`；其余只带拿到响应头后的 `response`。

> [!CAUTION]
> **别把整坨 `err` 直接打进日志**：`err.cause`、`err.data`、响应头、完整 URL（可能含 Query 参数）和 `StructIssue.received` 都可能包含用户的隐私数据或敏感信息。生产日志默认只挑安全字段白名单（例如你自己打的 `meta` 标签、`code`、`status` 和耗时）。
