# 错误处理

在 Defjs 中，请求、传输和解码失败不会在调用处抛出异常。每个操作都返回错误优先元组（`[error, ...]`），其中 `error` 要么是 `null`，要么是带类型的 `Fault`（原生 `Error` 实例，由 `error.code` 判别）。

编程误用是例外。它通常以 `TypeError` reject，而不是返回 `Fault`：不是 `AbortSignal` 的 `signal` 选项、`output` 或 `error` 不是 `struct` 的 HTTP 操作，以及不带 Client 调用操作。

### 为什么 HTTP 失败时 `error` 会携带响应元数据？

HTTP 失败时，元组是 `[error, undefined, undefined]`。到达的响应元数据（`status`、`statusText`、`headers`、`url`）直接挂在 `error.response` 上，因此只把 `error` 交给日志记录器或错误处理程序也不会丢失上下文。

## 2. Fault 类别与封闭的代码集合

第一个 `_` 之前的前缀是 Fault 类别（`HTTP`、`REQ`、`NET`、`RES`、`EXT`、`CAP`、`ENV`），完整的 `code` 构成封闭联合，可用于穷尽的 `switch`：

| 类别   | Fault 代码                                                             | 含义与处理                                                                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HTTP` | `HTTP_STATUS`                                                          | 服务端返回了非 `2xx` 状态码（`3xx`、`4xx`、`5xx`），若声明了 `error` struct 则其已被成功解码。                                                                                                                   |
| `REQ`  | `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`                                | 调用方输入校验失败、URL/路径无效、`builder` 抛出，或请求无法构造（HTTP：body 流已被使用、无效或被禁止的方法、GET/HEAD body、无效的 `Content-Type`；HTTP 和 SSE：带凭据的 URL、平台拒绝的请求头值）。绝不可重试。 |
| `RES`  | `RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED`, `RES_STRUCT_MISMATCH`   | 服务端响应破坏了已声明的媒体类型、底层表示或 `struct` 契约。                                                                                                                                                     |
| `NET`  | `NET_ABORTED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `NET_BODY_INCOMPLETE` | 调用方主动取消（`NET_ABORTED`）、请求超时（`NET_TIMEOUT`）、网络连不上，或响应流在传输中途中断。                                                                                                                 |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`     | 应用拦截器、hook 或进度/状态观察者抛出了自身的错误，或拦截器向 `next()` 传入了不是 `AbortSignal` 的 `signal`。                                                                                                   |
| `CAP`  | `CAP_BUFFER_EXCEEDED`                                                  | SSE 帧缓冲区超出了配置的上限。                                                                                                                                                                                   |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | 当前宿主运行时缺少必须的 Web API（如在 Firefox 中尝试流式发送请求体）。                                                                                                                                          |

代码命名的是什么失败了，而不是谁提供了这个值。对 HTTP 而言，平台无法构建的请求是 `REQ_BUILD_FAILED`，无论错误值来自 `builder`、Client 配置还是拦截器。SSE 对请求头值、无效 URL 和带凭据的 URL 适用同一规则，首次尝试和每次重连都一样。库会自行检查最后一种，因为 Bun 会接受这样的 URL 并发送请求。平台可能拒绝的其他值，库在 SSE 和 WebSocket 上并不检查（SSE 上的无效方法；WebSocket 上带凭据的 URL、无效子协议或不支持的 scheme），因此那里的拒绝报告为 `NET_UNREACHABLE`，`cause` 是平台的错误；接受该值的运行时（Bun，对于无效的 SSE 方法）会发送请求。`EXT_INTERCEPTOR_FAILED` 覆盖拦截器自身的行为：它抛出的错误，或不是 `AbortSignal` 的 `signal`（取消通道，不是请求内容）。

### 各 Fault 代码携带的属性

| Fault 代码    | `status` | `response`                                        | `data`                                  | `cause`                        |
| ------------- | -------- | ------------------------------------------------- | --------------------------------------- | ------------------------------ |
| `HTTP_STATUS` | `number` | `DecodedResponse<TErr>` 或 `HttpMeta`             | 解码后的 `error` struct，或 `undefined` | 底层原始原因（若存在）         |
| `RES_*`       | `number` | `HttpMeta`（**绝无 `body` 属性**）                | 不存在                                  | `StructError` 或解析器原始报错 |
| 其他代码      | 不存在   | 若已收到响应头则为 `HttpMeta`，否则为 `undefined` | 不存在                                  | 底层 `Error` / 中止原因        |

## 4. SSE 与 WebSocket 的启动期 vs. 连接建立后异常

对于长连接，操作元组报告**启动期**失败（流或 socket 打开之前）。连接打开后，运行时失败通过句柄或会话生命周期传递：

| 传输          | 启动期失败（在元组中返回）                                                                                                         | 打开后的失败（元组 resolve 之后）                                                                                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **HTTP**      | 所有失败都在操作元组中结算一次。                                                                                                   | 不适用。                                                                                                                                                                                               |
| **SSE**       | 非 `2xx`（`HTTP_STATUS`，或声明的 `error` body 无法解码时的解码 Fault），或内容类型不对的 `2xx` 握手（`RES_MEDIA_TYPE_INVALID`）。 | 异步迭代器直接 reject；`stream.closed` resolve 为 `{ kind: 'error', code }`。                                                                                                                          |
| **WebSocket** | 握手前连接关闭、构造器执行失败，或在握手期间触发取消信号。                                                                         | 非致命的数据帧错误触发 `session.onRuntimeError`；致命错误使 `session.receive` 报错并使 `session.closed` resolve 为 `{ kind: 'error', cause }`。心跳超时和重试耗尽仍使用普通运行时 `Error` 作为 cause。 |
