# 错误处理

处理 404、超时或读不出来的 body，靠的是读 error-first tuple，而不是 catch 抛出。`Fault` 是原生 `Error`（`instanceof Error` 为真），由一个字段判别：`code`。

没有 `kind`。失败的类别就是 code 里第一个 `_` 之前那一段，所以 `NET_TIMEOUT` 是 `NET` 类失败，`RES_STRUCT_MISMATCH` 是 `RES` 类失败。粗分看前缀，精确判断看整个 code。

## 稳定的 code

| 类别   | Code                                                                   | 谁得改                         |
| ------ | ---------------------------------------------------------------------- | ------------------------------ |
| `HTTP` | `HTTP_STATUS`                                                          | 对端回了非 2xx；当业务逻辑处理 |
| `REQ`  | `REQ_INPUT_INVALID`、`REQ_OPTIONS_INVALID`、`REQ_BUILD_FAILED`         | 调用方，或端点声明             |
| `NET`  | `NET_ABORTED`、`NET_TIMEOUT`、`NET_UNREACHABLE`、`NET_BODY_INCOMPLETE` | 没人，或者重试                 |
| `RES`  | `RES_MEDIA_TYPE_INVALID`、`RES_DECODE_FAILED`、`RES_STRUCT_MISMATCH`   | 声明和对端得对上               |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`、`EXT_HOOK_FAILED`、`EXT_OBSERVER_FAILED`     | 你挂到流水线上的代码           |
| `CAP`  | `CAP_BUFFER_EXCEEDED`、`CAP_QUEUE_OVERFLOW`                            | 声明的上限，或者消费方的节奏   |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | 宿主运行时                     |

集合是故意封闭的：这正是 `switch` 能穷尽的原因。扩展要报自己的细节就走 `cause`，不是加新 code。

HTTP、SSE 和 WebSocket 都要求客户端 `endpoint` 是有效的绝对 URL。URL 解析后，路径必须与基础端点同源，且位于其目录内。路径不得是绝对 URL 或协议相对路径，也不得包含 C0 控制字符（包括制表符、CR 和 LF）、反斜杠、`?`、`#` 或越出目录的路径。形似 scheme 的形式和协议相对形式即使带前导空格也会被拒绝；路径内部的普通空格允许，并按 `%20` 发送。缺失、相对或无效的端点，以及非法路径，都会在请求构建时、interceptor 运行前产生 `REQ_BUILD_FAILED`；短路 interceptor 也无法绕过这项检查。传输前还会按相同规则，相对于最终 `req.baseEndpoint` 检查 interceptor 的最终 `req.endpoint`；允许显式切换到另一个有效的绝对基础端点。这些确定性的 URL 错误不会重试。

### 各形状带哪些字段

| Code          | `status` | `response`                                       | `data`                                |
| ------------- | -------- | ------------------------------------------------ | ------------------------------------- |
| `HTTP_STATUS` | 总有     | 总有；只有声明过 `error` 且解码成功时才带 `body` | 解码后的 `error` body，或 `undefined` |
| `RES_*`       | 总有     | 总有，只有元数据——**没有 `body`**                | 没有                                  |
| 其余一切      | 没有     | 只有传输层当时已经拿到元数据时才有               | 没有                                  |

`cause` 带着底层的值：struct 不匹配时是 `StructError`，表示读不出来时是解析器的失败，扩展抛什么就是什么。

HTTP 失败时第三项是 `undefined`：当时存在的响应元数据已经由 fault 带着了。这一点重要，因为你传给 handler、写日志、重新抛出的就是 fault，所以元数据必须跟着它走，而不是搁在它旁边。

SSE 和 WebSocket 的第三项是启动快照，即使启动失败也可能有。handle 或 session 返回之后，后续的失败属于它自己的生命周期——它们永不改写已经定下来的启动 tuple。

## body 怎么读

`ok` 是唯一分流点，且只有一边会解码。`output` 读 2xx body；`error` 读其余一切。省略哪个，那个 body 就根本不会被读。

| 情况                                  | 结果                                           |
| ------------------------------------- | ---------------------------------------------- |
| 2xx，声明过 `output`，body 解码成功   | 成功；`data` 和 `response.body` 都带类型       |
| 2xx，省略了 `output`                  | 成功；`data` 是 `undefined`，响应没有 `body`   |
| 非 2xx，声明过 `error`，body 解码成功 | `HTTP_STATUS`，`data` 带类型                   |
| 非 2xx，省略了 `error`                | `HTTP_STATUS`，`data: undefined`               |
| 媒体类型不是那个表示需要的            | `RES_MEDIA_TYPE_INVALID`，在读 body **之前**报 |
| 字节不是那个表示                      | `RES_DECODE_FAILED`                            |
| 值不符合那个 struct                   | `RES_STRUCT_MISMATCH`（仅 HTTP）               |
| 你**没有**声明的那一侧 body 读不出来  | 整个忽略——见下                                 |

最后一行值得记住。如果你声明了 `output` 而没声明 `error`，那么一个 body 是坏 JSON 的 500，报出来是 `HTTP_STATUS` 加 `status: 500`。你说过你不关心错误 body，这也包括不关心它读不出来这件事。

对于 HTTP，Struct 只应用一次，且在 interceptor 链之后。interceptor 用 `makeResponse(...)` 构造的响应，与真实网络响应经过同一套媒体类型检查、表示转换和 Struct 校验。内置 Fetch 传输在把响应交回链之前，会按声明将 body 读取为 JSON、文本、`Blob` 或字节。只有 JSON 表示要求 JSON 媒体类型和 `JSON.parse`；非 JSON 的文本、blob 和字节都可以是符合声明的有效表示。任何表示都可能读取失败；这里的读取或解析失败会以同样的 `RES_*` 或 `NET_BODY_INCOMPLETE` fault 报出。

`HttpResponse.ok` 只表示 `200 <= status < 300`。传输失败是 fault，绝不是响应——不存在代表它的 status-0 响应。

## 窄化错误 body 的联合

一个 `error` struct 覆盖所有非 2xx 状态，所以形状不同时你会声明一个联合。之后你能拿 `fault.data` 做什么，完全取决于你怎么声明这个联合——库交还给你的，正是你要求的那个类型。

`struct.or(...)` 产出一个普通联合，TypeScript 自己窄化不了。去测你要的那个字段：

<include cwd lang="typescript">
  examples/errors/narrow-by-status.ts#example
</include>

只要 API 支持，最后这种写法值得优先。`fault.status` 是 HTTP 层的数字，代理、网关或 CDN 都能改写它；`data.status` 则通过了你声明的 `error` struct 校验。这只能证明 body 的形状，不能证明它来自后端：代理、网关或 CDN 也能返回符合该形状的 body。

一个不带判别字段、因此窄化不了的联合，是声明本身的属性，不是库的——库交给你的就是你声明的类型。想要窄化，就给 struct 加一个判别字段。

## 启动期与开启之后

SSE 在 resolve handle 之前会校验状态、`text/event-stream` 以及 body 是否存在。非 2xx 在未声明 `error` 或其 body 解码成功时 → `HTTP_STATUS`。已声明的握手 body 无法读取、无法解析或未通过 Struct 校验时 → `RES_DECODE_FAILED`；Struct 失败会以 `StructError` 作为 `cause`。媒体类型不对 → `RES_MEDIA_TYPE_INVALID`。成功握手却没有 body → `RES_DECODE_FAILED`。开启快照照样可能落在 tuple 第三项。

WebSocket 的启动期覆盖握手加第一次物理 open。构造器失败、open 之前就关闭、超时或取消，都会产出一个启动 tuple。即使 socket 从没到过 `open`，连接快照也可能存在。

| 传输      | 启动之后                                                                                                                                                                               |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE       | 致命错误时迭代器 reject；`stream.closed` 以 `kind: 'error'` 和对应的 fault `code` resolve                                                                                              |
| WebSocket | 消息/队列/心跳失败走 `onRuntimeError`；终止性错误让 `receive` 失败；`session.closed` → `kind: 'closed' \| 'aborted' \| 'error'`                                                        |
| HTTP      | execute 返回的 Promise 只会完成一次，结果为元组。拦截器抛出异常或返回非 `HttpResponse` 的结果时，元组中的错误码为 `EXT_INTERCEPTOR_FAILED`；进度回调抛出异常则为 `EXT_OBSERVER_FAILED` |

`NET_ABORTED` / `NET_TIMEOUT` 描述的是调用方在启动期看到了什么。返回给你的 stream 或 session，你照样要关掉并 await 它的终态 promise。

## 原生 Error 的日志与 cause

Fault 是原生 `Error` 实例，所以不需要诊断适配器。`String(fault)` 给出稳定的原生形式 `DefjsFault: <message>`。`code` 和各变体字段——`status`、`response`、`data`——保持可枚举，便于结构化日志；`name` 和原生 `cause` 链是不可枚举的。

<include cwd lang="typescript">
  examples/errors/log-fault.ts#example
</include>

调 `format()`、`flatten()` 或 `prettify()` 之前，先通过 `fault.cause instanceof StructError` 窄化底层原因。这些辅助方法属于 Struct 的 cause，不会被复制到 fault 上。不要让控制流去解析 `message` 或 `String(fault)`——契约是 `code` 和一个审过的 `status`。

Struct 的默认错误消息只描述收到的类型，不包含具体值，例如 `Expected number at email, received string`。`prettify()` 和 `String(fault)` 中也使用同一条消息。对于 JSON `SyntaxError` 导致的 `RES_DECODE_FAILED`，fault 消息为 `Response body could not be decoded`，原始解析器错误保留在 `cause` 上。原始 `StructIssue.received` 值和解析器 cause 仍是敏感信息；自定义 `errorMap` 消息会原样使用，因此记录日志前需审查自定义文本。

## 参考

| 分支             | 控制流判断                         | 好用的稳定字段                         | 通常没有／敏感              |
| ---------------- | ---------------------------------- | -------------------------------------- | --------------------------- |
| HTTP 状态策略    | `fault.code === 'HTTP_STATUS'`     | `fault.status`、审过的 `fault.data`    | Body、headers、URL、`cause` |
| 调用方取消       | `fault.code === 'NET_ABORTED'`     | `code`                                 | 取消原因和栈                |
| 超时             | `fault.code === 'NET_TIMEOUT'`     | `code`                                 | 请求 URL 和底层 cause       |
| 契约破了         | `fault.code.startsWith('RES_')`    | `code`、审过的 `fault.response.status` | Struct issue、body、输入值  |
| 你自己的代码抛了 | `fault.code.startsWith('EXT_')`    | `code`、`cause`                        | 扩展挂上来的任何东西        |
| 流／会话运行期   | `stream.closed` / `session.closed` | 终态 `kind` 和 `code`                  | 事件载荷、帧、cause         |

把 `cause`、`data`、响应 headers 和 body、URL、`StructIssue.received`、输入值、自定义消息和栈都当敏感信息。问题路径是结构性的，会保留 record 的键：`struct.record(...)` 可能产生 `Expected number at alice@example.com, received string`，因此键在默认消息、`prettify()` 和 `String(fault)` 中仍可能敏感。默认 Struct 消息和 `prettify()` 不包含收到的具体值，但记录完整 issue 或 JSON 解析器 cause 仍可能泄露这些值。一个保守的摘要：

<include cwd lang="typescript">
  examples/errors/summarize-fault.ts#example
</include>

`createNetworkFault`、`createPreflightFault`、`createDecodeFault`、`createHttpStatusFault` 和 `createUndecodedHttpStatusFault` 构造这些原生 Error 值。普通的请求失败照样在 tuple 里返回它们；不会因为它们继承了原生 Error 行为就被抛出。`ERR_ABORTED` 和 `ERR_TIMEOUT` 是传输归一化器能认出来的共享 cause。它们带有不可枚举的 `Symbol.for('defjs.cause.aborted')` 和 `Symbol.for('defjs.cause.timeout')` 标记，因此跨 Core 副本也能判定取消，无需依赖对象身份。[`isAbortCause`](/zh-Hans/api/core/isabortcause) 和 [`isTimeoutCause`](/zh-Hans/api/core/istimeoutcause) 提供这些检查及所支持的平台错误检查；判定 fault 的底层原因时，应传入 `fault.cause`。OpenTelemetry 跨副本也会抑制调用方取消的日志，同时继续记录超时。
