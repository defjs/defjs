# 核心架构设计

Defjs 构建于一条根本性的设计边界之上：**SDK 负责定义底层的网络传输契约，而消费方应用程序完全掌控具体的执行过程。** `@defjs/core` 中的每一条设计规则均源于这道清晰的职责划分。

## 1. 契约定义与应用执行

SDK 软件包对外导出具体的接口操作（`defineRequest`、`defineEventStream`、`defineWebSocket`）以及数据契约（`struct`）。它绝不调用 `createClient`、不维护单例全局 Client，也不读取任何外部环境变量。

<Tabs items={["sdk/orders.ts", "app/consumers.ts"]}>
<Tab value="sdk/orders.ts">

```ts
import { defineRequest, struct } from "@defjs/core";

export const Order = struct.object({
  id: struct.number(),
  status: struct.string(),
});

export const getOrder = defineRequest({
  method: "GET",
  path: "/orders/:id",
  operation: "orders.read",
  input: struct.object({ id: struct.number() }),
  builder: (input) => ({ path: input }),
  output: Order,
});
```

正是因为 `getOrder` 这类操作不捕获任何 Client 状态：

- 浏览器前端、后台定时任务、SSR 请求处理器以及单元测试，均可使用各自不同的 `Client` 配置来调用同一个 `getOrder` 接口定义。
- 框架扩展（`@defjs/react`、`@defjs/vue`）以及可观测性中间件（`@defjs/opentelemetry-server`）全部直接挂载在消费方应用的 `Client` 上，从而保证发布的 SDK 模块保持 100% 零依赖。

## 2. 显式参数放置与双向字段别名

在 Defjs 中，`input` 声明调用方需要传入哪些参数，`struct` 决定数据如何编码与校验解码，而 `builder` 则负责将这些值精确放置到请求的各个部分（`path`、`query`、`headers`、`body`）。

- **绝无隐式黑盒推断**：如果一个操作声明了 `input`，就必须提供一个显式、同步且纯净的 `builder` 函数。框架绝不会根据字段名随意猜测参数该放在 URL 还是 Body 中。
- **双向 `.alias(wireName)`**：在 struct 字段上调用 `.alias("customer_name")`，让代码层面保持优雅的 TypeScript 驼峰命名 `customerName`，同时在底层网络通信中自动完成与 `"customer_name"` 的双向映射转换。

当 `builder` 将类型化的 struct 对象赋值给 `body`、`query` 或 `headers` 时，其定义的字段别名以及 `Date` / `bigint` 编解码规则会自动生效。而你在外层匿名包装对象中手写的键名（例如上例中的 `account_id` 或 `x-api-version`）则保持原样字面量传输。

## 3. 声明即断言 [#declaration-is-an-assertion]

Defjs 在读取 HTTP 响应时严格遵循以下六大规则：

### 规则 1：声明什么就断言什么

`output` 用于断言 `2xx` 成功响应体的结构。`error` 则用于断言非 `2xx` 响应体的结构。所有声明都是运行时的刚性保证，绝非“尽力而为”的模糊提示。

### 规则 2：`ok`（`200..299`）是唯一分流点

`2xx` 状态码的响应只通过 `output` 进行校验与解码。除此以外的所有状态码（`3xx`、`4xx`、`5xx`）均只走 `error` 解码路径。Defjs 绝不会在一侧解析失败时拿另一侧作为兜底尝试。

### 规则 3：任何偏离声明的情况都会返回明确故障

Defjs 用 `response.ok` 选择响应的一侧：`2xx` 用 `output`，非 `2xx` 用 `error`。只有在这一侧声明了 JSON struct，才会触发解码，并可能产生 `RES_MEDIA_TYPE_INVALID` 或 `RES_DECODE_FAILED`；它的 `Content-Type` 会在读取 body 字节**之前**校验。非 `2xx` 的 HTML 网关页只有在声明了 JSON `error` struct 时才会产生 `RES_MEDIA_TYPE_INVALID`。活动的一侧没有声明时，不会读取 body；非 `2xx` 响应会返回未解码的 `HTTP_STATUS`。

| 响应读取阶段出现的异常                             | 返回的明确 Fault 错误码                                        |
| -------------------------------------------------- | -------------------------------------------------------------- |
| 媒体类型与所声明的 JSON 格式不匹配                 | `RES_MEDIA_TYPE_INVALID`（根本不会读取 body 字节流）           |
| 底层字节流无法按所声明的格式解码                   | `RES_DECODE_FAILED`                                            |
| 解码后的数据未能通过 `struct` 模式校验             | `RES_STRUCT_MISMATCH`（HTTP）/ `RES_DECODE_FAILED`（SSE 握手） |
| 非 `2xx` 状态码，且成功解码了声明的 `error` struct | `HTTP_STATUS`（附带强类型的 `error.data`）                     |
| 非 `2xx` 状态码，但未声明 `error`                  | `HTTP_STATUS`（此时 `error.data` 为 `undefined`）              |

### 规则 4：解码失败则无 Body 数据

只有完整通过了解码与 Schema 校验的数据，才被称为 Body。一旦解码失败，Fault 中携带的响应对象类型即为 `HttpMeta`（该接口本身就不包含 `body` 属性），具体的解析或校验错误会挂载在 `fault.cause` 上。

### 规则 5：省略声明即代表主动放弃读取

未声明 `output` 意味着完全不关心 `2xx` 响应体，此时根本不会触发 Body 读取。同理，省略 `error` 意味着完全忽略所有非 `2xx` 状态码的响应体——哪怕服务端在 `500` 时返回了非法畸形的 JSON，也不会触发解析错误。

### 规则 6：`3xx` 不属于成功状态区间

`ok` 的定义严格为 `200 <= status < 300`。像 `304 Not Modified` 属于非 `2xx` 状态：你可以保持 `error` 不声明从而在应用层捕获 `HTTP_STATUS` 错误（或者在 ETag 中间件中拦截处理 `304`），或者在明确期望空文本时声明 `struct.string()`。

## 4. 传输专属的返回结果元组

三种传输协议均采用错误优先三元组替代直接抛出异常：

- **HTTP** → `[error, data, response]` —— 解码后的数据载荷 + `DecodedResponse<T>`（未声明 `output` 时为 `HttpMeta`）。
- **SSE** → `[error, stream, open]` —— `EventStreamHandle` 事件流句柄 + 初始握手快照。
- **WebSocket** → `[error, session, connection]` —— `WebSocketSession` 会话对象 + 初始连接快照。

Client 仅承载配置信息，并不持有处于活跃状态的连接。发起 HTTP 请求、SSE 流或 WebSocket 会话的调用者自行负责其取消或关闭（HTTP 使用 `AbortSignal`；SSE 和 WebSocket 则使用 `await using` 或 `.close()` + `await .closed`）。
