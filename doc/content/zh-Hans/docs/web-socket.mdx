# WebSocket 会话

在 SDK 中，`defineWebSocket` 声明双向 WebSocket 契约：路径模板、可选的 `input` 与 `builder`（仅限 `path` 和 `query`）、`incoming` 与 `outgoing` 消息 struct、队列上限，以及静态子协议。消费方应用在自己的 Client 上配置心跳、重试（`withRetry`）和生命周期清理。

## 2. 消息校验与双向通信规则

- **入站帧（`session.receive`）**：文本、`ArrayBuffer`、类型化数组和 `Blob` 帧都按 UTF-8 解码，解析为 JSON，再用 `incoming` 校验。畸形 JSON 或 schema 不匹配会上报给 `session.onRuntimeError` 并被丢弃，不会关闭会话。`session.receive` 是单消费者；请求第二个迭代器会抛出 `TypeError`。传输失败时，已经收到的消息会先送达，然后 `receive` 以 `closed.cause` reject，心跳超时也算在内。调用方的取消（中止 `signal`）、`session.close()` 和销毁会丢弃未读消息，并且 `receive` 立即结束，无论会话是否已经结束；`session.close()` 之后到达的帧也会被丢弃。会话打开期间到期的 `signal`（如 `AbortSignal.timeout(ms)`）是超时：会话以错误结束，并先送达已入队的消息。会话已经结束之后才到期的，是一次停止，并丢弃它们。
- **出站帧（`session.send(payload)`）**：同步用 `outgoing` 校验，应用 `.alias()` 和编解码器，再用 `JSON.stringify` 序列化。`open` 状态下立即发送；`reconnecting` 期间若队列可用（`maxOutgoingQueueSize > 0`）则排队；载荷无效、队列已满/被禁用或会话已关闭时同步抛出异常。

## 3. 会话状态与观察者机制

| 成员                 | 说明                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `state`              | 当前连接状态：`'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'` |
| `connection`         | 底层最新物理 Socket 的实时快照（包含 `generation`、`url`、协商的 `protocol` 以及 `extensions`）                     |
| `bufferedAmount`     | 当前活跃物理 Socket 上未发送完成的缓冲字节数（未连接时为 `0`）                                                      |
| `receive`            | 单消费者的异步可迭代对象，提供经过强类型校验的 `incoming` 入站消息流                                                |
| `onStateChange(fn)`  | 订阅连接状态流转事件；返回一个用于取消订阅的 `unsubscribe` 函数                                                     |
| `onRuntimeError(fn)` | 订阅连接建立后的非启动期数据帧/解析异常；返回一个 `unsubscribe` 函数                                                |
| `closed`             | 一个返回最终终态结果（`kind: 'closed' \| 'aborted' \| 'error'`）的 Promise                                          |

## 4. 重试、心跳与队列

重连与心跳都需显式开启（opt-in），可通过 Client 选项（`withRetry`、`withWebSocketHeartbeat`）或单次调用的派生 Client 选项（`client({ retry, heartbeat })`）配置。重连使用与 HTTP 和 SSE 相同的 `withRetry` 策略：

- **重试**：设置了重试策略时，默认值为 `maxRetries: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0.2`。`session.close()` 没有请求的每一次关闭默认都会重试，包括从未打开的连接。构造函数抛出是重试只会重复的本地失败，因此它结束调用，且不会询问 `shouldRetry`。每次物理 `open` 都会重置中断计数。`shouldRetry` 可以推翻默认，也可以是异步的；手动关闭、调用方中止，或已经做了 `maxRetries` 次重试之后，不会调用它。被拒绝或用尽的重试会像没有策略时那样结束会话：连接错误是 `closed.kind: "error"`，对端的关闭帧是 `"closed"`。`beforeConnect({ attempt, signal })` 在首次连接和每次重试之前运行。已打开的 socket 向均衡器报告的结果只取决于关闭码，与 `wasClean` 无关：`1006` 或 `1015`（没有收到关闭帧）为 `NET_UNREACHABLE`，`1012` 或 `1013` 为 `NET_UNAVAILABLE`，其他关闭码都不算失败。
- **尝试超时（`attemptTimeoutMs`）**：提供时，它限制从构造到 `open` 的时间，握手后清除。它是 `withRetry`（或请求选项 `retry`）的选项，因此 `withRetry({ attemptTimeoutMs })` 也会重试，默认 `maxRetries: 3`。只要握手期限，写成 `withRetry({ maxRetries: 0, attemptTimeoutMs })`。到期向均衡器报告 `NET_UNREACHABLE`，重试耗尽则以 `NET_TIMEOUT` 结束。
- **心跳**：Defjs 不定义心跳格式、间隔或超时：`message` 和 `isAck` 是你的函数，类型要求有 `message`，并且只允许 `timeoutMs` 与 `isAck` 一起出现。浏览器 `WebSocket` 接口无法发送协议级 ping，因此应用级消息是唯一可移植的心跳。每过 `intervalMs`，它通过 `outgoing` struct 以 JSON 文本发送 `message()`，因此端点要声明 `outgoing` struct，裸的文本或二进制 ping 不可行。它至多等待 `timeoutMs`，寻找匹配 `isAck(msg)` 的已解码帧；未通过 `incoming` struct 的帧会报告给 `onRuntimeError`，永远到不了 `isAck`。匹配的 ack 帧由心跳监视器消费，不转发给 `session.receive`。漏掉 ack 算连接失败：socket 被关闭，漏掉的 ack 作为 `NET_UNREACHABLE` 报告给均衡器并归属于该端点，这次尝试像其他关闭一样进入重试流程。没有重试策略，或重试已经用尽时，`closed.kind` 为 `"error"`，`closed.cause` 是普通的 `Error("WebSocket heartbeat timeout")`。心跳序列化失败或 `message()` 抛出属于本地问题：它们以原始 cause 结束会话，不会重试，也不归属于端点。
- **队列上限**：
  - 入站消息：没有选项，也没有数量上限。库会把平台送达的每条消息排队，直到 `session.receive` 读走它，因此从不读取的消费者会让队列无界增长；会话打开期间请消费 `session.receive`，或者关闭会话。
  - `maxOutgoingQueueSize`（可选，默认 `0`）：仅在 `state === 'reconnecting'` 时缓冲 `session.send()` 调用，并在下一次 `open` 发布前全部刷出。

`shouldRetry` 在其 WebSocket context 中接收原生关闭 `code`、`reason` 和 `wasClean`，并且那里的 `retryable` 始终为 `true`。服务端可能以应用错误码 `1011` 完成正常的关闭握手，因此 `wasClean === true` 不代表应用处理成功。示例根据 `code` 决定；请根据自己的协议选择应用关闭码，而不要只依赖 `!wasClean`。

## 5. 子协议与身份认证 [#protocols-and-authentication]

浏览器 WebSocket 不支持任意握手请求头，因此 WebSocket 的 `builder` 只返回 `{ path?, query? }`。

- **子协议优先级**：`client({ protocols })` 覆盖 `withWebSocketProtocols(...)`，后者覆盖 `defineWebSocket({ protocols })`。
- **URL 转换**：Defjs 会在解析出的端点上自动把 `http:` 转为 `ws:`，把 `https:` 转为 `wss:`。
- **凭据**：`withCredentials(true)` 只适用于 Fetch（HTTP/SSE）。WebSocket 请通过 cookie/会话策略、子协议或短期连接 ticket 认证——避免在 query 字符串中放长期密钥。
- **`beforeConnect` 不是请求修改器**：输入解析、同步纯 `builder` 和拦截器链每次操作只运行一次。如果请求的基础端点未被拦截器替换，每次重连都会重新选择端点并用它重建 URL，但会复用已构建的 path/query 和捕获的协议列表。不论仍使用原端点还是发生故障转移，URL 都会在该次尝试的 `beforeConnect` 运行之前确定。在 hook 中修改闭包变量、input 或协议数组，不能为当前握手提供新的 ticket。同一个会话内不支持轮换 URL/子协议凭据；请先获取新凭据，再通过 input 或 client 配置发起新操作，并负责替代会话的清理。

## 6. 连接关闭与资源回收

调用 `session.close(code?, reason?)`（其中 `code` 必须为 `1000` 或 `3000..4999`，`reason` 长度不超过 123 个 UTF-8 字节）并等待 `await session.closed`，或者直接使用 `await using`：

  examples/web-socket/closure-and-ownership.ts#example
</include>

曾经打开、随后在没有关闭帧的情况下断开的连接（代码 `1006`，`wasClean: false`）始终以 `closed.kind: "error"` 结束，`closed.cause` 为 `Error("WebSocket connection error")`，无论运行时是否触发原生 `error` 事件。

重试中断耗尽其 `maxRetries` 后，会话以 `closed.kind: "error"` 结束，`closed.cause` 是普通传输错误，并带有原生关闭快照（升级失败时通常为代码 `1006`）；没有单独的稳定耗尽代码。会话以 `closed.kind: "error"` 结束时，已经入队的消息仍会送达，`session.receive` 在最后一条之后以 `closed.cause` reject；来自对端的关闭也会在 `session.receive` 结束之前送达已入队的消息。调用方停止会话时，未读消息被丢弃，`session.receive` 立即结束：调用方中止（`closed.kind: "aborted"`）、手动 `session.close()`，以及用 `await using` 销毁，都会这样做，会话已经结束之后也一样。会话结束之后的停止会丢弃未读消息，且不改变其他东西：`closed` 保持原值，一旦没有未读内容，`session.receive` 仍会以 `closed.cause` reject。组件或 worker 结束工作时，始终注销 `onStateChange` 和 `onRuntimeError` 监听器。
