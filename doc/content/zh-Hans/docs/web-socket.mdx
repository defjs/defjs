# WebSocket 会话

用 `defineWebSocket` 声明双向 WebSocket 契约：路径模板、可选 `input` 与 `builder`（只支持 `path` 和 `query`）、入站/出站消息 `struct` 契约、发送队列上限以及默认子协议。业务代码则在 `Client` 上决定怎么加心跳、怎么断线重连（`withRetry`）和怎么释放会话。

## 2. 收发消息怎么校验与排队

- **入站消息（`session.receive`）**：
  - 文本、`ArrayBuffer`、类型化数组或 `Blob` 帧统一先解为 UTF-8，再解析成 JSON 并用 `incoming` 校验。如果收到坏 JSON 或字段不匹配，**不会把整条连接弄挂**——而是交给 `session.onRuntimeError` 报警后跳过这条消息。
  - `session.receive` 只能有一个消费者，开第二个迭代器会报错 `TypeError`。
  - **异常断线 vs 主动关闭怎么处理未读消息**：如果是网络报错、服务端断连或心跳超时，已经推进队列的消息会先喂给 `session.receive` 读完，然后才抛出 `closed.cause`；相反，如果是你这边调用 `session.close()`、`await using` 销毁或触发 `signal` 中止（以及这之后才到来的帧），未读消息会被立刻清空。运行过程中 `AbortSignal.timeout(ms)` 到期按超时算，也会先把队列已有消息读完再报错；会话已结束之后再中止则按主动停止丢弃。
- **出站消息（`session.send(payload)`）**：
  - 同步用 `outgoing` struct 校验、转换 `.alias()` 别名并 `JSON.stringify`。
  - 当前在 `open` 状态就直接发送；如果正好在 `reconnecting` 重连且 `maxOutgoingQueueSize > 0`，消息会暂存进发送队列等下次连上再一起发出；校验没通过、队列满了/未开队列、或会话已经关了，则会直接同步 `throw` 异常。

## 3. 会话状态与事件观察

| 成员                 | 作用说明                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `state`              | 当前连接状态：`'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'` |
| `connection`         | 当前活跃底层物理 Socket 的实时快照（含 `generation`、`url`、协商出的 `protocol` 和 `extensions`）                   |
| `bufferedAmount`     | 底层物理 Socket 待发送缓冲区字节数（未连上时为 `0`）                                                                |
| `receive`            | 单消费者异步可迭代流，逐条吐出通过 `incoming` 校验后的强类型消息                                                    |
| `onStateChange(fn)`  | 订阅连接状态变迁，返回取消订阅的 `unsubscribe` 函数                                                                 |
| `onRuntimeError(fn)` | 订阅建连之后单帧解析/校验出错通知，返回 `unsubscribe` 函数                                                          |
| `closed`             | 最终停机状态 Promise，结束为 `{ kind: 'closed' \| 'aborted' \| 'error', ... }`                                      |

## 4. 自动重连、应用心跳与缓冲队列

重连和心跳默认都**关闭**，按需通过 Client 配置（`withRetry`、`withWebSocketHeartbeat`）或单次调用参数（`client({ retry, heartbeat })`）开启。重连共用 HTTP / SSE 那套 `withRetry` 机制：

- **重连规则（`withRetry`）**：
  - **默认参数**：开启 `withRetry()` 时默认 `maxRetries: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0.2`。
  - **什么时候重连、什么时候不重连**：只要不是调用方自己调 `session.close()`，哪怕是还没打开成功就被关闭，默认都会进重连；但如果 `WebSocket` 构造函数一上来就同步抛错（属于重连也必挂的本地错误），会立刻失败且不触发 `shouldRetry`。
  - **每次真正连上都会清零重连次数**：每当物理 `open` 触发，`maxRetries` 计数归零。你可以传同步或异步的 `shouldRetry` 改写策略（注意手动关闭、信号中止或已达 `maxRetries` 上限时不会再问 `shouldRetry`）。若触发 `error` 后 1 秒内都没等到 `close`，或者调底层 `close()` 时抛了错，都算一次失败，同样和心跳超时一样走 `shouldRetry`。重连前每次都会重新调一次 `beforeConnect({ attempt, signal })`。
  - **如何给均衡器记账**：已建连后的断线，无论 `wasClean` 是真是假，只看关闭码归因：`1006` 或 `1015` 算 `NET_UNREACHABLE`，`1012` 或 `1013` 算 `NET_UNAVAILABLE`，其他关闭码不算端点故障。
- **握手超时（`attemptTimeoutMs`）**：限制从构造 Socket 到收到 `open` 事件的时间（连上即清除定时器）。因为它属于 `withRetry`，写成 `withRetry({ attemptTimeoutMs })` 默认会开 3 次重试；**只卡握手时间不重连**请写 `withRetry({ maxRetries: 0, attemptTimeoutMs })`。超时的尝试报 `NET_UNREACHABLE` 给均衡器，重试耗尽返回 `NET_TIMEOUT`。
- **应用层心跳（`withWebSocketHeartbeat`）**：
  - **为什么不是协议级 ping frame**：浏览器标准的 `WebSocket` API 不允许 JS 发送控制帧 ping，所以只能靠业务约定的 JSON 消息模拟（这也要求端点声明了 `outgoing` struct，纯文本或裸二进制不行）。
  - **怎么跑**：每隔 `intervalMs` 按 `outgoing` 发送一次你 `message()` 生成的心跳包；若配了 `isAck`，就最多等 `timeoutMs` 找匹配 `isAck(msg)` 的回包（回包必须过 `incoming` struct，否则进 `onRuntimeError`）；匹配上的 ack 会被心跳模块内部消化，不会混进业务消费的 `session.receive`。
  - **心跳超时与本地报错怎么处理**：超时收不到 ack 就视为连接已断——客户端立刻关掉 Socket，按 `NET_UNREACHABLE` 上报均衡器，然后进入常规 `withRetry` 流程（没开重试或用完次数时，`closed.kind` 为 `"error"`，`closed.cause` 是 `Error("WebSocket heartbeat timeout")`）。如果是 `message()` 自己抛错或序列化失败，属于本地 Bug，直接以原错结束且不会重试或连累端点。
- **队列上限**：
  - **入站队列没有上限设置**：只要连接活着且服务端不停发消息，库就会把包一直存着等 `session.receive` 来拿；所以开启会话期间要么持续读取 `session.receive`，要么不用了马上关掉会话。
  - **`maxOutgoingQueueSize`（可选，默认 `0`）**：只用于在 `state === 'reconnecting'` 期间暂存 `session.send()`，等下次物理 `open` 触发后统一补发。

注意：`shouldRetry` 的 WebSocket 上下文里有原生的 `code`、`reason` 和 `wasClean`（且默认 `retryable` 始终为 `true`）。很多服务端报错关闭也会好好发 Close 帧（比如携带错误码 `1011`），这时 `wasClean` 同样是 `true`——所以判断要不要重连建议像示例那样看具体 `code`，别单靠 `!wasClean`。

## 5. 子协议与身份认证 [#protocols-and-authentication]

浏览器里的 `WebSocket` API 本身不支持任意自定义握手请求头，因此 WebSocket 的 `builder` 只返回 `{ path?, query? }`。

- **子协议优先级**：单次调用 `client({ protocols })` 覆盖 `withWebSocketProtocols(...)`，后者覆盖定义里的 `defineWebSocket({ protocols })`。
- **协议头自动转换**：配在 `endpoint` 上的 `http:` / `https:` 会自动转换成 `ws:` / `wss:`。
- **怎么传鉴权凭据**：`withCredentials(true)` 只管 Fetch（HTTP/SSE），不管 WebSocket。推荐用同站 Cookie/Session、子协议头或短期一次性连接 Ticket 传票据——尽量别把长期 Token 直接拼在 URL query 里。
- **`beforeConnect` 不能改写当前请求的 URL 和子协议**：入参解析、`builder` 和拦截器只在发起操作时运行一次。只要基础端点没被拦截器锁死替换，重连时虽然会按均衡器挑的新节点重拼前缀域名，但拼上去的 path、query 和协议列表依然是启动时那一份——所以在这个钩子里去改外部闭包变量、入参或协议数组，对本次握手生效不了；如果你需要轮换一次性的 WebSocket 凭据，请拿到新凭据后重新发起一条新会话操作，并关掉旧会话。

## 6. 关掉连接与释放资源

调 `session.close(code?, reason?)`（关闭码只允许 `1000` 或 `3000..4999`，原因 UTF-8 不超过 123 字节）然后 `await session.closed`，或者直接配 `await using`：

</include>

- **意外断开（`1006`）必走 error**：曾经打开的连接如果在没收到对端 Close 帧的情况下突然断掉（状态码 `1006`、`wasClean: false`），不管浏览器/运行环境有没有触发原生 `error` 事件，最终都会结束为 `closed.kind: "error"`，`closed.cause` 为 `Error("WebSocket connection error")`。
- **重试次数耗尽后**：会话结束为 `closed.kind: "error"`，`closed.cause` 为普通传输异常，同时带着最后一次原生关闭快照。
- **队列消息与监听器清理**：异常或对端关流结束时，已经收进队列的消息仍会在 `session.receive` 里正常读完；只有主动调 `session.close()`、`await using` 或触发 `signal` 中止时才会立即丢弃未读消息（如果中止发生于会话打开期间，迭代器还会抛出 `closed.cause`）。组件卸载或后台任务退出时，别忘了顺手调一下之前留的 `unsubscribe()` 注销 `onStateChange` 和 `onRuntimeError`。
