# 测试

`@defjs/core` 自身已经把底层的传输、重试和编解码测得很全了。你在业务项目或 SDK 仓库里写测试，重点测的是**你自己写的那部分代码**：`builder` 参数有没有放对地方、`.alias()` 线格式字段有没有配反、`struct` 能否解出真实接口返回、鉴权/刷新 Token 拦截器怎么工作、业务函数怎么把错误状态码转成业务结果，以及页面组件卸载时有没有把请求取消掉。

## 项目里该测什么——为什么别用 `vi.mock`

编写业务测试时，**不要**用 `vi.mock(...)` 或 stub 把导出的 `defineRequest`、`defineEventStream`、`defineWebSocket` 直接替换掉。一旦 mock 掉操作函数，你自己的 `builder` 参数映射、`.alias()` 编码、自定义拦截器、状态码分发和 `struct` 解码就会全被跳过，测试通过了也可能带着 bug 上线。

更可靠的做法是：在每个测试里新建一个 `Client`，挂上内存传输句柄（`withHTTPHandle`、`withSSEHandle` 或 `withWebSocketHandle`），让你写的真实接口定义和业务代码在不真正发网包的前提下完整走完一遍流程。

| 项目代码分层                                               | 测试主要验证什么                                               | 测试 `Client` 怎么接进去                                                    |
| :--------------------------------------------------------- | :------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| 接口定义与 Schema（`src/api/request/`、`src/api/schema/`） | 手写的 `builder` 参数位置、`.alias()` 映射、`output`/`error`   | 直接导入真实操作函数，传入挂载了 `withHTTPHandle` 的测试 `Client`           |
| 业务函数与自定义拦截器（`checkout.ts`、`client.ts`）       | 鉴权头注入、Token 刷新重放、多步业务流、错误映射与重试配置     | 把挂好 `withInterceptors(...)` 的测试 `Client` 直接传进业务函数             |
| SSE 与 WebSocket 消费逻辑（`src/events/`、`src/quotes/`）  | 业务函数对推送事件的聚合处理、上行报文格式、`await using` 释放 | 用 `withSSEHandle` 或 `withWebSocketHandle` 在内存中构造推送帧              |
| React / Vue UI 组件（`OrderCard.tsx`、`OrderView.vue`）    | 加载态、数据渲染、报错提示、组件卸载时 `AbortController` 取消  | 用 `<ClientProvider client={testClient}>` 包裹，或安装 `createClientPlugin` |

## 1. 测试接口定义与 Schema（`withHTTPHandle`）

直接导入项目里真实导出的 `defineRequest` 操作，并用 `withEndpoint("https://fixture.invalid")` 搭配 `withHTTPHandle(...)` 创建测试 `Client`：

- **为什么要配 `https://fixture.invalid`**：`createClient` 会在请求进入 `withHTTPHandle` 之前校验一次基础 URL；`.invalid` 是 RFC 标准保留的无效域名，即使配置写漏也不会意外打到真实公网 DNS。
- **注意句柄职责划分**：`withHTTPHandle` **只拦截 HTTP 操作（`defineRequest`）**；如果你测的是 `defineEventStream` 或 `defineWebSocket`，请分别使用 `withSSEHandle` 或 `withWebSocketHandle`。
- **关于 `withRetry` 的默认值**：未配置 `withRetry` 时默认**不重试**。普通单元测试尽量不要挂载 `withRetry`，这样遇到 `502`、`503`、`504` 或断网异常时一次就返回结果，不会卡在 `1s + 2s + 4s` 的退避等待上。**特别留意**：调用 `withRetry()` 或传入 `withRetry(undefined)` 会默认开启 **3 次重试**；如果你基于公共测试工厂关闭重试，请显式传入 `withRetry({ maxRetries: 0 })`。

### 三个实战要点：用例隔离、核对请求报文、模拟三种常见返回

- **每个用例新建一个 `Client`**：不要把带重试预算、健康度状态或请求计数器的 `Client` 放在外层 `describe` 里跨用例共享，随用随建最干净。
- **核对实际发出去的报文**：在 `withHTTPHandle(async (input, init) => ...)` 里构造 `const request = new Request(input, init)`，把 `request.method`、`request.url`、`request.headers` 和 `await request.text()`（或 `await request.json()`）断言一遍，确认 `builder` 和 `.alias()` 没有写偏。
- **常见返回分支怎么构造、怎么断言**：
  - **`2xx` 成功分支**：先 `expect(err).toBeNull()`，紧接着写 `if (err) throw err;` 收窄类型，然后再断言解码出来的 `data`。
  - **`4xx` / `5xx` 接口报错分支**：返回 `Response.json(..., { status: 422 })`，紧接 `if (err)` 判断，在块里通过 `if (err.code === "HTTP_STATUS")` 断言 `err.status`、`err.data` 和 `err.response`，处理完在 `if (err)` 块内直接 `return`，块外末尾补一句 `expect.unreachable("expected HTTP_STATUS fault")`（如果用 `bun:test` 没有 `expect.unreachable`，直接 `throw new Error("expected HTTP_STATUS fault")` 即可）。
  - **断网 / 连接失败分支（`NET_UNREACHABLE`）**：**不要**返回 `Response.error()`——只要 `withHTTPHandle` 返回了 `Response` 实例（哪怕状态码是 `0`），Defjs 都会按“已收到 HTTP 响应”处理，得到 `HTTP_STATUS` 而不是网络错误。要模拟断网、DNS 失败或连接重置，请在句柄里直接 `return Promise.reject(new TypeError("fetch failed"))`（或直接 `throw`）：

```ts
import { createClient, withEndpoint, withHTTPHandle } from "@defjs/core";
import { expect, test } from "vitest";
import { createOrder } from "./sdk/orders.ts";

test("断网时返回 NET_UNREACHABLE", async () => {
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withHTTPHandle(() => Promise.reject(new TypeError("fetch failed"))),
  );

  const [err] = await createOrder(client, { sku: "book", quantity: 1 });
  if (err) {
    expect(err.code).toBe("NET_UNREACHABLE");
    return;
  }

  expect.unreachable("expected NET_UNREACHABLE fault");
});
```

### 怎么测重试（`withRetry`）和 `401` 刷新 Token 重放

- **测试临时 `503` 重试恢复**：在 `withHTTPHandle` 外面放一个计数器 `let attempts = 0`，配置 `withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] })` 即可零等待测完重试。**坑点提醒**：传入 `methods` 会**整体覆盖**默认可重试方法列表（默认是 `["GET", "HEAD", "OPTIONS", "TRACE", "PUT", "DELETE"]`）；如果同一个测试 `Client` 上既要重试 `GET` 又要重试 `POST`，请写成 `methods: ["GET", "POST"]`。
- **测试 `401` 刷新 Token 重放**：拦截器里通过再调用一次 `next(...)` 重放请求时，**不依赖 `withRetry`**。直接用有状态的 `withHTTPHandle` 计数器记录第一次返回 `401`、第二次校验新 `Authorization` 头并返回 `200` 即可。另外注意：如果拦截器或业务代码需要读取 `401` 响应体（`err.data`），操作定义上必须声明 `error: struct(...)`，否则只会返回状态码而不会自动解码响应体。

```ts
import {
  createClient,
  createHttpInterceptor,
  withEndpoint,
  withHTTPHandle,
  withInterceptors,
  withRetry,
} from "@defjs/core";
import { expect, test } from "vitest";
import { submitOrder } from "./src/checkout.ts";

test("临时 503 通过 withRetry 恢复且 POST 需显式加入 methods", async () => {
  let attempts = 0;
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] }),
    withHTTPHandle(async () => {
      attempts += 1;
      if (attempts === 1) {
        return Response.json({ message: "try again" }, { status: 503 });
      }
      return Response.json({ id: "ord_2" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "pen", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_2");
});

test("拦截器在 401 时刷新 Token 并重放 next()", async () => {
  let token = "expired-token";
  let attempts = 0;

  const refreshAuth = createHttpInterceptor(async (req, next) => {
    const first = await next({
      ...req,
      headers: { ...req.headers, authorization: `Bearer ${token}` },
    });
    if (first[0]?.code === "HTTP_STATUS" && first[0].status === 401) {
      token = "fresh-token";
      return next({
        ...req,
        headers: { ...req.headers, authorization: `Bearer ${token}` },
      });
    }
    return first;
  });

  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withInterceptors(refreshAuth),
    withHTTPHandle(async (input, init) => {
      attempts += 1;
      const auth = new Request(input, init).headers.get("authorization");
      if (auth === "Bearer expired-token") {
        return new Response(null, { status: 401 });
      }
      expect(auth).toBe("Bearer fresh-token");
      return Response.json({ id: "ord_3" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "mug", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_3");
});
```

## 3. 测试 SSE 与 WebSocket 消费逻辑

测试项目里封装好的实时流消费函数或状态聚合器时，可以用 `withSSEHandle` 或 `withWebSocketHandle` 在内存里构造推送事件，直接验证解析结果和资源释放行为：

- **SSE（`withSSEHandle`）**：返回的 `Response` 必须带上 `"content-type": "text/event-stream"` 和一个 `ReadableStream<Uint8Array>`；如果要测试半路断流，在 `start(controller)` 里推送完几条分片后调用 `controller.error(new TypeError("stream dropped"))` 即可（若要测试握手阶段失败，直接返回 `{ status: 500 }` 响应）。
- **WebSocket（`withWebSocketHandle`）**：传入一个继承 `EventTarget`、实现 `WebSocketHandle`（提供 `static readonly OPEN = 1` 和 `readyState`）的轻量测试桩类。注意示例里的 `FakeQuoteSocket` 会用 **`queueMicrotask` 异步派发 `open` 和消息事件**——这是因为业务代码在发起连接后才会接着挂载监听或进入 `for await`，如果在构造函数里同步派发事件，事件发出时监听还没挂上就会丢消息。如果想测试中途异常关闭，可以在测试桩里派发 `this.dispatchEvent(new Event("error"))` 再接一个 `CloseEvent("close", { code: 1011, reason: "boom" })`。

## 4. 怎么组织项目代码，让业务层和 UI 组件都好测

只要按 [应用接口层](/zh-Hans/docs/application-api) 的目录规范来拆代码，项目测试基本不需要碰 `vi.mock`：

- **定义文件 `src/api/request/*.ts` 不绑定全局 Client**：只导出 `defineRequest`、`defineEventStream` 和 `defineWebSocket`，永远不在定义文件里 `import` 生产 `apiClient`，保证任何测试都能传进自己的测试 `Client`。
- **业务函数通过参数接收 `Client`（或 `DerivableClient`）**：
  - **什么时候写 `Client` vs `DerivableClient`**：`createClient(...)` 返回的类型是 `DerivableClient`，它可以传给要求 `Client` 的参数。但如果你在业务函数内部要调用 `client({ signal })` 或 `client({ headers })` 派生单次请求配置，参数类型**必须写 `DerivableClient`**（普通 `Client` 类型上没有可调用的函数签名）。
  - **参数位置与默认值**：可以把 `client` 放在第一个参数（`export async function placeOrder(client: DerivableClient, input: ...)`），也可以把带默认值的客户端放最后（`export async function placeOrder(input: PlaceOrderInput, client: Client = apiClient)`），这样业务代码里直接调用 `placeOrder(input)`，测试里写 `placeOrder(input, testClient)`。同时从 `src/api/client.ts` 导出自定义拦截器和 SSR 工厂函数（例如 `createServerApiClient(token, ...options: ClientOption[])`，把尾部可选配置透传进 `createClient(...)`），方便测试追加 `withHTTPHandle`。
  - **Node / Bun 测试里的 `withXSRF()` 注意事项**：`withXSRF()` 会读取浏览器全局对象（如 `globalThis.location`）。如果你的 `src/api/client.ts` 在模块顶层无条件导出 `export const apiClient = createClient(..., withXSRF())`，那么只要测试文件 `import` 了带默认参数 `= apiClient` 的业务函数，哪怕用例里显式传了 `testClient`，文件一加载就会在 Node 或 Bun 测试环境里报错。解决办法是仅在浏览器环境挂载 `withXSRF()`（例如通过工厂函数按运行环境组装），或让业务辅助函数不把浏览器专属的默认客户端挂在顶层导入链路里。
- **React 与 Vue 组件通过 Provider / Plugin 注入 `testClient`**：

## 5. 测试超时、退避与定时器

测试自定义拦截器里的退避等待、SSE/WebSocket 重连延迟或心跳检查时，Vitest 下建议使用 `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })`（Bun test 下使用 `jest.useFakeTimers()`）。之所以把 `toFake` 限制在定时器相关 API 上，是为了让 Promise 和微任务队列保持真实调度，避免 `async` / `await` 卡住。

需要注意，**Vitest 的假定时器不会推进运行时的原生 `AbortSignal.timeout` 时钟**：

- 如果你想确定地触发通过 `client({ signal })` 传入的超时中止分支，请在测试里用受控 `setTimeout` 手动以 `new DOMException("request deadline", "TimeoutError")` 触发 `AbortController.abort(...)`（先等待 `await ready` 确认请求已经真正进入 `withHTTPHandle` 并注册好定时器，再调用 `advanceTimersByTimeAsync`，否则时间快进时定时器还没挂上去）：

<include cwd lang="typescript">
  examples/testing/deadline.ts#example
</include>

- 另一种更省事的做法是：如果客户端本身启用了 Defjs 内置的 `withRetry({ maxRetries: 0, attemptTimeoutMs: 500 })`，它底层用的就是 JS `setTimeout`，Vitest 的 `vi.advanceTimersByTimeAsync(500)` 可以直接把它推进到 `NET_TIMEOUT`。
- 在 **Bun test** 中，`jest.useFakeTimers()` 与 `jest.advanceTimersByTime()` 同时支持推进 `AbortSignal.timeout`。无论用哪种测试框架，都请在状态改变或次数断言之后再放行，并在 `try ... finally` 里恢复真实定时器。
