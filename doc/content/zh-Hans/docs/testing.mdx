# 测试

由于 Defjs 将操作定义与 Client 执行分离，你可以在不启动网络服务器、也不 mock 库内部函数的情况下，离线测试真实的 SDK 操作和应用拦截器。

## 1. 注入本地传输句柄

在 `createClient(...)` 上使用 `withHTTPHandle`、`withSSEHandle` 或 `withWebSocketHandle` 替换底层平台传输。Defjs 仍会跑完整的操作流水线：输入 `struct` 校验、`builder` 映射、URL 目录限制检查、拦截器、状态码分发和响应 `struct` 解码。

## 2. 测试最佳实践

### 断言错误优先元组，而非内部实现细节

始终用测试 Client 调用导出的 SDK 操作，并断言返回的 `[error, data, response]` 元组：

- 对于 `2xx` 场景，断言 `expect(error).toBeNull()`，并检查解码后的 `data` 字段（包括 `.alias()` 的网络字段到逻辑字段映射）。
- 对于失败场景，按契约断言 `error?.code`、`error?.status`、`error?.data` 和 `error?.cause`。

### 校验出站请求的网络字节

在 `withHTTPHandle(async (input, init) => ...)` 内部构造 `const request = new Request(input, init)`，检查 `request.url`、`request.method`、`request.headers` 以及 `await request.text()`（或 `await request.json()`），确认 `builder` 和 struct 别名序列化出的正是后端期望的网络格式。

### 用假定时器确定性控制时间

拦截器重试退避、SSE/WebSocket 重连延迟或 WebSocket 心跳，在 Vitest 中使用 `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })`。这些假定时器不会推进原生 `AbortSignal.timeout` 的时钟。要在 Vitest 中得到确定的请求期限，用受控的 `setTimeout` 以 `TimeoutError` 为原因中止 `AbortController`：

在 Bun test 中使用 `jest.useFakeTimers()` 和 `jest.advanceTimersByTime()`；Bun 的假定时器也会控制 `AbortSignal.timeout`。不要假定两个运行器控制相同的原生时钟。只在被等待的阶段开始后推进定时器，断言状态变化或尝试次数而不是实际耗时，并在每个测试后恢复真实定时器。
