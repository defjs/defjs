# 中间件

中间件拦截器（Interceptors）允许在无需修改 SDK 接口定义的前提下，为消费方应用程序的 `Client` 统一挂载跨切面的执行策略——例如注入认证请求头、进行请求签名计算、在系统维护期执行快速短路，或针对幂等的读请求实施安全重试。

入参校验与 `builder` 参数放置在进入拦截器链**之前**运行；HTTP 状态码分支分流与 `output` / `error` 的 Struct 校验解码则在走出拦截器链**之后**执行。

### 拦截器执行链路规则

- **洋葱模型执行顺序**：在请求发出阶段（`before next(req)`），拦截器严格按照注册顺序从外向内执行；在响应返回阶段（`after await next(req)`），则按照相反顺序从内向外回溯。因此，诸如日志审计、全局链路追踪等通用中间件应注册在外层，而鉴权 Token 注入或局部重试拦截器则应放置在更内层。
- **不可变请求契约**：修改请求头时，始终克隆一份全新的 `Headers` 实例（`new Headers(req.headers)`），并将包装后的全新请求对象（`{ ...req, headers }`）传递给 `next(...)`，确保外层可能发生的重试逻辑能够看到干净、未受污染的请求头。
- **`content-type` 与 `bodyContentType`**：Defjs 会将根据 Body 推断出的媒体类型存放在 `req.bodyContentType` 上，而绝不暗中直接修改 `req.headers`。若需要计算请求签名，建议读取 `req.headers.get("content-type") ?? req.bodyContentType`。若拦截器修改并替换了 `req.body` 的内容格式，请务必显式设置 `content-type` 请求头。

## 3. 对安全的读请求执行重试

HTTP 重试默认关闭。要在 `502`、`503` 或 `504` 时故障转移到另一个端点，请使用 [`withRetry({ on: ["gateway-error"] })`](/zh-Hans/docs/load-balancing)。它会重新选择尚未尝试的端点、重新构建请求，并重新运行完整的拦截器链。

应用拦截器也可以自行处理同一端点的状态码，例如 `429` 和 `Retry-After`。下面这个有界的安全读取配方也处理 `502`/`503`/`504`：

<include cwd lang="typescript">
  examples/interceptors/retry-safe-reads.ts#example
</include>

- **两层重试**：这个 `next(request)` 循环始终使用选中的端点，不会重新运行外层认证或 builder。把三次内层发送与 `withRetry({ maxAttempts: 2, on: ["gateway-error"] })` 组合起来，可能发送四次 HTTP 请求（三次发给故障主端点，一次发给健康备用端点）；`maxAttempts` 限制外层尝试次数，而不是物理发送次数。应明确每种条件由哪一层负责，避免无意间叠加。
- **`Retry-After` 策略**：Core 的 `withRetry` 不读取这个响应头。配方中 30 秒的上限和 250 ms 的回退值是应用层的选择。对更长的服务器延迟设置上限，可能比服务器要求的时间更早重试；若不能接受，请等待完整延迟或直接返回响应。
- **401 写操作**：[Bearer 刷新配方](/zh-Hans/recipes/refresh-bearer-once) 可能投递同一个 JSON POST 两次。必须确保认证在业务处理前拒绝请求，并使用稳定的幂等键和服务端去重，否则就不要自动重放写操作。流式请求体不会重放。
- **处理传输层 Reject 异常**：当发生底层网络错误时，`next(request)` 会返回 rejected promise（底层不存在所谓的 status 为 0 的响应对象）。通过 `try...catch` 捕获并重新将其 throw 出去，即可完整保留原始的 `NET_*` 错误码。
- **在拦截器内部抛出异常**：未捕获的 throw（或返回了非预期的响应对象）会使操作元组直接返回 `EXT_INTERCEPTOR_FAILED` 故障，并将异常原因挂在 `fault.cause` 上。若在拦截器中显式抛出 `ERR_ABORTED` 或 `ERR_TIMEOUT`，则会精准结算为 `NET_ABORTED` 或 `NET_TIMEOUT`。

对于 SSE，优先使用 `withSSEReconnect`，而不是反复调用 `next()` 的拦截器。多次调用拦截器的 `next()` 会禁用这些替换流的端点归因和重新选择；这与通过迭代器的 `next()` 消费事件无关。

## 4. 包装并扩展 WebSocket 会话

WebSocket 拦截器在一次生命周期中**最多只能调用一次** `next(req)`。当需要对返回的 `WebSocketSessionLike` 进行包装增强时，请显式委托其实时 Getter（`state`、`connection`、`bufferedAmount`）、`close`、`closed`、`receive` 以及 `[Symbol.asyncDispose]()` 方法，切勿通过对象解构 `{ ...session }` 仅复制一次性的属性快照：

## 5. 内置工厂与常用辅助工具

| 导出名称                                       | 适用协议  | 功能描述                                                               |
| ---------------------------------------------- | --------- | ---------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP      | 包装 `(req, next) => Promise<HttpResponse<unknown>>` 中间件            |
| `createSSEInterceptor(fn)`                     | SSE       | 包装 `(req, next) => Promise<EventStreamHandle<unknown>>` 中间件       |
| `createWebSocketInterceptor(fn)`               | WebSocket | 包装 `(req, next) => Promise<WebSocketSessionLike>` 中间件             |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP      | 接收同步/异步凭证 Provider，自动注入 `Authorization: Basic ...` 请求头 |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE       | 在 SSE 握手请求阶段自动注入 `Authorization: Basic ...` 请求头          |
