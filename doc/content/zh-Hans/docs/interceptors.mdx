# 拦截器

拦截器为应用的 `Client` 挂载跨切面执行策略——认证请求头、请求签名、维护期短路或 `Retry-After` 处理——而无需修改 SDK 操作定义。

输入校验和 `builder` 映射在拦截器链**之前**运行；HTTP 状态码分发与 `output` / `error` struct 校验在链**之后**运行。

### 拦截器执行链路规则

- **洋葱顺序**：请求向外走时（`before next(req)`），拦截器按注册顺序执行；返回时（`after await next(req)`）按相反顺序执行。把范围较宽的日志/追踪拦截器放在较窄的认证或重试拦截器外层。
- **不可变请求约定**：始终克隆 `req.headers`（`new Headers(req.headers)`），并把新的请求对象（`{ ...req, headers }`）传给 `next(...)`，这样外层重试才能看到干净的请求头。
- **`content-type` 与 `bodyContentType`**：Defjs 把推断出的 body 内容类型放在 `req.bodyContentType` 上，不修改 `req.headers`。请求签名应读取 `req.headers.get("content-type") ?? req.bodyContentType`。如果拦截器用新格式替换了 `req.body`，请显式设置 `content-type` 请求头。

## 3. 重试与 `Retry-After`

HTTP 重试默认关闭。要在另一个端点上重试连接失败、超时，或 `502`、`503`、`504`，请使用 [`withRetry()`](/zh-Hans/docs/load-balancing#retries)。退避延迟之后，它会让均衡器再次选择、重新构建请求，并重新运行完整的拦截器链。

应用拦截器也可以自行处理同一端点的状态码，例如 `429` 和 `Retry-After`：

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **两层重试**：这个 `next(request)` 循环始终使用选中的端点，不会重新运行 builder 或外层拦截器。连接失败和 `502`/`503`/`504` 交给 `withRetry`。
- **`Retry-After` 策略**：Core 的 `withRetry` 不读取这个响应头。配方中 30 秒的上限和 250 ms 的回退值是应用层的选择。对更长的服务器延迟设置上限，可能比服务器要求的时间更早重试；若不能接受，请等待完整延迟或直接返回响应。
- **401 写操作**：[Bearer 刷新配方](/zh-Hans/recipes/refresh-bearer-once)可能投递同一个 JSON POST 两次。请要求认证在业务处理前拒绝请求，并使用稳定的幂等键与服务端去重；否则不要自动重放写操作。流式请求体不会重放。
- **处理传输层 rejection**：网络错误发生时 `next(request)` 会 reject（不存在 status 为 0 的响应）。捕获后重新抛出可保留原始 `NET_*` Fault 代码。
- **无法发送的请求**：在 HTTP 拦截器中，当平台拒绝该请求（无效或被禁止的方法、GET 或 HEAD 的 body、带凭据的 URL、无效的 `Content-Type`），或 `finalizeHeaders` hook 抛出时，`next(request)` 会以平台自己的错误（`TypeError`）或 hook 抛出的值 reject，而不是库的 `BodyFailure` 包装。重新抛出可保留 Fault 代码（`REQ_BUILD_FAILED` 或 `EXT_HOOK_FAILED`）；抛出另一个错误则使这次失败归你所有（`EXT_INTERCEPTOR_FAILED`）。传输周围发现的其他失败仍以 `BodyFailure` 到达 `next(request)`：无法读取、解码或与媒体类型匹配的响应 body、被截断的 body，以及抛出异常的上传进度观察者（`EXT_OBSERVER_FAILED`），后者可能发生在请求发出之前。
- **在拦截器内抛出异常**：拦截器自身未处理的抛出（或向 `next()` 传入不是 `AbortSignal` 的 `signal`）会让操作元组以 `EXT_INTERCEPTOR_FAILED` 结算，并设置 `fault.cause`。抛出 `ERR_ABORTED` 或 `ERR_TIMEOUT` 会结算为 `NET_ABORTED` 或 `NET_TIMEOUT`。

对于 SSE，优先使用 `withRetry`，而不是反复调用 `next()` 的拦截器。多次调用拦截器的 `next()` 会禁用这些替换流的端点归因和重新选择；这与通过迭代器的 `next()` 消费事件无关。

## 4. 包装并扩展 WebSocket 会话

WebSocket 拦截器**最多只能调用一次** `next(req)`。包装返回的 `WebSocketSessionLike` 时，请委托实时 getter（`state`、`connection`、`bufferedAmount`）、`close`、`closed`、`receive` 和 `[Symbol.asyncDispose]()`，不要用对象展开复制一次性快照：

## 5. 内置工厂与常用辅助工具

| 导出                                           | 传输      | 说明                                                                                  |
| ---------------------------------------------- | --------- | ------------------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP      | 包装 `(req, next) => Promise<HttpResponse<unknown>>`                                  |
| `createSSEInterceptor(fn)`                     | SSE       | 包装 `(req, next) => Promise<EventStreamHandle<unknown>>`                             |
| `createWebSocketInterceptor(fn)`               | WebSocket | 包装 `(req, next) => Promise<WebSocketSessionLike>`                                   |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP      | 接收同步凭证 Provider（每个请求调用一次），自动注入 `Authorization: Basic ...` 请求头 |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE       | 在 SSE 握手请求阶段自动注入 `Authorization: Basic ...` 请求头                         |
