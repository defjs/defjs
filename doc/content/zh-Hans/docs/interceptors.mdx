# 拦截器

拦截器让你把认证请求头、签名校验、维护期间直接拦截或 `Retry-After` 等待这类公共逻辑统一挂在应用的 `Client` 上，而不用去改任何一条接口定义。

**执行顺序位置**：入参校验和 `builder` 拼装请求发生在拦截器**之前**；HTTP 状态码分流和 `output` / `error` 的 `struct` 解码发生在拦截器**之后**。[操作拦截器](/zh-Hans/docs/interceptors#operation-interceptors)则包裹以上全部。

### 写拦截器的三个基本原则

- **洋葱模型顺序**：发起请求时（`await next(req)` 之前），按 `withInterceptors(...)` 传入顺序从外往里跑；拿到响应后（`await next(req)` 之后），按相反顺序一层层退出来。建议把日志、Trace 这类全局观测拦截器放最外层，把鉴权、Token 刷新放里层。
- **不要原地改 `req.headers`**：每次都用 `new Headers(req.headers)` 复制一份再传给 `next({ ...req, headers })`，这样外层触发重试时拿到的是干净的原始请求头。
- **读取内容类型用 `req.bodyContentType`**：Defjs 把自动推断的请求体媒体类型放在 `req.bodyContentType`，不会直接改 `req.headers`。写签名拦截器请读 `req.headers.get("content-type") ?? req.bodyContentType`。如果拦截器自己替换了 `req.body` 格式，记得同步改 `content-type` 头。

## 3. 重试与处理 `Retry-After`

HTTP 重试默认是关着的。遇到连接不通、超时或 `502`/`503`/`504` 时想自动换个节点重试，请用 [`withRetry()`](/zh-Hans/docs/load-balancing#retries)——每次等待完退避时间后会重新经由负载均衡选节点、重新拼请求并跑一遍完整拦截器链。

如果需要在同一个节点上处理 `429` + `Retry-After` 这类应用状态码，可以直接在 HTTP 拦截器里写等待重放：

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **和 `withRetry` 分工不同**：拦截器里的 `next(request)` 循环始终只打当前选好的那一个节点，不会重跑 `builder` 或外层拦截器。像连接超时、`502`/`503`/`504` 请交给外层的 `withRetry`。
- **`Retry-After` 要自己控制上限**：`@defjs/core` 内置的 `withRetry` 不读 `Retry-After` 响应头。示例里设的 30 秒最大等待和 250 ms 默认等待都是业务代码自己的取舍——如果限制上限短于服务端实际要求，可能提前重打过去；不希望这样就直接等满延迟，或者干脆把响应返回给业务提示用户稍后再试。
- **`401` 刷新重放写操作的幂等提醒**：参考 [401 自动刷新一次 Bearer Token](/zh-Hans/recipes/refresh-bearer-once) 时请记住，`POST` 重放有可能发两次请求体。请确保后端认证拦截在真正写库之前完成，或者带上幂等键，否则不要自动重放写请求。另外，`ReadableStream` 流式请求体不支持重放。
- **处理 `next(request)` 抛出的底层异常**：
  - 断网等传输错误会使 `next(request)` reject（Defjs 里没有 `status: 0` 的假响应），`catch` 后如果发现不是自己要处理的情况直接重新 `throw` 出去，就能原样保留原本的 `NET_*` 错误码。
  - 若请求连平台校验都过不去（例如 `GET` 带请求体、非法方法、含账密 URL、无效 `Content-Type`），或者 `finalizeHeaders` 钩子抛错，`next(request)` 会直接 reject 平台原始 `TypeError` 或钩子的报错——原样重新抛出就会保留 `REQ_BUILD_FAILED` 或 `EXT_HOOK_FAILED`；如果拦截器吞掉原异常并 `throw new Error(...)`，整个调用就会算成你拦截器自己的错（`EXT_INTERCEPTOR_FAILED`）。
  - 其余像响应流读失败、JSON 语法损坏、`Content-Type` 对不上或上传进度观察者抛错（`EXT_OBSERVER_FAILED`），在 `next(request)` 返回时会先以 `BodyFailure` 形态出现。
- **在拦截器里主动 `throw` 会怎样**：拦截器自身没接住的异常（或者给 `next()` 传了非法的 `signal`）会让最终元组返回 `EXT_INTERCEPTOR_FAILED`，原异常挂在 `err.cause`；如果特意抛出 `ERR_ABORTED` 或 `ERR_TIMEOUT`，则会分别映射成 `NET_ABORTED` 或 `NET_TIMEOUT`。

在 **SSE** 上如果想做断线重连，请用 `withRetry`，不要在 SSE 拦截器里自己写循环反复调 `next()`。在拦截器里多次重调用 `next()` 会让外层均衡器无法准确统计后续重连流的节点归因（注：这和消费者读取流时 `for await` 内部的迭代器毫无关）。

## 5. 观察整次操作调用 [#operation-interceptors]

传输拦截器一次只看到一个请求：校验失败的输入到不了它，每次重试都会再运行它，响应在它返回之后才解码。想观察调用本身，也就是从 `getOrder(client, input)` 被调用到它的元组 resolve 为止，请用 `createOperationInterceptor`：

<include cwd lang="typescript">
  examples/api/create-operation-interceptor.ts#example
</include>

- **能看到什么**：`call` 描述定义：`transport`（`"http"`、`"sse"` 或 `"websocket"`）、`method`、`path` 模板和 `meta`。它不带输入或请求，因为那时两者都还不存在。`next()` 以操作的元组 resolve，所以 `err` 就是最终的 Fault：`REQ_INPUT_INVALID`、`REQ_BUILD_FAILED`、`HTTP_STATUS`、`RES_STRUCT_MISMATCH` 等等。
- **只观察，不修改**：`next()` 不接收参数，第二次调用 `next()` 返回同一个 promise，不会再次运行调用，函数也只能以 `next()` resolve 的值来 resolve。要修改请求和响应，请用传输拦截器。
- **顺序**：操作拦截器按注册顺序运行，位于所有传输拦截器之外。围绕 `next()` 运行的代码，例如 OpenTelemetry 的 `context.with`，对整次调用都有效，包括其中的传输拦截器。
- **流与会话**：SSE 或 WebSocket 调用在流或会话打开后即 resolve；之后在其上发生的事情通过它的 `closed` 观察。
- **失败**：抛出或 reject 会让操作以 `EXT_INTERCEPTOR_FAILED` resolve，抛出的值作为 `cause`。调用已打开的流或会话会被关闭。

## 6. 内置工厂与工具函数速查

| 导出函数                                       | 适用协议  | 作用说明                                                                     |
| ---------------------------------------------- | --------- | ---------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP      | 包装 `(req, next) => Promise<HttpResponse<unknown>>`                         |
| `createSSEInterceptor(fn)`                     | SSE       | 包装 `(req, next) => Promise<EventStreamHandle<unknown>>`                    |
| `createWebSocketInterceptor(fn)`               | WebSocket | 包装 `(req, next) => Promise<WebSocketSessionLike>`                          |
| `createOperationInterceptor(fn)`               | 全部      | 围绕整次操作调用包装 `(call, next) => Promise<result>`                       |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP      | 接收同步凭据函数（每次请求调一次），自动加 `Authorization: Basic ...` 请求头 |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE       | 在 SSE 发起握手请求时自动加 `Authorization: Basic ...` 请求头                |
