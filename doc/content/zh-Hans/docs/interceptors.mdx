# Interceptors

加鉴权 header、短路维护窗口、重试安全读——不用碰 command 校验。每种传输各有一条链。你拿进 `HttpRequest`，返回该传输的结果（`HttpResponse`、事件流 handle 或 WebSocket session）。输入校验在链前；状态分派和解码结果在链后。

## 洋葱顺序

`withInterceptors(...items)` 收混合 interceptor。Client 按选中传输的 `kind` 过滤，保留相对注册顺序。每个 interceptor 可以在 `next` 前后各跑一段：

| Factory                      | Request       | `next` 的结果                         |
| ---------------------------- | ------------- | ------------------------------------- |
| `createHttpInterceptor`      | `HttpRequest` | `Promise<HttpResponse<unknown>>`      |
| `createSSEInterceptor`       | `HttpRequest` | `Promise<EventStreamHandle<unknown>>` |
| `createWebSocketInterceptor` | `HttpRequest` | `Promise<WebSocketSessionLike>`       |

<include cwd lang="typescript">

</include>

多次 `withInterceptors(...)` 会追加。外层要看到最终结果时，把宽观察放在窄变更/重试外面。

SSE 同理。浏览器 WebSocket 不能加任意握手 headers——改 `request.headers` 鉴权不了浏览器 socket。用协议、URL/query 策略，或服务端支持的握手。

替换 HTTP body 时，在拷贝请求上换 `body`。Body 值变了，Fetch 会忽略过期的 content-type 元数据。别复用已消费的 `ReadableStream` body。

Command 层仍按状态分派。调用方要类型化 `error.data` 时，用一个 `error` struct 描述非 2xx 侧。它也仍会检查声明过的那一侧：JSON `output` 或 `error` 要求合成响应带 JSON `content-type` header，`body` 则应当已经是解析后的值，和传输会交付的一样（`request.responseType` 与 `request.errorResponseType` 指明表示方式）。短路 SSE 或 WebSocket 需要完整兼容的 handle/session（关闭 promise、实时状态、所有权和 `[Symbol.asyncDispose]`）。半截对象不是合法策略。结构化 `EventStreamHandle` 与 `WebSocketSessionLike` 实现现在编译时必须提供标准 disposer；只接收 Defjs handle 的消费者无需新增运行时调用。

## 重试安全读

重试会改行为。策略收窄——这个例子只对可重放的 `GET` / `HEAD` / `OPTIONS`、状态 `429`、`502`、`503`、`504` 重试，把 `Retry-After` 封到 30s，两次重试或 abort 就停：

<include cwd lang="typescript">
  examples/interceptors/retry-safe-reads.ts#example
</include>

这个循环不会重试 interceptor/Fetch 抛出的错误——传输失败是 reject，根本不会产出一个能让这个循环去匹配的状态。重试 `POST` / `PUT` / `PATCH` / `DELETE` 需要可重放字节、服务端支持、幂等契约，以及审过的状态策略。重试归你管——Core 不导出 `retryAfter()`。

在这个示例之外抛错（或 reject）的 interceptor，会以 `EXT_INTERCEPTOR_FAILED` 回到调用方，抛出的值挂在
`cause` 上——见 [Errors](/zh-Hans/docs/errors)。在 HTTP interceptor 里，想表达取消就改成抛 `ERR_ABORTED` 或 `ERR_TIMEOUT`：调用会以 `NET_ABORTED` 或 `NET_TIMEOUT` resolve。SSE 和 WebSocket interceptor 没有这个例外，任何抛错都会报为 `EXT_INTERCEPTOR_FAILED`。

`next(request)` 可能 reject。传输失败是 fault，不是 status 0 的响应，所以想观察它的 interceptor 要在
`next` 外面套 `try` / `catch`。Defjs 的归因照样是对的：来自传输层的 reject 仍然是 `NET_*` fault，不会
算到你的 interceptor 头上。

展开 session 会把 `state` / `connection` / `bufferedAmount` 快照一次。除非你故意改所有权，否则保留 `closed`、`receive`、`close`、精确的 `[Symbol.asyncDispose]()` 转发和监听清理。Wrapper 必须返回内部 session 的 teardown promise，不能返回无关的 resolved promise。链创建了 session 却没交出去时，Core 会 settle 并关闭它；成功 interceptor 返回不同 session 时，Core 丢掉创建出来的那个。

## 参考

Factory 返回带标签的传输值：

- `createHttpInterceptor(fn)` → `{ kind: 'http', fn }`
- `createSSEInterceptor(fn)` → `{ kind: 'sse', fn }`
- `createWebSocketInterceptor(fn)` → `{ kind: 'web-socket', fn }`
- `basicAuthHttpInterceptor(provider, options?)` — HTTP 上的 Basic 凭证
- `basicAuthSSEInterceptor(provider, options?)` — SSE 上的 Basic 凭证

`HttpRequest` 可含 `endpoint`、`baseEndpoint`、`method`、`headers`、`body`、`queryParams`、`queryString`、`abort`、`timeout`、静态 `operation`。它是传输集成值——不是调用方解析后的输入。`queryParams` 是序列化之后的 `new URLSearchParams(queryString)`。builder 没产出 query 时，配好的 query serializer 不会被调用；builder 返回的 `URLSearchParams` 原样使用。Command 校验、output 校验、领域错误映射留在各自层。

SSE/WebSocket observer 是生命周期钩子，不是控制流。所有者结束时退订 WebSocket 监听。Observer 失败跟传输契约走；interceptor 本身可以抛或 reject。

日志用审过的白名单：静态 `operation`、method、status、耗时、稳定错误 code。默认别日志解析后的 URL、query、鉴权 headers、body、原始 cause、SSE 事件 ID、WebSocket payload。

Basic 凭证是 base64，不是加密。用 TLS，服务端凭证 provider 保持请求作用域，永远别日志生成的 header。默认编码器是 `globalThis.btoa`；运行时没有 `btoa` 或需要审过的编码器时传 `BasicAuthInterceptorOptions.encode`。

Interceptor 能落实传输策略。它不是输入校验、授权或资源所有权。启动长任务的代码仍要用 `await using`，或手动关闭并 await 终止 promise。普通 HTTP 是 request-scoped，通过 timeout / `AbortSignal` 管理；`Client` 不是 `AsyncDisposable`。
