# HTTP 请求

在 SDK 中，每个 HTTP 操作都用 `defineRequest` 定义：请求方法、路径模板、`input` schema、同步 `builder`，以及 `output` / `error` 响应 schema。消费方应用导入该操作，传入配置好的 `Client`，并处理返回的 `[error, data, response]` 元组。

### SDK 设计最佳实践

- **一个定义对应一个操作**：让每个方法、路径和契约各自成为独立的定义，应用才能对未使用的操作做 tree-shaking。
- **设置静态 `operation` 名称**：使用低基数标识，例如 `"orders.read"`。遥测插件（`@defjs/opentelemetry-server`）和日志拦截器会使用它，而不会泄露 URL 或用户 ID。
- **绝不在 SDK 内嵌 Client**：只导出定义、`struct` schema 和类型。

## 2. URL 解析与路径占位符

`withEndpoint(...)` 要求传入有效的绝对 URL。它的 pathname 作为基础目录（基地址上的 query 字符串或 hash 会被丢弃）。

<include cwd>examples/http/resolve-url.ts#example</include>

- **路径占位符（`:name`）**：恰好编码一次，作为单个路径片段。斜杠、`?`、`#`、`%`、空格和 Unicode 字符都留在该片段内——不要预先编码。空字符串、`.` 和 `..` 会以 `REQ_BUILD_FAILED` 失败。
- **源与目录限制**：定义中的 path 不能是绝对 URL 或协议相对 URL（`//...`），不能包含 C0 控制字符、反斜杠、`?` 或 `#`，也不能用 `../` 逃出基地址所在目录。任何违规都会在拦截器或传输层运行之前以 `REQ_BUILD_FAILED` 失败。

## 3. 使用 `builder` 放置入参

只要操作声明了 `input`，就**必须**提供同步、纯的 `builder`，返回 `{ path?, query?, headers?, body? }`。只有没有 `input` 的操作才能省略 `builder`。

### `builder` 如何处理字段别名

| `builder` 表达式                               | 实际网络输出                                                                |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| `body: input.profile`                          | 类型化的 struct 对象：自动应用 `.alias()` 别名以及 `Date` / `bigint` 编解码 |
| `body: { profile: input.profile }`             | 外层键名 `profile` 保持字面量；内层 struct 对象保留其别名规则               |
| `body: { ...input.profile, role: "admin" }`    | 对象展开操作会保留 struct 别名；新增的 `role` 保持字面量                    |
| `body: { name: input.profile.customerName }`   | 匿名对象：键名都是字面量                                                    |
| `query: input.filter` / `headers: input.trace` | 扁平类型化对象：字段的 `.alias()` 成为网络键名                              |

### 请求体格式适配

`GET` 和 `HEAD` 不能携带请求体。其他方法下，请求体格式由 `builder` 返回的 `body` 值决定：

| `body` 取值                                                | 实际传输格式                                   | 默认 `Content-Type`                       |
| ---------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------- |
| `undefined` / 省略                                         | 不发送请求体                                   | —                                         |
| 带有 `urlencoded` / `formData` 编解码器的根 struct         | `URLSearchParams` / `FormData`（自动应用别名） | 表单类型 / Multipart Boundary             |
| 原生 `FormData` 或 `URLSearchParams`                       | 原样直接传输                                   | Multipart Boundary / urlencoded           |
| `Blob` / `File`                                            | 原样二进制传输                                 | `blob.type` 或 `application/octet-stream` |
| `ArrayBuffer`、类型化数组、`DataView`、`ReadableStream`    | 原始字节流 / 流式传输                          | `application/octet-stream`                |
| `string` 纯字符串                                          | UTF-8 文本                                     | `text/plain;charset=UTF-8`                |
| 普通对象、数组、有限数字、布尔值、`null`、`Date`、`bigint` | 经 struct 编码的 JSON                          | `application/json`                        |

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

无法用 JSON 表示的值（`NaN`、`±Infinity`、`Map`、`Set`、函数、没有 `toJSON()` 的类实例或裸可迭代对象）会立即以 `REQ_BUILD_FAILED` 失败，而不是静默序列化成 `{}` 或 `null`。

## 4. 响应如何解码

`output` 校验 `2xx` 响应；`error` 校验非 `2xx` 响应（`3xx`、`4xx`、`5xx`）。struct 类型决定响应流如何读取（`struct.string()` → 文本，`struct.blob()` / `struct.file()` → `Blob`，`struct.arrayBuffer()` → `ArrayBuffer`，其他 → JSON）：

1. **按 `ok`（`200..299`）选择一侧**：`2xx` 用 `output`，非 `2xx` 用 `error`。
2. **省略即不读取**：该侧没有声明 struct 时，响应 body 从不读取（`2xx` 解析为 `data: undefined` + `HttpMeta`；非 `2xx` 解析为 `HTTP_STATUS` 且 `data: undefined`）。
3. **先校验 JSON 媒体类型**：对于 JSON struct，非 JSON 的 `Content-Type` 会在读取或查找 body 之前以 `RES_MEDIA_TYPE_INVALID` 失败。没有内容的响应（`HEAD`、`204`、`205`、`304`）与其他响应一样接受声明的约束。
4. **读取并解析**：无法读取的流或无效 JSON 以 `RES_DECODE_FAILED` 失败（流中途截断时为 `NET_BODY_INCOMPLETE`）。
   没有内容的响应（`HEAD`、`204`、`205`、`304`）没有 body 可读：`struct.string()` 得到 `''`，`struct.arrayBuffer()` 得到空的 `ArrayBuffer`，`struct.blob()` 得到空的 `Blob`。通过了第 3 步的 JSON struct 会解析这些空字节，并以 `RES_DECODE_FAILED` 失败。
5. **用 `struct` 校验**：schema 不匹配以 `RES_STRUCT_MISMATCH` 失败。

## 5. 取消请求与设置超时期限 [#cancel-the-work]

在派生的单次调用 Client 上传入 `signal`：`client({ signal })`。

- **期限（`NET_TIMEOUT`）**：使用 `AbortSignal.timeout(ms)`。
- **手动取消（`NET_ABORTED`）**：使用 `AbortController`。
- **组合信号**：使用 `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`。

## 6. 凭证、XSRF 与传输进度

- **`withCredentials(true)`**：为 HTTP 和 SSE 请求设置 Fetch `credentials: "include"`。
- **`withXSRF(options?)`**：来自 `@defjs/core/xsrf`。在浏览器中读取 XSRF cookie（默认 `XSRF-TOKEN`），并在同源的变更类 HTTP 方法（`POST`、`PUT`、`PATCH`、`DELETE`）上注入请求头（`X-XSRF-TOKEN`）。调用 `withXSRF()` 时，若缺少 `location` 或 `document`（包括 Worker）会抛错。同构代码只在浏览器里添加这个选项。令牌来自别处时，用拦截器设置。同源检查针对的是库构建出的 URL；Fetch 自己跟随重定向，并在重定向到另一个源之后保留这个请求头（它只移除 `Authorization`）。要拒绝这种情况，见 [`withXSRF`](/zh-Hans/api/core/withxsrf)。
- **`onDownloadProgress` / `onUploadProgress`**：通过 `client({ onDownloadProgress, onUploadProgress })` 传入。仅当 `Content-Length` 为正且 `Content-Encoding` 缺失或为 `identity` 时，下载进度才报告 `lengthComputable: true`。上传进度只在请求 body 是你传入的 `ReadableStream` 时才会报告；其他任何 body（`Blob`、`File`、`ArrayBuffer`、`FormData`、字符串、`URLSearchParams`）都按构建结果发送，并且在每个运行时上都不会调用 `onUploadProgress`。`ReadableStream` body 遵循 Fetch 对流式请求体的规则，无论有没有 `onUploadProgress`：Chromium 和 WebKit 只在 HTTP/2 及以上接受它，因此在 HTTP/1.1 上调用会以 `NET_UNREACHABLE` 失败（Node.js 和 Bun 接受 HTTP/1.1）；Firefox 不能流式发送请求体，并以 `ENV_UNSUPPORTED` 失败；在浏览器中，跨源请求需要 CORS 预检，除非浏览器持有缓存的预检结果；301、302、307 或 308 重定向会失败。浏览器不发送 `Content-Length`。负载均衡器对这些失败，以及对抛出的源流，收到 `{ attempted: false }`，因为 `fetch` 把它们报告成与不可达端点相同的网络错误；因此仅靠流式上传无法发现已宕机的端点。细节见 API 参考中的 `HttpProgressFn` 条目。进度回调抛出异常会以 `EXT_OBSERVER_FAILED` 使调用失败。
