# HTTP 请求

每个 HTTP 接口都用 `defineRequest` 定义：写清请求方法、路径模板、`input` schema、同步 `builder`，以及正常/错误响应的 `output` / `error` schema。业务代码拿到这个定义后，只需要传入配置好的 `Client`，再处理返回的 `[err, data, response]` 元组就行。

### 定义接口时的三条实用习惯

- **一个接口对应一个独立导出**：拆开定义之后，打包器才能把页面里没用到的接口干净地 tree-shake 掉。
- **需要给拦截器或均衡器传自定义上下文时用 `meta`**：
  - `meta` 形状是 `{ [key: string]: unknown }`，例如 `{ operation: "orders.read" }`，在拦截器（`request.meta`）和负载均衡器（`PickInfo.meta`）里都能读到。
  - 每个操作只共享同一份浅只读 `meta` 对象，所以请求级别的临时状态不要塞在 `meta` 里，而要放在拦截器执行时的闭包变量中；给 `meta` 声明类型时请用 `type` 别名而不是 `interface`（TS 不会把 `interface` 赋值给索引签名）。
  - Defjs 内核不会私自发掉 `meta`，也不会把它拼进 URL 或请求头；但 `@defjs/opentelemetry-server` 会把每个键值记成 `defjs.meta.<key>` 上报到 Span 和日志里，所以切勿往 `meta` 放 Token、密码或隐私字段。
- **绝不在定义文件里塞 `Client`**：定义文件只导出操作、`struct` schema 和类型。

## 2. 路径拼接与占位符规则

`withEndpoint(...)` 必须接收合法的绝对 URL，它的 pathname 会作为所有接口的基础前缀目录（基地址上带的 query 和 hash 会被忽略）。

<include cwd>examples/http/resolve-url.ts#example</include>

- **路径参数 `:name`**：只做一次 URL 编码，并整体作为单个路径片段。里面的斜杠、`?`、`#`、`%`、空格都会老老实实待在这个片段里——不要自己在外面手动 `encodeURIComponent`。如果参数是空字符串、`"."` 或 `".."`，会立即报错 `REQ_BUILD_FAILED`。
- **防路径逃逸约束**：定义里的 `path` 不能写成完整 URL 或协议相对 URL（`//...`），不能含控制字符、反斜杠、`?` 或 `#`，也不能靠 `../` 跳出 `endpoint` 的基础目录，违规则在拦截器和网络请求之前直接报 `REQ_BUILD_FAILED`。

## 3. 用 `builder` 把参数放到位

只要定义了 `input`，就**必须**配一个同步、无副作用的纯函数 `builder`，返回 `{ path?, query?, headers?, body? }`。只有完全不需要入参的接口才可以省略 `builder`。

### `builder` 里怎么触发 `.alias()` 字段转换

| `builder` 写法                                 | 实际发到网络上的结果                                                        |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| `body: input.profile`                          | 直接交出 `struct` 对象：自动应用 `.alias()` 别名和 `Date` / `bigint` 编码   |
| `body: { profile: input.profile }`             | 外层键名 `profile` 按字面量发；里面的 `input.profile` 仍保留别名映射        |
| `body: { ...input.profile, role: "admin" }`    | 展开对象会带走原有的别名规则；新写的 `role` 按字面量发                      |
| `body: { name: input.profile.customerName }`   | 全新匿名对象：所有键名都按你手写的字面量发送                                |
| `query: input.filter` / `headers: input.trace` | 扁平 `struct` 对象：字段上的 `.alias()` 会自动变成 query 键名或 header 名称 |

### 后端要特殊格式的查询参数？用 `withQuerySerializer`

默认情况下，普通值和一维数组（同键重复）直接序列化，遇到嵌套对象会直接报错 `REQ_BUILD_FAILED`。如果后端接口需要 `filter[status]=paid` 这种风格，在 `Client` 上挂 `withQuerySerializer` 即可：

<include cwd>examples/http/query-serializer.ts#example</include>

`withQuerySerializer` 返回的字符串会被解析进标准 URL 查询参数并最终以 `query.toString()`（`application/x-www-form-urlencoded`）发送。空格会编成 `+`，方括号会以 `filter%5Bstatus%5D=paid` 发出，绝大多数后端框架都会原样还原成同一个字段名。

### 请求体格式自动适配

`GET` 和 `HEAD` 不能带请求体。其他 HTTP 方法的请求体格式，取决于 `builder` 返回的 `body` 是什么类型：

| `body` 传的值                                              | 实际发出的请求体                               | 默认 `Content-Type`                       |
| ---------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------- |
| `undefined` / 不返回                                       | 不发 body                                      | —                                         |
| `struct.urlencoded` / `struct.formData` 构造的根对象       | `URLSearchParams` / `FormData`（自动保留别名） | 表单类型 / Multipart Boundary             |
| 原生 `FormData` 或 `URLSearchParams`                       | 原样发送                                       | Multipart Boundary / urlencoded           |
| `Blob` / `File`                                            | 原样二进制发送                                 | `blob.type` 或 `application/octet-stream` |
| `ArrayBuffer`、类型化数组、`DataView`、`ReadableStream`    | 原始字节流 / 流式发送                          | `application/octet-stream`                |
| `string` 纯字符串                                          | UTF-8 文本                                     | `text/plain;charset=UTF-8`                |
| 普通对象、数组、有限数字、布尔值、`null`、`Date`、`bigint` | 按 `struct` 编码为 JSON                        | `application/json`                        |

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

JSON 表达不了的值（比如 `NaN`、`±Infinity`、`Map`、`Set`、函数、没写 `toJSON()` 的类实例或裸可迭代对象）会在发出前直接报 `REQ_BUILD_FAILED`，不会偷偷给你序列成 `{}` 或 `null`。

## 4. 响应体怎么解码

`output` 校验 `2xx` 响应；`error` 校验非 `2xx` 响应（`3xx`、`4xx`、`5xx`）。读流方式跟着 `struct` 类型走（`struct.string()` → 文本，`struct.blob()`/`struct.file()` → `Blob`，`struct.arrayBuffer()` → `ArrayBuffer`，其余 → JSON）：

1. **按 `ok`（`200..299`）选一侧**：`2xx` 看 `output`，其余看 `error`。
2. **没写就不去读**：对应那一侧没有声明 `struct` 时，根本不读取响应流（`2xx` 直接返回 `data: undefined` + `HttpMeta`；非 `2xx` 返回 `HTTP_STATUS` 且 `data` 为 `undefined`）。
3. **JSON 先验媒体类型**：声明了 JSON `struct` 但响应头 `Content-Type` 不是 JSON 时，直接报 `RES_MEDIA_TYPE_INVALID`（`HEAD`、`204`、`205`、`304` 这种无内容响应也一视同仁）。
4. **读取并解析**：读流出错或 JSON 解析失败会返回 `RES_DECODE_FAILED`（传输半路被截断则是 `NET_BODY_INCOMPLETE`）。对 `HEAD`/`204`/`205`/`304` 来说：`struct.string()` 会拿到 `""`，`arrayBuffer()` / `blob()` 拿到空二进制对象，而通过第 3 步检查的 JSON `struct` 会因空体无法解析而返回 `RES_DECODE_FAILED`。
5. **用 `struct` 校验**：字段缺漏或类型对不上会返回 `RES_STRUCT_MISMATCH`。

## 6. 凭据、XSRF 与上传下载进度

- **`withCredentials(true)`**：同时为 HTTP 与 SSE 请求开启 Fetch `credentials: "include"`。
- **`withXSRF(options?)`**（从 `@defjs/core/xsrf` 导入）：
  - 在浏览器中自动读取 XSRF Cookie（默认 `XSRF-TOKEN`），并对同源的变更类请求（`POST`、`PUT`、`PATCH`、`DELETE`）自动带上请求头（默认 `X-XSRF-TOKEN`）。
  - **非浏览器环境注意**：缺少 `location` 或 `document` 时（包括 Node、Bun 和 Web Worker）调用 `withXSRF()` 会直接抛错，同构项目请先判断运行环境再挂载（自定义读取 Token 请改用拦截器）。另外，同源校验只检查请求构造出来的 URL；如果接口发生跨源 `30x` 重定向，原生 `fetch` 不会自动帮你剥除这个头（它只删 `Authorization`），需要严禁跨源携带请见 [`withXSRF`](/zh-Hans/api/core/withxsrf)。
- **`onDownloadProgress` / `onUploadProgress`**（通过 `client({ onDownloadProgress, onUploadProgress })` 传入）：
  - **下载进度**：仅当响应头带有正数 `Content-Length` 且没有开启压缩编码（`Content-Encoding` 缺失或为 `identity`）时，`lengthComputable` 才为 `true`。
  - **上传进度**：只有当你传给 `body` 的是你自己创建的 `ReadableStream` 时才会回调 `onUploadProgress`；像 `Blob`、`File`、`FormData`、字符串等常规请求体都不会触发。
  - **流式上传的运行时差异**：即使没传 `onUploadProgress`，传 `ReadableStream` 当请求体也要遵守浏览器原生限制——Chromium / WebKit 仅在 HTTP/2+ 支持流式上传（跑在 HTTP/1.1 会变成 `NET_UNREACHABLE`），Firefox 完全不支持（会报 `ENV_UNSUPPORTED`），Node.js 和 Bun 支持 HTTP/1.1；跨源流式上传在浏览器必须有 CORS 预检放行，且遇到 `301`/`302`/`307`/`308` 重定向会失败，浏览器也不发 `Content-Length`。
  - **与均衡器的关系 & 异常捕获**：以上因 Fetch 限制导致的失败和源流抛错，均衡器会收到 `{ attempted: false }`（单靠流式上传失败无法触发节点摘除）；如果在进度回调里自己抛出异常，调用会以 `EXT_OBSERVER_FAILED` 结束。详细签名见 API 参考中的 `HttpProgressFn`。
