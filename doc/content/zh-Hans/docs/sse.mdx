# SSE 事件流

在 SDK 中，通过 `defineEventStream` 声明服务端推送事件（Server-Sent Events）端点，指定 URL 路径、可选的输入参数与 `builder`、强类型的事件字典 `events`，以及针对缓冲区与等待队列的安全上限。消费方应用在自己的 Client 上配置认证凭据以及可选的自动重连策略，打开事件流，通过异步迭代器消费事件，并全权掌控连接的关闭与销毁。

## 1. 声明事件流并在应用中消费

对于成功打开的 `EventStreamHandle` 句柄，推荐始终通过 `await using`（或在 `finally` 块中调用 `stream.close()` 并等待 `await stream.closed`）来确保连接的绝对释放：

<Tabs items={["sdk/orders-stream.ts", "app/watch-orders.ts", "Single-file quick look"]}>
<Tab value="sdk/orders-stream.ts">

```ts
import { defineEventStream, struct } from "@defjs/core";

export const watchOrders = defineEventStream({
  path: "/orders/events",
  operation: "orders.watch",
  events: {
    updated: struct.object({
      id: struct.number(),
      status: struct.string(),
    }),
  },
});
```

</Tab>
<Tab value="app/watch-orders.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { watchOrders } from "../sdk/orders-stream.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, stream] = await watchOrders(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = stream;
  for await (const event of active) {
    console.log(event.event, event.data.id, event.data.status);
    break;
  }
}

void main();
```

## 2. 初始握手与返回元组

调用事件流操作只有在 HTTP 响应状态码为 `2xx`、媒体类型为 `text/event-stream` 且包含可读响应体时，才会成功 resolve 为 `[error, stream, startupOpen]` 元组：

- **握手返回非 `2xx` 状态码**：返回 `HTTP_STATUS` 错误（若在定义中声明了 `error` struct，则 `error.data` 会携带解码后的错误体）。
- **媒体类型不符或响应体不可读**：分别返回 `RES_MEDIA_TYPE_INVALID` 或 `RES_DECODE_FAILED`。
- **`startupOpen` 与 `stream.open` 的区别**：元组中的第三项 `startupOpen` 是首次建立连接时的握手快照；而 `stream.open` 则会随着后续发生的自动重连动态更新为最新一次物理连接的快照。

## 3. 事件路由分派与解码

当底层收到一个 SSE 数据帧时（以 WHATWG 规定的空行作为结束标识）：

1. **事件路由匹配**：根据数据流中的 `event:` 字段匹配 `events[eventName]`；若未指定 `event:` 字段，则默认寻找 `message`。若未匹配且定义了 `events.default`，则降级由其处理；未声明且无默认分支的事件将被自动丢弃。
2. **数据载荷解码**：若 Schema 声明为 `struct.string()`，则直接接收原始文本 `data:`；对于其他任意类型的 struct，均会先将 `data:` 解析为 JSON，然后再通过 struct 进行强类型校验。
3. **监听无效事件**：遇到格式非法或未声明的事件时，连接不会被异常中断，它们会被安全跳过。若需排查诊断，可在 Client 上配置 `withSSEOnInvalidEvent(...)`：

## 4. 自动重连与 `Last-Event-ID` [#reconnect]

SSE 的断线自动重连是**显式开启（opt-in）**的。若未配置 `withSSEReconnect(...)`，任何网络抖动或流读取异常都会直接终结整个流。

<include cwd>examples/sse/reconnect.ts#example</include>

- **重试预算（`attempts`）**：调用 `withSSEReconnect` 传入配置时默认重试 `3` 次。握手成功后会重置重试计数器和退避指数。服务端的正常 EOF 断开**不属于**错误，不会触发重连。
- **游标追踪（`Last-Event-ID`）**：只有在完整解析到事件末尾的终止空行后，才会正式提交游标 ID，并在重连时自动通过 `Last-Event-ID` 请求头发送。
- **幂等性安全限制**：默认情况下，只有幂等请求方法（`GET`、`HEAD`、`OPTIONS`、`PUT`、`DELETE`）才会自动执行重连。对于非幂等方法（如用于大模型流式输出的 `POST` 或 `PATCH`），只有在自定义的 `shouldReconnect` 回调显式返回 `true` 时才会重连。`ReadableStream` 类型的请求体在首次调用时即被消耗，永远不会重连。
- **握手超时保护（`connectTimeoutMs`）**：若提供，它必须是有限正数，且不得大于 2147483647（计时器上限）；否则该操作返回 `REQ_OPTIONS_INVALID`。它用于对每次握手请求（从发起 Fetch 到收到响应头）设置时间上限，但不会影响已建立的长连接存活时长。

## 5. 缓冲区与等待队列上限

这两项阈值均必须是大于零的安全整数。超出任何一项限制都属于致命错误（`stream.closed` 将以 `kind: "error"` 终结，异步迭代器会直接抛出异常——绝不会静默丢失事件）：

| 定义配置项      | 控制边界                                                        | 终态 Fault 错误码     |
| --------------- | --------------------------------------------------------------- | --------------------- |
| `maxBufferSize` | 单个 SSE 帧在遇到空行之前所允许的最大不完整或过长字节数         | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`  | 已解码但尚未被 `for await` 消费的事件在内存队列中的最大积压数量 | `CAP_QUEUE_OVERFLOW`  |

## 6. 连接关闭与资源释放 [#close-and-dispose]

发起并打开事件流的代码拥有其生命周期的完整所有权。在 `for await` 循环中通过 `break`、`return` 退出或抛出异常都会自动触发流的关闭，你也可以通过 `await using` 或直接调用 `stream.close()`：
