# 负载均衡与故障转移

当应用程序通过 `withEndpoint(...urls)` 配置了多个服务基地址时，Defjs 能够智能地在对等副本间分发流量，借助被动连续熔断或主动健康检查剔除不健康节点，并在同一次调用内部对安全的 HTTP 方法可选地执行故障转移。

## 1. 选择负载均衡策略

| 均衡策略                                                                        | 适用场景                                              | 默认健康检测机制                                   |
| ------------------------------------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------- |
| [`pickFirstBalancer(options?)`](/zh-Hans/api/core/pickfirstbalancer) _（默认）_ | 前端浏览器应用，配置了有序的“主节点 + 备用区域”列表   | 默认关闭（可通过 `outlierDetection` 选项显式开启） |
| [`roundRobinBalancer(options?)`](/zh-Hans/api/core/roundrobinbalancer)          | 服务端对等副本间调用（支持配置可选的 `weights` 权重） | 默认开启（连续 `5` 次失败后熔断剔除）              |
| [`p2cBalancer(options?)`](/zh-Hans/api/core/p2cbalancer)                        | 服务端调用，各副本间响应耗时或在途负载不均衡的场景    | 默认开启（连续 `5` 次失败后熔断剔除）              |

### `pickFirstBalancer` 与 `p2cBalancer` 的工作机制

- **`pickFirstBalancer`（主备粘性）**：始终停在第一个 URL 上，遇到 `NET_UNREACHABLE` 或 `NET_UNAVAILABLE`（HTTP 502、503 或 504）时才前进。配置 `failbackMs: 30_000`，在备用端点上停留这段时间之后，再探测一次主端点。
- **`p2cBalancer`（双选择随机 P2C 算法）**：不放回地随机抽取两个不同的候选端点，并选出综合评分更低的一个：`PeakEwma RTT × (pending + 1)`（或在配置 `load: "pending"` 时直接比较在途 `pending` 请求数）。其默认参数（`defaultRttMs: 30`、`decayMs: 10000`）完全遵循 Linkerd 与 tower 的业界成熟标准。

## 2. 同一次调用内的 HTTP 重试

重试由三个彼此独立的决定支配：**要不要再试一次**（`withRetry`）、**发到哪里**（运行时让均衡器重新 pick，并排除已经试过的端点），以及**等多久**（退避）。HTTP 的 `withRetry`、SSE 的 `withSSEReconnect` 和 WebSocket 的 `withWebSocketReconnect` 是对称的、各自传输上的策略。它们扁平的退避字段同名、同样校验、同样计算延迟。均衡器不知道重试策略；自定义均衡器不需要专门配合。

同一次调用内的 HTTP 重试**默认关闭**。省略 `withRetry` 时，每次调用只尝试一次，既不会创建重试预算，也不会向它存入额度。之后各次调用的选择方式不变：`pickFirstBalancer` 仍可以在一次失败的调用之后前进。`withRetry()` 与 `withRetry({})` 等价，会为 `GET`、`HEAD`、`OPTIONS` 和 `TRACE` 上的连接失败启用总共两次尝试。

这与 Go 生态一致：[gRPC 把 `retryPolicy` 放在 service configuration 里](https://grpc.io/docs/guides/retry/)，与负载均衡配置并列；[go-kit 的 `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) 则显式包住一个均衡器。二者默认都不套用应用自己的重试策略。gRPC 的重试策略要求配置退避，并使用 ±0.2 的抖动；[Envoy 默认以 25 毫秒为基数，上限是该基数的十倍](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff)。Defjs 使用 25 毫秒、系数 2、250 毫秒上限，以及 ±20% 的抖动。gRPC 可以针对底层竞态做透明重试；Defjs 不模拟这些行为。

- **总尝试次数（`maxAttempts`）**：包含首次尝试，与 gRPC 的 `retryPolicy.maxAttempts` 以及 go-kit `lb.Retry` 的 `max` 一致。该值必须是至少为 1 的安全整数；`1` 表示不重试。没有配置上的上限，但每个端点最多尝试一次。流式请求 body 从不重试。`methods` 不区分大小写；`methods: []` 会关闭所有方法的重试。
- **重试条件（`on`）**：默认为 `["connect-failure"]`。可以追加 `"gateway-error"`，对应 `NET_UNAVAILABLE`（HTTP `502`/`503`/`504`），包括被 `RES_*` 解码拒绝的网关错误体；配置了 `attemptTimeoutMs` 时还可以追加 `"attempt-timeout"`。一次符合条件的重试会重建请求，并从最外层重新跑整条拦截器链。
- **退避（`delayMs`、`factor`、`jitter`、`maxDelayMs`）**：第 n 次重试之前，等待 `delayMs × factor^(n−1)`，并带上乘性抖动，在抖动和取整之后封顶。默认值是 `25`、`2`、`0.2` 和 `250`。`delayMs: 0` 跳过等待。与重连一样，`delayMs` 必须是非负有限数，`factor` 必须是正的有限数，`jitter` 必须是 `[0, 1]` 内的有限数，`maxDelayMs` 必须是非负有限数或正 `Infinity`。平台计时器上限仍然生效。
- **单次尝试超时 vs. 整次调用超时**：`attemptTimeoutMs` 限制单次尝试，从发起 Fetch 一直到 body 解码结束。调用方的 `client({ signal: AbortSignal.timeout(ms) })` 覆盖每一次尝试**以及退避等待**。等待期间取消会返回调用方的取消错误，并且不再 pick。
- **Finagle / Linkerd 重试预算（`budget`）**：每份 client 配置拥有一份预算，只有使用这份配置的派生 client 会共享，共享均衡器的 client 并不共享。默认值是 `percentCanRetry: 0.2`、`minRetriesPerSecond: 10`、`ttlMs: 10000`：原始流量的 20% 再加上储备。存入和取出都在十个 TTL/10 切片上惰性过期。一次重试会在等待之前先取出额度；预算耗尽时既不等待，也不重试。设置 `budget: false` 可去掉这一上限。
- **浏览器离线环境感知**：当 `navigator.onLine === false` 时，连接失败会报告 `{ attempted: false }`，此时不会推进均衡器，也不会触发重试。

后一次 `withRetry` 会替换先前的策略。`withRetry()` 与 `withRetry(undefined)` 的行为与 `withRetry({})` 相同。启用之后若要关闭重试，传入 `withRetry({ maxAttempts: 1 })`。无效的重试设置会在 HTTP 操作运行时返回 `REQ_OPTIONS_INVALID`，消息为 `Invalid retry options`。

## 3. 被动熔断剔除与主动健康检查（`outlierDetection`）

`roundRobinBalancer()` 和 `p2cBalancer()` 默认在节点选择器外层自动包裹了 [`outlierDetection`](/zh-Hans/api/core/outlierdetection) 熔断机制：

1. **连续失败熔断**：默认分类器计入 `NET_UNREACHABLE`、`NET_UNAVAILABLE` 和 `NET_SERVER_ERROR`。连续出现 `consecutiveFailures` 次（默认 `5` 次）被计入的结果后，该端点将被熔断剔除 `min(minPenaltyMs × 2^level, maxPenaltyMs)`（`1000ms` 至 `60000ms`），并加上最高 `50%` 的均匀正向抖动。
2. **单次探测恢复机制**：当冷却时间到期后，系统会分配一个探测请求尝试访问该节点。若对端响应在 `end` 开始，且不是被计入的失败，正常流量立即恢复，惩罚等级重置为 `0`；若探测失败，惩罚时间翻倍。
3. **熔断兜底防雪崩（Panic-mode Fail-open）**：如果配置的所有节点均被熔断或被判定为不健康，负载均衡器会立即进入放行兜底模式，直接使用初始候选列表分发流量，而绝不在客户端本地自毁式拒绝所有请求。

## 4. 传输层生命周期记账（`pick` → `start` → `end` → `done`）

自定义均衡器实现同步的 `pick(info)`，以及可选的 `start()`、`end(info)` 和 `done(info)` 回调。`PickInfo` 只包含候选 `endpoints` 和可选的定义 `operation`，没有传输类型判别字段。传输层把自己的事实翻译成中立的 `DoneInfo.code` 结果。内置均衡器从不读取 `status`；这份原始响应信息只留给自定义均衡器。`start` 在尝试之前运行，`end` 在对端响应开始或响应前失败时运行，`done` 在完成时运行。因此，更晚发生的 body 失败可以改变最终的 code，而不改变更早的 `end` 样本：

| 物理传输实际结果                                                     | 最终 `done(info)` 统计样本                                 |
| -------------------------------------------------------------------- | ---------------------------------------------------------- |
| HTTP/SSE 响应状态 502、503 或 504                                    | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| HTTP/SSE 其他至少为 500 的响应状态                                   | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP/SSE 响应状态 2xx、3xx 或 4xx（包括 429）                        | `{ attempted: true, status }`                              |
| HTTP 响应体在传输流中途中断                                          | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE 握手成功，随后流 `reader.read()` 发生 reject                     | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| SSE 正常 EOF、握手成功后的解码失败，或队列上限                       | `{ attempted: true, status }`                              |
| 已建立的 WebSocket 异常断开，关闭码为 `1006` 或 `wasClean === false` | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 已建立的 WebSocket 正常平稳关闭                                      | `{ attempted: true }`                                      |
| 调用方主动取消请求，或手动关闭长连接流/Socket                        | `{ attempted: false }`                                     |
| 请求尝试开始后调用方设置的超时期限到期                               | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

握手解码失败会保留由握手状态推导出的中立结果（例如状态 `503` 对应 `NET_UNAVAILABLE`）。不完整的 HTTP body 则保留 `NET_BODY_INCOMPLETE` 及其原始 status，即使那是网关响应；默认的 outlier detection 不计入它。
