# 负载均衡与故障转移

当你在 `Client` 上配置了多个服务端地址（`withEndpoint(...urls)`）时，Defjs 可以按策略选路分发请求、临时摘除连续报错的节点、跳过你自己健康检查标红的实例，并在必要时切到另一个实例重试。注意 Defjs 本身不会主观猜哪个节点“健康”：只有你传入的健康函数才会决定业务层健康状态。

## 1. 选一个适合场景的负载均衡器

| 均衡策略                                                                        | 典型适用场景                                        | 默认失败摘除                           |
| ------------------------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------- |
| [`pickFirstBalancer(options?)`](/zh-Hans/api/core/pickfirstbalancer) _（默认）_ | 前端应用连“主站点 + 备灾节点”列表                   | 关闭（传 `outlierDetection: {}` 开启） |
| [`roundRobinBalancer(options?)`](/zh-Hans/api/core/roundrobinbalancer)          | 后端之间调对等副本实例（支持按 `weights` 分配权重） | 关闭（传 `outlierDetection: {}` 开启） |
| [`p2cBalancer(options?)`](/zh-Hans/api/core/p2cbalancer)                        | 后端副本耗时或当前并发负载经常不均的场景            | 关闭（传 `outlierDetection: {}` 开启） |

### `pickFirstBalancer`、`roundRobinBalancer` 与 `p2cBalancer` 怎么选路？

- **`pickFirstBalancer`（主备粘滞）**：
  - 默认盯住第一个地址发请求，只有遇到完全连不上（`NET_UNREACHABLE`）或 `502`/`503`/`504`（`NET_UNAVAILABLE`）时，才会往下一顺位切换（注意单次超时不会触发切换，重试仍打原节点）。
  - 配了 `failbackMs`（如 `30_000`）之后，离开主节点满这段时间就会切回第一节点再试一次；注意这个开关**纯粹按时间回切**，没东西提前探测主节点好没好——如果切回去又报错就再次顺延。务必把 `failbackMs` 设得比两次请求间隔或重连间隔更长，否则每次重选都会刚切完就回切。
- **`roundRobinBalancer`（轮询 / 加权轮询）**：
  - **无权重时**：从随机的 `uint32` 起始位开始按每次 `pick` 顺延（包括重试或流重连选节点）。所以如果没开 `outlierDetection` 且恰好是两个节点串行发请求：1 号节点挂了之后，每次新请求还是轮回 1 号先挂再重试到 2 号；并发请求会把次序错开，而开启 `outlierDetection: {}` 则能直接把坏节点暂时摘掉。
  - **带权重时**：没写权重的默认是 `1`，支持任意正数，内部走平滑加权轮询（比如 `3:1` 权重会在四次选中分给前者三次，且不会连续全挤在一起），每次选路复杂度为 O(节点数 + 候选数)。
- **`p2cBalancer`（随机二选一择优）**：
  - 每次不放回地随机抽两个可用候选节点，挑出综合得分更低的那个：`PeakEwma RTT × (pending + 1)`（若配置 `load: "pending"` 则直接比对当前在途并发数），默认参数（`defaultRttMs: 30`、`decayMs: 10000`）借鉴自 Linkerd 与 tower。
  - `pending` 计数在选中瞬间就加上，所以同一事件循环里的一批并发请求也会自动打散；在对端响应头到达（或 SSE 握手 / WebSocket 打开）时释放。因此对 SSE 和 WebSocket 来说，P2C 均衡的是“建连握手负载”而非长期已打开连接数。

**状态保存在哪里**：节点粘滞状态、摘除记录、P2C 负载和 HTTP 重试预算全部挂在 `Client` 上。全局只用一次 `createClient` 并通过 `client(options)` 派发请求，所有状态都会无缝延续；如果把同一个均衡器实例传进多个独立 `createClient`，只共享均衡器选路状态，各 Client 的重试预算分开算；如果每个请求都重新 `createClient`，状态每次都会从零开始。

## 2. 重试策略（`withRetry`）[#retries]

每次失败后要不要重试，被三个独立的问题控制：**让不让重试**（`withRetry` 配置）、**换哪个节点**（交给均衡器从全列表重新挑）、**等多久再打**（指数退避）。同一套 `withRetry(options)` 同时管 HTTP、SSE 和 WebSocket，单次调用也可以用 `client({ retry })` 临时替换策略；均衡器本身不管重试策略，自定义均衡器也不需要专门适配。

默认情况下重试**完全关闭**：不写 `withRetry` 时每次操作只打一次请求，没有退避等待也不创建 HTTP 重试预算（但不影响 `pickFirstBalancer` 下次调走坏节点）。如果只写 `withRetry()` 或 `withRetry({})`，则按默认参数启用：首次失败后最多重试 3 次（`maxRetries: 3`），从 `delayMs: 1000` 开始指数翻倍到封顶 `30000` ms，并加上 ±20% 的随机抖动（`jitter: 0.2`），默认 `statusCodes: [429, 502, 503, 504]`，并在 `429` 和 `503` 上原生支持 RFC 9110 `Retry-After`（`retryAfter: true`、`maxRetryAfterMs: 60_000`）。

这种显式开启的风格和 Go 生态对齐：比如 gRPC 的 `retryPolicy` 需在配置里单独声明（也支持抖动）；而 Defjs 的 `maxRetries` 只数“额外重试的次数”（不含首次尝试），和 `ky`、`got`、`undici` 及 Go 的 `go-retryablehttp` 口径一致（对比之下 gRPC 的 `maxAttempts` 把首轮也算在里面）。

每次尝试失败后，三种协议按完全一致的顺序做决定：

1. 如果调用方主动取消、手动 `close()`、撞上本地致命错误或使用了 `ReadableStream` 请求体，**立刻结束**（不再调用 `shouldRetry`）。
2. 当启用 `retryAfter` 且 `429` 或 `503` 响应携带有有效的 RFC 9110 `Retry-After` 延迟且超过 `maxRetryAfterMs`（默认 `60_000`）时，**直接快速结束**，不再调用 `shouldRetry` 也不消耗重试 `budget`。
3. 如果已达到 `maxRetries` 次重试上限，**直接结束**（不再调用 `shouldRetry`）。
4. 调 `shouldRetry(context)` 决定（支持 `async`，收到的 [`RetryContext`](/zh-Hans/api/core/retrycontext-type) 会按 `transport` 区分类型）；没提供该函数时直接看 `context.retryable`。自己写 `shouldRetry` 时若想保留默认判断再加规则，直接兜底 `return context.retryable;` 即可。
5. 仅 HTTP：从重试预算扣除一次额度；如果预算花光了，不等待退避直接结束。
6. 等待 `Retry-After` 延迟（当 `429` 或 `503` 响应携带且启用 `retryAfter` 时，附带不超过 `maxRetryAfterMs` 的正向抖动）或指数退避延迟，然后让均衡器重新选一次节点再发起下一次尝试。

### 五个关键细节提前理清

- **`maxRetries`（外层重试次数，默认 `3`）**：写 `0` 表示绝不重试（配合 `attemptTimeoutMs` 可以只卡单次尝试限时）。注意对 **SSE 和 WebSocket** 来说，每次成功连上都会重置已用次数，所以 `maxRetries: 1` 限制的是“单次断线最多重连几次”，不是“整段长会话最多重连几次”——如果遇到服务端刚建连就踢人的死循环，要在 `shouldRetry` 里主动熔断。此外 `maxRetries` 统计的是经过均衡器的外层重发，如果你自己的拦截器内部写了个循环反复调 `next()`，外层 `maxRetries: 1` 也可能实际打出更多物理包。
- **默认哪些错误会自动重连（`statusCodes`、`methods`）**：
  - **HTTP**：请求方法在 `methods` 内，且属于连不上（`NET_UNREACHABLE`）、状态码在 `statusCodes` 内（默认 `[429, 502, 503, 504]`）或耗尽了 `attemptTimeoutMs` 时自动重试。
  - **SSE**：方法在 `methods` 内，且发生握手连不上、握手状态码在 `statusCodes` 内（默认 `[429, 502, 503, 504]`）、握手超时或建连后流网络中断时自动重试（正常收到服务端 EOF 不算失败，直接结束）。
  - **WebSocket**：只要不是你主动调 `session.close()`（哪怕还没 open 成功或心跳没收到 ack）默认都重连；唯一不重试的是 `WebSocket` 构造函数一上来就抛错。
  - **方法安全清单（`methods`）**：默认是 `["GET", "HEAD", "OPTIONS", "TRACE", "PUT", "DELETE"]`（不区分大小写；如果拦截器里把方法改成了非清单方法就不会自动重连）。`statusCodes` 之外的状态码（如 `500`，或从自定义 `statusCodes` 中移除了 `429`）默认不自动重试（`shouldRetry` 收到的 `retryable` 为 `false`，并附带 `status` 和 `headers`，若你确认服务端幂等仍可返回 `true` 放行）。`POST` 默认**不重试**——只有在确认跨副本幂等、并在 `methods` 里显式传入 `"POST"` 或通过 `shouldRetry` 返回 `true` 后才会重发（参见 [`idempotencyKeyHttpInterceptor`](/zh-Hans/api/core/idempotencykeyhttpinterceptor)）。**提醒**：配置 `methods` 会整体覆盖默认清单，同时要重试 `GET` 和 `POST` 请写 `methods: ["GET", "POST"]`。符合条件触发 HTTP 重试时会重拼请求并从最外层拦截器重跑；SSE 复用原请求只换端点 URL，WebSocket 则重新跑 `beforeConnect`。
- **退避与 `Retry-After`（`delayMs`、`factor`、`jitter`、`maxDelayMs`、`retryAfter`、`maxRetryAfterMs`）**：第 `n` 次重试前，指数退避等待 `delayMs × factor^(n−1)`，算完 `±jitter` 乘性抖动并取整后再按 `maxDelayMs` 封顶（默认值分别为 `1000`、`2`、`0.2`、`30000`；`delayMs: 0` 跳过等待，`maxDelayMs: Infinity` 取消上限，但平台计时器上限 `2_147_483_647` ms 仍生效）。对于 SSE，若服务端推过纯数字 `retry:` 字段，后续重连会改用服务端指定的值作为基础 `delayMs`。当 `retryAfter` 为 `true`（默认值）时，Core 会在 `429` 和 `503` 的 HTTP 响应及 SSE 握手响应上原生解析 RFC 9110 `Retry-After` 头（`delay-seconds` 或 `HTTP-date`），并在 `HttpRetryContext` / `SSERetryContext` 上暴露 `headers` 和 `retryAfterMs`。此时重试不再走指数退避，而是等待 `retryAfterMs` 加上只正不负的抖动（`[1, 1 + jitter]`），确保绝不提前触发，并受 `maxRetryAfterMs` 封顶（默认 `60_000`；`Infinity` 取消上限，但仍受平台计时器上限约束）。若服务端要求的等待超过 `maxRetryAfterMs`，调用会直接快速失败而不调用 `shouldRetry` 也不消耗 `budget`。传入 `retryAfter: false` 可忽略 `Retry-After` 并改回指数退避（或在[应用拦截器](/zh-Hans/docs/interceptors)中用自定义策略处理）。
- **单次超时 vs 全程超时（`attemptTimeoutMs` vs `signal`）**：`attemptTimeoutMs` 只卡一次网络尝试的时间（HTTP 卡到读完 body，SSE 卡到拿到响应头，WebSocket 卡到 `open`），外层拦截器工作（例如 `401` 刷新 Token）与 `struct` 校验不算在里面。而通过 `client({ signal: AbortSignal.timeout(ms) })` 传的超时则管**所有重试加上中间退避等待的总耗时**——等待期间超时会直接取消并不再选节点。
- **预算与离线边界**：
  - **重试预算（`budget`，仅 HTTP）**：默认配置为 `percentCanRetry: 0.2`、`minRetriesPerSecond: 10`、`ttlMs: 10000`（相当于允许正常流量 20% 的额外重试加每秒 10 次保底额度），按 10 秒拆 10 个滑动时间桶统计。设为 `budget: false` 可关掉限额；SSE 与 WebSocket 不占 HTTP 预算，防止接口一阵抖动把实时流重连预算打光。
  - **浏览器离线判断**：当 `navigator.onLine === false` 时，连接报错会上报 `{ attempted: false }`，既不推动均衡器也不浪费 HTTP 重试。
  - **没节点可用时**：某一轮重试找不到可用节点或下一个 URL 无法解析时，HTTP 返回上一次尝试的底层错误（如 `NET_UNREACHABLE`）而不是 `REQ_BUILD_FAILED`。

后传入的 `withRetry` 会替换前一次配置；注意 **`withRetry()` 和 `withRetry(undefined)` 都会开启默认 3 次重试**，如果想明确关掉前面配过的重试，请传 `withRetry({ maxRetries: 0 })`。

### 从 `withSSEReconnect` 和 `withWebSocketReconnect` 迁移

旧版的 `withSSEReconnect` 和 `withWebSocketReconnect` 已正式移除，统一改用 `withRetry`，单次请求里的 `reconnect` 也统一更名为 `retry`：

- `attempts: N` → `maxRetries: N`。
- `shouldReconnect` → `shouldRetry`（新增 `transport` 与 `retryable` 字段，并且只有在还有剩余重试次数时才会触发；注意一旦传了 `shouldRetry`，同样会接管包括 `methods` 在内的默认规则，如果直接 `return true` 连 `POST` 流也会重试）。
- 默认退避参数对齐：SSE 的 `factor` 从 `1` 改为 `2`、`maxDelayMs` 从无上限改为 `30000`，SSE 与 WebSocket 的 `jitter` 从 `0` 改为 `0.2`。
- SSE 握手行为对齐：匹配 `statusCodes`（默认 `429`、`502`、`503` 或 `504`）的握手状态码会按可重试错误处理；其他非 `2xx` 握手以 `retryable: false` 进入 `shouldRetry`，若在重连期中止流，现在在 `stream.closed` 上报告 `HTTP_STATUS`（旧版报 `RES_DECODE_FAILED`）；`shouldRetry` 抛错在三种协议上统一报 `EXT_HOOK_FAILED`。
- WebSocket 心跳：心跳超时现在同样进入 `shouldRetry`（`retryable: true`、`code` 为空），返回 `false` 后行为与旧版相同。
- 只想重试 SSE / WebSocket 不想重试 HTTP？在 `shouldRetry` 第一行加上 `if (context.transport === "http") return false;` 即可。

```ts
// Before
createClient(
  withEndpoint(url),
  withSSEReconnect({ attempts: 3, delayMs: 1000 }),
  withWebSocketReconnect({
    attempts: 3,
    shouldReconnect: ({ code }) => code !== 1008,
  }),
);
// After
createClient(
  withEndpoint(url),
  withRetry({
    maxRetries: 3,
    shouldRetry: (context) => {
      if (context.transport === "http") return false;
      if (context.transport === "websocket" && context.code === 1008)
        return false;
      return context.retryable;
    },
  }),
);
```

### 浏览器环境必须注意的边界

- 浏览器端发生 **CORS 拦截** 时，Fetch 只会抛出网络错误并映射成 `NET_UNREACHABLE`，无法和真实机器宕机区分开——这可能会触发安全方法（如 `GET`）自动切去备节点，进而掩盖了主节点的 CORS 漏配；同时对于已经发出去的 `POST`，即使响应因为缺 CORS 头被浏览器拦下来，服务端也可能其实已经执行成功了，所以别随便对非幂等 `POST` 开重放。
- 浏览器里 WebSocket 握手被服务端拒绝（如 `401`）同样无法区分成状态码，只能收到 `NET_UNREACHABLE`，过期的鉴权 Token 也可能误伤节点健康统计。
- 同 `localhost` 不同端口的站点会共享 Cookie，但 `localhost` 和 `127.0.0.1` 不共享；跨多域名实例部署时请提前设计好 Cookie/Token 域策略。

## 3. 异常节点摘除与自定义健康检查（`outlierDetection`）

Defjs 没有内置主观的“健康状态”。[`outlierDetection`](/zh-Hans/api/core/outlierdetection) 可以传给任意内置均衡器（传入 `outlierDetection: {}` 即按默认参数开启），主要干两件事：连续失败自动暂避一段时间，以及配合你自己的 `isHealthy` 做主动过滤。

1. **怎么才算连续失败**：默认把所有带错误码的结果（`NET_UNREACHABLE`、`NET_UNAVAILABLE`、`NET_SERVER_ERROR`、`NET_TIMEOUT`、`NET_BODY_INCOMPLETE`）记作一次失败（可用自定义 `isFailure` 改规则）；一次正常无错误码的尝试就会把连续计数清零。连续失败满 `consecutiveFailures` 次（默认 `5` 次，写 `0` 关闭）就会把该节点暂时踢出候选池。
2. **按时间摘除与 `halfOpen` 试探**：每次被摘除时长按 `min(minPenaltyMs × level, maxPenaltyMs)`（默认从 `1000ms` 起步，上限 `60000ms`）加上最高 `50%` 的正向随机抖动计算（总时长不超上限）。其中 `level` 参考 gRPC 离群检测规范（gRFC A50）：每摘除一次加 1，单纯请求成功不会清掉它，得等到自上次摘除到期起连续 10 秒都没再被摘除才递减 1。默认（`halfOpen: false`）下，到期后所有调用方都可再次选中该节点；如果仍然失败，再连续出现 `consecutiveFailures` 次计入失败的结果就会以更长惩罚再次摘除（只要失败回得比等级衰减快，就会按 1s、2s、3s 递增到 `maxPenaltyMs`）。若设置 `halfOpen: true`，摘除到期后每次只放行一个试探请求：试探成功即解除门控并恢复全量流量，试探失败则不需再等 `consecutiveFailures` 次，立即按下一惩罚等级重新摘除（受 `maxEjectionPercent` 约束）。如果在节点被摘除**之前或期间**发出的滞后请求到得比较晚，即使到期后才到达也会被忽略，不会拿迟到的结果再把它罚一遍。摘除是否到期在下一次 `pick` 对照时钟判定，不跑后台定时器。
3. **接入你自己的健康状态（`isHealthy`）**：每次 `pick` 时同步对每个尚未被摘除的节点调一次（要求轻量、纯粹读取内存状态，别在里面做耗时操作或抛异常——一旦 `isHealthy` 抛错，这次调用会直接报 `REQ_BUILD_FAILED`）。返回 `false` 会跳过该节点，返回 `true` 只代表“你自己不拦截”，不会强行解除还在冷却期的摘除惩罚。
4. **有界内存记录**：在同配置 Client 上，节点健康、P2C RTT 和 Pick-first 乱序键都使用至少 256 槽位且覆盖当前节点总数的 LRU 缓存管理；正常情况下优先淘汰最久没用到的干净记录，加权轮询则严格按成员列表保留当前权重游标。计时优先采用单调 Performance 时钟。
5. **摘除配额（`maxEjectionPercent`）与全军覆没兜底（Fail-open）**：`maxEjectionPercent`（默认 `100`，不限制配额）限制同时可被摘除的候选节点数量上限（`Math.floor(endpoints.length * maxEjectionPercent / 100)`）。当配额已满时，后续失败的节点不会被摘除（如果当前已摘除的节点数超过配额，只排除惩罚时间最长、不超过上限的节点）。如果所有未被摘除的节点都被你的 `isHealthy` 否决了，均衡器会忽略 `isHealthy` 在这些未被摘除的节点中挑选；只有当所有配置的节点都被摘除（或正在等待半开试探请求完成）时，才会回退到完整候选列表放行请求，避免在本地彻底断流。

## 4. 底层传输事件与 `done(info)` 记账表（自定义均衡器必看）

自己实现均衡器时，必须原样返回 `info.endpoints` 里的某一项字符串，外层的健康过滤才能正确对接。

自定义均衡器需要实现同步的 `pick(info)` 以及可选的 `start()`、`end(info)`、`done(info)` 回调（注意运行时调用时不绑定 `this`，请在闭包里保存状态）。`PickInfo` 会给出过滤后的可用 `endpoints`、完整配置的 `members` 列表以及操作定义上的 `meta`（如果写了的话）。注意 `start` 在每次尝试前跑，`end` 在拿到对端响应或早早断连时跑，而 `done` 在整条响应体读完收尾时跑——因此响应体读到一半断了可能会让 `done` 的结果从正常变成 `NET_BODY_INCOMPLETE`：

| 底层实际发生的情况                                     | 最终传给均衡器 `done(info)` 的样本                         |
| ------------------------------------------------------ | ---------------------------------------------------------- |
| HTTP / SSE 响应状态码为 502、503 或 504                | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| HTTP / SSE 其他 >= 500 状态码                          | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP / SSE 响应状态码为 2xx、3xx 或 4xx（含 429）      | `{ attempted: true, status }`                              |
| HTTP 响应体传输到一半被截断                            | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE 握手成功但随后读取流时 reject                      | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| SSE 正常 EOF、媒体类型不对的 2xx 或帧缓冲爆上限        | `{ attempted: true, status }`                              |
| WebSocket 连上后意外断开（关闭码 `1006` 或 `1015`）    | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| WebSocket 连上后因 `1012` / `1013` 关闭                | `{ attempted: true, code: "NET_UNAVAILABLE" }`             |
| WebSocket 心跳等待 ack 超时                            | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| WebSocket 以其他任意关闭码结束（无论 `wasClean` 真假） | `{ attempted: true }`                                      |
| 调用方主动中止取消，或手动关闭流 / Socket              | `{ attempted: false }`                                     |
| `fetch` 拒绝了流式请求体（`ReadableStream` body）      | `{ attempted: false }`                                     |
| 发起尝试后超过了调用方设置的 `signal` 超时期限         | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

**特别说明**：当 HTTP 请求使用了调用方自己提供的 `ReadableStream` 请求体时，不管是因为浏览器环境不认 HTTP/1.1 流式上传、遇上 30x 重定向、CORS 预检没过还是流自己抛错了，Fetch 都会统一报成一个无法分辨原因的网络错误。因此除了给调用方返回 `NET_UNREACHABLE` 外，Defjs 只会向均衡器上报 `{ attempted: false }`——既不推进 `pickFirst`，也不冤枉摘除节点，更不会触发重试；另外若心跳 `message()` 抛错属于本地 Bug，也同样保持中立不上报节点故障。
