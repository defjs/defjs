# WebSocket-Sitzungen

`defineWebSocket` deklariert einen bidirektionalen WebSocket-Vertrag in deinem SDK: die Pfadvorlage, optionales `input` und `builder` (nur `path` und `query`), Nachrichten-Structs für `incoming` und `outgoing`, Warteschlangenlimits sowie statische Subprotokolle. Die konsumierende Anwendung konfiguriert Heartbeat, Reconnect und Ressourcen-Bereinigung an ihrem Client.

## 1. Vertrag definieren und eine Sitzung ausführen

Modelliere mehrere Frame-Typen auf `incoming` oder `outgoing` mithilfe von `struct.discriminatedUnion(...)`. Gib die zurückgegebene `WebSocketSession` mit `await using` oder explizitem `session.close()` + `await session.closed` frei:

<Tabs items={["sdk/ticks-socket.ts", "app/session.ts", "Single-file quick look"]}>
<Tab value="sdk/ticks-socket.ts">

```ts
import { defineWebSocket, struct } from "@defjs/core";

export const TickFrame = struct.discriminatedUnion("type", [
  struct.object({
    type: struct.literal("tick"),
    symbol: struct.string(),
    price: struct.number(),
  }),
  struct.object({
    type: struct.literal("subscribed"),
    symbol: struct.string(),
  }),
]);

export const SubscribeCommand = struct.object({
  type: struct.literal("subscribe"),
  symbol: struct.string(),
});

export const openTicker = defineWebSocket({
  path: "/market/ws",
  operation: "market.ticker",
  incoming: TickFrame,
  outgoing: SubscribeCommand,
  maxIncomingQueueSize: 64,
});
```

</Tab>
<Tab value="app/session.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { openTicker } from "../sdk/ticks-socket.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, session] = await openTicker(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = session;
  active.send({ type: "subscribe", symbol: "ACME" });

  for await (const message of active.receive) {
    if (message.type === "tick") {
      console.log(message.symbol, message.price);
      break;
    }
  }
}

void main();
```

## 2. Nachrichtenvalidierung und Richtungsregeln

- **Eingehende Frames (`session.receive`)**: Text-, `ArrayBuffer`-, typisierte Array- und `Blob`-Frames werden als UTF-8 dekodiert, als JSON geparst und gegen `incoming` validiert. Fehlerhaftes JSON oder Schema-Abweichungen werden an `session.onRuntimeError` gemeldet und verworfen, ohne die Sitzung zu schließen. `session.receive` erlaubt nur einen einzigen Konsumenten; das Anfordern eines zweiten Iterators wirft einen `TypeError`.
- **Ausgehende Frames (`session.send(payload)`)**: Validiert synchron gegen `outgoing`, wendet `.alias()` und Codecs an und serialisiert mit `JSON.stringify`. Sendet sofort, wenn `open`, puffert während `reconnecting` (falls `maxOutgoingQueueSize > 0`) und wirft synchron einen Fehler, falls die Payload ungültig ist, die Warteschlange voll/deaktiviert ist oder die Sitzung bereits geschlossen wurde.

## 3. Sitzungsstatus und Beobachter

| Element              | Beschreibung                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `state`              | `'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'` |
| `connection`         | Live-Snapshot des aktuellsten physischen Sockets (`generation`, `url`, `protocol`, `extensions`)      |
| `bufferedAmount`     | Ungesendete Byte-Anzahl am aktiven Socket (`0` bei getrennter Verbindung)                             |
| `receive`            | Asynchroner Iterable für einen einzelnen Konsumenten mit validierten `incoming`-Nachrichten           |
| `onStateChange(fn)`  | Abonniert Statusübergänge; gibt eine `unsubscribe`-Funktion zurück                                    |
| `onRuntimeError(fn)` | Abonniert Frame-/Parsing-Fehler nach dem Verbindungsaufbau; gibt eine `unsubscribe`-Funktion zurück   |
| `closed`             | Promise, das mit dem finalen Ergebnis auflöst (`kind: 'closed' \| 'aborted' \| 'error'`)              |

## 4. Reconnect, Heartbeat und Warteschlangen

Sowohl Reconnect als auch Heartbeat sind Opt-in über Client-Optionen (`withWebSocketReconnect`, `withWebSocketHeartbeat`) oder pro Aufruf abgeleitete Optionen (`client({ reconnect, heartbeat })`):

- **Reconnect**: Standardwerte im aktivierten Zustand sind `attempts: 3`, `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000`, `jitter: 0`. Jedes physische `open` setzt das Ausfallbudget zurück. `beforeConnect({ attempt, signal })` wird vor dem ersten Verbindungsaufbau und vor jedem Reconnect-Versuch ausgeführt.
- **Handshake-Timeout (`connectTimeoutMs`)**: Wenn angegeben, muss es endlich, positiv und nicht größer als 2147483647 (die Timer-Obergrenze) sein; sonst gibt die Operation `REQ_OPTIONS_INVALID` zurück. Es begrenzt die Konstruktion bis `open` und wird nach dem Handshake gelöscht.
- **Heartbeat**: Sendet periodisch `message()` durch das `outgoing`-Struct und wartet bis zu `timeoutMs` auf einen Frame, der `isAck(msg)` erfüllt. Passende Bestätigungs-Frames werden vom Heartbeat-Monitor konsumiert und nicht an `session.receive` weitergeleitet. Ein ausbleibendes Ack ist für die logische Sitzung fatal: `closed.kind` ist `"error"` und `closed.cause` der gewöhnliche `Error("WebSocket heartbeat timeout")`; es startet keinen Reconnect. Heartbeat-Serialisierungsfehler folgen demselben fatalen Pfad mit ihrer ursprünglichen Ursache.
- **Warteschlangenlimits**:
  - `maxIncomingQueueSize` (erforderliche positive Ganzzahl): Begrenzt sowohl Roh-Frames, die auf Dekodierung warten, als auch dekodierte Nachrichten, die auf den Konsumenten warten. Ein Überlauf beendet die Sitzung mit einem `CAP_QUEUE_OVERFLOW`-Fault als `closed.cause`; dieselbe Ursache wird an `onRuntimeError` gesendet und lässt `session.receive` fehlschlagen. Stelle sicher, dass `session.receive` kontinuierlich konsumiert wird, solange die Sitzung geöffnet ist.
  - `maxOutgoingQueueSize` (optionale nicht-negative Ganzzahl, Standard `0`): Puffert `session.send()`-Aufrufe ausschließlich während `state === 'reconnecting'` und leert sie vor dem Veröffentlichen des nächsten `open`.

`shouldReconnect` erhält den nativen Close-Code und `wasClean`. Ein Server kann einen regulären Close-Handshake mit dem Anwendungsfehlercode `1011` abschließen; `wasClean === true` bedeutet daher nicht, dass die Anwendung erfolgreich war. Das Beispiel erlaubt `1011` ausdrücklich; wähle Anwendungscodes nach deinem Protokoll, statt dich allein auf `!wasClean` zu verlassen.

## 5. Subprotokolle und Authentifizierung [#protocols-and-authentication]

Browser-WebSockets unterstützen keine beliebigen Handshake-Header, weshalb WebSocket-`builder`-Funktionen nur `{ path?, query? }` zurückgeben dürfen.

- **Vorrang von Subprotokollen**: `client({ protocols })` überschreibt `withWebSocketProtocols(...)`, was wiederum `defineWebSocket({ protocols })` überschreibt.
- **URL-Konvertierung**: Defjs wandelt `http:` automatisch in `ws:` und `https:` in `wss:` auf dem aufgelösten Endpunkt um.
- **Zugangsdaten**: `withCredentials(true)` gilt ausschließlich für Fetch (HTTP/SSE). Authentifiziere WebSockets über Cookies/Session-Richtlinien, Subprotokolle oder kurzlebige Connection-Tickets – vermeide langlebige Geheimnisse in Query-Parametern.
- **`beforeConnect` verändert keinen Request**: Input-Parsing, der synchrone reine `builder` und die Interceptor-Kette laufen einmal pro Operation. Bei einem Request, dessen Basis-Endpunkt nicht von einem Interceptor ersetzt wurde, wählt jeder Reconnect erneut einen Endpunkt und baut die URL damit neu auf, verwendet aber den gebauten Pfad/die Query und die erfasste Protokollliste wieder. Die URL steht vor dem `beforeConnect` dieses Versuchs fest, sowohl am selben Endpunkt als auch nach einem Failover. Das Ändern einer Closure-Variablen, des Inputs oder des Protokoll-Arrays im Hook kann dem aktuellen Handshake kein frisches Ticket geben. URL-/Subprotokoll-Zugangsdaten innerhalb einer Sitzung auszutauschen wird nicht unterstützt; beschaffe zuerst die neuen Zugangsdaten, übergib sie als Input oder Client-Konfiguration an eine neue Operation und übernimm dann die Bereinigung dieser Ersatz-Sitzung.

## 6. Schließen und Besitz

Rufe `session.close(code?, reason?)` auf (wobei `code` den Wert `1000` oder `3000..4999` haben darf und `reason` ≤ 123 UTF-8-Bytes lang sein muss) und warte auf `await session.closed`, oder nutze `await using`:

Sind bei einem Reconnect-Ausfall alle Versuche ausgeschöpft, endet die Sitzung mit `closed.kind: "error"`, dem nativen Close-Snapshot (bei einem fehlgeschlagenen Upgrade oft Code `1006`) und dem gewöhnlichen Transportfehler als `closed.cause`; sie stellt keinen separaten stabilen Code für die Erschöpfung bereit. Melde Listener von `onStateChange` und `onRuntimeError` stets ab, wenn deine Komponente oder dein Worker beendet wird.
