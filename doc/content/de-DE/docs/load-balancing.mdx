# Lastverteilung & Failover

Wenn eine Anwendung mehrere Basis-URLs über `withEndpoint(...urls)` konfiguriert, kann Defjs Anfragen auf Replikate verteilen, fehlerhafte Hosts durch passives Circuit-Breaking oder aktive Health-Checks vorübergehend ausschließen und bei sicheren HTTP-Methoden optional innerhalb desselben Aufrufs ein Failover ausführen.

## 1. Load-Balancer-Strategie wählen

| Strategie                                                                       | Am besten geeignet für                                                                  | Standard-Health-Filterung                           |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------- |
| [`pickFirstBalancer(options?)`](/de-DE/api/core/pickfirstbalancer) _(Standard)_ | Browser-Apps mit geordneter Liste aus primärer Region und Backup-Regionen               | Deaktiviert (Opt-in über Option `outlierDetection`) |
| [`roundRobinBalancer(options?)`](/de-DE/api/core/roundrobinbalancer)            | Server-zu-Server-Aufrufe über gleichwertige Replikate (unterstützt optionale `weights`) | Aktiviert (`5` aufeinanderfolgende Fehler)          |
| [`p2cBalancer(options?)`](/de-DE/api/core/p2cbalancer)                          | Server-Aufrufe mit schwankender Replikats-Latenz oder variierender In-Flight-Last       | Aktiviert (`5` aufeinanderfolgende Fehler)          |

### Wie `pickFirstBalancer` und `p2cBalancer` funktionieren

- **`pickFirstBalancer`**: Bleibt auf der ersten URL und schaltet bei `NET_UNREACHABLE` oder `NET_UNAVAILABLE` (HTTP 502, 503 oder 504) weiter. Konfiguriere `failbackMs: 30_000`, um den primären Endpunkt nach dieser Dauer auf einem Backup erneut zu prüfen. Es darf nur eine Prüfung des primären Endpunkts gleichzeitig laufen. Vor der ersten Prüfung nach einem Failover muss das Intervall abgelaufen und seit dem Verlassen des primären Endpunkts mindestens einmal eine Alternative ausgewählt worden sein. Eine fehlgeschlagene Prüfung setzt beide Voraussetzungen zurück: Vor der nächsten Prüfung sind eine neue Auswahl einer Alternative und ein abgelaufenes Intervall nötig, selbst wenn der SSE-/WebSocket-Reconnect-Backoff länger als `failbackMs` ist. So kommt ein gesundes Backup zum Zug, statt dass jeder Reconnect den ausgefallenen primären Endpunkt trifft.
- **Gewichte von `roundRobinBalancer`**: Ein fehlendes Gewicht ist `1`; konfigurierte Gewichte müssen endlich und positiv sein. Smooth Weighted Round-Robin erhält die proportionale Auswahl (etwa drei von vier Auswahlen für den stärker gewichteten Peer bei `3:1`). Extreme Größenordnungen werden skaliert, um Überläufe zu vermeiden; Verhältnisse unterhalb der Gleitkommagenauigkeit können auf null gerundet werden. Auswahl und Bereinigung veralteter aktueller Werte benötigen pro Pick O(Anzahl der Kandidaten) Arbeit.

- **`p2cBalancer` (Power of Two Choices)**: Zieht zwei unterschiedliche Kandidaten zufällig ohne Zurücklegen und wählt denjenigen mit dem niedrigeren Score: `PeakEwma RTT × (pending + 1)` (oder reine In-Flight-Anzahl `pending`, wenn `load: "pending"` gesetzt ist). Die Standardwerte (`defaultRttMs: 30`, `decayMs: 10000`) folgen den Linkerd-/Tower-Konventionen.

## 2. Same-Call-HTTP-Retry

Drei getrennte Entscheidungen steuern einen Retry: **ob erneut versucht wird** (`withRetry`), **wohin er geht** (die Laufzeit bittet den Balancer erneut zu picken und schließt bereits versuchte Endpunkte aus) und **wie lange gewartet wird** (Backoff). `withRetry` für HTTP, `withSSEReconnect` für SSE und `withWebSocketReconnect` für WebSocket sind symmetrische Policies auf Transportebene. Ihre flachen Backoff-Felder teilen Namen, Validierung und Verzögerungsberechnung. Der Balancer weiß nichts von der Retry-Policy; ein eigener Balancer braucht keine besondere Mitwirkung.

Same-Call-HTTP-Retry ist **standardmäßig aus**. `withRetry` wegzulassen heißt: ein Versuch pro Aufruf, und es wird kein Retry-Budget angelegt oder gutgeschrieben. Die Auswahl späterer Aufrufe bleibt unverändert: `pickFirstBalancer` kann nach einem fehlgeschlagenen Aufruf weiterhin weiterschalten. `withRetry()` entspricht `withRetry({})` und aktiviert insgesamt zwei Versuche bei Verbindungsfehlern von `GET`, `HEAD`, `OPTIONS` und `TRACE`.

Das folgt dem Go-Ökosystem: [gRPC legt `retryPolicy` in die Service-Konfiguration](https://grpc.io/docs/guides/retry/), neben die Lastverteilungs-Konfiguration, während [go-kit `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) einen Balancer ausdrücklich umhüllt. Keines von beiden wendet standardmäßig eine anwendungsseitige Retry-Policy an. Die Retry-Policy von gRPC verlangt Backoff-Einstellungen und nutzt Jitter von ±0.2; [Envoy verwendet standardmäßig eine Basis von 25 ms und ein Maximum vom Zehnfachen dieser Basis](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff). Defjs verwendet 25 ms, Faktor 2, eine Obergrenze von 250 ms und Jitter von ±20 %. gRPC kann bei Low-Level-Races transparente Retries ausführen; Defjs bildet das nicht nach.

- **Versuche insgesamt (`maxAttempts`)**: Schließt den ursprünglichen Versuch ein, entsprechend gRPC `retryPolicy.maxAttempts` und `max` von go-kit `lb.Retry`. Der Wert muss eine sichere Ganzzahl von mindestens 1 sein; `1` bedeutet kein Retry. Eine konfigurierte Obergrenze gibt es nicht, aber jede Balancer-Auswahl schließt Endpunkte aus, die innerhalb dieses Aufrufs bereits ausgewählt wurden. Gezählt werden äußere Versuche, nicht physische Sendevorgänge innerhalb eines Anwendungs-Interceptors: Ein Interceptor mit einer `next()`-Schleife kann mehrfach an denselben Endpunkt senden. Beispielsweise ergeben drei Interceptor-Sendevorgänge an einen fehlerhaften primären Endpunkt plus ein äußerer Retry an ein gesundes Backup vier Netzwerk-Requests bei `maxAttempts: 2`; der Builder und die äußere Authentifizierungsschicht der Interceptor-Kette laufen zweimal, nicht viermal. Streaming-Request-Bodies werden nie erneut versucht. `methods` ist unabhängig von der Großschreibung; `methods: []` schaltet Retries für alle Methoden ab.
- **Retry-Bedingungen (`on`)**: Standardmäßig `["connect-failure"]`. Ergänze `"gateway-error"` für `NET_UNAVAILABLE` (HTTP `502`/`503`/`504`), einschließlich Gateway-Fehler-Bodies, die die `RES_*`-Dekodierung zurückweist, und `"attempt-timeout"`, wenn `attemptTimeoutMs` gesetzt ist. Ein zulässiger Retry baut den Request neu und führt die gesamte Interceptor-Kette von ihrer äußersten Schicht an erneut aus.
- **Backoff (`delayMs`, `factor`, `jitter`, `maxDelayMs`)**: Vor Retry n wird `delayMs × factor^(n−1)` mit multiplikativem Jitter gewartet, gedeckelt nach Jitter und Rundung. Die Defaults sind `25`, `2`, `0.2` und `250`. `delayMs: 0` überspringt das Warten. Wie beim Reconnect muss `delayMs` endlich und nicht negativ sein, `factor` endlich und positiv, `jitter` endlich in `[0, 1]` und `maxDelayMs` nicht negativ endlich oder positiv `Infinity`. Die Timer-Obergrenze der Plattform gilt weiterhin.
  Core-`withRetry` liest `Retry-After` nicht. Die Behandlung dieses Headers, einschließlich einer eventuellen Wartezeit-Obergrenze, ist eine [Policy des Anwendungs-Interceptors](/de-DE/docs/interceptors), kein Bestandteil dieses Backoffs.

  Bei nur einem konfigurierten Endpunkt spielt `withRetry` den Request nicht erneut ab, weil jeder Retry bereits versuchte Endpunkte ausschließt.

- **Timeout pro Versuch vs. Gesamtaufruf**: `attemptTimeoutMs` muss endlich, positiv und nicht größer als 2147483647 (die Timer-Obergrenze) sein; sonst gibt die Operation `REQ_OPTIONS_INVALID` zurück. Es begrenzt einen einzelnen Versuch vom Fetch-Aufruf bis zur Body-Dekodierung. Das aufruferseitige `client({ signal: AbortSignal.timeout(ms) })` deckt jeden Versuch **und die Backoff-Wartezeit** ab. Ein Abbruch während einer Wartezeit gibt den Abbruch-Fault des Aufrufers zurück, ohne erneut zu picken.
- **Finagle- / Linkerd-Retry-Budget (`budget`)**: Jede Client-Konfiguration besitzt ein Budget, geteilt nur von abgeleiteten Clients derselben Konfiguration, nicht von Clients, die einen Balancer teilen. Die Defaults sind `percentCanRetry: 0.2`, `minRetriesPerSecond: 10` und `ttlMs: 10000`: 20 % des ursprünglichen Traffics plus die Reserve. Gutschriften und Belastungen laufen träge in zehn TTL/10-Abschnitten ab. Ein Retry bucht vor dem Warten ab; ein erschöpftes Budget wartet weder noch versucht es erneut. Setze `budget: false`, um die Obergrenze aufzuheben.
- **Browser-Offline-Hinweis**: Wenn `navigator.onLine === false` ist, werden Verbindungsfehler als `{ attempted: false }` gemeldet und schalten weder Balancer weiter noch lösen sie Retries aus.

### Grenzen beim Browser-Deployment

- Ein CORS-Fehler im Browser erreicht Fetch als Verbindungsfehler und wird als `NET_UNREACHABLE` gemeldet, ununterscheidbar von einem ausgefallenen Host. Er kann die Endpunktauswahl weiterschalten und einen aktivierten Retry für sichere Methoden auslösen; ein erfolgreiches Failover kann daher eine CORS-Fehlkonfiguration der primären Region verdecken.
- Ein POST kann vom Server verarbeitet werden, selbst wenn die Antwort die erforderlichen CORS-Header nicht enthält. Die Anwendung erhält dann `NET_UNREACHABLE`, ohne zu wissen, ob der Schreibzugriff erfolgreich war. POST wird standardmäßig nicht erneut abgespielt; explizit aktivierte Schreib-Retries erfordern Idempotenz auf Anwendungsebene über Replikate hinweg.
- Cookies sind an einen Host gebunden, nicht an einen Port: Zwei Endpunkte auf `localhost` mit unterschiedlichen Ports können ein Cookie teilen, `localhost` und `127.0.0.1` dagegen nicht. Endpunktmengen mit mehreren Origins brauchen eine bewusste Cookie-/Token- und CORS-Zugangsdaten-Policy; `withCredentials(true)` ändert den Geltungsbereich von Cookies nicht.
- Der explizite Offline-Hinweis (`navigator.onLine === false`) unterdrückt Endpunktzuordnung und Retries bei Verbindungsfehlern. Er ist nur ein Browser-Hinweis, keine zuverlässige Erreichbarkeitsprüfung.

Ein späteres `withRetry` ersetzt die Policy. `withRetry()` und `withRetry(undefined)` verhalten sich wie `withRetry({})`. `withRetry({ maxAttempts: 1 })` schaltet Retries aus, nachdem sie aktiviert wurden. Ungültige Retry-Einstellungen geben `REQ_OPTIONS_INVALID` mit `Invalid retry options` zurück, wenn die HTTP-Operation läuft.

## 3. Passives Circuit-Breaking und aktive Health-Checks (`outlierDetection`)

1. **Aufeinanderfolgende Fehler**: Der Standard-Klassifikator zählt `NET_UNREACHABLE`, `NET_UNAVAILABLE` und `NET_SERVER_ERROR`. Nach `consecutiveFailures` (standardmäßig `5`) aufeinanderfolgenden gezählten Ergebnissen wird der Endpunkt für `min(minPenaltyMs × 2^level, maxPenaltyMs)` (`1000ms` bis `60000ms`) zuzüglich bis zu `50%` gleichmäßig verteiltem positivem Jitter ausgeschlossen.
2. **Erholung durch Einzelprüfung (Single-Probe Recovery)**: Nach Ablauf der Sperrzeit prüft ein einzelner Request den Host. Beginnt seine Peer-Antwort (`end`) ohne gezählten Fehler, wird der normale Traffic sofort wieder aufgenommen und das Penalty-Level auf `0` zurückgesetzt; schlägt sie fehl, verdoppelt sich die Sperrzeit.
3. **Begrenzte Historie**: Die Health-Historie speichert höchstens 256 Endpunkte über abgeleitete Clients und aufrufspezifische Kandidatenausschlüsse hinweg. Am längsten ungenutzte unbelastete oder abgelaufene Einträge werden zuerst entfernt, danach unvollständige Fehlerfolgen. Ein Eintrag mit laufender Sperrzeit oder laufender Prüfung wird nur entfernt, wenn alle gespeicherten Einträge geschützt sind; dann wird der älteste entfernt. Einen Endpunkt in einem einzelnen Aufruf wegzulassen setzt seine Sperrzeit nicht zurück. P2C begrenzt auch die Last-Historie auf 256 Einträge und entfernt untätige vor beschäftigten Einträgen; ein vergessener Endpunkt beginnt wieder bei `defaultRttMs`. Die Shuffle-Schlüssel von Pick-first nutzen einen LRU-Cache mit 256 Einträgen, sodass ein vergessener Endpunkt bei seiner Rückkehr einen neuen Schlüssel erhält. Weighted Round-Robin behält aktuelle Werte nur für seine jüngste Kandidatenmenge; die kopierte Gewichtskonfiguration steht bei der Erstellung fest. Zeitdauern nutzen, sofern verfügbar, die monotone Performance-Uhr der Plattform, mit `Date.now()` nur als Fallback.

4. **Panikmodus / Fail-Open**: Werden sämtliche konfigurierten Endpunkte ausgeschlossen oder als ungesund eingestuft, schaltet der Balancer auf Fail-Open und greift für den gesamten Traffic auf die Kandidatenliste des Clients zurück, anstatt alle Aufrufe lokal abzuweisen.

## 4. Lifecycle der Transport-Abrechnung (`pick` → `start` → `end` → `done`)

Eigene Balancer müssen eine der exakten Zeichenketten in `info.endpoints` auswählen. Eine fremde Auswahl gibt ein `REQ_BUILD_FAILED`-Tupel mit der nicht sensiblen Ursachenmeldung `Balancer selected an endpoint outside the candidate set` zurück; kein Transport startet und kein Abschluss-Callback läuft. Diese Regel erhält Health-Filterung und aufrufspezifische Retry-Ausschlüsse.

Eigene Balancer implementieren synchrones `pick(info)` und optionale Callbacks `start()`, `end(info)` und `done(info)`. `PickInfo` enthält nur die Kandidaten-`endpoints` und die optionale Definitions-`operation`; einen Transport-Diskriminator gibt es nicht. Der Transport übersetzt seine Fakten in neutrale `DoneInfo.code`-Ergebnisse. Eingebaute Balancer lesen `status` nie; diese rohe Antwortinformation bleibt nur für eigene Balancer erhalten. `start` läuft vor dem Versuch, `end`, wenn die Peer-Antwort beginnt oder ein Fehler vor der Antwort auftritt, und `done` beim Abschluss. Ein späterer Body-Fehler kann daher den finalen Code ändern, ohne das frühere `end`-Sample zu ändern:

| Physisches Transport-Ergebnis                                                               | Finales `done(info)`-Sample                                |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| HTTP/SSE-Antwortstatus 502, 503 oder 504                                                    | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| Anderer HTTP/SSE-Antwortstatus ab 500                                                       | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP/SSE-Antwortstatus 2xx, 3xx oder 4xx (einschließlich 429)                               | `{ attempted: true, status }`                              |
| HTTP-Response-Body wird mitten im Stream abgeschnitten                                      | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE-Handshake gelingt, danach lehnt Stream `reader.read()` ab                               | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Reguläres SSE-EOF, Dekodierungsfehler nach erfolgreichem Handshake oder Warteschlangenlimit | `{ attempted: true, status }`                              |
| Geöffneter WebSocket schließt mit Code `1006` oder `wasClean === false`                     | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Geöffneter WebSocket schließt regulär                                                       | `{ attempted: true }`                                      |
| Abbruch durch den Aufrufer oder manuelles Schließen von Stream/Socket                       | `{ attempted: false }`                                     |
| Deadline des Aufrufers läuft ab, nachdem der Versuch gestartet wurde                        | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

Dekodierungsfehler beim Handshake behalten das neutrale Ergebnis, das sich aus dem Handshake-Status ableitet (zum Beispiel `NET_UNAVAILABLE` mit Status `503`). Ein unvollständiger HTTP-Body behält stattdessen `NET_BODY_INCOMPLETE` und seinen rohen Status, auch bei einer Gateway-Antwort; die Standard-Outlier-Detection zählt ihn nicht.
