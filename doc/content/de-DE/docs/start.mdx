# Schnellstart: Deine erste SDK-Operation [#getting-started-one-http-request]

In dieser Anleitung erstellst du ein SDK-Modul, das `GET /orders/:id` definiert, und rufst es aus zwei separaten Anwendungsmodulen auf: eines nutzt einen Offline-Mock-Transport und das andere greift auf eine echte API zu.

## 1. `@defjs/core` installieren

`@defjs/core` ist ein abhängigkeitsfreies ESM-Paket, das in Browsern, Bun und dem aktuellen Node.js LTS läuft. Achte darauf, dass `"type": "module"` in deiner `package.json` gesetzt ist.

```sh
bun add @defjs/core
```

Halte die Operationsdefinition in einem eigenen SDK-Modul (`src/define-request.ts`) und erstelle den Client in deiner Anwendung (`src/execute-locally.ts` oder `src/real-api.ts`):

### Wie die drei Dateien zusammenspielen

1. **`src/define-request.ts` (SDK-Definition)**:
   - Deklariert `input`, `output` (für `2xx`-Antworten) und `error` (für Nicht-`2xx`-Antworten) mithilfe von `struct`.
   - Stellt einen synchronen, reinen `builder` bereit, der `input` auf `{ path }` abbildet. Sobald `input` deklariert ist, ist ein expliziter `builder` Pflicht.
   - Exportiert `getOrder`, ohne einen Client zu erstellen oder an sich zu binden.
2. **`src/execute-locally.ts` (Lokale Offline-Ausführung für Tests)**:
   - Konfiguriert einen Client mit `withHTTPHandle(...)`, um die gesamte Defjs-Pipeline (Input-Validierung, URL-Auflösung, Status-Dispatch und Struct-Parsing der Antwort) zu durchlaufen – komplett ohne Netzwerkzugriff.
3. **`src/real-api.ts` (Produktionsausführung)**:
   - Importiert exakt dieselbe `getOrder`-Operation und ruft sie gegen eine über `withEndpoint(...)` konfigurierte Live-Basis-URL auf.

## 3. Das lokale Beispiel ausführen

Starte `src/execute-locally.ts` mit Bun:

```sh
bun src/execute-locally.ts
```

```txt
Loaded paid from 200
```

Wenn du die Eingabe von `{ id: 7 }` auf `{ id: 8 }` änderst, antwortet der Mock mit `404` und Defjs dekodiert das deklarierte `error`-Struct in `error.data`:

```txt
Order not found
```

## 4. Das Error-first-Tupel verstehen

Jeder HTTP-Aufruf liefert ein dreiteiliges Tupel `[error, data, response]` zurück:

- **Bei `2xx`-Erfolg**: `error` ist `null`, `data` ist der validierte `output`-Wert (`Order`), und `response` ist `DecodedResponse<Order>`.
- **Bei einem deklarierten Nicht-`2xx`-Status**: `error.code` lautet `'HTTP_STATUS'`, `error.status` ist der numerische HTTP-Statuscode (`404`), und `error.data` ist das validierte `error`-Struct (`NotFound`).
- **Bei Eingabe-, Dekodierungs- oder Netzwerkfehlern**: `error.code` kennzeichnet die genaue Fehlerphase:
  - `REQ_INPUT_INVALID` / `REQ_BUILD_FAILED` — ungültige Aufruf-Eingabe oder eine Exception im `builder`
  - `RES_MEDIA_TYPE_INVALID` — deklarierter JSON-Body traf mit einem Nicht-JSON-`Content-Type` ein (wird bereits vor dem Lesen des Body abgewiesen)
  - `RES_DECODE_FAILED` / `RES_STRUCT_MISMATCH` — unlesbarer Body oder Schema-Diskrepanz
  - `NET_UNREACHABLE` / `NET_ABORTED` / `NET_TIMEOUT` — Transportfehler, manueller Abbruch oder `AbortSignal.timeout(ms)`-Zeitüberschreitung

Per-Call-Deadlines oder Abbruchsignale übergibst du, indem du einen Client-Wert für einen einzelnen Aufruf ableitest: `getOrder(client({ signal: AbortSignal.timeout(5_000) }), { id: 7 })`.
