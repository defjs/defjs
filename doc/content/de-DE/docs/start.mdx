# Erste Schritte: deine erste SDK-Operation [#getting-started-one-http-request]

Du schreibst zwei Dateien: ein SDK-Modul, das `GET /orders/:id` exportiert, und eine Anwendung, die es importiert und den Client besitzt. Der lokale Fetch-Handler hält den ersten Lauf offline. Dieselbe API-Definition funktioniert danach mit einem Client, der auf deinen Service zeigt.

## Bewährte Praxis

Eine Definition bleibt vom Client unabhängig. Rufe die Operation mit dem Client der Anwendung auf, etwa `getOrder(client, { id: 7 })`. Es gibt kein drittes Options-Argument. Der Aufruf der Operation startet sie; `await` wartet nur. Die Anwendung besitzt außerdem die Service-Adresse und die Zugangsdaten. Lies zuerst das Error-first-Tupel. Wenn `error` gesetzt ist, melde `error.code` und kehre aus der Funktion zurück, bevor du den Erfolgswert liest.

## Schritt 1 — Installieren

`@defjs/core` ist ESM und läuft auf Node.js oder Bun. Node.js 22.18+ (oder 24+) führt die `.ts`-Datei direkt per Type Stripping aus; ältere 22.x-Releases brauchen `--experimental-strip-types`. Behalte `"type": "module"` in der package.json. Im Browser brauchst du weiterhin Bundler und Fetch.

```sh
bun add @defjs/core
```

## Schritt 2 — Request definieren

Lege `src/define-request.ts` an. Das ist das Modul des SDK-Autors: Es exportiert `getOrder`, ohne einen Client zu erzeugen. Der Input-Struct ist der Wert des Aufrufers. `builder` platziert diesen Wert auf dem Request. Hier ist die ganze Eingabe das Path-Objekt, also füllen skalare Felder ohne Alias `:id`.

<include cwd meta="define-request.ts">
  examples/start/define-request.ts#example
</include>

`output` ist der 2xx-Body. `error` ist jeder andere Status. Je ein Struct. Nutze `struct.or(...)` oder eine Discriminated Union, wenn diese Bodies auseinanderlaufen.

`defineRequest(...)` gibt eine Operation zurück. Der Aufruf `getOrder(client, input)` startet den Request. Der `builder` oben ist die Funktion, die Input platziert; er ist nicht die Operation. Wo `input` deklariert ist, ist `builder` erforderlich, synchron und pure.

## Schritt 3 — Lokal aufrufen

Lege `src/execute-locally.ts` neben die Definition. Das ist die konsumierende Anwendung: Sie importiert `getOrder`, erzeugt ihren eigenen Client und stellt einen lokalen Fetch-Handler bereit. Defjs validiert weiterhin die Eingabe, baut den `Request`, wählt anhand des Status und parst den Body.

<include cwd meta="execute-locally.ts">
  examples/start/execute-locally.ts#example
</include>

So startest du:

```sh
bun src/execute-locally.ts
```

```txt
Loaded paid from 200
```

Probier eine fehlende Bestellung — ändere die Path-id auf `8` und lauf nochmal:

```txt
Order not found
```

Bei Erfolg: `error` ist `null`, `order` ist der `200`-Struct-Output, `response` ist ein `DecodedResponse<Order>`. Bei deklariertem `404`: `error.code` ist `'HTTP_STATUS'`, `error.status` ist `404`, und `error.data` ist typisiert als `NotFound`. Der zweite Tupel-Eintrag ist bei Fehler `undefined`.

## Schritt 4 — Auf eine echte API zeigen

Importiere in `src/real-api.ts` dasselbe `getOrder` und erzeuge einen Client mit der Base-URL deines Services. Führe diese Version erst aus, nachdem du die Beispieladresse durch einen Service ersetzt hast, der `GET /v1/orders/:id` mit diesen Bodies implementiert.

<include cwd>examples/start/real-api.ts#example</include>

Die API-Definition bleibt im SDK-Modul. Service-Adressen, Zugangsdaten, Interceptors und die Lebensdauer der Ausführung bleiben bei der Anwendung. Beide Clients nutzen denselben Defjs-Endpoint-Vertrag.

## Die Definition veröffentlichen

Verschiebe die Definition in ein SDK-Paket, wenn weitere Anwendungen sie brauchen. Exportiere `getOrder`, liefere die TypeScript-Deklarationen mit und deklariere die kompatible Core-Version. Nutzer importieren dann aus dem Paket statt aus `./define-request.ts`; ihre Client-Konfiguration bleibt ihre eigene. [SDK entwickeln und veröffentlichen](/de-DE/recipes/publish-http-sdk) zeigt das vollständige Paket-Setup.

## Wenn das Ergebnis abweicht

- Schlechter Input → `REQ_INPUT_INVALID`; ein fehlschlagendes `builder` → `REQ_BUILD_FAILED`
- Ein Non-2xx-Status → `HTTP_STATUS`, mit typisiertem `error.data`, wenn `error` deklariert war und sein Body dekodiert
- Ein deklarierter JSON-Body mit anderem Media-Type → `RES_MEDIA_TYPE_INVALID`, gemeldet bevor der Body gelesen wird
- Ein deklarierter Body (`output` bei 2xx, sonst `error`), der nicht dekodiert → `RES_DECODE_FAILED` oder `RES_STRUCT_MISMATCH`, egal bei welchem Status
- Fetch-Fehler / Abbruch / Deadline → `NET_UNREACHABLE` / `NET_ABORTED` / `NET_TIMEOUT`

Eine Deadline ist `client({ signal: AbortSignal.timeout(ms) })` und wird als `NET_TIMEOUT` klassifiziert. Ein manueller Abbruch ist `NET_ABORTED`. Es gibt keine Default-Deadline auf Client-Ebene. Leite einen Client ab, wenn ein Aufruf sein eigenes `signal` braucht; siehe [Client](/de-DE/docs/client). Cancellation sagt dir, was der Caller gesehen hat — nicht, ob ein Server-Write übernommen wurde.
