# SSE-Ereignisströme

Ein SDK deklariert einen Server-Sent-Events-Endpunkt mit `defineEventStream`: inklusive Pfad, optionalem Input und Builder, einem `events`-Dictionary aus Structs sowie Puffer- und Warteschlangenlimits. Die konsumierende Anwendung konfiguriert Authentifizierung und optionale Wiederverbindung an ihrem Client, öffnet den Stream, iteriert über typisierte Ereignisse und besitzt das Schließen des Streams.

## 1. Event-Stream definieren und konsumieren

Gib ein geöffnetes `EventStreamHandle` immer mit `await using` (oder `stream.close()` + `await stream.closed` in einem `finally`-Block) frei:

<Tabs items={["sdk/orders-stream.ts", "app/watch-orders.ts", "Single-file quick look"]}>
<Tab value="sdk/orders-stream.ts">

```ts
import { defineEventStream, struct } from "@defjs/core";

export const watchOrders = defineEventStream({
  path: "/orders/events",
  operation: "orders.watch",
  events: {
    updated: struct.object({
      id: struct.number(),
      status: struct.string(),
    }),
  },
});
```

</Tab>
<Tab value="app/watch-orders.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { watchOrders } from "../sdk/orders-stream.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, stream] = await watchOrders(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = stream;
  for await (const event of active) {
    console.log(event.event, event.data.id, event.data.status);
    break;
  }
}

void main();
```

## 2. Handshake beim Öffnen und Tupel-Form

Der Aufruf der Operation liefert `[error, stream, startupOpen]` erst zurück, nachdem die anfängliche HTTP-Antwort `2xx` ist, den Medientyp `text/event-stream` aufweist und einen lesbaren Body bereitstellt:

- **Nicht-`2xx`-Handshake**: Gibt `HTTP_STATUS` zurück (mit dekodiertem `error.data`, falls ein `error`-Struct an der Definition deklariert ist).
- **Falscher Content-Type oder unlesbarer Body**: Gibt `RES_MEDIA_TYPE_INVALID` oder `RES_DECODE_FAILED` zurück.
- **`startupOpen` vs. `stream.open`**: Das dritte Element des Tupels (`startupOpen`) hält die erste Handshake-Antwort als Snapshot fest; `stream.open` aktualisiert sich dynamisch, falls sich der Stream später neu verbindet.

## 3. Event-Dispatching und Dekodierung

Wenn ein SSE-Frame eintrifft (nach WHATWG-Regeln durch eine Leerzeile abgeschlossen):

1. **Event-Routing**: Das Wire-Feld `event:` wählt `events[eventName]` aus und fällt auf `events.default` zurück, falls deklariert. Ein weggelassenes `event:`-Feld hat standardmäßig den Wert `"message"`. Undeklarierte Events ohne `events.default` werden verworfen.
2. **Payload-Dekodierung**: Ein `struct.string()`-Schema empfängt den rohen Text von `data:`. Jede andere Struct-Art parst `data:` zuerst als JSON und validiert anschließend gegen das Struct.
3. **Ungültige Events beobachten**: Ungültige oder undeklarierte Events werden ignoriert, ohne den Stream zu beenden. Hänge `withSSEOnInvalidEvent(...)` an den Client für eine gezielte Diagnose:

## 4. Wiederverbindung und `Last-Event-ID` [#reconnect]

Die SSE-Wiederverbindung ist **Opt-in**. Ohne `withSSEReconnect(...)` beendet jeder Netzwerkabbruch oder Stream-Lesefehler den Stream dauerhaft.

<include cwd>examples/sse/reconnect.ts#example</include>

- **Ausfallbudget (`attempts`)**: Standardmäßig `3`, wenn ein Optionen-Objekt an `withSSEReconnect` übergeben wird. Ein erfolgreicher Handshake setzt den Versuchszähler und den Backoff-Exponenten zurück. Ein reguläres Server-EOF gilt **nicht** als Fehler und löst keinen Reconnect aus.
- **Cursor-Tracking (`Last-Event-ID`)**: Wird gespeichert, sobald die abschließende Leerzeile eines Events geparst ist, und beim Reconnect automatisch als `Last-Event-ID` mitgesendet.
- **Idempotenz-Sicherheit**: Standardmäßig verbinden sich nur idempotente Methoden (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`) automatisch wieder. Nicht-idempotente Methoden (`POST`, `PATCH` – wie etwa LLM-Streaming-Requests) verbinden sich nur dann neu, wenn ein benutzerdefinierter `shouldReconnect`-Callback explizit `true` zurückgibt. `ReadableStream`-Request-Bodys werden beim ersten Versuch verbraucht und bauen niemals einen Reconnect auf.
- **Handshake-Timeout (`connectTimeoutMs`)**: Begrenzt jeden einzelnen Handshake vom Fetch-Aufruf bis zu den Response-Headern, ohne die Offenhaltezeit eines bereits etablierten Streams einzuschränken.

## 5. Puffer- und Warteschlangenlimits

Beide Limits müssen positive, sichere Ganzzahlen sein. Das Überschreiten eines Limits ist fatal (`stream.closed` löst mit `kind: "error"` auf und der Iterator schlägt fehl – Ereignisse werden niemals stillschweigend verworfen):

| Definitions-Option | Was sie begrenzt                                                  | Fataler Fehlercode    |
| ------------------ | ----------------------------------------------------------------- | --------------------- |
| `maxBufferSize`    | Unvollständige oder zu große SSE-Frame-Bytes vor einer Leerzeile  | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`     | Validierte Ereignisse, die auf den `for await`-Konsumenten warten | `CAP_QUEUE_OVERFLOW`  |

## 6. Schließen und Freigeben [#close-and-dispose]

Der Aufrufer, der einen Stream öffnet, ist für dessen Beendigung verantwortlich. Das Verlassen einer `for await`-Schleife über `break`, `return` oder eine geworfene Exception schließt den Stream automatisch; alternativ kannst du `await using` / `stream.close()` nutzen:
