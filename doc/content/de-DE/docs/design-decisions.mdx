# Kernarchitektur

Defjs basiert auf einer grundlegenden Grenze: **Ein SDK definiert den Wire-Vertrag; die konsumierende Anwendung besitzt die Ausführung.** Jedes Designprinzip in `@defjs/core` folgt aus dieser Trennung.

## 1. Definition vs. Ausführung

Ein SDK-Paket exportiert Operationen (`defineRequest`, `defineEventStream`, `defineWebSocket`) und Datenverträge (`struct`). Es ruft niemals `createClient` auf, speichert keinen Singleton-Client und liest keine Umgebungsvariablen aus.

Weil `getOrder` keinerlei Client-Zustand an sich bindet:

- Können eine Browser-UI, ein Hintergrundjob, ein SSR-Request-Handler und ein Unit-Test dieselbe `getOrder`-Operation mit unterschiedlichen `Client`-Konfigurationen aufrufen.
- Hängen sich Framework-Plugins (`@defjs/react`, `@defjs/vue`) und das Observability-Middleware-Plugin (`@defjs/opentelemetry-server`) an den `Client` der Anwendung an, wodurch das veröffentlichte SDK-Paket zu 100 % frei von Abhängigkeiten bleibt.

## 2. Explizite Input-Platzierung und bidirektionale Aliase

In Defjs deklariert `input`, was der Aufrufer übergibt, `struct` steuert, wie Werte kodiert/dekodiert werden, und `builder` platziert jeden Wert an der richtigen Stelle des Requests (`path`, `query`, `headers`, `body`).

- **Keine implizite Magie**: Wenn eine Operation `input` deklariert, muss sie einen expliziten, synchronen, reinen `builder` bereitstellen. Die Platzierung von Feldern wird niemals anhand von Parameternamen erraten.
- **Bidirektionale `.alias(wireName)`**: Mit `.alias("customer_name")` an einem Struct-Feld bleibt in TypeScript `customerName` erhalten, während auf Wire-Ebene automatisch von und zu `"customer_name"` zugeordnet wird.

## 3. Eine Deklaration ist eine Assertion [#declaration-is-an-assertion]

Sechs strikte Regeln bestimmen, wie Defjs HTTP-Antworten einliest:

### Regel 1: Was du deklarierst, ist das, was du zusicherst

`output` sichert die Form eines `2xx`-Bodys zu. `error` sichert die Form eines Nicht-`2xx`-Bodys zu. Eine Deklaration ist eine Laufzeitgarantie, kein Best-Effort-Hinweis.

### Regel 2: `ok` (`200..299`) ist die einzige Verzweigung

Eine `2xx`-Antwort wird ausschließlich über `output` dekodiert. Jeder andere Status (`3xx`, `4xx`, `5xx`) wird ausschließlich über `error` dekodiert. Defjs fällt niemals von einem Schema auf das andere zurück.

### Regel 3: Jede Abweichung von der Zusicherung führt zu einem expliziten Fehler

Defjs wählt die Response-Seite über `response.ok`: `output` für `2xx`, `error` für Nicht-`2xx`. Nur ein auf dieser Seite deklariertes JSON-Struct löst die Dekodierung aus und kann `RES_MEDIA_TYPE_INVALID` oder `RES_DECODE_FAILED` erzeugen; sein `Content-Type` wird **zuerst** geprüft, bevor der Body gelesen oder gesucht wird. Eine Response ohne Inhalt (`HEAD`, `204`, `205`, `304`) unterliegt derselben Prüfung: Eine deklarierte JSON-Repräsentation ohne JSON-`Content-Type` schlägt mit `RES_MEDIA_TYPE_INVALID` fehl, und mit einem solchen parst sie die leeren Bytes und schlägt mit `RES_DECODE_FAILED` fehl. Eine HTML-Gateway-Seite bei Nicht-`2xx` erzeugt `RES_MEDIA_TYPE_INVALID` nur, wenn ein JSON-`error`-Struct deklariert ist. Ohne Deklaration für die aktive Seite wird der Body nicht gelesen; eine Nicht-`2xx`-Response liefert einen undekodierten `HTTP_STATUS`. Ein SSE-Handshake folgt denselben Regeln: Ein Nicht-`2xx`-Handshake, dessen deklarierter `error`-Body nicht dekodiert werden kann, liefert diesen Dekodierfehler beim Start, mit dem Status in seinen Metadaten, während Interceptors, Reconnect-Policies und das `closed` eines Reconnects weiterhin `HTTP_STATUS` sehen.

| Was beim Lesen der Antwort fehlgeschlagen ist                           | Zurückgegebener Fault                                                                                                       |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Medientyp stimmt nicht mit der deklarierten JSON-Repräsentation überein | `RES_MEDIA_TYPE_INVALID` (zuerst geprüft; der Body wird nie gelesen, und ob Inhalt vorhanden ist, macht keinen Unterschied) |
| Bytes können nicht als deklarierte Repräsentation dekodiert werden      | `RES_DECODE_FAILED` (leere JSON-Bytes eingeschlossen)                                                                       |
| Dekodierter Wert verletzt die `struct`-Validierung                      | `RES_STRUCT_MISMATCH`                                                                                                       |
| Nicht-`2xx`-Status mit dekodiertem `error`-Struct                       | `HTTP_STATUS` mit typisiertem `error.data`                                                                                  |
| Nicht-`2xx`-Status mit weggelassenem `error`                            | `HTTP_STATUS` mit `error.data: undefined`                                                                                   |

### Regel 4: Ein fehlgeschlagener Decode besitzt keinen Body

Ein Body existiert erst, nachdem Dekodierung und Validierung erfolgreich durchlaufen wurden. Schlägt das Dekodieren fehl, ist die `response` des Faults als `HttpMeta` typisiert (welches keine `body`-Eigenschaft besitzt), und der Parser-/Validierungsfehler wird an `fault.cause` angehängt.

### Regel 5: Das Weglassen einer Seite schließt das Lesen aus

Lässt du `output` weg, werden `2xx`-Bodys niemals gelesen. Lässt du `error` weg, werden Nicht-`2xx`-Bodys niemals gelesen – selbst dann nicht, wenn der Server bei einem `500` ungültiges JSON gesendet hat.

### Regel 6: `3xx` ist kein Erfolgsstatus

`ok` bedeutet `200 <= status < 300`. Ein `304 Not Modified` ist Nicht-`2xx`: Lasse `error` undeklariert und behandle `HTTP_STATUS` (siehe [ETag-Bedingungsanfragen](/de-DE/recipes/etag-revalidate)), oder deklariere `struct.string()`, wenn du einen leeren Text-Body erwartest.

## 4. Transportspezifische Ergebnis-Tupel

Alle drei Transporte geben ein dreiteiliges Error-first-Tupel zurück, statt an der Aufrufstelle Exceptions zu werfen:

- **HTTP** → `[error, data, response]` — dekodierte Payload + `DecodedResponse<T>` (`HttpMeta`, wenn `output` weggelassen wurde).
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + anfänglicher Handshake-Snapshot.
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + anfänglicher Verbindungs-Snapshot.

Clients verwalten Konfiguration, keine aktiven Verbindungen. Der Aufrufer, der einen HTTP-Request, einen SSE-Stream oder eine WebSocket-Sitzung startet, ist auch für den Abbruch oder das Schließen verantwortlich (`AbortSignal` bei HTTP; `await using` oder `.close()` + `await .closed` bei SSE und WebSocket).

## 5. Was Defjs nicht bietet

Mehrere Muster anderer HTTP-Clients haben in Defjs bewusst keine Entsprechung. Verwenden Sie den Ersatz in der rechten Spalte.

| Nicht vorhanden                                                             | Stattdessen verwenden                                                                    |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Ein globaler Client-Singleton                                               | Ein anwendungseigenes `createClient(...)`, das an Operationen übergeben wird             |
| Eine Client-Methode, die eine Operation ausführt                            | Die Operation direkt aufrufen: `getOrder(client, input)`                                 |
| Ein Standard-Timeout auf Client-Ebene oder die Optionen `timeout` / `abort` | `client({ signal: AbortSignal.timeout(ms) })` oder ein `AbortController`                 |
| Ein Feld `responseType` an `defineRequest`                                  | Die Struct-Art von `output` (`string`, `blob`, `arrayBuffer` oder JSON)                  |
| `.parse()` auf einer Struct-Instanz oder `struct.encode`                    | `struct.parse(schema, value)` und die Platzierung durch `builder`                        |
| Eigene WebSocket-Handshake-Header                                           | Cookies, kurzlebige Query-Tickets oder `protocols`                                       |
| Eine WebSocket-Nachrichtenzuordnung oder ein Typ-Envelope                   | `struct.discriminatedUnion` und `session.onRuntimeError`                                 |
| OpenAPI-Codegenerierung                                                     | OpenAPI als externe Spezifikation beibehalten oder an der Grenze mit `struct` validieren |
