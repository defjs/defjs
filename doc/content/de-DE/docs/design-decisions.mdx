# Kernarchitektur

Defjs basiert auf einer grundlegenden Trennlinie: **Ein SDK definiert den Wire-Vertrag; die konsumierende Anwendung besitzt die Ausführung.** Jedes Designprinzip in `@defjs/core` folgt dieser strikten Trennung.

## 1. Definition vs. Ausführung

Ein SDK-Paket exportiert Operationen (`defineRequest`, `defineEventStream`, `defineWebSocket`) und Datenverträge (`struct`). Es ruft niemals `createClient` auf, speichert keinen Singleton-Client und liest keine Umgebungsvariablen aus.

<Tabs items={["sdk/orders.ts", "app/consumers.ts"]}>
<Tab value="sdk/orders.ts">

```ts
import { defineRequest, struct } from "@defjs/core";

export const Order = struct.object({
  id: struct.number(),
  status: struct.string(),
});

export const getOrder = defineRequest({
  method: "GET",
  path: "/orders/:id",
  operation: "orders.read",
  input: struct.object({ id: struct.number() }),
  builder: (input) => ({ path: input }),
  output: Order,
});
```

Weil `getOrder` keinerlei Client-Zustand an sich bindet:

- Können eine Browser-UI, ein Hintergrundjob, ein SSR-Request-Handler und ein Unit-Test dieselbe `getOrder`-Definition mit ganz unterschiedlichen `Client`-Konfigurationen aufrufen.
- Hängen sich Framework-Plugins (`@defjs/react`, `@defjs/vue`) und Observability-Middleware (`@defjs/opentelemetry-server`) an den `Client` der Anwendung an, wodurch das veröffentlichte SDK-Paket zu 100 % frei von Abhängigkeiten bleibt.

## 2. Explizite Input-Platzierung und bidirektionale Aliase

In Defjs deklariert `input`, was der Aufrufer übergibt, `struct` steuert, wie Werte enkodiert/dekodiert werden, und `builder` platziert jeden Wert an der richtigen Stelle des Requests (`path`, `query`, `headers`, `body`).

- **Keine implizite Magie**: Wenn eine Operation `input` deklariert, muss sie einen expliziten, synchronen, reinen `builder` bereitstellen. Die Platzierung von Feldern wird niemals anhand von Parameternamen erraten.
- **Bidirektionale `.alias(wireName)`**: Mit `.alias("customer_name")` an einem Struct-Feld bleibt in TypeScript `customerName` erhalten, während auf Wire-Ebene automatisch von und zu `"customer_name"` gemappt wird.

Wenn der Builder ein typisiertes Struct-Objekt an `body`, `query` oder `headers` übergibt, greifen dessen Feld-Aliase sowie `Date`- / `bigint`-Codecs vollautomatisch. Schlüssel, die du in einem anonymen Wrapper-Objekt schreibst (wie `account_id` oder `x-api-version` oben), bleiben unverändert literal.

## 3. Eine Deklaration ist eine Assertion [#declaration-is-an-assertion]

Sechs strikte Regeln bestimmen, wie Defjs HTTP-Antworten einliest:

### Regel 1: Was du deklarierst, ist das, was du zusicherst

`output` sichert die Form eines `2xx`-Bodys zu. `error` sichert die Form eines Nicht-`2xx`-Bodys zu. Eine Deklaration ist eine Laufzeit-Garantie, kein vager Best-Effort-Hinweis.

### Regel 2: `ok` (`200..299`) ist die einzige Verzweigung

Eine `2xx`-Antwort wird ausschließlich über `output` dekodiert. Jeder andere Status (`3xx`, `4xx`, `5xx`) wird ausschließlich über `error` dekodiert. Defjs fällt niemals von einem Schema auf das andere zurück.

### Regel 3: Jede Abweichung von der Zusicherung führt zu einem expliziten Fehler

Wurde ein JSON-`output` deklariert und ein Gateway liefert eine HTML-Fehlerseite oder ungültiges JSON zurück, schlägt der Aufruf sofort fehl (`RES_MEDIA_TYPE_INVALID` oder `RES_DECODE_FAILED`). Bei JSON-Repräsentationen wird der `Content-Type`-Header **vor** dem Auslesen der Body-Bytes geprüft.

| Was beim Lesen der Antwort fehlgeschlagen ist                           | Zurückgegebener Fehler (Fault)                                     |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Medientyp stimmt nicht mit der deklarierten JSON-Repräsentation überein | `RES_MEDIA_TYPE_INVALID` (Body wird erst gar nicht gelesen)        |
| Bytes können nicht als deklarierte Repräsentation dekodiert werden      | `RES_DECODE_FAILED`                                                |
| Dekodierter Wert verletzt die `struct`-Validierung                      | `RES_STRUCT_MISMATCH` (HTTP) / `RES_DECODE_FAILED` (SSE-Handshake) |
| Nicht-`2xx`-Status mit dekodiertem `error`-Struct                       | `HTTP_STATUS` mit typisiertem `error.data`                         |
| Nicht-`2xx`-Status mit weggelassenem `error`                            | `HTTP_STATUS` mit `error.data: undefined`                          |

### Regel 4: Ein fehlgeschlagener Decode besitzt keinen Body

Ein Body existiert erst, nachdem Dekodierung und Validierung erfolgreich durchlaufen wurden. Schlägt das Dekodieren fehl, ist `response` des Fehlers als `HttpMeta` typisiert (welches keine `body`-Eigenschaft besitzt), und der Parser-/Validierungsfehler wird an `fault.cause` angehängt.

### Regel 5: Das Weglassen einer Seite schließt das Lesen aus

Lässt du `output` weg, werden `2xx`-Bodys niemals gelesen. Lässt du `error` weg, werden Nicht-`2xx`-Bodys niemals gelesen – selbst dann nicht, wenn der Server bei einem `500` ungültiges JSON gesendet hat.

### Regel 6: `3xx` ist kein Erfolgsstatus

`ok` bedeutet `200 <= status < 300`. Ein `304 Not Modified` ist Nicht-`2xx`: Lasse `error` undeklariert und behandle `HTTP_STATUS` (oder fange `304` in einem ETag-Interceptor ab), oder deklariere `struct.string()`, wenn du einen leeren Text-Body erwartest.

## 4. Transportspezifische Ergebnis-Tupel

Alle drei Transporte geben ein dreiteiliges Error-first-Tupel zurück, statt am Aufruf-Ort Exceptions zu werfen:

- **HTTP** → `[error, data, response]` — dekodierte Payload + `DecodedResponse<T>` (`HttpMeta`, wenn `output` weggelassen wurde).
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + anfänglicher Handshake-Snapshot.
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + anfänglicher Verbindungs-Snapshot.

Clients verwalten Konfiguration, keine aktiven Verbindungen. Der Aufrufer, der einen HTTP-Request, einen SSE-Stream oder eine WebSocket-Sitzung startet, ist auch für den Abbruch oder das Schließen verantwortlich (`AbortSignal` bei HTTP; `await using` oder `.close()` + `await .closed` bei SSE und WebSocket).
