# HTTP-Operationen

Ein SDK definiert jede HTTP-Operation mit `defineRequest`: ihre Methode, die Pfadvorlage, das `input`-Schema, einen synchronen `builder` sowie die Response-Schemas für `output` und `error`. Konsumierende Anwendungen importieren die Operation, übergeben ihren konfigurierten `Client` und behandeln das zurückgegebene `[error, data, response]`-Tupel.

### Best Practices für das SDK-Design

- **Eine Operation pro Definition**: Halte jede Methode, jeden Pfad und jeden Vertrag in einer eigenen Definition, damit Anwendungen ungenutzte Operationen per Tree-Shaking entfernen können.
- **Statischen `operation`-Namen vergeben**: Verwende einen Bezeichner mit geringer Kardinalität wie `"orders.read"`. Telemetrie-Plugins (`@defjs/opentelemetry-server`) und Logging-Interceptors nutzen diesen, ohne URLs oder Benutzer-IDs preiszugeben.
- **Niemals einen Client im SDK einbetten**: Exportiere ausschließlich Definitionen, `struct`-Schemas und Typen.

## 2. URL-Auflösung und Pfadparameter

`withEndpoint(...)` erfordert eine gültige, absolute URL. Ihr Pfad wirkt als Basisverzeichnis (etwaige Query-Strings oder Hashes am Basis-Endpunkt werden verworfen).

<include cwd>examples/http/resolve-url.ts#example</include>

- **Pfad-Platzhalter (`:name`)**: Werden exakt einmal als einzelnes Pfadsegment URL-kodiert. Schrägstriche, `?`, `#`, `%`, Leerzeichen und Unicode verbleiben innerhalb dieses Segments – kodiere Werte daher nicht vorab. Leere Zeichenketten, `.` und `..` schlagen mit `REQ_BUILD_FAILED` fehl.
- **Origin- und Verzeichnisgrenzen**: Definitionspfade dürfen keine absoluten URLs sein, nicht protokollrelativ (`//...`) beginnen, keine C0-Steuerzeichen, Backslashes, `?` oder `#` enthalten und das Basisverzeichnis nicht über `../` verlassen. Jeder Verstoß schlägt mit `REQ_BUILD_FAILED` fehl, bevor Interceptors oder der Transport überhaupt ausgeführt werden.

## 3. Eingaben mit `builder` platzieren

Sobald eine Operation `input` deklariert, **muss** sie einen synchronen, reinen `builder` bereitstellen, der `{ path?, query?, headers?, body? }` zurückgibt. Nur Operationen ohne `input` dürfen auf `builder` verzichten.

### Wie `builder` Feld-Aliase kodiert

| Builder-Ausdruck                               | Ausgabe auf Wire-Ebene                                                             |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| `body: input.profile`                          | Typisiertes Struct: `.alias()` sowie `Date`- / `bigint`-Codecs greifen             |
| `body: { profile: input.profile }`             | Äußerer Schlüssel `profile` ist literal; inneres Objekt behält seine Struct-Aliase |
| `body: { ...input.profile, role: "admin" }`    | Spread behält Struct-Aliase bei; `role` ist literal                                |
| `body: { name: input.profile.customerName }`   | Anonymes Objekt: Schlüssel bleiben literal                                         |
| `query: input.filter` / `headers: input.trace` | Flache typisierte Objekte: Feld-`.alias()` wird zum Wire-Schlüssel                 |

### Eigene Query-Serialisierung

Standardmäßig werden Query-Skalare und Skalar-Arrays (wiederholte Schlüssel) direkt kodiert, während verschachtelte Query-Objekte mit `REQ_BUILD_FAILED` fehlschlagen. Erwartet dein Backend eine verschachtelte Query-Syntax (`filter[status]=paid`), konfiguriere `withQuerySerializer` am Client:

### Formate des Request-Bodys

`GET` und `HEAD` dürfen keinen Body tragen. Bei anderen Methoden wird das Format anhand des vom `builder` zurückgegebenen Werts gewählt:

| `body`-Wert                                                            | Auf Wire-Ebene gesendet als                        | Standard-`Content-Type`                     |
| ---------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------- |
| `undefined` / weggelassen                                              | Kein Body                                          | —                                           |
| Wurzel-Struct mit `urlencoded`- / `formData`-Codec                     | `URLSearchParams` / `FormData` (Aliase angewendet) | Formulartyp / Multipart-Boundary            |
| Natives `FormData` oder `URLSearchParams`                              | Unverändert durchgereicht                          | Multipart-Boundary / urlencoded             |
| `Blob` / `File`                                                        | Unverändert durchgereicht                          | `blob.type` oder `application/octet-stream` |
| `ArrayBuffer`, typisiertes Array, `DataView`, `ReadableStream`         | Rohe Bytes / Stream                                | `application/octet-stream`                  |
| `string`                                                               | UTF-8-Text                                         | `text/plain;charset=UTF-8`                  |
| Reines Objekt, Array, endliche Zahl, Boolean, `null`, `Date`, `bigint` | Struct-kodiertes JSON                              | `application/json`                          |

Werte, die sich nicht in JSON darstellen lassen (`NaN`, `±Infinity`, `Map`, `Set`, Funktionen, Klasseninstanzen ohne `toJSON()` oder rohe Iterables), schlagen sofort mit `REQ_BUILD_FAILED` fehl, anstatt stillschweigend zu `{}` oder `null` serialisiert zu werden.

## 4. Wie Antworten dekodiert werden

`output` validiert `2xx`-Antworten; `error` validiert Nicht-`2xx`-Antworten (`3xx`, `4xx`, `5xx`). Die Art des Structs bestimmt, wie der Response-Stream gelesen wird (`struct.string()` → Text, `struct.blob()` / `struct.file()` → `Blob`, `struct.arrayBuffer()` → `ArrayBuffer`, alles andere → JSON):

1. **Zweig anhand von `ok` (`200..299`) wählen**: `output` für `2xx`, `error` für Nicht-`2xx`.
2. **Opt-out beim Weglassen**: Ist für diesen Zweig kein Struct deklariert, wird der Response-Body niemals gelesen (`2xx` liefert `data: undefined` + `HttpMeta`; Nicht-`2xx` liefert `HTTP_STATUS` mit `data: undefined`).
3. **JSON-Medientyp zuerst prüfen**: Bei JSON-Structs führt ein Nicht-JSON-`Content-Type` zu `RES_MEDIA_TYPE_INVALID`, bevor der Body-Stream gelesen wird.
4. **Einlesen und Parsen**: Unlesbare Streams oder ungültiges JSON scheitern mit `RES_DECODE_FAILED` (oder `NET_BODY_INCOMPLETE`, falls mitten im Stream abgeschnitten).
5. **Mit `struct` validieren**: Schema-Abweichungen schlagen mit `RES_STRUCT_MISMATCH` fehl.

## 5. Anfragen abbrechen und Fristen setzen [#cancel-the-work]

Übergib `signal` an einen pro Aufruf abgeleiteten Client: `client({ signal })`.

- **Fristen (`NET_TIMEOUT`)**: Nutze `AbortSignal.timeout(ms)`.
- **Manueller Abbruch (`NET_ABORTED`)**: Nutze `AbortController`.
- **Kombinierte Signale**: Nutze `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`.

## 6. Zugangsdaten, XSRF und Übertragungsfortschritt

- **`withCredentials(true)`**: Setzt Fetch `credentials: "include"` für HTTP- und SSE-Anfragen.
- **`withXSRF(options?)`**: Liest das XSRF-Cookie (standardmäßig `XSRF-TOKEN`) aus und injiziert den Header (`X-XSRF-TOKEN`) bei Same-Origin-mutierenden HTTP-Methoden (`POST`, `PUT`, `PATCH`, `DELETE`).
- **`onDownloadProgress` / `onUploadProgress`**: Übergibst du an `client({ onDownloadProgress, onUploadProgress })`. Der Download-Fortschritt meldet `lengthComputable: true` nur dann, wenn `Content-Length` positiv ist und `Content-Encoding` fehlt oder `identity` lautet. Der Upload-Fortschritt streamt Bodys auf Server-Laufzeitumgebungen (Bun, Node.js). Ein Fortschritts-Callback, der eine Exception wirft, lässt den Aufruf mit `EXT_OBSERVER_FAILED` fehlschlagen.
