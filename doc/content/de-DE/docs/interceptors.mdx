# Interceptors

Interceptors gehören zur Laufzeitkonfiguration des Clients der Anwendung. So nutzt derselbe exportierte SDK-Endpoint je nach Umgebung andere Credentials, Tracing- oder Retry-Regeln. Stabile Parameter und ihre Request-Abbildung bleiben im Endpoint und seinem `builder`; Authentifizierung und andere übergreifende Regeln werden am Client eingerichtet.

Füge Auth-Headers hinzu, schließe Maintenance Windows per Short-Circuit kurz oder wiederhole sichere Reads — ohne Command-Validierung anzufassen. Jeder Transport hat seine eigene Chain. Du bekommst ein `HttpRequest` rein; du gibst das Ergebnis dieses Transports zurück (`HttpResponse`, Event-Stream-Handle oder WebSocket-Session). Input-Validierung läuft vor der Chain; Status-Dispatch und dekodierte Results danach.

## Onion-Order

`withInterceptors(...items)` akzeptiert gemischte Interceptors. Der Client filtert nach `kind` für den gewählten Transport und behält relative Registration-Order. Jeder Interceptor darf vor und nach `next` laufen:

| Factory                      | Request       | Ergebnis von `next`                   |
| ---------------------------- | ------------- | ------------------------------------- |
| `createHttpInterceptor`      | `HttpRequest` | `Promise<HttpResponse<unknown>>`      |
| `createSSEInterceptor`       | `HttpRequest` | `Promise<EventStreamHandle<unknown>>` |
| `createWebSocketInterceptor` | `HttpRequest` | `Promise<WebSocketSessionLike>`       |

<include cwd lang="typescript">
  examples/interceptors/onion-order.ts#example
</include>

Mehrere `withInterceptors(...)`-Aufrufe hängen ihre Interceptors an. Packe breite Observation außerhalb engerer Mutation/Retry, wenn der äußere Layer das finale Result sehen muss.

## Clonen und Request-Headers hinzufügen

Behandle das eingehende `HttpRequest` als Eigentum der Chain. Clone `Headers`, bevor du sie änderst; gib einen neuen Request an `next`:

<include cwd lang="typescript">
  examples/interceptors/add-request-headers.ts#example
</include>

Dasselbe Muster für SSE. Browser-WebSocket kann keine beliebigen Handshake-Headers hinzufügen — `request.headers` zu ändern authentifiziert keinen Browser-Socket. Nutze Protocol, URL-/Query-Policy oder einen server-supported Handshake.

HTTP schreibt nie einen abgeleiteten Content-Type in `request.headers`; Interceptors sehen nur deklarierte Header. `request.bodyContentType` enthält den abgeleiteten Typ des Builder-Bodys als gewöhnliches Feld und bleibt deshalb bei `{ ...req }`-Kopien erhalten. Ein expliziter `content-type`-Header hat immer Vorrang vor diesem Feld und der Erkennung, egal ob er vom Builder, von Client-Defaults, einem Interceptor oder einem rohen `fetchHandler`-Request deklariert wurde. Signierer sollten `headers.get('content-type') ?? request.bodyContentType` lesen.

Wenn du einen HTTP-Body ersetzt, ersetze `body` auf dem kopierten Request und deklariere seinen Typ mit einem `content-type`-Header. `bodyContentType` gilt nur, solange `body` der Wert des Builders ist; Ersatz-Bodys werden erneut erkannt, daher ist ein Ersatz-String Text, sofern der Header nichts anderes deklariert. `body: undefined` lässt keinen von der Library abgeleiteten Content-Type. Beim unveränderten Builder-Body unterdrückt `bodyContentType: null` die Typableitung der Library, wenn kein expliziter Header vorhanden ist; natives Fetch kann für einen String aber weiterhin einen eigenen Typ setzen. FormData nutzt immer seine tatsächliche Multipart-Boundary. Verwende keinen bereits konsumierten `ReadableStream`-Body erneut.

## Request short-circuiten

Du kannst `next` überspringen, musst aber den erwarteten Result-Type zurückgeben. Für HTTP baut `makeResponse(...)` einen kompatiblen Wrapper:

<include cwd lang="typescript">
  examples/interceptors/short-circuit.ts#example
</include>

Die Command-Layer dispatcht weiterhin nach Status. Deklariere ein einzelnes `error`-Struct für die Nicht-2xx-Seite, wenn Caller typisiertes `error.data` brauchen. Sie prüft außerdem weiterhin die deklarierte Seite: Ein JSON-`output` oder -`error` braucht einen JSON-`content-type`-Header auf der synthetischen Response, und `body` sollte bereits der geparste Wert sein, so wie der Transport ihn liefern würde (`request.responseType` und `request.errorResponseType` benennen die Representation). Short-Circuit von SSE oder WebSocket braucht ein vollständiges kompatibles Handle/Session (Closure-Promises, Live-State, Ownership und `[Symbol.asyncDispose]`). Partial Objects sind keine gültige Policy. Strukturelle `EventStreamHandle`- und `WebSocketSessionLike`-Implementierungen brauchen diesen Standard-Disposer jetzt zur Compile-Zeit; Consumer, die nur Defjs-Handles empfangen, haben keine neue Runtime-Aufrufpflicht.

## Sichere Reads wiederholen

Retries ändern Verhalten. Halte die Policy eng — dieses Beispiel wiederholt wiederholbare `GET` / `HEAD` / `OPTIONS` für Statuses `429`, `502`, `503`, `504`, cappt `Retry-After` bei 30s und stoppt nach zwei Retries oder bei Abort:

<include cwd lang="typescript">
  examples/interceptors/retry-safe-reads.ts#example
</include>

Geworfene Interceptor-/Fetch-Errors werden von diesem Loop nicht wiederholt — ein Transport-Failure lehnt ab, statt einen Status zu produzieren, auf den dieser Loop passen könnte. `POST` / `PUT` / `PATCH` / `DELETE` zu wiederholen braucht wiederholbare Bytes, Server-Support, einen Idempotency-Vertrag und eine geprüfte Status-Policy. Retry gehört dir — Core exportiert kein `retryAfter()`.

Ein Interceptor, der außerhalb dieses Samples einen Fehler wirft (oder abgelehnt wird), kommt beim Caller als
`EXT_INTERCEPTOR_FAILED` an, mit dem geworfenen Wert auf `cause` — siehe [Errors](/de-DE/docs/errors).
Das gilt auch, wenn ein Interceptor etwas anderes als das Ergebnis seines Transports liefert:
`undefined` durch ein vergessenes `return` oder eine native `Response` anstelle einer `HttpResponse`.
In einem HTTP-Interceptor ist das Werfen von `ERR_ABORTED` oder `ERR_TIMEOUT` stattdessen die Art, wie du Cancellation ausdrückst:
der Aufruf wird mit `NET_ABORTED` oder `NET_TIMEOUT` aufgelöst. SSE verpackt einen geworfenen Fehler, der nicht vom Transport kommt, als `EXT_INTERCEPTOR_FAILED`. Ein von WebSocket geworfener Fehler wird unverändert zurückgegeben, wenn er bereits ein Fault ist (ein `Error` mit einem String-`code`); jeder andere ist `EXT_INTERCEPTOR_FAILED`.

`next(request)` kann abgelehnt werden. Ein Transport-Failure ist ein Fault, keine Status-0-Response — ein
Interceptor, der einen beobachten will, legt also `try` / `catch` um `next`. Defjs ordnet ihn trotzdem
korrekt zu: ein Rejection, das vom Transport kam, bleibt ein `NET_*`-Fault und wird nicht deinem
Interceptor angelastet.

## WebSocket-Sessions umhüllen

Ein WebSocket-Interceptor darf `next` höchstens einmal aufrufen. Wenn du die Session umhüllst, delegiere Live-Getter und Lifecycle-Members explizit:

<include cwd lang="typescript">
  examples/interceptors/websocket-sessions.ts#example
</include>

Ein Spread einer Session hält `state` / `connection` / `bufferedAmount` nur als einmaligen Snapshot fest. Bewahre `closed`, `receive`, `close`, die exakte `[Symbol.asyncDispose]()`-Delegation und Listener-Cleanup, außer du änderst Ownership absichtlich. Ein Wrapper muss das Teardown-Promise der inneren Session zurückgeben, kein fremdes, bereits aufgelöstes Promise. Erzeugt eine Chain eine Session, die nicht ausgeliefert wird, beendet Core sie und schließt sie; gibt ein erfolgreicher Interceptor eine andere Session zurück, verwirft Core die erzeugte.

## Referenz

Factories geben tagged Transport-Values zurück:

- `createHttpInterceptor(fn)` → `{ kind: 'http', fn }`
- `createSSEInterceptor(fn)` → `{ kind: 'sse', fn }`
- `createWebSocketInterceptor(fn)` → `{ kind: 'web-socket', fn }`
- `basicAuthHttpInterceptor(provider, options?)` — Basic Credentials auf HTTP
- `basicAuthSSEInterceptor(provider, options?)` — Basic Credentials auf SSE

`HttpRequest` kann `endpoint`, `baseEndpoint`, `method`, `headers`, `body`, `queryParams`, `queryString`, `abort`, `timeout` und static `operation` enthalten. Es ist ein Transport-Integrationswert — nicht der geparste Input des Callers. `queryParams` ist `new URLSearchParams(queryString)` nach der Serialisierung. Ein konfigurierter Query-Serializer wird nicht aufgerufen, wenn der Builder keine Query erzeugt hat, und Builder-`URLSearchParams` werden as-is genutzt. Halte Command-Validierung, Output-Validierung und Domain-Error-Mapping in ihren Layern.

Die URL-Validierung beginnt während des Request-Baus: Ein fehlender, relativer oder ungültiger Basis-Endpoint oder ein unzulässiger Pfad scheitert mit `REQ_BUILD_FAILED`, bevor ein Interceptor oder Transport läuft, auch ein kurzschließender Interceptor. Vor dem Dispatch wird das endgültige `req.endpoint` gegen das endgültige `req.baseEndpoint` geprüft: Die aufgelöste URL muss den Origin dieser Basis behalten und unter ihrem Verzeichnis bleiben; C0-Steuerzeichen (einschließlich Tab, CR und LF), Backslashes, `?`, `#` und Verzeichnis-Escapes im Pfad werden abgelehnt. Schemaähnliche und protokollrelative Formen werden auch mit führenden Leerzeichen abgelehnt; ein normales Leerzeichen im Pfadinneren ist erlaubt und wird als `%20` gesendet. Ein Interceptor darf `baseEndpoint` absichtlich durch eine andere gültige absolute URL ersetzen. HTTP, SSE und WebSocket teilen die Regel, und deterministische URL-Fehler werden nie erneut versucht.

SSE-/WebSocket-Observer sind Lifecycle-Hooks, kein Control Flow. Melde WebSocket-Listener ab, wenn der Owner endet. Observer-Failures folgen dem Transport-Vertrag; ein Interceptor selbst kann einen Fehler werfen oder abgelehnt werden.

Logge eine geprüfte Allowlist: statische `operation`, Method, Status, Duration, stabiler Error-Code. Logge keine aufgelösten URLs, Query Strings, Auth-Headers, Bodies, Raw Causes, SSE-Event-IDs oder WebSocket-Payloads standardmäßig.

Basic Credentials sind Base64, nicht encrypted. Nutze TLS, halte Credential-Provider request-scoped auf einem Server, logge nie den generierten Header. Default-Encoder ist `globalThis.btoa`; gib `BasicAuthInterceptorOptions.encode`, wenn die Runtime kein `btoa` hat oder einen reviewed Encoder braucht.

Ein Interceptor kann Transport-Policy erzwingen. Er ist keine Input-Validierung, Authorization oder Resource-Ownership. Der Code, der langlebige Arbeit startet, nutzt weiterhin `await using` oder schließt manuell und wartet auf das Terminal-Promise. Normales HTTP bleibt request-scoped und wird mit seinem Timeout / `AbortSignal` verwaltet; `Client` ist nicht `AsyncDisposable`.
