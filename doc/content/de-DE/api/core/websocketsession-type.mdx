<ApiReference identity="@defjs/core:WebSocketSession" />

```ts
interface WebSocketSession<TIncoming = unknown, TOutgoing = never> extends AsyncDisposable {
  readonly bufferedAmount: number
  readonly connection: WebSocketConnectionInfo
  readonly closed: Promise<WebSocketCloseInfo>
  readonly receive: AsyncIterable<TIncoming>
  readonly state: WebSocketState
  close(code?: number, reason?: string): void
  [Symbol.asyncDispose](): PromiseLike<void>
  send(message: TOutgoing): void
  onRuntimeError(listener: (error: unknown) => void): () => void
  onStateChange(listener: (state: WebSocketState) => void): () => void
}
```

- `state` ist der logische [`WebSocketState`](/de-DE/api/core/websocketstate-type); `connection` ist die jüngste [`WebSocketConnectionInfo`](/de-DE/api/core/websocketconnectioninfo-type). `bufferedAmount` ist die native Zahl noch nicht gesendeter Bytes, oder `0` ohne physischen Socket.
- `receive` liefert eingehende Messages, die bereits mit dem `incoming`-Struct geparst sind. Es hat genau einen Consumer: Einen zweiten Iterator anzufordern wirft einen `TypeError`. Ein Frame, der sich nicht parsen lässt, wird an `onRuntimeError`-Listener gemeldet und übersprungen.
- `send(message)` validiert und kodiert die Message mit dem `outgoing`-Struct und sendet dann JSON-Text. Es sendet sofort, solange die Session `open` ist, puffert bei `reconnecting`, wenn `maxOutgoingQueueSize` es erlaubt, und wirft eine `DOMException` namens `InvalidStateError`, wenn die Session nicht beschreibbar ist. Es wirft außerdem, wenn kein `outgoing`-Struct deklariert ist, die Message am Struct scheitert oder die Queue abgeschaltet oder voll ist.
- Nach der Kodierung wirft ein Wert, den JSON nicht treu darstellen kann, `TypeError`, bevor gesendet oder in die Queue eingereiht wird. Dazu gehören nicht endliche Zahlen, Funktionen, Symbols, `Map`, `Set`, Streams und Klasseninstanzen ohne JSON-Darstellung, an der Wurzel oder verschachtelt. Dieselbe Prüfung schützt Heartbeat-Messages; ein Serialisierungsfehler des Heartbeats beendet die Session. Die Struct-Validierung kann einen Wert zuerst ablehnen.
- `close(code?, reason?)` fordert das Schließen an und stoppt den Heartbeat. `code` muss `1000` sein oder in `3000..4999` liegen, `reason` höchstens 123 UTF-8-Bytes; ungültige Argumente werfen, bevor sich der State ändert.
- `closed` wird aufgelöst mit der logischen terminalen [`WebSocketCloseInfo`](/de-DE/api/core/websocketcloseinfo-type).
- `onStateChange` und `onRuntimeError` geben eine Unsubscribe-Funktion zurück.

Nutze lieber `await using ownedSession = session` für Scope-Cleanup in deiner Verantwortung. Manuelles `session.close()` und `await session.closed` bleiben verfügbar.

```ts
async function consume(session: WebSocketSession<unknown, never>): Promise<void> {
  await using ownedSession = session
  for await (const message of ownedSession.receive) console.log(message)
}
```

Der Async-Disposer fordert den nativen Close an und wartet auf Defjs-eigenen Teardown, begrenzt ein fehlendes Close-Event aber auf eine Sekunde und kann mit einer `DOMException` namens `TimeoutError` abgelehnt werden. Er kann nicht beweisen, dass die physische TCP-Verbindung geschlossen ist.
