```ts
interface HttpRequest {
  abort?: AbortSignal
  baseEndpoint?: string
  body?: Blob | ArrayBuffer | FormData | URLSearchParams | ReadableStream<Uint8Array> | object | string | number | boolean | null
  bodyContentType?: string | null
  downloadProgress?: HttpProgressFn
  endpoint: string
  headers?: Headers
  method: string
  operation?: string
  queryParams?: URLSearchParams
  queryString?: string
  readonly responseType?: HttpResponseType
  readonly errorResponseType?: HttpResponseType
  timeout?: number
  uploadProgress?: HttpProgressFn
  withCredentials?: boolean
  xsrf?: {
    cookieName: string
    headerName: string
    tokenProvider?: (context: { request: HttpRequest }) => string | null | undefined
  }
  // plus an @internal bodyContentTypeSource field
}
```

Der Request, nachdem der Builder gelaufen ist, wie ihn Handler, Interceptors und `fetchHandler` nutzen.

- `body` ist bereits der Wire-Wert. Bei JSON ist das ein **JSON-Text-String**; signiere HMAC oder Digests gegen diesen String, nicht gegen den ursprünglichen Struct-Input.
- `endpoint` ist der Pfad mit eingesetzten Pfadparametern; `baseEndpoint` ist der Client-Endpoint.
- Interceptors sehen `queryParams` als `new URLSearchParams(queryString)`. Gibt ein Builder `URLSearchParams` zurück, wird diese Instanz durchgereicht.
- `operation` ist eine statische Endpoint-Identität mit niedriger Kardinalität für Telemetrie und Diagnose.
- `downloadProgress` und `uploadProgress` sind die Hooks `onDownloadProgress` und `onUploadProgress` aus `HttpExecuteOptions`.
- `responseType` und `errorResponseType` sind readonly: Sie werden aus den Struct-Kinds von `output` und `error` des Endpoints abgeleitet und dürfen nicht geändert werden. Jedes wird nur gesetzt, wenn sein Struct deklariert ist. Ein Interceptor, der per Short-Circuit mit `makeResponse` antwortet, liest sie, um zum Transport zu passen.
