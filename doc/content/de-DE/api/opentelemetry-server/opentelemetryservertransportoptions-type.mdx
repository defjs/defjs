description: 'Optionen, die alle Transporte teilen — `enabled` und die Span-Hooks, generisch über den Response-Typ.'
---

<ApiReference identity="@defjs/opentelemetry-server:OpenTelemetryServerTransportOptions" />

```ts
interface OpenTelemetryServerTransportOptions<TResponse> {
  enabled?: boolean
  startSpanHook?: (request: HttpRequest) => Attributes
  requestHook?: (span: Span, req: HttpRequest) => Promise<void> | void
  responseHook?: (span: Span, res: TResponse, req: HttpRequest) => Promise<void> | void
}
```

`TResponse` ist das, was `responseHook` erhält: `HttpResponse<unknown>` bei HTTP, `EventStreamHandle<unknown>` bei SSE, `WebSocketSessionLike` bei WebSocket. Siehe [OpenTelemetryServerHttpOptions](/de-DE/api/opentelemetry-server/opentelemetryserverhttpoptions-type), [OpenTelemetryServerSSEOptions](/de-DE/api/opentelemetry-server/opentelemetryserversseoptions-type) und [OpenTelemetryServerWebSocketOptions](/de-DE/api/opentelemetry-server/opentelemetryserverwebsocketoptions-type).

`enabled` ist standardmäßig `true`; nur `enabled: false` schaltet den Transport ab. Der alte boolesche Schalter (`http: false`) und Hooks auf oberster Ebene werden nur von den TypeScript-Typen abgelehnt. Es gibt keine Laufzeitprüfung: Zur Laufzeit lässt `http: false` den Transport aktiv, und ein Hook auf oberster Ebene wird stillschweigend ignoriert.

Span-Hooks werden nur mit einem übergebenen `tracer` aufgerufen. `startSpanHook` läuft für den jeweiligen Transport synchron vor der Span-Erzeugung. Seine Attribute werden nach den Built-in-Attributen angewandt, die Application darf also `url.full` oder einen anderen Initialwert überschreiben. Wirft er, erzeugt Defjs den Span mit Built-in-Attributen und setzt den Request fort. `requestHook` läuft nach der Span-Erzeugung und bevor der Request gesendet wird; `responseHook` läuft, nachdem das Transport-Ergebnis vorliegt. Beide dürfen ein Promise zurückgeben, aber auf keines wird gewartet: Ein geworfener Fehler oder eine Ablehnung blockiert die Operation nicht und lässt sie nicht fehlschlagen. `responseHook` bekommt den ursprünglichen Request als drittes Argument.

Solange `span.isRecording()` true ist, zeichnen Hook-Fehler die Events `defjs.otel.hook.error` und `exception` auf. Bei nicht aufzeichnenden Spans (beendet oder nicht gesampelt) gehen Fehler über `diag.error` an den OpenTelemetry-Diagnostic-Logger. Die Anwendung muss dafür `diag.setLogger(...)` aus `@opentelemetry/api` konfigurieren; standardmäßig erfolgt keine automatische Ausgabe. Das Paket initialisiert kein SDK, und diese Diagnose ist kein separater SDK-`LogRecord`.

Standardmäßig löst `url.full` nur `request.endpoint` gegen das optionale `request.baseEndpoint` auf; ein unabhängiges `request.queryString` wird nicht angehängt. Diese Grenze ist keine Redaction, und das Paket hat weder einen eingebauten Redactor noch eine Richtlinie für sensible Keys. Baue eine anwendungseigene URL explizit und schwärze sie bei Bedarf:
