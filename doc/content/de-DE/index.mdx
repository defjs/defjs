# Defjs

**TypeScript SDK & Resilient Client Kit — Den API-Vertrag einmal definieren. Die Ausführung pro Anwendung konfigurieren.**

Defjs trennt die beiden Seiten eines TypeScript-SDKs sauber voneinander:

- **SDK-Definition (`@defjs/core`, `@defjs/cli`)** — Deklariere typisierte HTTP-, SSE- und WebSocket-Operationen samt ihrer `struct`-Schemas (handgeschrieben oder als zustandsloses ESM aus OpenAPI-2.0/3.0/3.1/3.2-Spezifikationen generiert). Eine Definition sind reine Daten: Ihr Import startet weder einen Netzwerkaufruf noch bindet er einen globalen Client.
- **Fehlertolerante Anwendungsausführung (`@defjs/core`)** — Anwendungen erstellen ihren eigenen `Client` (`createClient(withEndpoint(...))`), hängen Zugangsdaten und Interceptors an (`basicAuth*`, `idempotencyKeyHttpInterceptor`, `concurrencyLimitHttpInterceptor`), konfigurieren P2C-Load-Balancing und `outlierDetection` (`halfOpen`, `maxEjectionPercent`), aktivieren `429`/`Retry-After`-Retries, verteilen Aufrufe parallel über `@defjs/core/concurrent` oder überbrücken Worker/Erweiterungen mit `@defjs/core/port`.

## Warum Definitionen von Clients trennen?

| Verantwortung | SDK-Autor (Definition)                                                                                                      | Anwendung (Ausführung)                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Besitzt**   | Methode, Pfadvorlage, `input`- / `output`- / `error`-Schemas, `builder`-Mapping und optionalen anwendungsdefinierten `meta` | Basis-URLs, Zugangsdaten, Auth-Interceptors, Load-Balancing, Timeouts und Ressourcen-Bereinigung |
| **Liefert**   | Wiederverwendbare ESM-Module und `.d.ts`-Deklarationen                                                                      | Laufzeitkonfiguration für Browser, Server oder Testumgebung                                      |
| **Vorteil**   | Keinerlei Bindung an die Laufzeitumgebung; funktioniert im Browser, bei SSR und in Tests                                    | Volle Kontrolle über Wiederholungsversuche (Retries), Failover, Telemetrie und Lifecycles        |

## Unterstützte Transporte und Ergebnis-Tupel

Jede Operation gibt ein dreiteiliges Error-first-Tupel zurück, das auf den Lebenszyklus des jeweiligen Transports zugeschnitten ist:

| Transport                               | Einstiegspunkt      | Tupel-Form                   | Lifecycle-Verwaltung                                                        |
| --------------------------------------- | ------------------- | ---------------------------- | --------------------------------------------------------------------------- |
| **[HTTP](/de-DE/docs/http)**            | `defineRequest`     | `[err, data, response]`      | In-Flight-Aufrufe via `client({ signal })` abbrechen                        |
| **[SSE](/de-DE/docs/sse)**              | `defineEventStream` | `[err, stream, open]`        | Freigeben mit `await using` oder `stream.close()` + `await stream.closed`   |
| **[WebSocket](/de-DE/docs/web-socket)** | `defineWebSocket`   | `[err, session, connection]` | Freigeben mit `await using` oder `session.close()` + `await session.closed` |

Bei einem HTTP-Fehler ist das Tupel `[err, undefined, undefined]`, da `err` bereits alle `HttpMeta`-Response-Metadaten enthält. Bei SSE und WebSocket enthält der dritte Slot den Startup-Snapshot, sofern vor dem Fehler einer erfasst wurde.
