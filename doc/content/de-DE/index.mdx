# Defjs

**Den API-Vertrag einmal definieren. Die Ausführung pro Anwendung konfigurieren.**

Defjs trennt die beiden Seiten eines TypeScript-SDKs sauber voneinander:

- **SDK-Definition (`@defjs/core`)** — Als SDK-Autor deklarierst du typisierte HTTP-, SSE- und WebSocket-Operationen zusammen mit ihren `struct`-Schemas. Eine Definition ist reine Daten: Ihr Import startet weder einen Netzwerkaufruf noch bindet er einen globalen Client.
- **Anwendungsausführung** — Konsumierende Anwendungen erstellen ihren eigenen `Client` (`createClient(withEndpoint(...))`), hängen Anmeldedaten und Interceptors an, konfigurieren Load-Balancing und übergeben diesen Client beim Aufruf einer Operation.

## Warum Definitionen von Clients trennen?

| Verantwortung | SDK-Autor (Definition)                                                                                                      | Anwendung (Ausführung)                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Besitzt**   | Methode, Pfadvorlage, `input`- / `output`- / `error`-Schemas, `builder`-Mapping und optionalen anwendungsdefinierten `meta` | Basis-URLs, Zugangsdaten, Auth-Interceptors, Load-Balancing, Timeouts und Ressourcen-Bereinigung |
| **Liefert**   | Wiederverwendbare ESM-Module und `.d.ts`-Deklarationen                                                                      | Laufzeitkonfiguration für Browser, Server oder Testumgebung                                      |
| **Vorteil**   | Keinerlei Bindung an die Laufzeitumgebung; funktioniert im Browser, bei SSR und in Tests                                    | Volle Kontrolle über Wiederholungsversuche (Retries), Failover, Telemetrie und Lifecycles        |

## Unterstützte Transporte und Ergebnis-Tupel

Jede Operation gibt ein dreiteiliges Error-first-Tupel zurück, das auf den Lebenszyklus des jeweiligen Transports zugeschnitten ist:

| Transport                               | Einstiegspunkt      | Tupel-Form                     | Lifecycle-Verwaltung                                                        |
| --------------------------------------- | ------------------- | ------------------------------ | --------------------------------------------------------------------------- |
| **[HTTP](/de-DE/docs/http)**            | `defineRequest`     | `[error, data, response]`      | In-Flight-Aufrufe via `client({ signal })` abbrechen                        |
| **[SSE](/de-DE/docs/sse)**              | `defineEventStream` | `[error, stream, open]`        | Freigeben mit `await using` oder `stream.close()` + `await stream.closed`   |
| **[WebSocket](/de-DE/docs/web-socket)** | `defineWebSocket`   | `[error, session, connection]` | Freigeben mit `await using` oder `session.close()` + `await session.closed` |

Bei einem HTTP-Fehler ist das Tupel `[error, undefined, undefined]`, da `error` bereits alle `HttpMeta`-Response-Metadaten enthält. Bei SSE und WebSocket enthält der dritte Slot den Startup-Snapshot, sofern vor dem Fehler einer erfasst wurde.
