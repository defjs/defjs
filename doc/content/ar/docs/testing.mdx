# الاختبارات

تختبر مكتبة `@defjs/core` محرك النقل والترميز الخاص بها بالفعل. عند استخدام Defjs في تطبيقك أو حزمة SDK الخاصة بك، فإن اختباراتك تتحقق من **الشيفرة التي كتبتها أنت**: مواضع `builder` ومفاتيح `.alias()` وفك ترميز `struct` ومعترضات المصادقة وتحويل أخطاء الأعمال وإلغاء الطلبات عند تفكيك المكونات.

## ما الذي تختبره في مشروعك — ولماذا تتجنب `vi.mock`

**لا** تقم بمحاكاة أو استبدال دوال `defineRequest` أو `defineEventStream` أو `defineWebSocket` المصدّرة باستخدام `vi.mock(...)`. استبدال العملية يتجاوز `builder` الخاص بك وترميز `.alias()` والمعترضات وتوزيع الحالات وفك ترميز `struct`.

بدلاً من ذلك، أنشئ `Client` اختبارياً معزولاً لكل اختبار عبر مقبض في الذاكرة (`withHTTPHandle` أو `withSSEHandle` أو `withWebSocketHandle`). هكذا تعمل تعريفاتك الحقيقية ومنطق أعمالك في الذاكرة دون فتح أي مقبس شبكي:

| طبقة في مشروعك                                                    | ما الذي يتحقق منه اختبارك                                                               | كيف توصل عميل الاختبار `Client`                                                                 |
| :---------------------------------------------------------------- | :-------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| تعريفات الطلبات والمخططات (`src/api/request/`، `src/api/schema/`) | مواضع `builder` (`path`، `query`، `headers`، `body`)، و`.alias()`، وفك `output`/`error` | استورد العملية الحقيقية ومرّر لها عميلاً جديداً مزوداً بـ `withHTTPHandle`                      |
| دوال الأعمال والمعترضات المخصصة (`checkout.ts`، `client.ts`)      | ترويسات المصادقة، إعادة الإرسال بعد `401`، التدفقات متعددة الخطوات، تحويل أخطاء الأعمال | مرّر `testClient` (مع تثبيت `withInterceptors(...)`) مباشرة إلى دالة الأعمال                    |
| مستهلكو SSE وWebSocket (`src/events/`، `src/quotes/`)             | معالجة الأحداث الواردة في منطق الأعمال، الرسائل الصادرة، وإغلاق `await using`           | غذِّ إطارات محاكاة في الذاكرة عبر `withSSEHandle` أو `withWebSocketHandle`                      |
| مكونات React / Vue (`OrderCard.tsx`، `OrderView.vue`)             | حالة التحميل، عرض البيانات، واجهة الخطأ، وإلغاء `AbortController` عند التفكيك           | غلّف المكوّن بـ `<ClientProvider client={testClient}>` أو ثبّت `createClientPlugin(testClient)` |

## 1. اختبار تعريفات الطلبات والمخططات في مشروعك (`withHTTPHandle`)

استورد عمليات `defineRequest` الحقيقية من مشروعك وأنشئ `Client` اختبارياً عبر `withEndpoint("https://fixture.invalid")` و`withHTTPHandle(...)`:

- **لماذا `https://fixture.invalid`**: تتحقق `createClient` من صحة رابط الأساس قبل وصول الطلب إلى `withHTTPHandle`؛ والنطاق `.invalid` محجوز حسب RFC ولا يستعلم DNS عاماً أبداً حتى مع خطأ في الإعدادات.
- **مقبض مستقل لكل بروتوكول**: يعترض `withHTTPHandle` طلبات HTTP (`defineRequest`) فقط. استخدم `withSSEHandle` مع `defineEventStream` و`withWebSocketHandle` مع `defineWebSocket`.
- **الإعدادات الافتراضية لإعادة المحاولة وفخ `withRetry(undefined)`**: إعادة المحاولة معطّلة عند حذف `withRetry` — اتركها معطلة في اختبارات الوحدة العادية كي تعود حالات `429`/`502`/`503`/`504` وأخطاء الشبكة بعد محاولة واحدة دون انتظار تراجع `1s + 2s + 4s`. انتبه: استدعاء `withRetry()` أو `withRetry(undefined)` يفعّل **3 محاولات افتراضية**. لتعطيلها صراحةً مرّر `withRetry({ maxRetries: 0 })`.

### ثلاث ركائز: العزل، فحص الطلب الصادر، والنتائج الثلاثة الشائعة

- **اعزل عميلاً لكل اختبار**: أنشئ `createClient(...)` جديداً داخل كل `test(...)` أو دالة مساعدة كي لا تتسرب ميزانية إعادة المحاولة أو العدادات بين الاختبارات.
- **تحقق من الصيغة الصادرة**: داخل `withHTTPHandle(async (input, init) => ...)` أنشئ `const request = new Request(input, init)` وتحقّق من `request.method` و`request.url` و`request.headers` و`await request.text()` (أو `await request.json()`).
- **محاكاة نتائج HTTP الثلاثة الشائعة والتحقق منها**:
  - **نجاح `2xx`**: أكّد `expect(err).toBeNull()` متبوعاً فوراً بـ `if (err) throw err;` ثم افحص حقول `data` المفكوكة.
  - **خطأ API `4xx` / `5xx`**: أعد `Response.json(..., { status: 422 })`، احرس بـ `if (err)` ثم ضيّق عبر `if (err.code === "HTTP_STATUS")` للتحقق من `err.status` و`err.data` و`err.response` ثم `return` وأتبعها بـ `expect.unreachable(...)` (وفي `bun:test` ارمِ `new Error("expected fault")`).
  - **فشل الشبكة (`NET_UNREACHABLE`)**: **لا** تعد `Response.error()`. أي `Response` مُعاد (حتى بالحالة `0`) يمر عبر معالجة حالة HTTP وينتج `HTTP_STATUS`. ارفض الوعد بدلاً من ذلك — مثل `Promise.reject(new TypeError("fetch failed"))` — لتفعيل `NET_UNREACHABLE`:

```ts
import { createClient, withEndpoint, withHTTPHandle } from "@defjs/core";
import { expect, test } from "vitest";
import { createOrder } from "./sdk/orders.ts";

test("يعيد NET_UNREACHABLE عند رفض fetch", async () => {
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withHTTPHandle(() => Promise.reject(new TypeError("fetch failed"))),
  );

  const [err] = await createOrder(client, { sku: "book", quantity: 1 });
  if (err) {
    expect(err.code).toBe("NET_UNREACHABLE");
    return;
  }

  expect.unreachable("expected NET_UNREACHABLE fault");
});
```

### اختبار استعادة `withRetry` وإعادة الإرسال بعد تجديد `401`

- **التعافي من `503` عبر `withRetry`**: احتفظ بعداد `let attempts = 0` خارج `withHTTPHandle` واضبط `withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] })` لتجربة الإعادة دون انتظار. انتبه: تمرير `methods` **يستبدل** القائمة الآمنة الافتراضية (`["GET", "HEAD", "OPTIONS", "TRACE", "PUT", "DELETE"]`)، لذا استخدم `methods: ["GET", "POST"]` إذا كان العميل نفسه يعيد `GET` أيضاً.
- **إعادة الإرسال بعد تجديد `401` في المعترض**: استدعاء `next(...)` مجدداً داخل المعترض لا يستخدم `withRetry`. اختبره مباشرةً عبر عداد في `withHTTPHandle`. وإذا قرأت `err.data` عند `401` فيلزم تعريف `error: struct(...)` على العملية.

```ts
import {
  createClient,
  createHttpInterceptor,
  withEndpoint,
  withHTTPHandle,
  withInterceptors,
  withRetry,
} from "@defjs/core";
import { expect, test } from "vitest";
import { submitOrder } from "./src/checkout.ts";

test("يعيد محاولة 503 لطلبات POST عند تضمين POST في methods", async () => {
  let attempts = 0;
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] }),
    withHTTPHandle(async () => {
      attempts += 1;
      if (attempts === 1) {
        return Response.json({ message: "try again" }, { status: 503 });
      }
      return Response.json({ id: "ord_2" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "pen", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_2");
});

test("يجدد الرمز عند 401 ويعيد استدعاء next() داخل المعترض", async () => {
  let token = "expired-token";
  let attempts = 0;

  const refreshAuth = createHttpInterceptor(async (req, next) => {
    const first = await next({
      ...req,
      headers: { ...req.headers, authorization: `Bearer ${token}` },
    });
    if (first[0]?.code === "HTTP_STATUS" && first[0].status === 401) {
      token = "fresh-token";
      return next({
        ...req,
        headers: { ...req.headers, authorization: `Bearer ${token}` },
      });
    }
    return first;
  });

  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withInterceptors(refreshAuth),
    withHTTPHandle(async (input, init) => {
      attempts += 1;
      const auth = new Request(input, init).headers.get("authorization");
      if (auth === "Bearer expired-token") {
        return new Response(null, { status: 401 });
      }
      expect(auth).toBe("Bearer fresh-token");
      return Response.json({ id: "ord_3" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "mug", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_3");
});
```

## 3. اختبار مستهلكي SSE وWebSocket في مشروعك

عندما يغلّف مشروعك `defineEventStream` أو `defineWebSocket`، مرّر إطارات محاكاة في الذاكرة عبر `withSSEHandle` أو `withWebSocketHandle`:

- **SSE (`withSSEHandle`)**: أعد `Response` مدعوماً بـ `ReadableStream<Uint8Array>` مع `"content-type": "text/event-stream"`. لمحاكاة انقطاع البث في منتصفه استدعِ `controller.error(new TypeError("stream dropped"))` بعد إرسال بعض الأجزاء (أو أعد `{ status: 500 }` لفشل البداية).
- **WebSocket (`withWebSocketHandle`)**: مرّر فئة فرعية من `EventTarget` تطبّق `WebSocketHandle` (`static readonly OPEN = 1` و`readyState`). يرسل `FakeQuoteSocket` أحداث `open` والرسائل الأولية عبر `queueMicrotask` كي يتمكن المستدعي من ربط المستمعات أو دخول `for await` قبل الإطلاق؛ الإرسال المتزامن في الباني يحدث مبكراً جداً. لمحاكاة خطأ أثناء الجلسة أطلق `new Event("error")` ثم `new CloseEvent("close", { code: 1011, reason: "boom" })`.

## 4. كيف تنظّم مشروعك لتظل كل طبقة سهلة الاختبار

اتباع البنية الموضحة في [طبقة API للتطبيق](/ar/docs/application-api) يُبقي اختباراتك خالية من `vi.mock`:

- **أبقِ `src/api/request/*.ts` خالياً من العميل**: صدّر فقط قيم `defineRequest` و`defineEventStream` و`defineWebSocket` ولا تستورد `apiClient` أبداً.
- **استقبل `Client` (أو `DerivableClient`) في دوال الأعمال**:
  - **الفرق بين `Client` و`DerivableClient`**: تعيد `createClient(...)` قيمة `DerivableClient` المتوافقة مع `Client`. لكن إذا اشتقت الدالة خيارات لكل استدعاء عبر `client({ signal })` فيجب أن يكون نوع المعامل **`DerivableClient`**.
  - **موضع المعاملات ومصانع SSR**: مرّر `client` أولاً (`placeOrder(client: DerivableClient, input: ...)`) أو أخيراً بقيمة افتراضية (`placeOrder(input: PlaceOrderInput, client: Client = apiClient)`)، وصدّر المعترضات مع `createServerApiClient(token, ...options: ClientOption[])` من `src/api/client.ts`.
  - **فخ `withXSRF()` في اختبارات Node / Bun**: تقرأ `withXSRF()` متغيرات المتصفح العامة (`globalThis.location`). إذا أنشأت `src/api/client.ts` عميل `apiClient = createClient(..., withXSRF())` دون شرط في أعلى الملف، فسيُخفق استيراد أي دالة ذات `= apiClient` فوراً عند التحميل في Node أو Bun. قيّد `withXSRF()` بشرط `typeof window !== "undefined"` أو ابنِ العميل داخل دالة مصنع.
- **احقن `testClient` في مكونات React وVue**:

## 5. اختبار المهل الزمنية والسلوك المعتمد على المؤقتات

لاختبار تراجع إعادة المحاولة أو تأخيرات إعادة الاتصال أو نبضات القلب، استخدم `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })` في Vitest (`jest.useFakeTimers()` في Bun test). تحديد `toFake` يترك الوعود والمهام الدقيقة تعمل بشكل طبيعي فلا تتجمد `async`/`await`.

لاحظ أن **مؤقتات Vitest الوهمية لا تقدّم ساعة `AbortSignal.timeout` الأصلية** لأنها تعتمد على مؤقت وقت التشغيل الأصلي لا على `setTimeout` في JS:

- لاختبار مهلة `client({ signal })` في Vitest، ألغِ `AbortController` من `setTimeout` مضبوط مع `new DOMException("request deadline", "TimeoutError")`. انتظر دائماً `await ready` قبل استدعاء `advanceTimersByTimeAsync` لضمان جدولة `setTimeout` داخل المقبض أولاً:

- بديلاً عن ذلك، يعتمد `withRetry({ maxRetries: 0, attemptTimeoutMs: 500 })` داخلياً على `setTimeout` في JS، لذا يفعّل `vi.advanceTimersByTimeAsync(500)` خطأ `NET_TIMEOUT` مباشرةً في Vitest.
- في **Bun test**، يتحكم `jest.useFakeTimers()` و`jest.advanceTimersByTime()` في `AbortSignal.timeout` أيضاً. تحقق من تغيرات الحالة أو عدد المحاولات وأعد المؤقتات الحقيقية دائماً في `finally`.
