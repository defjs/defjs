## حلّ عنوان URL

`withEndpoint(...)` يحتاج عنوان URL مطلقًا صالحًا. يبقى مسار نقطة النهاية مجلدًا؛ ويُهمل الاستعلام والـ hash قبل حل الأمر. إذا كانت نقطة النهاية الأساسية غائبة أو نسبية أو غير صالحة، يفشل بناء الطلب بـ `REQ_BUILD_FAILED` قبل تشغيل أي معترض أو وسيلة نقل، حتى لو كان المعترض سيُنهي السلسلة مبكرًا. تشترك HTTP وSSE وWebSocket في هذه القاعدة.

<include cwd>examples/http/resolve-url.ts#example</include>

عناصر المسار النائبة قيم مفردة (scalar) خام، تُرمَّز مرة واحدة بالضبط. تُرفض القيم الفارغة و`.` / `..`. الشرطة المائلة و`?` و`#` و`%` والمسافات وUnicode داخل عنصر نائب واحد تبقى مقطعًا مرمَّزًا واحدًا — لا ترمّز مسبقًا.

يبدأ اسم العنصر النائب عند `:` ويمتد حتى `/` التالية أو نهاية المسار: في `/files/:name.json` يكون اسم المعامل `name.json`، لا `name`. لا تُدعم النقطتان الحرفيتان في مقطع ثابت.

لا يجوز أن تكون مسارات التعريف شبيهة بـ scheme أو نسبية للبروتوكول (بما في ذلك مع مسافات بادئة)، أو أن تحتوي محارف التحكم C0 (بما فيها tab وCR وLF) أو شرطات مائلة عكسية أو `?` أو `#`. ويُسمح بمسافة عادية داخل المسار وتُرسَل كـ `%20`. بعد الحل، يجب أن يحتفظ URL بأصل نقطة النهاية الأساسية ويبقى ضمن مجلدها؛ فلا يجوز لمسار مثل `../users` الخروج منه. تفشل المسارات غير القانونية بـ `REQ_BUILD_FAILED` أثناء البناء، قبل النقل. يُفحص `req.endpoint` النهائي للمعترض مقابل `req.baseEndpoint` النهائي بالقاعدة نفسها؛ ويمكن للمعترض استبدال الأساس عمدًا بعنوان URL مطلق صالح آخر. لا تُعاد محاولة أخطاء URL الحتمية أبدًا.

مرمّز الاستعلام الافتراضي يقبل القيم المفردة ومصفوفاتها (المصفوفات تكرر المفتاح). كائن متداخل يفشل بـ `REQ_BUILD_FAILED` ما لم يملك العميل `withQuerySerializer(...)`. `null` في `path` أو `query` أو `headers` يفشل بالطريقة نفسها. `undefined` يُحذف.

## ضع المدخل

الـ struct يرمّز القيمة. والـ builder يضعها. عند التصريح بـ `input`، يجب دائمًا توفير `builder` صريح، حتى لو كان المدخل يطابق شكل الطلب أصلًا. يمكن حذف `builder` فقط من التعريفات التي لا تصرّح بـ `input`.

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

ذلك الجسم هو `{"display_name":"Ada"}` مع `application/json`. اسم الرأس على السلك هو `x-request-id`. المستدعون والنتائج المحلَّلة يبقون `displayName`.

فضّل تسليم القيمة المحدَّدة النوع على تهجئة مفاتيح السلك. يُعلَن alias مرة واحدة على الحقل وينطبق في الاتجاهين: `output` / `error` / الأحداث / الإطارات الواردة تفك `display_name` إلى `displayName`، و`body: input.order` يعيد كتابة الشجرة كلها. يمكن لـ struct `User` نفسه أن يكون جسم إنشاء ومخرج جلب. المفتاح الذي تكتبه بنفسك هو الاستثناء: الكائن الأب مجهول، فلا يعمل الـ alias.

| تعبير الـ builder                               | على السلك                                                    |
| ----------------------------------------------- | ------------------------------------------------------------ |
| `body: input.profile`                           | كائن محدَّد النوع: ترميز alias و`Date` / `bigint`            |
| `body: { profile: input.profile }`              | المفاتيح الخارجية حرفية، والكائن الداخلي ما زال محدَّد النوع |
| `body: { ...input.profile, role: 'admin' }`     | النشر يُبقي الـ struct؛ والمفتاح الإضافي حرفي                |
| `body: { name: input.profile.displayName }`     | أب مجهول: لا ينطبق الـ alias                                 |
| `query: input.query` / `headers: input.headers` | كائنات مسطّحة محدَّدة النوع: يصبح alias مفتاح السلك          |

نشر كائن محدَّد النوع مع تعيين مفتاح سلكه أيضًا (`display_name` بجانب `displayName`) هو `REQ_BUILD_FAILED`. كائن متداخل في `path` أو `headers` يفشل بالطريقة نفسها.

يُختار الدليل عند كل عقدة، لا عند الجذر فقط. الكائن الجديد تحت أب مجهول يُبقي المفاتيح التي كتبتها. الكائن نفسه تحت أب محدَّد النوع يستخدم struct ذلك الحقل.

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

عندما يطابق دليل الاتحاد أكثر من فرع، يُرمَّز كل فرع ثم تُقارَن النتائج. يُبقى الخرج السلكي المتطابق؛ والاختلاف هو `REQ_BUILD_FAILED`.

التقاطع المختلط الذي يتضمن جزءًا غير كائن يُوسَم عند التحليل باقتران وسوم الأجزاء المطابقة؛ وقيمة التقاطع المختلط المكتوبة من جديد دون تحليل تُعامَل ككائن مجهول.

### الاستعلام

شكل الاستعلام المتداخل (`a[b]` و`a.b` والقوائم المفصولة بفواصل) اصطلاح للخلفية، لذا الخطاف على العميل:

<include cwd>examples/http/query-serializer.ts#example</include>

`query` هنا هو الكائن المرمَّز بصيغة النقل. الأسماء المستعارة مُطبَّقة أصلًا، لذا مُسلسِل مثل `qs` لا يسقطها. السلسلة المُعادة هي سلسلة الاستعلام. Defjs لا تعتمد على `qs`.

بلا مُسلسِل، المصفوفات تكرر المفاتيح والكائن المتداخل هو `REQ_BUILD_FAILED`. إرجاع `URLSearchParams` من الـ builder يستخدم تلك القيمة كما هي ويتخطى المُسلسِل. لا يُستدعى المُسلسِل عندما لا يوجد استعلام. يرى المعترضون بعد ذلك `queryParams` كـ `new URLSearchParams(queryString)`.

### الجسم

أول تطابق يفوز:

| قيمة `body`                                                   | تُرسَل كـ                                                                   | نوع المحتوى الافتراضي                                 |
| ------------------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------- |
| محذوف / `undefined`                                           | بلا جسم                                                                     | —                                                     |
| كائن محدَّد النوع جذره يحمل وسم `urlencoded` أو `formData`    | `URLSearchParams` / `FormData`؛ المفاتيح أسماء سلك؛ المصفوفات تكرر المفاتيح | نوع النموذج / الفاصل الذي تحدده المنصة                |
| `FormData`، `URLSearchParams`                                 | كما هي                                                                      | نفسه؛ Defjs تمسح `Content-Type` القديم على `FormData` |
| `Blob` / `File`                                               | كما هي                                                                      | `blob.type`، أو `application/octet-stream`            |
| `ArrayBuffer`، `TypedArray`، `DataView`                       | كما هي                                                                      | `application/octet-stream`                            |
| `ReadableStream`                                              | متدفّق (`duplex: 'half'` عندما يسمح وقت التشغيل)                            | `application/octet-stream`                            |
| `string`                                                      | كما هي                                                                      | `text/plain;charset=UTF-8`                            |
| كائن بسيط، مصفوفة، عدد، قيمة منطقية، `null`، `Date`، `bigint` | مرمَّز، ثم `JSON.stringify`                                                 | `application/json`                                    |

يبقي HTTP النوع المستنتج لجسم المنشئ في الحقل العادي `request.bodyContentType`، الذي يبقى بعد نسخ `{ ...req }`؛ ولا يكتب هذا الاستنتاج أبدًا في `request.headers`. يتقدّم رأس `content-type` الصريح دائمًا، سواء ضبطه المنشئ أو قيم العميل الافتراضية أو معترض أو طلب `fetchHandler` خام، حتى عندما يحوّل تقدّم الرفع الجسم إلى تدفق. لا ينطبق `bodyContentType` إلا ما دام `body` قيمة المنشئ؛ ويُكتشف الجسم البديل من جديد، لذا يعلن المعترض نوعه برأس `content-type`. لا يرسل `body: undefined` أي Content-Type تستنتجه المكتبة. FormData هي الاستثناء: يجب أن يستخدم نوع محتواها الفاصل الناتج عن التسلسل الفعلي. وسم الترميز ينطبق فقط عند جذر الجسم: `body: { meta: input.form }` هو JSON، وحقول النموذج حقول JSON عادية. السلسلة نص خام؛ وسلسلة JSON مثل `"abc"` تحتاج `JSON.stringify` مع `application/json`. حقول `undefined` تُحذف؛ وحقل `nullable` مُرسَل كـ `null` هو JSON `null`.

يجب أن يقتصر محتوى JSON، في جميع مستويات التداخل، على بيانات JSON: كائنات بسيطة، ومصفوفات، وسلاسل نصية، وأعداد منتهية، وقيم منطقية، و`null`، إضافةً إلى القيم التي تُرجع دالتها `toJSON()` بيانات من هذه الأنواع، مثل `Date` أو `URL`. أي قيمة أخرى، سواء في الجذر أو في مستوى متداخل، تؤدي إلى فشل الاستدعاء بـ `REQ_BUILD_FAILED` قبل أن يُرسَل أي شيء، بدلًا من إرسالها كـ `{}` أو `null` أو عدم إرسال جسم أصلًا: `Map` أو `Set`، أو نسخة من صنف بلا `toJSON`، أو دالة، أو `NaN`، أو `Readable` من Node، أو كائن يدعم التكرار أو التكرار غير المتزامن، بما في ذلك كائن حرفي فيه أسلوب `Symbol.iterator` أو `Symbol.asyncIterator`. تحدّد رسالة الخطأ اسم الحقل. كائن يدعم التكرار يُعطى كـ `query` أو `headers` يفشل بالطريقة نفسها بدلًا من إسقاطه؛ مرّر أزواج الرؤوس كمصفوفة. أرسل التدفق كـ `ReadableStream` للويب: `ReadableStream.from(iterable)` أو `Readable.toWeb(readable)`. يرفض نوع `body` معظم هذه القيم وقت الترجمة؛ أما القيمة المعرَّفة بواسطة `interface` أو نسخة الصنف فتحتاج إلى `{ ...value }`.

`GET` و`HEAD` لا يمكنهما إرجاع جسم — ذلك خطأ نوع. لا يمكن لـ builder في WebSocket إرجاع `headers` أو `body`.

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

`JSON.stringify` أو `qs` أو protobuf الذي تشغّله بنفسك يرى الأسماء المنطقية. لا ينطبق alias على ذلك المسار. لا يوجد `struct.encode` عام.

يجوز للـ builder أن يتفرّع على المدخل الحقيقي ويُرجع جسمًا مختلفًا لكل حالة (سجلات JSON أو `File` أو `URLSearchParams`). `Headers` الأصلية تُمرَّر أيضًا ولا تُعاد ترميزها.

## كيف يُقرأ الجسم

`output` هو Struct واحد لجسم 2xx؛ و`error` هو Struct واحد لكل ما عداه. نوع الـ struct
يختار التمثيل: `string` نص خام، و`blob` / `file` blobs، و`arrayBuffer` بايتات،
وكل نوع آخر JSON. وإن لم يُعلَن أي طرف، فالجسم لا يُقرأ أبدًا.

ترتيب العمليات:

1. `ok` يختار الطرف: `output` لـ 2xx، و`error` لكل ما عداه. لا الاثنان معًا أبدًا.
2. لا شيء معلَن لذلك الطرف ← الجسم لا يُقرأ أبدًا. 2xx ينجح مع `data === undefined`؛
   وغير-2xx هو `HTTP_STATUS` مع `data === undefined`. جسم غير مقروء في طرف لم
   تُعلنه يُتجاهل، بما في ذلك حقيقة أنه لم يكن قابلًا للقراءة.
3. يُفحص نوع الوسائط **قبل** قراءة الجسم. عدم التطابق هو `RES_MEDIA_TYPE_INVALID` ولا
   يُحلَّل شيء ولا يُفك.
4. يُقرأ التمثيل. الفشل هو `RES_DECODE_FAILED`. يُحلَّل JSON القادم من النقل مرة واحدة: السلسلة النصية في
   هذه القيمة جذر نصي JSON ولا تُحلَّل مرة أخرى؛ البايتات والـ blobs خامّة وتُحلَّل مرة واحدة.
5. يحلّل الـ Struct القيمة. الفشل هو `RES_STRUCT_MISMATCH`.
6. 2xx ← النتيجة و`response.body` محدَّد النوع؛ وغير-2xx → `data` محدَّد النوع على `HTTP_STATUS`.

ينفّذ نقل Fetch المدمج الخطوتين 3 و4 للطرف المعلَن بينما الاستجابة ما زالت داخل سلسلة المعترضات، فتتلقى المعترضات استجابة يكون `body` فيها هو JSON المحلَّل أو النص أو `Blob` أو البايتات؛ وأي فشل في هاتين الخطوتين يظهر كالـ fault نفسه من فئة `RES_*`، أو كـ `NET_BODY_INCOMPLETE` عندما ينقطع تدفق الجسم. أما الخطوة 5 فتعمل مرة واحدة، بعد السلسلة. لذا فالاستجابة التي بناها معترض بـ `makeResponse(...)` تمرّ بالفحص نفسه لنوع الوسائط والتحويل نفسه للتمثيل والـ Struct نفسه كتلك القادمة من الشبكة. في تمثيل JSON، جسم السلسلة النصية هو جذر نصي JSON.

الاستجابة الناجحة هي `DecodedResponse<T>`: `url` و`status` و`statusText` و`headers` و`ok` و
`body` محدَّد النوع. وحيث لم يُفك شيء تحصل على `HttpMeta` — الحقول نفسها بلا `body`. `ok`
يعني فقط `200 <= status < 300`. وليس أي منهما `Response` أصليًا. فشل النقل خطأ، فلا
توجد استجابة بحالة 0 تنوب عنه.

## ألغِ العمل

خيارات التنفيذ تأخذ `signal` مع إما `abort` أو `timeout`. **`abort` و`timeout` متنافيان.** يمكن لـ `signal` أن يجتمع مع أي منهما.

<include cwd>examples/http/cancel.ts#example</include>

يجب أن يكون `timeout` عددًا صحيحًا آمنًا موجبًا في `1..2_147_483_647`. الاستدعاء الذي يحذف `timeout` يحصل على القيمة الافتراضية من `withTimeout` في العميل. الإلغاء المتعرَّف عليه ← `NET_ABORTED`؛ ومهلة التنفيذ ← `NET_TIMEOUT`؛ ورمي المعترض ← `EXT_INTERCEPTOR_FAILED`، إلا `ERR_ABORTED` / `ERR_TIMEOUT` فيعطيان `NET_ABORTED` / `NET_TIMEOUT`؛ وفشل Fetch الآخر ← `NET_UNREACHABLE`. الإلغاء بعد أن قبل الخادم كتابة **لا** يثبت أن الكتابة تراجعت.

## بيانات الاعتماد وXSRF

`withCredentials(true)` يضبط Fetch `credentials: 'include'` لـ HTTP وSSE. لا ينشئ `Authorization` ولا يضبط مصادقة WebSocket. `false` يترك بيانات الاعتماد غير محددة.

`withXSRF(...)` لـ HTTP فقط. الافتراضي: `cookieName: 'XSRF-TOKEN'`، `headerName: 'X-XSRF-TOKEN'`. يُحقن الرأس فقط للطرائق غير الآمنة، وفقط عندما لم يضبطه المستدعي أصلًا. كلما وُجد `location`، بما في ذلك داخل Worker، يجب أن يطابق URL الطلب المحلول `location.origin`؛ ولا يستدعي الطلب العابر للأصول `tokenProvider`. أما قراءة ملف تعريف الارتباط فتتطلب `document` بشكل مستقل. يتخطى `GET` و`HEAD` و`OPTIONS` و`TRACE`. في Worker أو على الخادم، مرّر `tokenProvider` متزامنًا محدودًا بالطلب إن احتجت الحقن.

أبقِ بيانات الاعتماد ورموز XSRF وسلاسل الاستعلام خارج السجلات الروتينية. لا تستخدم معاملات الاستعلام قناة بيانات اعتماد عامة.

## التقدّم وحد Fetch

`onDownloadProgress` يعمل أثناء قراءة جسم استجابة معلَن. يحسب `loaded` البايتات المقروءة من تدفق الاستجابة، والتي ربما فكّ Fetch ضغطها بالفعل. لا يكون `lengthComputable` صحيحًا إلا مع `Content-Length` موجب وغياب `Content-Encoding` أو كونه `identity`. تُبلّغ الترميزات الأخرى، بما فيها gzip وbr، عن `total: 0` و`lengthComputable: false`، فلا تُقارَن البايتات المفكوك ضغطها بطول البيانات المضغوطة على السلك. بلا struct لذلك الطرف ← الجسم لا يُقرأ ← لا تقدّم لقراءة الجسم.

`onUploadProgress` يبلّغ عن تقدّم جسم `ReadableStream<Uint8Array>` بينما يقرأه Fetch، لا عندما يقرّ الخادم باستلامه. يُبلَّغ عن تقدّم الرفع فقط في بيئات التشغيل التي تدعم إرسال أجسام الطلبات كتدفق: في Bun وNode وDeno، تحوّل Defjs أيضًا أجسام `Blob` / `File` و`ArrayBuffer` و`FormData` إلى تدفق، فيُبلَّغ عن تقدّم رفعها أيضًا. في بيئات تشغيل الخادم، تستخدم FormData مع `onUploadProgress` التدفق الناتج عن التسلسل مباشرةً، وتحتفظ بفاصل multipart، وتُرسَل دون `Content-Length` تولّده المكتبة (مجزّأة عبر HTTP/1.1)، فيعمل التقدّم والمهلة والإلغاء دون تخزين الجسم كاملًا. يبقى حجمها الإجمالي مجهولًا ما لم يحدده `Content-Length` صريح صالح. ولنقطة نهاية تتطلب `Content-Length`، مثل بعض وجهات الرفع الموقَّعة مسبقًا، احذف `onUploadProgress`؛ عندئذٍ يرسل Fetch الخاص بالمنصة FormData مع طولها. يحرّر الإلغاء التدفق المغلّف. تُستثنى المتصفحات، بما فيها Workers، لأن Chromium لا يدعم إرسال جسم الطلب كتدفق إلا عبر HTTP/2 أو أحدث، بينما لا يدعم Firefox ذلك إطلاقًا؛ لذا تُرسل تلك الأجسام دون تغيير ولا يُستدعى `onUploadProgress`. أما أجسام JSON والنص و`URLSearchParams` والمصفوفات المُنمَّطة فتُرسل كاملةً ولا تنتج أي أحداث. قيمة `total` هي `0` (فتكون `lengthComputable` بقيمة `false`) لتدفق بلا طول معروف. أما إرسال جسم `ReadableStream` في بيئة تشغيل لا تدعم إرسال أجسام الطلبات كتدفق، مثل Firefox، فيُفشل الاستدعاء بـ `ENV_UNSUPPORTED` قبل أن يُرسَل أي شيء؛ ورسالة `cause` هي `ERR_STREAMING_REQUEST_UNSUPPORTED`. في Chromium يحتاج جسم `ReadableStream` إلى HTTP/2 أو أحدث؛ وعبر HTTP/1.1 يفشل الاستدعاء بـ `NET_UNREACHABLE`. ويعمل `onDownloadProgress` بالطريقة نفسها في جميع بيئات التشغيل.

ردّ نداء التقدّم الذي يرمي استثناءً أو يُرجع وعدًا مرفوضًا يُفشل الاستدعاء بـ `EXT_OBSERVER_FAILED`، مع القيمة المرمية في `cause`، للتنزيل والرفع على السواء. ويظل الإلغاء من جانب المستدعي و`timeout` يُبلَّغ عنهما بالرمزين `NET_ABORTED` / `NET_TIMEOUT` على الترتيب.

`fetchHandler(httpRequest, fetchImpl?)` هو حد Fetch الأدنى: يحل عنوان URL، ويستدعي Fetch، ويقرأ التمثيل، ويُرجع `HttpResponse`. يحل معالجا HTTP وSSE الافتراضيان `globalThis.fetch` عند كل استدعاء، فيُستخدم البديل المثبّت بعد الاستيراد. يستخدم HTTP الصيغة `(url, init)` فقط مع Fetch الأصلي للمنصة دون تعديل؛ أما Fetch العام المستبدل أو المعالج المخصص فيتلقى `Request` أصليًا. يجوز استيراد Core دون Fetch؛ إذا ظل Fetch غائبًا، يفشل تنفيذ HTTP/SSE الافتراضي بـ `ENV_UNSUPPORTED`، بينما تبقى المعالجات المخصصة قابلة للاستخدام. هذا الحد **لا** يتحقق من مدخل الأمر، ولا يوزّع `output`، ولا يشغّل المعترضات. مفيد لاختبارات النقل المحقون — وليس بديلًا عن `client.execute`.

## حدود إعادة الإرسال

Defjs **لا** تعيد محاولة HTTP تلقائيًا. إعادة محاولة قراءة ما زالت تحتاج سياسة مهلة/شبكة/تكرار مراجعة. إعادة محاولة عملية كتابة تحتاج بايتات قابلة لإعادة الإرسال، ودعم الخادم، ومفتاح idempotency مربوط بنطاق المصادقة + بايتات الطلب، وسياسة تكرار لدى المستقبِل.

حد العميل/الأمر/Fetch لا يستطيع أن يعرف إن كانت الكتابة الفاشلة قد اكتملت. أبقِ قرارات إعادة الإرسال في التطبيق أو في معترض مراجع. يمكن للمعترضات أن تختصر المسار أو تستبدل الطلب منخفض المستوى؛ ويجب أن تظل الحالة النهائية والجسم مستوفيين لعقد الأمر.
