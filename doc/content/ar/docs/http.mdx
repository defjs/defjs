# عمليات HTTP

تُعرّف حزمة SDK كل عملية HTTP باستخدام `defineRequest`: طريقة الطلب، وقالب المسار، ومخطط المدخلات `input`، ودالة `builder` التزامنية، ومخططات الاستجابة للمخرجات `output` والأخطاء `error`. تستورد التطبيقات المستهلكة هذه العملية، وتمرر عميلها المهيأ `Client`، وتتعامل مع مصفوفة النتائج الناتجة `[error, data, response]`.

## 1. تعريف العملية واستدعاؤها

امنح كل عملية تصديراً مستقلاً عبر `defineRequest` داخل وحدة SDK الخاصة بك، واحتفظ بإنشاء العميل `createClient` داخل التطبيق المستهلك:

### أفضل ممارسات تصميم حزم SDK

- **عملية واحدة لكل تعريف**: احتفظ بكل طريقة ومسار وعقد في تعريف منفصل ومستقل حتى تتمكن التطبيقات من استخدام تقنية tree-shaking واستبعاد العمليات غير المستخدمة.
- **تحديد اسم ثابت للعملية `operation`**: استخدم معرّفاً ثابتاً منخفض التباين مثل `"orders.read"`. تستخدمه إضافات القياس عن بُعد (`@defjs/opentelemetry-server`) ومعترضات تسجيل السجلات دون تسريب عناوين URL أو معرّفات المستخدمين الحساسة.
- **عدم تضمين العميل داخل SDK أبداً**: صدّر فقط التعريفات، ومخططات `struct`، وتصريحات الأنواع.

## 2. تحديد الروابط ومعلمات المسار

تتطلب الدالة `withEndpoint(...)` عنوان URL مطلقاً وصالحاً. ويعمل مساره كدليل أساسي (يتم تجاهل أي معلمات استعلام أو وسم تجزئة hash في العنوان الأساسي).

<include cwd>examples/http/resolve-url.ts#example</include>

- **العناصر النائبة في المسار (`:name`)**: تُرمّز مرة واحدة فقط كقطاع مسار مفرد. وتبقى الشرطات المائلة و`?` و`#` و`%` والمسافات ومحارف Unicode داخل هذا القطاع — لا تقم بترميز القيم مسبقاً. بينما النصوص الفارغة و`.` و`..` تفشل فوراً بخطأ `REQ_BUILD_FAILED`.
- **حظر الخروج عن النطاق والدليل الأساسي**: لا يمكن لمسارات التعريفات أن تكون عناوين URL مطلقة، ولا نسبية للبروتوكول (`//...`)، ولا أن تحتوي على محارف تحكم C0، أو شرطات مائلة عكسية `\`، أو `?`، أو `#`، أو الهروب من دليل نقطة النهاية الأساسية (`../`). وأي مخالفة تفشل بخطأ `REQ_BUILD_FAILED` قبل تشغيل أي معترضات أو وسائل نقل.

## 3. وضع المدخلات باستخدام `builder`

كلما أعلنت العملية عن `input`، **يجب** عليها تقديم دالة `builder` تزامنية ونقية تُرجع `{ path?, query?, headers?, body? }`. ولا يجوز إغفال `builder` إلا في العمليات التي لا تتطلب أي `input`.

### كيف تُرمّز دالة `builder` الأسماء البديلة للحقول

| تعبير Builder                                  | المخرج السلكي عبر الشبكة                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------ |
| `body: input.profile`                          | بنية struct محددة الأنواع: تُطبّق `.alias()` ومحولات `Date` و`bigint`          |
| `body: { profile: input.profile }`             | المفتاح الخارجي `profile` حرفي؛ بينما يحتفظ الكائن الداخلي بأسمائه البديلة     |
| `body: { ...input.profile, role: "admin" }`    | يحافظ النشر (Spread) على أسماء struct البديلة؛ بينما `role` حرفي               |
| `body: { name: input.profile.customerName }`   | كائن مجهول: المفاتيح حرفية تماماً                                              |
| `query: input.filter` / `headers: input.trace` | كائنات بسيطة ذات أنواع محددة: يتحول `.alias()` الخاص بالحقل إلى المفتاح السلكي |

### تخصيص تسلسل معلمات الاستعلام (Query Serialization)

افتراضياً، تُرمّز القيم القياسية ومصفوفات القيم القياسية (المفاتيح المتكررة) مباشرة، بينما تفشل كائنات الاستعلام المتداخلة بخطأ `REQ_BUILD_FAILED`. فإذا كانت واجهتك الخلفية تتطلب بنية استعلام متداخلة (مثل `filter[status]=paid`)، فاضبط `withQuerySerializer` على مستوى العميل:

### تنسيقات جسم الطلب (Request Body)

لا يمكن لطلبي `GET` و`HEAD` حمل جسم طلب. وبالنسبة للطرق الأخرى، يُحدد تنسيق الجسم بناءً على القيمة التي تُرجعها دالة `builder`:

| قيمة `body`                                                         | طريقة الإرسال سلكياً                                      | ترويسة `Content-Type` الافتراضية          |
| ------------------------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------- |
| `undefined` / تم إغفالها                                            | بدون جسم للطلب                                            | —                                         |
| بنية struct جذرية مع محول `urlencoded` أو `formData`                | `URLSearchParams` / `FormData` (مع تطبيق الأسماء البديلة) | نوع النموذج / حدود multipart              |
| كائن أصلي من نوع `FormData` أو `URLSearchParams`                    | يُمرر كما هو دون تغيير                                    | حدود multipart / urlencoded               |
| `Blob` / `File`                                                     | يُمرر كما هو دون تغيير                                    | `blob.type` أو `application/octet-stream` |
| `ArrayBuffer`، مصفوفة ذات نوع، `DataView`، `ReadableStream`         | بايتات خام / تدفق                                         | `application/octet-stream`                |
| `string`                                                            | نص UTF-8                                                  | `text/plain;charset=UTF-8`                |
| كائن بسيط، مصفوفة، رقم محدود، قيمة منطقية، `null`، `Date`، `bigint` | JSON مُرمَّز عبر struct                                   | `application/json`                        |

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

تؤدي القيم التي لا يمكن تمثيلها في JSON (مثل `NaN` أو `±Infinity` أو `Map` أو `Set` أو الدوال أو كائنات الأصناف التي لا تحتوي على `toJSON()` أو المكررات الخام) إلى الفشل فوراً بخطأ `REQ_BUILD_FAILED` بدلاً من تحويلها بصمت إلى `{}` أو `null`.

## 4. كيفية فك ترميز الاستجابات

يتحقق `output` من صحة استجابات `2xx`؛ بينما يتحقق `error` من استجابات الحالات غير `2xx` (`3xx` و`4xx` و`5xx`). ويحدد نوع struct كيفية قراءة تدفق الاستجابة (`struct.string()` ← نص، `struct.blob()` / `struct.file()` ← `Blob`، `struct.arrayBuffer()` ← `ArrayBuffer`، وأي شيء آخر ← JSON):

1. **اختيار الجانب بناءً على `ok` (`200..299`)**: استخدام `output` لحالات `2xx`، و`error` لغير `2xx`.
2. **الامتناع عن القراءة عند الإغفال**: إذا لم يُعلن عن أي بنية لذلك الجانب، فلن يُقرأ جسم الاستجابة أبداً (تُرجع حالات `2xx` القيمة `data: undefined` مع `HttpMeta`؛ وتُرجع الحالات غير `2xx` خطأ `HTTP_STATUS` مع `data: undefined`).
3. **التحقق من ترويسة نوع وسائط JSON أولاً**: بالنسبة لبنى JSON، تؤدي ترويسة `Content-Type` غير المطابقة لـ JSON إلى الفشل بخطأ `RES_MEDIA_TYPE_INVALID` قبل البدء بقراءة تدفق الجسم.
4. **القراءة والتحليل**: تفشل التدفقات غير القابلة للقراءة أو بيانات JSON غير الصالحة بخطأ `RES_DECODE_FAILED` (أو `NET_BODY_INCOMPLETE` إذا انقطع التدفق أثناء القراءة).
5. **التحقق بواسطة `struct`**: يؤدي عدم تطابق المخطط إلى الفشل بخطأ `RES_STRUCT_MISMATCH`.

## 5. إلغاء الطلبات وتعيين المهل الزمنية [#cancel-the-work]

مرّر خاصية `signal` عبر عميل مشتق مخصص لكل استدعاء: `client({ signal })`.

- **المهل الزمنية (`NET_TIMEOUT`)**: استخدم `AbortSignal.timeout(ms)`.
- **الإلغاء اليدوي (`NET_ABORTED`)**: استخدم `AbortController`.
- **دمج إشارات متعددة**: استخدم `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`.

## 6. بيانات الاعتماد، حماية XSRF، وتتبع تقدم النقل

- **`withCredentials(true)`**: يضبط خيار Fetch على `credentials: "include"` لطلبات HTTP وتدفقات أحداث SSE.
- **`withXSRF(options?)`**: يقرأ ملف تعريف ارتباط XSRF (`XSRF-TOKEN` افتراضياً) ويحقن الترويسة (`X-XSRF-TOKEN`) مع طرق HTTP المعدِّلة من نفس المصدر (`POST` و`PUT` و`PATCH` و`DELETE`).
- **`onDownloadProgress` / `onUploadProgress`**: تُمرَّر عبر `client({ onDownloadProgress, onUploadProgress })`. يُبلغ تقدم التنزيل عن `lengthComputable: true` فقط عندما تكون ترويسة `Content-Length` موجبة وتكون `Content-Encoding` غائبة أو مضبوطة على `identity`. ويتيح تقدم الرفع دفق الأجسام على بيئات تشغيل الخادم (Bun وNode.js). ويؤدي إلقاء استثناء داخل دالة رد نداء التقدم إلى فشل الاستدعاء بخطأ `EXT_OBSERVER_FAILED`.
