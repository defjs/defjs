# HTTP

يعرّف SDK طريقة كل عملية HTTP ومسارها النسبي وربط المدخل والاستجابة وعقد الخطأ. يستورد التطبيق تلك العملية، ويضبط عميله، ويستدعيها، ويعالج النتيجة. يمكن شحن التعريف نفسه في حزمة npm أو مشاركته محليًا.

أبقِ عناوين الخدمة وبيانات الاعتماد في إعداد العميل. يملك المستدعي الإلغاء وأي سياسة لإعادة محاولة الكتابة؛ وقد يكون الطلب المُلغى قد وصل إلى الخدمة أصلًا.

## حل عنوان URL

يحتاج `withEndpoint(...)` إلى عنوان URL مطلق صالح. يبقى مسار نقطة النهاية مجلدًا؛ ويُهمَل الاستعلام والـ hash قبل حل عنوان URL للطلب. نقطة النهاية الأساسية الغائبة أو النسبية أو غير الصالحة تفشل بـ `REQ_BUILD_FAILED` أثناء بناء الطلب، قبل تشغيل أي معترض أو وسيلة نقل، حتى لو كان المعترض سيُنهي الطلب مبكرًا. تشترك HTTP وSSE وWebSocket في هذه القاعدة.

<include cwd>examples/http/resolve-url.ts#example</include>

عناصر المسار النائبة قيم مفردة خام، تُرمَّز مرة واحدة بالضبط. تُرفض القيم الفارغة و`.` / `..`. تبقى الشرطة المائلة و`?` و`#` و`%` والمسافات وUnicode في عنصر نائب واحد مقطعًا مرمَّزًا واحدًا — لا تُرمّز مسبقًا.

يبدأ اسم العنصر النائب عند `:` ويمتد إلى `/` التالية أو نهاية المسار: يسمّي `/files/:name.json` المعامل `name.json`، لا `name`. النقطتان الحرفيتان في مقطع ثابت غير مدعومتين.

لا يمكن أن تكون مسارات التعريف شبيهة بمخطط أو نسبية إلى البروتوكول (بما في ذلك مع مسافات بادئة)، أو تحتوي محارف تحكم C0 (بما فيها tab وCR وLF) أو شرطات مائلة عكسية أو `?` أو `#`. يُسمح بمسافة عادية داخل المسار وتُرسَل كـ `%20`. بعد الحل، يجب أن يُبقي عنوان URL أصل الأساس ويبقى تحت مجلده؛ ومسار مثل `../orders` لا يستطيع الخروج منه. تفشل المسارات غير القانونية بـ `REQ_BUILD_FAILED` أثناء البناء، قبل النقل. يُفحص `req.endpoint` النهائي للمعترض مقابل `req.baseEndpoint` النهائي بالقاعدة نفسها؛ ويجوز للمعترض أن يستبدل الأساس عمدًا بعنوان URL مطلق صالح آخر. أخطاء URL الحتمية لا تُعاد محاولتها أبدًا.

يقبل مرمّز الاستعلام الافتراضي القيم المفردة ومصفوفات القيم المفردة (تكرر المصفوفات المفتاح). يفشل الكائن المتداخل بـ `REQ_BUILD_FAILED` إلا إذا كان لدى العميل `withQuerySerializer(...)`. يفشل `null` في `path` أو `query` أو `headers` بالطريقة نفسها. تُحذف قيم الاستعلام والرؤوس التي هي `undefined`. يفشل عنصر مسار نائب `undefined` أو غائب بـ `REQ_BUILD_FAILED`.

## ضع المدخل

يرمّز الـ struct القيمة. ويضعها الـ builder. `input` المعلَن يتطلب دائمًا `builder` صريحًا. يقتصر `input` على تعريف المعاملات؛ والـ builder وحده يقرر أين تذهب كل قيمة. يمكن حذف `builder` فقط من التعريفات التي لا تعلن `input`.

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

ذلك الجسم هو `{"customer_name":"Ada"}` مع `application/json`. اسم الرأس على السلك هو `x-request-id`. يُبقي المستدعون والنتائج المحلَّلة `customerName`.

فضّل تسليم القيمة محدَّدة النوع على تهجئة مفاتيح السلك. يُعلَن alias مرة واحدة على الحقل وينطبق في الاتجاهين: تفك `output` / `error` / الأحداث / الإطارات الواردة `customer_name` إلى `customerName`، و`body: input.order` يعيد كتابة الشجرة كاملة. يمكن أن يكون struct `Order` نفسه جسم إنشاء ومخرج جلب. المفتاح المكتوب يدويًا هو الاستثناء: الكائن الأب مجهول، فلا يعمل alias.

| تعبير الـ builder                              | على السلك                                                    |
| ---------------------------------------------- | ------------------------------------------------------------ |
| `body: input.profile`                          | كائن محدَّد النوع: ترميز alias و`Date` / `bigint`            |
| `body: { profile: input.profile }`             | المفاتيح الخارجية حرفية، والكائن الداخلي ما زال محدَّد النوع |
| `body: { ...input.profile, role: 'admin' }`    | النشر يُبقي الـ struct؛ والمفتاح الإضافي حرفي                |
| `body: { name: input.profile.customerName }`   | أب مجهول: لا ينطبق alias                                     |
| `query: input.filter` / `headers: input.trace` | كائنات مسطحة محدَّدة النوع: يصبح alias مفتاح السلك           |

نشر كائن محدَّد النوع وضبط مفتاح سلكه أيضًا (`customer_name` بجانب `customerName`) هو `REQ_BUILD_FAILED`. يفشل الكائن المتداخل في `path` أو `headers` بالطريقة نفسها.

يُختار الدليل عند كل عقدة، لا عند الجذر فقط. يُبقي كائن جديد تحت أب مجهول المفاتيح التي كتبتها. ويستخدم الكائن نفسه تحت أب محدَّد النوع struct ذلك الحقل.

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

عندما يطابق دليل اتحاد أكثر من فرع، يُرمَّز كل فرع ويُقارَن. يُحفَظ مخرج السلك المتطابق؛ والاختلاف هو `REQ_BUILD_FAILED`.

التقاطع المختلط الذي يحتوي جزءًا ليس كائنًا يُوسَم، عند التحليل، باقتران الوسوم من الأجزاء التي طابقت؛ والقيمة المكتوبة حديثًا لتقاطع مختلط لم تُحلَّل هي كائن مجهول.

### الاستعلام

شكل الاستعلام المتداخل (`a[b]` و`a.b` والقوائم المفصولة بفواصل) اصطلاح للخلفية، فالخطاف على العميل:

<include cwd>examples/http/query-serializer.ts#example</include>

`query` هنا هو كائن السلك المرمَّز. الأسماء المستعارة مطبَّقة أصلًا، فيرى المسلسِل مفاتيح السلك. تُخزَّن السلسلة المُرجَعة كـ `queryString`، ثم تُسنَد إلى `URL.search`، الذي يرمّز بالمئة المسافات و`#` وعلامات الاقتباس وغير ASCII. لا يشحن Defjs مرمّز استعلام متداخل.

دون مسلسِل، تكرر المصفوفات المفاتيح ويكون الكائن المتداخل `REQ_BUILD_FAILED`. إرجاع `URLSearchParams` من الـ builder يستخدم تلك القيمة كما هي ويتجاوز المسلسِل. لا يُستدعى المسلسِل عندما لا يوجد استعلام. ثم يرى المعترضون `queryParams` كـ `new URLSearchParams(queryString)`.

### الجسم

أول تطابق يغلب:

| قيمة `body`                                                | تُرسَل كـ                                                                   | نوع المحتوى الافتراضي                                 |
| ---------------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------- |
| محذوف / `undefined`                                        | بلا جسم                                                                     | —                                                     |
| كائن محدَّد النوع جذره له ترميز `urlencoded` أو `formData` | `URLSearchParams` / `FormData`؛ المفاتيح أسماء سلك؛ المصفوفات تكرر المفاتيح | نوع النموذج / حد المنصة                               |
| `FormData`، `URLSearchParams`                              | كما هي                                                                      | نفسه؛ يمسح Defjs `Content-Type` القديم على `FormData` |
| `Blob` / `File`                                            | كما هي                                                                      | `blob.type`، أو `application/octet-stream`            |
| `ArrayBuffer`، `TypedArray`، `DataView`                    | كما هي                                                                      | `application/octet-stream`                            |
| `ReadableStream`                                           | متدفق (`duplex: 'half'` عندما يسمح وقت التشغيل)                             | `application/octet-stream`                            |
| `string`                                                   | كما هي                                                                      | `text/plain;charset=UTF-8`                            |
| كائن عادي، مصفوفة، عدد، منطقي، `null`، `Date`، `bigint`    | مرمَّز، ثم `JSON.stringify`                                                 | `application/json`                                    |

يُبقي HTTP النوع المستنتج لجسم الـ builder في الحقل العادي `request.bodyContentType`، الذي يبقى بعد نسخ `{ ...req }`؛ وهو لا يكتب ذلك الاستنتاج أبدًا في `request.headers`. يغلب رأس `content-type` الصريح دائمًا، سواء ضبطه الـ builder أو افتراضيات العميل أو معترض أو طلب `fetchHandler` خام، بما في ذلك عندما يحوّل تقدّم الرفع الجسم إلى تدفق. ينطبق `bodyContentType` فقط ما دام `body` هو قيمة الـ builder؛ ويُكتشف الجسم البديل من جديد، فيعلن المعترض نوعه برأس `content-type`. `body: undefined` لا يرسل Content-Type مستنتجًا من المكتبة. FormData هو الاستثناء: يجب أن يستخدم نوع محتواه الحد من التسلسل الفعلي. ينطبق وسم الترميز عند جذر الجسم فقط: `body: { meta: input.form }` هو JSON، وحقول النموذج حقول JSON عادية. السلسلة نص خام؛ وسلسلة JSON مثل `"abc"` تحتاج `JSON.stringify` مع `application/json`. تُحذف حقول `undefined`؛ والحقل `nullable` المرسَل كـ `null` هو `null` في JSON.

يجب أن تكون JSON بيانات JSON حتى القاع: كائنات عادية ومصفوفات وسلاسل وأعداد محدودة وقيم منطقية و`null`، إضافة إلى القيم التي تُرجع `toJSON()` تلك، مثل `Date` أو `URL`. أي شيء آخر، في الجذر أو متداخلًا، يفشل بـ `REQ_BUILD_FAILED` قبل إرسال أي شيء، بدل أن يُرسَل كـ `{}` أو `null` أو بلا جسم أصلًا: `Map` أو `Set`، أو نسخة صنف بلا `toJSON`، أو دالة، أو `NaN`، أو `Readable` من Node، أو قابل للتكرار أو قابل للتكرار غير متزامن، بما فيه كائن حرفي له طريقة `Symbol.iterator` أو `Symbol.asyncIterator`. تسمّي الرسالة الحقل. يفشل الكائن القابل للتكرار المعطى كـ `query` أو `headers` بالطريقة نفسها بدل أن يُسقَط؛ مرّر أزواج الرؤوس كمصفوفة. أرسل تدفقًا كـ `ReadableStream` من Web: `ReadableStream.from(iterable)` أو `Readable.toWeb(readable)`. يرفض نوع `body` معظم هذه وقت الترجمة؛ وقيمة `interface` أو نسخة صنف تحتاج `{ ...value }`.

لا يستطيع `GET` و`HEAD` إرجاع جسم — ذلك خطأ نوع. لا يستطيع بناة WebSocket إرجاع `headers` أو `body`.

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

`JSON.stringify` أو `qs` أو protobuf الذي تشغّله بنفسك يرى الأسماء المنطقية. لا ينطبق alias على ذلك المسار. لا يوجد `struct.encode` عام.

يجوز للـ builder أن يتفرّع على المدخل الحقيقي ويُرجع جسمًا مختلفًا لكل حالة (سجلات JSON، أو `File`، أو `URLSearchParams`). تُمرَّر `Headers` الأصلية أيضًا ولا تُعاد ترميزها.

## كيف يُقرأ الجسم

`output` هو Struct واحد لجسم 2xx؛ و`error` هو Struct واحد لكل ما عدا ذلك. يختار نوع الـ struct
التمثيل: `string` نص خام، و`blob` / `file` كائنات blob، و`arrayBuffer` بايتات،
وكل نوع آخر JSON. عندما لا يُعلَن أي طرف، لا يُقرأ الجسم أبدًا.

ترتيب العمليات:

1. يختار `ok` الطرف: `output` لـ 2xx، و`error` لكل ما عدا ذلك. لا الاثنان معًا أبدًا.
2. لا شيء معلَن لذلك الطرف ← لا يُقرأ الجسم أبدًا. ينجح 2xx مع `data === undefined`؛
   وغير-2xx هو `HTTP_STATUS` مع `data === undefined`. يُتجاهل الجسم غير المقروء على طرف لم
   تعلنه، بما في ذلك حقيقة أنه لم يكن قابلًا للقراءة.
3. لتمثيل JSON، يُفحص نوع الوسائط **قبل** قراءة الجسم. عدم التطابق هو
   `RES_MEDIA_TYPE_INVALID` ولا يُحلَّل شيء ولا يُفك. يتجاوز النص والـ blob والملف والبايتات هذا الفحص.
4. يُقرأ التمثيل. الفشل هو `RES_DECODE_FAILED`. يُحلَّل JSON من النقل مرة واحدة:
   السلسلة على تلك القيمة جذر سلسلة JSON ولا تُحلَّل مرة أخرى؛ والبايتات والـ blobs خام
   وتُحلَّل مرة واحدة.
5. يحلّل الـ Struct القيمة. الفشل هو `RES_STRUCT_MISMATCH`.
6. 2xx ← نتيجة و`response.body` محدَّد النوع؛ وغير-2xx ← `data` محدَّد النوع على `HTTP_STATUS`.

ينفّذ نقل Fetch المدمج الخطوتين 3 و4 لطرف معلَن بينما الاستجابة ما زالت
داخل سلسلة المعترضات، فيتلقى المعترضون استجابة `body` فيها هو JSON المحلَّل أصلًا
أو النص أو `Blob` أو البايتات. يرفض فشل نوع الوسائط أو القراءة `next()` كـ `BodyFailure` قبل أن تحل السلسلة
(`RES_MEDIA_TYPE_INVALID` أو `RES_DECODE_FAILED` أو `NET_BODY_INCOMPLETE` عندما ينكسر التدفق).
تعمل الخطوة 5 مرة واحدة، بعد السلسلة. يتجاوز `makeResponse(...)` تلك القراءة داخل السلسلة. يُفك جسمه فقط
بعد السلسلة، في الخطوة نفسها مع التحقق من Struct. في تمثيل JSON، تُحلَّل سلسلة الجسم
هناك؛ والقيمة التي حلّلها النقل أصلًا لا تُحلَّل مرة أخرى.

الاستجابة الناجحة هي `DecodedResponse<T>`: `url` و`status` و`statusText` و`headers` و`ok` و
`body` محدَّد النوع. حيث لم يُفك شيء تحصل على `HttpMeta` — الحقول نفسها دون `body`. يعني `ok`
فقط `200 <= status < 300`. لا أي منهما `Response` أصلي. فشل النقل عطل، فلا
توجد استجابة بحالة 0 تنوب عنه.

## ألغِ العمل [#cancel-the-work]

مرّر `signal` على عميل مشتق. المهلة هي `AbortSignal.timeout(ms)` وتُصنَّف `NET_TIMEOUT`. يُصنَّف الإجهاض اليدوي `NET_ABORTED`. لا يوجد حقل `timeout`، ولا حقل `abort`، ولا مهلة افتراضية على مستوى العميل. `signal` هو إشارة الاستدعاء؛ اجمع الإشارات بـ `AbortSignal.any` في شيفرة التطبيق. اجمع إشارة المستدعي مع مهلة باستخدام `AbortSignal.any` في شيفرة التطبيق.

الإلغاء المتعرَّف عليه ← `NET_ABORTED`؛ وإجهاض المهلة ← `NET_TIMEOUT`؛ ورمي المعترض ← `EXT_INTERCEPTOR_FAILED`، إلا `ERR_ABORTED` / `ERR_TIMEOUT` فيعطيان `NET_ABORTED` / `NET_TIMEOUT`؛ وفشل Fetch الآخر ← `NET_UNREACHABLE`. الإلغاء بعد أن قبل الخادم كتابة **لا** يثبت أن الكتابة تراجعت.

## بيانات الاعتماد وXSRF

يضبط `withCredentials(true)` القيمة `credentials: 'include'` في Fetch لـ HTTP وSSE. وهو لا ينشئ `Authorization` ولا يضبط مصادقة WebSocket. تترك `false` بيانات الاعتماد غير محددة.

`withXSRF(...)` لـ HTTP فقط. الافتراضيات: `cookieName: 'XSRF-TOKEN'`، و`headerName: 'X-XSRF-TOKEN'`. يُحقن الرأس فقط للطرق غير الآمنة وفقط عندما لم يضبطه المستدعي أصلًا. حيثما وُجد `location`، بما في ذلك Worker، يجب أن يطابق عنوان URL المحلول للطلب `location.origin`؛ والطلب العابر للأصل لا يستدعي `tokenProvider`. بحث ملف تعريف الارتباط يتطلب `document` على حدة. يتجاوز `GET` و`HEAD` و`OPTIONS` و`TRACE`. في Worker أو خادم، مرّر `tokenProvider` متزامنًا بنطاق الطلب إذا احتجت الحقن.

أبقِ بيانات الاعتماد ورموز XSRF وسلاسل الاستعلام خارج السجلات الروتينية. لا تستخدم معامِلات الاستعلام قناة بيانات اعتماد عامة.

## التقدّم وحد Fetch

يعمل `onDownloadProgress` أثناء قراءة جسم استجابة معلَن. يعدّ `loaded` البايتات المقروءة من تدفق الاستجابة، التي قد يكون Fetch قد فك ضغطها أصلًا. `lengthComputable` صحيح فقط مع `Content-Length` موجب و`Content-Encoding` غائب أو `identity`. الترميزات الأخرى، بما فيها gzip وbr، تبلّغ `total: 0` و`lengthComputable: false`، فلا تُقارَن البايتات المفكوكة بطول سلك مضغوط أبدًا. بلا struct لذلك الطرف ← لا يُقرأ الجسم ← لا تقدّم لقراءة الجسم.

يبلّغ `onUploadProgress` عن تقدّم جسم `ReadableStream<Uint8Array>` بينما يقرأه Fetch، لا عندما يقرّ به الخادم. يُبلَّغ تقدّم الرفع فقط حيث يستطيع وقت التشغيل بث أجسام الطلب: في Bun وNode، يحوّل Defjs أيضًا أجسام `Blob` / `File` و`ArrayBuffer` و`FormData` إلى تدفق، فتبلّغ عن التقدّم أيضًا. على بيئات الخادم، يستخدم FormData مع `onUploadProgress` التدفق المسلسَل مباشرة، ويحافظ على حد multipart، ويُرسَل دون `Content-Length` تولّده المكتبة (مقطَّع على HTTP/1.1)، فيعمل التقدّم والإجهاض دون تخزين الجسم كاملًا. مجموعه غير معروف إلا إذا وفّره `Content-Length` صريح صالح. لنقطة نهاية تتطلب `Content-Length`، مثل بعض أهداف الرفع الموقَّعة مسبقًا، احذف `onUploadProgress`؛ فيرسل Fetch في المنصة FormData مع طوله. يحرر الإلغاء التدفق المغلف. تُستثنى المتصفحات، بما فيها Workers، لأن Chromium يبث جسم طلب فقط على HTTP/2 أو أحدث ولا يستطيع Firefox بثه أصلًا؛ وهناك تُرسَل تلك الأجسام دون تغيير ولا يُستدعى `onUploadProgress`. تُرسَل أجسام JSON والنص و`URLSearchParams` والمصفوفة محدَّدة النوع كاملة ولا تنتج أحداثًا. `total` هو `0` (فـ `lengthComputable` هو `false`) لتدفق بلا طول معروف. يفشل جسم `ReadableStream` على وقت تشغيل لا يستطيع بث الطلبات، مثل Firefox، بـ `ENV_UNSUPPORTED` قبل إرسال أي شيء؛ ورسالة السبب هي `ERR_STREAMING_REQUEST_UNSUPPORTED`. في Chromium، يحتاج جسم `ReadableStream` إلى HTTP/2 أو أحدث؛ وعلى HTTP/1.1 يفشل الاستدعاء بـ `NET_UNREACHABLE`. يتصرف `onDownloadProgress` بالطريقة نفسها في كل وقت تشغيل.

رد نداء التقدّم الذي يرمي أو يرفض يُفشل الاستدعاء بـ `EXT_OBSERVER_FAILED` والقيمة المرمية في `cause`، للتنزيل والرفع على السواء. يظل إلغاء المستدعي يبلّغ `NET_ABORTED`، أو `NET_TIMEOUT` عندما يكون سبب الإجهاض مهلة.

`fetchHandler(httpRequest, fetchImpl?)` هو حد Fetch الأدنى: يحل عنوان URL، ويستدعي Fetch، ويقرأ التمثيل، ويُرجع `HttpResponse`. يحل معالجا HTTP وSSE الافتراضيان `globalThis.fetch` عند كل استدعاء، فيُستخدم البديل المثبّت بعد الاستيراد. يستخدم HTTP الصيغة `(url, init)` فقط مع Fetch الأصلي للمنصة دون تعديل؛ ويتلقى العام المستبدل أو المعالج المخصص `Request` أصليًا. استيراد Core دون Fetch صالح؛ ويفشل استدعاء HTTP/SSE الافتراضي بـ `ENV_UNSUPPORTED` إذا ظل Fetch غائبًا، بينما تبقى المعالجات المخصصة قابلة للاستخدام. هذا الحد **لا** يتحقق من مدخل العملية، ولا يوزّع `output`، ولا يشغّل المعترضات. مفيد لاختبارات النقل المحقون — وليس بديلًا عن استدعاء العملية.

## حدود إعادة الإرسال

Defjs **لا** يعيد محاولة HTTP تلقائيًا. إعادة محاولة القراءة ما زالت تحتاج سياسة مهلة/شبكة/تكرار مُراجَعة. إعادة محاولة التغيير تحتاج بايتات قابلة لإعادة الإرسال، ودعم الخادم، ومفتاح تماثل مربوط بنطاق المصادقة + بايتات الطلب، وسياسة تكرار لدى المستقبل.

حد العميل أو Fetch لا يستطيع أن يعرف إن كانت الكتابة الفاشلة قد اكتملت. أبقِ قرارات إعادة الإرسال في التطبيق أو في معترض مُراجَع. يمكن للمعترضات أن تنهي المسار مبكرًا أو تستبدل الطلب منخفض المستوى؛ ويجب أن تظل الحالة النهائية والجسم مستوفيين لعقد العملية.
