# توزيع الحمل والتبديل عند الفشل

عندما يضبط تطبيق مستهلك عناوين أساسية متعددة عبر `withEndpoint(...urls)`، يمكن لـ Defjs توزيع الطلبات عبر النسخ المتماثلة، واستبعاد الخوادم غير السليمة باستخدام قواطع الدوائر السلبية أو فحوصات السلامة النشطة، والتبديل الاختياري عند الفشل لطرق HTTP الآمنة في نفس الاستدعاء.

## 1. اختيار استراتيجية موزع الحمل

| الاستراتيجية                                                                   | الأنسب لـ                                                                | تصفية السلامة الافتراضية                          |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------- |
| [`pickFirstBalancer(options?)`](/ar/api/core/pickfirstbalancer) _(الافتراضية)_ | تطبيقات المتصفح ذات القائمة المرتبة للمناطق الأساسية والاحتياطية         | معطلة (تفعيل اختياري عبر خيار `outlierDetection`) |
| [`roundRobinBalancer(options?)`](/ar/api/core/roundrobinbalancer)              | اتصالات الخادم بالخادم بين نسخ متكافئة (تدعم أوزاناً اختيارية `weights`) | مفعلة (`5` إخفاقات متتالية)                       |
| [`p2cBalancer(options?)`](/ar/api/core/p2cbalancer)                            | اتصالات الخادم حيث يتباين زمن الاستجابة أو الحمل اللحظي بين النسخ        | مفعلة (`5` إخفاقات متتالية)                       |

### كيف تعمل `pickFirstBalancer` و`p2cBalancer`

- **`pickFirstBalancer`**: يلتزم بالعنوان الأول ويتقدّم عند `NET_UNREACHABLE` أو `NET_UNAVAILABLE` (HTTP 502 أو 503 أو 504). اضبط `failbackMs: 30_000` لإعادة فحص نقطة النهاية الأساسية بعد قضاء تلك المدة على النسخة الاحتياطية.
- **`p2cBalancer` (خوارزمية القوة المزدوجة لاختيارين)**: تأخذ عينتين لمرشحين متمايزين دون إحلال وتختار المرشح ذا النتيجة الأقل: `PeakEwma RTT × (pending + 1)` (أو عدد العمليات قيد التنفيذ `pending` عندما يكون `load: "pending"`). الإعدادات الافتراضية (`defaultRttMs: 30` و`decayMs: 10000`) تتبع معايير Linkerd/tower.

## 2. إعادة محاولة HTTP في نفس الاستدعاء

تحكم إعادة المحاولة ثلاثة قرارات منفصلة: **هل تُعاد المحاولة** (`withRetry`)، و**إلى أين تُرسَل** (يطلب وقت التشغيل من الموازن أن يختار من جديد، مع استبعاد نقاط النهاية التي جُرِّبت)، و**كم يُنتظَر** (backoff). `withRetry` في HTTP و`withSSEReconnect` في SSE و`withWebSocketReconnect` في WebSocket سياسات متناظرة على مستوى النقل. تشترك حقول backoff المسطّحة في الأسماء نفسها والتحقق نفسه وحساب التأخير نفسه. لا يعرف الموازن شيئًا عن سياسة إعادة المحاولة؛ ولا يحتاج الموازن المخصص إلى تعاون خاص.

إعادة محاولة HTTP في نفس الاستدعاء **معطّلة افتراضياً**. حذف `withRetry` يعني محاولة واحدة لكل استدعاء، دون إنشاء ميزانية إعادة محاولة أو إضافة رصيد إليها. لا يتغيّر الاختيار في الاستدعاءات اللاحقة: لا يزال `pickFirstBalancer` يستطيع التقدّم بعد استدعاء فاشل. `withRetry()` يعادل `withRetry({})` ويفعّل محاولتين إجمالًا عند فشل الاتصال لـ `GET` و`HEAD` و`OPTIONS` و`TRACE`.

يتبع ذلك منظومة Go: [يضع gRPC الخيار `retryPolicy` في إعداد الخدمة](https://grpc.io/docs/guides/retry/)، إلى جانب إعداد توزيع الحمل، بينما [go-kit `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) يغلّف الموازن صراحة. لا يطبّق أيّ منهما سياسة إعادة محاولة للتطبيق افتراضياً. تتطلب سياسة إعادة المحاولة في gRPC إعدادات backoff وتستخدم تذبذبًا بمقدار ±0.2؛ [وافتراض Envoy قاعدة 25 مللي ثانية وحد أقصى عشرة أضعاف تلك القاعدة](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff). يستخدم Defjs 25 مللي ثانية، والعامل 2، وسقفًا 250 مللي ثانية، وتذبذبًا ±20%. لا يزال gRPC يستطيع تنفيذ إعادات شفافة لسباقات المستوى المنخفض؛ ولا يحاكي Defjs تلك الإعادات.

- **إجمالي المحاولات (`maxAttempts`)**: يشمل المحاولة الأصلية، بما يطابق `retryPolicy.maxAttempts` في gRPC و`max` لدى `lb.Retry` في go-kit. يجب أن تكون القيمة عددًا صحيحًا آمنًا لا يقل عن 1؛ ويعني `1` عدم إعادة المحاولة. لا يوجد حد أعلى مضبوط، لكن كل نقطة نهاية تُجرَّب مرة واحدة على الأكثر. لا تُعاد أجسام الطلب المتدفقة أبدًا. `methods` غير حساس لحالة الأحرف؛ ويعطّل `methods: []` إعادات المحاولة لكل الطرق.
- **شروط إعادة المحاولة (`on`)**: القيمة الافتراضية هي `["connect-failure"]`. أضف `"gateway-error"` من أجل `NET_UNAVAILABLE` (HTTP `502`/`503`/`504`)، بما فيها أجسام أخطاء البوابة التي رفضها فك `RES_*`، و`"attempt-timeout"` عند ضبط `attemptTimeoutMs`. تعيد المحاولة المؤهّلة بناء الطلب وتشغّل سلسلة المعترضات بأكملها من طبقتها الأبعد.
- **Backoff (`delayMs` و`factor` و`jitter` و`maxDelayMs`)**: قبل إعادة المحاولة n، الانتظار هو `delayMs × factor^(n−1)` مع تذبذب ضربي، ويُسقَف بعد التذبذب والتقريب. الافتراضيات هي `25` و`2` و`0.2` و`250`. يتخطى `delayMs: 0` الانتظار. كما في إعادة الاتصال، يجب أن يكون `delayMs` منتهيًا وغير سالب، و`factor` منتهيًا وموجبًا، و`jitter` منتهيًا ضمن `[0, 1]`، و`maxDelayMs` منتهيًا غير سالب أو `Infinity` موجبًا. ويبقى سقف مؤقت المنصة ساريًا.
- **مهلة المحاولة الواحدة مقابل مهلة الاستدعاء الكامل**: تقيّد `attemptTimeoutMs` محاولة واحدة بدءاً من استدعاء Fetch حتى فك تشفير الجسم. تغطي إشارة المستدعي `client({ signal: AbortSignal.timeout(ms) })` كل محاولة **وانتظار backoff**. الإلغاء أثناء الانتظار يُرجع خطأ إلغاء المستدعي دون اختيار آخر.
- **ميزانية إعادة المحاولة بنمط Finagle / Linkerd (`budget`)**: يملك كل إعداد عميل ميزانية، ولا يشاركها إلا العملاء المشتقون الذين يستخدمون ذلك الإعداد نفسه، لا العملاء الذين يشاركون موازنًا. الافتراضيات هي `percentCanRetry: 0.2` و`minRetriesPerSecond: 10` و`ttlMs: 10000`: 20% من الحركة الأصلية زائد الاحتياطي. تنتهي الأرصدة والخصوم كلاهما بكسل في عشر شرائح من TTL/10. تسحب إعادة المحاولة قبل الانتظار؛ والميزانية المستنفدة لا تنتظر ولا تعيد المحاولة. عيّن `budget: false` لإزالة السقف.
- **تلميح انقطاع اتصال المتصفح**: عندما تكون `navigator.onLine === false`، تُبلّغ إخفاقات الاتصال كـ `{ attempted: false }` ولا تؤدي إلى تقدّم الموازنات أو إطلاق إعادات المحاولة.

`withRetry` لاحق يستبدل السياسة. `withRetry()` و`withRetry(undefined)` يتصرفان مثل `withRetry({})`. لإيقاف إعادات المحاولة بعد تفعيلها، مرّر `withRetry({ maxAttempts: 1 })`. تُرجع إعدادات إعادة المحاولة غير الصالحة `REQ_OPTIONS_INVALID` مع `Invalid retry options` عند تشغيل عملية HTTP.

1. **الإخفاقات المتتالية**: يحصي المصنّف الافتراضي `NET_UNREACHABLE` و`NET_UNAVAILABLE` و`NET_SERVER_ERROR`. بعد حدوث `consecutiveFailures` (افتراضياً `5`) من النتائج المحصاة المتتالية، تُستبعد نقطة النهاية لمدة `min(minPenaltyMs × 2^level, maxPenaltyMs)` (من `1000ms` إلى `60000ms`) بالإضافة إلى تذبذب إيجابي منتظم يصل إلى `50%`.
2. **التعافي بفحص مفرد**: بمجرد انتهاء مدة العقوبة، يُرسل طلب استكشافي وحيد إلى الخادم. فإذا بدأت استجابة الطرف المقابل (`end`) دون إخفاق محصي، تُستأنف حركة المرور العادية فوراً ويُعاد ضبط مستوى العقوبة إلى `0`؛ أما إذا فشلت، فتتضاعف مدة العقوبة.
3. **وضع الطوارئ (Fail-Open)**: إذا تم استبعاد جميع نقاط النهاية المهيأة أو تصنيفها كغير سليمة، ينتقل موزع الحمل إلى وضع الطوارئ ويفتح المرور لقائمة المرشحين بدلاً من إسقاط كافة الطلبات محلياً.

## 4. دورة حياة محاسبة وسيلة النقل (`pick` ← `start` ← `end` ← `done`)

تُنفّذ موزعات الحمل المخصصة الاختيار التزامني `pick(info)` ودوال رد النداء الاختيارية `start()` و`end(info)` و`done(info)`. لا يحتوي `PickInfo` إلا على `endpoints` المرشحة و`operation` الاختياري للتعريف؛ وليس فيه مميّز للنقل. تترجم وسيلة النقل وقائعها إلى نتائج محايدة في `DoneInfo.code`. لا تقرأ الموازنات المدمجة `status` أبدًا؛ وتُحفظ معلومات الاستجابة الخام هذه لموزعات الحمل المخصصة فقط. يعمل `start` قبل المحاولة، و`end` عندما تبدأ استجابة الطرف المقابل أو يقع إخفاق قبل الاستجابة، و`done` عند الاكتمال. لذلك يمكن لإخفاق لاحق في الجسم أن يغيّر الرمز النهائي دون أن يغيّر عيّنة `end` السابقة:

| النتيجة الفيزيائية لوسيلة النقل                                                  | العينة النهائية المسلمة لـ `done(info)`                    |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| حالة استجابة HTTP/SSE هي 502 أو 503 أو 504                                       | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| حالة استجابة HTTP/SSE أخرى لا تقل عن 500                                         | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| حالة استجابة HTTP/SSE هي 2xx أو 3xx أو 4xx (بما فيها 429)                        | `{ attempted: true, status }`                              |
| انقطاع جسم استجابة HTTP في منتصف التدفق                                          | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| نجاح مصافحة SSE ثم رفض قراءة `reader.read()`                                     | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| نهاية ملف طبيعية في SSE، أو فشل فك التشفير بعد مصافحة ناجحة، أو تجاوز حد القائمة | `{ attempted: true, status }`                              |
| إغلاق WebSocket مفتوح برمز `1006` أو `wasClean === false`                        | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| إغلاق WebSocket مفتوح بشكل نظيف                                                  | `{ attempted: true }`                                      |
| إلغاء من قِبل المستدعي أو إغلاق يدوي للتدفق/المقبس                               | `{ attempted: false }`                                     |
| انتهاء مهلة المستدعي بعد بدء المحاولة                                            | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

تحتفظ إخفاقات فك تشفير المصافحة بالنتيجة المحايدة المشتقة من حالة المصافحة (على سبيل المثال `NET_UNAVAILABLE` مع الحالة `503`). أما جسم HTTP غير المكتمل فيحتفظ بدلًا من ذلك بـ `NET_BODY_INCOMPLETE` وحالته الخام، حتى لاستجابة بوابة؛ ولا تحصيه outlier detection الافتراضية.
