# معمارية النواة

تتمحور بنية Defjs حول حد فاصل وجوهري: **تعرّف حزمة SDK العقد السلكي؛ بينما يملك التطبيق المستهلك التنفيذ.** وكل قاعدة تصميمية في `@defjs/core` تنبثق مباشرة من هذا المبدأ.

## 1. التعريف مقابل التنفيذ

تصدّر حزمة SDK العمليات البرمجية (`defineRequest` و`defineEventStream` و`defineWebSocket`) وعقود البيانات (`struct`). وهي لا تستدعي أبداً `createClient`، ولا تحتفظ بعميل عام وحيد (singleton)، ولا تقرأ متغيرات البيئة.

نظراً لأن العملية `getOrder` لا تلتقط أي حالة عميل:

- يمكن لواجهة متصفح، ومهمة خلفية مجدولة، ومعالج طلبات SSR، واختبار وحدة، استدعاء نفس تعريف `getOrder` تماماً بإعدادات `Client` متباينة تناسب كل بيئة.
- ترتبط إضافات أطر العمل (`@defjs/react` و`@defjs/vue`) وإضافة البرمجيات الوسيطة للمراقبة والقياس (`@defjs/opentelemetry-server`) بـ `Client` التطبيق المستهلك مباشرة، مما يحافظ على حزمة SDK المنشورة خالية 100% من أي اعتماديات خارجية.

## 2. موضع المدخلات الصريح والأسماء البديلة ثنائية الاتجاه

في Defjs، يعلن `input` عما يمرره المستدعي، ويتحكم `struct` في كيفية ترميز وفك ترميز القيم، وتضع دالة `builder` كل قيمة في موضعها الصحيح من الطلب (`path`، و`query`، و`headers`، و`body`).

- **لا استنتاج تلقائي**: إذا أعلنت العملية عن `input`، يجب عليها تقديم دالة `builder` صريحة وتزامنية ونقية. ولا يتم أبداً تخمين موضع الحقل في الطلب بناءً على اسمه.
- **أسماء بديلة ثنائية الاتجاه عبر `.alias(wireName)`**: يتيح الإعلان عن `.alias("customer_name")` في حقل المخطط الإبقاء على اسم `customerName` داخل TypeScript مع التحويل التلقائي من وإلى `"customer_name"` عبر الشبكة.

عندما تمرر دالة `builder` كائن struct ذي نوع محدد إلى `body` أو `query` أو `headers`، تُطبّق الأسماء البديلة للحقول ومحولات `Date` و`bigint` تلقائياً. أما المفاتيح التي تكتبها في كائن مجهول يدوياً (مثل `account_id` أو `x-api-version` أعلاه) فتبقى حرفية كما هي.

## 3. الإعلان توكيد [#declaration-is-an-assertion]

تحكم ست قواعد صارمة كيفية قراءة Defjs لاستجابات HTTP:

### القاعدة 1: ما تعلنه هو ما تؤكده بدقة

يؤكد `output` شكل جسم الاستجابة لحالات النجاح `2xx`. ويؤكد `error` شكل جسم الاستجابة للحالات غير `2xx`. الإعلان هنا ضمانة قطعية وقت التشغيل وليس مجرد تلميح تقريبي.

### القاعدة 2: النجاح `ok` (`200..299`) هو المفترق الوحيد

تُفك استجابة `2xx` حصراً باستخدام `output`. وتُفك أي حالة أخرى (`3xx` أو `4xx` أو `5xx`) حصراً باستخدام `error`. ولا يتراجع Defjs أبداً من أحدهما إلى الآخر.

### القاعدة 3: أي انحراف عن التأكيد المعلن ينتج عنه خطأ صريح

يختار Defjs جانب الاستجابة باستخدام `response.ok`: `output` لحالات `2xx`، و`error` لما ليس `2xx`. لا يطلق فك الترميز إلا struct من JSON مُعلن على ذلك الجانب، ويمكن أن ينتج `RES_MEDIA_TYPE_INVALID` أو `RES_DECODE_FAILED`؛ ويُتحقق من `Content-Type` الخاص به **أولًا**، قبل قراءة الجسم أو البحث عنه. الاستجابة بلا محتوى (`HEAD` أو `204` أو `205` أو `304`) تخضع للفحص نفسه: تمثيل JSON معلَن بلا `Content-Type` من JSON يفشل بـ `RES_MEDIA_TYPE_INVALID`، ومعه يحلّل البايتات الفارغة ويفشل بـ `RES_DECODE_FAILED`. لا تنتج صفحة HTML من البوابة ليست `2xx` الخطأ `RES_MEDIA_TYPE_INVALID` إلا عند إعلان struct من JSON لـ `error`. دون إعلان للجانب النشط لا يُقرأ الجسم؛ وتُرجع استجابة ليست `2xx` حالة `HTTP_STATUS` غير مفكوكة. تتبع مصافحة SSE القواعد نفسها: المصافحة غير `2xx` التي يتعذّر فك جسم `error` المعلَن فيها تُرجع خطأ الفك ذلك عند البدء، والحالة في بياناته الوصفية، بينما ما زال المعترضون وسياسات إعادة الاتصال و`closed` لإعادة الاتصال يرون `HTTP_STATUS`.

| سبب الفشل أثناء قراءة الاستجابة                | الخطأ المُرجع (Fault)                                                                               |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| ترويسة Media type لا تطابق تمثيل JSON المعلن   | `RES_MEDIA_TYPE_INVALID` (يُفحص أولًا؛ لا يُقرأ الجسم أبدًا، ووجود المحتوى أو غيابه لا يغيّر شيئًا) |
| تعذر فك ترميز البايتات بالتمثيل المعلن         | `RES_DECODE_FAILED` (بما فيها بايتات JSON الفارغة)                                                  |
| القيمة المفكوكة لا تطابق مخطط `struct`         | `RES_STRUCT_MISMATCH`                                                                               |
| حالة غير `2xx` مع فك ترميز كائن `error` المعلن | `HTTP_STATUS` مع بيانات `error.data` محددة الأنواع                                                  |
| حالة غير `2xx` دون الإعلان عن `error`          | `HTTP_STATUS` مع `error.data: undefined`                                                            |

### القاعدة 4: فك الترميز الفاشل ليس له جسم استجابة

لا يتوفر جسم الاستجابة إلا بعد اجتياز فك الترميز والتحقق بنجاح. وعند فشل فك الترميز، يكون نوع كائن `response` في الخطأ هو `HttpMeta` (الذي لا يحتوي على خاصية `body`)، ويُرفق خطأ المحلل/التحقق داخل `fault.cause`.

### القاعدة 5: إغفال أحد الجانبين يعني الامتناع عن قراءته

إغفال `output` يعني عدم قراءة أجسام استجابات `2xx` مطلقاً. وإغفال `error` يعني عدم قراءة أجسام الاستجابات غير `2xx` مطلقاً — حتى لو أرسل الخادم استجابة JSON غير صالحة مع رمز الحالة `500`.

### القاعدة 6: الحالة `3xx` ليست حالة نجاح

يعني `ok` حصراً: `200 <= status < 300`. وتُعد استجابة `304 Not Modified` حالة غير `2xx`: اترك `error` غير معلن وتعامل مع خطأ `HTTP_STATUS` (راجع [طلبات ETag الشرطية](/ar/recipes/etag-revalidate))، أو أعلن عن `struct.string()` إذا كنت تتوقع نصاً فارغاً.

## 4. مصفوفات نتائج مخصصة لكل وسيلة نقل

تُرجع جميع وسائل النقل الثلاث مصفوفة الخطأ أولاً بدلاً من إلقاء استثناءات (exceptions) في مكان الاستدعاء:

- **HTTP** ← `[error, data, response]` — الحمولة المفكوكة + `DecodedResponse<T>` (`HttpMeta` عند إغفال `output`).
- **SSE** ← `[error, stream, open]` — مقبض `EventStreamHandle` + لقطة مصافحة الاتصال الأولية.
- **WebSocket** ← `[error, session, connection]` — جلسة `WebSocketSession` + لقطة الاتصال الأولية.

تحمل كائنات Client الإعدادات ولا تحمل اتصالات نشطة. فالمستدعي الذي يبدأ طلب HTTP أو تدفق SSE أو جلسة WebSocket هو المسؤول عن إلغائها أو إغلاقها (`AbortSignal` لـ HTTP، و`await using` أو `.close()` مع `await .closed` لـ SSE وWebSocket).
