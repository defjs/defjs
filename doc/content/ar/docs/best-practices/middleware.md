## مسؤولية واحدة لكل معترض [#one-concern]

أعطِ كل معترض مهمة واحدة: إرفاق المصادقة، أو إضافة رأس تتبع، أو تسجيل التوقيت، أو إنهاء مسار حالة مسموح بها مبكرًا. فالوسيط الذي يصادق ويعيد كتابة الجسم ويعيد المحاولة ويسجّل يصعب اختباره ويصعب التفكير فيه.

فضّل:

```ts
const auth = createHttpInterceptor(async (request, next) => {
  const response = await next(request);
  return response;
});
```

وتجنّب معترضًا واحدًا يغيّر عدة أجزاء غير مترابطة في الطلب.

## الترتيب سياسة [#order]

تعمل المعترضات بترتيب التسجيل. أول معترض مسجَّل هو الأبعد: يرى الطلب أولًا والاستجابة أخيرًا. ضع السياسة التي يجب أن تلتف حول المحاولة كاملة في الأبعد، والسياسة التي يجب أن تكون أقرب إلى وسيلة النقل في الأقرب.

```ts
const client = createClient(
  withEndpoint("https://api.example.com"),
  withInterceptors(trace, auth),
);
```

يلفّ `trace` المعترض `auth`؛ ويعمل `auth` قبل وسيلة النقل.

## أنهِ المسار عمدًا [#short-circuit]

يجوز للمعترض أن يُرجع استجابة بـ `makeResponse` دون استدعاء `next`. استخدم ذلك لذاكرة مؤقتة مُعتمدة، أو استجابة صيانة، أو اختبار محلي. يجب أن تستوفي الاستجابة ما زال المخرج المعلَن للعملية؛ فلا تحوّل فشلًا إلى نجاح.

## لا تُعد كتابة العقد [#contract]

يجوز للوسيط ضبط الرؤوس أو سياق التتبع أو عنوان URL للطلب ضمن قواعد التحقق في المكتبة. ولا يجوز له تغيير معنى المدخل أو المخرج المعلَن. المصادقة والتتبع ينتميان إلى هنا، لا إلى `builder`.

## أبقِه عديم الحالة [#stateless]

لا تخزّن بيانات خاصة بكل طلب على عميل أو وحدة مشتركة. مرّر القيمة عبر الطلب أو إعداد العميل أو إغلاق أُنشئ لذلك العميل. فالوسيط الذي يغيّر حالة مشتركة يتسرّب بين الاستدعاءات المتزامنة.

## تعامل مع الإخفاقات عند الحد [#failures]

رمي الوسيط إخفاق؛ أرجِع استجابة فقط عندما يتعامل الوسيط مع الطلب عمدًا. لا تلتقط عطلًا لمجرد تسجيله ثم المتابعة بـ `undefined`. استخدم خطاف القياس عن بُعد في التطبيق أو المعترض للتسجيل، وأبقِ التعريف خاليًا من كليهما.
