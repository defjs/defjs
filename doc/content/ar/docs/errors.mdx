# الأخطاء

تعامَل مع 404 أو مهلة أو جسم غير مقروء بقراءة الـ tuple الذي يضع الخطأ أولًا، لا بالتقاط ما يُرمى. `Fault` هو `Error` أصلي (`instanceof Error` صحيح) ويُميَّز بحقل واحد: `code`.

لا يوجد `kind`. فصنف الفشل هو المقطع الذي يسبق أول `_` في رمزه، فـ `NET_TIMEOUT` فشلٌ من صنف `NET` و`RES_STRUCT_MISMATCH` فشلٌ من صنف `RES`. اقرأ البادئة للفرز التقريبي، والرمز كاملًا للحالة الدقيقة.

## رموز مستقرة

| الصنف  | الرموز                                                                 | من الذي يجب أن يتغيّر                             |
| ------ | ---------------------------------------------------------------------- | ------------------------------------------------- |
| `HTTP` | `HTTP_STATUS`                                                          | الطرف المقابل أجاب بغير 2xx؛ تعامَل معه كمنطق عمل |
| `REQ`  | `REQ_INPUT_INVALID`، `REQ_OPTIONS_INVALID`، `REQ_BUILD_FAILED`         | الاستدعاء أو إعلان نقطة النهاية                   |
| `NET`  | `NET_ABORTED`، `NET_TIMEOUT`، `NET_UNREACHABLE`، `NET_BODY_INCOMPLETE` | لا أحد، أو إعادة المحاولة                         |
| `RES`  | `RES_MEDIA_TYPE_INVALID`، `RES_DECODE_FAILED`، `RES_STRUCT_MISMATCH`   | يجب التوفيق بين الإعلان والطرف المقابل            |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`، `EXT_HOOK_FAILED`، `EXT_OBSERVER_FAILED`     | الشيفرة التي وصلتها بخط المعالجة                  |
| `CAP`  | `CAP_BUFFER_EXCEEDED`، `CAP_QUEUE_OVERFLOW`                            | حدٌّ معلَن، أو وتيرة المستهلك                     |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | بيئة التشغيل المضيفة                              |

المجموعة مغلقة عن قصد: وهذا بالضبط ما يجعل `switch` شاملًا لكل الحالات. والإضافات تُبلِّغ عن تفصيلها الخاص عبر `cause`، لا عبر رمز جديد.

تتطلب HTTP وSSE وWebSocket `endpoint` مطلقًا صالحًا للعميل. بعد حل URL، يجب أن يبقى المسار ضمن أصل نقطة النهاية الأساسية ومجلدها. تُرفض عناوين URL المطلقة والمسارات النسبية للبروتوكول ومحارف التحكم C0 (بما فيها tab وCR وLF) والشرطات المائلة العكسية و`?` و`#` والخروج من المجلد. تُرفض الأشكال الشبيهة بـ scheme والنسبية إلى البروتوكول حتى مع مسافات بادئة؛ ويُسمح بمسافة عادية داخل المسار وتُرسَل كـ `%20`. تنتج نقاط النهاية الغائبة أو النسبية أو غير الصالحة والمسارات غير القانونية `REQ_BUILD_FAILED` أثناء بناء الطلب، قبل تشغيل المعترضات؛ ولا يستطيع معترض يُنهي السلسلة مبكرًا تجاوز هذا الفحص. قبل النقل، يُفحص `req.endpoint` النهائي للمعترض مقابل `req.baseEndpoint` النهائي بالقواعد نفسها؛ ويُسمح بالانتقال الصريح إلى أساس مطلق صالح آخر. لا تُعاد محاولة أخطاء URL الحتمية هذه.

### الحقول بحسب الشكل

| الرمز         | `status` | `response`                                                | `data`                              |
| ------------- | -------- | --------------------------------------------------------- | ----------------------------------- |
| `HTTP_STATUS` | دائمًا   | دائمًا؛ ولا يحمل `body` إلا إذا أُعلن `error` وفُكّ بنجاح | جسم `error` المفكوك، أو `undefined` |
| `RES_*`       | دائمًا   | دائمًا، بيانات وصفية فقط — **بلا `body`**                 | غائب                                |
| كل ما عدا ذلك | غائب     | فقط حيث كانت لدى طبقة النقل بيانات وصفية بالفعل           | غائب                                |

`cause` يحمل القيمة الأساسية: `StructError` عند عدم مطابقة struct، وفشل المحلِّل عند تمثيل غير مقروء، وأيّ شيء رمته إضافة.

عند فشل HTTP يكون العنصر الثالث `undefined`: فالخطأ يحمل أصلًا ما وُجد من بيانات الاستجابة الوصفية. وهذا مهم لأن الخطأ هو ما تمرّره إلى معالِج، أو تسجّله، أو ترميه من جديد، فوجب أن تسافر البيانات الوصفية _معه_ لا بجانبه.

في SSE و WebSocket يكون العنصر الثالث لقطةَ بدءٍ قد تكون موجودة حتى عند فشل البدء. وبعد أن يعود المِقبض أو الجلسة، تعيش حالات الفشل اللاحقة على دورة حياته — ولا تُعيد كتابة tuple البدء الذي استقر.

## كيف يُقرأ الجسم

`ok` هو نقطة التفرّع الوحيدة، ولا يُفكّ إلا طرف واحد. `output` يقرأ جسم 2xx؛ و`error` يقرأ كل ما عداه. وحذف أحدهما يعني أن ذلك الجسم لا يُقرأ أبدًا.

| الحالة                                    | النتيجة                                                |
| ----------------------------------------- | ------------------------------------------------------ |
| 2xx، و`output` معلَن، والجسم يُفكّ        | نجاح؛ `data` و`response.body` محدَّدا النوع            |
| 2xx، و`output` محذوف                      | نجاح؛ `data` هو `undefined`، والاستجابة بلا `body`     |
| غير-2xx، و`error` معلَن، والجسم يُفكّ     | `HTTP_STATUS` مع `data` محدَّد النوع                   |
| غير-2xx، و`error` محذوف                   | `HTTP_STATUS` مع `data: undefined`                     |
| نوع الوسائط ليس ما يحتاجه التمثيل         | `RES_MEDIA_TYPE_INVALID`، ويُبلَّغ **قبل** قراءة الجسم |
| البايتات ليست ذلك التمثيل                 | `RES_DECODE_FAILED`                                    |
| القيمة ليست ذلك الـ struct                | `RES_STRUCT_MISMATCH` (HTTP فقط)                       |
| جسم غير مقروء في الطرف الذي **لم** تُعلنه | يُهمَل كليًّا — انظر أدناه                             |

السطر الأخير هو ما يستحق التذكّر. فإن أعلنت `output` ولم تُعلن `error`، فإن استجابة 500 بجسم JSON تالف تُبلَّغ كـ `HTTP_STATUS` مع `status: 500`. لقد قلت إن أجسام الأخطاء لا تهمّك، وهذا يشمل ألّا يهمّك أن أحدها لم يكن قابلًا للقراءة.

في HTTP، يُطبَّق الـ Struct مرة واحدة، بعد سلسلة المعترضات. والاستجابة التي بناها معترض بـ `makeResponse(...)` تمرّ بنفس فحص نوع الوسائط ونفس تحويل التمثيل ونفس الـ Struct كأي استجابة من الشبكة. يقرأ نقل Fetch المدمج الجسم المعلَن كـ JSON أو نص أو `Blob` أو بايتات قبل إعادة الاستجابة إلى السلسلة. تمثيلات JSON وحدها تتطلب نوع وسائط JSON و`JSON.parse`؛ أما النص والـ blobs والبايتات غير JSON فصالحة لتمثيلها المعلَن. ينطبق فشل القراءة على جميع التمثيلات؛ ويظهر فشل القراءة أو التحليل هناك كالـ fault نفسه من فئة `RES_*` أو `NET_BODY_INCOMPLETE`.

`HttpResponse.ok` يعني فقط `200 <= status < 300`. وفشل النقل خطأ لا استجابة أبدًا — فلا توجد استجابة بحالة صفر تنوب عنه.

## تضييق اتحاد أجسام الأخطاء

`error` واحد يغطي كل الحالات غير-2xx، فعندما تختلف الأشكال تُعلن اتحادًا. وما تستطيع فعله بـ `fault.data` بعد ذلك يتوقف كليًّا على كيفية إعلانك لذلك الاتحاد — فالمكتبة تُعيد لك بالضبط النوع الذي طلبته.

`struct.or(...)` ينتج اتحادًا عاديًا لا يستطيع TypeScript تضييقه وحده. فاختبر الحقل الذي تحتاجه:

</include>

وحين تضع الـ API الحالة **داخل** الجسم، مَيِّز عبرها بدل `fault.status`:

  examples/errors/narrow-by-status.ts#example
</include>

تستحق هذه الصورة الأخيرة التفضيل حيث تدعمها الـ API. فـ `fault.status` رقمٌ في طبقة HTTP يستطيع وكيل أو بوابة أو CDN إعادة كتابته؛ أما `data.status` فقد اجتاز تحقق الـ struct المعلَن لـ `error`. هذا يثبت شكل الجسم، لا أن مصدره الخادم الخلفي: فقد يعيد وكيل أو بوابة أو CDN جسمًا مطابقًا أيضًا.

والاتحاد غير المُميَّز الذي لا يمكن تضييقه صفةٌ في الإعلان لا في المكتبة — فهي تعطيك النوع الذي أعلنته. أضِف حقلًا مميِّزًا إلى الـ struct إن أردت تضييقًا.

## البدء مقابل ما بعد الفتح

يتحقّق SSE من الحالة ومن `text/event-stream` ومن وجود جسم قبل أن يستقرّ المِقبض. غير-2xx → `HTTP_STATUS` عندما يُحذف `error` أو يُفك جسمه بنجاح. جسم مصافحة معلَن لا يمكن قراءته أو تحليله، أو يفشل في الـ Struct، ينتج `RES_DECODE_FAILED`؛ ويحمل فشل Struct `StructError` في `cause`. نوع وسائط خاطئ ← `RES_MEDIA_TYPE_INVALID`. مصافحة ناجحة بلا جسم ← `RES_DECODE_FAILED`. ومع ذلك قد تحلّ لقطة الفتح في العنصر الثالث من الصفيف.

بدء WebSocket يغطي المصافحة مع أول فتح فيزيائي. وفشل المُنشئ، أو الإغلاق قبل الفتح، أو المهلة، أو الإلغاء، تنتج كلها tuple بدء. وقد توجد لقطة اتصال حتى لو لم يصل المقبس إلى `open` أبدًا.

| النقل     | بعد البدء                                                                                                                                                                  |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE       | يرفض المُكرِّر عند خطأ قاتل؛ ويستقرّ `stream.closed` بـ `kind: 'error'` ورمز الخطأ `code`                                                                                  |
| WebSocket | `onRuntimeError` لفشل الرسائل/الطابور/النبض؛ ويفشل `receive` عند الأخطاء النهائية؛ و`session.closed` يستقرّ بقيمة تتضمن: `kind: 'closed' \| 'aborted' \| 'error'`          |
| HTTP      | يستقرّ وعد التنفيذ مرة واحدة بالنتيجة الثلاثية. وإذا رمى المعترض أو ردّ نداء التقدّم استثناءً، يُدرَج خطأ في هذه النتيجة (`EXT_INTERCEPTOR_FAILED`، `EXT_OBSERVER_FAILED`) |

`NET_ABORTED` / `NET_TIMEOUT` تصف ما رآه المستدعي عند البدء. ومع ذلك تُغلق أي مجرى أو جلسة عادت إليك وتنتظر وعدها النهائي.

## تسجيل Error الأصلي و cause

الأخطاء هنا نسخ من `Error` الأصلي، فلا حاجة إلى مُهايئ تشخيص. و`String(fault)` يعطي الصورة الأصلية المستقرّة `DefjsFault: <message>`. و`code` وحقول كل صيغة — `status` و`response` و`data` — تبقى قابلة للتعداد من أجل التسجيل المهيكل؛ أما `name` وسلسلة `cause` الأصلية فغير قابلة للتعداد.

<include cwd lang="typescript">
  examples/errors/log-fault.ts#example
</include>

ضيِّق `fault.cause instanceof StructError` قبل استدعاء `format()` أو `flatten()` أو `prettify()`. فهذه الدوال تعيش على cause الخاص بـ Struct ولا تُنسخ إلى الخطأ. ولا تجعل مسار التحكم يحلّل `message` أو `String(fault)` — فالعقد هو `code` و`status` مُراجَع.

تذكر رسائل Struct الافتراضية نوع القيمة المستلَمة، ولا تذكر قيمتها أبدًا: `Expected number at email, received string`. تظهر الرسالة نفسها في `prettify()` و`String(fault)`. في `RES_DECODE_FAILED` الناتج عن JSON `SyntaxError`، تكون رسالة الخطأ `Response body could not be decoded`؛ ويبقى خطأ المحلّل الأصلي في `cause`. تظل قيم `StructIssue.received` الخام وأسباب أخطاء المحلّل حساسة، وتُستخدم رسالة `errorMap` المخصصة كما هي، لذا راجع النص المخصص قبل تسجيله.

## مرجع

| الفرع                   | فحص مسار التحكم                    | حقول مستقرّة مفيدة                         | غالبًا غائب / حسّاس                |
| ----------------------- | ---------------------------------- | ------------------------------------------ | ---------------------------------- |
| سياسة حالة HTTP         | `fault.code === 'HTTP_STATUS'`     | `fault.status`، و`fault.data` مُراجَعًا    | الجسم، الترويسات، الـ URL، `cause` |
| إلغاء من المستدعي       | `fault.code === 'NET_ABORTED'`     | `code`                                     | سبب الإلغاء والمكدّس               |
| مهلة                    | `fault.code === 'NET_TIMEOUT'`     | `code`                                     | عنوان الطلب والسبب الأساسي         |
| انكسر العقد             | `fault.code.startsWith('RES_')`    | `code`، و`fault.response.status` مُراجَعًا | مشكلات Struct، الجسم، قيم الدخل    |
| شيفرتك أنت رمت          | `fault.code.startsWith('EXT_')`    | `code`، `cause`                            | أيّ شيء أرفقته الإضافة             |
| زمن تشغيل المجرى/الجلسة | `stream.closed` / `session.closed` | `kind` و`code` النهائيان                   | حمولات الأحداث، الأُطُر، الأسباب   |

اعتبر `cause` و`data` وترويسات الاستجابة وأجسامها وعناوين URL و`StructIssue.received` وقيم الدخل والرسائل المخصصة والمكادس معلوماتٍ حسّاسة. مسارات المشكلة بنيوية وتحتفظ بمفاتيح record: يمكن أن ينتج `struct.record(...)` الرسالة `Expected number at alice@example.com, received string`، لذا قد تظل المفاتيح حساسة في الرسائل الافتراضية و`prettify()` و`String(fault)`. تحذف رسائل Struct الافتراضية و`prettify()` القيم المستلَمة؛ لكن تسجيل المشكلة كاملةً أو سبب خطأ محلّل JSON قد يكشفها. وهذا ملخّص محافظ:

<include cwd lang="typescript">
  examples/errors/summarize-fault.ts#example
</include>

`createNetworkFault` و`createPreflightFault` و`createDecodeFault` و`createHttpStatusFault` و`createUndecodedHttpStatusFault` تبني قيم Error الأصلية هذه. وحالات فشل الطلب العادية تُعاد كما هي في الصفيف؛ ولا تُرمى لمجرد أنها ترث سلوك Error الأصلي. و`ERR_ABORTED` و`ERR_TIMEOUT` هما السببان المشتركان اللذان يتعرّف عليهما مُطبِّع النقل. يحملان علامتي `Symbol.for('defjs.cause.aborted')` و`Symbol.for('defjs.cause.timeout')` غير القابلتين للتعداد، فيعمل تصنيف الإلغاء عبر نسخ Core المختلفة دون الاعتماد على تطابق هوية الكائن. تتيح [`isAbortCause`](/ar/api/core/isabortcause) و[`isTimeoutCause`](/ar/api/core/istimeoutcause) هذه الفحوص وفحوص أخطاء المنصة المدعومة؛ مرّر `fault.cause` الأساسي عند تصنيف سبب الخطأ. يمنع OpenTelemetry سجلات إلغاء المستدعي عبر النسخ المختلفة، ويواصل تسجيل المهل.
