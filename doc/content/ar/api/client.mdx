# العميل

أنشئ عميلًا، ركّب الخيارات من اليسار إلى اليمين، ثم `execute` أوامر HTTP / SSE / WebSocket.

## createClient()

```ts
function createClient(...options: ClientOption[]): Client
```

تُطبَّق الخيارات بالترتيب. يُفضَّل إنشاء العميل ضمن نطاق كل طلب عندما تحتفظ المعترضات ببيانات المصادقة أو المستأجرين في إغلاقاتها (closures).

- **options** — مساعدات خيارات مثل `withEndpoint`.
- **يُرجع** عميلًا تكون لدالة `execute` فيه صيغ استدعاء متعددة حسب وسيلة النقل.

## مساعدات الخيارات

كل المساعدات تُرجع `ClientOption`. استدعاء لاحق يستبدل سابقه لنفس الإعداد، باستثناء `withInterceptors` الذي يُلحق.

### withEndpoint()

```ts
function withEndpoint(endpoint: string): ClientOption
```

يعيّن URL الأساس الذي يُلحق أمام المسارات النسبية.

### withInterceptors()

```ts
function withInterceptors(...interceptors: Interceptor[]): ClientOption
```

يُلحق المعترضات بترتيب التسجيل. الأنواع المختلطة تُصفّى حسب وسيلة النقل عند التنفيذ.

### withQuerySerializer()

```ts
function withQuerySerializer(serializer: QuerySerializer): ClientOption
```

يستبدل ترميز الاستعلام لـ HTTP وSSE وWebSocket. `serializer(query)` يستقبل **الكائن المرمَّز بصيغة النقل** (الأسماء المستعارة مُطبَّقة، و`Date` بصيغة ISO، و`bigint` كسلسلة) ويجب أن يُرجع سلسلة الاستعلام دون `?` بادئة. لا يُستدعى عندما لا يملك الطلب استعلامًا. الـ `builder` الذي يُرجع `URLSearchParams` يتخطاه.

### withHeaders()

```ts
function withHeaders(headers: HeadersInit): ClientOption
```

يعيّن رؤوسًا افتراضية ثابتة لطلبات HTTP وSSE. لا تستخدمها طلبات WebSocket. تُنسخ قيمة `HeadersInit` عند تطبيق الخيار، فلا تصل التغييرات اللاحقة على الكائن إلى العميل. استدعاء `withHeaders` ثانٍ يستبدل الأول ولا يدمج معه.

الأسبقية لطلب واحد:

1. الرؤوس الافتراضية هي مجموعة الرؤوس الابتدائية.
2. الرؤوس `headers` التي يُرجعها `builder` الطلب تستبدل الرأس الافتراضي ذا الاسم نفسه عندما تكون القيمة قيمة مفردة (scalar) أو نسخة `Headers`. أما القيمة المصفوفة (مدخل في سجل مثل `{ 'x-a': ['one', 'two'] }`، أو `HeadersInit` على شكل مصفوفة أزواج) فتُلحق بالرأس الافتراضي بدل أن تستبدله.
3. تستقبل المعترضات الرؤوس المدموجة ويجوز لها تغييرها.
4. مع نقل HTTP الافتراضي، يُضاف رأس XSRF أخيرًا، وفقط إذا كان لا يزال غائبًا (انظر `withXSRF`).

استخدم معترضًا للقيم التي تتغير من طلب لآخر: رمز Bearer مُجدَّد، أو HMAC على الجسم المُسلسَل.

### withTimeout()

```ts
function withTimeout(ms: number): ClientOption
```

يعيّن المهلة الافتراضية، بالمللي ثانية، لـ `execute` في **HTTP** فقط. يتجاهلها SSE وWebSocket؛ فـ `timeout` في execute لديهما مهلة بدء مستقلة لكل استدعاء. يجب أن تكون `ms` عددًا صحيحًا آمنًا موجبًا لا يتجاوز `2_147_483_647`، وإلا رمى `withTimeout` الخطأ `RangeError` عند استدعائه. استدعاء `withTimeout` ثانٍ يستبدل الأول.

يشمل الموعد النهائي تحليل المدخل، والـ `builder`، والمعترضات، ووسيلة النقل، وقراءة الجسم المصرَّح به. ويتحد مع خيارات execute في كل استدعاء:

| خيارات execute              | الأثر                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| لا شيء                      | تُطبَّق القيمة الافتراضية للعميل؛ والانتهاء هو `NET_TIMEOUT`.                             |
| `{ timeout }`               | تستبدل القيمة الافتراضية للعميل في هذا الاستدعاء.                                         |
| `{ abort }` أو `{ signal }` | تتحد مع الافتراضية: إشارة المستدعي هي `NET_ABORTED`، والمؤقت هو `NET_TIMEOUT`.            |
| `{ abort, timeout }`        | لا يزال غير صالح: `REQ_OPTIONS_INVALID`. القيمة الافتراضية للعميل لا تُعدّ تعارضًا أبدًا. |

### withCredentials()

```ts
function withCredentials(value: boolean): ClientOption
```

عندما يكون `true`، يستخدم Fetch `credentials: 'include'` لـ HTTP وSSE. الافتراضي معطّل. اتصالات WebSocket غير متأثرة.

### withXSRF()

```ts
function withXSRF(options?: {
  cookieName?: string
  headerName?: string
  tokenProvider?: (context: { request: HttpRequest }) => string | null | undefined
}): ClientOption
```

يضيف رأس رمز XSRF إلى طلبات HTTP. الافتراضي: الكوكي `XSRF-TOKEN`، الرأس `X-XSRF-TOKEN`. طلبات SSE وWebSocket غير متأثرة.

يضيف نقل HTTP الافتراضي الرأس عندما تتحقق كل الشروط التالية: الطريقة ليست `GET` ولا `HEAD` ولا `OPTIONS` ولا `TRACE`؛ ولا يحمل الطلب هذا الرأس أصلًا؛ والطلب من الأصل نفسه (same-origin)؛ ويوجد رمز غير فارغ. متى وُجد `location`، بما في ذلك داخل Worker، يجب أن يطابق أصل عنوان الطلب بعد حله `location.origin`؛ وفي غيابه يُعدّ الطلب الذي له `baseEndpoint` من الأصل نفسه. لا تستدعي الطلبات العابرة للأصل `tokenProvider`. يأتي الرمز من هذا المزوّد إن وُجد، وإلا من `document.cookie`، التي لا تُقرأ إلا عند وجود `document`.

## الأنواع

### Client

```ts
type Client = {
  execute(command: EventStreamCommand, options?: EventStreamExecuteOptions): Promise<StreamAwaitResult>
  execute(command: WebSocketCommand, options?: WebSocketExecuteOptions): Promise<SocketAwaitResult>
  execute(command: HttpCommand, options?: HttpExecuteOptions): Promise<HttpAwaitResult>
}
```

معاملات النوع محذوفة هنا؛ كل صيغة استدعاء تستنتج نتيجتها من الأمر.

### ClientOption

```ts
type ClientOption = (config: ClientConfig) => void
```

يعدّل `ClientConfig` الذي يبنيه `createClient`. اكتب واحدًا عندما لا يناسبك أي مساعد `with*`.

### QuerySerializer

```ts
type QuerySerializer = (query: { [key: string]: unknown }) => string
```

### FetchHandle

```ts
type FetchHandle = (input: RequestInfo | URL, init?: RequestInit) => Promise<Response>
```

توقيع الاستدعاء الذي تحتاجه Defjs من تنفيذ Fetch. وهو ليس `typeof fetch`، فلا يحتاج المحاكي (mock) إلى إضافات المضيف مثل `preconnect`. تحلّ معالجات HTTP/SSE الافتراضية `globalThis.fetch` عند كل استدعاء. يستخدم HTTP الوسيطين `(url, init)` فقط مع Fetch الأصلي للمنصة الذي لم يُستبدَل؛ أما البديل العام والمعالجات المخصصة فتستقبل `Request`. يمرّر SSE دائمًا `Request`. يمكن استيراد Core دون Fetch؛ وإذا ظل Fetch غائبًا عند التنفيذ الافتراضي، يُبلَّغ عن `ENV_UNSUPPORTED`، بينما تظل المعالجات المخصصة قابلة للاستخدام.

### ClientSSEOptions

### ClientWebSocketOptions

```ts
interface ClientSSEOptions {
  handle?: FetchHandle
  onInvalidEvent?: (context: {
    reason: 'missing-struct' | 'validation-failed'
    message: { id: string; event: string; data: string }
    cause?: unknown
    signal: AbortSignal
  }) => unknown
  reconnect?: {
    attempts?: number
    delayMs?: number
    factor?: number
    jitter?: number
    maxDelayMs?: number
    shouldReconnect?: (context: {
      attempt: number
      cause?: unknown
      lastEventId: string
      method: string
      open?: { response: { status: number; statusText: string; url: string }; url: string }
    }) => boolean | Promise<boolean>
  }
}

interface ClientWebSocketOptions {
  handle?: WebSocketHandleConstructor
  beforeConnect?: (context: { attempt: number; signal: AbortSignal }) => void | Promise<void>
  heartbeat?: {
    intervalMs: number
    isAck?: (message: unknown) => boolean
    message?: <T = unknown>() => T | unknown
    timeoutMs?: number
  }
  protocols?: readonly string[]
  reconnect?: {
    attempts?: number
    delayMs?: number
    factor?: number
    jitter?: number
    maxDelayMs?: number
    shouldReconnect?: (context: { attempt: number; cause?: unknown; code?: number; reason?: string; wasClean?: boolean }) => boolean
  }
}
```

إعادة الاتصال اختيارية في كلتا وسيلتي النقل: بدون `withSSEReconnect` / `withWebSocketReconnect` لا توجد إعادة محاولة. بمجرد ضبط `reconnect` تُطبَّق هذه القيم الافتراضية:

| الحقل        | SSE            | WebSocket      |
| ------------ | -------------- | -------------- |
| `attempts`   | `3` لكل انقطاع | `3` لكل انقطاع |
| `delayMs`    | `1000`         | `1000`         |
| `factor`     | `1`            | `2`            |
| `jitter`     | `0`            | `0`            |
| `maxDelayMs` | بلا سقف        | `30000`        |

في كلتا وسيلتي النقل، تعيد المصافحة الناجحة ضبط ميزانية إعادة المحاولة لكل انقطاع، ورقم المحاولة الممرَّر إلى ردّ النداء، وأُسّ التراجع. تعطّل `attempts: 0` إعادة المحاولة؛ ولا يعني حذف `attempts` السماح بمحاولات غير محدودة أثناء انقطاع واحد. تضع `maxDelayMs` سقفًا للتأخير النهائي بعد تطبيق `jitter` والتقريب؛ ويُطبَّق أيضًا حد مؤقت المنصة البالغ `2_147_483_647` مللي ثانية، حتى عندما لا يُضبط سقف لـ SSE. يبقى التأخير الأساسي الصفري صفرًا؛ وعند تجاوز نطاق الحساب بأعداد صالحة، تتوقف النتيجة عند هذه الحدود القصوى.

تُفحَص خيارات إعادة الاتصال قبل بدء النقل: يجب أن تكون `attempts` عددًا صحيحًا آمنًا غير سالب؛ وأن تكون `delayMs` و`maxDelayMs` المحددة صراحةً قيمتين منتهيتين وغير سالبتين؛ وأن تكون `factor` عددًا منتهيًا وموجبًا؛ وأن تكون `jitter` عددًا منتهيًا بين 0 و1. تُرجع القيم غير الصالحة `REQ_OPTIONS_INVALID`. في WebSocket، تعطّل `attempts: 0` إعادة المحاولة فورًا وتتجاهل حقول إعادة الاتصال غير المستخدمة؛ أما SSE فيظل يتحقق منها. يزيد `jitter` التأخير الأساسي المقيد بسقف أو ينقصه نسبيًا قبل تطبيق السقف النهائي.

في SSE، `delayMs` هو التأخير الأساسي الابتدائي فقط: يستبدله حقل `retry:` الذي يرسله الخادم ويتكوّن من أرقام فقط في المحاولات اللاحقة، بما في ذلك بعد استعادة الاتصال. إرجاع `shouldReconnect` القيمة `false` يوقف إعادة المحاولة. يستقبل ردّ النداء الخاص بـ SSE أيضًا `lastEventId` وطريقة الطلب `method` وأحدث معلومات `open`، ويمكن أن يكون غير متزامن. بدونه، تقتصر إعادة اتصال SSE على طلبات `GET` و`HEAD` و`OPTIONS` و`PUT` و`DELETE`؛ وعند توفيره، تحدّد نتيجته قرار إعادة الاتصال لكل طريقة. يُرسل أحدث معرّف حدث كبايتات UTF-8 في `Last-Event-ID`؛ ويمسحه المعرّف الفارغ، ويُتجاهل المعرّف الذي يحتوي على NUL. أما ردّ النداء الخاص بـ WebSocket فيستقبل بدلًا من ذلك `code` و`reason` و`wasClean` للإغلاق.

يعالج `onInvalidEvent` في SSE حدثًا لا يطابقه أي struct، بما في ذلك غياب `default` (`missing-struct`)، أو حدثًا تفشل بياناته في struct الخاص به (`validation-failed`). يُسقَط الحدث دائمًا؛ وتُتجاهل قيمة إرجاع المعالج، ولا يغلق الخطأ الذي يرميه التدفق.

في WebSocket يمكن أيضًا تمرير `beforeConnect` و`heartbeat` و`protocols` و`reconnect` لكل استدعاء `execute`؛ وقيمة execute تستبدل قيمة العميل لذلك الاستدعاء. يبني `heartbeat.message` كل ping؛ ولا يُرسل شيء عند حذفه أو عندما يُرجع `undefined`.

### ClientOptions

```ts
interface ClientOptions extends HttpClientOptions {
  sse?: ClientSSEOptions
  webSocket?: ClientWebSocketOptions
}
```

الوصف على شكل المدخل للعميل: `endpoint` و`headers` و`http` و`interceptors` و`querySerializer` و`timeout` و`xsrf` و`withCredentials` و`sse` و`webSocket`. لا يأخذه `createClient`؛ فهو يأخذ مساعدات الخيارات.

### ClientConfig

اللقطة المحلولة التي تعدّلها مساعدات الخيارات ويقرؤها `execute`: `ClientOptions` بعد تطبيق القيم الافتراضية، مع حضور `http.handle` و`interceptors` و`sse` (من نوع `ClientSSEConfig`) و`webSocket` دائمًا.

### ClientSSEConfig

```ts
interface ClientSSEConfig extends ClientSSEOptions {
  handle: FetchHandle
}
```

تهيئة SSE المحلولة على `ClientConfig.sse`: هي `ClientSSEOptions` مع `handle` مطلوب.

### WebSocketHandle

واجهة نسخة WebSocket التي تستخدمها وسيلة النقل: `WebSocket` من دون `binaryType` وثوابت حالة الجاهزية و`dispatchEvent` وخصائص المعالجات `on*`، ومع `readyState: number` للقراءة فقط.

### WebSocketHandleConstructor

```ts
type WebSocketHandleConstructor = { readonly OPEN: number } & (new (...args: never[]) => WebSocketHandle)
```

المُنشئ الممرَّر إلى `withWebSocketHandle`. يجب أن يكشف ثابت حالة الجاهزية `OPEN`.
