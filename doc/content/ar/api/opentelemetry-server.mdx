# خادم OpenTelemetry

إضافة وسيطة: رصد HTTP / SSE / WebSocket الصادر كمعترضات أساسية. لا تهيئ هذه الحزمة OpenTelemetry SDK، وليست رصدًا واردًا للخادم.

انظر [دليل خادم OpenTelemetry](/ar/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

يُلحق معترضًا واحدًا لكل وسيلة نقل مفعّلة، بالترتيب HTTP ثم SSE ثم WebSocket. طبّقه عند `createClient`. `options` مطلوب؛ مرّر `{}` لتثبيت المعترضات مع النشر فقط.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer` و`meter` و`logger` كل منها اختياري. بلا `propagator` ← W3C Trace Context + Baggage.

دون `tracer`، لا تنشئ الإضافة spans محلية، ولا تستدعي `trace.getTracer(...)` أبدًا، وتتخطى `startSpanHook` و`requestHook` و`responseHook`. تعمل نسخ `meter` و`logger` الممرَّرة باستقلال. ما زال النشر يمرّر سياق الأب المستخرَج؛ ويبقى `queryPropagation` في WebSocket بقيمة `false` افتراضيًا. مع tracer، يتجاوز `requireParentSpan: true` كل أدوات الرصد، بما فيها السجلات، عندما لا يوجد أب نشط؛ ودون tracer لا يحجب المقاييس ولا السجلات.

HTTP وSSE وWebSocket مفعّلة افتراضيًا. مرّر `{ enabled: false }` على وسيلة نقل لتجاوزها.

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| الحقل               | الافتراضي                   | الأثر                                                                      |
| ------------------- | --------------------------- | -------------------------------------------------------------------------- |
| `tracer`            | لا شيء                      | دونه لا توجد spans محلية ولا خطافات span.                                  |
| `meter`             | لا شيء                      | دونه لا تُسجَّل مقاييس الحزمة.                                             |
| `logger`            | لا شيء                      | `Logger` من `@opentelemetry/api-logs`. دونه لا تُصدَر LogRecords تشخيصية.  |
| `propagator`        | W3C Trace Context + Baggage | يستخرج سياق الأب ويحقن السياق الصادر.                                      |
| `requireParentSpan` | `false`                     | مع `tracer`، يتجاوز الرصد عندما لا يوجد span أب نشط. يُتجاهل دون `tracer`. |
| `http`              | `{}`                        | خيارات نقل HTTP.                                                           |
| `sse`               | `{}`                        | خيارات نقل SSE.                                                            |
| `webSocket`         | `{}`                        | خيارات نقل WebSocket.                                                      |

`enabled` افتراضيًا `true`؛ و`enabled: false` فقط يطفئ وسيلة نقل.

تعمل خطافات فترة التتبع فقط عند توفير `tracer`. يعمل `startSpanHook` بشكل متزامن قبل إنشاء فترة التتبع لوسيلة نقله HTTP أو SSE أو WebSocket. تُطبَّق سماته بعد السمات المدمجة، فيجوز للتطبيق تغليب `url.full` أو قيمة ابتدائية أخرى. إذا ألقى استثناءً، ينشئ Defjs فترة التتبع بالسمات المدمجة ويواصل الطلب؛ ويعمل `requestHook` و`responseHook` بعد إنشاء فترة التتبع. لا يُنتظَر أي منهما: الإلقاء أو الرفض لا يحجب العملية ولا يُفشلها أبدًا.

ما دام `span.isRecording()` صحيحًا، تسجّل إخفاقات الخطاف حدثي `defjs.otel.hook.error` و`exception`. يحمل حدث `exception` فقط `exception.type` (اسم الصنف، لا رمز خطأ Defjs)، ولا يحمل أبدًا `exception.message` أو `exception.stacktrace`، لأن نص خطأ وقت التشغيل قد يتضمن عنوان URL الكامل للطلب أو جزءًا من جسم الاستجابة؛ والقاعدة نفسها تنطبق على حدث `exception` المسجَّل عند فشل النقل. فترات التتبع غير المسجِّلة (المنتهية أو غير المأخوذة عينة)، تذهب الإخفاقات إلى مسجّل تشخيص OpenTelemetry عبر `diag.error`. يجب أن تضبط التطبيقات `diag.setLogger(...)` من `@opentelemetry/api` لتلقيها؛ ولا يوجد إخراج تلقائي افتراضيًا. لا تهيئ هذه الحزمة SDK، وهذا التشخيص ليس `LogRecord` منفصلًا في SDK.

يتلقى `responseHook` ما أرجعه النقل: `HttpResponse` لـ HTTP، ومقبض التدفق لـ SSE بعد نجاح البدء، والجلسة لـ WebSocket بعد فتحها. وسيطه الثالث هو الطلب الأصلي.

افتراضيًا، يحل `url.full` فقط `request.endpoint` مقابل `request.baseEndpoint` الاختياري؛ ولا يُلحَق `request.query`. ذلك الحد ليس حجبًا للاستعلام. كما تتطلب اصطلاحات OpenTelemetry الدلالية، تُستبدل بيانات الاعتماد في userinfo لنقطة النهاية بـ `REDACTED:REDACTED`، وتُستبدل قيم مفاتيح الاستعلام الحساسة الافتراضية (`sig` و`Signature` و`AWSAccessKeyId` و`X-Amz-Signature` و`X-Amz-Credential` و`X-Amz-Security-Token` و`X-Goog-Signature`) بـ `REDACTED`، لكن الحزمة بلا محجوب مدمج آخر أو سياسة مفاتيح حساسة. يُحجَب `url.full` الذي يُرجعه `startSpanHook` بالطريقة نفسها، أما عنوان URL يكتبه التطبيق عبر كائن `Span` في `requestHook` أو `responseHook` فلا يُعترَض، فابنِه واحجبه عند الحاجة صراحةً:

## تشخيص المسجّل

يستخدم خيار `logger?: Logger` في المستوى الأعلى `@opentelemetry/api-logs`، لا Logger للتطبيق. وهو اختياري ويجوز استخدامه وحده. لا يحصل Defjs أبدًا على مسجّل عام ولا يملك موفّره. يُصدر على الأكثر `LogRecord` واحدًا بمستوى `WARN` (رقم الشدة 13) لكل طلب أو اتصال منطقي، برسالة ثابتة والسمات `server.address` و`server.port` (عند المعرفة) و`defjs.phase` و`exception.type`، والسمات `defjs.meta.*` المأخوذة من `meta` الخاص بالتعريف، إضافة إلى `http.request.method` لـ HTTP، و`defjs.sse.fault.code` عندما ينتهي تدفق SSE بخطأ، و`websocket.close.code` عندما تحمل معلومات إغلاق WebSocket رمزًا عدديًا:

| النتيجة                                                      | الحدث                                                             | `defjs.phase` |
| ------------------------------------------------------------ | ----------------------------------------------------------------- | ------------- |
| يرفض `next()` في HTTP، باستثناء الإلغاء و`HTTP_STATUS` العام | `http.client.request.exception`                                   | `request`     |
| يفشل اتصال SSE أو WebSocket                                  | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `connect`     |
| ينتهي SSE أو WebSocket بخطأ، بما فيه `closed` مرفوض          | حدث النقل نفسه                                                    | `connection`  |

الاستجابات ذات الحالة العادية (بما فيها 4xx/5xx التي يُفك فيها جسم `error` المعلَن) والنجاح والإغلاق الطبيعي وEOF وإلغاء المستدعي لا تنتج LogRecord. تُسجَّل مهلة HTTP مرة واحدة فقط إذا وصل رفض مهلة إلى حد `next()` / النقل في معترض OTel (يُعدّ الإلغاء الذي سببه `TimeoutError`، مثل `AbortSignal.timeout()`، مهلة لا إلغاءً). إذا رصد استدعاء العملية وحده انتهاء المهلة أثناء تحليل المدخل أو البناء أو عمل معترض التطبيق بعد `next()` أو تحويل الجسم بعد السلسلة، فلا يُصدَر LogRecord؛ راقب استدعاء العملية. تُسجَّل إخفاقات قراءة أجسام `output` / `error` المعلَنة داخل حد معالج HTTP لكل تمثيل؛ أما إخفاق نوع الوسائط و`JSON.parse` فيُسجَّل فقط لتمثيلات JSON، أيًّا كانت حالة HTTP. لا تُعدّ النصوص وblobs والبايتات غير JSON فاشلة لمجرد أن نوع وسائطها ليس JSON. الجسم غير المعلَن لا يُقرأ أبدًا ولا يمكن أن يُسجَّل. التحقق من Struct وغياب جسم معلَن مثل 204 وتحويل `HTTP_STATUS` اللاحق تحدث بعد المعترض ولا تُسجَّل. مصافحة SSE غير-2xx تُسجَّل دائمًا مرة واحدة؛ وإطار إغلاق WebSocket من الخادم لا يُسجَّل أبدًا، أيًّا كان رمزه. الانقطاع المفاجئ بلا إطار إغلاق (1006) ينهي الجلسة بخطأ ويُسجَّل مرة واحدة، على كل بيئة تشغيل.

`exception.type` هو اسم صنف ما لاحظه المعترض، لا رمز خطأ Defjs: مثل `BodyFailure` (جسم HTTP) و`EventStreamFatalError` (مصافحة SSE تفشل لسبب غير حالة غير 2xx، مثل استجابة ليست `text/event-stream`) و`DefjsFault` (بدء WebSocket، ومصافحة SSE ذات حالة غير 2xx) و`TypeError` (فشل شبكة) أو `Error` (مهلة). تملك التطبيقات الترشيح والمصدّرين والتفريغ والإيقاف.

انظر أمثلة التسجيل الكاملة وتكامل الطرف الثالث في [دليل OpenTelemetry](/ar/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
