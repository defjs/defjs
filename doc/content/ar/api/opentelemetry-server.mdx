# خادم OpenTelemetry

إضافة وسيطة: رصد صادر لكل استدعاء عملية ولوسيلة نقله HTTP / SSE / WebSocket، كمعترضات أساسية. لا تهيئ هذه الحزمة OpenTelemetry SDK، وليست رصدًا واردًا للخادم.

انظر [دليل خادم OpenTelemetry](/ar/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

يُلحق معترض عملية عند توفير `tracer` أو `meter` أو `logger`، ثم معترضًا واحدًا لكل وسيلة نقل مفعّلة، بالترتيب HTTP ثم SSE ثم WebSocket. طبّقه عند `createClient`، مرة واحدة لكل عميل. `options` مطلوب؛ مرّر `{}` لتثبيت معترضات النقل مع النشر فقط.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer` و`meter` و`logger` كل منها اختياري. بلا `propagator` ← W3C Trace Context + Baggage.

يُرصد كل استدعاء عملية من الاستدعاء حتى مصفوفة نتيجته: span من نوع `INTERNAL` للعملية باسم `defjs.operation.name` (مثل `GET /orders/:id`) يُضبط فيه `error.type` على رمز الخطأ عند الإخفاق، وعينة واحدة لـ `defjs.client.operation.duration`، وسجل `WARN` واحد عند الإخفاق. وتحصل كل محاولة HTTP وكل اتصال SSE أو WebSocket على span نقل من نوع `CLIENT` تحته. الاستدعاء بلا span أب نشط يبدأ تتبعًا خاصًا به؛ ويقرر sampler الخاص بـ SDK ما يُحتفظ به.

دون `tracer`، لا تنشئ الإضافة spans محلية، ولا تستدعي `trace.getTracer(...)` أبدًا، وتتخطى `startSpanHook` و`requestHook` و`responseHook`. تعمل نسخ `meter` و`logger` الممرَّرة باستقلال. ما زال النشر يمرّر سياق الأب المستخرَج؛ ويبقى `queryPropagation` في WebSocket بقيمة `false` افتراضيًا.

HTTP وSSE وWebSocket مفعّلة افتراضيًا. مرّر `{ enabled: false }` على وسيلة نقل لتجاوزها.

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| الحقل                     | الافتراضي                   | الأثر                                                                                   |
| ------------------------- | --------------------------- | --------------------------------------------------------------------------------------- |
| `tracer`                  | لا شيء                      | دونه لا توجد spans محلية ولا خطافات span.                                               |
| `meter`                   | لا شيء                      | دونه لا تُسجَّل مقاييس الحزمة.                                                          |
| `logger`                  | لا شيء                      | `Logger` من `@opentelemetry/api-logs`. دونه لا تُصدَر LogRecords تشخيصية.               |
| `propagator`              | W3C Trace Context + Baggage | يستخرج سياق الأب ويحقن السياق الصادر.                                                   |
| `includeErrorDiagnostics` | `false`                     | يصدّر رسائل الأخطاء وتتبعات المكدس على spans الفاشلة وأحداث `exception` وسجلات الإخفاق. |
| `http`                    | `{}`                        | خيارات نقل HTTP.                                                                        |
| `sse`                     | `{}`                        | خيارات نقل SSE.                                                                         |
| `webSocket`               | `{}`                        | خيارات نقل WebSocket.                                                                   |

`enabled` افتراضيًا `true`؛ و`enabled: false` فقط يطفئ وسيلة نقل، مع قياس العمليات عن بُعد لاستدعاءاتها.

تعمل خطافات فترة التتبع فقط عند توفير `tracer`. يعمل `startSpanHook` بشكل متزامن قبل إنشاء فترة التتبع لوسيلة نقله HTTP أو SSE أو WebSocket. تُطبَّق سماته بعد السمات المدمجة، فيجوز للتطبيق تغليب `url.full` أو قيمة ابتدائية أخرى. إذا ألقى استثناءً، ينشئ Defjs فترة التتبع بالسمات المدمجة ويواصل الطلب؛ ويعمل `requestHook` و`responseHook` بعد إنشاء فترة التتبع. لا يُنتظَر أي منهما: الإلقاء أو الرفض لا يحجب العملية ولا يُفشلها أبدًا.

تشكّل الخطافات span النقل؛ ولا خطافات لـ span العملية. ما دام `span.isRecording()` صحيحًا، تسجّل إخفاقات الخطاف حدثي `defjs.otel.hook.error` و`exception`. يحمل حدث `exception` فقط `exception.type` (اسم الصنف، لا رمز خطأ Defjs)، ولا يحمل `exception.message` ولا `exception.stacktrace` إلا إذا كان `includeErrorDiagnostics` مفعّلًا، لأن نص خطأ وقت التشغيل قد يتضمن عنوان URL الكامل للطلب أو جزءًا من جسم الاستجابة؛ والقاعدة نفسها تنطبق على حدث `exception` المسجَّل عند فشل النقل. فترات التتبع غير المسجِّلة (المنتهية أو غير المأخوذة عينة)، تذهب الإخفاقات إلى مسجّل تشخيص OpenTelemetry عبر `diag.error`. يجب أن تضبط التطبيقات `diag.setLogger(...)` من `@opentelemetry/api` لتلقيها؛ ولا يوجد إخراج تلقائي افتراضيًا. لا تهيئ هذه الحزمة SDK، وهذا التشخيص ليس `LogRecord` منفصلًا في SDK.

يتلقى `responseHook` ما أرجعه النقل: `HttpResponse` لـ HTTP، ومقبض التدفق لـ SSE بعد نجاح البدء، والجلسة لـ WebSocket بعد فتحها. وسيطه الثالث هو الطلب الأصلي.

افتراضيًا، يحل `url.full` فقط `request.endpoint` مقابل `request.baseEndpoint` الاختياري؛ ولا يُلحَق `request.query`. ذلك الحد ليس حجبًا للاستعلام. كما تتطلب اصطلاحات OpenTelemetry الدلالية، تُستبدل بيانات الاعتماد في userinfo لنقطة النهاية بـ `REDACTED:REDACTED`، وتُستبدل قيم مفاتيح الاستعلام الحساسة الافتراضية (`sig` و`Signature` و`AWSAccessKeyId` و`X-Amz-Signature` و`X-Amz-Credential` و`X-Amz-Security-Token` و`X-Goog-Signature`) بـ `REDACTED`، لكن الحزمة بلا محجوب مدمج آخر أو سياسة مفاتيح حساسة. يُحجَب `url.full` الذي يُرجعه `startSpanHook` بالطريقة نفسها، أما عنوان URL يكتبه التطبيق عبر كائن `Span` في `requestHook` أو `responseHook` فلا يُعترَض، فابنِه واحجبه عند الحاجة صراحةً:

</include>

`webSocket.queryPropagation` (WebSocket فقط) افتراضيًا `false`. فعّله فقط بعد أن تقبل سياق التتبع في عنوان URL الخاص بـ WebSocket.

## تشخيص المسجّل

يستخدم خيار `logger?: Logger` في المستوى الأعلى `@opentelemetry/api-logs`، لا Logger للتطبيق. وهو اختياري ويجوز استخدامه وحده. لا يحصل Defjs أبدًا على مسجّل عام ولا يملك موفّره. يُصدر `LogRecord` واحدًا بمستوى `WARN` (رقم الشدة 13) لكل استدعاء عملية فاشل، وآخر لكل تدفق SSE أو جلسة WebSocket تفشل بعد أن فُتحت، لكل منها رسالة ثابتة:

| النتيجة                                                       | الحدث                                                             | السمات                                                                                                              |
| ------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| يُحل استدعاء عملية بخطأ غير `NET_ABORTED`                     | `defjs.client.operation.exception`                                | `defjs.operation.name` و`error.type` (رمز الخطأ) و`exception.type` و`defjs.meta.*`                                  |
| ينتهي تدفق SSE أو جلسة WebSocket بخطأ، بما فيه `closed` مرفوض | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address` و`server.port` و`exception.type` و`defjs.meta.*` و`defjs.sse.fault.code` أو `websocket.close.code` |

النجاح، ومحاولة أُعيدت ثم تعافت في محاولة لاحقة، والإغلاق الطبيعي، وEOF، وإطار إغلاق WebSocket من الخادم أيًّا كان رمزه، وإلغاء المستدعي لا تنتج LogRecord. الانقطاع المفاجئ في WebSocket بلا إطار إغلاق (1006) ينهي الجلسة بخطأ ويُسجَّل مرة واحدة، على كل بيئة تشغيل. يُصدَر سجل العملية بسياق span العملية.

مع `includeErrorDiagnostics: true`، يحمل كل سجل أيضًا `exception.message` و`exception.stacktrace`؛ وفي استدعاء العملية هما `message` و`stack` الخاصان بالخطأ. لا تُصدَّر سلسلة الأسباب ولا الحقول القابلة للعدّ في الخطأ أبدًا، لكن الرسالة غير مرشَّحة: رسالة الخطأ غالبًا هي رسالة سببه، وقد يقتبس نص أخطاء المنصة عنوان URL للطلب. تملك التطبيقات الترشيح والمصدّرين والتفريغ والإيقاف.

انظر أمثلة التسجيل الكاملة وتكامل الطرف الثالث في [دليل OpenTelemetry](/ar/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
