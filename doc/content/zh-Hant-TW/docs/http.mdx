# HTTP 操作

SDK 開發者用 `defineRequest` 定義每項 HTTP 操作：HTTP 方法、路徑模板、`input` schema、同步的 `builder`，以及 `output` / `error` 回應 schema。取用端應用程式匯入該操作、傳入自己設定好的 `Client`，並處理回傳的 `[error, data, response]` tuple。

### SDK 設計最佳實務

- **每項定義只對應一項操作**：讓每個方法、路徑與契約各自成為一份定義，應用程式才能對未使用的操作進行 Tree-shaking。
- **設定靜態的 `operation` 名稱**：使用低基數（low-cardinality）的識別碼，例如 `"orders.read"`。遙測外掛（`@defjs/opentelemetry-server`）與日誌攔截器會使用它，而不會洩漏 URL 或使用者 ID。
- **絕不把 Client 嵌進 SDK**：只匯出定義、`struct` schema 與型別。

## 2. URL 解析與路徑參數

`withEndpoint(...)` 需要傳入合法的絕對 URL。其 pathname 會作為基礎目錄（基礎端點上的任何 query string 或 hash 都會被自動丟棄）。

<include cwd>examples/http/resolve-url.ts#example</include>

- **路徑佔位符（`:name`）**：只會被編碼一次，成為單一路徑區段。斜線、`?`、`#`、`%`、空白與 Unicode 都留在該區段內——請勿事先自行編碼。空字串、`.` 與 `..` 會以 `REQ_BUILD_FAILED` 失敗。
- **Origin 與目錄範圍限制**：定義路徑不能是絕對 URL 或協定相對路徑（`//...`），不能包含 C0 控制字元、反斜線、`?` 或 `#`，也不能脫離基礎端點的目錄範圍（`../`）。任何違規都會在攔截器或傳輸層執行之前，立即以 `REQ_BUILD_FAILED` 失敗。

## 3. 使用 builder 放置輸入參數

只要操作宣告了 `input`，就**必須**提供一個回傳 `{ path?, query?, headers?, body? }` 的同步純函式 `builder`。只有未宣告 `input` 的操作才可以省略 `builder`。

<include cwd lang="typescript">

</include>

### `builder` 如何處理欄位別名

| Builder 運算式                                 | 傳輸實際輸出                                                    |
| ---------------------------------------------- | --------------------------------------------------------------- |
| `body: input.profile`                          | 具型別 struct：`.alias()` 與 `Date` / `bigint` 編解碼器自動生效 |
| `body: { profile: input.profile }`             | 外層鍵名 `profile` 為字面值；內層物件保留其 struct 別名         |
| `body: { ...input.profile, role: "admin" }`    | 物件展開會保留 struct 別名；`role` 則為字面值                   |
| `body: { name: input.profile.customerName }`   | 匿名物件：所有鍵名皆為字面值                                    |
| `query: input.filter` / `headers: input.trace` | 扁平的具型別物件：欄位的 `.alias()` 會成為傳輸鍵名              |

### 自訂 Query 序列化

預設情況下，query 的純量與純量陣列（重複鍵名）會直接編碼，巢狀的 query 物件則會以 `REQ_BUILD_FAILED` 失敗。若後端需要巢狀 query 語法（例如 `filter[status]=paid`），請在 Client 上設定 `withQuerySerializer`：

### 請求本文格式

`GET` 與 `HEAD` 不能攜帶本文。其他方法的本文格式，取決於 `builder` 回傳的值：

| `body` 值                                                  | 實際傳輸格式                               | 預設 `Content-Type`                       |
| ---------------------------------------------------------- | ------------------------------------------ | ----------------------------------------- |
| `undefined` / 省略                                         | 無本文                                     | —                                         |
| 帶有 `urlencoded` / `formData` 編解碼器的根 struct         | `URLSearchParams` / `FormData`（套用別名） | 表單型別 / multipart boundary             |
| 原生 `FormData` 或 `URLSearchParams`                       | 原樣傳遞                                   | Multipart boundary / urlencoded           |
| `Blob` / `File`                                            | 原樣傳遞                                   | `blob.type` 或 `application/octet-stream` |
| `ArrayBuffer`、型別化陣列、`DataView`、`ReadableStream`    | 原始位元組 / 串流                          | `application/octet-stream`                |
| `string`                                                   | UTF-8 字串                                 | `text/plain;charset=UTF-8`                |
| 一般物件、陣列、有限數值、布林值、`null`、`Date`、`bigint` | Struct 編碼的 JSON                         | `application/json`                        |

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

無法以 JSON 表示的值（`NaN`、`±Infinity`、`Map`、`Set`、函式、未實作 `toJSON()` 的類別實例，或原始的可迭代物件）會立即以 `REQ_BUILD_FAILED` 失敗，而不會悄悄序列化成 `{}` 或 `null`。

## 4. 回應如何被解碼

`output` 驗證 `2xx` 回應，`error` 驗證非 `2xx` 回應（`3xx`、`4xx`、`5xx`）。struct 的種類決定回應串流要怎麼讀（`struct.string()` → 文字，`struct.blob()` / `struct.file()` → `Blob`，`struct.arrayBuffer()` → `ArrayBuffer`，其餘皆為 JSON）：

1. **依 `ok` (`200..299`) 選邊**：`2xx` 走 `output`，非 `2xx` 走 `error`。
2. **省略即不讀取**：該側沒有宣告 struct 時，回應本文完全不會被讀取（`2xx` 解析為 `data: undefined` + `HttpMeta`；非 `2xx` 解析為 `HTTP_STATUS` 且 `data: undefined`）。
3. **先驗證 JSON 媒體型別**：對於 JSON struct，非 JSON 的 `Content-Type` 會在讀取本文串流之前以 `RES_MEDIA_TYPE_INVALID` 失敗。
4. **讀取與剖析**：無法讀取的串流或無效的 JSON 會以 `RES_DECODE_FAILED` 失敗（若在傳輸途中被截斷則為 `NET_BODY_INCOMPLETE`）。
5. **以 `struct` 驗證**：schema 不符時以 `RES_STRUCT_MISMATCH` 失敗。

## 5. 取消工作與設定逾時期限 [#cancel-the-work]

透過衍生單次呼叫的 Client 傳入 `signal`：`client({ signal })`。

- **逾時期限（`NET_TIMEOUT`）**：使用 `AbortSignal.timeout(ms)`。
- **手動取消（`NET_ABORTED`）**：使用 `AbortController`。
- **組合訊號**：使用 `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`。

## 6. 憑證、XSRF 與傳輸進度

- **`withCredentials(true)`**：為 HTTP 與 SSE 請求設定 Fetch 的 `credentials: "include"`。
- **`withXSRF(options?)`**：在同源的變更型 HTTP 方法（`POST`、`PUT`、`PATCH`、`DELETE`）上，讀取 XSRF Cookie（預設 `XSRF-TOKEN`）並注入標頭（`X-XSRF-TOKEN`）。
- **`onDownloadProgress` / `onUploadProgress`**：透過 `client({ onDownloadProgress, onUploadProgress })` 傳入。只有當 `Content-Length` 為正值、且沒有 `Content-Encoding` 或為 `identity` 時，下載進度才會回報 `lengthComputable: true`。上傳進度在伺服器執行環境（Bun、Node.js）會以串流方式傳送本文。進度回呼若拋出例外，該次呼叫會以 `EXT_OBSERVER_FAILED` 失敗。
