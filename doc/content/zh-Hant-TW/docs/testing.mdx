# 測試

因為 Defjs 將操作定義與 Client 執行徹底分開，你可以在離線環境下完整測試真實的 SDK 定義與應用程式攔截器，不需要啟動實體網路伺服器，也不必 Mock 內部函式庫。

## 1. 注入本機傳輸層控制代碼

在 `createClient(...)` 上使用 `withHTTPHandle`、`withSSEHandle` 或 `withWebSocketHandle` 來替換底層的平台傳輸層。Defjs 依然會執行完整的操作管線：輸入 `struct` 驗證、`builder` 參數對應、URL 限制檢查、中介層攔截器、狀態碼分派以及回應 `struct` 解碼。

## 2. 測試最佳實踐

### 斷言 error-first tuple，而不是內部實作細節

始終使用測試 Client 呼叫匯出的 SDK 操作，並對回傳的 `[error, data, response]` tuple 進行斷言：

- 針對 `2xx` 成功案例，斷言 `expect(error).toBeNull()`，並驗證解碼後的 `data` 欄位（包含 `.alias()` 從網路到邏輯名稱的轉換）。
- 針對失敗案例，若屬於公開契約的一部分，斷言 `error?.code`、`error?.status`、`error?.data` 與 `error?.cause`。

### 驗證出站請求的網路位元組

在你的 `withHTTPHandle(async (input, init) => ...)` 函式內部，建構 `const request = new Request(input, init)`，並檢查 `request.url`、`request.method`、`request.headers` 以及 `await request.text()`（或 `await request.json()`），以驗證你的 `builder` 與 struct 別名是否正確序列化出後端預期的通訊格式。

### 使用虛擬計時器（Fake Timers）進行確定性時間控制

攔截器重試退避、SSE/WebSocket 重新連線延遲或 WebSocket 心跳，在 Vitest 裡用 `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })`。這些虛擬計時器不會推動原生的 `AbortSignal.timeout`。要在 Vitest 裡得到確定的請求期限，請用受控的 `setTimeout`，以 `TimeoutError` 為原因中止一個 `AbortController`：

在 Bun test 裡用 `jest.useFakeTimers()` 與 `jest.advanceTimersByTime()`；Bun 的虛擬計時器也會控制 `AbortSignal.timeout`。不要假定兩種執行器控制同一套原生時鐘。只在被等待的階段已經開始之後再推進時間，斷言狀態轉換或嘗試次數，而不是牆上時間，並在每個測試之後恢復真實計時器。
