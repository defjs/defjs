# 負載平衡與容錯移轉

當應用程式使用 `withEndpoint(...urls)` 設定多個基礎網址時，Defjs 能將請求分發至各個副本節點、透過被動斷路器或主動健康檢查剔除不健康的伺服器，並可選擇性地在同一呼叫內對安全的 HTTP 方法進行容錯移轉。

## 1. 選擇負載平衡器策略

| 策略                                                                             | 最佳使用情境                                     | 預設健康狀態過濾                           |
| -------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------ |
| [`pickFirstBalancer(options?)`](/zh-Hant-TW/api/core/pickfirstbalancer) _(預設)_ | 具有優先順序的主備區域清單的瀏覽器前端應用       | 關閉（可透過 `outlierDetection` 選項開啟） |
| [`roundRobinBalancer(options?)`](/zh-Hant-TW/api/core/roundrobinbalancer)        | 跨同等權重伺服器副本的呼叫（支援選用 `weights`） | 開啟（連續失敗 `5` 次觸發）                |
| [`p2cBalancer(options?)`](/zh-Hant-TW/api/core/p2cbalancer)                      | 副本節點延遲或進行中請求負載差異較大的伺服器呼叫 | 開啟（連續失敗 `5` 次觸發）                |

### `pickFirstBalancer` 與 `p2cBalancer` 的運作機制

- **`pickFirstBalancer`**：停在第一個 URL 上，遇到 `NET_UNREACHABLE` 或 `NET_UNAVAILABLE`（HTTP 502、503 或 504）時才前進。順序與黏性端點遵循 client 的完整端點清單（`members`），且 HTTP 重試絕不會移動黏性端點：對第一個端點的逾時被重試到第二個端點後，後續呼叫仍留在第一個端點，failback 也保持待命。設定 `failbackMs: 30_000`，在備用端點上停留這段時間之後，再探測主要端點。同時最多只能有一個進行中的主要端點探測。探測在對端回應開始時判定（HTTP 回應標頭、SSE 交握或 WebSocket 開啟），因此作為探測的長時間串流不會讓整個 client 的 failback 一直被阻擋；從未到達該時刻的嘗試則在完成時判定。容錯移轉後首次探測主要端點之前，必須滿足間隔已過，且離開主要端點後至少選取過一次替代端點。探測失敗會重新開始這兩項要求：下次探測前，必須重新選取過替代端點，並再次經過該間隔，即使 SSE/WebSocket 重連退避比 `failbackMs` 更長也一樣。如此健康的備用端點才有機會被使用，而非每次重連都命中失效的主要端點。
- **`roundRobinBalancer` 權重**：未指定的權重為 `1`；設定的權重必須是有限正數。平滑加權輪詢會維持比例（例如 `3:1` 時，權重較高的節點每四次選取會被選中三次）。極端的量級會被縮放以避免溢位；低於浮點精確度的比例可能四捨五入成零。每次選取與清理過時 current 值都要花 O(候選數量) 的工作。
- **`p2cBalancer`（兩者隨機取優，Power of Two Choices）**：不重複地隨機抽取兩個候選端點，並選擇評分較低者：`PeakEwma RTT × (pending + 1)`（若設定 `load: "pending"` 則只計算進行中的 `pending` 請求數）。預設值（`defaultRttMs: 30`、`decayMs: 10000`）遵循 Linkerd/tower 慣例。pending 在 `pick` 選取端點的那一刻就被預留，因此同一個 tick 內的一批呼叫會分散到不同端點；它在對端回應開始時（HTTP 回應標頭、SSE 交握、WebSocket 開啟）釋放，若沒有回應開始，則在嘗試完成時釋放。對 SSE 與 WebSocket 而言，這表示 p2c 平衡的是交握，而不是已開啟連線的數量。

平衡器狀態（黏性端點、剔除狀態與 p2c 負載）以及重試預算都歸 Client 所有：整個應用程式只建立一次 Client，並以 `client(options)` 衍生每次呼叫的 Client：衍生的 Client 同時保留平衡器狀態與重試預算。用 `withBalancer` 把同一個平衡器值傳給多個 Client 時，只共用平衡器狀態；每個 Client 仍有各自的重試預算。每個請求都新建一個 `createClient`，則兩者都會從頭開始。

## 2. 同一次呼叫內的 HTTP 重試

重試由三個各自獨立的決定支配：**要不要再試一次**（`withRetry`）、**要送到哪裡**（執行時要求平衡器重新選取，並排除已經試過的端點），以及**要等多久**（退避）。HTTP 的 `withRetry`、SSE 的 `withSSEReconnect` 與 WebSocket 的 `withWebSocketReconnect` 是對稱的、各傳輸層級的策略。它們扁平的退避欄位名稱相同、驗證相同、延遲計算也相同。平衡器完全不知道重試策略；自訂平衡器也不需要特別配合。

同一次呼叫內的 HTTP 重試**預設關閉**。省略 `withRetry` 時，每次呼叫只嘗試一次，既不會建立重試預算，也不會向它存入額度。之後各次呼叫的選擇方式不變：`pickFirstBalancer` 仍可以在一次失敗的呼叫之後前進。`withRetry()` 與 `withRetry({})` 等價，會為 `GET`、`HEAD`、`OPTIONS` 與 `TRACE` 上的連線失敗啟用總共兩次嘗試。

這與 Go 生態系一致：[gRPC 把 `retryPolicy` 放在 service configuration 裡](https://grpc.io/docs/guides/retry/)，與負載平衡設定並列；[go-kit 的 `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) 則明確包住一個平衡器。兩者預設都不套用應用程式自己的重試策略。gRPC 的重試策略要求設定退避，並使用 ±0.2 的抖動；[Envoy 預設以 25 毫秒為基數，上限是該基數的十倍](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff)。Defjs 使用 25 毫秒、係數 2、250 毫秒上限，以及 ±20% 的抖動。gRPC 可以針對底層競態做透明重試；Defjs 不模擬這些行為。

- **總嘗試次數（`maxAttempts`）**：包含首次嘗試，與 gRPC 的 `retryPolicy.maxAttempts` 以及 go-kit `lb.Retry` 的 `max` 一致。該值必須是至少為 1 的安全整數；`1` 表示不重試。沒有設定上的上限，但平衡器每次選取都會排除該次呼叫內已選取過的端點。這裡計算的是外層嘗試，而非應用程式攔截器內部的實際傳送次數：循環呼叫 `next()` 的攔截器可以多次傳送至同一端點。例如，使用 `maxAttempts: 2` 時，攔截器向故障主要端點傳送三次，再由外層向健康備用端點重試一次，就會產生四次網路請求；builder 與攔截器鏈外層的驗證只會執行兩次，不是四次。串流請求本文不會重試。`methods` 不區分大小寫；`methods: []` 會關閉所有方法的重試。
- **重試條件（`on`）**：預設為 `["connect-failure"]`。可以追加 `"gateway-error"`，對應 `NET_UNAVAILABLE`（HTTP `502`/`503`/`504`），包括被 `RES_*` 解碼拒絕的閘道錯誤本文；設定了 `attemptTimeoutMs` 時還可以追加 `"attempt-timeout"`。一次符合條件的重試會重建請求，並從最外層重新執行整條攔截器鏈。
- **退避（`delayMs`、`factor`、`jitter`、`maxDelayMs`）**：第 n 次重試之前，等待 `delayMs × factor^(n−1)`，並加上乘性抖動，在抖動與取整之後封頂。預設值是 `25`、`2`、`0.2` 與 `250`。`delayMs: 0` 略過等待。與重新連線一樣，`delayMs` 必須是非負有限數，`factor` 必須是正的有限數，`jitter` 必須是 `[0, 1]` 內的有限數，`maxDelayMs` 必須是非負有限數或正 `Infinity`。平台計時器上限仍然生效。
  Core 的 `withRetry` 不會讀取 `Retry-After`。這個標頭的處理方式（包含任何延遲上限）屬於[應用程式攔截器策略](/zh-Hant-TW/docs/interceptors)，不是此處退避機制的一部分。
  只設定了一個端點時，`withRetry` 不會重放請求，因為每一次重試都會排除已經試過的端點。

- **單次嘗試 vs. 整次呼叫逾時**：`attemptTimeoutMs` 必須是有限正數，並且不得大於 2147483647（計時器上限）；否則該操作回傳 `REQ_OPTIONS_INVALID`。它為送往所選端點的每次 Fetch 計時，從呼叫一直到其回應本文讀取完成。傳送前後的攔截器工作（例如 `401` 之後更新權杖）以及 struct 解碼都不計時，也絕不會算到端點頭上；傳送完成之後，呼叫端期限在攔截器工作期間到期，不會以 `NET_TIMEOUT` 回報給平衡器，回報的是端點自身的結果。呼叫端的 `client({ signal: AbortSignal.timeout(ms) })` 涵蓋每一次嘗試**以及退避等待**。等待期間取消會回傳呼叫端的取消錯誤，也不會再重新選取。
- **重試時沒有可用端點**：當某一輪重試無法使用任何端點（平衡器 pick 失敗，或下一個端點的 URL 無法解析）時，呼叫會回傳上一次嘗試的錯誤（例如 `NET_UNREACHABLE`），而不是 `REQ_BUILD_FAILED`。
- **Finagle / Linkerd 重試預算（`budget`）**：每一份 client 設定各自擁有一份預算，只有使用同一份設定衍生的 client 會共享，共用平衡器的 client 之間則不共享。預設值是 `percentCanRetry: 0.2`、`minRetriesPerSecond: 10`、`ttlMs: 10000`：原始流量的 20% 再加上儲備。存入與取出都在十個 TTL/10 的時間切片上惰性到期。一次重試會在等待之前先取出額度；預算耗盡時既不等待，也不重試。設定 `budget: false` 可移除這項限制。
- **瀏覽器離線提示**：當 `navigator.onLine === false` 時，連線失敗會回報 `{ attempted: false }`，此時不會推進平衡器，也不會觸發重試。

### 瀏覽器部署邊界

- 瀏覽器 CORS 失敗會以連線失敗的形式傳給 Fetch，並回報為 `NET_UNREACHABLE`，無法與主機停機區分。它可能推進端點選取，並觸發明確啟用的安全方法重試；成功的容錯移轉因此可能掩蓋主要區域的 CORS 設定錯誤。
- 即使回應缺少必要的 CORS 標頭，伺服器仍可能已處理 POST。應用程式隨後收到 `NET_UNREACHABLE`，卻不知道寫入是否成功。預設不會重播 POST；明確啟用寫入重試，需要應用程式層級保證跨副本的冪等性。
- 在瀏覽器中，伺服器拒絕的 WebSocket 升級（例如 `401`）與端點無法連線無從區分，都會回報為 `NET_UNREACHABLE`，因此過期的憑證可能導致端點被剔除。
- Cookie 的範圍依主機而非連接埠劃分：`localhost` 上不同連接埠的兩個端點可以共用 Cookie，但 `localhost` 與 `127.0.0.1` 不會。多來源端點集合需要審慎規劃 Cookie/Token 與 CORS 憑證策略；`withCredentials(true)` 不會改變 Cookie 範圍。
- 明確的離線提示（`navigator.onLine === false`）會抑制端點歸屬與連線失敗重試。這只是瀏覽器提示，不是可靠的可達性檢查。

後一次 `withRetry` 會替換該策略。`withRetry()` 與 `withRetry(undefined)` 的行為與 `withRetry({})` 相同。啟用之後若要關閉重試，傳入 `withRetry({ maxAttempts: 1 })`。無效的重試設定會在 HTTP 操作執行時回傳 `REQ_OPTIONS_INVALID`，訊息為 `Invalid retry options`。

1. **連續失敗**：預設分類器把每個帶 code 的結果都計為失敗：`NET_UNREACHABLE`、`NET_UNAVAILABLE`、`NET_SERVER_ERROR`、`NET_TIMEOUT` 與 `NET_BODY_INCOMPLETE`。已嘗試但沒有 code 的結果會重設連續計數；未歸屬的嘗試與被丟棄的取樣則維持計數不變。連續出現 `consecutiveFailures` 次（預設 `5`）計入的結果後，該端點會被剔除 `min(minPenaltyMs × 2^level, maxPenaltyMs)`（`1000ms` 至 `60000ms`），再加上最多 `50%` 的均勻正向抖動；基礎時長加抖動的總和不會超過 `maxPenaltyMs`。
2. **單次探測復原**：懲罰到期後，會以單一請求探測該主機。若對端回應開始（`end`）且沒有計入失敗，正常流量立即恢復，懲罰等級重設為 `0`；若失敗（包括逾時），該端點會再次被剔除，懲罰加倍。
3. **有界歷史**：在衍生 Client 與每次呼叫的候選排除之間，健康歷史總共至少保留 256 個端點，且至少涵蓋目前成員數量。優先淘汰最近最少使用的乾淨或已過期項目，接著才是尚未達到門檻的部分連續失敗紀錄。只有所有保留項目都受保護時，才會淘汰懲罰尚未到期或有進行中探測的項目，此時移除最舊的一項。僅在某次呼叫省略端點，不會重設其懲罰。P2C 的負載歷史紀錄同樣至少保留 256 項且至少涵蓋目前成員數量，因此超過 256 個端點的清單也會保留每一份估計，先淘汰閒置項目，再淘汰忙碌項目；被遺忘的端點會從 `defaultRttMs` 重新開始。Pick-first 的 shuffle key 在 LRU 快取中至少保留 256 項且至少涵蓋目前成員，因此被遺忘的端點再次出現時會取得新 key。加權輪詢為用戶端的成員保留 current 值：在某次選擇中被排除的端點（HTTP 重試或健康過濾）仍保留其值，如同 nginx 跳過已下線的節點，只有離開成員清單的端點才會丟棄其值；複製後的權重設定在建構時固定。可用時，時長使用平台的單調 Performance 時鐘，只有在無法使用時才以 `Date.now()` 作為後備。
4. **應急放行（panic-mode fail-open）**：若 `isHealthy` 否決了所有未被剔除的端點，平衡器會忽略 `isHealthy`，改在未被剔除的端點中挑選；只有所有設定的端點都被剔除時，才會放行至 Client 的完整候選清單，而不是在本機直接丟棄所有流量。

## 4. 傳輸統計生命週期 (`pick` → `start` → `end` → `done`)

自訂平衡器必須選取 `info.endpoints` 中某個完全相同的字串。若選了候選集之外的值，會回傳 `REQ_BUILD_FAILED` tuple，cause 訊息為不含敏感資訊的 `Balancer selected an endpoint outside the candidate set`；此時不會啟動任何傳輸，該選取的 `done` 會以 `{ attempted: false }` 執行一次。這項規則讓健康過濾與每次呼叫的重試排除得以維持。

自訂平衡器要實作同步的 `pick(info)`，以及可選的 `start()`、`end(info)` 與 `done(info)` 回呼。`PickInfo` 包含一次 pick 的候選 `endpoints`（重試以及包裝器過濾時該清單會縮小）、`members`（client 的完整端點清單，每次嘗試都相同；有狀態的平衡器以它為依據維護順序與狀態）與可選的定義 `operation`，沒有傳輸類型的判別欄位。傳輸層會把自己的事實轉譯成中立的 `DoneInfo.code` 結果。內建平衡器從不讀取 `status`；這份原始回應資訊只保留給自訂平衡器。`start` 在嘗試之前執行，`end` 在對端回應開始或發生回應前失敗時執行，`done` 則在完成時執行。因此，之後的本文失敗可以改變最終的 code，卻不會改變更早的 `end` 取樣：

| 實體傳輸層結果                                                    | 最終 `done(info)` 取樣資料                                 |
| ----------------------------------------------------------------- | ---------------------------------------------------------- |
| HTTP/SSE 回應狀態 502、503 或 504                                 | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| HTTP/SSE 其他至少為 500 的回應狀態                                | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP/SSE 回應狀態 2xx、3xx 或 4xx（包括 429）                     | `{ attempted: true, status }`                              |
| HTTP 回應本文中途截斷                                             | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE 交握成功，之後串流 `reader.read()` 拒絕                       | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| SSE 正常 EOF、交握成功後的解碼失敗，或佇列上限                    | `{ attempted: true, status }`                              |
| 已連線的 WebSocket 以代碼 `1006` 或 `1015` 關閉（未收到關閉訊框） | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 已開啟的 WebSocket 以代碼 `1012` 或 `1013` 關閉                   | `{ attempted: true, code: "NET_UNAVAILABLE" }`             |
| WebSocket 心跳確認逾時                                            | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 已開啟的 WebSocket 以其他任何代碼關閉，無論 `wasClean` 為何       | `{ attempted: true }`                                      |
| 呼叫端取消，或手動關閉串流／Socket                                | `{ attempted: false }`                                     |
| 嘗試開始後呼叫端期限到期                                          | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

交握解碼失敗會保留由交握狀態推導出的中立結果（例如狀態 `503` 對應 `NET_UNAVAILABLE`）。不完整的 HTTP 本文則保留 `NET_BODY_INCOMPLETE` 及其原始 status，即使是閘道回應也一樣；如同任何帶 code 的結果，它會被預設的 outlier detection 計為失敗。無法送出的心跳（`message()` 拋出或序列化失敗）屬於本機問題，維持中立。
