# 設計決策

Defjs 圍繞著一個核心邊界建構：**SDK 定義通訊契約；取用端應用程式掌控請求執行。** `@defjs/core` 中的所有設計原則皆源自這項分離。

## 1. 定義 vs. 執行

SDK 套件匯出各項操作（`defineRequest`、`defineEventStream`、`defineWebSocket`）與資料契約（`struct`）。它絕不呼叫 `createClient`、不儲存全域 Singleton Client，也不會讀取環境變數。

<Tabs items={["sdk/orders.ts", "app/consumers.ts"]}>
<Tab value="sdk/orders.ts">

```ts
import { defineRequest, struct } from "@defjs/core";

export const Order = struct.object({
  id: struct.number(),
  status: struct.string(),
});

export const getOrder = defineRequest({
  method: "GET",
  path: "/orders/:id",
  operation: "orders.read",
  input: struct.object({ id: struct.number() }),
  builder: (input) => ({ path: input }),
  output: Order,
});
```

由於 `getOrder` 完全不捕捉任何 Client 狀態：

- 瀏覽器前端、背景工作任務、SSR 請求處理常式與單元測試，都能使用各自的 `Client` 設定呼叫同一個 `getOrder` 定義。
- 框架外掛（`@defjs/react`、`@defjs/vue`）與可觀測性中介層（`@defjs/opentelemetry-server`）只掛載在應用程式的 `Client` 上，讓發布的 SDK 套件保持 100% 零依賴。

## 2. 明確的輸入放置與雙向欄位別名

在 Defjs 中，`input` 宣告呼叫端應傳入什麼值，`struct` 控管值如何編碼與解碼，而 `builder` 則負責將每個值精確放置到請求的各個部分（`path`、`query`、`headers`、`body`）。

- **無隱式推論**：只要操作宣告了 `input`，就必須提供一個明確、同步且純粹的 `builder`。欄位放置位置絕不會從參數名稱隱式猜測。
- **雙向 `.alias(wireName)`**：在 struct 欄位上宣告 `.alias("customer_name")`，讓 TypeScript 程式碼保持慣用的 `customerName`，同時在網路通訊時自動完成對應 `"customer_name"` 的雙向轉換。

當 builder 將具型別的 struct 物件傳遞給 `body`、`query` 或 `headers` 時，其欄位別名以及 `Date` / `bigint` 編解碼器會自動生效。而在匿名包裝物件中直接撰寫的鍵名（例如上面的 `account_id` 或 `x-api-version`）則會如實保留。

## 3. 宣告即斷言 [#declaration-is-an-assertion]

Defjs 依循六項嚴格的規則來讀取與處理 HTTP 回應：

### 規則 1：宣告什麼，就斷言什麼

`output` 斷言 `2xx` 回應本文的結構；`error` 斷言非 `2xx` 回應本文的結構。型別宣告是一項執行時期的硬性保證，而非盡力而為的提示。

### 規則 2：`ok` (`200..299`) 是唯一的分歧點

`2xx` 回應一律只使用 `output` 進行解碼；所有其他狀態碼（`3xx`、`4xx`、`5xx`）一律只使用 `error` 進行解碼。Defjs 絕不會在兩者之間互相 fallback。

### 規則 3：任何違反宣告的情況都會明確報錯

Defjs 用 `response.ok` 選擇回應的一側：`2xx` 用 `output`，非 `2xx` 用 `error`。只有在這一側宣告了 JSON struct，才會觸發解碼，並可能產生 `RES_MEDIA_TYPE_INVALID` 或 `RES_DECODE_FAILED`；它的 `Content-Type` 會在讀取 body 位元組**之前**驗證。非 `2xx` 的 HTML 閘道頁只有在宣告了 JSON `error` struct 時才會產生 `RES_MEDIA_TYPE_INVALID`。作用中的一側沒有宣告時，不會讀取 body；非 `2xx` 回應會回傳未解碼的 `HTTP_STATUS`。

| 讀取回應時發生的失敗情況                   | 回傳的 Fault 錯誤碼                                            |
| ------------------------------------------ | -------------------------------------------------------------- |
| 媒體型別不符合宣告的 JSON 格式             | `RES_MEDIA_TYPE_INVALID`（完全不讀取本文串流）                 |
| 位元組無法以宣告的表示法解碼               | `RES_DECODE_FAILED`                                            |
| 解碼後的值未通過 `struct` 結構驗證         | `RES_STRUCT_MISMATCH`（HTTP）/ `RES_DECODE_FAILED`（SSE 交握） |
| 非 `2xx` 狀態碼且成功解碼出 `error` struct | `HTTP_STATUS`，並帶有具型別的 `error.data`                     |
| 非 `2xx` 狀態碼但未宣告 `error`            | `HTTP_STATUS`，且 `error.data: undefined`                      |

### 規則 4：解碼失敗的回應沒有本文

只有在通過解碼與驗證後，本文才會存在。當解碼失敗時，錯誤物件中的 `response` 型別為 `HttpMeta`（不包含 `body` 屬性），而實際的剖析或驗證錯誤會附加在 `fault.cause` 上。

### 規則 5：省略任一側即代表選擇不讀取

省略 `output` 代表完全不讀取 `2xx` 回應本文；省略 `error` 代表完全不讀取非 `2xx` 回應本文——即使伺服器在 `500` 時傳送了無效的 JSON 也是如此。

### 規則 6：`3xx` 不是成功狀態碼

`ok` 代表 `200 <= status < 300`。`304 Not Modified` 屬於非 `2xx` 狀態：你可以不宣告 `error` 並以 `HTTP_STATUS` 進行處理（或在 ETag 攔截器中攔截 `304`），或者在預期為空字串本文時宣告 `struct.string()`。

## 4. 針對傳輸協定特化的結果 Tuple

這三種傳輸協定都回傳三元素 error-first tuple，呼叫端無須使用 try-catch：

- **HTTP** → `[error, data, response]` — 解碼後的負載 + `DecodedResponse<T>`（省略 `output` 時為 `HttpMeta`）。
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + 初始交握快照。
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + 初始連線快照。

Client 僅保存設定，不持有活躍連線。發起 HTTP 請求、SSE 串流或 WebSocket 工作階段的呼叫端，擁有取消或關閉該連線的責任（HTTP 使用 `AbortSignal`；SSE 與 WebSocket 使用 `await using` 或 `.close()` + `await .closed`）。
