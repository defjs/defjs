# 核心架構

Defjs 圍繞著一個核心邊界建構：**SDK 定義通訊契約；取用端應用程式掌控請求執行。** `@defjs/core` 中的所有設計原則皆源自這項分離。

## 1. 定義 vs. 執行

SDK 套件匯出各項操作（`defineRequest`、`defineEventStream`、`defineWebSocket`）與資料契約（`struct`）。它絕不呼叫 `createClient`、不儲存全域 Singleton Client，也不會讀取環境變數。

由於 `getOrder` 完全不捕捉任何 Client 狀態：

- 瀏覽器介面、背景工作、SSR 請求處理常式與單元測試，都能以各自的 `Client` 設定呼叫同一個 `getOrder` 操作。
- 框架外掛（`@defjs/react`、`@defjs/vue`）與可觀測性中介層外掛（`@defjs/opentelemetry-server`）只掛在應用程式的 `Client` 上，讓發布的 SDK 套件保持 100% 零依賴。

## 2. 明確的輸入放置與雙向欄位別名

在 Defjs 中，`input` 宣告呼叫端要傳入什麼值，`struct` 控管值如何編碼與解碼，而 `builder` 負責把每個值放到請求的哪個位置（`path`、`query`、`headers`、`body`）。

- **沒有魔法推論**：只要操作宣告了 `input`，就必須提供明確、同步且純粹的 `builder`。欄位放置位置絕不會從參數名稱猜測。
- **雙向 `.alias(wireName)`**：在 struct 欄位上宣告 `.alias("customer_name")`，TypeScript 端就能保留 `customerName`，同時在傳輸時自動雙向對應 `"customer_name"`。

## 3. 宣告即斷言 [#declaration-is-an-assertion]

Defjs 依循六項嚴格的規則來讀取與處理 HTTP 回應：

### 規則 1：宣告什麼，就斷言什麼

`output` 斷言 `2xx` 回應本文的結構；`error` 斷言非 `2xx` 回應本文的結構。宣告是執行時期的保證，不是盡力而為的提示。

### 規則 2：`ok` (`200..299`) 是唯一的分歧點

`2xx` 回應只會用 `output` 解碼；其他所有狀態碼（`3xx`、`4xx`、`5xx`）只會用 `error` 解碼。Defjs 絕不會從一側回退到另一側。

### 規則 3：任何違反宣告的情況都會明確報錯

Defjs 用 `response.ok` 選擇回應的一側：`2xx` 用 `output`，非 `2xx` 用 `error`。只有在該側宣告了 JSON struct，才會觸發解碼，並可能產生 `RES_MEDIA_TYPE_INVALID` 或 `RES_DECODE_FAILED`；它的 `Content-Type` 會**先**驗證，在讀取或尋找本文之前。沒有內容的回應（`HEAD`、`204`、`205`、`304`）也要通過同樣的檢查：宣告了 JSON 表示法卻沒有 JSON `Content-Type` 時，會以 `RES_MEDIA_TYPE_INVALID` 失敗；有的話，則會剖析空位元組並以 `RES_DECODE_FAILED` 失敗。非 `2xx` 的 HTML 閘道頁面只有在宣告了 JSON `error` struct 時，才會產生 `RES_MEDIA_TYPE_INVALID`。該側沒有宣告時就不會讀取本文；非 `2xx` 回應會回傳未解碼的 `HTTP_STATUS`。SSE 交握遵循相同規則：非 `2xx` 交握若無法解碼已宣告的 `error` 本文，啟動時會回傳該解碼 fault，狀態碼放在其中繼資料裡；攔截器、重連策略，以及重連的 `closed` 仍會看到 `HTTP_STATUS`。

| 讀取回應時發生的失敗情況                   | 回傳的 Fault                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------ |
| 媒體型別不符合宣告的 JSON 格式             | `RES_MEDIA_TYPE_INVALID`（最先檢查；本文完全不會被讀取，有沒有內容都沒有差別） |
| 位元組無法以宣告的表示法解碼               | `RES_DECODE_FAILED`（包含空的 JSON 位元組）                                    |
| 解碼後的值未通過 `struct` 結構驗證         | `RES_STRUCT_MISMATCH`                                                          |
| 非 `2xx` 狀態碼且成功解碼出 `error` struct | `HTTP_STATUS`，並帶有具型別的 `error.data`                                     |
| 非 `2xx` 狀態碼但未宣告 `error`            | `HTTP_STATUS`，且 `error.data: undefined`                                      |

### 規則 4：解碼失敗的回應沒有本文

本文只有通過解碼與驗證後才會存在。解碼失敗時，fault 的 `response` 型別為 `HttpMeta`（沒有 `body` 屬性），而實際的剖析或驗證錯誤則掛在 `fault.cause` 上。

### 規則 5：省略任一側即代表選擇不讀取

省略 `output` 代表完全不讀取 `2xx` 回應本文；省略 `error` 代表完全不讀取非 `2xx` 回應本文——即使伺服器在 `500` 時送出了無效的 JSON 也一樣。

### 規則 6：`3xx` 不是成功狀態碼

`ok` 代表 `200 <= status < 300`。`304 Not Modified` 屬於非 `2xx` 狀態：可以不宣告 `error` 並處理 `HTTP_STATUS`（或在 ETag 攔截器中攔截 `304`），也可以在預期會收到空的文字本文時宣告 `struct.string()`。

## 4. 依傳輸協定設計的結果 Tuple

三種傳輸協定都回傳三元素 error-first tuple，而不是在呼叫端拋出例外：

- **HTTP** → `[error, data, response]` — 解碼後的酬載 + `DecodedResponse<T>`（省略 `output` 時為 `HttpMeta`）。
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + 初始交握快照。
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + 初始連線快照。

Client 只保存設定，不持有進行中的連線。發起 HTTP 請求、SSE 串流或 WebSocket 工作階段的呼叫端，負責取消或關閉它（HTTP 使用 `AbortSignal`；SSE 與 WebSocket 使用 `await using` 或 `.close()` + `await .closed`）。
