# WebSocket

SDK 作者透過 `defineWebSocket` 描述連線輸入、接收和傳送訊息的 Struct 與傳輸限制。應用程式用自己的 Client 開啟 session，收發具型別的訊息，並決定心跳、重連和工作生命週期。

啟動、接收、傳送後，用 `await using` 釋放 session，或手動 `close()` 並等待 `closed`。取消訂閱和資源釋放屬於呼叫端；Client、provider、interceptor 不會自動關閉成功回傳的 session。

## 每個方向一個 struct

`incoming` 是每一個文字 frame 的一個 struct。`outgoing` 是 `session.send(...)` 的一個 struct。多種訊息用 `struct.discriminatedUnion`。那些欄位上的 alias 就是雙向的 wire 名稱。沒有另外的 type envelope，也沒有 normalizer。

```json
{ "type": "message", "text": "Hello" }
```

進來的文字、`ArrayBuffer`、typed-array、`Blob` frames 會讀成 UTF-8，再 JSON parse，然後對 `incoming` 檢查。畸形 JSON 與 struct 失敗走 `session.onRuntimeError`，而且不會進 queue。Session 維持開著。不是文字、bytes 或 `Blob` 的 frames 會被忽略。沒有 `withWebSocketOnInvalidEvent`。

`session.send(...)` 同步驗證並序列化：先 struct encode，再 `JSON.stringify`。Open 時立刻送；有啟用 outgoing queue 時，在 `reconnecting` 期間會排隊；不可寫時丟 `InvalidStateError`。沒有 outgoing struct、payload 驗證失敗、停用／滿的 outgoing queue，或原生 send 失敗時也會 throw。定義上的靜態 `protocols` list 是 endpoint 契約（例如 `graphql-transport-ws`）。Execute options 與 `withWebSocketProtocols` 仍可覆寫它。只有這些 options 能選 subprotocols：builder、`beforeConnect` 與 interceptors 都改不了，所以把 token 放進 subprotocol 時，要在該次呼叫以 execute 的 `protocols` option 傳入。Builder 只能回傳 `path` 與 `query`。

Struct 編碼之後，JSON 無法忠實表示的值會在送出或進入重連佇列之前丟出 `TypeError`：非有限數字、函式、symbol、`Map`、`Set`、串流，以及沒有 JSON 表示的類別實例。巢狀值跟 HTTP JSON body 同一套規則。`struct.number()` 仍然接受 infinities 並拒絕 `NaN`；在 struct 層被接受，不代表它是有效的 JSON。Heartbeat 用同一個 serializer；它的序列化失敗會結束邏輯 session。

`receive` 是單消費者。要求第二個 iterator 會丟出 `TypeError`。

## State 快照

| Member                     | 意義                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------- |
| `state`                    | `idle`、`connecting`、`open`、`reconnecting`、`closing`、`closed`、`aborted` 或 `error` |
| `connection`               | 最新實體連線：`generation`、URL、協商到的 protocol、可用時的 extensions                 |
| `bufferedAmount`           | 原生未送出的 byte 數；沒有實體 socket 時是 `0`                                          |
| `receive`                  | 單消費者的 async iterable，產出已驗證的進來訊息                                         |
| `onStateChange(listener)`  | 訂閱邏輯 state 轉換；回傳 unsubscribe                                                   |
| `onRuntimeError(listener)` | 訂閱非啟動的 runtime 錯誤；回傳 unsubscribe                                             |
| `closed`                   | 邏輯終端 close 結果的 Promise                                                           |

`open` = 實體 socket 已開。`reconnecting` 包含替換前的準備 + delay。`connection.generation` 在每個到達 `open` 的實體 socket 遞增。`session.connection` 會在重連時更新。只有 Defjs 原生 session，或直接傳遞同一 live `connection` 物件的 wrapper，tuple 的 `startupConnection` 才會保留首次成功連線的快照。自訂 session 或轉換 `connection` 的 wrapper，則以回傳 session 目前公開的 `connection` 為準。共用 `closed` 不能略過 URL 清理或中繼資料過濾，Defjs 也不會從任意轉換重建首次連線的中繼資料。

啟動失敗 → `[error, undefined, connection?]`。開之前的 constructor 失敗可能沒有 connection；啟動期間逾時／close 仍可能提供快照。Session 回傳後，runtime 錯誤走 observers、`receive`、`closed` — 不是第二次 execute tuple。

## 重連

重連是選擇性開啟。沒有 `reconnect` 物件 → 實體 close 結束邏輯 session。設定後，預設是 `attempts: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0`。`attempts` 是每次斷線的重試預算；成功的 `open` 會重設預算與 backoff 指數。因此之後每一次斷線都從 retry 1 與 `delayMs` 基底重新開始。`attempts: 0` 關掉。預設 predicate 接受該次斷線預算內的每一個非手動 close 結果。反覆成功的 open 沒有終身重試上限。socket 若成功開啟後立刻又被伺服器關閉，可能持續以基底延遲重新連線（仍受 jitter 與上限約束），因為每次開啟都會重設預算；請用 `shouldReconnect` 停止這種情況。

<include cwd>examples/web-socket/reconnect.ts#example</include>

`shouldReconnect` 拿到下一次重試 attempt、close cause、code、reason、`wasClean`。手動 `session.close(...)` 不會進 predicate。Preparation／策略 throw 會以錯誤結束邏輯 session。

WebSocket backoff jitter 是**乘法**（`jitter: 0.2` 會在捨入前，把已設上限的基底縮放成 `0.8x`–`1.2x`）。最終延遲會再次被 `maxDelayMs` 與平台 timer 上限 `2_147_483_647` ms 卡住，所以那個範圍的上端可能被截掉。基底為零就維持零；有效數字的溢位會被夾住，而不是丟出錯誤。SSE 用同一套 0–1 jitter 規則。重連選項會在 constructor 之前驗證：`attempts` 是非負的 safe integer；`delayMs` 必須是非負有限數；`maxDelayMs` 可以是非負有限數或正 `Infinity`，後者移除設定上限，但最終等待仍不超過 `2_147_483_647` ms；`factor` 是有限且為正；`jitter` 是有限且落在 0–1。無效的值會回傳 `REQ_OPTIONS_INVALID`。WebSocket 的 `attempts: 0` 停用後續重試，但所有明確提供的重連欄位仍會在首次連線前驗證，與 SSE 一樣。

`beforeConnect({ attempt, signal })` 在初始 constructor 與每次重連前跑。把它的 signal 傳進 token refresh，讓取消同時停掉 prep 與 connect。

## Heartbeat

在 execute 或 client 範圍選擇性開啟。Interval 透過 outgoing struct 送 `message()`。選填的 `isAck(message)` 辨識 ack — 該訊息會清 timeout，且**不會**交付給 `receive`。

<include cwd>examples/web-socket/heartbeat.ts#example</include>

`intervalMs` 與 `timeoutMs` 必須是正的 finite timers，且 ≤ `2_147_483_647`。Heartbeat 訊息必須對 outgoing struct 有效。序列化、原生 send、ack 分類、逾時失敗對邏輯 session 是致命的 — 不會變成一般重連。

## Queues

| 設定                   | 必要值                            | 行為                                                                                           |
| ---------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------- |
| `maxIncomingQueueSize` | 正的 safe integer                 | 限制等著 `receive` 的已剖析訊息，以及等著 transform 的 raw frames。Overflow → `state: 'error'` |
| `maxOutgoingQueueSize` | 選填的非負 safe integer；預設 `0` | 只在 `state === 'reconnecting'` 時 FIFO。滿／停用 → `send(...)` throw                          |

排隊的 outgoing frames 會在替換 socket 發佈 `open` 前 flush。已在較早 socket 送出的 frames 不會自動重放。重連 queues 是給你在重連期間送出的訊息 — 不是重建應用狀態用。

進來的 overflow 會清掉 pending sequence、讓 `receive` 失敗、停掉 session，並以 `kind: 'error'` resolve `session.closed`。讓消費者夠快，或依量測到的大小／記憶體提高上限。

## Protocols 與認證

定義的 `protocols`、client 的 `withWebSocketProtocols(...)`、execute 的 `protocols` 設定 constructor subprotocol list。優先序：execution → client → definition。第一個定義的 list 會複製給邏輯 session，並在重連時重用。

瀏覽器 WebSocket constructors 不接受任意 handshake headers，而且 builder 不能回傳 `headers` 或 `body`。Defjs 把 `http:` → `ws:`、`https:` → `wss:`，path placeholders encode 一次，並使用跟 HTTP 一樣的 query 規則：預設是 scalars 與重複的 keys，巢狀物件用 `withQuerySerializer`，沒有 query 時不呼叫 serializer。

跟 HTTP 與 SSE 一樣，缺少、相對或無效的 base endpoint，或非法 path，會在建構期間、任何 interceptor 或傳輸跑之前以 `REQ_BUILD_FAILED` 失敗，即使 interceptor 本來會 short-circuit 也一樣。解析後的 URL 必須維持 base 的 origin，並留在其目錄之下；path 裡的 C0 控制字元（包括 tab、CR 與 LF）、反斜線、`?`、`#` 與目錄跳脫都會被拒絕。即使前面有空格，類似 scheme 或 protocol-relative 的形式仍會被拒絕；路徑內的一般空格則允許使用，並以 `%20` 送出。Interceptor 最終的 `req.endpoint` 會按其最終的 `req.baseEndpoint`、用同一條規則驗證，但它可以刻意把 base 換成另一個有效的絕對 URL。確定性的 URL 錯誤絕不會重試。

`withCredentials(true)` 是 HTTP／SSE 的 Fetch credentials — 不是 WebSocket auth。用審過的 cookie／session 策略、subprotocol，或短效 connection ticket。別把一般憑證或長效 secrets 放進 query string。

## 關閉與擁有權

`session.close(code?, reason?)` 請求終端關閉並停掉 heartbeat。Code 必須是 `1000` 或 `3000..4999`；reason ≤ 123 UTF-8 bytes。無效的 close 參數會在改 state 前 throw。需要手動 close reason 或邏輯終端結果時，搭配 `await session.closed` 使用。

傳給 `execute` 的 `signal` 或 `abort` 會一直附著在已開啟的 session 上。逾時形狀的 abort（`TimeoutError` 或 `ERR_TIMEOUT`）會以 `'error'`（`NET_TIMEOUT`）結束。其他 reason 則以 `'aborted'` 結束，而且 `receive` 會以該 reason 本身 reject，不是新的 `AbortError`。`timeout` 只是啟動期限。

</include>

`session.closed` 是邏輯終端快照：`'closed'`、`'aborted'` 或 `'error'`，可帶選填的原生 `code`／`reason`／`wasClean`，以及 aborted／error 的 `cause`。觀察到的原生 close 欄位勝過擁有者請求的 fallback。

標準 async disposer 會要求 best-effort 原生 close，再等待 Defjs 自有 lifecycle、message pump、timers、listeners、queues 與 socket references teardown。若一秒內始終沒有觀察到 close event，teardown 會被強制完成，disposer 可能用名為 `TimeoutError` 的 `DOMException` reject；這無法證明實體 TCP 連線已經關閉。重複呼叫 disposer 會共用同一個 teardown。結構化實作 session 的程式碼現在必須提供同一份 `[Symbol.asyncDispose](): PromiseLike<void>` 契約。

## GraphQL 邊界

Defjs 提供一個 incoming struct、一個 outgoing struct，以及邏輯 session 生命週期。它**不會**實作 WebSocket 應用協定。GraphQL-over-WebSocket 功能 — connection init、operation IDs、`next`／`error`／`complete`、disposal、subscription replay — 都在核心契約之外。

伺服器要求該協定時，用像 `graphql-ws` 這類協定 client，或用 `defineWebSocket(...)` 建模 frames。把 `graphql-transport-ws` 這類靜態 subprotocol 放在 `protocols` 上。單靠 struct 協商不出 GraphQL 語意。
