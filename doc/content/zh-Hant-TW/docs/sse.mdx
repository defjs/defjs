# SSE 事件串流

SDK 開發者使用 `defineEventStream` 宣告 Server-Sent Events 端點：指定路徑、選用的 input 與 builder、定義事件 struct 對照表的 `events` 物件，以及緩衝區與佇列大小上限。取用端應用程式則在 Client 上設定身分驗證與選用的自動重連機制，開啟串流、迭代接收具型別的事件，並負責最終關閉串流。

## 1. 定義事件串流並使用它

開啟的 `EventStreamHandle` 務必使用 `await using`（或在 `finally` 區塊中使用 `stream.close()` + `await stream.closed`）進行釋放：

<Tabs items={["sdk/orders-stream.ts", "app/watch-orders.ts", "Single-file quick look"]}>
<Tab value="sdk/orders-stream.ts">

```ts
import { defineEventStream, struct } from "@defjs/core";

export const watchOrders = defineEventStream({
  path: "/orders/events",
  operation: "orders.watch",
  events: {
    updated: struct.object({
      id: struct.number(),
      status: struct.string(),
    }),
  },
});
```

</Tab>
<Tab value="app/watch-orders.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { watchOrders } from "../sdk/orders-stream.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, stream] = await watchOrders(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = stream;
  for await (const event of active) {
    console.log(event.event, event.data.id, event.data.status);
    break;
  }
}

void main();
```

## 2. 開啟連線交握與 Tuple 結構

呼叫該操作僅會在初始 HTTP 回應為 `2xx`、媒體型別為 `text/event-stream` 且帶有可讀取本文時，才會成功解析為 `[error, stream, startupOpen]`：

- **非 `2xx` 交握失敗**：回傳 `HTTP_STATUS`（若定義中宣告了 `error` struct，則會包含解碼後的 `error.data`）。
- **Content-Type 錯誤或本文無法讀取**：回傳 `RES_MEDIA_TYPE_INVALID` 或 `RES_DECODE_FAILED`。
- **`startupOpen` vs. `stream.open`**：Tuple 中的第三項（`startupOpen`）保存首次交握成功的靜態快照；而 `stream.open` 則會在串流後續重新連線時即時更新。

## 3. 事件分派與解碼

當 SSE 封包抵達時（根據 WHATWG 規範以連續空行結尾）：

1. **事件路由**：網路傳送的 `event:` 欄位會比對 `events[eventName]`；若未比對成功，則會降級使用宣告的 `events.default`。省略 `event:` 欄位時，事件名稱預設為 `"message"`。未宣告且無 `events.default` 的未知事件會被自動忽略。
2. **負載解碼**：`struct.string()` schema 會直接接收原始文字 `data:`；所有其他 struct 種類都會先將 `data:` 剖析為 JSON，接著再透過 struct 進行結構驗證。
3. **觀察無效事件**：無效或未宣告的事件會被丟棄，而不會中斷整個串流。可以在 Client 上掛載 `withSSEOnInvalidEvent(...)` 以進行受控的診斷：

## 4. 重新連線與 Last-Event-ID [#reconnect]

SSE 的自動重新連線機制屬於**選擇性啟用（opt-in）**。若未設定 `withSSEReconnect(...)`，任何網路斷線或串流讀取錯誤都會直接終止串流。

<include cwd>examples/sse/reconnect.ts#example</include>

- **斷線重試預算（`attempts`）**：傳入設定物件至 `withSSEReconnect` 時，預設為 `3` 次。交握成功後會重設重試次數與退避指數。伺服器正常的 EOF 結束**不屬於**失敗，不會觸發重新連線。
- **游標追蹤（`Last-Event-ID`）**：在事件結尾的空白行完成剖析時確認並提交，重新連線時會自動作為 `Last-Event-ID` 標頭送出。
- **冪等安全性**：預設情況下，只有冪等方法（`GET`、`HEAD`、`OPTIONS`、`PUT`、`DELETE`）會自動重新連線。非冪等方法（`POST`、`PATCH`，例如 LLM 串流生成請求）只有在自訂 `shouldReconnect` 回呼明確回傳 `true` 時才會重連。使用 `ReadableStream` 請求本文的請求在第一次嘗試時即會消耗串流，因此絕不會重連。
- **交握逾時（`connectTimeoutMs`）**：限制從呼叫 Fetch 到接收回應標頭之間的交握時間，而不會限制已建立串流的存活時長。

## 5. 緩衝區與佇列上限

兩項上限值皆必須為大於零的安全整數。超過任一上限皆屬於嚴重錯誤（`stream.closed` 會以 `kind: "error"` 解析且迭代器會被拒絕——事件絕不會被靜默丟棄）：

| 定義選項        | 限制項目                                  | 致命錯誤碼            |
| --------------- | ----------------------------------------- | --------------------- |
| `maxBufferSize` | 遇到空行前未完成或過大的 SSE 封包位元組數 | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`  | 等待 `for await` 消費端處理的已驗證事件數 | `CAP_QUEUE_OVERFLOW`  |
