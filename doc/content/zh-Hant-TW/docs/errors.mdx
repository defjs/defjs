# 錯誤

SDK 作者在定義中描述錯誤 body 的 Struct，應用程式在呼叫點保留對狀態與故障的判斷。例如，HTTP 宣告的錯誤 body 成功解碼後，`HTTP_STATUS` 的 `data` 具有型別；取消、逾時和解碼失敗仍使用 Defjs 的 fault 契約。

處理 404、逾時或讀不出來的 body，靠的是讀取 error-first tuple。`Fault` 是原生 `Error`（`instanceof Error` 為真），由欄位 `code` 判別。

沒有 `kind`。失敗的類別就是 code 裡第一個 `_` 之前那一段，所以 `NET_TIMEOUT` 是 `NET` 類失敗，`RES_STRUCT_MISMATCH` 是 `RES` 類失敗。粗分看前綴，精確判斷看整個 code。

## 穩定的 code

| 類別   | Code                                                                   | 誰得改                         |
| ------ | ---------------------------------------------------------------------- | ------------------------------ |
| `HTTP` | `HTTP_STATUS`                                                          | 對端回了非 2xx；當業務邏輯處理 |
| `REQ`  | `REQ_INPUT_INVALID`、`REQ_OPTIONS_INVALID`、`REQ_BUILD_FAILED`         | 呼叫方，或端點宣告             |
| `NET`  | `NET_ABORTED`、`NET_TIMEOUT`、`NET_UNREACHABLE`、`NET_BODY_INCOMPLETE` | 沒人，或者重試                 |
| `RES`  | `RES_MEDIA_TYPE_INVALID`、`RES_DECODE_FAILED`、`RES_STRUCT_MISMATCH`   | 宣告和對端得對上               |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`、`EXT_HOOK_FAILED`、`EXT_OBSERVER_FAILED`     | 你掛到流水線上的程式碼         |
| `CAP`  | `CAP_BUFFER_EXCEEDED`、`CAP_QUEUE_OVERFLOW`                            | 宣告的上限，或者消費方的節奏   |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | 宿主執行環境                   |

集合是故意封閉的：這正是 `switch` 能窮盡的原因。擴充要報自己的細節就走 `cause`，不是加新 code。

HTTP、SSE 與 WebSocket 都需要有效的絕對 client `endpoint`。URL 解析之後，path 必須留在 base endpoint 的 origin 與目錄之內。絕對 URL、protocol-relative path、C0 控制字元（包括 tab、CR 與 LF）、反斜線、`?`、`#` 以及目錄跳脫都會被拒絕。即使前面有空格，類似 scheme 或 protocol-relative 的形式仍會被拒絕；路徑內的一般空格則允許使用，並以 `%20` 送出。缺少、相對或無效的 endpoint，以及非法 path，會在建構請求時、interceptor 跑之前產生 `REQ_BUILD_FAILED`；short-circuit interceptor 繞不過這項檢查。傳輸之前，interceptor 最終的 `req.endpoint` 會按其最終的 `req.baseEndpoint`、用同一套規則檢查；明確切到另一個有效的絕對 base 是允許的。這些確定性的 URL fault 不可重試。

### 各形狀帶哪些欄位

| Code          | `status` | `response`                                         | `data`                                |
| ------------- | -------- | -------------------------------------------------- | ------------------------------------- |
| `HTTP_STATUS` | 總是有   | 總是有；只有宣告過 `error` 且解碼成功時才帶 `body` | 解碼後的 `error` body，或 `undefined` |
| `RES_*`       | 總是有   | 總是有，只有 metadata——**沒有 `body`**             | 沒有                                  |
| 其餘一切      | 沒有     | 只有傳輸層當時已經拿到 metadata 時才有             | 沒有                                  |

`cause` 帶著底層的值：struct 不匹配時是 `StructError`，表示讀不出來時是 parser 的失敗，擴充丟什麼就是什麼。

HTTP 失敗時第三項是 `undefined`：當時存在的回應 metadata 已經由 fault 帶著了。這一點重要，因為你傳給 handler、寫 log、重新丟出的就是 fault，所以 metadata 必須跟著它走，而不是擺在它旁邊。

SSE 與 WebSocket 的第三項是啟動快照，即使啟動失敗也可能有。handle 或 session 回來之後，後續的失敗活在它自己的生命週期上——它們絕不改寫已經定下來的啟動 tuple。

## body 怎麼讀

`ok` 是唯一分流點，而且只有一邊會解碼。`output` 讀 2xx body；`error` 讀其餘一切。省略哪個，那個 body 就根本不會被讀。

| 情況                                  | 結果                                           |
| ------------------------------------- | ---------------------------------------------- |
| 2xx，宣告過 `output`，body 解碼成功   | 成功；`data` 與 `response.body` 都有型別       |
| 2xx，省略了 `output`                  | 成功；`data` 是 `undefined`，回應沒有 `body`   |
| 非 2xx，宣告過 `error`，body 解碼成功 | `HTTP_STATUS`，`data` 有型別                   |
| 非 2xx，省略了 `error`                | `HTTP_STATUS`，`data: undefined`               |
| 媒體類型不是那個表示需要的            | `RES_MEDIA_TYPE_INVALID`，在讀 body **之前**報 |
| bytes 不是那個表示                    | `RES_DECODE_FAILED`                            |
| 值不符合那個 struct                   | `RES_STRUCT_MISMATCH`（僅 HTTP）               |
| 你**沒有**宣告的那一側 body 讀不出來  | 整個忽略——見下                                 |

最後一列值得記住。如果你宣告了 `output` 而沒宣告 `error`，那麼一個 body 是壞 JSON 的 500，報出來是 `HTTP_STATUS` 加 `status: 500`。你說過你不在乎錯誤 body，這也包括不在乎它讀不出來這件事。

對於 HTTP，Struct 只套用一次，而且在 interceptor 鏈之後。Interceptor 用 `makeResponse(...)` 造的回應，和線上來的走同一套媒體類型檢查、表示轉換與 Struct。內建的 Fetch 傳輸在把回應交回鏈之前，會把已宣告的 body 讀成 JSON、文字、`Blob` 或 bytes。只有 JSON 表示才要求 JSON 媒體類型與 `JSON.parse`；非 JSON 的文字、blobs 與 bytes 對其宣告的表示是有效的。讀取失敗適用於每一種表示；那裡的讀取或剖析失敗會以同樣的 `RES_*` 或 `NET_BODY_INCOMPLETE` fault 回報。

`HttpResponse.ok` 只表示 `200 <= status < 300`。傳輸失敗是 fault，絕不是回應——不存在代表它的 status-0 回應。

## 窄化錯誤 body 的聯集

一個 `error` struct 覆蓋所有非 2xx 狀態，所以形狀不同時你會宣告一個聯集。之後你能拿 `fault.data` 做什麼，完全取決於你怎麼宣告這個聯集——函式庫交還給你的，正是你要求的那個型別。

`struct.or(...)` 產出一個普通聯集，TypeScript 自己窄化不了。去測你要的那個欄位：

</include>

`struct.discriminatedUnion(...)` 按 body 真正帶著的欄位窄化。API 本身已經給錯誤打了標籤時，這是最舒服的寫法：

  examples/errors/narrow-by-kind.ts#example
</include>

當 API 把狀態放在 body **裡面**時，就按它窄化，而不是按 `fault.status`：

<include cwd lang="typescript">
  examples/errors/narrow-by-status.ts#example
</include>

只要 API 支援，最後這種寫法值得優先。`fault.status` 是 HTTP 層的數字，proxy、閘道器或 CDN 都能改寫它；`data.status` 通過了你所宣告的 `error` struct 驗證。這證明的是 body 的形狀，不是後端出處：proxy、閘道器或 CDN 也能回傳一份相符的 body。

一個不帶判別欄位、因此窄化不了的聯集，是宣告本身的性質，不是函式庫的——函式庫交給你的就是你宣告的型別。想要窄化，就給 struct 加一個判別欄位。

## 啟動期與開啟之後

SSE 在 resolve handle 之前會驗證狀態、`text/event-stream` 以及 body 是否存在。非 2xx → 在省略 `error` 或其 body 解碼成功時是 `HTTP_STATUS`。已宣告的握手 body 讀不出來、剖析失敗，或 Struct 失敗，會產生 `RES_DECODE_FAILED`；Struct 失敗時 `cause` 是 `StructError`。媒體類型不對 → `RES_MEDIA_TYPE_INVALID`。成功的握手卻沒有 body → `RES_DECODE_FAILED`。開啟快照照樣可能落在 tuple 第三項。

WebSocket 的啟動期覆蓋握手加第一次實體 open。建構器失敗、open 之前就關閉、逾時或取消，都會產出一個啟動 tuple。即使 socket 從沒到過 `open`，連線快照也可能存在。

| 傳輸      | 啟動之後                                                                                                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE       | 致命錯誤時 iterator reject；`stream.closed` 以 `kind: 'error'` 和對應的 fault `code` resolve                                                                                                      |
| WebSocket | 訊息／佇列／心跳失敗走 `onRuntimeError`；終止性錯誤讓 `receive` 失敗；`session.closed` → `kind: 'closed' \| 'aborted' \| 'error'`                                                                 |
| HTTP      | 執行時的 Promise 只會確定結果一次，結果為 tuple。攔截器拋出錯誤、回傳非 `HttpResponse` 的結果，或進度回呼拋出錯誤時，都會在 tuple 中回傳 fault（`EXT_INTERCEPTOR_FAILED`、`EXT_OBSERVER_FAILED`） |

`NET_ABORTED` / `NET_TIMEOUT` 描述的是呼叫方在啟動期看到了什麼。回傳給你的 stream 或 session，你照樣要關掉並 await 它的終態 promise。

## 原生 Error 的 log 與 cause

Fault 是原生 `Error` 實例，所以不需要診斷 adapter。`String(fault)` 給出穩定的原生形式 `DefjsFault: <message>`。`code` 和各變體欄位——`status`、`response`、`data`——保持可列舉，方便結構化 log；`name` 和原生 `cause` 鏈是不可列舉的。

<include cwd lang="typescript">
  examples/errors/log-fault.ts#example
</include>

呼叫 `format()`、`flatten()` 或 `prettify()` 之前，先窄化 `fault.cause instanceof StructError`。這些 helper 長在 Struct 的 cause 上，不會被複製到 fault 上。不要讓控制流去解析 `message` 或 `String(fault)`——契約是 `code` 和一個審過的 `status`。

預設的 Struct 訊息只點出收到的 kind，絕不包含值本身：`Expected number at email, received string`。同一段訊息會出現在 `prettify()` 與 `String(fault)`。由 JSON `SyntaxError` 造成的 `RES_DECODE_FAILED`，fault 訊息是 `Response body could not be decoded`；原始 parser 錯誤留在 `cause`。原始的 `StructIssue.received` 值與 parser cause 仍然敏感，自訂 `errorMap` 訊息會原樣使用，所以記錄前先審自訂文字。

## 參考

| 分支               | 控制流判斷                         | 好用的穩定欄位                         | 通常沒有／敏感              |
| ------------------ | ---------------------------------- | -------------------------------------- | --------------------------- |
| HTTP 狀態策略      | `fault.code === 'HTTP_STATUS'`     | `fault.status`、審過的 `fault.data`    | Body、headers、URL、`cause` |
| 呼叫方取消         | `fault.code === 'NET_ABORTED'`     | `code`                                 | 取消原因和堆疊              |
| 逾時               | `fault.code === 'NET_TIMEOUT'`     | `code`                                 | 請求 URL 和底層 cause       |
| 契約破了           | `fault.code.startsWith('RES_')`    | `code`、審過的 `fault.response.status` | Struct issue、body、輸入值  |
| 你自己的程式碼丟了 | `fault.code.startsWith('EXT_')`    | `code`、`cause`                        | 擴充掛上來的任何東西        |
| 流／工作階段執行期 | `stream.closed` / `session.closed` | 終態 `kind` 和 `code`                  | 事件負載、frame、cause      |

把 `cause`、`data`、回應 headers 和 body、URL、`StructIssue.received`、輸入值、自訂訊息和堆疊都當敏感資訊。Issue path 反映結構並保留 record 的 key：`struct.record(...)` 可能產生 `Expected number at alice@example.com, received string`，因此預設訊息、`prettify()` 與 `String(fault)` 中的 key 仍可能含有敏感資訊。預設 Struct 訊息與 `prettify()` 會省略收到的值；記錄完整 issue 或 JSON parser 的 cause 仍可能把它們暴露出來。一個保守的摘要：

<include cwd lang="typescript">
  examples/errors/summarize-fault.ts#example
</include>

`createNetworkFault`、`createPreflightFault`、`createDecodeFault`、`createHttpStatusFault` 和 `createUndecodedHttpStatusFault` 建構這些原生 Error 值。普通的請求失敗照樣在 tuple 裡回傳它們；不會因為它們繼承了原生 Error 行為就被丟出。`ERR_ABORTED` 和 `ERR_TIMEOUT` 是傳輸正規化器能認出來的共享 cause。它們帶著不可列舉的 `Symbol.for('defjs.cause.aborted')` 與 `Symbol.for('defjs.cause.timeout')` 標記，所以取消分類能跨 Core 副本運作，不依賴物件同一性。[`isAbortCause`](/zh-Hant-TW/api/core/isabortcause) 與 [`isTimeoutCause`](/zh-Hant-TW/api/core/istimeoutcause) 暴露這些檢查以及支援的平台錯誤檢查；分類 fault 的 cause 時，傳底層的 `fault.cause`。OpenTelemetry 會跨副本抑制呼叫方取消的 log，逾時則繼續記錄。
