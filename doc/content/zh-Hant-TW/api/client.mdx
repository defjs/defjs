# Client

`createClient(...)` 回傳 [`DerivableClient`](/zh-Hant-TW/api/core/derivableclient-type)。選項由左至右組合，接著呼叫 `client(options?)` 取得 [`Client`](/zh-Hant-TW/api/core/client-type) 值，再傳給操作：`getOrder(client(options), input)`。

## createClient()

<ApiSignature name="createClient" />

選項依序套用。若攔截器會以閉包捕捉 auth 或租戶（tenant），請在請求邊界內建立 client。回傳的 factory 是一個函式；呼叫它會取得 `Client` 值，不會進行 I/O。factory 本身也是 `Client`，但不帶任何 request options。

- **options** — 例如 `withEndpoint` 這類選項輔助函式。
- **回傳** 可呼叫的 factory。基礎設定由每個 client 值共用，執行時不會凍結。它靠慣例維持不變：函式庫不會改它，應用程式也不該改。

## 選項輔助函式

所有輔助函式都回傳 `ClientOption`。同一項設定，後面的呼叫會取代前面的呼叫；唯一的例外是 `withInterceptors`，它是附加。

### withEndpoint()

<ApiSignature name="withEndpoint" />

依首次出現的順序複製候選 base URL，並捨棄同一字串的後續重複項。後面的 `withEndpoint` 會整份取代清單。它不檢查 URL，也不取代平衡器。空清單是合法值，呼叫會以 `REQ_BUILD_FAILED` 失敗。

### withBalancer()

<ApiSignature name="withBalancer" />

取代後續呼叫使用的平衡器。物件以參考方式儲存。沒有這個選項時，每個 client 各自取得一個 `pickFirstBalancer()`。

### withInterceptors()

<ApiSignature name="withInterceptors" />

依註冊順序附加攔截器。混合的 kind 會在操作執行時依傳輸篩選。

### withQuerySerializer()

<ApiSignature name="withQuerySerializer" />

替換 HTTP、SSE 與 WebSocket 的 query 編碼。`serializer(query)` 收到的是**已編碼的傳輸物件**（別名已套用、`Date` 已是 ISO、`bigint` 已是字串），必須回傳不含開頭 `?` 的 query string。請求沒有 query 時不會呼叫它。builder 回傳 `URLSearchParams` 時也會跳過它。

### withHeaders()

<ApiSignature name="withHeaders" />

為 HTTP 與 SSE 請求設定靜態的預設標頭。WebSocket 請求不會用到它們。`headers` 會在選項套用時複製，所以之後修改該物件不會影響 client。第二次呼叫 `withHeaders` 會取代第一次，不會合併。

單一請求的優先順序：

1. 起始的標頭集合就是預設值。
2. 請求 builder 回傳的 `headers` 會取代同名的預設值。該名稱的第一個值取代預設；同一陣列中後面的值只會接在這次取代結果之後。純量或 `Headers` 實例同樣是取代。其他預設名稱維持不變。
3. 攔截器收到的是合併後的標頭，可以加以修改。
4. 使用 `@defjs/core/xsrf` 時，XSRF 標頭最後才加入，而且只在它仍不存在時才加入（見 `withXSRF`）。

每個請求都會變的值，請交給攔截器處理，例如重新整理後的 Bearer token，或對序列化本文計算的 HMAC。

Client 層級沒有預設期限。某次呼叫需要期限時，在衍生的 client 上傳 `signal: AbortSignal.timeout(ms)`。手動中止歸類為 `NET_ABORTED`；`AbortSignal.timeout` 歸類為 `NET_TIMEOUT`。

### withXSRF()

<ApiSignature name="withXSRF" />

為瀏覽器中的 HTTP 請求加上 XSRF token 標頭。從 `@defjs/core/xsrf` 匯入。`options` 是 `XSRFOptions`：`cookieName`（預設 `XSRF-TOKEN`）與 `headerName`（預設 `X-XSRF-TOKEN`）。不帶參數呼叫 `withXSRF()` 會啟用這些預設值；缺少 `location` 或 `document` 時（包含 Worker）會丟出錯誤。同構程式只在瀏覽器裡加上這個選項。令牌來自別處時，用攔截器設定。SSE 與 WebSocket 請求不受影響。

只在下列條件全部成立時設定該標頭：HTTP 方法不是 `GET`、`HEAD`、`OPTIONS` 或 `TRACE`；請求尚未帶有該標頭；解析後的請求 origin 等於頁面 origin；而且 `document.cookie` 中有非空 token。跨來源請求不會讀取 cookie。讀取 cookie 時丟出錯誤視為沒有 token。空 token 不設定該標頭。

## 型別

### DerivableClient

<ApiSignature name="DerivableClient" />

`createClient` 回傳的根 client，有兩種形態。factory 是一個函式，同時也是不帶 request options 的 `Client`，所以 `getOrder(client, input)` 可直接使用。以 [`RequestOptions`](/zh-Hant-TW/api/core/requestoptions-type) 呼叫它，會回傳供單次呼叫使用的一般 `Client` 值。該值不可呼叫，因此 `client()()` 無法編譯，執行時會拋出 `TypeError`。衍生只發生一次，起點是 factory，沒有鏈式呼叫。型別請寫成 `DerivableClient`，不要寫 `ReturnType<typeof createClient>`。

### Client

<ApiSignature name="Client" />

`Client` 是一個值，不是函式。以 [`RequestOptions`](/zh-Hant-TW/api/core/requestoptions-type) 呼叫 [`DerivableClient`](/zh-Hant-TW/api/core/derivableclient-type) 就會得到一個。`client()` 與 `client(undefined)` 不儲存任何 request options。`client({})` 保留一份空快照。這次呼叫會把每個頂層欄位讀一次。`protocols` 陣列會被複製。`heartbeat` 與 `reconnect` 會複製各自已知的欄位。缺少的巢狀區塊仍然保持缺少。`signal`、`beforeConnect` 與 callback 保持原本的身份。被複製欄位上的 getter 會在該次呼叫期間執行；若它拋出例外，例外會離開該次呼叫。無效數字仍會在稍後以 `REQ_OPTIONS_INVALID` 失敗。衍生不會進行 I/O。Client 值不可呼叫，呼叫它會在編譯時失敗，並在執行時拋出 `TypeError`。請為每次呼叫建立一個 client 值。同一個值可以傳給許多操作，但重複使用帶有 `signal` 的值會共用該 signal。`signal` 不會合併；請在應用程式碼中用 `AbortSignal.any` 組合。factory 的基礎設定仍然共用，也不會凍結。標準的 `with*` 輔助函式會在套用時複製它們擁有的固定 record。

不要把 factory 傳給 React 的 state setter（`setState(factory)` 會把它當成 updater 呼叫），也不要當成 Vue 的 `watch` 或 `computed` 來源（它們會呼叫函式）。

### RequestOptions

<ApiSignature name="RequestOptions" />

七個扁平欄位。每種協定只讀自己看得懂的欄位，其餘忽略。把 `heartbeat` 傳給 HTTP 會被忽略，不會產生 fault。`client(options)` 會在該次呼叫複製 `protocols` 陣列，以及 `heartbeat` 與 `reconnect` 的已知欄位。缺少的巢狀區塊仍然保持缺少。`signal`、`beforeConnect` 與 callback 保持原本的身份。SSE 只從請求 options 讀取 `signal`。SSE 重連來自 client 設定（`withSSEReconnect`），所以 `client({ reconnect })` 只影響 WebSocket。沒有編譯期的協定篩選，也沒有 `timeout` 或 `abort` 欄位。

| 欄位                 | 協定                   | 替換方式                                                          |
| -------------------- | ---------------------- | ----------------------------------------------------------------- |
| `signal`             | HTTP、SSE 與 WebSocket | 取消該次呼叫。對 SSE 與 WebSocket，它涵蓋整條連線，包含開啟之後。 |
| `onUploadProgress`   | HTTP                   | 其他協定會忽略。                                                  |
| `onDownloadProgress` | HTTP                   | 其他協定會忽略。                                                  |
| `beforeConnect`      | WebSocket              | 在該次呼叫取代 client 的設定。                                    |
| `protocols`          | WebSocket              | 取代 client 的清單。                                              |
| `heartbeat`          | WebSocket              | 整份替換。`timeoutMs` 是確認等待，不是請求期限。                  |
| `reconnect`          | WebSocket              | 整份替換。                                                        |

[`HttpExecuteOptions`](/zh-Hant-TW/api/core/httpexecuteoptions-type) 是 HTTP 切片（`signal` 加上進度）。[`EventStreamExecuteOptions`](/zh-Hant-TW/api/core/eventstreamexecuteoptions-type) 是 `{ signal? }`。[`WebSocketExecuteOptions`](/zh-Hant-TW/api/core/websocketexecuteoptions-type) 是 WebSocket 切片再加上 `signal`。

### FetchHandle

<ApiSignature name="FetchHandle" />

Defjs 對 Fetch 實作要求的呼叫簽章。它不是 `typeof fetch`，所以 mock 不需要 `preconnect` 這類宿主額外成員。預設的 HTTP／SSE handle 會在每次呼叫時解析 `globalThis.fetch`。HTTP 只對未經替換的平台 Fetch 使用 `(url, init)`；被替換的全域 Fetch 與自訂 handle 會收到 `Request`。SSE 一律傳入 `Request`。沒有 Fetch 也能匯入 Core；若預設執行環境仍缺少 Fetch，會回報 `ENV_UNSUPPORTED`，自訂 handle 依然可用。

### ClientSSEOptions

### ClientWebSocketOptions

<ApiSignature name="ClientSSEOptions, ClientWebSocketOptions" />

兩種傳輸的重新連線都需要主動啟用：沒有 `withSSEReconnect`／`withWebSocketReconnect` 就不會重試。一旦設定 `reconnect`，就套用以下預設值：

| 欄位         | SSE            | WebSocket      |
| ------------ | -------------- | -------------- |
| `attempts`   | `3` 每一次中斷 | `3` 每一次中斷 |
| `delayMs`    | `1000`         | `1000`         |
| `factor`     | `1`            | `2`            |
| `jitter`     | `0`            | `0`            |
| `maxDelayMs` | 無上限         | `30000`        |

`connectTimeoutMs` 是選用的，必須是有限正數，且不得大於 2147483647（計時器上限）；否則該操作回傳 `REQ_OPTIONS_INVALID`。對 SSE 而言，它限制從 Fetch 到收到回應標頭的時間；對 WebSocket 而言，它限制從建構到 `open` 的時間；交握之後就會清除。到期時會向平衡器回報 `NET_UNREACHABLE`，讓重連可以選取下一個端點。重試次數用盡時以 `NET_TIMEOUT` 結束。它只存在於重連選項內；只要該物件存在，`attempts` 就預設為 `3`，因此單獨設定 `connectTimeoutMs` 也會啟用重連。只想限制交握時，請同時設定 `attempts: 0`。

兩種傳輸在交握成功後，都會重設每次中斷的重試額度、回呼的 attempt 與 backoff 指數。`attempts: 0` 停用重試；省略 `attempts` 並不會在同一次中斷內取得無限次重試。`maxDelayMs` 會在 jitter 與捨入之後限制最終延遲；平台計時器上限 `2_147_483_647` ms 同樣適用，包括 SSE 未設定上限的情況。base 為零時維持零；有效數值溢位時會飽和在這些上限。

重連選項會在傳輸之前驗證：`attempts` 必須是非負安全整數；`delayMs` 必須是有限非負數；`maxDelayMs` 必須是有限非負數或正 `Infinity`，後者移除設定的上限，但最終等待仍不超過 `2_147_483_647` ms；`factor` 必須有限且為正；`jitter` 必須有限且在 0–1 之間。無效值會回傳 `REQ_OPTIONS_INVALID`。WebSocket 的 `attempts: 0` 停用後續重試，但所有明確提供的重連欄位仍會在首次連線前驗證，與 SSE 相同。jitter 會在套用最終上限之前，把已設限的 base 往正負兩個方向縮放。

對 SSE 而言，`delayMs` 只是起始的 base delay：伺服器送出的純數字 `retry:` 欄位會取代它，用於之後的嘗試，包括恢復之後。`shouldReconnect` 回傳 `false` 就停止重試。SSE 的回呼另外會收到 `lastEventId`、請求的 `method` 與最新的 `open` 資訊，也可以是非同步函式。未提供此回呼時，SSE 只會重連 `GET`、`HEAD`、`OPTIONS`、`PUT` 與 `DELETE` 請求；有提供時，所有請求方法是否重連都由它的回傳值決定。最新的事件 ID 會以 UTF-8 位元組放進 `Last-Event-ID` 送出；空 ID 會清除它，含 NUL 的 ID 則會被忽略。WebSocket 的回呼則會收到關閉時的 `code`、`reason` 與 `wasClean`。

SSE 的 `onInvalidEvent` 會處理兩種事件：找不到對應 struct 的事件（包括連 `default` 都沒有，`missing-struct`），以及資料未通過其 struct 驗證的事件（`validation-failed`）。這類事件一律會被丟棄；handler 的回傳值會被忽略，它拋出的錯誤也不會關閉串流。

對 WebSocket 而言，`beforeConnect`、`heartbeat`、`protocols` 與 `reconnect` 也可以在衍生的 client 上傳入；每一項都會在該次呼叫整份取代 client 的設定。`heartbeat.message` 負責產生每一次 ping；省略它或它回傳 `undefined` 時就不會送出任何東西。`heartbeat.timeoutMs` 是等待確認的時間，不是請求期限。

### ClientOptions

<ApiSignature name="ClientOptions" />

簽名中列出的是 `sse` 與 `webSocket`。另外六個——`endpoints`、`headers`、`http`、`interceptors`、`querySerializer` 與 `withCredentials`——繼承自未匯出的 HTTP 基底型別。`endpoints` 是 `readonly string[]`。解析後的預設值是 `[]`。空陣列是合法值，呼叫會以 `REQ_BUILD_FAILED` 失敗。沒有 client 層級的 `timeout`。`createClient` 不接收這個物件，而是接收選項輔助函式。

### ClientConfig

由選項輔助函式修改、供操作讀取的解析後快照：套用預設值之後的 `ClientOptions`，其中 `http.handle`、`interceptors`、`sse`（一個 `ClientSSEConfig`）、`webSocket` 與 `balancer` 必定存在。`http.retry` 是選用的，預設為 `undefined`（一次嘗試，沒有預算）；由 `withRetry(options?)` 設定。`balancer` 預設為該 client 新建的 `pickFirstBalancer()`。它不是 [`RequestOptions`](/zh-Hant-TW/api/core/requestoptions-type) 的欄位。

### roundRobinBalancer()

<ApiSignature name="pickFirstBalancer, roundRobinBalancer" />

`pickFirstBalancer` 會停在第一個端點，遇到 `NET_UNREACHABLE` 或 `NET_UNAVAILABLE`（HTTP 502、503 或 504）時才前進；HTTP 重試絕不會移動其黏性端點，順序遵循 client 的完整端點清單 `members`。它選用的正有限數 `failbackMs` 會在該間隔之後，對第一個端點進行一次單一並行探測；探測在對端回應開始（`end`）時判定，從未到達 `end` 的探測由 `done` 判定。HTTP 重試是另一套以 `withRetry` 設定的 client 策略。`roundRobinBalancer` 依序走訪清單，`weights` 為選用。見[多個端點](/zh-Hant-TW/docs/client#multiple-endpoints)。

### p2cBalancer()

<ApiSignature name="p2cBalancer" />

在不放回的情況下抽取不同的候選（與 Envoy/gRPC A48 不同），再選擇 tower 的 PeakEwma 或 pending 負載較低者。Linkerd 的預設值為 RTT 30 ms、衰減 10 秒。pending 在 `pick` 選取端點時預留，`end` 在收到回應標頭或 socket 開啟時釋放它，並為每種傳輸記錄真實 RTT，包括失敗的情況。只有 `done` 而沒有 `end` 時，只會釋放 pending，不產生 RTT 樣本。沒有 p2c 失敗分類器，也沒有懲罰。`choiceCount` 預設為 2，上限為 10。

### outlierDetection()

<ApiSignature name="outlierDetection, OutlierDetectionOptions" />

以 Linkerd 風格的連續失敗斷路包裝子策略。Round robin 與 p2c 預設啟用它（與 Finagle 相同）；傳入 `false` 可關閉。Pick-first 則要傳入物件才會啟用。預設分類器把每個帶 code 的結果都計為失敗，包括 `NET_TIMEOUT` 與 `NET_BODY_INCOMPLETE`。連續五次失敗之後，懲罰從 1000 ms 起算，探測失敗後加倍，再加上不超過基數 0.5 倍的正向抖動，上限為 60000 ms。到期後只允許一次探測，並在 `end` 時判定；若沒有 `end`，則在 `done` 時判定。成功會重設退避；取消只會釋放名額。沒有假定成功的逾時、配額、最後一台主機保護、結算網格、百分比判準或慢啟動。`isHealthy` 讀取的是應用程式自己持有的快取狀態，永遠不會取消懲罰。所有主機都可能被斷路；Finagle 式、只限目前清單的失敗時放行仍會送出請求。與 Envoy/gRPC A50 不同，這裡沒有驅逐配額。見[健康過濾與 p2c](/zh-Hant-TW/docs/client#health-filtering-and-p2c)。

### withRetry()

<ApiSignature name="withRetry, RetryOptions, RetryContext, HttpRetryContext, SSERetryContext, WebSocketRetryContext" />

獨立於端點選擇，啟用同一次呼叫內的 HTTP 重試。省略 `withRetry` 代表只嘗試一次，也不會建立預算。`withRetry()` 等於 `withRetry({})`，預設為 `maxAttempts: 2`（含首次）、`on: ["connect-failure"]`，以及安全方法 `GET`、`HEAD`、`OPTIONS`、`TRACE`。方法名稱不區分大小寫；`[]` 會關閉重試。`maxAttempts` 是至少為 1 的安全整數，且每個端點最多嘗試一次。`"gateway-error"` 涵蓋 `NET_UNAVAILABLE`（HTTP 502/503/504），以及被 `RES_*` 解碼拒絕的閘道本文；`"attempt-timeout"` 則使用 `attemptTimeoutMs`。串流請求本文不會重試。

退避預設為 `delayMs: 25`、`factor: 2`、`jitter: 0.2`、`maxDelayMs: 250`，欄位語意與 SSE/WebSocket 重連相同。`delayMs: 0` 會跳過等待。`attemptTimeoutMs` 必須是有限正數，且不得大於 2147483647（計時器上限）；否則該操作回傳 `REQ_OPTIONS_INVALID`。它為送往所選端點的每次 Fetch 計時，從呼叫一直到其回應本文讀取完成；傳送前後的攔截器工作以及 struct 解碼都不計時，也絕不會算到端點頭上。呼叫端的 signal 涵蓋整次呼叫，包括退避等待。當某一輪重試無法使用任何端點（平衡器 pick 失敗，或下一個端點的 URL 無法解析）時，呼叫會回傳上一次嘗試的錯誤，而不是 `REQ_BUILD_FAILED`。

由 client 擁有的 Finagle 預算預設為 20%，再加上 10 秒 TTL 內每秒 10 次的儲備。存入與取出會在十個 TTL/10 的時間切片上惰性到期。`budget: false` 會移除這項限制。共用同一份設定的衍生 client 會共用預算；各自獨立的 client 則不共用，即使共用同一個平衡器也一樣。無效選項會在 HTTP 執行時回傳 `REQ_OPTIONS_INVALID`，訊息為 `Invalid retry options`。該選項會在套用時複製自己擁有的欄位、陣列與巢狀 budget。`withRetry()` 與 `withRetry(undefined)` 的行為與 `withRetry({})` 相同。後一次 `withRetry` 會取代該策略；`withRetry({ maxAttempts: 1 })` 會在啟用之後關閉重試。平衡器與健康包裝器沒有重試設定。見[負載平衡與容錯移轉](/zh-Hant-TW/docs/load-balancing)。

### Balancer

<ApiSignature name="Balancer, PickOutcome, PickInfo, PickResult, PickFaultCode, DoneInfo, ERR_NO_CANDIDATE, isNoCandidateCause" />

`pick` 回傳 error-first tuple。選用的 `start` 會在所選傳輸開始之前同步執行至多一次；選用的 `end` 會在 `start` 之後、對端回應開始（或回應前發生失敗）時執行一次；選用的 `done` 則在完成時執行一次。Fetch 無法揭露 Linkerd 的首個本文訊框，也無法揭露 Envoy 的串流邊界。所有鉤子拋出的例外，以及 thenable 的 rejection，都會被接住。選取候選集之外的值會以 `REQ_BUILD_FAILED` 失敗，其 `done` 會以 `{ attempted: false }` 呼叫。`ERR_NO_CANDIDATE` 只會作為 `REQ_BUILD_FAILED` 的 `cause`，不是 `FaultCode`。[`isNoCandidateCause`](/zh-Hant-TW/api/core/isnocandidatecause) 也能辨識來自另一份 Core 副本的它。

平衡器只看得到中立的結果；每種傳輸會把自己的事實轉譯成 `DoneInfo.code`。預設的 outlier detection 把每個帶 code 的結果都計為失敗，包括 `NET_TIMEOUT` 與 `NET_BODY_INCOMPLETE`。原始的 `DoneInfo.status` 只保留給自訂平衡器，內建策略從不讀取它。`PickInfo` 包含一次 pick 的候選 `endpoints`、`members`（client 的完整端點清單，每次嘗試都相同）與選用的 `operation`，沒有傳輸類型的判別欄位。
