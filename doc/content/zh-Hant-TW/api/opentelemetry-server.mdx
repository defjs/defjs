# OpenTelemetry server

中介層外掛：以 core 攔截器為每次操作呼叫及其 HTTP／SSE／WebSocket 傳輸提供出站遙測。這個套件不會初始化 OpenTelemetry SDK，也不是入站的伺服器遙測。

見 [OpenTelemetry server 指南](/zh-Hant-TW/docs/integrations/opentelemetry-server)。

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

提供 `tracer`、`meter` 或 `logger` 時，先附加一個操作攔截器，再為每個啟用的傳輸各附加一個攔截器，順序為 HTTP、SSE、WebSocket。請在 `createClient` 時套用，每個 client 一次。`options` 必填；傳入 `{}` 只會安裝帶有脈絡傳播的傳輸攔截器。

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`、`meter` 與 `logger` 都是選用的。沒有 `propagator` 時 → W3C Trace Context + Baggage。

每次操作呼叫都會從呼叫開始一路觀察到它的 tuple：一個名為 `defjs.operation.name`（例如 `GET /orders/:id`）的 `INTERNAL` 操作 span，失敗時其 `error.type` 為 fault code；一筆 `defjs.client.operation.duration` 樣本；失敗時一條 `WARN` 日誌。每次 HTTP 嘗試，以及每個 SSE 或 WebSocket 連線，都會在它底下得到一個 `CLIENT` 傳輸 span。沒有進行中父 span 的呼叫會開啟自己的 trace；要保留哪些由 SDK 的取樣器決定。

省略 `tracer` 時，外掛不建立本機 span、不呼叫 `trace.getTracer(...)`，並跳過 `startSpanHook`、`requestHook` 與 `responseHook`。傳入的 `meter` 與 `logger` 可獨立運作。脈絡傳播仍會轉發擷取到的父脈絡；WebSocket 的 `queryPropagation` 預設仍為 `false`。

HTTP、SSE 與 WebSocket 預設全部啟用。對某個傳輸傳入 `{ enabled: false }` 就會跳過它。

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| 欄位                      | 預設值                      | 效果                                                                         |
| ------------------------- | --------------------------- | ---------------------------------------------------------------------------- |
| `tracer`                  | 無                          | 沒有它就沒有本地 span，也沒有 span hooks。                                   |
| `meter`                   | 無                          | 沒有它就不記錄這個套件的 metrics。                                           |
| `logger`                  | 無                          | 來自 `@opentelemetry/api-logs` 的 `Logger`。沒有它就不會發出診斷 LogRecord。 |
| `propagator`              | W3C Trace Context + Baggage | 擷取父 context，並注入外送的 context。                                       |
| `includeErrorDiagnostics` | `false`                     | 在失敗的 span、`exception` 事件與失敗日誌上匯出錯誤訊息與堆疊。              |
| `http`                    | `{}`                        | HTTP 傳輸選項。                                                              |
| `sse`                     | `{}`                        | SSE 傳輸選項。                                                               |
| `webSocket`               | `{}`                        | WebSocket 傳輸選項。                                                         |

`enabled` 預設為 `true`；只有 `enabled: false` 才會關閉某個傳輸，連同該傳輸上各次呼叫的操作遙測一起關閉。

span 鉤子只有在傳入 `tracer` 時才會執行。`startSpanHook` 會在對應的 HTTP、SSE 或 WebSocket 傳輸建立 span 前同步執行。它回傳的 attributes 會在內建 attributes 之後套用，因此應用程式可以覆寫 `url.full` 或其他初始值。若它拋出例外，Defjs 會以內建 attributes 建立 span，並繼續請求；`requestHook` 與 `responseHook` 在 span 建立之後執行。兩者都不會被 await：拋出例外或 rejection 不會阻擋或導致操作失敗。

鉤子作用於傳輸 span；操作 span 沒有鉤子。`span.isRecording()` 為 true 時，鉤子失敗會記錄 `defjs.otel.hook.error` 與 `exception` 事件。`exception` 事件只帶 `exception.type`（類別名稱，不是 Defjs 的 fault code），除非開啟 `includeErrorDiagnostics`，否則不帶 `exception.message` 或 `exception.stacktrace`，因為執行時期的錯誤文字可能包含完整的請求 URL 或一段回應本文；傳輸失敗時記錄的 `exception` 事件也適用同一條規則。span 不再記錄（已結束或未取樣）時，失敗會透過 `diag.error` 交給 OpenTelemetry 診斷 logger。應用程式必須設定 `@opentelemetry/api` 的 `diag.setLogger(...)` 才能收到；預設不會自動輸出。本套件不初始化 SDK，這類診斷也不是獨立的 SDK `LogRecord`。

`responseHook` 收到的是傳輸層回傳的東西：HTTP 是 `HttpResponse`，SSE 是啟動成功後的串流 handle，WebSocket 是開啟後的工作階段。它的第三個參數是原始請求。

預設的 `url.full` 只會把 `request.endpoint` 對照選用的 `request.baseEndpoint` 解析，不會附加 `request.query`。這條界線不是 query 遮蔽。依照 OpenTelemetry 語意慣例的要求，端點 userinfo 裡的憑證會被換成 `REDACTED:REDACTED`，預設敏感 query 鍵（`sig`、`Signature`、`AWSAccessKeyId`、`X-Amz-Signature`、`X-Amz-Credential`、`X-Amz-Security-Token`、`X-Goog-Signature`）的值會被換成 `REDACTED`，但套件沒有其他內建的遮蔽器或敏感鍵策略。`startSpanHook` 回傳的 `url.full` 會以同樣方式遮蔽，但應用程式在 `requestHook` 或 `responseHook` 裡透過 `Span` 物件寫入的 URL 不會被攔截，因此請自行建構，並視需要明確遮蔽：

## Logger 診斷

頂層的 `logger?: Logger` 選項使用 `@opentelemetry/api-logs`，不是應用程式層級的 logger。它是選用的，也可以單獨使用。Defjs 不會取得全域 logger，也不擁有它的 provider。每次失敗的操作呼叫會發出一筆 `WARN` LogRecord（severity number 13），每個開啟後失敗的 SSE 串流或 WebSocket 工作階段也會發出一筆，訊息皆為固定內容：

| 結果                                                          | 事件                                                              | 屬性                                                                                                                |
| ------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 操作呼叫以 `NET_ABORTED` 以外的 fault 解析                    | `defjs.client.operation.exception`                                | `defjs.operation.name`、`error.type`（fault code）、`exception.type`、`defjs.meta.*`                                |
| SSE 串流或 WebSocket 工作階段以錯誤結束，包含 `closed` 被拒絕 | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address`、`server.port`、`exception.type`、`defjs.meta.*`、`defjs.sse.fault.code` 或 `websocket.close.code` |

成功、之後的嘗試已復原的重試嘗試、正常關閉、EOF、伺服器送來的 WebSocket 關閉訊框（無論 code 為何），以及呼叫端取消，都不會產生 LogRecord。沒有關閉訊框的 WebSocket 突發斷線（1006）會讓工作階段以錯誤結束並記錄一次，每個執行環境都一樣。操作的紀錄會帶著操作 span 的脈絡發出。

開啟 `includeErrorDiagnostics: true` 後，每筆紀錄還會帶 `exception.message` 與 `exception.stacktrace`；對操作呼叫來說，它們是 fault 的 `message` 與 `stack`。錯誤的 cause 鏈與可列舉欄位絕不匯出，但訊息本身不會被過濾：fault 的訊息往往就是其 cause 的訊息，平台的錯誤文字也可能引用請求 URL。過濾、exporter、flush 與 shutdown 由應用程式負責。

完整的日誌與第三方整合範例請見 [OpenTelemetry 指南](/zh-Hant-TW/docs/integrations/opentelemetry-server#logs-and-third-party-loggers)。
