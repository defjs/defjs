# Errors

操作會把可判別的 `Fault` 放在 tuple 的第一項——宣告過的失敗不會以例外拋出。

## FaultCode

<ApiSignature name="FaultCode" />

封閉集合。第一個 `_` 之前的那一段就是類別，沒有獨立的 `kind` 欄位。集合保持封閉，`switch (fault.code)` 才能窮盡——擴充要報自己的細節，請走 `cause`，而不是新增 code。

## FaultClass

<ApiSignature name="FaultClass" />

`FaultClass<FaultCode>` 是 `'CAP' | 'ENV' | 'EXT' | 'HTTP' | 'NET' | 'REQ' | 'RES'`。

## Fault

<ApiSignature name="Fault" />

對 `fault.code` 做 switch。

### FaultOf

<ApiSignature name="FaultOf, Fault" />

`FaultOf` 是以解碼後的錯誤本文型別（而非產生它的 struct）來表達的 `Fault`。`HttpAwaitResult` 與各個 fault 建立函式處理的是解碼後的值，所以使用這種形式。

每個變體都是名為 `DefjsFault` 的原生 `Error`，所以 `String(fault)` 會給出 `DefjsFault: <message>`。`code` 與各變體的中繼資料——`status`、`response`、`data`——都是可列舉的自有屬性。原生 `cause` 鏈則不可列舉。

預設的 struct 訊息會說 `received <kind>`，絕不包含收到的值，例如 `Expected number at email, received string`。`RES_DECODE_FAILED` 背後若是 JSON 的 `SyntaxError`，訊息會是 `Response body could not be decoded`。issue path 反映結構並保留 record 的鍵：`struct.record(...)` 可能產生 `Expected number at alice@example.com, received string`，因此預設訊息、`prettify()` 與 `String(fault)` 中的鍵仍可能含有敏感資訊。原始的 `StructIssue.received` 與 parser 的 cause 同樣敏感；自訂的 `errorMap` 與擴充訊息會原樣使用，寫入日誌之前需要先審閱。

只有把 `fault.cause` 窄化到 `StructError` 之後，才能呼叫 `format()`、`flatten()` 或 `prettify()`；這些輔助函式不會被複製到 fault 上。

### HttpStatusFault

<ApiSignature name="HttpStatusFaultOf, HttpStatusFault" />

任何非 2xx 狀態。定義宣告過 `error` 且本文解碼成功時，`data` 就是該本文，`response` 也帶著它。省略 `error` 時，本文根本不會被讀取，於是 `data` 是 `undefined`，`response` 只剩中繼資料。

### DecodeFault

<ApiSignature name="DecodeFaultCode, DecodeFault" />

回應到了，但無法依宣告讀取。`response` 只有中繼資料：本文就是解碼後的值，而失敗的正是解碼本身，所以沒有 `body` 欄位可取。出錯細節在 `cause` 上——struct 不符時是 `StructError`，表示法無法讀取時則是 parser 的失敗。

### PreflightFault

<ApiSignature name="PreflightFaultCode, PreflightFault" />

所有可能在回應出現之前就失敗的情況：`REQ_*`、`NET_*`、`EXT_*`、`CAP_*`、`ENV_UNSUPPORTED`。在傳輸層有中繼資料可回報之前，`response` 是 `undefined`，例如下載到一半被截斷的本文。

重試選項不會在執行時期驗證。省略 `withRetry` 會關閉重試。`withRetry()` 與 `withRetry(undefined)` 的行為與 `withRetry({})` 相同。`withRetry({ maxRetries: 0 })` 會在啟用之後關閉重試。`shouldRetry` 函式若拋出例外，該次呼叫會以 `EXT_HOOK_FAILED` 結束，拋出的值成為 `cause`；HTTP、SSE 與 WebSocket 皆同。對於已經開啟的串流或工作階段，見 [Client](/zh-Hant-TW/api/client#withretry)。

### AnyFault

<ApiSignature name="AnyFault" />

任何 fault，不論它解碼後的錯誤本文是什麼型別。寫那種只做分類、不在乎是哪個操作產生的 handler 時用它；本文型別要緊的地方，請優先使用 `Fault<typeof yourErrorStruct>`。

## createPreflightFault()

<ApiSignature name="createHttpStatusFault, createUndecodedHttpStatusFault, createDecodeFault, createNetworkFault, createPreflightFault" />

`createHttpStatusFault` 接受已經帶著解碼後本文的回應；`createUndecodedHttpStatusFault` 只接受中繼資料，供未宣告 `error` 的定義使用。

`createNetworkFault` 以 [`isAbortCause`](/zh-Hant-TW/api/core/isabortcause) 判定 `NET_ABORTED`，以 [`isTimeoutCause`](/zh-Hant-TW/api/core/istimeoutcause) 判定 `NET_TIMEOUT`：兩者都能辨認來自任何 Core 副本、帶有品牌的哨兵；`isAbortCause` 也會辨認名為 `AbortError` 的 `DOMException`，`isTimeoutCause` 則辨認名為 `TimeoutError` 的 `DOMException` 或 `Error`。其餘一律對應到 `NET_UNREACHABLE`。`createPreflightFault` 直接接受 code；沒有 `cause` 時，code 就成為訊息。

所有建立函式都回傳帶有上述結構化欄位的原生 `Error` 實例；它們不會產生普通物件錯誤，`String(fault)` 也不需要 adapter。

## 哨兵

## ERR_ABORTED

## ERR_TIMEOUT

<ApiSignature name="ERR_ABORTED, ERR_TIMEOUT" />

abort 與 timeout 共用的 `Error` 哨兵物件，作為 `cause` 使用。從 HTTP 攔截器丟出其中一個，該呼叫就會以 `NET_ABORTED` 或 `NET_TIMEOUT` 結束。SSE 與 WebSocket 攔截器則會把任何拋出的東西（包含這兩個）都回報為 `EXT_INTERCEPTOR_FAILED`。

這些哨兵帶有不可列舉的 `Symbol.for('defjs.cause.aborted')` 與 `Symbol.for('defjs.cause.timeout')` 品牌。分類不依賴哨兵的物件同一性，也不依賴無關的較早執行。

## Cause 檢查

<ApiSignature name="isAbortCause, isTimeoutCause" />

[`isAbortCause`](/zh-Hant-TW/api/core/isabortcause) 會辨認帶有 abort 品牌的 `Error`，或名為 `AbortError` 的 `DOMException`。[`isTimeoutCause`](/zh-Hant-TW/api/core/istimeoutcause) 會辨認帶有 timeout 品牌的 `Error`，或名為 `TimeoutError` 的 `DOMException`／`Error`。請傳入 `fault.cause` 來分類底層的值；這些函式不會解開 fault。它們也能處理來自另一份 Core 副本的哨兵。

## ERR_NO_CANDIDATE

## isNoCandidateCause

<ApiSignature name="ERR_NO_CANDIDATE, isNoCandidateCause" />

沒有候選端點可選時，`ERR_NO_CANDIDATE` 只會作為 `REQ_BUILD_FAILED` 的 `cause` 出現。它不會新增 `FaultCode`。這個哨兵帶有不可列舉的 `Symbol.for('defjs.cause.no-endpoint')` 品牌。[`isNoCandidateCause`](/zh-Hant-TW/api/core/isnocandidatecause) 能辨認來自另一份 Core 副本的這個品牌，方式與 [`isAbortCause`](/zh-Hant-TW/api/core/isabortcause) 辨認 abort 相同。請傳入 `fault.cause`。它不會解開 fault。
