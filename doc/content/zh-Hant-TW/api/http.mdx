# HTTP

宣告具型別的請求，再帶著 client 與 input 呼叫操作。

## defineRequest()

<ApiSignature name="defineRequest" />

- **definition** — `method`、`path`、選用的 `input` struct、選用的 `output` 與 `error` struct，以及選用的 `operation`。只要宣告了 `input`，就必須提供明確的 `builder`。`input` 只宣告參數，每個值放在哪裡全由 builder 決定。只有未宣告 `input` 的定義可以省略 `builder`。這些 `definition` 成員的文件位於 [`RequestDefinition`](/zh-Hant-TW/api/core/requestdefinition-type)。`builder` 恰好在宣告 `input` 時必填。
- **回傳** 一個操作。呼叫方式是 `getOrder(client, input)`；沒有宣告 input 時則是 `health(client)`。整個 input struct 都是選用時，可以省略 input 引數。呼叫它就會啟動請求。沒有第三個選項引數。

<include cwd>examples/api/define-request.ts#example</include>

`output` 是 2xx 本文的單一 struct；`error` 是所有非 2xx 本文的單一 struct。兩者都不依狀態碼分鍵。省略任一側，該側本文就永遠不會被讀取——見[宣告即斷言](/zh-Hant-TW/docs/design-decisions#declaration-is-an-assertion)。

呼叫操作會回傳一個 promise，其值為 [`HttpAwaitResult`](/zh-Hant-TW/api/core/httpawaitresult-type) 所描述的 tuple。單次呼叫的選項，請從 [`RequestOptions`](/zh-Hant-TW/api/core/requestoptions-type) 衍生 client 來傳。HTTP 只讀 `signal` 與進度回呼，並忽略其他欄位。

沒有宣告 `error` struct，或已宣告的 `error` 本文解碼成功時，非 2xx 狀態才是 `HTTP_STATUS`。有宣告 `error` 時，fault 的 `data` 是解碼後的錯誤本文，否則為 `undefined`。若已宣告的 `error` 本文無法讀取（媒體型別不符、JSON 無效），或與其 struct 不符，fault 會改成 `RES_MEDIA_TYPE_INVALID`、`RES_DECODE_FAILED` 或 `RES_STRUCT_MISMATCH`，而回應狀態仍會記錄在中繼資料中。失敗時 tuple 第三項是 `undefined`；回應中繼資料由 fault 帶著。

## fetchHandler()

<ApiSignature name="fetchHandler" />

預設的 HTTP 傳輸。`fetchImpl` 預設為送出當下才解析的全域 `fetch`；`withHTTPHandle` 可以換成別的。未經替換的平台 Fetch 會收到 `(url, init)`，被替換的全域 Fetch 或自訂 handle 則收到 `Request`。若沒有任何回應到達 client，或讀取已宣告的本文失敗，它會拒絕，而不會解析成合成回應。

## makeResponse()

<ApiSignature name="makeResponse" />

不經網路就能建立 `HttpResponse`（供攔截器與測試使用）。預設 status 是 `0`。2xx 時 `ok` 為 true。它回傳的值會走和線上回應完全相同的媒體型別檢查與 struct 驗證；沒有可信任的短路。

## HttpExecuteOptions

<ApiSignature name="HttpExecuteOptions" />

`HttpExecuteOptions` 是 [`RequestOptions`](/zh-Hant-TW/api/core/requestoptions-type) 的 HTTP 切片：[`UseRequestConfig`](/zh-Hant-TW/api/core/userequestconfig-type)，也就是 `signal` 加上 `onDownloadProgress` 與 `onUploadProgress`。沒有 `timeout` 或 `abort` 欄位。期限是 `signal: AbortSignal.timeout(ms)`，歸類為 `NET_TIMEOUT`。手動中止是 `NET_ABORTED`。`signal` 是該次呼叫的 signal；請在應用程式碼中用 `AbortSignal.any` 組合。沒有 client 層級的預設期限。其他請求欄位（例如 `heartbeat`）會被忽略。

## 型別

### RequestDefinition

`method`、`path`，選用的 `input`、`output`、`error`、`operation` 與 `builder`。struct 的種類決定已宣告的本文如何讀取。只要宣告了 `input`，就必須提供明確的 `builder`。`input` 只宣告參數，每個值放在哪裡全由 builder 決定。只有未宣告 `input` 的定義可以省略 `builder`。

### HttpAwaitResult

<ApiSignature name="HttpAwaitResult" />

成功時，第三項只有在宣告 `output` 時才帶 `body`。失敗時它是 `undefined`——fault 已經握有當時存在的回應中繼資料。

### HttpRequest

正規化後的外送請求：`method`、`endpoint`、`headers`、`body`、`signal`、`operation`、`withCredentials`、`finalizeHeaders`、`downloadProgress`／`uploadProgress`、`baseEndpoint`、`queryString` 與 `queryParams`。攔截器看到它時，`body` 已經是傳輸值——JSON 就是一串 JSON 文字——所以 HMAC 與摘要請對它計算，而不是對 struct input 計算。攔截器看到的 `queryParams` 是 `new URLSearchParams(queryString)`。builder 回傳 `URLSearchParams` 時，會把該實例直接傳下去。`responseType` 與 `errorResponseType` 是唯讀的：它們由定義的 `output` 與 `error` struct 種類推導而來，不能修改。

### HttpMeta

<ApiSignature name="HttpMeta" />

回應中繼資料，只要有回應到達 client 就會提供。它**不**帶 `body`：本文只有在宣告的 struct 解碼之後才存在。

### DecodedResponse

<ApiSignature name="DecodedResponse" />

本文已依宣告的 struct 解碼成功的回應。持有這個型別，就證明解碼確實發生過——這也是解碼失敗時只回報 `HttpMeta` 的原因。

### HttpResponse

<ApiSignature name="HttpResponse" />

回應沒有本文時，`body` 是 `undefined`；JSON 的 `null` 則維持 `null`。這個型別帶有品牌，所以請用 `makeResponse` 建立，不要用物件字面值。這是傳輸層產出、攔截器看到的線上形狀：`body` 是文字或已解析的 JSON，不是解碼後的值。對 JSON 表示而言，字串是 JSON 字串根，不會再次解析；位元組與 blob 是原始資料，只會解析一次。呼叫端拿到的是 `DecodedResponse`。

### HttpProgressEvent

### HttpProgressFn

`loaded`、`total`、`lengthComputable`。回呼可以是非同步函式。`onDownloadProgress` 或 `onUploadProgress` 拋出例外時，該次呼叫會以 `EXT_OBSERVER_FAILED` 失敗，並以拋出的值作為 `cause`；取消仍回報 `NET_ABORTED`，中止原因為逾時時則回報 `NET_TIMEOUT`。轉換發生在 `fetch` 能串流請求本文的執行環境：`Blob`／`File`、`ArrayBuffer` 與 `FormData` 會轉成串流並回報上傳進度。Chromium 只在 HTTP/2 及以上可用；HTTP/1.1 下帶 `onUploadProgress` 的上傳會失敗（`NET_UNREACHABLE`）。Firefox 原樣送出這些本文，且不會呼叫 `onUploadProgress`。

發生該轉換的執行環境裡，FormData 會使用序列化後的串流，不會把整個本文緩衝成 Blob，並保留實際的 multipart boundary。除非有效且明確的 `Content-Length` 提供總量，否則 total 未知。明確的 content type 經過上傳轉換後仍會保留，但 FormData 必須使用其序列化產生的 boundary。`loaded` 計算的是串流位元組，不是伺服器已確認的位元組。帶有非 identity `Content-Encoding` 的下載會回報 `total: 0` 與 `lengthComputable: false`；這些串流位元組可能早已解壓縮。

見 [HTTP 指南](/zh-Hant-TW/docs/http) 與 [Client](/zh-Hant-TW/docs/client)。

## RequestEndpoint

`defineRequest` 的回傳值。第一個引數是 [`Client`](/zh-Hant-TW/api/core/client-type)。其餘引數只有 input。

## BuilderInput

`builder` 看到的、已剖析的操作 input。物件節點會帶著產生它們的 struct，所以別名、`Date` 與 `bigint` 編碼會跟著值走。

## HttpRequestShape

<ApiSignature name="HttpRequestShape" />

四個欄位都是選用的。`query` 是 `URLSearchParams` 或一個 record；巢狀物件在執行時需要 `withQuerySerializer`。`headers` 是 `HeadersInit`，或由純量與純量陣列組成的 record。`path` 會為每個 `:name` 區段提供一個純量。

`GET` 與 `HEAD` 的 `body` 是 `never`。其他方法下，它可以是傳輸值（`string`、`Blob`、`ArrayBuffer`、型別化陣列或 `DataView`、`FormData`、`URLSearchParams` 或 `ReadableStream<Uint8Array>`），也可以是 JSON 資料（`number`、`boolean`、`bigint`、`Date`、`null`、陣列，或鍵為字串的物件）。

## UseRequestConfig

`signal`，加上選用的 `onDownloadProgress` 與 `onUploadProgress`。`HttpExecuteOptions` 就是這個切片。沒有 `timeout` 或 `abort` 欄位。

## RequestSuccessData

從宣告的 `output` struct 推導出的成功本文；未宣告時為 `undefined`。

## RequestErrorData

從宣告的 `error` struct 推導出的錯誤本文；未宣告時為 `undefined`。

## HttpResponseType

`'arraybuffer' | 'blob' | 'json' | 'text'`

由宣告的 struct 種類決定（`string` → `text`，`blob`／`file` → `blob`，`arrayBuffer` → `arraybuffer`，其餘 → `json`）。它不是 `defineRequest` 上的欄位。

## MakeResponseOptions

給 `makeResponse` 的欄位：`status`、`statusText`、`url`、`headers`、`body`、`request`。
