```ts
function withSSEReconnect(options: ClientSSEOptions['reconnect']): ClientOption
```

設定 SSE stream 失敗後的自動重新連線。重新連線需要主動啟用：沒有這個 option，失敗的 stream 不會重試。傳入 `undefined` 會清除先前的設定。

```ts
type SSEReconnect = {
  attempts?: number
  delayMs?: number
  factor?: number
  jitter?: number
  maxDelayMs?: number
  shouldReconnect?: (context: {
    attempt: number
    cause?: unknown
    lastEventId: string
    method: string
    open?: { response: { status: number; statusText: string; url: string }; url: string }
  }) => boolean | Promise<boolean>
}
```

- `attempts` 是每一次中斷的重試額度。設定了 `reconnect` 時預設為 `3`，`0` 停用重試。成功的握手會重設額度、callback 的 `attempt`，以及 backoff 指數。省略它並不會在同一次中斷內提供無限次重試。反覆成功開啟後立即發生可重試的串流失敗時，可能持續以目前的基底延遲重新連線（仍受 jitter 與上限約束），因為每次開啟都會重設預算；請用 `shouldReconnect` 停止這種情況。正常 EOF 仍會結束串流。
- 未提供 `shouldReconnect` 時，只有 `GET`、`HEAD`、`OPTIONS`、`PUT` 與 `DELETE` 會重新連線。提供後，所有請求方法是否重新連線都由它的回傳值決定，包括 `POST`；傳入的情境物件中的 `method` 用來區分端點。回傳 `false` 會停止針對此次失敗的重試。此回呼會在檢查重試次數上限之前執行。
- 使用 `ReadableStream` 請求主體的請求絕不會重新連線，也不會為此呼叫 `shouldReconnect`。
- `delayMs`、`factor`、`jitter`（0 到 1）與 `maxDelayMs` 決定 backoff 的形狀。`factor` 預設為 `1`，`jitter` 預設為 `0`。`maxDelayMs` 會在 jitter 與捨入之後，把最終延遲封頂。沒有設定上限時，平台計時器上限 `2_147_483_647` 毫秒仍然適用。base 為零時維持零；有效數值若溢位，會飽和在這些上限。
- `delayMs` 只是起始的 base delay（預設 `1000`）。server 傳來的 `retry:` field（僅限數字，單位為毫秒）會取代它，用於之後的嘗試。
- 下一次嘗試時，最後的 event id 會再次以 UTF-8 位元組放進 `Last-Event-ID` 送出。空的 `id:` 會清除它；含有 NUL 的 ID 會被忽略。
- 重新連線選項會在 interceptors 或 Fetch 之前驗證：`attempts` 必須是非負 safe integer；`delayMs` 與明確的 `maxDelayMs` 必須是有限且非負；`factor` 必須是有限且為正；`jitter` 必須是有限且落在 0–1。無效的值會在 execute 時回傳 `REQ_OPTIONS_INVALID`。
