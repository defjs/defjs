# Serveur OpenTelemetry

Un plugin middleware : instrumentation sortante de chaque appel d’opération et de son transport HTTP / SSE / WebSocket, sous forme d’intercepteurs core. Ce paquet n’initialise pas un SDK OpenTelemetry, et ce n’est pas une instrumentation serveur entrante.

Voir le [guide serveur OpenTelemetry](/fr-FR/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

Ajoute un intercepteur d’opération quand un `tracer`, un `meter` ou un `logger` est fourni, puis un intercepteur par transport activé, dans l’ordre HTTP, SSE, WebSocket. Appliquez-le au moment de `createClient`, une fois par client. `options` est obligatoire ; passez `{}` pour installer les intercepteurs de transport avec la propagation seule.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter` et `logger` sont chacun facultatifs. Pas de `propagator` → W3C Trace Context + Baggage.

Chaque appel d’opération est observé de l’appel jusqu’à son tuple : un span d’opération `INTERNAL` nommé `defjs.operation.name` (comme `GET /orders/:id`) avec `error.type` défini au code de fault en cas d’échec, un échantillon `defjs.client.operation.duration`, et un log `WARN` s’il échoue. Chaque tentative HTTP et chaque connexion SSE ou WebSocket reçoit en dessous un span de transport `CLIENT`. Un appel sans span parent actif démarre sa propre trace ; l’échantillonneur du SDK décide de ce qui est conservé.

Sans `tracer`, le plugin ne crée pas de spans locaux, n’appelle jamais `trace.getTracer(...)`, et ignore `startSpanHook`, `requestHook` et `responseHook`. Les instances `meter` et `logger` fournies fonctionnent indépendamment. La propagation transmet toujours le contexte parent extrait ; `queryPropagation` WebSocket reste `false` par défaut.

HTTP, SSE et WebSocket sont activés par défaut. Passez `{ enabled: false }` sur un transport pour l'ignorer.

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| Champ                     | Défaut                      | Effet                                                                                                          |
| ------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `tracer`                  | aucun                       | Sans lui, pas de spans locaux ni de hooks de span.                                                             |
| `meter`                   | aucun                       | Sans lui, aucune métrique du paquet n’est enregistrée.                                                         |
| `logger`                  | aucun                       | Un `Logger` de `@opentelemetry/api-logs`. Sans lui, aucun LogRecord de diagnostic n’est émis.                  |
| `propagator`              | W3C Trace Context + Baggage | Extrait le contexte parent et injecte le contexte sortant.                                                     |
| `includeErrorDiagnostics` | `false`                     | Exporte les messages et piles d’erreur sur les spans en échec, les événements `exception` et les logs d’échec. |
| `http`                    | `{}`                        | Options du transport HTTP.                                                                                     |
| `sse`                     | `{}`                        | Options du transport SSE.                                                                                      |
| `webSocket`               | `{}`                        | Options du transport WebSocket.                                                                                |

`enabled` vaut `true` par défaut ; seul `enabled: false` désactive un transport, ainsi que la télémétrie d’opération de ses appels.

Les hooks de span ne s'exécutent que lorsqu'un `tracer` est fourni. `startSpanHook` s'exécute de façon synchrone avant la création du span pour son propre transport HTTP, SSE ou WebSocket. Ses attributs sont appliqués après les attributs intégrés, donc l’application peut remplacer `url.full` ou une autre valeur initiale. S'il lève une exception, Defjs crée le span avec les attributs intégrés et continue la requête ; `requestHook` et `responseHook` s'exécutent après la création du span. Aucun des deux n’est attendu : une levée ou un rejet ne bloque ni ne fait échouer l’opération.

Les hooks façonnent le span de transport ; le span d’opération n’en a pas. Tant que `span.isRecording()` est vrai, les échecs de hook enregistrent les événements `defjs.otel.hook.error` et `exception`. L’événement `exception` ne porte que `exception.type` (le nom de classe, pas un code de fault Defjs), et ni `exception.message` ni `exception.stacktrace` sauf si `includeErrorDiagnostics` est activé, car le texte d’erreur du runtime peut inclure l’URL complète de la requête ou un fragment de corps de réponse ; la même règle s’applique à l’événement `exception` enregistré quand un transport échoue. Pour les spans qui n’enregistrent pas (terminés ou non échantillonnés), les échecs vont au logger de diagnostic OpenTelemetry via `diag.error`. Les applications doivent configurer `diag.setLogger(...)` depuis `@opentelemetry/api` pour les recevoir ; il n’y a pas de sortie automatique par défaut. Le paquet n’initialise pas le SDK, et ce diagnostic n’est pas un `LogRecord` de SDK séparé.

`responseHook` reçoit ce que le transport a renvoyé : le `HttpResponse` pour HTTP, le handle de flux pour SSE une fois le démarrage réussi, et la session pour WebSocket une fois ouverte. Son troisième argument est la requête d’origine.

Par défaut, `url.full` ne résout que `request.endpoint` contre un `request.baseEndpoint` facultatif ; `request.query` n’est pas ajoutée. Cette frontière n’est pas un masquage de la query. Comme l’exigent les conventions sémantiques OpenTelemetry, les identifiants du userinfo de l’endpoint sont remplacés par `REDACTED:REDACTED`, et les valeurs des clés de query sensibles par défaut (`sig`, `Signature`, `AWSAccessKeyId`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `X-Goog-Signature`) sont remplacées par `REDACTED`, mais le paquet n’a aucun autre mécanisme de masquage intégré ni politique de clés sensibles. Un `url.full` renvoyé par `startSpanHook` est masqué de la même façon, mais une URL qu’une application écrit via l’objet `Span` dans `requestHook` ou `responseHook` n’est pas interceptée : construisez-la donc et, si besoin, masquez-la explicitement :

## Diagnostics du logger

L’option de premier niveau `logger?: Logger` utilise `@opentelemetry/api-logs`, pas un Logger applicatif. Elle est facultative et peut être utilisée seule. Defjs n’obtient jamais un logger global et ne possède pas son provider. Il émet un LogRecord `WARN` (numéro de sévérité 13) par appel d’opération en échec, et un par flux SSE ou session WebSocket qui échoue après son ouverture, chacun avec un message fixe :

| Issue                                                                                   | Événement                                                         | Attributs                                                                                                           |
| --------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Un appel d’opération se résout avec une fault autre que `NET_ABORTED`                   | `defjs.client.operation.exception`                                | `defjs.operation.name`, `error.type` (le code de fault), `exception.type`, `defjs.meta.*`                           |
| Un flux SSE ou une session WebSocket se termine en erreur, y compris un `closed` rejeté | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address`, `server.port`, `exception.type`, `defjs.meta.*`, `defjs.sse.fault.code` ou `websocket.close.code` |

Le succès, une tentative retentée qu’une tentative ultérieure rétablit, la fermeture normale, l’EOF, une trame de fermeture WebSocket venue du serveur quel que soit son code, et l’annulation par l’appelant ne produisent aucun LogRecord. Une chute abrupte de WebSocket sans trame de fermeture (1006) termine la session en erreur et journalise une fois, sur tous les runtimes. Le record d’opération est émis avec le contexte du span d’opération.

Avec `includeErrorDiagnostics: true`, chaque record porte aussi `exception.message` et `exception.stacktrace` ; pour un appel d’opération, ce sont le `message` et la `stack` de la fault. La chaîne de causes et les champs énumérables d’une erreur ne sont jamais exportés, mais le message n’est pas filtré : le message d’une fault est souvent celui de sa cause, et le texte d’erreur de la plateforme peut citer l’URL de la requête. L’application gère filtres, exporters, flush et shutdown.

Voir les exemples complets de journalisation et d’intégration tierce dans le [guide OpenTelemetry](/fr-FR/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
