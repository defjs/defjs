# Créer et publier un SDK [#publish-an-http-sdk-without-hiding-execute]

Un SDK empaquette l’API que ton équipe propose. Avec Defjs, exporte les définitions d’endpoints et leurs contrats de données ; les applications consommatrices fournissent la configuration du client et décident quand les appeler. Cette recette utilise HTTP, et la même frontière de paquet vaut pour les définitions SSE et WebSocket.

## 1. Définir les opérations du SDK

Crée `src/orders.ts` dans ton projet SDK. Garde ici les chemins, le mapping d’entrée, les réponses et les erreurs de service. Aucune instance de client, adresse de déploiement ou identifiant courant n’est nécessaire pour définir cette opération.

<include cwd meta='title="src/orders.ts"'>
  examples/recipes/publish-http-sdk/orders-sdk.ts#example
</include>

Expose-la depuis `src/index.ts` :

```ts
export { getOrder } from "./orders";
```

Ajoute d’autres modules d’opérations et réexporte leurs endpoints à mesure que le SDK grandit.

## 2. Empaqueter le JavaScript et les déclarations

Le projet SDK a sa propre frontière de paquet :

```txt
orders-sdk/
  package.json
  tsconfig.json
  src/
    index.ts
    orders.ts
```

Utilise ce `package.json`, en remplaçant le nom d’exemple par un scope de paquet que tu possèdes :

```json
{
  "name": "@company/orders-sdk",
  "version": "0.1.0",
  "type": "module",
  "sideEffects": false,
  "files": ["dist"],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    }
  },
  "scripts": {
    "build": "tsdown --platform neutral"
  },
  "peerDependencies": {
    "@defjs/core": "^0.6.0"
  },
  "devDependencies": {
    "@defjs/core": "^0.6.0",
    "tsdown": "^0.23.3",
    "typescript": "^7.0.2"
  }
}
```

Core reste une dépendance de runtime externe, partagée avec l’application. La plage peer indique quelles versions de Core ton SDK prend en charge ; la dépendance de développement te permet de builder et de tester contre cette plage. Cet exemple correspond au contrat `0.4.x` actuel. Choisis et teste la plage de ton SDK avant publication ; les déclarations et le comportement au runtime en dépendent tous les deux.

Ajoute `tsconfig.json` :

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2022", "ESNext.Disposable", "DOM", "DOM.Iterable"],
    "strict": true,
    "noEmit": true
  },
  "include": ["src/**/*.ts"]
}
```

Ces déclarations de bibliothèque fournissent des types, pas des polyfills au runtime. L’application a toujours besoin des API Web utilisées par les transports qu’elle choisit.

`tsdown` empaquette l’entrée dans `dist/index.js` et émet `dist/index.d.ts`.

Construis et inspecte le paquet :

```sh
bun install
bun run build
bun pm pack --dry-run
bun pm pack
```

Vérifie que la tarball contient `dist/index.js` et `dist/index.d.ts`. Installe cette tarball dans une application séparée et vérifie ses types et son exécution avant publication. Le README du SDK doit documenter l’API du service, les versions de Core compatibles, l’authentification attendue et les défauts facultatifs.

## 3. L’appeler depuis l’application consommatrice

L’exemple local garde la définition dans `orders-sdk.ts` à côté de `app.ts` pour pouvoir tourner hors ligne. Son import ne crée pas de client ; l’application configure un handle Fetch local et appelle l’opération importée :

<include cwd meta='title="app.ts"'>
  examples/recipes/publish-http-sdk/app.ts#example
</include>

```txt
paid
```

Pour le SDK empaqueté, installe-le avec une version de Core compatible :

```sh
bun add @company/orders-sdk @defjs/core@^0.6.0
```

Remplace l’import relatif de l’exemple par :

```ts
import { getOrder } from "@company/orders-sdk";
```

Configure l’adresse de ton service et l’authentification sur le client de l’application. Garde `withHTTPHandle(...)` pour les tests locaux ; retire-le pour utiliser l’implémentation Fetch de la plateforme. Une seconde application peut importer le même endpoint et choisir d’autres réglages de client sans changer la définition du SDK.

## 4. Vérifier et publier

Utilise les [tests locaux au client](/fr-FR/recipes/test-with-handle) pour exercer la définition exportée, le mapping de requête, la validation de réponse et les erreurs déclarées. Vérifie le même endpoint avec deux clients configurés pour des adresses de service et des identifiants différents. Garde le traitement typé de `HTTP_STATUS` disponible au site d’appel, et teste l’annulation ainsi que le nettoyage des flux pour les transports que ton SDK exporte.

Quand le paquet a passé tes contrôles, publie depuis le répertoire du SDK avec ton compte npm :

```sh
bun publish --access public
```

Cette commande publie un paquet public. Utilise le registre et la politique d’accès de ton organisation pour un SDK privé. Defjs ne génère ni ne publie le paquet à ta place.

Les fabriques de client et les méthodes de commodité sont des ajouts facultatifs. Elles peuvent fournir des défauts de service ou un comportement de domaine tout en acceptant la configuration de l’appelant et en préservant les exports d’endpoints directs. Documente tout mapping d’erreur ou toute politique de cycle de vie qu’elles introduisent. Ni l’une ni l’autre n’est requise pour un SDK réutilisable.

Voir [HTTP](/fr-FR/docs/http), [Client](/fr-FR/docs/client) et [Décisions de conception](/fr-FR/docs/design-decisions) pour les contrats sous-jacents.
