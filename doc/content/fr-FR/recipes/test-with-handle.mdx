### Trois détails utiles pour vos tests

- **Pourquoi envelopper `(input, init)` dans `new Request(input, init)`** : `withHTTPHandle` suit la signature standard `fetch(input, init)`. Construire `new Request(input, init)` donne un accès uniforme à `method`, `url`, `headers` et `await request.json()`.
- **Pourquoi passer `withEndpoint("https://fixture.invalid")`** : `createClient` valide l'URL de base avant `withHTTPHandle` ; `.invalid` est réservé par RFC et n'interroge jamais le DNS public.
- **Simuler les trois issues HTTP courantes** :
  - Succès `2xx` : renvoyer `Response.json(...)` -> `[null, data, response]`
  - Erreur `4xx` / `5xx` : renvoyer `Response.json(..., { status: 422 })` -> `err.code === "HTTP_STATUS"`
  - Panne réseau : rejeter ou lever (`Promise.reject(new TypeError("fetch failed"))`) -> `err.code === "NET_UNREACHABLE"`. Ne renvoyez **pas** `Response.error()`, car toute `Response` (même statut `0`) est traitée comme une réponse HTTP (`HTTP_STATUS`).

En production, appelez la même opération `getOrder` avec un client configuré via `withEndpoint(...)`. Consultez [Tests](/fr-FR/docs/testing) et [Client](/fr-FR/docs/client).
