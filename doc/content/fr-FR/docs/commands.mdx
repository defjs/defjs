# Commandes

L’auteur du SDK exporte l’endpoint renvoyé par `defineRequest`, `defineEventStream` ou `defineWebSocket`. Cet endpoint décrit une opération d’API réutilisable, ses contrats Struct et le placement des entrées par `builder`. L’application appelle l’endpoint avec ses entrées, reçoit une commande opaque et la transmet à son client.

Définition → endpoint exporté → commande pour un appel → `client.execute(...)`. Cette répartition vaut pour HTTP, SSE et WebSocket. Les exemples regroupent définition et exécution pour faciliter la lecture ; lors de la [publication d’un SDK](/fr-FR/recipes/publish-http-sdk), le module d’endpoints reste séparé de l’application.

Les fabriques de clients et méthodes pratiques sont des ajouts facultatifs. Elles peuvent fournir des valeurs par défaut ou un comportement métier tout en acceptant la configuration de l’appelant et en conservant les exports directs d’endpoints. Documente les transformations d’erreurs et les règles de cycle de vie qu’elles introduisent. Aucune fabrique n’est nécessaire pour créer un SDK réutilisable.

## Choisir une définition

| Définition               | Contrat                                                                    | Valeur en succès                             |
| ------------------------ | -------------------------------------------------------------------------- | -------------------------------------------- |
| `defineRequest(...)`     | Méthode, chemin relatif, entrée optionnelle, `output` / `error` optionnels | Données décodées + réponse                   |
| `defineEventStream(...)` | Chemin, limites de buffer/queue, map nom d’événement → Struct              | `EventStreamHandle` + instantané open        |
| `defineWebSocket(...)`   | Chemin, un struct entrant, struct sortant optionnel, limite de queue       | `WebSocketSession` + instantané de connexion |

Pas d’`input` → l’endpoint ne prend pas d’argument, et `builder` peut être `() => request`. Avec `input` → passe la valeur du struct. Un champ optionnel peut être omis ; un champ requis non.

Garde les commandes opaques. Ne fouille pas les tags ni les symboles.

## Où vont les valeurs

Le struct décide comment une valeur est encodée. Le `builder` décide où elle va. `builder` est une fonction synchrone pure de l’entrée **parsée**. Il tourne à l’execute. Une erreur levée devient `REQ_BUILD_FAILED` sur le tuple — l’appel de l’endpoint lui-même ne lève rien.

Un `input` déclaré exige toujours un `builder` explicite. `input` ne fait que définir les paramètres ; seul le builder décide où va chaque valeur. Seules les définitions sans `input` peuvent omettre `builder`.

Fais passer la valeur typée. Alias, `Date` → ISO et `bigint` → string s’appliquent ensuite partout où ce struct est utilisé : placement de la requête, décodage de la réponse, événements SSE et frames WebSocket.

Le corps est le JSON `{"display_name":"…","email":"…"}`. Une clé écrite à la main est la trappe de sortie : `body: { name: input.user.displayName }` envoie `name`, parce que l’objet parent est anonyme et que l’alias ne s’applique pas.

## Quand les formes diffèrent

Utilise `builder` pour les placeholders de path, les littéraux et les branches. Il reçoit la vraie valeur, donc `if`, `??`, les templates et `switch` marchent.

`query: input.filter` envoie `page_size`. `headers: { 'x-api-version': '2' }` est un littéral. L’auth et le tracing restent dans les intercepteurs : ils voient la requête native après le builder.

## Formes de `output` et `error`

`output` est un Struct pour le corps 2xx ; `error` est un Struct pour tout le reste. `ok` est le seul
embranchement, et un seul côté décode, jamais les deux. Omettre un côté veut dire que ce corps n’est jamais lu : le fault
porte le statut et `data` reste `undefined`.
