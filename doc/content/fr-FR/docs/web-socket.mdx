# WebSocket

Le SDK définit le chemin, les entrées, les messages entrants et sortants, et la limite de file d’une opération WebSocket. L’application consommatrice configure son client, appelle l’opération, et choisit les options de connexion propres à l’appel sur un client dérivé. Exporte l’opération à côté des opérations HTTP ou SSE de ton SDK.

Démarrage → recevoir → envoyer → relâcher avec `await using`. Tu possèdes le désabonnement et la disposition. `close()` / `closed` manuels restent disponibles ; les clients, les providers et les intercepteurs ne ferment pas les sessions tout seuls.

## Un struct par direction

`incoming` est un struct pour chaque frame texte. `outgoing` est un struct pour `session.send(...)`. Modélise plusieurs kinds avec `struct.discriminatedUnion`. L’alias sur ces champs est le nom wire dans les deux sens. Il n’y a pas d’enveloppe de type séparée ni de normaliseur.

```json
{ "type": "message", "text": "Hello" }
```

Les frames entrantes texte, `ArrayBuffer`, typed-array et `Blob` sont lues en UTF-8, parsées en JSON, puis vérifiées contre `incoming`. Le JSON malformé et les échecs de struct vont à `session.onRuntimeError` et ne sont pas mis en file. La session reste ouverte. Les frames qui ne sont ni du texte, ni des octets, ni un `Blob` sont ignorées. Il n’y a pas de `withWebSocketOnInvalidEvent`.

`session.send(...)` valide et sérialise de façon synchrone : encodage struct, puis `JSON.stringify`. Il envoie immédiatement quand c’est ouvert, met en file pendant `reconnecting` quand une file sortante est activée, et lève `InvalidStateError` quand ce n’est pas inscriptible. Il lève aussi quand il n’y a pas de struct sortant, que le payload échoue le struct, que la file sortante est désactivée ou pleine, ou que l’envoi natif échoue. Une liste `protocols` statique sur la définition est le contrat de l’endpoint (par exemple `graphql-transport-ws`). Les `protocols` d’un client dérivé et `withWebSocketProtocols` peuvent encore la remplacer. Seules ces options choisissent les sous-protocoles : le builder, `beforeConnect` et les intercepteurs ne peuvent pas les changer, donc un jeton dans le sous-protocole est passé comme `protocols` sur le client dérivé pour cet appel. Le builder ne peut renvoyer que `path` et `query`.

Après l’encodage struct, les valeurs que JSON ne peut pas représenter fidèlement lèvent `TypeError` avant l’envoi ou l’entrée dans la file de reconnexion : nombres non finis, fonctions, symboles, `Map`, `Set`, flux, et instances de classe sans représentation JSON. Les valeurs imbriquées suivent la même règle que les corps JSON HTTP. `struct.number()` accepte encore les infinis et rejette `NaN` ; accepter une valeur à la couche struct ne la rend pas un JSON valide. Le heartbeat utilise le même serializer ; son échec de sérialisation termine la session logique.

`receive` est à un seul consommateur. Demander un second itérateur lève une `TypeError`.

## Instantanés d’état

| Membre                     | Sens                                                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `state`                    | `idle`, `connecting`, `open`, `reconnecting`, `closing`, `closed`, `aborted` ou `error`                     |
| `connection`               | Dernière connexion physique : `generation`, URL, protocole négocié, extensions quand elles sont disponibles |
| `bufferedAmount`           | Nombre d’octets natifs non envoyés, ou `0` sans socket physique                                             |
| `receive`                  | Itérable async à un consommateur des messages entrants validés                                              |
| `onStateChange(listener)`  | S’abonne aux transitions d’état logique ; renvoie le désabonnement                                          |
| `onRuntimeError(listener)` | S’abonne aux erreurs runtime hors démarrage ; renvoie le désabonnement                                      |
| `closed`                   | Promesse du résultat de fermeture terminal logique                                                          |

`open` = socket physique ouvert. `reconnecting` inclut la préparation + le délai avant un remplacement. `connection.generation` s’incrémente à chaque socket physique qui atteint `open`. `session.connection` avance à la reconnexion. Le `startupConnection` du tuple ne préserve le premier instantané réussi que pour une session native Defjs ou un wrapper qui transmet le même objet `connection` live. Les sessions personnalisées et les wrappers qui transforment `connection` utilisent à la place le `connection` public courant de la session renvoyée pour le tuple. Partager `closed` ne peut pas contourner la sanitation d’URL ou le filtrage de métadonnées, et Defjs ne reconstruit pas les métadonnées de la première connexion à partir de transformations arbitraires.

Échec de démarrage → `[error, undefined, connection?]`. Un échec de constructeur avant l’ouverture peut n’avoir aucune connexion ; un abort ou une fermeture pendant le démarrage peut encore fournir un instantané. Après le retour de la session, les erreurs runtime passent par les observateurs, `receive` et `closed` — pas un second tuple de résultat.

## Reconnexion

La reconnexion est opt-in. Pas d’objet `reconnect` → une fermeture physique termine la session logique. Quand elle est configurée, les défauts sont `attempts: 3`, `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000`, `jitter: 0`. `attempts` est le budget de nouvelles tentatives pour chaque coupure ; un `open` réussi réinitialise le budget et l’exposant de backoff. Chaque coupure suivante repart donc avec la tentative 1 et la base `delayMs`. `attempts: 0` désactive. Le prédicat par défaut accepte chaque issue de fermeture non manuelle dans le budget de cette coupure. Les ouvertures réussies répétées n’ont pas de limite de nouvelles tentatives à vie. Un socket qui s’ouvre avec succès et est immédiatement refermé par le serveur peut continuer à se reconnecter au délai de base (sous jitter et plafonds), parce que chaque ouverture réinitialise le budget ; utilise `shouldReconnect` pour l’arrêter.

<include cwd>examples/web-socket/reconnect.ts#example</include>

`shouldReconnect` reçoit la prochaine tentative, la cause de fermeture, le code, la raison et `wasClean`. Un `session.close(...)` manuel n’entre pas dans le prédicat. Une préparation ou une politique qui lève termine la session logique avec une erreur.

Le jitter de backoff WebSocket est **multiplicatif** (`jitter: 0.2` met la base plafonnée à l’échelle `0.8x`–`1.2x` avant arrondi). Le délai final est à nouveau plafonné à `maxDelayMs` et à la limite de timer de la plateforme de `2_147_483_647` ms, donc la partie haute de cette plage peut être tronquée. Une base nulle reste nulle ; un dépassement de nombres valides est clampé au lieu de lever. SSE utilise la même règle de jitter 0–1. Les options de reconnexion sont validées avant le constructeur : `attempts` est un entier sûr non négatif ; `delayMs` doit être fini et non négatif ; `maxDelayMs` doit être un nombre fini non négatif ou `Infinity` positif, ce qui retire le plafond configuré mais pas la limite de plateforme de `2_147_483_647` ms ; `factor` est fini et positif ; `jitter` est fini et dans 0–1. Les valeurs invalides renvoient `REQ_OPTIONS_INVALID`. WebSocket `attempts: 0` désactive les nouvelles tentatives suivantes, mais tous les champs de reconnexion explicitement fournis sont encore validés avant la connexion initiale, comme pour SSE.

`beforeConnect({ attempt, signal })` tourne avant le constructeur initial et chaque reconnexion. Passe son signal au refresh de token pour que l’annulation arrête à la fois la prep et le connect.

## Heartbeat

Opt-in sur le client ou sur un client dérivé. L’intervalle envoie `message()` à travers le struct sortant. Un `isAck(message)` facultatif reconnaît un ack — ce message efface l’attente d’acquittement et n’est **pas** livré à `receive`. `heartbeat` est remplacé comme une valeur entière. `timeoutMs` est le temps d’attente de cet acquittement. Ce n’est pas une échéance de requête.

<include cwd>examples/web-socket/heartbeat.ts#example</include>

`intervalMs` et `timeoutMs` doivent être des timers finis et strictement positifs ≤ `2_147_483_647`. Le message de heartbeat doit être valide pour le struct sortant. Les échecs de sérialisation, d’envoi natif, de classification d’ack et de timeout sont fatals pour la session logique — ils ne deviennent pas des reconnexions ordinaires.

## Files

| Réglage                | Valeur requise                                 | Comportement                                                                                                                   |
| ---------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `maxIncomingQueueSize` | Entier sûr positif                             | Borne les messages parsés en attente de `receive` et les frames brutes en attente de transform. Dépassement → `state: 'error'` |
| `maxOutgoingQueueSize` | Entier sûr non négatif facultatif ; défaut `0` | FIFO seulement tant que `state === 'reconnecting'`. Pleine ou désactivée → `send(...)` lève                                    |

Les frames sortantes en file sont vidées avant que le socket de remplacement publie `open`. Les frames déjà envoyées sur un socket antérieur ne sont jamais rejouées automatiquement. Les files de reconnexion sont pour les messages que tu envoies pendant la reconnexion — pas pour reconstruire l’état de l’app.

Le dépassement entrant efface la séquence en attente, fait échouer `receive`, arrête la session, résout `session.closed` avec `kind: 'error'`. Garde le consommateur assez rapide ou relève la borne à partir d’une taille et d’une mémoire mesurées.

## Protocoles et authentification

Les `protocols` de la définition, `withWebSocketProtocols(...)` du client, et `protocols` sur le client dérivé définissent la liste de sous-protocoles du constructeur. Préséance : client dérivé → client → définition. La liste dérivée remplace la liste du client ; elle n’est pas ajoutée. La première liste définie est copiée pour la session logique et réutilisée à la reconnexion.

Les constructeurs WebSocket du navigateur n’acceptent pas d’en-têtes de handshake arbitraires, et le builder ne peut pas renvoyer `headers` ni `body`. Defjs convertit `http:` → `ws:` et `https:` → `wss:`, encode les placeholders de chemin une fois, et utilise les mêmes règles de query que HTTP : scalaires et clés répétées par défaut, `withQuerySerializer` pour les objets imbriqués, et pas d’appel de serializer quand il n’y a pas de query.

Comme pour HTTP et SSE, un endpoint de base absent, relatif ou invalide, ou un chemin illégal, échoue avec `REQ_BUILD_FAILED` pendant la construction, avant tout intercepteur ou transport, même si un intercepteur court-circuiterait. L’URL résolue doit garder l’origine de base et rester sous son répertoire ; les caractères de contrôle C0 (y compris tab, CR et LF), les antislashs, `?`, `#` et les échappements de répertoire dans le chemin sont rejetés. Les formes scheme-like et protocol-relative sont rejetées même avec des espaces initiaux ; un espace intérieur simple est autorisé et envoyé comme `%20`. Le `req.endpoint` final d’un intercepteur est validé contre son `req.baseEndpoint` final avec la même règle, mais il peut délibérément remplacer la base par une autre URL absolue valide. Les erreurs d’URL déterministes ne sont jamais réessayées.

`withCredentials(true)` est les identifiants Fetch pour HTTP/SSE — pas l’auth WebSocket. Utilise une politique cookie/session revue, un sous-protocole, ou un ticket de connexion de courte durée. Ne mets pas d’identifiants généraux ni de secrets de longue durée dans la query string.

## Fermeture et propriété

`session.close(code?, reason?)` demande la fermeture terminale et arrête le heartbeat. Le code doit être `1000` ou `3000..4999` ; la raison ≤ 123 octets UTF-8. Des arguments de fermeture invalides lèvent avant de changer l’état. Utilise-le avec `await session.closed` quand tu as besoin d’une raison de fermeture manuelle ou du résultat terminal logique.

Le signal `abort` passé à l’opération reste attaché à la session ouverte et couvre toute la connexion, y compris après son ouverture. Un abort en forme de timeout (`TimeoutError` ou `ERR_TIMEOUT`, y compris `AbortSignal.timeout(...)`) la termine en `'error'` (`NET_TIMEOUT`). Toute autre raison la termine en `'aborted'`, et `receive` rejette avec cette raison elle-même, pas une nouvelle `AbortError`. Il n’y a pas d’échéance limitée au démarrage. Une application qui en veut une crée son propre `AbortController`, l’abandonne avec `new DOMException("...", "TimeoutError")` depuis un timer, et efface le timer après le retour de l’await. Voir [SSE](/fr-FR/docs/sse#close-and-dispose).

`session.closed` est l’instantané terminal logique : `'closed'`, `'aborted'` ou `'error'`, avec `code` / `reason` / `wasClean` natifs facultatifs et une `cause` pour aborted/error. Les champs de fermeture native observés l’emportent sur le repli demandé par le propriétaire.

Le disposer async standard demande une fermeture native au mieux, puis attend le teardown du cycle de vie, de la pompe de messages, des timers, des listeners, de la file et des références de socket possédés par Defjs. Si un événement de fermeture n’est pas observé dans la seconde, le teardown est forcé et le disposer peut rejeter avec une `DOMException` nommée `TimeoutError` ; cela ne prouve pas que la connexion TCP physique s’est fermée. Les appels répétés du disposer partagent le même teardown. Les implémentations de session structurelles personnalisées doivent maintenant fournir le même contrat `[Symbol.asyncDispose](): PromiseLike<void>`.

## Frontière GraphQL

Defjs fournit un struct entrant, un struct sortant, et un cycle de vie de session logique. Il n’implémente **pas** un protocole applicatif WebSocket. Les fonctions GraphQL-over-WebSocket — init de connexion, ID d’opération, `next`/`error`/`complete`, disposition, rejeu d’abonnement — sont hors du contrat core.

Utilise un client de protocole comme `graphql-ws` quand le serveur exige ce protocole, ou modélise les frames avec `defineWebSocket(...)`. Pose un sous-protocole statique tel que `graphql-transport-ws` sur `protocols`. Un struct seul ne négocie pas la sémantique GraphQL.
