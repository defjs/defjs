# Sessions WebSocket

`defineWebSocket` déclare un contrat WebSocket bidirectionnel dans votre SDK : le patron de chemin, `input` et `builder` optionnels (`path` et `query` uniquement), les structs de messages `incoming` et `outgoing`, les limites de file et les sous-protocoles statiques. L'application consommatrice configure le heartbeat, les retries (`withRetry`) et le nettoyage du cycle de vie sur son propre client.

## 2. Validation des messages et sens d'échange

- **Trames entrantes (`session.receive`)** : Les trames texte, `ArrayBuffer`, vues typées et `Blob` sont décodées en UTF-8, analysées en JSON et validées selon `incoming`. Tout JSON malformé ou non-conformité de schéma est notifié à `session.onRuntimeError` et ignoré sans refermer la session. `session.receive` n'admet qu'un seul consommateur ; demander un second itérateur lève un `TypeError`. Quand le transport échoue, les messages déjà reçus sont livrés d'abord, puis `receive` rejette avec `closed.cause`, et cela comprend un timeout de heartbeat. Une annulation par l'appelant (un abort de `signal`), `session.close()` et la libération écartent les messages non lus, que la session se soit déjà terminée ou non. Sur une session ouverte, `receive` se termine alors aussitôt après `session.close()` ou la libération, et rejette avec la raison de l'abort (un `AbortError` par défaut) après un abort ; une trame qui arrive après `session.close()` est écartée aussi. Un `signal` qui expire, comme le fait `AbortSignal.timeout(ms)`, pendant que la session est ouverte est un timeout : la session se termine en erreur et livre d'abord les messages en file. Un `signal` qui expire après la fin de la session est un arrêt et les écarte.
- **Trames sortantes (`session.send(payload)`)** : Valide de manière synchrone selon `outgoing`, applique les `.alias()` et codecs, puis sérialise avec `JSON.stringify`. L'envoi est immédiat si l'état est `open`, mis en file pendant `reconnecting` (si `maxOutgoingQueueSize > 0`), et lève de manière synchrone si la charge utile est invalide, la file pleine/désactivée ou la session fermée.

## 3. États de session et observateurs

| Membre               | Description                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| `state`              | `'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'`    |
| `connection`         | Instantané dynamique du dernier socket physique (`generation`, `url`, `protocol`, `extensions`)          |
| `bufferedAmount`     | Nombre d'octets natifs non envoyés sur le socket physique actif (`0` en l'absence de connexion)          |
| `receive`            | Itérable asynchrone à consommateur unique délivrant les messages validés par `incoming`                  |
| `onStateChange(fn)`  | S'abonne aux transitions d'état ; renvoie une fonction de désabonnement                                  |
| `onRuntimeError(fn)` | S'abonne aux erreurs d'analyse ou de trames hors phase de démarrage ; renvoie une fonction `unsubscribe` |
| `closed`             | Promesse résolue avec l'issue terminale (`kind: 'closed' \| 'aborted' \| 'error'`)                       |

## 4. Retries, heartbeat et files d'attente

La reconnexion et le heartbeat sont activables à la demande via les options du client (`withRetry`, `withWebSocketHeartbeat`) ou sur un client dérivé par appel (`client({ retry, heartbeat })`). La reconnexion utilise la même politique `withRetry` que HTTP et SSE :

- **Retries** : Quand une politique de retry est définie, les défauts sont `maxRetries: 3`, `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000`, `jitter: 0.2`. Toute fermeture que `session.close()` n'a pas demandée est retentée par défaut, y compris une connexion qui ne s'est jamais ouverte. Un constructeur qui lève est un échec local qu'un retry ne ferait que répéter, donc il termine l'appel sans interroger `shouldRetry`. Chaque `open` physique réinitialise le compte de la coupure. `shouldRetry` peut passer outre le défaut et peut être async ; il n'est pas appelé pour une fermeture manuelle, un abort de l'appelant, ou une fois que `maxRetries` retries ont été faits. Un retry décliné ou épuisé termine la session comme elle se terminerait sans politique : une erreur de connexion est `closed.kind: "error"`, une trame de fermeture du pair est `"closed"`. `beforeConnect({ attempt, signal })` s'exécute avant la connexion initiale et chaque retry. Ce que le répartiteur apprend d'un socket ouvert ne dépend que du code de fermeture, quelle que soit la valeur de `wasClean` : `1006` ou `1015` (aucune trame de fermeture reçue) donne `NET_UNREACHABLE`, `1012` ou `1013` donne `NET_UNAVAILABLE`, tout autre code n'est pas un échec.
- **Délai de tentative (`attemptTimeoutMs`)** : Lorsqu'il est fourni, il borne la construction jusqu'à `open` et est effacé après le handshake. C'est une option de `withRetry` (ou de l'option de requête `retry`), donc `withRetry({ attemptTimeoutMs })` retente aussi, avec le défaut `maxRetries: 3`. Pour une échéance limitée au handshake, écrivez `withRetry({ maxRetries: 0, attemptTimeoutMs })`. L'expiration signale `NET_UNREACHABLE` au répartiteur, et les retries épuisés se terminent par `NET_TIMEOUT`.
- **Heartbeat** : Defjs ne définit aucun format, intervalle ou timeout de heartbeat : `message` et `isAck` sont vos fonctions, et le type exige `message` et n'admet `timeoutMs` qu'avec `isAck`. L'interface `WebSocket` du navigateur n'a aucun moyen d'envoyer un ping de niveau protocole, donc un message applicatif est le seul heartbeat portable. Tous les `intervalMs`, il envoie `message()` à travers le struct `outgoing` en texte JSON, donc l'endpoint déclare un struct `outgoing` et un ping texte ou binaire nu n'est pas possible. Il attend jusqu'à `timeoutMs` une trame décodée qui satisfait `isAck(msg)` ; une trame qui échoue au struct `incoming` est signalée à `onRuntimeError` et n'atteint jamais `isAck`. Les trames d'acquittement correspondantes sont consommées par le moniteur de heartbeat et ne parviennent pas à `session.receive`. Un acquittement manqué compte comme un échec de connexion : le socket est fermé, l'acquittement manqué est signalé au répartiteur comme `NET_UNREACHABLE` pour l'endpoint, et la tentative entre dans le flux de retry comme n'importe quelle autre fermeture. Sans politique de retry, ou une fois les retries épuisés, `closed.kind` vaut `"error"` et `closed.cause` est l'ordinaire `Error("WebSocket heartbeat timeout")`. Les échecs de sérialisation du heartbeat, ou un `message()` qui lève, sont locaux : ils terminent la session avec leur cause initiale, ne sont pas retentés et ne sont pas attribués à l'endpoint.
- **Limites de file d'attente** :
  - Messages entrants : Il n'y a ni option ni limite de nombre. La bibliothèque met en file chaque message que la plateforme livre jusqu'à ce que `session.receive` le lise, donc un consommateur qui ne lit jamais laisse la file croître sans borne ; consommez `session.receive` tant que la session est ouverte, ou fermez la session.
  - `maxOutgoingQueueSize` (facultatif, défaut `0`) : Met en tampon les appels `session.send()` uniquement lorsque `state === 'reconnecting'` et les expédie avant de publier le prochain `open`.

`shouldRetry` reçoit le `code` de fermeture natif, `reason` et `wasClean` dans son contexte WebSocket, et `retryable` y vaut toujours `true`. Un serveur peut achever un handshake de fermeture normal avec le code d’erreur applicative `1011` ; `wasClean === true` ne signifie donc pas que l’application a réussi. L’exemple décide selon `code` ; choisissez les codes applicatifs selon votre protocole au lieu de vous fier uniquement à `!wasClean`.

## 5. Sous-protocoles et authentification [#protocols-and-authentication]

Les WebSocket de navigateur ne permettent pas de définir des en-têtes de handshake arbitraires, par conséquent les fonctions `builder` WebSocket renvoient exclusivement `{ path?, query? }`.

- **Priorité des sous-protocoles** : `client({ protocols })` l'emporte sur `withWebSocketProtocols(...)`, qui l'emporte sur `defineWebSocket({ protocols })`.
- **Conversion d'URL** : Defjs convertit automatiquement `http:` → `ws:` et `https:` → `wss:` sur l'endpoint résolu.
- **Identifiants** : `withCredentials(true)` s'applique exclusivement à Fetch (HTTP/SSE). Authentifiez les connexions WebSocket à l'aide de cookies/politiques de session, de sous-protocoles ou de jetons temporaires de connexion — évitez de placer des secrets pérennes dans les chaînes de requête.
- **`beforeConnect` n’est pas un mutateur de requête** : L’analyse d’entrée, le `builder` pur synchrone et la chaîne d’intercepteurs s’exécutent une fois par opération. Pour une requête dont l’endpoint de base n’est pas remplacé par un intercepteur, chaque reconnexion sélectionne à nouveau un endpoint et reconstruit l’URL avec cet endpoint, mais réutilise le chemin/la query construits et la liste de protocoles capturée. L’URL est fixée avant le `beforeConnect` de cette tentative, sur le même endpoint comme après un basculement. Modifier une variable de closure, l’entrée ou le tableau de protocoles dans le hook ne peut pas fournir un nouveau ticket au handshake courant. Le renouvellement d’un identifiant d’URL/sous-protocole au sein d’une session n’est pas pris en charge ; obtenez d’abord le nouvel identifiant, passez-le comme entrée ou configuration client à une nouvelle opération, puis prenez en charge le nettoyage de cette session de remplacement.

## 6. Fermeture et propriété

Appelez `session.close(code?, reason?)` (où `code` vaut `1000` ou `3000..4999` et `reason` ne dépasse pas 123 octets UTF-8) et attendez `await session.closed`, ou bien recourez à `await using` :

  examples/web-socket/closure-and-ownership.ts#example
</include>

Une connexion qui était ouverte puis coupée sans trame de fermeture (code `1006`, `wasClean: false`) se termine toujours avec `closed.kind: "error"` et `closed.cause` `Error("WebSocket connection error")`, que le runtime émette ou non un événement `error` natif.

Lorsqu’une coupure de retry épuise son `maxRetries`, la session se termine avec `closed.kind: "error"` et l’erreur de transport ordinaire comme `closed.cause`, aux côtés de l’instantané de fermeture natif (souvent le code `1006` pour un upgrade échoué) ; elle n’expose aucun code stable distinct d’épuisement. Quand une session se termine avec `closed.kind: "error"`, les messages déjà en file sont encore livrés et `session.receive` rejette avec `closed.cause` après le dernier ; une fermeture venue du pair livre aussi les messages en file avant que `session.receive` se termine. Quand l’appelant arrête la session, les messages non lus sont écartés : un abort de l’appelant (`closed.kind: "aborted"`), un `session.close()` manuel et une libération avec `await using` le font tous, y compris après que la session s’est déjà terminée. Sur une session ouverte, `session.receive` se termine alors aussitôt après `session.close()` ou la libération, et rejette avec `closed.cause`, la raison de l’abort, après un abort de l’appelant. Un arrêt après la fin de la session écarte les messages non lus et ne change rien d’autre : `closed` conserve sa valeur, et `session.receive` rejette encore avec `closed.cause` dès qu’il ne reste rien de non lu. Désabonnez systématiquement vos écouteurs `onStateChange` et `onRuntimeError` dès la destruction de votre composant ou worker.
