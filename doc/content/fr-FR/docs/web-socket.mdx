# WebSocket

Le SDK exporte avec `defineWebSocket` le contrat d’une session : chemin, messages entrants et sortants, exigences de protocole. L’application fournit le client, exécute l’endpoint et gère la session obtenue, ses écouteurs, ses règles de reconnexion et sa libération.

Démarre → reçois → envoie → relâche avec `await using`. Tu possèdes le désabonnement et la libération. `close()` / `closed` manuels restent disponibles ; les clients, providers et intercepteurs ne ferment pas les sessions tout seuls.

## Un struct par direction

`incoming` est un struct pour chaque frame texte. `outgoing` est un struct pour `session.send(...)`. Modélise plusieurs kinds avec `struct.discriminatedUnion`. L’alias sur ces champs est le nom wire dans les deux sens. Il n’y a pas d’enveloppe de type séparée ni de normalizer.

```json
{ "type": "message", "text": "Hello" }
```

Les frames entrantes texte, `ArrayBuffer`, typed-array et `Blob` sont lues en UTF-8, parsées en JSON, puis vérifiées contre `incoming`. Le JSON malformé et les échecs de struct vont à `session.onRuntimeError` et ne sont pas mis en queue. La session reste ouverte. Les frames qui ne sont ni texte, ni octets, ni `Blob` sont ignorées. Il n’y a pas de `withWebSocketOnInvalidEvent`.

`session.send(...)` valide et sérialise de façon synchrone : encode du struct, puis `JSON.stringify`. Il envoie tout de suite quand la session est ouverte, met en file pendant `reconnecting` quand une queue sortante est activée, et lève `InvalidStateError` quand l’écriture est impossible. Il lève aussi une erreur quand il n’y a pas de struct sortant, que le payload échoue au struct, que la queue sortante est désactivée ou pleine, ou que le send natif échoue. Une liste `protocols` statique sur la définition est le contrat de l’endpoint (par exemple `graphql-transport-ws`). Les options d’execute et `withWebSocketProtocols` peuvent encore la remplacer. Seules ces options choisissent les sous-protocoles : le builder, `beforeConnect` et les intercepteurs ne peuvent pas les changer, donc un token dans un sous-protocole se passe via l’option `protocols` d’execute pour cet appel. Le builder ne peut renvoyer que `path` et `query`.

Après l’encodage du struct, les valeurs que JSON ne peut pas représenter fidèlement lèvent `TypeError` avant l’envoi ou l’entrée dans la file de reconnexion : nombres non finis, fonctions, symbols, `Map`, `Set`, flux et instances de classe sans représentation JSON. Les valeurs imbriquées suivent la même règle que les corps JSON HTTP. `struct.number()` accepte encore les infinis et rejette `NaN` ; accepter une valeur au niveau du struct ne la rend pas un JSON valide. Le heartbeat utilise le même sérialiseur ; son échec de sérialisation met fin à la session logique.

`receive` est à un seul consommateur. Demander un second itérateur lève une `TypeError`.

## Instantanés d’état

| Membre                     | Sens                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| `state`                    | `idle`, `connecting`, `open`, `reconnecting`, `closing`, `closed`, `aborted`, ou `error`      |
| `connection`               | Dernière connexion physique : `generation`, URL, protocole négocié, extensions si disponibles |
| `bufferedAmount`           | Nombre d’octets natifs non envoyés, ou `0` sans socket physique                               |
| `receive`                  | Itérable async à un consommateur, de messages entrants validés                                |
| `onStateChange(listener)`  | S’abonne aux transitions d’état logique ; renvoie le désabonnement                            |
| `onRuntimeError(listener)` | S’abonne aux erreurs runtime hors démarrage ; renvoie le désabonnement                        |
| `closed`                   | Promesse du résultat de fermeture terminal logique                                            |

`open` = socket physique ouvert. `reconnecting` inclut la préparation + le délai avant un remplacement. `connection.generation` s’incrémente pour chaque socket physique qui atteint `open`. `session.connection` est mis à jour à chaque reconnexion. Le tuple `startupConnection` ne conserve le premier instantané de connexion réussie que pour une session native Defjs ou un wrapper transmettant le même objet `connection` live. Les sessions personnalisées et les wrappers qui transforment `connection` utilisent à la place le `connection` public courant de la session renvoyée. Partager `closed` ne permet pas de contourner l’assainissement des URL ni le filtrage des métadonnées, et Defjs ne reconstruit pas les métadonnées de la première connexion à partir de transformations arbitraires.

Échec de démarrage → `[error, undefined, connection?]`. Un échec de constructeur avant l’ouverture peut n’avoir aucune connexion ; un timeout/close pendant le démarrage peut encore fournir un instantané. Après le retour de la session, les erreurs runtime passent par les observateurs, `receive` et `closed` — pas un second tuple d’execute.

## Reconnect

Le reconnect est opt-in. Pas d’objet `reconnect` → une fermeture physique termine la session logique. Une fois configuré, les défauts sont `attempts: 3`, `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000`, `jitter: 0`. `attempts` est le budget de nouvelles tentatives de chaque coupure ; un `open` réussi réinitialise le budget et l’exposant de backoff. Chaque coupure suivante repart donc au retry 1 et à la base `delayMs`. `attempts: 0` désactive. Le prédicat par défaut accepte chaque résultat de fermeture non manuelle dans le budget de cette coupure. Des ouvertures réussies répétées n’ont pas de limite de nouvelles tentatives à vie. Un socket qui s’ouvre avec succès puis est immédiatement refermé par le serveur peut continuer à se reconnecter avec le délai de base (sous réserve du jitter et des plafonds), car chaque ouverture réinitialise le budget ; utilise `shouldReconnect` pour l’arrêter.

<include cwd>examples/web-socket/reconnect.ts#example</include>

`shouldReconnect` reçoit la prochaine tentative de retry, la cause de close, le code, la reason et `wasClean`. Un `session.close(...)` manuel n’entre pas dans le prédicat. Une préparation ou une politique qui lève une erreur termine la session logique avec une erreur.

Le jitter de backoff WebSocket est **multiplicatif** (`jitter: 0.2` met à l’échelle la base déjà plafonnée de `0.8x` à `1.2x` avant l’arrondi). Le délai final est de nouveau plafonné à `maxDelayMs` et à la limite de timer de la plateforme, `2_147_483_647` ms, donc la partie haute de cette plage peut être tronquée. Une base nulle reste nulle ; le dépassement de nombres valides est borné au lieu de lever. SSE utilise la même règle de jitter 0–1. Les options de reconnexion sont validées avant le constructeur : `attempts` est un entier sûr positif ou nul ; `delayMs` doit être fini et positif ou nul ; `maxDelayMs` doit être un nombre fini positif ou nul ou `Infinity` positif, qui supprime le plafond configuré sans lever la limite de la plateforme de `2_147_483_647` ms pour le délai final ; `factor` est fini et strictement positif ; `jitter` est fini et compris entre 0 et 1. Les valeurs invalides renvoient `REQ_OPTIONS_INVALID`. Pour WebSocket, `attempts: 0` désactive les nouvelles tentatives ultérieures, mais tous les champs de reconnexion explicitement fournis restent validés avant la connexion initiale, comme pour SSE.

`beforeConnect({ attempt, signal })` tourne avant le constructeur initial et chaque reconnect. Passe son signal au refresh de token pour que l’annulation arrête à la fois la prep et le connect.

## Heartbeat

Opt-in au scope execute ou client. L’intervalle envoie `message()` à travers le struct sortant. Un `isAck(message)` optionnel reconnaît un ack — ce message efface le timeout et n’est **pas** livré à `receive`.

<include cwd>examples/web-socket/heartbeat.ts#example</include>

`intervalMs` et `timeoutMs` doivent être des timers finis et strictement positifs ≤ `2_147_483_647`. Le message de heartbeat doit être valide pour le struct sortant. Les échecs de sérialisation, de send natif, de classification d’ack et de timeout sont fatals pour la session logique — ils ne deviennent pas des reconnects ordinaires.

## Queues

| Réglage                | Valeur requise                                | Comportement                                                                                                                |
| ---------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `maxIncomingQueueSize` | Entier sûr strictement positif                | Borne les messages parsés en attente de `receive` et les frames brutes en attente de transform. Overflow → `state: 'error'` |
| `maxOutgoingQueueSize` | Entier sûr non négatif optionnel ; défaut `0` | FIFO seulement tant que `state === 'reconnecting'`. Pleine/désactivée → `send(...)` lève une erreur                         |

Les frames sortantes en file sont envoyées avant que le socket de remplacement publie `open`. Les frames déjà envoyées sur un socket précédent ne sont jamais rejouées auto. Les queues de reconnect sont pour les messages que tu envoies pendant le reconnect — pas pour reconstruire l’état de l’app.

L’overflow entrant vide la séquence en attente, fait échouer `receive`, arrête la session, résout `session.closed` avec `kind: 'error'`. Garde le consommateur assez rapide ou relève la borne d’après la taille/mémoire mesurée.

## Protocoles et authentification

Les `protocols` de définition, `withWebSocketProtocols(...)` du client, et `protocols` d’execute posent la liste de sous-protocoles du constructeur. Précédence : exécution → client → définition. La première liste définie est copiée pour la session logique et réutilisée au reconnect.

Les constructeurs WebSocket navigateur n’acceptent pas d’en-têtes de handshake arbitraires, et le builder ne peut pas renvoyer `headers` ni `body`. Defjs convertit `http:` → `ws:` et `https:` → `wss:`, encode les placeholders de path une fois, et utilise les mêmes règles de query que HTTP : scalaires et clés répétées par défaut, `withQuerySerializer` pour les objets imbriqués, et pas d’appel de serializer quand il n’y a pas de query.

Comme pour HTTP et SSE, un endpoint de base absent, relatif ou invalide, ou un chemin illégal, échoue avec `REQ_BUILD_FAILED` pendant la construction, avant tout intercepteur ou transport, même si un intercepteur court-circuiterait. L’URL résolue doit conserver l’origine de base et rester sous son répertoire ; les caractères de contrôle C0 (dont tab, CR et LF), les barres obliques inverses, `?`, `#` et les traversées de répertoire dans le chemin sont rejetés. Les formes ressemblant à un schéma et celles relatives au protocole sont rejetées même avec des espaces initiaux ; un espace ordinaire à l’intérieur est autorisé et envoyé sous la forme `%20`. Le `req.endpoint` final d’un intercepteur est validé contre son `req.baseEndpoint` final avec la même règle, mais il peut remplacer délibérément la base par une autre URL absolue valide. Les erreurs d’URL déterministes ne sont jamais retentées.

`withCredentials(true)` est les credentials Fetch pour HTTP/SSE — pas l’auth WebSocket. Utilise une politique cookie/session revue, un sous-protocole, ou un ticket de connexion de courte durée. Ne mets pas de credentials généraux ni de secrets longue durée dans la query string.

## Fermeture et propriété

`session.close(code?, reason?)` demande la fermeture terminale et arrête le heartbeat. Le code doit être `1000` ou `3000..4999` ; la reason ≤ 123 octets UTF-8. Des arguments de close invalides lèvent une erreur avant de changer l’état. Utilise-le avec `await session.closed` quand tu as besoin d’une raison de close manuel ou du résultat terminal logique.

Le `signal` ou `abort` passé à `execute` reste attaché à la session ouverte. Un abort en forme de timeout (`TimeoutError` ou `ERR_TIMEOUT`) la termine en `'error'` (`NET_TIMEOUT`). Toute autre raison d’abort la termine en `'aborted'`, et `receive` rejette avec cette raison elle-même, pas une nouvelle `AbortError`. `timeout` n’est qu’un délai de démarrage.

`session.closed` est l’instantané terminal logique : `'closed'`, `'aborted'`, ou `'error'`, avec `code` / `reason` / `wasClean` natifs optionnels et une `cause` pour aborted/error. Les champs de close natif observés l’emportent sur le fallback demandé par le propriétaire.

La méthode de libération asynchrone standard demande une fermeture native best-effort, puis attend le teardown du cycle de vie, de la pompe de messages, des timers, des écouteurs, de la queue et des références de socket possédés par Defjs. Si un événement de close n’est pas observé dans la seconde, le teardown est forcé et la libération peut être rejetée avec une `DOMException` nommée `TimeoutError` ; cela ne prouve pas que la connexion TCP physique s’est fermée. Les appels répétés de la libération partagent le même teardown. Les implémentations structurelles de session custom doivent maintenant fournir le même contrat `[Symbol.asyncDispose](): PromiseLike<void>`.

## Frontière GraphQL

Defjs fournit un struct entrant, un struct sortant, et un cycle de vie de session logique. Il n’implémente **pas** un protocole applicatif WebSocket. Les fonctions GraphQL-over-WebSocket — connection init, IDs d’opération, `next`/`error`/`complete`, dispose, replay d’abonnement — sont hors du contrat core.

Utilise un client de protocole comme `graphql-ws` quand le serveur exige ce protocole, ou modélise les frames avec `defineWebSocket(...)`. Pose un sous-protocole statique comme `graphql-transport-ws` sur `protocols`. Un struct seul ne négocie pas la sémantique GraphQL.
