# Architecture du cœur

Defjs repose sur une frontière fondamentale : **un SDK définit le contrat réseau ; l'application consommatrice possède l'exécution.** Chaque choix de conception dans `@defjs/core` découle de cette séparation.

## 1. Définition vs exécution

Un package de SDK exporte des opérations (`defineRequest`, `defineEventStream`, `defineWebSocket`) et des contrats de données (`struct`). Il n'appelle jamais `createClient`, ne stocke aucun singleton de client et ne lit aucune variable d'environnement.

Comme `getOrder` ne capture aucun état de client :

- Une interface navigateur, une tâche de fond, un gestionnaire de requêtes SSR et un test unitaire peuvent appeler la même opération `getOrder` avec des configurations de `Client` différentes.
- Les plugins de frameworks (`@defjs/react`, `@defjs/vue`) et le plugin middleware d'observabilité (`@defjs/opentelemetry-server`) se greffent sur le `Client` applicatif, préservant ainsi le package SDK publié de toute dépendance tierce.

## 2. Placement explicite des entrées et alias bidirectionnels

Dans Defjs, `input` déclare ce que l'appelant transmet, `struct` régit l'encodage et le décodage des valeurs, et `builder` place chaque valeur sur la requête (`path`, `query`, `headers`, `body`).

- **Aucune inférence magique** : Si une opération déclare un `input`, elle doit obligatoirement fournir un `builder` synchrone et pur. La destination des champs n'est jamais devinée à partir du nom des paramètres.
- **`.alias(wireName)` bidirectionnel** : Déclarer `.alias("customer_name")` sur un champ de struct conserve `customerName` dans le typage TypeScript tout en assurant automatiquement la conversion vers et depuis `"customer_name"` sur le réseau.

## 3. Une déclaration est une affirmation [#declaration-is-an-assertion]

Six règles strictes régissent la manière dont Defjs lit les réponses HTTP :

### Règle 1 : Ce que vous déclarez est ce que vous affirmez

`output` affirme la structure d'un corps `2xx`. `error` affirme la structure d'un corps non-`2xx`. Une déclaration est une garantie d'exécution, et non un simple indice au mieux.

### Règle 2 : `ok` (`200..299`) est la seule bifurcation

Une réponse `2xx` est décodée exclusivement avec `output`. Tout autre statut (`3xx`, `4xx`, `5xx`) est décodé exclusivement avec `error`. Defjs ne bascule jamais de l'un vers l'autre en repli.

### Règle 3 : Tout écart par rapport à l'affirmation est un échec explicite

Defjs choisit le côté de la réponse avec `response.ok` : `output` pour `2xx`, `error` pour un non-`2xx`. Seul un struct JSON déclaré de ce côté déclenche le décodage et peut produire `RES_MEDIA_TYPE_INVALID` ou `RES_DECODE_FAILED` ; son `Content-Type` est vérifié **avant** de lire les octets du corps. Une page de passerelle HTML non-`2xx` produit `RES_MEDIA_TYPE_INVALID` seulement lorsqu'un struct JSON `error` est déclaré. Sans déclaration pour le côté actif, le corps n'est pas lu ; une réponse non-`2xx` renvoie un `HTTP_STATUS` non décodé.

| Ce qui a échoué pendant la lecture de la réponse          | Fault retourné                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------ |
| Le media type ne correspond pas au JSON déclaré           | `RES_MEDIA_TYPE_INVALID` (le corps n'est jamais lu)                |
| Les octets ne peuvent être décodés dans la représentation | `RES_DECODE_FAILED`                                                |
| La valeur décodée échoue à la validation `struct`         | `RES_STRUCT_MISMATCH` (HTTP) / `RES_DECODE_FAILED` (handshake SSE) |
| Statut non-`2xx` avec struct `error` décodé               | `HTTP_STATUS` avec `error.data` typé                               |
| Statut non-`2xx` avec `error` omis                        | `HTTP_STATUS` avec `error.data: undefined`                         |

### Règle 4 : Un décodage échoué n'a pas de corps

Un corps n'existe qu'après avoir franchi le décodage et la validation. En cas d'échec de décodage, le `response` du fault est typé comme `HttpMeta` (qui ne possède aucune propriété `body`), et l'erreur d'analyse/validation est rattachée à `fault.cause`.

### Règle 5 : Omettre un côté revient à renoncer à le lire

Omettre `output` signifie que les corps `2xx` ne sont jamais lus. Omettre `error` signifie que les corps non-`2xx` ne sont jamais lus — même si le serveur a envoyé un JSON invalide sur un code `500`.

### Règle 6 : `3xx` n'est pas un statut de succès

`ok` signifie strictement `200 <= status < 300`. Un code `304 Not Modified` est non-`2xx` : laissez `error` non déclaré et traitez `HTTP_STATUS` (ou interceptez `304` dans un intercepteur ETag), ou déclarez `struct.string()` si vous attendez un corps texte vide.

## 4. Tuples de résultat propres au transport

Les trois transports renvoient un tuple error-first de trois éléments plutôt que de lever une exception au point d'appel :

- **HTTP** → `[error, data, response]` — charge utile décodée + `DecodedResponse<T>` (`HttpMeta` quand `output` est omis).
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + instantané du handshake initial.
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + instantané de la connexion initiale.

Les clients portent la configuration, pas les connexions actives. L'appelant qui initie une requête HTTP, un flux SSE ou une session WebSocket en possède l'annulation ou la fermeture (`AbortSignal` pour HTTP ; `await using` ou `.close()` + `await .closed` pour SSE et WebSocket).
