# Conception de SDK public [#public-sdk-design]

Lorsque votre entreprise ou votre équipe plateforme publie un SDK TypeScript officiel destiné à des développeurs externes (par exemple un SDK de stockage d'objets, un SDK de passerelle de paiement ou un SDK de plateforme SaaS), le paquet du SDK doit **définir le contrat réseau sans imposer l'environnement d'exécution**.

En prenant pour modèle concret un **SDK compatible Amazon S3 (`@company/s3-sdk`)**, ce guide montre comment concevoir un SDK public multi-modules articulé autour de `models/` et de `services/` composés de fonctions pures.

---

## 1. Pourquoi les SDK publics tirent parti de la séparation de Defjs

Les SDK traditionnels embarquent une classe de client lourde (`new S3Client({ region, credentials })`) étroitement couplée à des classes de commandes ou à des classes de services statiques. Écrire votre SDK public avec `@defjs/core` résout quatre problèmes récurrents pour vos utilisateurs externes :

1. **Flexibilité multi-environnements et bac à sable (sandbox)** : Comme `@company/s3-sdk` ne lie aucun endpoint ni aucun client, un client peut faire pointer exactement les mêmes définitions d'opérations vers la production (`https://s3.us-east-1.amazonaws.com`), un bac à sable de préproduction, Cloudflare R2 ou un conteneur MinIO local lors des tests CI.
2. **100 % de _tree-shaking_ par le bundler** : Exporter des fonctions pures autonomes (`listBuckets`, `listObjectsV2`, `getObject`, `putObject`, `deleteObject`) avec `"sideEffects": false` garantit qu'un bundle navigateur qui n'appelle que `getObject` et `putObject` élimine tous les autres endpoints et modèles.
3. **Validation à l'exécution + types statiques depuis une source unique** : Les consommateurs externes bénéficient à la fois des types TypeScript à la compilation (`Infer<typeof ...>`) et de la validation des réponses et des erreurs à l'exécution (`struct`), ce qui les protège contre les charges utiles réseau inattendues et convertit automatiquement les champs `snake_case` ou les chaînes de dates ISO.
4. **Contrôle total sur l'authentification, les réessais et la télémétrie** : Les clients attachent leurs propres intercepteurs de rotation d'identifiants, leurs politiques `withRetry(...)`, leurs répartiteurs de charge multi-régions (`withBalancer(...)`) ou OpenTelemetry côté serveur (`@defjs/opentelemetry-server`) sur leur propre `Client`.

## 2. Structure de répertoires du paquet

Découpez le paquet du SDK en `src/models/` (structures de données) et `src/services/` (définitions d'opérations pures regroupées par ressource), avec un fichier barrel à plat `src/index.ts` :

```text
@company/s3-sdk/
├── src/
│   ├── models/                 # 1. Schémas struct partagés + types Infer<typeof ...>
│   │   ├── common.ts           #    StorageClass, S3Error
│   │   ├── bucket.ts           #    Bucket, ListBucketsOutput
│   │   └── object.ts           #    ObjectSummary, ListObjectsOutput
│   ├── services/               # 2. Fonctions defineRequest pures par domaine de ressource
│   │   ├── buckets.ts          #    BucketInput, listBuckets, headBucket, deleteBucket
│   │   └── objects.ts          #    listObjectsV2, headObject, getObject, putObject, deleteObject
│   └── index.ts                # 3. Exports barrel pour les imports racine et compatibles tree-shaking
├── package.json                # sideEffects: false, peerDependencies: { "@defjs/core": "^0.8.0" }
└── tsconfig.json
```

### Concevoir des contrats d'opération ergonomiques

- **Aplatissez les entrées de l'appelant et répartissez-les dans `builder`** : Dans `putObject`, les appelants passent un unique objet ergonomique (`{ bucket, key, body, contentType, storageClass }`). Le `builder` synchrone répartit cette entrée entre `path` (`:bucket/:key`), `headers` (`content-type`, `x-amz-storage-class`) et le `body` binaire (`Blob`). Dans `listObjectsV2`, `builder` associe `continuationToken` et `maxKeys` aux paramètres de requête `continuation-token` et `max-keys` de S3 aux côtés de `list-type: 2`.
- **Adaptez `output` à la charge utile réseau** :
  - **JSON structuré (`listBuckets`, `listObjectsV2`)** : Déclarez un `struct.object(...)` avec des correspondances `.alias()` et des champs `struct.date()`.
  - **Charge utile binaire (`getObject`)** : Déclarez `output: struct.blob()` (ou `struct.arrayBuffer()`).
  - **Corps vide (`headBucket`, `headObject`, `putObject`, `deleteObject`)** : Omettez `output` afin que les réponses `HEAD`, `200` et `204` de zéro octet réussissent sans tenter de décodage JSON, tout en permettant aux appelants de lire les en-têtes de réponse (`response.headers.get("etag")`) depuis le troisième élément du tuple.

## 4. Comment les développeurs externes consomment votre SDK

Les applications externes installent `@company/s3-sdk` aux côtés de `@defjs/core`, configurent leur propre `Client` avec leur endpoint et leur intercepteur de signature, puis invoquent directement vos opérations exportées comme des fonctions pures. L'exemple suit la gestion d'erreurs à la Go : `syncReport` effectue trois appels, elle nomme donc chaque erreur d'après son étape (`putErr`, `listErr`, `getErr`), renvoie un tuple error-first et enveloppe l'étape en échec avec `new Error("put object", { cause: putErr })`, comme le `fmt.Errorf("put object: %w", err)` de Go. Seul `main`, le sommet du programme, traite l'erreur en la journalisant :
