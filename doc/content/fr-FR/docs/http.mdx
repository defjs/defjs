# HTTP

Le SDK définit la méthode, le chemin relatif, le mapping d’entrée, la réponse et le contrat d’erreur de chaque opération HTTP. L’application importe cette opération, configure son propre client, l’appelle et traite le résultat. La même définition peut être livrée dans un paquet npm ou partagée localement.

Garde les adresses de service et les identifiants dans la configuration du client. L’appelant possède l’annulation et toute politique de nouvelle tentative d’une écriture ; une requête annulée peut déjà avoir atteint le service.

## Résoudre l’URL

`withEndpoint(...)` a besoin d’une URL absolue valide. Le pathname de l’endpoint reste un répertoire ; query et hash sont jetés avant la résolution de l’URL de requête. Un endpoint de base absent, relatif ou invalide échoue avec `REQ_BUILD_FAILED` pendant la construction de la requête, avant tout intercepteur ou transport, même si un intercepteur court-circuiterait la requête. HTTP, SSE et WebSocket partagent cette règle.

<include cwd>examples/http/resolve-url.ts#example</include>

Les placeholders de chemin sont des scalaires bruts, encodés exactement une fois. Les valeurs vides et `.` / `..` sont rejetés. Les slashes, `?`, `#`, `%`, espaces et Unicode dans un placeholder restent un seul segment encodé — ne pré-encode pas.

Un nom de placeholder commence à `:` et court jusqu’au `/` suivant ou à la fin du chemin : `/files/:name.json` nomme le paramètre `name.json`, pas `name`. Un deux-points littéral dans un segment statique n’est pas pris en charge.

Les chemins de définition ne peuvent pas ressembler à un scheme ni être protocol-relative (y compris avec des espaces initiaux), ni contenir des caractères de contrôle C0 (y compris tab, CR et LF), des antislashs, `?` ou `#`. Un espace intérieur simple est autorisé et envoyé comme `%20`. Après résolution, l’URL doit garder l’origine de base et rester sous son répertoire ; un chemin tel que `../users` ne peut pas s’en échapper. Les chemins illégaux échouent avec `REQ_BUILD_FAILED` pendant la construction, avant le transport. Le `req.endpoint` final d’un intercepteur est vérifié contre son `req.baseEndpoint` final avec la même règle ; un intercepteur peut délibérément remplacer la base par une autre URL absolue valide. Les erreurs d’URL déterministes ne sont jamais réessayées.

L’encodeur de query par défaut accepte les scalaires et les tableaux de scalaires (les tableaux répètent la clé). Un objet imbriqué échoue avec `REQ_BUILD_FAILED` sauf si le client a `withQuerySerializer(...)`. `null` dans `path`, `query` ou `headers` échoue de la même façon. Les valeurs `undefined` de query et d’en-tête sont omises. Un placeholder de chemin `undefined` ou manquant échoue avec `REQ_BUILD_FAILED`.

## Placer l’entrée

Le struct encode la valeur. Le builder la place. Un `input` déclaré exige toujours un `builder` explicite. `input` ne fait que définir les paramètres ; seul le builder décide où va chaque valeur. Seules les définitions sans `input` peuvent omettre `builder`.

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

Ce corps est `{"display_name":"Ada"}` avec `application/json`. Le nom wire de l’en-tête est `x-request-id`. Les appelants et les résultats parsés gardent `displayName`.

Préfère remettre la valeur typée plutôt que d’épeler les clés wire. L’alias est déclaré une fois sur le champ et s’applique dans les deux sens : `output` / `error` / événements / frames entrantes décodent `display_name` en `displayName`, et `body: input.order` réécrit tout l’arbre. Le même struct `User` peut être un corps de création et une sortie de lecture. Une clé écrite à la main est l’exception : l’objet parent est anonyme, donc l’alias ne tourne pas.

| Expression du builder                          | Sur le fil                                               |
| ---------------------------------------------- | -------------------------------------------------------- |
| `body: input.profile`                          | Objet typé : alias et encodage `Date` / `bigint`         |
| `body: { profile: input.profile }`             | Clés extérieures littérales, objet intérieur encore typé |
| `body: { ...input.profile, role: 'admin' }`    | Le spread garde le struct ; la clé en plus est littérale |
| `body: { name: input.profile.displayName }`    | Parent anonyme : l’alias ne s’applique pas               |
| `query: input.filter` / `headers: input.trace` | Objets plats typés : l’alias devient la clé wire         |

Étaler un objet typé et poser aussi sa clé wire (`display_name` à côté de `displayName`) est `REQ_BUILD_FAILED`. Un objet imbriqué dans `path` ou `headers` échoue de la même façon.

Le guide est choisi à chaque nœud, pas seulement à la racine. Un nouvel objet sous un parent anonyme garde les clés que tu as écrites. Le même objet sous un parent typé utilise le struct de ce champ.

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

Quand un guide d’union correspond à plus d’une branche, chaque branche est encodée et comparée. Une sortie wire identique est gardée ; une différence est `REQ_BUILD_FAILED`.

Une intersection mixte qui contient une partie non objet est marquée, quand elle est parsée, avec la conjonction des tags des parties qui ont correspondu ; une valeur d’intersection mixte nouvellement écrite qui n’a pas été parsée est un objet anonyme.

### Query

La forme de query imbriquée (`a[b]`, `a.b`, listes à virgules) est une convention de backend, donc le hook est sur le client :

<include cwd>examples/http/query-serializer.ts#example</include>

`query` ici est l’objet wire encodé. Les aliases sont déjà appliqués, donc le serializer voit les clés wire. La chaîne renvoyée est stockée comme `queryString`, puis assignée à `URL.search`, qui encode en pourcent les espaces, `#`, guillemets et le non-ASCII. Defjs ne livre pas d’encodeur de query imbriquée.

Sans serializer, les tableaux répètent les clés et un objet imbriqué est `REQ_BUILD_FAILED`. Renvoyer `URLSearchParams` depuis le builder utilise cette valeur telle quelle et saute le serializer. Le serializer n’est pas appelé quand il n’y a pas de query. Les intercepteurs voient ensuite `queryParams` comme `new URLSearchParams(queryString)`.

### Corps

La première correspondance gagne :

| Valeur de `body`                                                 | Envoyé comme                                                                                  | Content type par défaut                                     |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| omis / `undefined`                                               | pas de corps                                                                                  | —                                                           |
| objet typé dont la racine a un codec `urlencoded` ou `formData`  | `URLSearchParams` / `FormData` ; les clés sont des noms wire ; les tableaux répètent les clés | type de formulaire / boundary de la plateforme              |
| `FormData`, `URLSearchParams`                                    | tel quel                                                                                      | idem ; Defjs efface un `Content-Type` périmé sur `FormData` |
| `Blob` / `File`                                                  | tel quel                                                                                      | `blob.type`, ou `application/octet-stream`                  |
| `ArrayBuffer`, `TypedArray`, `DataView`                          | tel quel                                                                                      | `application/octet-stream`                                  |
| `ReadableStream`                                                 | en flux (`duplex: 'half'` quand le runtime le permet)                                         | `application/octet-stream`                                  |
| `string`                                                         | tel quel                                                                                      | `text/plain;charset=UTF-8`                                  |
| objet simple, tableau, nombre, booléen, `null`, `Date`, `bigint` | encodé, puis `JSON.stringify`                                                                 | `application/json`                                          |

HTTP garde le type inféré du corps du builder dans le champ simple `request.bodyContentType`, qui survit aux copies `{ ...req }` ; il n’écrit jamais cette inférence dans `request.headers`. Un en-tête `content-type` explicite gagne toujours, qu’il soit posé par le builder, les défauts du client, un intercepteur ou une requête `fetchHandler` brute, y compris quand la progression d’envoi convertit le corps en flux. `bodyContentType` ne s’applique que tant que `body` est la valeur du builder ; un corps de remplacement est détecté à nouveau, donc un intercepteur déclare son type avec un en-tête `content-type`. `body: undefined` n’envoie aucun Content-Type inféré par la bibliothèque. FormData est l’exception : son content type doit utiliser la boundary de la sérialisation réelle. Le tag de codec ne s’applique qu’à la racine du corps : `body: { meta: input.form }` est du JSON, et les champs du formulaire sont des champs JSON ordinaires. Une string est du texte brut ; une string JSON telle que `"abc"` a besoin de `JSON.stringify` plus `application/json`. Les champs `undefined` sont omis ; un champ `nullable` envoyé comme `null` est le JSON `null`.

Le JSON doit être des données JSON de bout en bout : objets simples, tableaux, strings, nombres finis, booléens et `null`, plus les valeurs dont `toJSON()` renvoie cela, comme `Date` ou `URL`. Tout le reste, à la racine ou imbriqué, échoue avec `REQ_BUILD_FAILED` avant que quoi que ce soit soit envoyé, au lieu d’être envoyé comme `{}`, `null` ou pas de corps du tout : un `Map` ou un `Set`, une instance de classe sans `toJSON`, une fonction, `NaN`, un `Readable` Node, ou un itérable ou async itérable, y compris un objet littéral avec une méthode `Symbol.iterator` ou `Symbol.asyncIterator`. Le message nomme le champ. Un objet itérable donné comme `query` ou `headers` échoue de la même façon au lieu d’être écarté ; passe les paires d’en-têtes comme un tableau. Envoie un flux comme un `ReadableStream` Web : `ReadableStream.from(iterable)` ou `Readable.toWeb(readable)`. Le type `body` rejette la plupart de ces cas à la compilation ; une valeur `interface` ou une instance de classe a besoin de `{ ...value }`.

`GET` et `HEAD` ne peuvent pas renvoyer un corps — c’est une erreur de type. Les builders WebSocket ne peuvent pas renvoyer `headers` ni `body`.

<include cwd lang="typescript">

</include>

`JSON.stringify`, `qs` ou protobuf que tu exécutes toi-même voient les noms logiques. L’alias ne s’applique pas sur ce chemin. Il n’y a pas de `struct.encode` public.

Un builder peut brancher sur l’entrée réelle et renvoyer un corps différent par cas (records JSON, un `File` ou `URLSearchParams`). Les `Headers` natifs sont aussi transmis et ne sont pas ré-encodés.

## Comment un corps est lu

`output` est un Struct pour le corps 2xx ; `error` est un Struct pour tout le reste. Le kind du struct
choisit la représentation : `string` est du texte brut, `blob` / `file` sont des blobs, `arrayBuffer` est des octets,
et tout autre kind est du JSON. Si aucun des deux côtés n’est déclaré, le corps n’est jamais lu.

Ordre des opérations :

1. `ok` choisit le côté : `output` pour un 2xx, `error` pour tout le reste. Jamais les deux.
2. Rien de déclaré pour ce côté → le corps n’est jamais lu. Un 2xx réussit avec `data === undefined` ;
   un non-2xx est `HTTP_STATUS` avec `data === undefined`. Un corps illisible sur un côté que tu n’as pas
   déclaré est ignoré, y compris le fait qu’il n’ait pas pu être lu.
3. Pour une représentation JSON, le media type est vérifié **avant** la lecture du corps. Un écart est
   `RES_MEDIA_TYPE_INVALID` et rien n’est parsé ni décodé. Texte, blob, fichier et octets sautent cette vérification.
4. La représentation est lue. Un échec est `RES_DECODE_FAILED`. Le JSON venu du transport est parsé une fois :
   une string sur cette valeur est une racine de string JSON et n’est pas parsée à nouveau ; les octets et les blobs sont bruts et
   sont parsés une fois.
5. Le Struct parse la valeur. Un échec est `RES_STRUCT_MISMATCH`.
6. 2xx → résultat et un `response.body` typé ; non-2xx → `data` typé sur `HTTP_STATUS`.

Le transport Fetch intégré effectue les étapes 3 et 4 pour un côté déclaré pendant que la réponse est encore
dans la chaîne d’intercepteurs, donc les intercepteurs reçoivent une réponse dont `body` est déjà le JSON parsé,
le texte, le `Blob` ou les octets. Un échec de media type ou de lecture rejette `next()` en `BodyFailure` avant que la chaîne
se résolve (`RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED`, ou `NET_BODY_INCOMPLETE` quand le flux casse).
L’étape 5 tourne une fois, après la chaîne. `makeResponse(...)` saute cette lecture dans la chaîne. Son corps n’est décodé
qu’après la chaîne, dans la même étape que la validation Struct. Sur une représentation JSON, un corps string est parsé
là ; une valeur que le transport a déjà parsée n’est pas parsée à nouveau.

Une réponse réussie est un `DecodedResponse<T>` : `url`, `status`, `statusText`, `headers`, `ok` et
un `body` typé. Là où rien n’a été décodé, tu obtiens `HttpMeta` — les mêmes champs sans `body`. `ok`
veut seulement dire `200 <= status < 300`. Ni l’un ni l’autre n’est une `Response` native. Un échec de transport est un fault, donc
il n’y a pas de réponse de statut 0 qui en tienne lieu.

## Annuler le travail [#cancel-the-work]

Passe `abort` sur un client dérivé. Une échéance est `AbortSignal.timeout(ms)` et se classe en `NET_TIMEOUT`. Un abort manuel se classe en `NET_ABORTED`. Il n’y a pas de champ `timeout`, pas de champ `signal`, et pas d’échéance par défaut au niveau du client. `abort` est le signal de l’appel ; combine les signaux avec `AbortSignal.any` dans le code applicatif. Combine un signal d’appelant avec une échéance grâce à `AbortSignal.any` dans le code applicatif.

<include cwd>examples/http/cancel.ts#example</include>

Annulation reconnue → `NET_ABORTED` ; un abort d’échéance → `NET_TIMEOUT` ; `throw` d’un intercepteur → `EXT_INTERCEPTOR_FAILED`, sauf `ERR_ABORTED` / `ERR_TIMEOUT`, qui donnent `NET_ABORTED` / `NET_TIMEOUT` ; autres échecs Fetch → `NET_UNREACHABLE`. Annuler après que le serveur a accepté une écriture ne **prouve pas** que l’écriture a été annulée.

## Identifiants et XSRF

`withCredentials(true)` pose Fetch `credentials: 'include'` pour HTTP et SSE. Il ne crée pas `Authorization` et ne configure pas l’auth WebSocket. `false` laisse les identifiants non spécifiés.

`withXSRF(...)` est HTTP seulement. Défauts : `cookieName: 'XSRF-TOKEN'`, `headerName: 'X-XSRF-TOKEN'`. L’en-tête n’est injecté que pour les méthodes non sûres et seulement si l’appelant ne l’a pas déjà posé. Dès que `location` existe, y compris dans un Worker, l’URL de requête résolue doit correspondre à `location.origin` ; une requête cross-origin n’appelle pas `tokenProvider`. La lecture du cookie exige séparément `document`. Saute `GET`, `HEAD`, `OPTIONS`, `TRACE`. Dans un Worker ou un serveur, passe un `tokenProvider` synchrone borné à la requête si tu as besoin de l’injection.

Garde les identifiants, les jetons XSRF et les query strings hors des journaux de routine. N’utilise pas les query params comme canal général d’identifiants.

## Progression et la frontière Fetch

`onDownloadProgress` tourne pendant qu’un corps de réponse déclaré est lu. `loaded` compte les octets lus depuis le flux de réponse, que Fetch peut déjà avoir décompressés. `lengthComputable` n’est vrai qu’avec un `Content-Length` positif et un `Content-Encoding` absent ou `identity`. Les autres encodages, y compris gzip et br, signalent `total: 0` et `lengthComputable: false`, donc les octets décodés ne sont jamais comparés à une longueur wire compressée. Pas de struct pour ce côté → le corps n’est pas lu → pas de progression de lecture du corps.

`onUploadProgress` signale la progression d’un corps `ReadableStream<Uint8Array>` à mesure que Fetch le lit, pas quand le serveur l’acquitte. Cette progression n’est signalée que là où le runtime peut transmettre les corps de requête en flux : dans Bun et Node, Defjs convertit aussi les corps `Blob` / `File`, `ArrayBuffer` et `FormData` en flux, ce qui permet également d’en signaler la progression. Dans les runtimes serveur, FormData avec `onUploadProgress` utilise directement le flux sérialisé, conserve sa boundary multipart et est envoyé sans `Content-Length` généré par la bibliothèque (transfert chunked en HTTP/1.1), donc la progression et l’abort fonctionnent sans mettre tout le corps en tampon. Son total est inconnu sauf si un `Content-Length` explicite valide le fournit. Pour un endpoint qui exige `Content-Length`, comme certaines destinations d’envoi avec URL présignée, omets `onUploadProgress` ; le Fetch de la plateforme envoie alors FormData avec sa longueur. L’annulation relâche le flux enveloppé. Les navigateurs, Workers compris, sont exclus, parce que Chromium ne transmet un corps de requête en flux qu’en HTTP/2 ou plus et que Firefox ne peut pas en transmettre du tout ; là, ces corps sont envoyés inchangés et `onUploadProgress` n’est pas appelé. JSON, texte, `URLSearchParams` et corps typed-array sont envoyés en entier et ne produisent pas d’événements. `total` est `0` (donc `lengthComputable` est `false`) pour un flux sans longueur connue. Un corps `ReadableStream` sur un runtime qui ne peut pas transmettre les requêtes en flux, comme Firefox, échoue avec `ENV_UNSUPPORTED` avant que quoi que ce soit soit envoyé ; le message de cause est `ERR_STREAMING_REQUEST_UNSUPPORTED`. Dans Chromium, un corps `ReadableStream` a besoin d’HTTP/2 ou plus ; en HTTP/1.1 l’appel échoue avec `NET_UNREACHABLE`. `onDownloadProgress` se comporte de la même façon dans chaque runtime.

Un callback de progression qui lève ou rejette fait échouer l’appel avec `EXT_OBSERVER_FAILED` et la valeur levée comme `cause`, pour les téléchargements comme pour les envois. L’annulation par l’appelant signale toujours `NET_ABORTED`, ou `NET_TIMEOUT` quand la raison de l’abort est un timeout.

`fetchHandler(httpRequest, fetchImpl?)` est la frontière Fetch de plus bas niveau : résout l’URL, appelle Fetch, lit la représentation et renvoie `HttpResponse`. Les handles HTTP et SSE par défaut résolvent `globalThis.fetch` à chaque appel, donc un remplacement installé après l’import est utilisé. HTTP n’utilise `(url, init)` que pour le Fetch de plateforme non modifié ; un global remplacé ou un handle personnalisé reçoit une `Request` native. Importer Core sans Fetch est valide ; un appel HTTP/SSE par défaut échoue avec `ENV_UNSUPPORTED` si Fetch manque encore, tandis que les handles personnalisés restent utilisables. Cette frontière ne **valide pas** l’entrée de l’opération, ne dispatche pas `output` et ne fait pas tourner les intercepteurs. Utile pour des tests de transport injecté — pas un substitut de l’appel de l’opération.

## Limites de rejeu

Defjs ne réessaie **pas** HTTP de lui-même. Réessayer une lecture demande encore une politique revue de timeout, de réseau et de doublon. Réessayer une mutation demande des octets rejouables, le support serveur, une clé d’idempotence liée au scope d’auth + aux octets de la requête, et une politique de doublon côté récepteur.

Une frontière client ou Fetch ne peut pas savoir si une écriture échouée a été appliquée. Garde les décisions de replay dans l’app ou un intercepteur revu. Les intercepteurs peuvent court-circuiter ou remplacer la requête bas niveau ; le statut et le corps finaux doivent quand même satisfaire le contrat de l’opération.
