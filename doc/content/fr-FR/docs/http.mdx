# Opérations HTTP

Un SDK définit chaque opération HTTP avec `defineRequest` : sa méthode, son patron de chemin, son schéma `input`, son `builder` synchrone et ses schémas de réponse `output` / `error`. Les applications consommatrices importent l'opération, lui transmettent leur `Client` configuré et traitent le tuple `[error, data, response]` renvoyé.

### Bonnes pratiques de conception d'un SDK

- **Une opération par définition** : Isolez chaque méthode, chemin et contrat dans sa propre définition pour permettre aux applications de tree-shaker les opérations non utilisées.
- **Définissez un nom d'opération statique (`operation`)** : Choisissez un identifiant de faible cardinalité tel que `"orders.read"`. Les plugins de télémétrie (`@defjs/opentelemetry-server`) et les intercepteurs de journalisation l'utilisent sans exposer d'URL ou d'identifiants utilisateur.
- **N'embarquez jamais de client dans le SDK** : N'exportez que des définitions, des schémas `struct` et des types.

## 2. Résolution d'URL et paramètres de chemin

`withEndpoint(...)` exige une URL absolue valide. Son chemin agit comme répertoire de base (toute query string ou ancre présente sur l'endpoint de base est ignorée).

<include cwd>examples/http/resolve-url.ts#example</include>

- **Placeholders de chemin (`:name`)** : Encodés exactement une fois en un segment de chemin unique. Les slashes, `?`, `#`, `%`, espaces et caractères Unicode restent au sein de ce segment — ne pré-encodez pas vos valeurs. Les chaînes vides, `.` et `..` échouent avec `REQ_BUILD_FAILED`.
- **Confinement d'origine et de répertoire** : Les chemins de définition ne peuvent pas être des URL absolues, ni protocol-relative (`//...`), ni contenir de caractères de contrôle C0, d'antislashs, `?`, `#`, ni s'échapper du répertoire de base (`../`). Tout écart échoue avec `REQ_BUILD_FAILED` avant même l'appel des intercepteurs ou du transport.

## 3. Placer l'entrée avec `builder`

Dès qu'une opération déclare un `input`, elle **doit** fournir un `builder` synchrone et pur renvoyant `{ path?, query?, headers?, body? }`. Seules les opérations sans `input` peuvent omettre le `builder`.

### Comment `builder` encode les alias de champs

| Expression du builder                          | Sortie réseau                                                        |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| `body: input.profile`                          | Struct typé : `.alias()` et codecs `Date` / `bigint` s'appliquent    |
| `body: { profile: input.profile }`             | Clé externe `profile` littérale ; l'objet interne conserve ses alias |
| `body: { ...input.profile, role: "admin" }`    | Le spread préserve les alias du struct ; `role` reste littéral       |
| `body: { name: input.profile.customerName }`   | Objet anonyme : les clés sont littérales                             |
| `query: input.filter` / `headers: input.trace` | Objets typés plats : le `.alias()` du champ devient la clé réseau    |

### Sérialisation personnalisée des requêtes (query)

Par défaut, les scalaires et tableaux de scalaires (clés répétées) sont encodés directement, tandis que les objets imbriqués échouent avec `REQ_BUILD_FAILED`. Si votre backend attend une syntaxe d'objets imbriqués (`filter[status]=paid`), configurez `withQuerySerializer` sur le client :

### Formats du corps de requête

`GET` et `HEAD` ne peuvent pas transporter de corps. Pour les autres méthodes, le format est déterminé selon la valeur renvoyée par le `builder` :

| Valeur de `body`                                                      | Envoyé sur le réseau comme                       | `Content-Type` par défaut                 |
| --------------------------------------------------------------------- | ------------------------------------------------ | ----------------------------------------- |
| `undefined` / omis                                                    | Aucun corps                                      | —                                         |
| Struct racine avec codec `urlencoded` / `formData`                    | `URLSearchParams` / `FormData` (alias appliqués) | Type de formulaire / boundary multipart   |
| `FormData` ou `URLSearchParams` natifs                                | Transmis tel quel                                | Boundary multipart / urlencoded           |
| `Blob` / `File`                                                       | Transmis tel quel                                | `blob.type` ou `application/octet-stream` |
| `ArrayBuffer`, vue typée, `DataView`, `ReadableStream`                | Octets bruts / flux                              | `application/octet-stream`                |
| `string`                                                              | Texte UTF-8                                      | `text/plain;charset=UTF-8`                |
| Objet simple, tableau, nombre fini, booléen, `null`, `Date`, `bigint` | JSON encodé par struct                           | `application/json`                        |

Les valeurs non représentables en JSON (`NaN`, `±Infinity`, `Map`, `Set`, fonctions, instances de classe sans `toJSON()`, ou itérables bruts) échouent immédiatement avec `REQ_BUILD_FAILED` au lieu d'être silencieusement sérialisées en `{}` ou `null`.

## 4. Décodage des réponses

`output` valide les réponses `2xx` ; `error` valide les réponses hors `2xx` (`3xx`, `4xx`, `5xx`). Le type de struct détermine la lecture du flux (`struct.string()` → texte, `struct.blob()` / `struct.file()` → `Blob`, `struct.arrayBuffer()` → `ArrayBuffer`, tout le reste → JSON) :

1. **Sélection de la branche selon `ok` (`200..299`)** : `output` pour `2xx`, `error` pour non-`2xx`.
2. **Renoncement en cas d'omission** : Si aucun struct n'est déclaré pour cette branche, le corps n'est jamais lu (`2xx` résout `data: undefined` + `HttpMeta` ; non-`2xx` résout `HTTP_STATUS` avec `data: undefined`).
3. **Vérification préalable du media type JSON** : Pour les structs JSON, un `Content-Type` non-JSON échoue avec `RES_MEDIA_TYPE_INVALID` avant que le corps soit lu ou recherché. Une réponse sans contenu (`HEAD`, `204`, `205`, `304`) est soumise à la déclaration comme n'importe quelle autre.
4. **Lecture et analyse** : Un flux illisible ou un JSON malformé échoue avec `RES_DECODE_FAILED` (ou `NET_BODY_INCOMPLETE` en cas d'interruption du flux).
   Une réponse sans contenu (`HEAD`, `204`, `205`, `304`) n'a pas de corps à lire : `struct.string()` obtient `''`, `struct.arrayBuffer()` un `ArrayBuffer` vide, et `struct.blob()` un `Blob` vide. Un struct JSON qui a passé l'étape 3 analyse les octets vides, ce qui échoue avec `RES_DECODE_FAILED`.
5. **Validation avec `struct`** : Toute non-conformité au schéma échoue avec `RES_STRUCT_MISMATCH`.

## 5. Annuler le travail et fixer des délais d'attente [#cancel-the-work]

Passez `signal` sur un client dérivé pour chaque appel : `client({ signal })`.

- **Délais d'attente (`NET_TIMEOUT`)** : Utilisez `AbortSignal.timeout(ms)`.
- **Annulation manuelle (`NET_ABORTED`)** : Utilisez un `AbortController`.
- **Signaux combinés** : Utilisez `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`.

## 6. Identifiants, XSRF et progression du transfert

- **`withCredentials(true)`** : Active Fetch `credentials: "include"` pour les requêtes HTTP et SSE.
- **`withXSRF(options?)`** : Depuis `@defjs/core/xsrf`. Dans un navigateur, lit le cookie XSRF (`XSRF-TOKEN` par défaut) et injecte l'en-tête (`X-XSRF-TOKEN`) sur les méthodes HTTP mutantes de même origine (`POST`, `PUT`, `PATCH`, `DELETE`). `withXSRF()` lève une erreur s'il manque `location` ou `document`, y compris dans un Worker. Le code isomorphe ajoute cette option seulement dans le navigateur. Un jeton venu d'une autre source se définit avec un intercepteur. Le contrôle de même origine s'applique à l'URL que la bibliothèque construit ; Fetch suit lui-même les redirections et conserve cet en-tête après une redirection vers une autre origine (il ne retire que `Authorization`). Pour refuser cela, voir [`withXSRF`](/fr-FR/api/core/withxsrf).
- **`onDownloadProgress` / `onUploadProgress`** : À passer via `client({ onDownloadProgress, onUploadProgress })`. La progression de téléchargement n'indique `lengthComputable: true` que si `Content-Length` est positif et si `Content-Encoding` est absent ou `identity`. La progression d'envoi n'est signalée que lorsque le corps de la requête est un `ReadableStream` que vous transmettez ; tout autre corps (`Blob`, `File`, `ArrayBuffer`, `FormData`, une chaîne, `URLSearchParams`) est envoyé tel qu'il a été construit et `onUploadProgress` n'est pas appelé, sur tous les runtimes. Un corps `ReadableStream` suit les règles de Fetch pour les corps de requête en flux, avec ou sans `onUploadProgress` : Chromium et WebKit ne l'acceptent qu'à partir de HTTP/2, donc l'appel échoue avec `NET_UNREACHABLE` sous HTTP/1.1 (Node.js et Bun acceptent HTTP/1.1) ; Firefox ne peut pas transmettre de corps de requête en flux et échoue avec `ENV_UNSUPPORTED` ; dans les navigateurs, une requête cross-origin a besoin d'un preflight CORS sauf si le navigateur détient un résultat de preflight en cache ; et une redirection 301, 302, 307 ou 308 échoue. Les navigateurs n'envoient pas de `Content-Length`. Le répartiteur de charge reçoit `{ attempted: false }` pour ces échecs, et pour un flux source qui lève, parce que `fetch` les signale comme la même erreur réseau qu'un endpoint injoignable ; un envoi en flux, à lui seul, ne peut donc pas détecter un endpoint hors service. Voir l'entrée `HttpProgressFn` de la référence d'API pour le détail. Un callback de progression qui lève fait échouer l'appel avec `EXT_OBSERVER_FAILED`.
