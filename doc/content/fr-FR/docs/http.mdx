# HTTP

Définis → exécute → branche sur le tuple → annule quand l’écran s’en va. C’est toute la boucle HTTP.

## Résoudre l’URL

`withEndpoint(...)` a besoin d’une URL absolue valide. Le pathname de l’endpoint reste un répertoire ; query et hash sont jetés avant la résolution de la commande. Un endpoint de base absent, relatif ou invalide échoue avec `REQ_BUILD_FAILED` pendant la construction de la requête, avant tout intercepteur ou transport, même si un intercepteur court-circuiterait la requête. HTTP, SSE et WebSocket partagent cette règle.

<include cwd>examples/http/resolve-url.ts#example</include>

Les placeholders de path sont des scalaires bruts, encodés exactement une fois. Les valeurs vides et `.` / `..` sont rejetées. Slashes, `?`, `#`, `%`, espaces et Unicode dans un placeholder restent un seul segment encodé — n’encode pas à l’avance.

Un nom de placeholder commence à `:` et court jusqu’au `/` suivant ou jusqu’à la fin du path : `/files/:name.json` nomme le paramètre `name.json`, pas `name`. Un deux-points littéral dans un segment statique n’est pas pris en charge.

Les paths de définition ne peuvent pas ressembler à un schéma ou être relatifs au protocole (même avec des espaces initiaux), ni contenir de caractères de contrôle C0 (dont tab, CR et LF), de barres obliques inverses, `?` ou `#`. Un espace ordinaire à l’intérieur est autorisé et envoyé sous la forme `%20`. Après résolution, l’URL doit conserver l’origine de base et rester sous son répertoire ; un path tel que `../users` ne peut pas s’en échapper. Les paths illégaux échouent avec `REQ_BUILD_FAILED` pendant la construction, avant le transport. Le `req.endpoint` final d’un intercepteur est vérifié contre son `req.baseEndpoint` final avec la même règle ; un intercepteur peut remplacer délibérément la base par une autre URL absolue valide. Les erreurs d’URL déterministes ne sont jamais retentées.

L’encodeur de query par défaut accepte les scalaires et les tableaux de scalaires (les tableaux répètent la clé). Un objet imbriqué échoue avec `REQ_BUILD_FAILED` sauf si le client a `withQuerySerializer(...)`. `null` dans `path`, `query` ou `headers` échoue de la même façon. `undefined` est omis.

## Placer l’entrée

Le struct encode la valeur. Le builder la place. Un `input` déclaré exige toujours un `builder` explicite, même si l’entrée a déjà la forme de la requête. Seules les définitions sans `input` peuvent omettre `builder`.

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

Ce corps est `{"display_name":"Ada"}` avec `application/json`. Le nom wire de l’en-tête est `x-request-id`. Les appelants et les résultats parsés gardent `displayName`.

Préfère faire passer la valeur typée plutôt que d’épeler les clés wire. L’alias se déclare une fois sur le champ et s’applique dans les deux sens : `output` / `error` / événements / frames entrantes décodent `display_name` vers `displayName`, et `body: input.order` réécrit tout l’arbre. Le même struct `User` peut être un corps de création et une sortie de get. Une clé écrite à la main est l’exception : l’objet parent est anonyme, donc l’alias ne tourne pas.

| Expression du builder                           | Sur le wire                                              |
| ----------------------------------------------- | -------------------------------------------------------- |
| `body: input.profile`                           | Objet typé : alias et encodage `Date` / `bigint`         |
| `body: { profile: input.profile }`              | Clés externes littérales, objet interne toujours typé    |
| `body: { ...input.profile, role: 'admin' }`     | Le spread garde le struct ; la clé en plus est littérale |
| `body: { name: input.profile.displayName }`     | Parent anonyme : l’alias ne s’applique pas               |
| `query: input.query` / `headers: input.headers` | Objets plats typés : l’alias devient la clé wire         |

Étaler (spread) un objet typé et poser aussi sa clé wire (`display_name` à côté de `displayName`) est `REQ_BUILD_FAILED`. Un objet imbriqué dans `path` ou `headers` échoue de la même façon.

Le guide se choisit à chaque nœud, pas seulement à la racine. Un nouvel objet sous un parent anonyme garde les clés que tu as écrites. Le même objet sous un parent typé utilise le struct de ce champ.

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

Quand un guide union correspond à plus d’une branche, chaque branche est encodée puis comparée. Une sortie wire identique est conservée ; une différence est `REQ_BUILD_FAILED`.

Une intersection mixte qui contient une partie non-objet est taguée, à l’analyse, avec la conjonction des tags des parties correspondantes ; une valeur d’intersection mixte écrite à neuf et non analysée reste un objet anonyme.

### Query

La forme de query imbriquée (`a[b]`, `a.b`, listes à virgules) est une convention du backend, donc le hook est sur le client :

<include cwd>examples/http/query-serializer.ts#example</include>

Ici `query` est l’objet wire encodé. Les alias sont déjà appliqués, donc un serializer comme `qs` ne les laisse pas tomber. La string renvoyée est la query string. Defjs ne dépend pas de `qs`.

Sans serializer, les tableaux répètent les clés et un objet imbriqué est `REQ_BUILD_FAILED`. Renvoyer `URLSearchParams` depuis le builder utilise cette valeur telle quelle et saute le serializer. Le serializer n’est pas appelé quand il n’y a pas de query. Les intercepteurs voient ensuite `queryParams` comme `new URLSearchParams(queryString)`.

### Body

Le premier match gagne :

| Valeur de `body`                                                 | Envoyé comme                                                                                  | Content type par défaut                                          |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| omis / `undefined`                                               | pas de corps                                                                                  | —                                                                |
| objet typé dont la racine a un codec `urlencoded` ou `formData`  | `URLSearchParams` / `FormData` ; les clés sont des noms wire ; les tableaux répètent les clés | type form / boundary de la plateforme                            |
| `FormData`, `URLSearchParams`                                    | tel quel                                                                                      | identique ; Defjs efface un `Content-Type` périmé sur `FormData` |
| `Blob` / `File`                                                  | tel quel                                                                                      | `blob.type`, ou `application/octet-stream`                       |
| `ArrayBuffer`, `TypedArray`, `DataView`                          | tel quel                                                                                      | `application/octet-stream`                                       |
| `ReadableStream`                                                 | streamé (`duplex: 'half'` quand le runtime le permet)                                         | `application/octet-stream`                                       |
| `string`                                                         | tel quel                                                                                      | `text/plain;charset=UTF-8`                                       |
| objet simple, tableau, nombre, booléen, `null`, `Date`, `bigint` | encodé, puis `JSON.stringify`                                                                 | `application/json`                                               |

HTTP conserve le type inféré du corps du builder dans le champ ordinaire `request.bodyContentType`, qui est préservé dans les copies `{ ...req }` ; il n’écrit jamais cette inférence dans `request.headers`. Un header `content-type` explicite a toujours priorité, qu’il soit défini par le builder, les valeurs par défaut du client, un intercepteur ou une requête directe à `fetchHandler`, y compris quand la progression d’envoi convertit le corps en flux. `bodyContentType` ne s’applique que tant que `body` est la valeur du builder ; un corps de remplacement est détecté à nouveau, donc un intercepteur déclare son type avec un header `content-type`. `body: undefined` n’envoie aucun Content-Type inféré par la bibliothèque. FormData est l’exception : son content type doit utiliser la boundary de la sérialisation réelle. Le tag de codec ne s’applique qu’à la racine du corps : `body: { meta: input.form }` est du JSON, et les champs du formulaire sont des champs JSON ordinaires. Une string est du texte brut ; une string JSON comme `"abc"` a besoin de `JSON.stringify` plus `application/json`. Les champs `undefined` sont omis ; un champ `nullable` envoyé comme `null` est le JSON `null`.

Le JSON doit contenir uniquement des données JSON à tous les niveaux d’imbrication : objets simples, tableaux, chaînes de caractères, nombres finis, booléens et `null`, ainsi que des valeurs dont `toJSON()` renvoie de telles données, comme `Date` ou `URL`. Toute autre valeur, à la racine ou dans une structure imbriquée, provoque un échec avec `REQ_BUILD_FAILED` avant tout envoi, au lieu d’être envoyée sous la forme `{}`, `null` ou sans corps : une `Map` ou un `Set`, une instance de classe sans `toJSON`, une fonction, `NaN`, un `Readable` Node ou un itérable ou un itérable asynchrone, y compris un objet littéral avec une méthode `Symbol.iterator` ou `Symbol.asyncIterator`. Le message indique le champ concerné. Un objet itérable fourni comme `query` ou `headers` échoue de la même façon au lieu d’être écarté ; passe les paires d’en-têtes sous forme de tableau. Envoie un flux sous la forme d’un `ReadableStream` Web : `ReadableStream.from(iterable)` ou `Readable.toWeb(readable)`. Le type `body` rejette la plupart de ces valeurs à la compilation ; pour une valeur typée par une `interface` ou une instance de classe, il faut utiliser `{ ...value }`.

`GET` et `HEAD` ne peuvent pas renvoyer un corps — c’est une erreur de type. Les builders WebSocket ne peuvent pas renvoyer `headers` ni `body`.

<include cwd lang="typescript">

</include>

`JSON.stringify`, `qs` ou protobuf que tu lances toi-même voient les noms logiques. L’alias ne s’applique pas sur ce chemin. Il n’y a pas de `struct.encode` public.

Un builder peut brancher sur l’entrée réelle et renvoyer un corps différent selon le cas (records JSON, un `File`, ou `URLSearchParams`). Les `Headers` natifs passent aussi tels quels et ne sont pas ré-encodés.

## Comment un corps est lu

`output` est un Struct pour le corps 2xx ; `error` est un Struct pour tout le reste. Le kind du struct
choisit la représentation : `string` est du texte brut, `blob` / `file` sont des blobs, `arrayBuffer` est des octets,
et tout autre kind est du JSON. Si aucun des deux côtés n’est déclaré, le corps n’est jamais lu.

Ordre des opérations :

1. `ok` choisit le côté : `output` pour les 2xx, `error` pour tout le reste. Jamais les deux.
2. Rien de déclaré pour ce côté → le corps n’est jamais lu. Un 2xx réussit avec `data === undefined` ;
   un non-2xx est `HTTP_STATUS` avec `data === undefined`. Un corps illisible du côté que tu n’as pas
   déclaré est ignoré, y compris le fait qu’il n’ait pas pu être lu.
3. Le media type est vérifié **avant** la lecture du corps. Un écart est `RES_MEDIA_TYPE_INVALID` et
   rien n’est parsé ni décodé.
4. La représentation est lue. Un échec est `RES_DECODE_FAILED`. Le JSON du transport est parsé une fois :
   une chaîne sur cette valeur est une racine string JSON et n’est pas reparsée ; les octets et les blobs
   sont bruts et sont parsés une fois.
5. Le Struct parse la valeur. Un échec est `RES_STRUCT_MISMATCH`.
6. 2xx → résultat et un `response.body` typé ; non-2xx → `data` typé sur `HTTP_STATUS`.

Le transport Fetch intégré exécute les étapes 3 et 4 pour un côté déclaré alors que la réponse est encore
dans la chaîne d’intercepteurs : les intercepteurs reçoivent donc une réponse dont le `body` est déjà le JSON,
le texte, le `Blob` ou les octets parsés ; un échec à ces étapes remonte toujours comme le même fault `RES_*`,
ou comme `NET_BODY_INCOMPLETE` quand le flux du corps se rompt. L’étape 5 s’exécute une seule fois, après la chaîne.
Une réponse qu’un intercepteur a construite avec `makeResponse(...)` passe donc par la même vérification de media type,
la même conversion de représentation et le même Struct qu’une réponse venue du réseau. Pour une représentation JSON,
un corps string est une racine string JSON.

Une réponse réussie est un `DecodedResponse<T>` : `url`, `status`, `statusText`, `headers`, `ok`, et
un `body` typé. Là où rien n’a été décodé tu obtiens `HttpMeta` — les mêmes champs sans `body`. `ok`
veut seulement dire `200 <= status < 300`. Ni l’un ni l’autre n’est une `Response` native. Un échec de transport est un fault, donc
il n’y a pas de réponse au statut 0 qui en tienne lieu.

## Annuler le travail

Les options d’exécution prennent `signal` plus soit `abort` soit `timeout`. **`abort` et `timeout` s’excluent.** `signal` peut se combiner avec l’un ou l’autre.

<include cwd>examples/http/cancel.ts#example</include>

`timeout` doit être un entier sûr positif dans `1..2_147_483_647`. Un appel qui omet `timeout` reçoit le défaut `withTimeout` du client. Annulation reconnue → `NET_ABORTED` ; timeout d’exécution → `NET_TIMEOUT` ; `throw` d’un intercepteur → `EXT_INTERCEPTOR_FAILED`, sauf `ERR_ABORTED` / `ERR_TIMEOUT`, qui donnent `NET_ABORTED` / `NET_TIMEOUT` ; autres échecs Fetch → `NET_UNREACHABLE`. Annuler après que le serveur a accepté une écriture ne **prouve pas** que l’écriture a été annulée (rollback).

## Credentials et XSRF

`withCredentials(true)` pose Fetch `credentials: 'include'` pour HTTP et SSE. Il ne crée pas `Authorization` et ne configure pas l’auth WebSocket. `false` laisse les credentials non spécifiés.

`withXSRF(...)` est HTTP seulement. Défauts : `cookieName: 'XSRF-TOKEN'`, `headerName: 'X-XSRF-TOKEN'`. L’en-tête n’est injecté que pour les méthodes non safe, et seulement si l’appelant ne l’a pas déjà posé. Lorsque `location` existe, y compris dans un Worker, l’URL de requête résolue doit correspondre à `location.origin` ; une requête cross-origin n’appelle pas `tokenProvider`. La lecture du cookie exige séparément `document`. Saute `GET`, `HEAD`, `OPTIONS`, `TRACE`. Dans un Worker ou un serveur, passe un `tokenProvider` synchrone, scopé à la requête, si tu as besoin de l’injection.

Garde credentials, tokens XSRF et query strings hors des logs de routine. N’utilise pas les query params comme canal général de credentials.

## Progress et la frontière Fetch

`onDownloadProgress` tourne pendant qu’un corps de réponse déclaré est lu. `loaded` compte les octets lus depuis le flux de réponse, que Fetch peut déjà avoir décompressés. `lengthComputable` n’est vrai qu’avec un `Content-Length` positif et un `Content-Encoding` absent ou `identity`. Les autres encodages, y compris gzip et br, signalent `total: 0` et `lengthComputable: false`, donc les octets décodés ne sont jamais comparés à une longueur wire compressée. Pas de struct pour ce côté → le corps n’est pas lu → pas de progress de lecture du corps.

`onUploadProgress` signale la progression de l’envoi d’un corps `ReadableStream<Uint8Array>` à mesure que Fetch le lit, pas quand le serveur l’acquitte. Cette progression n’est signalée que dans les environnements d’exécution capables de transmettre les corps de requête en flux : dans Bun, Node et Deno, Defjs convertit aussi les corps `Blob` / `File`, `ArrayBuffer` et `FormData` en flux, ce qui permet également d’en signaler la progression. Dans les environnements d’exécution serveur, FormData avec `onUploadProgress` utilise directement le flux sérialisé, conserve sa boundary multipart et est envoyé sans `Content-Length` généré par la bibliothèque (avec transfert chunked en HTTP/1.1), ce qui permet à la progression, au timeout et à l’annulation de fonctionner sans mettre tout le corps en tampon. Son total est inconnu, sauf si un `Content-Length` explicite valide le fournit. Pour un endpoint qui exige `Content-Length`, comme certaines destinations d’envoi avec URL présignée, omets `onUploadProgress` ; le Fetch de la plateforme envoie alors FormData avec sa longueur. L’annulation libère le flux enveloppé. Les navigateurs, Workers compris, sont exclus de ce mécanisme, car Chromium ne peut transmettre un corps de requête en flux que via HTTP/2 ou une version ultérieure, tandis que Firefox ne le permet pas du tout ; ces corps y sont donc envoyés tels quels et `onUploadProgress` n’est pas appelé. Les corps JSON, texte, `URLSearchParams` et tableaux typés sont envoyés d’un bloc et ne produisent aucun événement. `total` vaut `0` (donc `lengthComputable` est `false`) pour un flux dont la longueur est inconnue. Dans un environnement d’exécution qui ne permet pas l’envoi de requêtes en flux, comme Firefox, une requête dont le corps est un `ReadableStream` échoue avec `ENV_UNSUPPORTED` avant tout envoi ; le message de la cause est `ERR_STREAMING_REQUEST_UNSUPPORTED`. Dans Chromium, un corps `ReadableStream` exige HTTP/2 ou une version ultérieure ; avec HTTP/1.1, l’appel échoue avec `NET_UNREACHABLE`. `onDownloadProgress` se comporte de la même façon dans tous les environnements d’exécution.

Un callback de progression qui lève une erreur ou renvoie une promesse rejetée fait échouer l’appel avec `EXT_OBSERVER_FAILED` ; la valeur à l’origine de l’échec est conservée dans `cause`. Cela vaut pour les téléchargements comme pour les envois. L’annulation par l’appelant et `timeout` signalent toujours `NET_ABORTED` / `NET_TIMEOUT`.

`fetchHandler(httpRequest, fetchImpl?)` est la frontière Fetch de plus bas niveau : résout l’URL, appelle Fetch, lit la représentation et renvoie `HttpResponse`. Les handles HTTP et SSE par défaut résolvent `globalThis.fetch` à chaque appel, donc un remplacement installé après l’import est utilisé. HTTP n’utilise `(url, init)` que pour le Fetch de plateforme non modifié ; un global remplacé ou un handle personnalisé reçoit une `Request` native. Importer Core sans Fetch est valide ; une exécution HTTP/SSE par défaut échoue avec `ENV_UNSUPPORTED` si Fetch manque encore, tandis que les handles personnalisés restent utilisables. Cette frontière ne **valide pas** l’entrée de commande, ne dispatche pas `output`, et ne fait pas tourner les intercepteurs. Utile pour des tests de transport injecté — pas un substitut de `client.execute`.

## Limites de replay

Defjs ne relance **pas** HTTP tout seul. Relancer une lecture demande encore une politique revue de timeout/réseau/doublon. Relancer une mutation demande des octets rejouables, le support serveur, une clé d’idempotence liée au scope d’auth + aux octets de la requête, et une politique de doublon côté récepteur.

Une frontière client/commande/Fetch ne peut pas savoir si une écriture échouée a été appliquée. Garde les décisions de replay dans l’app ou un intercepteur revu. Les intercepteurs peuvent court-circuiter ou remplacer la requête bas niveau ; le statut et le corps finaux doivent quand même satisfaire le contrat de la commande.
