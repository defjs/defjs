# React

Importe les opérations de ton SDK ou d’un module de définition partagé. L’application React possède le client et le fournit à travers ce plugin de framework ; le paquet SDK peut rester indépendant de React et être réutilisé par d’autres applications.

Ces plugins sont des helpers facultatifs pour fournir et lire un `Client` existant. Importe un client fixe possédé par l’application, passe un `Client` explicitement à de la logique réutilisable, utilise l’injection du framework pour les défauts et les surcharges au niveau de l’arbre, ou choisis ta propre organisation. Les définitions de SDK n’exigent pas ces plugins.

Branche un client `@defjs/core` existant dans un arbre React. Tu obtiens Context et `useClient()`. Le package ne **crée pas** de client, n’ajoute pas de cache, ne réessaie pas les opérations et ne libère pas les ressources de transport. Le composant, l’effet ou la lib de data qui démarre le travail le possède. Le client issu de `useClient()` est passé à l’opération. Le hook renvoie le [`DerivableClient`](/fr-FR/api/core/derivableclient-type) fourni. Pour des options par appel comme `signal`, appelle-le là où l’opération s’exécute : `getUser(client({ signal }), input)`. Ne le passe pas à un setter d’état, car `setState(client)` l’appellerait comme updater. Une valeur `Client` dérivée n’est pas acceptée par `ClientProvider` ni `useClient`.

`ClientProvider` est un provider de Context ordinaire. Une prop `client` différente change ce que voient les descendants — pas de clone, de remplacement ni de dispose. Les providers imbriqués créent des frontières explicites.

React peut monter et nettoyer un effet plus d’une fois en développement. Le check du signal empêche une promesse périmée d’écrire dans le render courant. L’erreur du tuple reste de la data.

## Lire avec `useClient`

`useClient(overrideClient)` préfère le client explicite ; omis ou `undefined`, il lit le `ClientProvider` le plus proche. Une `Error` n’est levée que lorsqu’aucune des deux sources ne fournit de client. Les appels `useClient()` sans argument restent valides.

Appelle toujours `useClient(explicitClient)` au niveau supérieur d’un composant ou d’un Hook personnalisé, même avec un client explicite ; pas dans une fonction ordinaire ni dans un callback d’événement. N’écris pas `explicitClient ?? useClient()`, qui appelle un Hook de façon conditionnelle. La surcharge n’écrit pas le Context et ne crée pas de provider, et le Hook s’abonne quand même au Context.

<include cwd>examples/react/read-with-use-client.tsx#example</include>

Le hook ne fournit que le client. Il ne démarre pas de travail, ne s’abonne pas à un transport et ne transforme pas le tuple error-first en exception.

## Posséder le travail de query

Une lib de query peut posséder le cache, les retries, la suppression de résultats périmés et l’annulation. Passe le signal qu’elle fournit comme `signal` sur un client dérivé. Pour les pages de liste, appelle l’opération depuis TanStack Query (ou équivalent) — `@defjs/react` reste DI seulement et ne fournit **pas** `useRequest`.

<include cwd>examples/react/own-query-work.tsx#example</include>

`throw error` dans ce hook est le canal de rejet de la fonction de query, pas l’appel Defjs par défaut. Le tuple est inspecté d’abord ; seul cet adaptateur rejette, pour que la lib de query puisse enregistrer l’échec.

Ne démarre pas la même opération dans un second effet — deux propriétaires rendent l’annulation et la gestion des résultats périmés ambiguës.

## Posséder le travail temps réel

Les handles SSE et WebSocket survivent à l’appel d’opération. Enregistre le cleanup avant d’attendre le démarrage, ferme un handle qui arrive après libération, consomme son unique itérateur, attends sa promesse terminale :

<include cwd>examples/react/own-realtime-work.tsx#example</include>

Le `signal` passé à l’opération continue de gouverner une session ouverte. L’abandonner dans le cleanup termine la session en `aborted` et fait rejeter `receive` avec `AbortError`, donc le `catch` ci-dessus ignore les erreurs une fois l’effet nettoyé et ne rapporte que les vrais échecs (dépassement de file, timeout d’acquittement de heartbeat). Un flux SSE abandonné termine à la place son itérateur normalement. Sans le `catch`, un rejet venant de la boucle serait un rejet de promesse non géré.

Même règle pour `EventStreamHandle` : ferme dans `finally`, attends `stream.closed`. Les consommateurs WebSocket doivent aussi se désabonner des listeners d’état et d’erreur runtime et continuer à lire `session.receive` — une file bornée non lue peut déborder.

## SSR et portée du client

L’entrée du package est une frontière de Client Component. Une app navigateur peut partager un client au scope du module quand l’endpoint, les intercepteurs et l’état capturé sont sûrs pour le navigateur et indépendants de la requête. Pour le SSR, crée un client séparé dans chaque frontière de requête quand les en-têtes, cookies, utilisateurs, tenants ou identifiants diffèrent.

Le unmount du provider n’**abandonne pas** HTTP, ne ferme pas SSE/WebSocket, ne désabonne pas les listeners et n’appelle pas `dispose`. `@defjs/react` n’a pas une telle API de cycle de vie. Le code qui démarre chaque opération doit la terminer ou l’annuler.

## Référence

Exports publics de `@defjs/react` :

- `ClientProvider` — accepte `ClientProviderProps`, fournit le client donné
- `useClient` — client explicite d’abord, sinon le client fourni le plus proche ; lève si aucun des deux n’existe
- `ClientProviderProps` — `{ client: Client; children?: ReactNode }`

Crée les clients et les options dans `@defjs/core`. Voir [Client](/fr-FR/docs/client), [Gestion des erreurs](/fr-FR/docs/errors), [SSE](/fr-FR/docs/sse) et [WebSocket](/fr-FR/docs/web-socket).
