Appeler un service d’IA depuis l’application est distinct du fait de faire écrire Defjs par un assistant. [Développement assisté par IA](/fr-FR/docs/ai) décrit ce parcours d’assistant. Les formats d’API et d’événements SSE sont propres à chaque fournisseur. Le flux de cette page est un backend fictif, pas un protocole de fournisseur.

## Appeler une API d’IA depuis l’application [#call-an-api]

Définis l’appel avec le contrat HTTP ou SSE que tu utilises déjà, puis appelle l’opération sur un client que l’application possède. Commence par les [requêtes HTTP](/fr-FR/docs/http) et les [flux d’événements SSE](/fr-FR/docs/sse). [Envoyer du JSON](/fr-FR/recipes/post-json) est le corps JSON habituel. [Consommer les événements SSE](/fr-FR/recipes/consume-sse) montre comment lire et fermer un flux, mais s’arrête après le premier événement. Cette recette n’est pas une réponse d’IA complète. Pour une réponse d’IA complète, poursuis la lecture jusqu’au signal de fin du fournisseur ou jusqu’à EOF, gère les erreurs de flux et ferme le flux ; adapte les noms d’événements et les schémas de payload au fournisseur. [Annulation et délais](/fr-FR/recipes/cancel-http) montre comment l’appelant arrête un appel HTTP.

Garde le secret du fournisseur sur un serveur autorisé à le dépenser. Ne le place pas dans un paquet navigateur, une variable de build publique, ni un client livré au navigateur. Les identifiants appartiennent à l’application : règle-les sur le client du serveur, ou attache-les dans un intercepteur qui ne s’exécute que dans cette frontière serveur. La [configuration du client](/fr-FR/docs/client) et les [intercepteurs](/fr-FR/docs/interceptors) sont l’endroit de cette configuration. `withCredentials` choisit seulement le mode cookie de Fetch. Il ne conserve pas un secret de fournisseur.

Après le retour de l’opération, l’application possède le flux. Pour SSE, lis les événements, ferme le handle et attends qu’il soit fermé. Pour HTTP, abandonne l’appel avec `signal` quand la réponse n’est plus utile. Un abort ne prouve pas que le service a défait un travail déjà accepté.

Ne renvoie pas un POST en flux seulement parce que la tentative a échoué. Defjs ne réessaie pas HTTP de lui-même. La reconnexion SSE reste inactive tant que l’application ne l’active pas, et une méthode telle que POST n’est pas renvoyée sauf si cette politique l’autorise explicitement. Une tentative échouée peut déjà avoir lancé un travail que le service facture. Renvoyer le même POST peut lancer ce travail une seconde fois. Lis les règles de rejeu dans les [requêtes HTTP](/fr-FR/docs/http) et les règles de reconnexion dans les [flux d’événements SSE](/fr-FR/docs/sse) avant d’ajouter une nouvelle tentative.

## Flux hors ligne fictif [#fictional-stream]

Le format ci-dessous est fictif. Ce n’est pas le format d’événements d’un fournisseur précis. `withSSEHandle` fournit la réponse, donc l’exemple n’a besoin ni de réseau ni d’identifiants réels. Le corps contient deux événements `delta`, puis un événement de fin. La boucle conserve les deux textes. Elle ne s’arrête pas après le premier événement.

bun fictional-completion.ts
