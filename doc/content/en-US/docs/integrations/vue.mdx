# Vue

Import operations from your SDK or shared definition module. The Vue application configures and provides the client; the SDK package can stay independent of Vue. Components and composables execute those definitions and own the work they start.

These plugins are optional helpers for providing and reading an existing `Client`. Import a fixed application-owned client, pass a `Client` explicitly to reusable logic, use framework injection for tree-level defaults and overrides, or choose your own organization. SDK definitions do not require these plugins.

Wire an existing `@defjs/core` client into Vue. You get a plugin, an injection key, and `injectClient()`. The package does **not** create clients, cache results, retry commands, or close transport resources on unmount.

## Basic Setup

Install `@defjs/core`, `@defjs/vue`, and Vue 3.2+ (the plugin only needs `provide` / `inject`, but the examples use `<script setup>` and `onScopeDispose`, which arrived in 3.2). ESM:

`bun add @defjs/core @defjs/vue vue`

## Inject and override

`injectClient(key)` reads the nearest provider for that key; omitted or `undefined` uses `HTTP_CLIENT`. Call in a valid Vue injection context: synchronous `setup()` or `app.runWithContext()` (Vue 3.3+). The latter supplies only synchronous app-level context, not subtree overrides or context across ordinary `await`. Compiler-restored contexts after top-level `await` in `<script setup>` remain valid.

For a custom `InjectionKey<Client>`, use `app.provide(key, client)` or an ancestor’s `provide(key, client)`. Share the same `Symbol` object; matching descriptions do not make keys equal. `createClientPlugin(client)` still takes only the client and provides `HTTP_CLIENT`.

Throws an `Error` without an active injection context or a client for the selected key. A missing custom key never falls back to `HTTP_CLIENT`; installing the plugin alone does not establish an injection context.

An application function that only retrieves a client may use `explicitClient ?? injectClient()`: only the fallback branch needs injection context. Other lifecycle APIs in the same composable retain their own context requirements. Read the client in a valid context before async work and reuse the object.

## Own HTTP work outside a watcher

For work started by a composable or component outside a watcher, use `AbortController` + `onScopeDispose`. Abort startup and active work; check the signal before assigning reactive state. A plugin or injection scope does not infer who owns a command. For list pages, wrap `execute` with Vue Query (or similar) — `@defjs/vue` stays DI only and does **not** ship `useRequest`.

When a scope owns a client, keep it request-independent for browser-wide reuse. If it captures headers, cookies, users, tenants, or credentials, create it in the relevant app/SSR request boundary and provide that instance there.

## Clean up realtime scope

Close a stream or session even when the scope disappears mid-connect. Abort startup, close a late-arriving handle, consume the single iterator, await the terminal promise:

<include cwd>examples/vue/realtime-scope.vue#example</include>

Fatal stream errors and queue overflow reject the iterator, so the loop has a `catch`; otherwise that rejection is unhandled. The example keeps only the last 100 messages and keys rows by an id, because identical payloads would give duplicate keys. Stopping the scope ends iteration normally for SSE; an aborted WebSocket session instead rejects `receive` with `AbortError`, so guard the `catch` the same way.

WebSocket: same sequence — abort prep, close a late session, consume `session.receive`, unsubscribe `onStateChange` / `onRuntimeError`, close, await `session.closed`. Keep cleanup idempotent; disposal and iterator completion can meet.

## SSR scope

`createClientPlugin(client)` provides one instance to one Vue app. In the browser, share it when endpoint, interceptors, and captured state are safe to share. During SSR, create and install a separate client per request when headers, cookies, users, tenants, or credentials differ.

App unmount, plugin removal, and component scope disposal do **not** abort HTTP, close SSE/WebSocket, unsubscribe listeners, or dispose the core client. The owner that starts the work must finish it.
