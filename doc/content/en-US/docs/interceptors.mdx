# Interceptors

Interceptors attach cross-cutting execution policies—authentication headers, request signing, maintenance short-circuiting, or `Retry-After` handling—to the application's `Client` without modifying SDK operation definitions.

Input validation and `builder` mapping run **before** the interceptor chain; HTTP status dispatch and `output` / `error` struct validation run **after** the chain. An [operation interceptor](#operation-interceptors) wraps all of it.

### Interceptor pipeline rules

- **Onion order**: Interceptors run in registration order on the way out (`before next(req)`) and in reverse order on the way back (`after await next(req)`). Place broad logging/tracing interceptors outside narrower auth or retry interceptors.
- **Immutable request convention**: Always clone `req.headers` (`new Headers(req.headers)`) and pass a new request object (`{ ...req, headers }`) to `next(...)` so outer retries see clean headers.
- **`content-type` and `bodyContentType`**: Defjs stores its inferred body content type on `req.bodyContentType` without mutating `req.headers`. Request signers should read `req.headers.get("content-type") ?? req.bodyContentType`. If an interceptor replaces `req.body` with a new format, set an explicit `content-type` header.

## 3. Retries and `Retry-After`

HTTP retries are off by default. To retry a connection failure, a timeout, or a status in `statusCodes` (`429`, `502`, `503`, or `504` by default) with native RFC 9110 `Retry-After` support on `429` and `503` (`retryAfter: true`, `maxRetryAfterMs: 60_000`), use [`withRetry()`](/docs/load-balancing#retries). After the delay it lets the balancer pick again, rebuilds the request, and reruns the complete interceptor chain.

When an application needs **custom same-endpoint** status handling—such as retrying on the selected endpoint without re-running `builder` or outer interceptors, substituting a fallback delay when `Retry-After` is absent, or capping waits instead of failing fast—an interceptor can loop on `next(request)` directly:

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **Two retry layers**: This `next(request)` loop stays on the selected endpoint and does not rerun the builder or outer interceptors. Connection failures, cross-endpoint failover, and default `429`/`502`/`503`/`504` policies belong to `withRetry`.
- **Built-in vs. custom `Retry-After` policy**: Core `withRetry()` honors RFC 9110 `Retry-After` on `429` and `503` by default (failing fast without retrying if the server-requested delay exceeds `maxRetryAfterMs`). If you handle `429` inside a custom interceptor like the recipe above, configure `withRetry({ retryAfter: false })` (or omit `429` from `statusCodes`) to avoid double-retrying; the recipe's 30-second cap and 250 ms fallback are application choices, and capping a longer server delay can retry earlier than requested.
- **401 writes**: The [Bearer-refresh recipe](/recipes/refresh-bearer-once) can deliver a JSON POST twice. Require authentication rejection before business processing and a stable idempotency key with server-side deduplication, or do not automatically replay writes. Stream request bodies are not replayed.
- **Handling transport rejections**: `next(request)` rejects when a network error occurs (there is no status-0 response). Catching and rethrowing that rejection preserves the original `NET_*` fault code.
- **Requests that cannot be sent**: In an HTTP interceptor, when the platform refuses the request (an invalid or forbidden method, a GET or HEAD body, a URL with credentials, an invalid `Content-Type`) or a `finalizeHeaders` hook throws, `next(request)` rejects with the platform's own error (a `TypeError`) or the value the hook threw, not with the library's `BodyFailure` wrapper. Rethrowing it keeps the fault code (`REQ_BUILD_FAILED` or `EXT_HOOK_FAILED`); throwing a different error makes the failure yours (`EXT_INTERCEPTOR_FAILED`). The other failures found around the transport still reach `next(request)` as `BodyFailure`: a response body that cannot be read, decoded or matched to its media type, a truncated body, and a throwing upload progress observer (`EXT_OBSERVER_FAILED`), which can happen before the request is sent.
- **Throwing inside an interceptor**: An unhandled throw of the interceptor's own (or passing `next()` a `signal` that is not an `AbortSignal`) resolves the operation tuple with `EXT_INTERCEPTOR_FAILED` and sets `err.cause`. Throwing `ERR_ABORTED` or `ERR_TIMEOUT` resolves `NET_ABORTED` or `NET_TIMEOUT`.

For SSE, prefer `withRetry` over an interceptor that calls `next()` repeatedly. Calling the interceptor's `next()` more than once disables endpoint attribution and re-picking for those replacement streams; it is unrelated to consuming events with an iterator's `next()`.

## 5. Observe a whole operation call [#operation-interceptors]

A transport interceptor sees one request at a time: an input that fails validation never reaches it, each retry runs it again, and the response is decoded after it returns. To observe the call itself, from the moment `getOrder(client, input)` is called until its tuple resolves, use `createOperationInterceptor`:

<include cwd lang="typescript">
  examples/api/create-operation-interceptor.ts#example
</include>

- **What it sees**: `call` describes the definition: `transport` (`"http"`, `"sse"` or `"websocket"`), `method`, the `path` template and `meta`. It does not carry the input or the request, because neither exists yet. `next()` resolves with the operation's tuple, so `err` is the final fault: `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`, `HTTP_STATUS`, `RES_STRUCT_MISMATCH` and the rest.
- **It observes, it does not change**: `next()` takes no arguments, a second `next()` returns the same promise without running the call again, and the function can only resolve with what `next()` resolved with. Change requests and responses in a transport interceptor.
- **Order**: Operation interceptors run outside every transport interceptor, in registration order. Code that runs around `next()`, such as an OpenTelemetry `context.with`, is in effect for the whole call, the transport interceptors included.
- **Streams and sessions**: An SSE or WebSocket call resolves once the stream or session is open; what happens on it later is observed through its `closed`.
- **Failures**: A throw or rejection resolves the operation with `EXT_INTERCEPTOR_FAILED` and the thrown value as `cause`. A stream or session the call had already opened is closed.

## 6. Built-in factories and helpers

| Export                                         | Transport | Description                                                                                                                                                            |
| ---------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP      | Wraps `(req, next) => Promise<HttpResponse<unknown>>`                                                                                                                  |
| `createSSEInterceptor(fn)`                     | SSE       | Wraps `(req, next) => Promise<EventStreamHandle<unknown>>`                                                                                                             |
| `createWebSocketInterceptor(fn)`               | WebSocket | Wraps `(req, next) => Promise<WebSocketSessionLike>`                                                                                                                   |
| `createOperationInterceptor(fn)`               | All       | Wraps `(call, next) => Promise<result>` around a whole operation call                                                                                                  |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP      | Injects `Authorization: Basic ...` from a synchronous credential provider called per request                                                                           |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE       | Injects `Authorization: Basic ...` on SSE handshakes                                                                                                                   |
| `concurrencyLimitHttpInterceptor(options)`     | HTTP      | Limits concurrent in-flight attempts per bucket (`ConcurrencyLimitInterceptorOptions`); queues FIFO up to `maxQueue` and rejects overflow with `BulkheadOverflowError` |
| `idempotencyKeyHttpInterceptor(options?)`      | HTTP      | Injects an idempotency key header (`IdempotencyKeyInterceptorOptions`, default `Idempotency-Key`) on mutating methods (`POST`, `PATCH`), reusing `req.correlationId`   |

`concurrencyLimitHttpInterceptor` releases permits during `withRetry` backoff waits so retries cannot deadlock the bulkhead, and throws `BulkheadOverflowError` (surfaced as `EXT_INTERCEPTOR_FAILED` with `{ attempted: false }`) when `maxQueue` is exceeded. See the [Interceptors API reference](/api/interceptors).
