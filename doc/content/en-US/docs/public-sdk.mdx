# Public SDK design [#public-sdk-design]

When your company or platform team publishes an official TypeScript SDK for external developers (for example, an object storage SDK, a payment gateway SDK, or a SaaS platform SDK), the SDK package must **define the wire contract without dictating the runtime environment**.

Using an **Amazon S3-compatible SDK (`@company/s3-sdk`)** as a concrete blueprint, this guide shows how to design a multi-module public SDK with `models/` and pure-function `services/`.

---

## 1. Why public SDKs benefit from Defjs's separation

Traditional SDKs bundle a heavyweight client class (`new S3Client({ region, credentials })`) tightly coupled to command classes or static service classes. Authoring your public SDK with `@defjs/core` solves four recurring problems for your external users:

1. **Multi-environment & sandbox flexibility**: Because `@company/s3-sdk` binds no endpoint or client, a customer can point the exact same operation definitions at production (`https://s3.us-east-1.amazonaws.com`), a staging sandbox, Cloudflare R2, or a local MinIO container during CI tests.
2. **100% bundler tree-shaking**: Exporting standalone pure functions (`listBuckets`, `listObjectsV2`, `getObject`, `putObject`, `deleteObject`) with `"sideEffects": false` ensures a browser bundle that only calls `getObject` and `putObject` drops every other endpoint and model.
3. **Runtime validation + static types from one source**: External consumers get both compile-time TypeScript types (`Infer<typeof ...>`) and runtime response/error validation (`struct`), protecting them against unexpected wire payloads and converting wire `snake_case` fields or ISO date strings automatically.
4. **Full control over auth, retries, and telemetry**: Customers attach their own credential rotation interceptors, `withRetry(...)` policies, multi-region load balancers (`withBalancer(...)`), or server-side OpenTelemetry (`@defjs/opentelemetry-server`) on their own `Client`.

## 2. Package directory layout

Split the SDK package into `src/models/` (data structures) and `src/services/` (resource-grouped pure operation definitions), with a flat barrel `src/index.ts`:

```text
@company/s3-sdk/
├── src/
│   ├── models/                 # 1. Shared struct schemas + Infer<typeof ...> types
│   │   ├── common.ts           #    StorageClass, S3Error
│   │   ├── bucket.ts           #    Bucket, ListBucketsOutput
│   │   └── object.ts           #    ObjectSummary, ListObjectsOutput
│   ├── services/               # 2. Pure defineRequest functions by resource domain
│   │   ├── buckets.ts          #    BucketInput, listBuckets, headBucket, deleteBucket
│   │   └── objects.ts          #    listObjectsV2, headObject, getObject, putObject, deleteObject
│   └── index.ts                # 3. Barrel exports for root and tree-shakable imports
├── package.json                # sideEffects: false, peerDependencies: { "@defjs/core": "^0.8.0" }
└── tsconfig.json
```

### Designing ergonomic operation contracts

- **Flatten caller inputs and route in `builder`**: In `putObject`, callers pass a single ergonomic object (`{ bucket, key, body, contentType, storageClass }`). The synchronous `builder` splits that input into `path` (`:bucket/:key`), `headers` (`content-type`, `x-amz-storage-class`), and binary `body` (`Blob`). In `listObjectsV2`, `builder` maps `continuationToken` and `maxKeys` to S3's `continuation-token` and `max-keys` query parameters alongside `list-type: 2`.
- **Match `output` to the wire payload**:
  - **Structured JSON (`listBuckets`, `listObjectsV2`)**: Declare a `struct.object(...)` with `.alias()` mappings and `struct.date()` fields.
  - **Binary payload (`getObject`)**: Declare `output: struct.blob()` (or `struct.arrayBuffer()`).
  - **Empty body (`headBucket`, `headObject`, `putObject`, `deleteObject`)**: Omit `output` so `HEAD`, `200`, and `204` responses with zero bytes succeed without attempting JSON decoding, while callers still read response headers (`response.headers.get("etag")`) from the third tuple slot.
