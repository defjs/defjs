# SSE event streams

An SDK declares a Server-Sent Events (SSE) operation with `defineEventStream`, specifying the path, optional input and builder, an `events` dictionary of structs, and a buffer limit. The consuming application configures authentication and opt-in retries (`withRetry`) on its client, opens the stream, iterates typed events, and owns closing the stream.

- **Non-`2xx` handshake**: Returns `HTTP_STATUS`. With a declared `error` struct, `error.data` is the decoded body. When that body cannot be decoded, the result is the decode fault instead, as for HTTP: `RES_MEDIA_TYPE_INVALID` for a JSON declaration that meets another media type (an HTML `503` from a gateway, for example), `RES_DECODE_FAILED` for an unreadable or unparsable body, and `RES_STRUCT_MISMATCH` for a body that does not match the struct. Its `status` and `response` carry the handshake status as metadata and `cause` holds the reason. Interceptors, `shouldRetry` and the `closed` of a stream that fails on reconnect still receive `HTTP_STATUS` for that response, and its `cause` is the same reason, so a gateway `503` is retried however its body looks. A declared `error` makes the client read the handshake body to its end before it reports the fault, so the server should end every non-`2xx` response. The body is not read when the status has no content (`304`) or when a JSON declaration meets a media type that is not JSON. A body that is read and never ends keeps the call pending until the caller's `signal` aborts or the platform cuts the connection, which reports `HTTP_STATUS` with the platform failure as `cause`; `attemptTimeoutMs` does not bound that read. Without a declared `error`, the body is cancelled unread. Without `withRetry` this ends the current operation. With it, a `502`, `503`, or `504` handshake is retried like a refused connection under the rules in section 4, and any other status is given to `shouldRetry` with `retryable: false` and its `status`, so it ends the stream unless your function says otherwise. Exhausted or declined retries end with `HTTP_STATUS`. The next operation performs a fresh endpoint pick, so a balancer may choose another endpoint.
- **Wrong content type**: A `2xx` handshake whose media type is not `text/event-stream` returns `RES_MEDIA_TYPE_INVALID`, a `204` or `205` included.
- **No body**: A `2xx` handshake with `text/event-stream` and no body (Node.js and Bun expose a `204` or `205` as a null body) is an empty event stream: the call succeeds and the stream ends at once with `kind: "eof"`, which is never retried.
- **`startupOpen` vs. `stream.open`**: The tuple's third item (`startupOpen`) snapshots the first handshake response; `stream.open` updates live if the stream reconnects later. If a reconnect handshake ends the stream with a non-2xx status, the iterator rejects and `stream.closed` reports `HTTP_STATUS`, while `stream.open.response.status` keeps that status; inspect `stream.open` for the live response status.

## 3. Event dispatch and decoding

When an SSE frame arrives (terminated by a blank line per WHATWG rules):

1. **Event routing**: The wire `event:` field selects `events[eventName]`, falling back to `events.default` if declared. An omitted `event:` field defaults to `"message"`. Undeclared events without `events.default` are dropped.
2. **Payload decoding**: A `struct.string()` schema receives the raw text `data:`. Every other struct kind parses `data:` as JSON first, then validates with the struct.
3. **Observing invalid events**: Invalid or undeclared events are dropped without killing the stream. Attach `withSSEOnInvalidEvent(...)` on the client for bounded diagnostics:

## 4. Retries and `Last-Event-ID` [#reconnect]

SSE retries are **opt-in** and use the same `withRetry` policy as HTTP and WebSocket. Without `withRetry(...)`, any network drop or stream read error terminates the stream. A request option `retry` replaces the client policy for one call.

<include cwd>examples/sse/reconnect.ts#example</include>

- **Outage budget (`maxRetries`)**: Defaults to `3`. Every successful handshake resets the retry count and backoff exponent, so `maxRetries: 1` can still create many physical connections over a long-lived session when each one opens successfully; stop a flapping server with `shouldRetry`. Normal server EOF is **not** a failure and does not trigger a retry.
- **Cursor tracking (`Last-Event-ID`)**: The cursor commits when an event's terminating blank line is parsed and is sent automatically as `Last-Event-ID` on reconnect. A partial frame never commits its `id`, whether the connection ends cleanly or fails. Resume after a reconnectable read/network failure starts from the last committed id; the server must implement replay from that cursor. An event without its own `id:` field carries the most recently committed id, on the same connection and after a reconnect. An empty `id:` field clears it: later events have no `id`, and later reconnects omit `Last-Event-ID`.
- **Idempotency safety**: By default, only the methods in `methods` (`GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT`, `DELETE`) are retried automatically. Other methods (`POST`, `PATCH`—such as LLM streaming requests) are retried only when you add them to `methods` or `shouldRetry` returns `true`; a function that returns `context.retryable` keeps the default. `ReadableStream` request bodies are consumed on the first attempt and never retried.
- **Gateway handshakes**: A `502`, `503`, or `504` handshake, whether the initial open or a reconnect, is retried like a refused connection under the same rules (method, `shouldRetry`, `maxRetries`, `ReadableStream` body). Other non-2xx handshakes are given to `shouldRetry` with `retryable: false` and end the stream by default. Exhausted and declined retries end with `HTTP_STATUS`. Retrying these three statuses is a deliberate deviation from the HTML Standard: `EventSource` treats any response that is not a `200` event stream as a failed connection and never tries again, whereas Defjs treats a gateway that is momentarily unavailable the way it treats a refused connection.
- **Handshake timeout (`attemptTimeoutMs`)**: When provided, it bounds each handshake from Fetch invocation to response headers without limiting how long an established stream stays open. It is an option of `withRetry`, so `withRetry({ attemptTimeoutMs })` also retries, with the default `maxRetries: 3`. For a handshake-only deadline write `withRetry({ maxRetries: 0, attemptTimeoutMs })`. An expired attempt reports `NET_UNREACHABLE` to the balancer so the retry can pick another endpoint, and exhausted retries end with `NET_TIMEOUT`.

### Idle streams on Node.js [#idle-streams]

Node.js's built-in `fetch` (undici) applies a `bodyTimeout` to every response body, 300 seconds by default, measured between two chunks of data. An SSE stream that stays silent for that long is cut by the runtime even though the server is healthy.

- **What you see**: The iterator rejects with the runtime's own error, a `TypeError` with message `terminated` whose `cause.code` is `UND_ERR_BODY_TIMEOUT`. `stream.closed` resolves with `kind: "error"`, `code: "NET_UNREACHABLE"`, and that `TypeError` as `cause`. Without `withRetry(...)` the stream ends there. With it, the stream resumes under the [retry rules](#reconnect) using `Last-Event-ID`, and each cut reports one `NET_UNREACHABLE` outcome to the endpoint balancer (see [load balancing](/docs/load-balancing)).
- **Fix on the server**: Send a comment line such as `: keepalive` at an interval well below 300 seconds. The HTML Standard's authoring notes suggest about every 15 seconds so that legacy proxies do not drop an idle connection. Parsers ignore comment lines, but their bytes still reset the timer.
- **No client-side setting**: Defjs has no idle-timeout option of its own. If the server cannot send comment lines, a stream that stays silent is cut when the runtime's limit is reached.

Idle behavior differs on other runtimes and is not covered here.

## 5. Buffer and queue limits

The one definition option is `maxBufferSize`, default `64 * 1024` bytes. The event queue is not configurable: the library holds at most 1024 validated events waiting for the `for await` consumer. There is no default handshake deadline: a pending Fetch waits for the platform, caller cancellation, or an explicitly configured `attemptTimeoutMs`.

| Limit                    | What it bounds                                              | At the limit                                                                                             |
| ------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `maxBufferSize` (option) | Incomplete or oversized SSE frame bytes before a blank line | Fatal: `stream.closed` resolves with `kind: "error"` and `CAP_BUFFER_EXCEEDED`; the iterator rejects     |
| Event queue (fixed 1024) | Validated events waiting for the `for await` consumer       | Reading from the response pauses until the consumer takes an event; no event is dropped for lack of room |

- **A slow consumer slows the server, not the stream.** A burst larger than the queue, such as a `Last-Event-ID` replay, is delivered in full; the library stops reading the response while the queue is full, so the backlog stays in the connection instead of being dropped or failing the stream. The queue holds at most 1024 events, plus one parsed event waiting for room.
- **An unattended stream stops reading.** A stream nobody iterates stops reading once its queue is full, and `stream.closed` does not resolve on its own until reading reaches the end of the response; `stream.close()`, an abort, or a timeout still resolves it, and a close or an abort drops the queued events. Call `stream.close()` or use `await using` when you no longer need the stream.
- **Failures keep what was already received.** When the stream ends with an error or a timeout, the events that were already queued are still delivered, and the iterator rejects after the last one, unless the caller stops the stream first (see section 6). `stream.closed` resolves when the connection ends, which can be before the iterator has read every event. Bytes still unread in the response body when the connection fails are not delivered and never advance `Last-Event-ID`, so with retries enabled the server must replay from the committed cursor.

`stream.close()`, disposal, and a caller `signal` abort are the caller stopping the stream: they end it at once and discard the events nobody has read yet, as `EventSource.close()` does. This holds whether or not the stream had already ended, so events that are still unread when the response has ended or the stream has failed are discarded as well. After a failure, the stop changes nothing else: `stream.closed` keeps its value and the iterator still rejects with the failure once nothing unread is left. A response that ends normally, and a stream that fails with an error or a timeout, deliver the events already queued first (see section 5) unless the caller stops the stream. A `signal` that expires, as `AbortSignal.timeout(ms)` does, while the stream is running is a timeout and belongs to that second group, not to a stop by the caller; one that expires after the stream has ended is a stop.

The `signal` passed via `client({ signal })` governs the entire lifetime of the stream. To bound only the initial connection handshake without killing an open stream later, clear your timer once `await watchOrders(...)` returns (as shown in the second tab above) or write `withRetry({ maxRetries: 0, attemptTimeoutMs })`; without `maxRetries: 0`, `withRetry` keeps its default of 3 retries.
