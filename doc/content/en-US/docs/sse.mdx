# SSE event streams

An SDK declares a Server-Sent Events (SSE) operation with `defineEventStream`, specifying the path, optional input and builder, an `events` dictionary of structs, and buffer/queue limits. The consuming application configures authentication and opt-in reconnection on its client, opens the stream, iterates typed events, and owns closing the stream.

- **Non-`2xx` handshake**: Returns `HTTP_STATUS`, whatever the body. With a declared `error` struct, `error.data` is the decoded body; when that body cannot be decoded (wrong media type, unreadable, or not matching the struct), `error.data` is `undefined`, `response` carries metadata only, and `error.cause` holds the decode failure. This is fatal for the current operation and `shouldReconnect` is not called, except for a `502`, `503`, or `504` handshake when `withSSEReconnect` is configured: it is retried like a refused connection under the reconnect rules in section 4, and `shouldReconnect`, when set, is consulted. Exhausted retries end with `HTTP_STATUS`. The next operation performs a fresh endpoint pick, so a balancer may choose another endpoint.
- **Wrong content type or unreadable body**: A `2xx` handshake that is not an event stream returns `RES_MEDIA_TYPE_INVALID`, and one without a readable body returns `RES_DECODE_FAILED`. A non-`2xx` handshake never returns these; it returns `HTTP_STATUS` above.
- **`startupOpen` vs. `stream.open`**: The tuple's third item (`startupOpen`) snapshots the first handshake response; `stream.open` updates live if the stream reconnects later. If a reconnect handshake ends the stream with a non-2xx status, the iterator rejects and `stream.closed` reports `HTTP_STATUS`, while `stream.open.response.status` keeps that status; inspect `stream.open` for the live response status.

## 3. Event dispatch and decoding

When an SSE frame arrives (terminated by a blank line per WHATWG rules):

1. **Event routing**: The wire `event:` field selects `events[eventName]`, falling back to `events.default` if declared. An omitted `event:` field defaults to `"message"`. Undeclared events without `events.default` are dropped.
2. **Payload decoding**: A `struct.string()` schema receives the raw text `data:`. Every other struct kind parses `data:` as JSON first, then validates with the struct.
3. **Observing invalid events**: Invalid or undeclared events are dropped without killing the stream. Attach `withSSEOnInvalidEvent(...)` on the client for bounded diagnostics:

## 4. Reconnect and `Last-Event-ID` [#reconnect]

SSE reconnection is **opt-in**. Without `withSSEReconnect(...)`, any network drop or stream read error terminates the stream.

<include cwd>examples/sse/reconnect.ts#example</include>

- **Outage budget (`attempts`)**: Defaults to `3` when an options object is passed to `withSSEReconnect`. Every successful handshake resets the attempt counter and backoff exponent, so `attempts: 1` can still create many physical connections over a long-lived session when each one opens successfully. Normal server EOF is **not** a failure and does not trigger reconnect.
- **Cursor tracking (`Last-Event-ID`)**: The cursor commits when an event's terminating blank line is parsed and is sent automatically as `Last-Event-ID` on reconnect. A partial frame never commits its `id`, whether the connection ends cleanly or fails. Resume after a reconnectable read/network failure starts from the last committed id; the server must implement replay from that cursor. An event without its own `id:` field carries the most recently committed id, on the same connection and after a reconnect. An empty `id:` field clears it: later events have no `id`, and later reconnects omit `Last-Event-ID`.
- **Idempotency safety**: By default, only idempotent methods (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`) reconnect automatically. Non-idempotent methods (`POST`, `PATCH`—such as LLM streaming requests) reconnect only when a custom `shouldReconnect` callback explicitly returns `true`. `ReadableStream` request bodies are consumed on the first attempt and never reconnect.
- **Gateway handshakes**: A `502`, `503`, or `504` handshake, whether the initial open or a reconnect, is retried like a refused connection under the same reconnect rules (method, `shouldReconnect`, `attempts`, `ReadableStream` body). Other non-2xx handshakes stay fatal. Exhausted retries and fatal reconnect handshakes end with `HTTP_STATUS`.
- **Handshake timeout (`connectTimeoutMs`)**: When provided, it must be finite, positive, and no greater than 2147483647 (the timer limit); otherwise the operation returns `REQ_OPTIONS_INVALID`. It bounds each handshake from Fetch invocation to response headers without limiting how long an established stream stays open. The option exists only inside the `withSSEReconnect({...})` options object. Passing that object enables automatic reconnect with the default `attempts: 3`, so `connectTimeoutMs` alone also reconnects; add `attempts: 0` for a handshake-only deadline.

### Idle streams on Node.js [#idle-streams]

Node.js's built-in `fetch` (undici) applies a `bodyTimeout` to every response body, 300 seconds by default, measured between two chunks of data. An SSE stream that stays silent for that long is cut by the runtime even though the server is healthy.

- **What you see**: The iterator rejects with the runtime's own error, a `TypeError` with message `terminated` whose `cause.code` is `UND_ERR_BODY_TIMEOUT`. `stream.closed` resolves with `kind: "error"`, `code: "NET_UNREACHABLE"`, and that `TypeError` as `cause`. Without `withSSEReconnect(...)` the stream ends there. With it, the stream resumes under the [reconnect rules](#reconnect) using `Last-Event-ID`, and each cut reports one `NET_UNREACHABLE` outcome to the endpoint balancer (see [load balancing](/docs/load-balancing)).
- **Fix on the server**: Send a comment line such as `: keepalive` at an interval well below 300 seconds. The HTML Standard's authoring notes suggest about every 15 seconds so that legacy proxies do not drop an idle connection. Parsers ignore comment lines, but their bytes still reset the timer.
- **No client-side setting**: Defjs has no idle-timeout option of its own. If the server cannot send comment lines, a stream that stays silent is cut when the runtime's limit is reached.

Idle behavior differs on other runtimes and is not covered here.

## 5. Buffer and queue limits

The defaults are `maxBufferSize: 64 * 1024` bytes and `maxQueueSize: 1024` events. Both limits must be positive safe integers. There is no default handshake deadline: a pending Fetch waits for the platform, caller cancellation, or an explicitly configured `connectTimeoutMs`.

| Definition option | What it bounds                                              | At the limit                                                                                             |
| ----------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `maxBufferSize`   | Incomplete or oversized SSE frame bytes before a blank line | Fatal: `stream.closed` resolves with `kind: "error"` and `CAP_BUFFER_EXCEEDED`; the iterator rejects     |
| `maxQueueSize`    | Validated events waiting for the `for await` consumer       | Reading from the response pauses until the consumer takes an event; no event is dropped for lack of room |

- **A slow consumer slows the server, not the stream.** A burst larger than `maxQueueSize`, such as a `Last-Event-ID` replay, is delivered in full; the library stops reading the response while the queue is full, so the backlog stays in the connection instead of being dropped or failing the stream. The queue holds at most `maxQueueSize` events, plus one parsed event waiting for room.
- **An unattended stream stops reading.** A stream nobody iterates stops reading once its queue is full, and `stream.closed` does not resolve on its own until reading reaches the end of the response; `stream.close()`, an abort, or a timeout still resolves it. Call `stream.close()` or use `await using` when you no longer need the stream.
- **Failures keep what was already received.** When the stream ends with an error or a timeout, the events that were already queued are still delivered, and the iterator rejects after the last one. `stream.closed` resolves when the connection ends, which can be before the iterator has read every event. Bytes still unread in the response body when the connection fails are not delivered and never advance `Last-Event-ID`, so with reconnect enabled the server must replay from the committed cursor.

`stream.close()` and disposal stop the stream at once and discard the events nobody has read yet, as `EventSource.close()` does. A response that ends normally, a caller abort, and a stream that fails with an error or a timeout still deliver the events already queued first (see section 5).

The `signal` passed via `client({ signal })` governs the entire lifetime of the stream. To bound only the initial connection handshake without killing an open stream later, clear your timer once `await watchOrders(...)` returns (as shown in the second tab above) or set `connectTimeoutMs` together with `attempts: 0` in `withSSEReconnect` (`connectTimeoutMs` alone also enables automatic reconnect with 3 attempts).
