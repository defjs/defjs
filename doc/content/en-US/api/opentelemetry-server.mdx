# OpenTelemetry server

A middleware plugin: outbound instrumentation of every operation call and of its HTTP / SSE / WebSocket transport, as core interceptors. This package does not initialize an OpenTelemetry SDK, and it is not inbound server instrumentation.

See the [OpenTelemetry server guide](/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

Appends an operation interceptor when a `tracer`, `meter`, or `logger` is supplied, then one interceptor per enabled transport, in the order HTTP, SSE, WebSocket. Apply it at `createClient` time, once per client. `options` is required; pass `{}` to install the transport interceptors with propagation only.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter`, and `logger` are each optional. No `propagator` → W3C Trace Context + Baggage.

Every operation call is observed from the call to its tuple: an `INTERNAL` operation span named `defjs.operation.name` (such as `GET /orders/:id`) with `error.type` set to the fault code on failure, one `defjs.client.operation.duration` sample, and one `WARN` log when it fails. Each HTTP attempt and each SSE or WebSocket connection gets a `CLIENT` transport span under it. A call without an active parent span starts a trace of its own; the SDK's sampler decides what is kept.

Without `tracer`, the plugin creates no local spans, never calls `trace.getTracer(...)`, and skips `startSpanHook`, `requestHook`, and `responseHook`. Supplied `meter` and `logger` instances work independently. Propagation still forwards the extracted parent context; WebSocket `queryPropagation` remains `false` by default.

HTTP, SSE, and WebSocket are on by default. Pass `{ enabled: false }` on a transport to skip it.

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| Field                     | Default                     | Effect                                                                                      |
| ------------------------- | --------------------------- | ------------------------------------------------------------------------------------------- |
| `tracer`                  | none                        | Without it there are no local spans and no span hooks.                                      |
| `meter`                   | none                        | Without it no package metrics are recorded.                                                 |
| `logger`                  | none                        | A `Logger` from `@opentelemetry/api-logs`. Without it no diagnostic LogRecords are emitted. |
| `propagator`              | W3C Trace Context + Baggage | Extracts the parent context and injects the outgoing context.                               |
| `includeErrorDiagnostics` | `false`                     | Export error messages and stacks on failed spans, `exception` events, and failure logs.     |
| `http`                    | `{}`                        | HTTP transport options.                                                                     |
| `sse`                     | `{}`                        | SSE transport options.                                                                      |
| `webSocket`               | `{}`                        | WebSocket transport options.                                                                |

`enabled` defaults to `true`; only `enabled: false` turns a transport off, together with the operation telemetry of its calls.

Span hooks run only when a `tracer` is supplied. `startSpanHook` runs synchronously before span creation for its own HTTP, SSE, or WebSocket transport. Its attributes are applied after built-in attributes, so the application may override `url.full` or another initial value. If it throws, Defjs creates the span with built-in attributes and continues the request; `requestHook` and `responseHook` run after span creation. Neither is awaited: a throw or rejection never blocks or fails the operation.

Hooks shape the transport span; the operation span has none. While `span.isRecording()` is true, hook failures record `defjs.otel.hook.error` and `exception` events. The `exception` event carries only `exception.type` (the class name, not a Defjs fault code), and neither `exception.message` nor `exception.stacktrace` unless `includeErrorDiagnostics` is on, because runtime error text can include the full request URL or a response body fragment; the same rule applies to the `exception` event recorded when a transport fails. For non-recording spans (ended or unsampled), failures go to the OpenTelemetry diagnostic logger through `diag.error`. Applications must configure `diag.setLogger(...)` from `@opentelemetry/api` to receive them; there is no automatic output by default. The package does not initialize the SDK, and this diagnostic is not a separate SDK `LogRecord`.

`responseHook` receives what the transport returned: the `HttpResponse` for HTTP, the stream handle for SSE once startup succeeded, and the session for WebSocket once it opened. Its third argument is the original request.

By default, `url.full` resolves only `request.endpoint` against optional `request.baseEndpoint`; `request.query` is not appended. That boundary is not query redaction. As the OpenTelemetry semantic conventions require, credentials in the endpoint's userinfo are replaced with `REDACTED:REDACTED`, and the values of the default sensitive query keys (`sig`, `Signature`, `AWSAccessKeyId`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `X-Goog-Signature`) are replaced with `REDACTED`, but the package has no other built-in redactor or sensitive-key policy. A `url.full` returned by `startSpanHook` is redacted the same way, but a URL an application writes through the `Span` object in `requestHook` or `responseHook` is not intercepted, so construct and, if needed, redact it explicitly:

`webSocket.queryPropagation` (WebSocket only) defaults to `false`. Turn it on only after you accept trace context in the WebSocket URL.

## Logger diagnostics

The top-level `logger?: Logger` option uses `@opentelemetry/api-logs`, not an application logger. It is optional and may be used alone. Defjs never obtains a global logger or owns its provider. It emits one `WARN` LogRecord (severity number 13) per failed operation call, and one per SSE stream or WebSocket session that fails after it opened, each with a fixed message:

| Outcome                                                                         | Event                                                             | Attributes                                                                                                          |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| An operation call resolves with a fault other than `NET_ABORTED`                | `defjs.client.operation.exception`                                | `defjs.operation.name`, `error.type` (the fault code), `exception.type`, `defjs.meta.*`                             |
| An SSE stream or WebSocket session ends in error, including a rejected `closed` | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address`, `server.port`, `exception.type`, `defjs.meta.*`, `defjs.sse.fault.code` or `websocket.close.code` |

Success, a retried attempt that a later attempt recovers, normal closure, EOF, a WebSocket close frame from the server whatever its code, and caller cancellation produce no LogRecord. An abrupt WebSocket drop without a close frame (1006) ends the session in error and logs once, on every runtime. The operation record is emitted with the operation span's context.

With `includeErrorDiagnostics: true`, every record also carries `exception.message` and `exception.stacktrace`; for an operation call they are the fault's `message` and `stack`. The cause chain and the enumerable fields of an error are never exported, but the message is not filtered: a fault's message is often its cause's, and platform error text can quote the request URL. Applications own filtering, exporters, flush and shutdown.

See the full logging and third-party integration examples in the [OpenTelemetry guide](/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
