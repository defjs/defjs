# HTTP

Declare a typed request, then call the operation with a client and its input.

## defineRequest()

<ApiSignature name="defineRequest" />

- **definition** — `method`, `path`, optional `input` struct, optional `output` and `error` structs, optional `operation`. A declared `input` always requires an explicit `builder`. `input` only defines the parameters; the builder alone decides where each value goes. Only definitions without `input` may omit `builder`. These `definition` members are documented under [`RequestDefinition`](/api/core/requestdefinition-type). `builder` is required exactly when `input` is declared.
- **Returns** an operation. Call it as `getOrder(client, input)`, or `health(client)` when no input is declared. When the whole input struct is optional, the input argument may be omitted. Calling it starts the request. There is no third options argument.

<include cwd>examples/api/define-request.ts#example</include>

`output` is one struct for the 2xx body; `error` is one struct for every non-2xx body. Neither is
keyed by status. Omitting one means that body is never read — see
[Declaration is an assertion](/docs/design-decisions#declaration-is-an-assertion).

Calling the operation returns a promise of the tuple described under [`HttpAwaitResult`](/api/core/httpawaitresult-type). Pass per-call options by deriving a client from [`RequestOptions`](/api/core/requestoptions-type). HTTP reads `signal` and the progress callbacks and ignores the other fields.

A non-2xx status is `HTTP_STATUS` when no `error` struct is declared or the declared `error` body decodes. The fault's `data` is the decoded
`error` body when one was declared, and `undefined` otherwise. When a declared `error` body cannot be read (wrong media type, invalid JSON) or
does not match its struct, the fault is `RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED` or `RES_STRUCT_MISMATCH` instead, and the response status is still
reported in its metadata. On failure the tuple's third slot is `undefined`; the fault carries the response metadata.

## fetchHandler()

<ApiSignature name="fetchHandler" />

Default HTTP transport. `fetchImpl` defaults to the global `fetch` resolved at send time; `withHTTPHandle` supplies another. Untouched platform Fetch receives `(url, init)`, while a replaced global or custom handle receives a `Request`. It rejects — rather than resolving
with a synthetic response — when no response reached the client or reading a declared body failed.

## makeResponse()

<ApiSignature name="makeResponse" />

Build an `HttpResponse` without a network call (interceptors, tests). Default status is `0`. `ok` is
true for 2xx. The value it returns goes through the same media-type check and the same declared
struct as one off the wire; there is no trusted short-circuit.

## HttpExecuteOptions

<ApiSignature name="HttpExecuteOptions" />

`HttpExecuteOptions` is the HTTP slice of [`RequestOptions`](/api/core/requestoptions-type): [`UseRequestConfig`](/api/core/userequestconfig-type), which is `signal` plus `onDownloadProgress` and `onUploadProgress`. There is no `timeout` or `abort` field. A deadline is `signal: AbortSignal.timeout(ms)` and classifies as `NET_TIMEOUT`. A manual abort is `NET_ABORTED`. `signal` is the call's signal; combine signals with `AbortSignal.any` in application code. There is no client-level default deadline. Other request fields, such as `heartbeat`, are ignored.

## Types

### RequestDefinition

`method`, `path`, optional `input`, `output`, `error`, `operation`, and `builder`. The struct kind selects how a declared body is read. A declared `input` always requires an explicit `builder`. `input` only defines the parameters; the builder alone decides where each value goes. Only definitions without `input` may omit `builder`.

### HttpAwaitResult

<ApiSignature name="HttpAwaitResult" />

On success the third slot carries `body` only when `output` was declared. On failure it is
`undefined` — the fault already holds whatever response metadata existed.

### HttpRequest

Normalized outgoing request: `method`, `endpoint`, `headers`, `body`, `signal`, `operation`, `withCredentials`, `finalizeHeaders`, `downloadProgress` / `uploadProgress`, `baseEndpoint`, `queryString`, and `queryParams`. By the time interceptors see it, `body` is already the wire value — for JSON, a JSON text string — so sign HMACs and digests against that, not the struct input. Interceptors see `queryParams` as `new URLSearchParams(queryString)`. A builder that returns `URLSearchParams` passes that instance through. `responseType` and `errorResponseType` are readonly: they are derived from the declared `output` and `error` struct kinds and must not be changed.

### HttpMeta

<ApiSignature name="HttpMeta" />

Response metadata, available whenever a response reached the client. It carries **no** `body`: a body
only exists once a declared struct decoded one.

### DecodedResponse

<ApiSignature name="DecodedResponse" />

A response whose body decoded against the declared struct. Holding this type is the proof that
decoding happened, which is why a decode failure reports `HttpMeta` alone.

### HttpResponse

<ApiSignature name="HttpResponse" />

`body` is `undefined` when the response had none; a JSON `null` stays `null`. The type is branded, so build one with `makeResponse` rather than an object literal. The wire shape transports produce and interceptors see: `body` is text or already-parsed JSON, not a
decoded value. For a JSON representation, a string is a JSON string root and is not parsed again; bytes
and blobs are raw and are parsed once. `DecodedResponse` is what reaches the caller.

### HttpProgressEvent

### HttpProgressFn

`loaded`, `total`, `lengthComputable`. Callbacks may be async. A throwing `onDownloadProgress` or `onUploadProgress` fails the call with
`EXT_OBSERVER_FAILED`, with the thrown value as `cause`; cancellation still reports `NET_ABORTED`, or `NET_TIMEOUT` when the abort reason is a timeout.
Upload progress converts `Blob` / `File`, `ArrayBuffer`, and `FormData` bodies where `fetch` supports a streaming request body. The converted body is an ordinary streaming request, so the Fetch rules for streaming request bodies apply, as they do to a `ReadableStream` you pass yourself, with or without `onUploadProgress`: Chromium and WebKit accept it only over HTTP/2 or later (`NET_UNREACHABLE` on HTTP/1.1; WebKit was checked manually at 27.2 only; Node.js and Bun accept HTTP/1.1); in browsers a cross-origin request needs a CORS preflight unless the browser holds a cached preflight result, so the server must answer `OPTIONS`; a 301, 302, 307, or 308 redirect fails after the body was sent once, while 303 becomes a GET and succeeds. Browsers send no `Content-Length`; Node.js and Bun send the known length of a Blob, File, or ArrayBuffer and use chunked encoding for FormData. `fetch` reports these failures, and a source `ReadableStream` that throws while `fetch` reads it, as the same network error as an unreachable endpoint, so the load balancer receives `{ attempted: false }` for them, as it does for a throwing progress callback (`EXT_OBSERVER_FAILED`). A streamed upload alone therefore cannot detect a down endpoint, and a rejected streamed upload is not retried as a `connect-failure`. For an endpoint that cannot accept this, omit `onUploadProgress`; the library does not fall back automatically. Firefox sends those bodies unchanged and does not call `onUploadProgress`.

Where that conversion runs, FormData uses its serialized stream without whole-body Blob buffering and preserves the actual multipart boundary. Its total is unknown unless a valid explicit `Content-Length` header sets the reported total (browsers do not send that header). Explicit content types survive upload conversion, except that FormData must use its serialization's boundary. `loaded` counts stream bytes, not server acknowledgements. Downloads with a non-identity `Content-Encoding` report `total: 0` and `lengthComputable: false`; their stream bytes may already be decompressed.

See [HTTP guide](/docs/http) and [Client](/docs/client).

## RequestEndpoint

Returned by `defineRequest`. The first argument is a [`Client`](/api/core/client-type). Further arguments are the input only.

## BuilderInput

Parsed operation input seen by `builder`. Object nodes carry the struct that produced them, so alias, `Date`, and `bigint` encoding follow the value.

## HttpRequestShape

<ApiSignature name="HttpRequestShape" />

All four fields are optional. `query` is `URLSearchParams` or a record; a nested object needs `withQuerySerializer` at runtime. `headers` is `HeadersInit` or a record of scalars or arrays of scalars. `path` supplies one scalar per `:name` segment.

`body` is `never` for `GET` and `HEAD`. Otherwise it is a wire value (`string`, `Blob`, `ArrayBuffer`, a typed array or `DataView`, `FormData`, `URLSearchParams`, or `ReadableStream<Uint8Array>`) or JSON data (`number`, `boolean`, `bigint`, `Date`, `null`, an array, or an object with string keys).

## UseRequestConfig

`signal`, plus optional `onDownloadProgress` and `onUploadProgress`. `HttpExecuteOptions` is this slice. There is no `timeout` or `abort` field.

## RequestSuccessData

Inferred success body from the declared `output` struct, or `undefined` when none is declared.

## RequestErrorData

Inferred error body from the declared `error` struct, or `undefined` when none is declared.

## HttpResponseType

`'arraybuffer' | 'blob' | 'json' | 'text'`

Chosen from the declared struct kind (`string` → `text`, `blob` / `file` → `blob`, `arrayBuffer` → `arraybuffer`, everything else → `json`). Not a field on `defineRequest`.

## MakeResponseOptions

Fields for `makeResponse`: `status`, `statusText`, `url`, `headers`, `body`, `request`.
