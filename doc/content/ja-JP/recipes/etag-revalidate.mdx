# ETag と 304 によるキャッシュ再検証

Defjs では、成功分岐を通過するのは `2xx` レスポンスのみであるため、`304 Not Modified` は `HTTP_STATUS` Fault として返ります。空の `304` ボディが読み取られないように `defineRequest` で `error` を未宣言のままにしておき、キャッシュ用の `Map` は操作呼び出しをラップするアプリケーションコード側で保持します。

- `if (err)` の中で処理するのは、キャッシュ済みのエントリがある `304` だけです（キャッシュ済みの製品を返します）。それ以外の Fault はすべてそのまま返され、Go の `return nil, err` と同じです。そのため `createReader` は `Promise<[Error, undefined] | [null, Product]>` を返し、throw しません。`ETag` ヘッダーの欠落はヘルパー自身の失敗であり、これも新しい `Error` として返されます。`main` はプログラムの最上位なので、エラーをログに出して return します。
- インターセプター内で `304` を擬似的な `200` へと書き換えることは避けてください。キャッシュの状態は、操作呼び出しを囲むアプリケーションコード側で管理するのが原則です。詳細は [HTTP 操作](/ja-JP/docs/http) を参照してください。
