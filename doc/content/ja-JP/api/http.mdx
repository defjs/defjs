# HTTP

型付きリクエストを宣言し、クライアントとその入力を渡して操作を呼びます。

## defineRequest()

<ApiSignature name="defineRequest" />

- **definition** — `method`、`path`、任意の `input` struct、任意の `output` と `error` struct、任意の `operation`。`input` を宣言した定義では、明示的な `builder` が必須です。`input` は引数を定義するだけで、各値をどこに置くかは `builder` だけが決めます。`builder` を省略できるのは `input` がない定義だけです。これらの `definition` のメンバーは [`RequestDefinition`](/ja-JP/api/core/requestdefinition-type) にあります。`builder` が必須なのは `input` を宣言したときだけです。
- **戻り値** 操作です。`getOrder(client, input)` のように呼び、入力を宣言していなければ `health(client)` です。入力 struct 全体が任意なら、入力引数は省略できます。呼ぶとリクエストが始まります。3 番目のオプション引数はありません。

<include cwd>examples/api/define-request.ts#example</include>

`output` は 2xx ボディ用の struct 1 つ、`error` は 2xx 以外すべてのボディ用の struct 1 つです。どちらも status でキー分けされません。省いた側のボディは読まれません — [宣言はアサーション（保証）である](/ja-JP/docs/design-decisions#declaration-is-an-assertion) を参照してください。

操作を呼ぶと、[`HttpAwaitResult`](/ja-JP/api/core/httpawaitresult-type) に書かれたタプルの promise が返ります。呼び出しごとのオプションは、[`RequestOptions`](/ja-JP/api/core/requestoptions-type) からクライアントを派生させて渡します。HTTP が読むのは `signal` と進捗コールバックで、他のフィールドは無視します。

2xx 以外の status は、`error` struct を宣言していないか、宣言した `error` ボディがデコードできる場合に `HTTP_STATUS` になります。Fault の `data` は、`error` を宣言していればデコード済みのエラーボディ、していなければ `undefined` です。宣言した `error` ボディを読めない場合（メディアタイプが違う、JSON が不正）や struct に一致しない場合、Fault は代わりに `RES_MEDIA_TYPE_INVALID`、`RES_DECODE_FAILED`、`RES_STRUCT_MISMATCH` のいずれかになり、レスポンスの status はそのメタデータに引き続き含まれます。失敗時のタプルの 3 番目の要素は `undefined` で、レスポンスのメタデータは Fault が持ちます。

## fetchHandler()

<ApiSignature name="fetchHandler" />

デフォルトの HTTP トランスポートです。`fetchImpl` のデフォルトは送信時に解決されるグローバルの `fetch` で、別のものは `withHTTPHandle` で与えます。差し替えられていないプラットフォームの Fetch には `(url, init)` を、差し替えたグローバルやカスタムハンドラーには `Request` を渡します。レスポンスがクライアントに届かなかったとき、または宣言されたボディの読み取りに失敗したときは、合成レスポンスで解決するのではなく reject します。

## makeResponse()

<ApiSignature name="makeResponse" />

ネットワークなしで `HttpResponse` を作ります（インターセプター、テスト）。デフォルトの status は `0` です。`ok` は 2xx のとき true です。返る値は、ワイヤから来たレスポンスと同じメディアタイプ確認と同じ宣言 struct を通ります。信頼による短絡経路はありません。

## HttpExecuteOptions

<ApiSignature name="HttpExecuteOptions" />

`HttpExecuteOptions` は [`RequestOptions`](/ja-JP/api/core/requestoptions-type) の HTTP スライスです。[`UseRequestConfig`](/ja-JP/api/core/userequestconfig-type)、つまり `signal` に `onDownloadProgress`、`onUploadProgress`、`retry` を足したものです。`timeout` フィールドも `abort` フィールドもありません。期限は `signal: AbortSignal.timeout(ms)` で、`NET_TIMEOUT` に分類されます。手動の abort は `NET_ABORTED` です。`signal` はその呼び出しのシグナルです。シグナルを合成するときは、アプリケーションコードで `AbortSignal.any` を使ってください。クライアント単位のデフォルトの期限はありません。`heartbeat` のような他のリクエストフィールドは無視されます。

## 型

### RequestDefinition

`method`、`path`、任意の `input`、`output`、`error`、`operation`、`builder` です。宣言したボディの読み方は struct の種類が決めます。`input` を宣言した定義では、明示的な `builder` が必須です。`input` は引数を定義するだけで、各値をどこに置くかは `builder` だけが決めます。`builder` を省略できるのは `input` がない定義だけです。

### HttpAwaitResult

<ApiSignature name="HttpAwaitResult" />

成功時、3 番目の要素が `body` を持つのは `output` を宣言していたときだけです。失敗時は `undefined` です — 存在したレスポンスのメタデータはすでに Fault が抱えています。

### HttpRequest

正規化された送信リクエストです。`method`、`endpoint`、`headers`、`body`、`signal`、`operation`、`withCredentials`、`finalizeHeaders`、`downloadProgress` / `uploadProgress`、`baseEndpoint`、`queryString`、`queryParams` です。インターセプターが見る時点で `body` はすでにワイヤ上の値（JSON なら JSON テキストの文字列）になっているので、HMAC やダイジェストの署名は struct の入力ではなくこの値に対して行ってください。インターセプターが見る `queryParams` は `new URLSearchParams(queryString)` です。`builder` が `URLSearchParams` を返すと、そのインスタンスがそのまま渡されます。`responseType` と `errorResponseType` は readonly です。宣言された `output` と `error` の struct の種類から導出され、変更してはいけません。

### HttpMeta

<ApiSignature name="HttpMeta" />

レスポンスのメタデータで、レスポンスがクライアントに届いていれば使えます。`body` は**持ちません**。ボディは、宣言された struct がデコードしたあとにだけ存在します。

### DecodedResponse

<ApiSignature name="DecodedResponse" />

ボディが宣言された struct でデコードできたレスポンスです。この型を手にしていること自体がデコードが起きた証拠であり、だからデコード失敗は `HttpMeta` だけを報告します。

### HttpResponse

<ApiSignature name="HttpResponse" />

`body` は、レスポンスにボディがなかったときは `undefined` で、JSON の `null` は `null` のままです。この型はブランド付きなので、オブジェクトリテラルではなく `makeResponse` で作ってください。トランスポートが作り、インターセプターが見るワイヤ上の形です。`body` はテキストか、すでにパースされた JSON で、デコード済みの値ではありません。JSON 表現では、文字列は JSON の文字列ルートであり、もう一度パースされません。バイトと blob は生のままで、一度だけパースされます。呼び出し側に届くのは `DecodedResponse` です。

### HttpProgressEvent

### HttpProgressFn

`loaded`、`total`、`lengthComputable` です。コールバックは非同期でも構いません。`onDownloadProgress` または `onUploadProgress` が例外を投げると、投げられた値を `cause` として呼び出しが `EXT_OBSERVER_FAILED` で失敗します。キャンセルは引き続き `NET_ABORTED` を報告し、abort の理由がタイムアウトなら `NET_TIMEOUT` を報告します。アップロード進捗が報告されるのは、渡したリクエストボディが `ReadableStream` のときだけです。それ以外のボディ（`Blob`、`File`、`ArrayBuffer`、`FormData`、文字列、`URLSearchParams`）は構築されたまま送られ、どのランタイムでも `onUploadProgress` は呼ばれません。ライブラリがボディをストリームに変換することはありません。`ReadableStream` ボディは、`onUploadProgress` の有無にかかわらず、ストリーミングリクエストボディの Fetch の規則に従います。Chromium と WebKit が受け入れるのは HTTP/2 以降だけです（HTTP/1.1 では `NET_UNREACHABLE`。WebKit は 27.2 でのみ手動で確認しました。Node.js と Bun は HTTP/1.1 を受け入れます）。Firefox はリクエストボディをストリームできません（`ENV_UNSUPPORTED`）。ブラウザでは、キャッシュされたプリフライト結果をブラウザが持っていない限り、クロスオリジンのリクエストに CORS プリフライトが必要なので、サーバーは `OPTIONS` に答えなければなりません。301、302、307、308 のリダイレクトは、ボディが一度送られたあと失敗し、303 は GET になって成功します。ブラウザは `Content-Length` を送りません。`fetch` はこれらの失敗と、`fetch` が読んでいるあいだに throw する元の `ReadableStream` を、到達不能なエンドポイントと同じネットワークエラーとして報告するので、ロードバランサーはそれらについて `{ attempted: false }` を受け取ります。throw する進捗コールバック（`EXT_OBSERVER_FAILED`）と同じです。そのため、ストリーミングアップロードだけでは停止したエンドポイントを検出できず、拒否されたストリーミングアップロードはリトライされません。`ReadableStream` ボディは、`shouldRetry` が聞かれる前にリトライの流れを終えるからです。

ストリーミングボディの長さは分かりません。報告される総量は、有効な明示的 `Content-Length` ヘッダーがそれを設定しない限り不明です（ブラウザはそのヘッダーを送りません）。`loaded` が数えるのはストリームのバイト数であり、サーバーの受信確認ではありません。`Content-Encoding` が identity 以外のダウンロードは `total: 0`、`lengthComputable: false` を報告します。そのストリームのバイト列はすでに展開されている場合があります。

[HTTP ガイド](/ja-JP/docs/http) と [Client](/ja-JP/docs/client) を見てください。

## RequestEndpoint

`defineRequest` の戻り値です。第 1 引数は [`Client`](/ja-JP/api/core/client-type) です。それ以降の引数は入力だけです。

## BuilderInput

`builder` が見る、パース済みの操作入力です。オブジェクトノードは、その値を生成した struct の情報を保持するため、値に対応するエイリアス、`Date`、`bigint` のエンコードが適用されます。

## HttpRequestShape

<ApiSignature name="HttpRequestShape" />

4 つのフィールドはすべて任意です。`query` は `URLSearchParams` または record です。入れ子オブジェクトには実行時の `withQuerySerializer` が要ります。`headers` は `HeadersInit`、またはスカラーかスカラーの配列の record です。`path` は `:name` セグメントごとにスカラーを 1 つ渡します。

`GET` と `HEAD` の `body` は `never` です。それ以外では、ワイヤ値（`string`、`Blob`、`ArrayBuffer`、typed array または `DataView`、`FormData`、`URLSearchParams`、`ReadableStream<Uint8Array>`）か、JSON データ（`number`、`boolean`、`bigint`、`Date`、`null`、配列、文字列キーのオブジェクト）です。

## UseRequestConfig

`signal` に、任意の `onDownloadProgress`、`onUploadProgress`、`retry` が加わります。`HttpExecuteOptions` はこのスライスです。`timeout` フィールドも `abort` フィールドもありません。

## RequestSuccessData

宣言された `output` struct から推論される成功ボディです。宣言がなければ `undefined` です。

## RequestErrorData

宣言された `error` struct から推論されるエラーボディです。宣言がなければ `undefined` です。

## HttpResponseType

`'arraybuffer' | 'blob' | 'json' | 'text'`

宣言した struct の種類から選ばれます（`string` → `text`、`blob` / `file` → `blob`、`arrayBuffer` → `arraybuffer`、それ以外 → `json`）。`defineRequest` のフィールドではありません。

## MakeResponseOptions

`makeResponse` 用のフィールドです。`status`、`statusText`、`url`、`headers`、`body`、`request`。
