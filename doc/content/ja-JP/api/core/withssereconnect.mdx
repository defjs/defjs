<ApiReference identity="@defjs/core:withSSEReconnect" />

```ts
function withSSEReconnect(options: ClientSSEOptions['reconnect']): ClientOption
```

SSE ストリームが失敗したあとの自動再接続を設定します。再接続はオプトインで、この option がなければ失敗したストリームはリトライされません。`undefined` を渡すと、先の設定を解除します。

```ts
type SSEReconnect = {
  attempts?: number
  delayMs?: number
  factor?: number
  jitter?: number
  maxDelayMs?: number
  shouldReconnect?: (context: {
    attempt: number
    cause?: unknown
    lastEventId: string
    method: string
    open?: { response: { status: number; statusText: string; url: string }; url: string }
  }) => boolean | Promise<boolean>
}
```

- `attempts` は接続障害 1 回ごとの再試行回数の上限です。`reconnect` を設定したときのデフォルトは `3` で、`0` は再試行を無効にします。ハンドシェイクが成功すると、再試行の残り回数が初期値に戻り、コールバックの `attempt` とバックオフの指数がリセットされます。省略しても、1 回の接続障害に対する再試行が無制限になるわけではありません。オープン成功の直後に再試行可能なストリーム失敗が繰り返されると、オープンのたびに予算がリセットされるため、現在のベース遅延（jitter と上限の制約下）で再接続が続き得ます。止めるには `shouldReconnect` を使ってください。通常の EOF は引き続き終端です。
- `shouldReconnect` がなければ、再接続するのは `GET`、`HEAD`、`OPTIONS`、`PUT`、`DELETE` だけです。指定されていれば、`POST` を含むすべてのメソッドについて、その戻り値で再接続するかどうかを決めます。コンテキストの `method` でエンドポイントを区別できます。この失敗に対するリトライを止めるには `false` を返します。`attempts` の上限を確認する前に実行されます。
- `ReadableStream` をボディに持つリクエストは再接続せず、そのリクエストに対して `shouldReconnect` が呼ばれることもありません。
- `delayMs`、`factor`、`jitter`（0 から 1）、`maxDelayMs` がバックオフの形を決めます。`factor` のデフォルトは `1`、`jitter` は `0` です。`maxDelayMs` はジッターと丸めの後の最終的な待ち時間を制限します。上限を設定していなくても、プラットフォームのタイマー上限 `2_147_483_647` ミリ秒が適用されます。基準値がゼロなら待ち時間もゼロのままです。有効な数値による計算がオーバーフローした場合は、上限値に制限されます。
- `delayMs` は開始時の基準の待ち時間（デフォルトは `1000`）にすぎません。サーバーの `retry:` フィールド（数字のみ、ミリ秒）があれば、以降の試行ではそれに置き換わります。
- 最後のイベント ID は、次の試行で `Last-Event-ID` に UTF-8 バイト列としてもう一度送られます。空の `id:` は保存された ID を消去し、NUL を含む ID は無視されます。
- 再接続の options はインターセプターや Fetch の実行前に検証されます。`attempts` は非負の安全な整数、`delayMs` と明示的な `maxDelayMs` は非負の有限値、`factor` は正の有限値、`jitter` は 0–1 の範囲内の有限値でなければなりません。不正な値は execute 時に `REQ_OPTIONS_INVALID` を返します。

ストリームハンドルは [SSE](/ja-JP/api/sse) を見てください。
