# WebSocket

ソケットを宣言し、実行し、型付きメッセージを送受信してから閉じます。

## defineWebSocket()

```ts
function defineWebSocket(definition: WebSocketDefinition): WebSocketEndpoint
```

- **definition** — `path`、`incoming` struct 1 つ、必須で正の整数の `maxIncomingQueueSize`、任意の `outgoing` と `input` struct、`operation`、静的な `protocols`、0 以上の `maxOutgoingQueueSize` です。`input` を宣言した定義では、入力がすでにリクエストの形でも、明示的な `builder` が必須です。`builder` を省略できるのは `input` がない定義だけです。
- **戻り値** エンドポイントです。入力を渡して呼ぶと `WebSocketCommand` になります。

## executeWebSocketCommand()

```ts
function executeWebSocketCommand<
  TInput extends AnyStruct | undefined,
  TIncoming extends AnyStruct,
  TOutgoing extends AnyStruct | undefined,
>(
  clientConfig: ClientConfig,
  command: WebSocketCommand<TInput, TIncoming, TOutgoing>,
  options?: WebSocketExecuteOptions<WebSocketIncomingData<TIncoming>, WebSocketOutgoingData<TOutgoing>>,
): Promise<SocketAwaitResult<WebSocketIncomingData<TIncoming>, WebSocketOutgoingData<TOutgoing>>>
```

`client.execute` の低レベル入口です。アプリコードではクライアントを使ってください。

- **戻り値** `[null, session, connection]`、または `[error, undefined, connection?]` です。

WebSocket の execute は `beforeConnect`、`heartbeat`、`protocols`、`reconnect` を 1 回の呼び出しに限って上書きでき、それぞれクライアントの値を置き換えます。protocols の優先順位は、execute、`withWebSocketProtocols`、定義の `protocols` の順です。

## WebSocketSession

```ts
interface WebSocketSession<TIncoming = unknown, TOutgoing = never> extends AsyncDisposable {
  readonly bufferedAmount: number
  readonly connection: WebSocketConnectionInfo
  readonly closed: Promise<WebSocketCloseInfo>
  readonly receive: AsyncIterable<TIncoming>
  readonly state: WebSocketState
  close(code?: number, reason?: string): void
  [Symbol.asyncDispose](): PromiseLike<void>
  send(message: TOutgoing): void
  onRuntimeError(listener: (error: unknown) => void): () => void
  onStateChange(listener: (state: WebSocketState) => void): () => void
}
```

所有するスコープのクリーンアップには `await using ownedSession = session` を選んでください。手動の `session.close()` と `await session.closed` も残っています。

```ts
async function consume(session: WebSocketSession<unknown, never>): Promise<void> {
  await using ownedSession = session
  for await (const message of ownedSession.receive) console.log(message)
}
```

`closed` は論理的な終端状態を報告します。非同期 disposer はネイティブ close を要求し、Defjs が所有する teardown を待ちますが、close イベントが無い場合は 1 秒で打ち切り、`TimeoutError` という名前の `DOMException` で reject することがあります。物理 TCP 接続が閉じたことは証明できません。

### WebSocketState

`'idle' | 'connecting' | 'open' | 'closing' | 'closed' | 'reconnecting' | 'aborted' | 'error'`

### WebSocketConnectionInfo

`generation`（再接続で増えます）と、わかった時点での `url`、`protocol`、`extensions` です。

### WebSocketCloseInfo

```ts
type WebSocketCloseInfo =
  | { kind: 'closed'; code?: number; reason?: string; wasClean?: boolean }
  | { kind: 'aborted'; cause?: unknown; code?: number; reason?: string; wasClean?: boolean }
  | { kind: 'error'; cause: unknown; code?: number; reason?: string; wasClean?: boolean }
```

ソケット終了後の close スナップショットです（code、reason、clean フラグ、任意の cause）。手動 close は `ManualSocketCloseReason` を持てます。

## 実行 options

## WebSocketExecuteOptions

```ts
type WebSocketExecuteOptions<TIncoming = unknown, TOutgoing = unknown> = {
  signal?: AbortSignal
  beforeConnect?: (context: { attempt: number; signal: AbortSignal }) => void | Promise<void>
  protocols?: readonly string[]
  heartbeat?: WebSocketHeartbeatConfig<TIncoming, TOutgoing>
  reconnect?: ClientWebSocketOptions['reconnect']
} & ({ abort?: AbortSignal; timeout?: never } | { abort?: never; timeout?: number })
```

`WebSocketHeartbeatConfig` は `intervalMs`、任意の `message`、`isAck`、`timeoutMs` です。

`abort` と `timeout` は同時に使えません。型は両方の指定を拒否し、実行時に両方を渡すと `REQ_OPTIONS_INVALID` の fault で失敗します。`signal` はどちらとも組み合わせられます。`timeout` は接続の開始期限です。あとの再接続で再び設定されることはなく、`withTimeout` は WebSocket には適用されません。

`reconnect` を指定したとき、`attempts` のデフォルトは障害ごとに 3 です。`0` はリトライを無効にします。`open` に成功すると予算とバックオフの指数がリセットされるため、新たな障害ではリトライ 1 から始まります。`attempts` を省いても、1 回の障害に対するリトライが無制限になるわけではありません。デフォルトと検証規則は [Client](/ja-JP/api/client) を参照してください。

## メッセージ

`incoming` は struct 1 つです。テキスト、`ArrayBuffer`、typed-array、`Blob` のフレームは UTF-8 として読まれ、JSON パースされ、その struct に対して検査されます。JSON パースか struct に失敗したフレームは `session.onRuntimeError` に報告され、キューには入りません。クライアント側の不正フレーム option はありません。

`outgoing` は struct 1 つです。`session.send` はその struct の `StructInput` を受け、エイリアスをエンコードしてから `JSON.stringify` します。エンコード後に JSON で忠実に表現できない値は、送信や再接続キューへの追加の前に `TypeError` を投げます。非有限数、関数、symbol、`Map`、`Set`、ストリーム、JSON 表現を持たないクラスインスタンスなどが該当します。入れ子の値にも HTTP の JSON ボディと同じチェックを使います。ハートビートにもこのチェックが適用され、ハートビートのシリアライズに失敗するとセッションが終了します。メッセージの種類が複数なら `struct.discriminatedUnion` です。

```ts
session.send({ type: 'message', text: 'Hello' })
```

[WebSocket ガイド](/ja-JP/docs/web-socket) と [WebSocket セッションを開く](/ja-JP/recipes/websocket-session) を見てください。

## WebSocketDefinition

`path`、`incoming`、必須の `maxIncomingQueueSize`、任意の `outgoing` / `input` / `operation` / `protocols` / `maxOutgoingQueueSize` です。ビルダーが返せるのは `path` と `query` だけです。`input` を宣言した定義では、入力がすでにリクエストの形でも、明示的な `builder` が必須です。`builder` を省略できるのは `input` がない定義だけです。

## WebSocketEndpoint

`defineWebSocket` の戻り値です。入力を渡して呼ぶと `WebSocketCommand` になります。

## WebSocketRequestShape

`path` と `query` だけです。`headers` と `body` は `never` です。

## WebSocketCommand

不透明な WebSocket コマンドです。`client.execute` に渡します。

## UseWebSocketConfig

ハートビート、再接続、`beforeConnect`、protocols、それにキャンセルです。`WebSocketExecuteOptions` は `signal` を足します。

## SocketAwaitResult

`[null, session, connection]` または `[error, undefined, connection?]` です。

## ManualSocketCloseReason

`session.close()` で閉じたときに記録される理由です。

## WebSocketHeartbeatConfig

`intervalMs`、任意の `message`、`isAck`、`timeoutMs` です。

## WebSocketIncomingData

デコードされた受信フレームです。`incoming` struct の `Infer` です。

## WebSocketOutgoingData

`session.send` が受け付ける値です。`outgoing` struct の `StructInput` で、宣言が無ければ `never` です。

## SocketLifecycleOutcome

1 回の接続試行の結果（`closeInfo`、`connection`、`cause`、`opened`）で、再接続のロジックが使います。セッションの最終結果ではありません。それは `WebSocketCloseInfo` を見てください。
