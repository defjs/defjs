# WebSocket

ソケットを宣言し、クライアントを渡して操作を呼び、型付きメッセージを送受信してから閉じます。

## defineWebSocket()

<ApiSignature name="defineWebSocket" />

- **definition** — `path` と `incoming` struct 1 つ、任意の `outgoing` と `input` struct、`operation`、静的な `protocols`、`maxOutgoingQueueSize` です。`input` を宣言した定義では、明示的な `builder` が必須です。`input` は引数を定義するだけで、各値をどこに置くかは `builder` だけが決めます。`builder` を省略できるのは `input` がない定義だけです。これらの `definition` のメンバーは [`WebSocketDefinition`](/ja-JP/api/core/websocketdefinition-type) にあります。`builder` が必須なのは `input` を宣言したときだけです。
- **戻り値** 操作です。第 1 引数は [`Client`](/ja-JP/api/core/client-type) です。それ以降の引数は入力だけです。呼ぶとセッションが開きます。

<include cwd>examples/api/define-web-socket.ts#example</include>

呼び出しは `[null, session, connection]` または `[error, undefined, connection?]` を返します。呼び出しごとのオプションは、[`RequestOptions`](/ja-JP/api/core/requestoptions-type) からクライアントを派生させて渡します。WebSocket が読むのは `signal`、`beforeConnect`、`heartbeat`、`protocols`、`retry` で、HTTP の進捗フィールドは無視します。

`beforeConnect`、`heartbeat`、`protocols`、`retry` は、それぞれがその呼び出しに限り、クライアントレベルのオプションを全体として置き換えます。protocols の優先順位は、派生したクライアント、`withWebSocketProtocols`、定義の `protocols` の順です。`heartbeat.timeoutMs` は確認待ちであり、リクエストの期限ではありません。

## WebSocketSession

<ApiSignature name="WebSocketSession" />

所有するスコープのクリーンアップには `await using ownedSession = session` を選んでください。手動の `session.close()` と `await session.closed` も残っています。

</include>

`closed` は論理的な終端状態を報告します。非同期 disposer はネイティブ close を要求し、Defjs が所有する teardown を待ちますが、close イベントが無い場合は 1 秒で打ち切り、`TimeoutError` という名前の `DOMException` で reject することがあります。物理 TCP 接続が閉じたことは証明できません。

### WebSocketState

`'idle' | 'connecting' | 'open' | 'closing' | 'closed' | 'reconnecting' | 'aborted' | 'error'`

### WebSocketConnectionInfo

`generation`（`open` のたびに増えます）と、わかった時点での `url`、`protocol`、`extensions` です。

### WebSocketCloseInfo

<ApiSignature name="WebSocketCloseInfo" />

`kind` は `closed`、`aborted`、`error` のいずれかです。`cause` は `closed` にはなく、`aborted` では任意、`error` では必須です。`error` では、同じ cause が、すでにキューにあったメッセージのあとで `receive` を reject し、`onRuntimeError` にも届きます。セッションが `aborted` で終わるとき、および呼び出し元が `session.close()` または解放で終えるとき、未読のメッセージは捨てられます。呼び出し元の停止（`session.close()`、解放、`signal` の abort）は、セッションが終わったあとでもそれらを捨て、`closed` や `receive` の reject は変えません。ハートビートのタイムアウトやリトライ回数の使い切りでは、通常の実行時 `Error` が cause となり、個別の安定したコードはありません。開いたあとクローズフレームなしで切れた接続（コード `1006`）は、どのランタイムでも `error` です。`code`、`reason`、`wasClean` はどのバリアントにも現れ得ます。手動の `session.close()` は、close イベント側にそれらが無いとき、`{ kind: "closed" }` の `code` と `reason` を埋めます。

## WebSocketExecuteOptions

<ApiSignature name="WebSocketExecuteOptions" />

`WebSocketExecuteOptions` は [`UseWebSocketConfig`](/ja-JP/api/core/usewebsocketconfig-type) です。`beforeConnect`、`heartbeat`、`protocols`、`retry`、`signal` です。`WebSocketHeartbeatConfig` は `intervalMs` と `message` が必須で、`timeoutMs` は `isAck` と一緒のときだけ許可されます。`timeout` フィールドも `abort` フィールドもありません。

`signal` は、開いたあとも含めてセッション全体を対象にします。期限は `AbortSignal.timeout(ms)` で、`NET_TIMEOUT` に分類されます。手動の abort は `NET_ABORTED` です。クライアント単位のデフォルトの期限はありません。接続の確立中だけに期限を設けるには `retry: { maxRetries: 0, attemptTimeoutMs }` で、`open` で終わります。`signal` はその呼び出しのシグナルです。シグナルを合成するときは、アプリケーションコードで `AbortSignal.any` を使ってください。`heartbeat` は全体が置き換わり、その `timeoutMs` は確認を待ち、リクエストの期限ではありません。

`builder` とインターセプターチェーンは操作ごとに 1 回だけ実行されます。再接続では構築済みの path/query と取り込んだ protocols を再利用し、`beforeConnect` より前に URL を構築します。インターセプターがリクエストのベースエンドポイントを置き換えていない場合、再接続では新たに選んだエンドポイントに置き換えます。このフックではセッション内で URL やサブプロトコルの認証情報を更新できません。新しい input またはクライアント設定で新たな操作を開始してください。

リトライポリシー（`withRetry`）を設定したとき、`maxRetries` のデフォルトは障害ごとに 3 です。`0` は無効にします。`session.close()` が要求していないすべての close はデフォルトでリトライされます。開かなかった接続と、応答のないハートビートを含み、`shouldRetry` はそれを覆せます。WebSocket のコンストラクターが throw する（たとえばプラットフォームが拒否するサブプロトコル）のは、リトライしても繰り返すだけのローカルな失敗です。`shouldRetry` を聞かずに呼び出しを終えます。`open` に成功すると回数とバックオフの指数がリセットされるため、新たな障害ではリトライ 1 から始まります。デフォルトと判断の順序は [Client](/ja-JP/api/client#withretry) を参照してください。

## メッセージ

`incoming` は struct 1 つです。テキスト、`ArrayBuffer`、typed array、`Blob` のフレームは UTF-8 として読まれ、JSON パースされ、その struct に対して検査されます。JSON パースか struct に失敗したフレームは `session.onRuntimeError` に報告され、キューには入りません。クライアント側の不正フレームオプションはありません。

`outgoing` は struct 1 つです。`session.send` はその struct の `StructInput` を受け、エイリアスをエンコードしてから `JSON.stringify` します。エンコード後に JSON で忠実に表現できない値は、送信や再接続キューへの追加の前に `TypeError` を投げます。非有限数、関数、symbol、`Map`、`Set`、ストリーム、JSON 表現を持たないクラスインスタンスなどが該当します。入れ子の値にも HTTP の JSON ボディと同じチェックを使います。ハートビートにもこのチェックが適用され、ハートビートのシリアライズに失敗するとセッションが終了します。メッセージの種類が複数なら `struct.discriminatedUnion` です。

## WebSocketDefinition

`path`、`incoming`、任意の `outgoing` / `input` / `operation` / `protocols` / `maxOutgoingQueueSize` です。`builder` が返せるのは `path` と `query` だけです。`input` を宣言した定義では、明示的な `builder` が必須です。`input` は引数を定義するだけで、各値をどこに置くかは `builder` だけが決めます。`builder` を省略できるのは `input` がない定義だけです。

## WebSocketEndpoint

`defineWebSocket` の戻り値です。第 1 引数はクライアントです。それ以降の引数は入力だけです。

## WebSocketRequestShape

`path` と `query` だけです。`headers` と `body` は `never` です。

## UseWebSocketConfig

`beforeConnect`、`heartbeat`、`protocols`、`retry`、`signal` です。`WebSocketExecuteOptions` はこのスライスです。`abort` フィールドはありません。

## SocketAwaitResult

`[null, session, connection]` または `[error, undefined, connection?]` です。

## ManualSocketCloseReason

`session.close()` で閉じたときに記録される理由です。

## WebSocketHeartbeatConfig

`intervalMs` と `message` は必須です。`isAck` は確認を識別し、`timeoutMs` は `isAck` と一緒のときだけ許可されます。union 型がそれを強制し、実行時に検査するものはありません。Defjs はハートビートの形式を定義しません。すべての値は利用者の関数から来ます。ペイロードは `outgoing` struct を通じて JSON テキストとして送られます。応答のないハートビートはソケットを閉じ、`withRetry` のリトライの流れに入ります。リトライポリシーがなければ、セッションは `error` で終わります。

## WebSocketIncomingData

デコードされた受信フレームです。`incoming` struct の `Infer` です。

## WebSocketOutgoingData

`session.send` が受け付ける値です。`outgoing` struct の `StructInput` で、宣言が無ければ `never` です。

## SocketLifecycleOutcome

1 回の接続試行の結果（`closeInfo`、`connection`、`cause`、`opened`）で、リトライのロジックが使います。セッションの最終結果ではありません。それは `WebSocketCloseInfo` を見てください。
