# WebSocket セッション

`defineWebSocket` は、SDK における双方向の WebSocket 契約を宣言します。パステンプレート、任意の `input` と `builder`（`path` と `query` のみ）、`incoming` および `outgoing` メッセージの struct、キューの上限、静的なサブプロトコルを指定します。利用側アプリケーションは、ハートビート、リトライ（`withRetry`）、ライフサイクルのクリーンアップをクライアント側で構成します。

## 1. 契約の定義とセッションの実行

`incoming` や `outgoing` で複数のフレーム種別を扱うには、`struct.discriminatedUnion(...)` を使用してモデル化します。返された `WebSocketSession` は、`await using` または明示的な `session.close()` + `await session.closed` で解放します。

## 2. メッセージ検証と方向のルール

- **受信フレーム (`session.receive`)**: テキスト、`ArrayBuffer`、typed array、`Blob` の各フレームは UTF-8 としてデコードされ、JSON としてパースされた後に `incoming` スキーマで検証されます。壊れた JSON やスキーマ不一致は `session.onRuntimeError` に報告され、セッションを切断することなく破棄されます。`session.receive` は単一コンシューマー専用です。2 つ目のイテレーターを取得しようとすると `TypeError` が throw されます。トランスポートが失敗したときは、すでに受信したメッセージが先に届けられ、そのあと `receive` が `closed.cause` で reject します。ハートビートのタイムアウトも含まれます。呼び出し元によるキャンセル（`signal` の abort）、`session.close()`、解放は、セッションがすでに終わっていたかどうかにかかわらず、未読のメッセージを捨てます。開いているセッションでは、そのあと `receive` は `session.close()` または解放のあとすぐに終わり、abort のあとは abort の理由（既定では `AbortError`）で reject します。`session.close()` のあとに届いたフレームも捨てられます。`AbortSignal.timeout(ms)` のように、セッションが開いているあいだに期限が切れる `signal` はタイムアウトです。セッションはエラーとして終わり、キューにあるメッセージを先に届けます。セッションが終わったあとに期限が切れるものは停止であり、それらを捨てます。
- **送信フレーム (`session.send(payload)`)**: `outgoing` スキーマに対して同期的に検証され、`.alias()` とコーデックが適用され、`JSON.stringify` でシリアライズされます。`open` 状態では即座に送信され、`reconnecting`（再接続中）状態では `maxOutgoingQueueSize > 0` の場合にキューイングされます。ペイロードが無効な場合、キューが無効または満杯の場合、あるいはセッションがクローズされている場合は、同期的に例外が throw されます。

## 3. セッションの状態とオブザーバー

| メンバー             | 説明                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `state`              | `'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'` |
| `connection`         | 最新の物理ソケットのライブスナップショット（`generation`、`url`、`protocol`、`extensions`）           |
| `bufferedAmount`     | アクティブな物理ソケット上の未送信バイト数（切断時は `0`）                                            |
| `receive`            | 検証済み `incoming` メッセージの単一コンシューマー向け非同期イテラブル                                |
| `onStateChange(fn)`  | 状態遷移を購読。`unsubscribe` 関数を返します                                                          |
| `onRuntimeError(fn)` | 接続確立後のフレームパースエラーなどを購読。`unsubscribe` 関数を返します                              |
| `closed`             | 最終的な結果（`kind: 'closed' \| 'aborted' \| 'error'`）へと解決される Promise                        |

## 4. リトライ、ハートビート、キューの制御

再接続とハートビートは、クライアントオプション（`withRetry`、`withWebSocketHeartbeat`）または呼び出しごとの一時クライアントオプション（`client({ retry, heartbeat })`）を通じたオプトイン設定です。再接続は HTTP と SSE と同じ `withRetry` ポリシーを使います。

- **リトライ**: リトライポリシーを設定したときのデフォルトは `maxRetries: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0.2` です。`session.close()` が要求していないすべての close はデフォルトでリトライされます。開かなかった接続も含みます。throw するコンストラクターは、リトライしても繰り返すだけのローカルな失敗なので、`shouldRetry` を聞かずに呼び出しを終えます。物理的な `open` が完了するたびに障害の回数がリセットされます。`shouldRetry` はデフォルトを覆すことができ、非同期でも構いません。手動の close、呼び出し元の abort、`maxRetries` 回のリトライを終えたあとには呼ばれません。辞退された、または使い切ったリトライは、ポリシーがないときと同じようにセッションを終えます。接続エラーは `closed.kind: "error"`、ピアからの close フレームは `"closed"` です。`error` イベントのあと 1 秒以内に `close` イベントが届かない場合、またはエラーになったソケットでネイティブの `close()` が throw する場合は、ハートビートの未応答と同じく失敗した試行となり、続きはリトライポリシーが決めます。`session.close()` のあとで同じ状況になったときは、セッションは `closed.kind: "closed"` で終わります。`beforeConnect({ attempt, signal })` は、初回接続およびすべてのリトライの直前に実行されます。open 済みのソケットがバランサーへ報告される結果は、`wasClean` の値にかかわらずクローズコードだけで決まります。`1006` または `1015`（クローズフレームが届かなかった）は `NET_UNREACHABLE`、`1012` または `1013` は `NET_UNAVAILABLE`、それ以外のコードは失敗として扱われません。
- **試行のタイムアウト (`attemptTimeoutMs`)**: 渡したときは、構築から `open` までを区切り、ハンドシェイクのあとで解除されます。これは `withRetry`（または `retry` リクエストオプション）のオプションなので、`withRetry({ attemptTimeoutMs })` はデフォルトの `maxRetries: 3` でリトライもします。ハンドシェイクだけに期限を設けるには、`withRetry({ maxRetries: 0, attemptTimeoutMs })` と書いてください。期限が切れるとバランサーへ `NET_UNREACHABLE` を報告し、リトライを使い切ると `NET_TIMEOUT` で終わります。
- **ハートビート**: Defjs はハートビートの形式、間隔、タイムアウトを定義しません。`message` と `isAck` は利用者の関数であり、型は `message` を必須とし、`timeoutMs` は `isAck` と一緒のときだけ許可します。ブラウザの `WebSocket` インターフェイスにはプロトコルレベルの ping を送る手段がないため、移植できるハートビートはアプリケーションレベルのメッセージだけです。`intervalMs` ごとに `message()` を `outgoing` struct 経由で JSON テキストとして送るので、エンドポイントは `outgoing` struct を宣言し、素のテキストやバイナリの ping はできません。デコードされたフレームが `isAck(msg)` に一致するまで、最大 `timeoutMs` 待ちます。`incoming` struct に失敗したフレームは `onRuntimeError` に報告され、`isAck` には届きません。合致した ACK フレームはハートビートモニターによって消費され、`session.receive` には転送されません。ACK を受信できなければ接続失敗として数えられます。ソケットは閉じられ、ACK の未受信はそのエンドポイントについて `NET_UNREACHABLE` としてバランサーに報告され、試行は他の close と同じようにリトライの流れに入ります。リトライポリシーがないとき、またはリトライを使い切ったとき、`closed.kind` は `"error"`、`closed.cause` は通常の `Error("WebSocket heartbeat timeout")` です。ハートビートのシリアライズ失敗や `message()` の throw はローカルです。元の cause でセッションを終え、リトライされず、エンドポイントにも帰属しません。
- **キューの制限**:
  - 受信メッセージ: オプションも件数の上限もありません。ライブラリは、プラットフォームが届けたメッセージを `session.receive` が読むまで全部キューに入れるので、読まないコンシューマーはキューを際限なく増やします。セッションが開いているあいだは `session.receive` を消費するか、セッションを閉じてください。
  - `maxOutgoingQueueSize`（任意、デフォルトは `0`）: `state === 'reconnecting'` の間のみ `session.send()` の呼び出しをバッファリングし、次の `open` 状態が公開される直前にフラッシュ（送信）します。

`shouldRetry` は、WebSocket のコンテキストでネイティブの close の `code`、`reason`、`wasClean` を受け取り、そこでの `retryable` は常に `true` です。サーバーはアプリケーションエラーコード `1011` でも正常なクローズハンドシェイクを完了できるため、`wasClean === true` はアプリケーションの成功を意味しません。サンプルは `code` で判断します。`!wasClean` だけに頼らず、プロトコルに応じてアプリケーションのコードを選んでください。

## 5. サブプロトコルと認証 [#protocols-and-authentication]

ブラウザの WebSocket API は任意のハンドシェイクヘッダーをサポートしていないため、WebSocket の `builder` 関数は `{ path?, query? }` のみを返します。

- **サブプロトコルの優先順位**: `client({ protocols })` が `withWebSocketProtocols(...)` を上書きし、それが `defineWebSocket({ protocols })` を上書きします。
- **URL の自動変換**: Defjs は、解決されたエンドポイントのスキームを自動的に `http:` → `ws:`、`https:` → `wss:` へと変換します。
- **認証情報**: `withCredentials(true)` は Fetch（HTTP/SSE）のみに適用されます。WebSocket の認証は、Cookie／セッションポリシー、サブプロトコル、または短寿命の接続トークン（チケット）を使用して行います（クエリ文字列に長寿命のシークレットを配置することは避けてください）。
- **`beforeConnect` はリクエストを書き換えるフックではありません**: 入力のパース、同期的な純粋関数である `builder`、インターセプターチェーンは、操作ごとに 1 回だけ実行されます。インターセプターがベースエンドポイントを置き換えていないリクエストでは、各再接続でエンドポイントを選び直し、そのエンドポイントで URL を再構築しますが、構築済みの path/query と取り込んだプロトコル一覧は再利用します。同じエンドポイントでもフェイルオーバー後でも、URL はその試行の `beforeConnect` が実行される前に確定します。フック内でクロージャ変数、input、プロトコル配列を変更しても、現在のハンドシェイクに新しいチケットを渡すことはできません。1 つのセッション内での URL／サブプロトコル認証情報の更新は未対応です。新しい認証情報を先に取得し、新たな操作に input またはクライアント設定として渡して、置き換えたセッションのクリーンアップを管理してください。

## 6. クローズと所有権

`session.close(code?, reason?)`（`code` は `1000` または `3000..4999`、`reason` は 123 バイト以下の UTF-8 文字列）を呼び出して `await session.closed` を待つか、`await using` を使用します。

開いたあとクローズフレームなしで切れた接続（コード `1006`、`wasClean: false`）は、ランタイムがネイティブの `error` イベントを発火するかどうかにかかわらず、常に `closed.kind: "error"` と `closed.cause` の `Error("WebSocket connection error")` で終わります。

リトライの障害が `maxRetries` を使い切ると、セッションは `closed.kind: "error"` で終了し、ネイティブのクローズスナップショット（アップグレード失敗では多くの場合コード `1006`）を保持し、通常のトランスポートエラーを `closed.cause` とします。試行回数の枯渇を表す専用の安定したコードは公開しません。セッションが `closed.kind: "error"` で終わるとき、すでにキューにあったメッセージは届けられ、`session.receive` は最後の 1 件のあと `closed.cause` で reject します。ピアからの close も、`session.receive` が終わる前にキューのメッセージを届けます。呼び出し元がセッションを止めるときは、未読のメッセージが捨てられます。呼び出し元の abort（`closed.kind: "aborted"`）、手動の `session.close()`、`await using` による解放は、セッションがすでに終わったあとでもこれをします。開いているセッションでは、そのあと `session.receive` は `session.close()` または解放のあとすぐに終わり、呼び出し元の abort のあとは abort の理由である `closed.cause` で reject します。セッションが終わったあとの停止は、未読のメッセージを捨て、それ以外は何も変えません。`closed` は値を保ち、未読がなくなれば `session.receive` は引き続き `closed.cause` で reject します。コンポーネントやワーカーの処理が終わったら、`onStateChange` と `onRuntimeError` のリスナーを必ず解除してください。
