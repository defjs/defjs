# WebSocket

SDK の作成者は `defineWebSocket` で path、入力の配置、incoming / outgoing の Struct を公開します。利用アプリケーションは接続先、プラットフォームの WebSocket 実装、実行時の方針を構成し、セッションの送受信と終了を管理します。

開始 → 受信 → 送信 → `await using` で解放します。購読解除と破棄は呼び出し側の所有です。手動の `close()` / `closed` も残っています。クライアント、プロバイダ、インターセプターはセッションを自動 close しません。

## 方向ごとに struct は 1 つ

`incoming` はすべてのテキストフレーム用の struct 1 つです。`outgoing` は `session.send(...)` 用の struct 1 つです。種類が複数なら `struct.discriminatedUnion` でモデルします。それらのフィールドのエイリアスが、両方向のワイヤ名です。別の型エンベロープも、ノーマライザもありません。

```json
{ "type": "message", "text": "Hello" }
```

受信したテキスト、`ArrayBuffer`、typed-array、`Blob` のフレームは UTF-8 として読まれ、JSON パースされ、`incoming` に対して検査されます。壊れた JSON と struct の失敗は `session.onRuntimeError` へ行き、キューには入りません。セッションは開いたままです。テキストでもバイト列でも `Blob` でもないフレームは無視されます。`withWebSocketOnInvalidEvent` はありません。

`session.send(...)` は同期的に検証してシリアライズします。struct のエンコード、それから `JSON.stringify` です。open ならすぐ送り、送信キューが有効な `reconnecting` 中はキューし、書けないときは `InvalidStateError` を throw します。outgoing struct が無いとき、ペイロードが struct に失敗したとき、送信キューが無効か満杯のとき、ネイティブ send が失敗したときも throw します。定義上の静的な `protocols` リストはエンドポイント契約です（たとえば `graphql-transport-ws`）。実行 options と `withWebSocketProtocols` はそれでも上書きできます。サブプロトコルを決められるのはこれらの options だけです。ビルダー、`beforeConnect`、インターセプターは変更できないので、サブプロトコルに載せるトークンは、その呼び出しの execute の `protocols` option として渡します。ビルダーが返せるのは `path` と `query` だけです。

struct のエンコード後、JSON で忠実に表現できない値は、送信や再接続キューへの追加の前に `TypeError` を throw します。非有限の数値、関数、symbol、`Map`、`Set`、ストリーム、JSON 表現を持たないクラスインスタンスが該当します。入れ子の値も HTTP の JSON ボディと同じ規則に従います。`struct.number()` は引き続き無限大を受け付け、`NaN` を拒否します。struct 層で受け付けられた値でも、有効な JSON になるとは限りません。ハートビートも同じシリアライザを使い、シリアライズの失敗で論理セッションが終了します。

`receive` は消費者 1 人です。2 つ目のイテレータを要求すると `TypeError` が throw されます。

## 状態のスナップショット

| メンバー                   | 意味                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------- |
| `state`                    | `idle`、`connecting`、`open`、`reconnecting`、`closing`、`closed`、`aborted`、`error` |
| `connection`               | 最新の物理接続。`generation`、URL、交渉した protocol、取れるときの extensions         |
| `bufferedAmount`           | ネイティブの未送信バイト数。物理ソケットが無ければ `0`                                |
| `receive`                  | 検証済み受信メッセージの、消費者 1 人の非同期イテラブル                               |
| `onStateChange(listener)`  | 論理状態の遷移を購読する。購読解除を返す                                              |
| `onRuntimeError(listener)` | 起動後のランタイムエラーを購読する。購読解除を返す                                    |
| `closed`                   | 論理的な終端クローズ結果の promise                                                    |

`open` は物理ソケットが開いた状態です。`reconnecting` は、置き換え前の準備と待ちを含みます。`connection.generation` は `open` に達した物理ソケットごとに増えます。`session.connection` は再接続のたびに更新されます。タプルの `startupConnection` が最初の成功した接続のスナップショットを保持するのは、Defjs のネイティブセッションか、同じライブ `connection` オブジェクトをそのまま渡すラッパーの場合だけです。独自セッションや `connection` を変換するラッパーでは、返されたセッションが現在公開している `connection` が使われます。`closed` の共有では URL のサニタイズやメタデータのフィルタリングを迂回できず、Defjs は任意の変換から最初の接続のメタデータを再構築しません。

起動失敗 → `[error, undefined, connection?]` です。open 前のコンストラクタ失敗では connection が無いことがあります。起動中のタイムアウトや close では、スナップショットがまだ付くことがあります。セッションが返ったあとのランタイムエラーは、オブザーバー、`receive`、`closed` を通ります — 2 つ目の execute タプルにはなりません。

## 再接続

再接続はオプトインです。`reconnect` オブジェクトが無い → 物理 close で論理セッションは終わります。設定したときのデフォルトは `attempts: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0` です。`attempts` は中断ごとのリトライ予算で、`open` が成功すると予算とバックオフ指数がリセットされます。そのため、その後の各中断もリトライ 1 と `delayMs` のベースから始まります。`attempts: 0` はリトライを無効にします。デフォルトの述語は、その中断の予算内で、手動以外のすべての close 結果を受け入れます。open の成功が繰り返されても、全ライフサイクルにわたるリトライ回数の上限はありません。正常に開いた直後にサーバーから再び閉じられるソケットは、open のたびに予算がリセットされるため、ベース遅延（jitter と上限の制約下）で再接続が続き得ます。止めるには `shouldReconnect` を使ってください。

<include cwd>examples/web-socket/reconnect.ts#example</include>

`shouldReconnect` は次のリトライ試行、close の cause、code、reason、`wasClean` を受け取ります。手動の `session.close(...)` は述語に入りません。準備や方針が throw すると、論理セッションはエラーで終わります。

WebSocket のバックオフ jitter は**乗法**です（`jitter: 0.2` は、上限適用済みのベースを丸め前に `0.8x`–`1.2x` 倍にします）。最終遅延は再び `maxDelayMs` とプラットフォームのタイマー上限 `2_147_483_647` ms で制限されるので、その範囲の上側は切り詰められることがあります。ベースがゼロならゼロのままで、有効な数値から生じるオーバーフローは例外ではなく上限への切り詰めになります。SSE も同じ 0–1 の jitter 規則です。再接続 options はコンストラクタの前に検証されます。`attempts` は非負の安全な整数、`delayMs` は非負の有限値、`maxDelayMs` は非負の有限値または正の `Infinity`（設定上の上限を解除しますが、最終遅延は引き続き `2_147_483_647` ms 以下に制限されます）、`factor` は有限で正、`jitter` は有限で 0–1 の範囲である必要があります。無効な値では `REQ_OPTIONS_INVALID` が返ります。WebSocket の `attempts: 0` は以降のリトライを無効にしますが、明示的に指定したすべての再接続フィールドは SSE と同様に初回接続前に検証されます。

`beforeConnect({ attempt, signal })` は、最初のコンストラクタの前と、再接続のたびに走ります。キャンセルが準備と接続の両方を止めるよう、その signal をトークン更新に渡してください。

## ハートビート

実行時かクライアントスコープでオプトインします。間隔ごとに `message()` を outgoing struct 経由で送ります。任意の `isAck(message)` が ack を認識します — そのメッセージはタイムアウトを消し、`receive` には**届けられません**。

<include cwd>examples/web-socket/heartbeat.ts#example</include>

`intervalMs` と `timeoutMs` は、`2_147_483_647` 以下の正の有限タイマーである必要があります。ハートビートのメッセージは outgoing struct に対して妥当である必要があります。シリアライズ、ネイティブ send、ack の分類、タイムアウトの失敗は論理セッションにとって致命的です — 普通の再接続にはなりません。

## キュー

| 設定                   | 必要な値                               | 振る舞い                                                                                                  |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `maxIncomingQueueSize` | 正の安全な整数                         | `receive` を待つパース済みメッセージと、変換を待つ生フレームを上限する。オーバーフロー → `state: 'error'` |
| `maxOutgoingQueueSize` | 任意の非負の安全な整数。デフォルト `0` | `state === 'reconnecting'` のあいだだけ FIFO。満杯か無効 → `send(...)` が throw                           |

キューされた送信フレームは、置き換えソケットが `open` を公開する前に流されます。前のソケットですでに送ったフレームが自動で再送されることはありません。再接続キューは、再接続中に送るメッセージ用です — アプリ状態の再構成用ではありません。

受信オーバーフローは保留シーケンスを消し、`receive` を失敗させ、セッションを止め、`kind: 'error'` で `session.closed` を解決します。消費者を十分速くするか、測ったサイズ/メモリから上限を上げてください。

## プロトコルと認証

定義の `protocols`、クライアントの `withWebSocketProtocols(...)`、execute の `protocols` が、コンストラクタのサブプロトコルリストを決めます。優先順位は、実行 → クライアント → 定義です。最初に決まったリストは論理セッション用にコピーされ、再接続でも再利用されます。

ブラウザーの WebSocket コンストラクタは任意のハンドシェイクヘッダーを受け付けず、ビルダーも `headers` や `body` を返せません。Defjs は `http:` を `ws:` に、`https:` を `wss:` に変換し、path プレースホルダを一度だけエンコードし、query 規則は HTTP と同じです。デフォルトはスカラーと繰り返すキー、入れ子オブジェクトには `withQuerySerializer`、query が無いときはシリアライザを呼びません。

HTTP と SSE と同様、ベースエンドポイントの欠落、相対 URL、無効な URL、不正な path は、組み立て中に `REQ_BUILD_FAILED` になります。インターセプターがショートサーキットする場合でも、インターセプターやトランスポートの実行前に失敗します。解決後の URL はベースのオリジンを保ち、ディレクトリ内に収まる必要があります。path 内の C0 制御文字（タブ、CR、LF を含む）、バックスラッシュ、`?`、`#`、ディレクトリ外への移動は拒否されます。先頭に空白があっても、スキームらしき形式とプロトコル相対形式は拒否されます。パス内部の普通の空白は許可され、`%20` として送られます。インターセプターの最終的な `req.endpoint` は、最終的な `req.baseEndpoint` に対して同じ規則で検証されますが、ベースを意図的に別の有効な絶対 URL に差し替えることは許可されます。決定的な URL エラーは決してリトライされません。

`withCredentials(true)` は HTTP/SSE の Fetch credentials であり、WebSocket 認証ではありません。レビュー済みの cookie/セッション方針、サブプロトコル、短命の接続チケットを使ってください。一般的な資格情報や長命の秘密を query 文字列に置かないでください。

## 閉鎖と所有権

`session.close(code?, reason?)` は終端クローズを要求し、ハートビートを止めます。code は `1000` か `3000..4999`、reason は UTF-8 で 123 バイト以下です。不正な close 引数は、状態を変える前に throw します。手動の close 理由や論理的な終端結果が要るときは、`await session.closed` と一緒に使ってください。

`execute` に渡した `signal` や `abort` は、open されたセッションに付いたままです。タイムアウト形の abort（`TimeoutError` または `ERR_TIMEOUT`）は `'error'`（`NET_TIMEOUT`）として終わります。それ以外の abort 理由は `'aborted'` として終わり、`receive` はその理由そのもので reject し、新しい `AbortError` にはなりません。`timeout` は起動時の期限にすぎません。

</include>

`session.closed` は論理的な終端スナップショットです。`'closed'`、`'aborted'`、`'error'` と、任意のネイティブ `code` / `reason` / `wasClean`、aborted/error の `cause` です。観測したネイティブ close のフィールドは、所有者が要求したフォールバックより優先されます。

標準の非同期 disposer はベストエフォートでネイティブ close を要求し、それから Defjs が所有するライフサイクル、メッセージポンプ、タイマー、リスナー、キュー、ソケット参照の teardown を待ちます。close イベントが 1 秒以内に観測されなければ teardown は強制され、disposer は `TimeoutError` という名前の `DOMException` で reject することがあります。これは物理 TCP 接続が閉じたことの証明ではありません。disposer を繰り返して呼んでも、同じ teardown を共有します。構造的な独自セッション実装は、今や同じ `[Symbol.asyncDispose](): PromiseLike<void>` 契約を提供する必要があります。

## GraphQL の境界

Defjs が渡すのは、incoming struct 1 つ、outgoing struct 1 つ、論理セッションのライフサイクルです。WebSocket のアプリケーションプロトコルは**実装しません**。GraphQL-over-WebSocket の機能 — connection init、operation ID、`next`/`error`/`complete`、破棄、サブスクリプションの再送 — はコア契約の外です。

サーバーがそのプロトコルを要求するときは `graphql-ws` のようなプロトコルクライアントを使うか、フレームを `defineWebSocket(...)` でモデルしてください。`graphql-transport-ws` のような静的サブプロトコルは `protocols` に置きます。struct だけでは GraphQL の意味論は交渉されません。
