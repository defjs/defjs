# WebSocket セッション

`defineWebSocket` は、SDK における双方向の WebSocket 契約を宣言します。パステンプレート、任意の `input` と `builder`（`path` と `query` のみ）、`incoming` および `outgoing` メッセージの struct、キューの上限、静的なサブプロトコルを指定します。利用側アプリケーションは、ハートビート、再接続、ライフサイクルのクリーンアップをクライアント側で構成します。

## 1. 契約の定義とセッションの実行

`incoming` や `outgoing` で複数のフレーム種別を扱うには、`struct.discriminatedUnion(...)` を使用してモデル化します。返された `WebSocketSession` は、`await using` または明示的な `session.close()` + `await session.closed` で解放します。

## 2. メッセージ検証と方向のルール

- **受信フレーム (`session.receive`)**: テキスト、`ArrayBuffer`、typed array、`Blob` の各フレームは UTF-8 としてデコードされ、JSON としてパースされた後に `incoming` スキーマで検証されます。壊れた JSON やスキーマ不一致は `session.onRuntimeError` に報告され、セッションを切断することなく破棄されます。`session.receive` は単一コンシューマー専用です。2 つ目のイテレーターを取得しようとすると `TypeError` が throw されます。
- **送信フレーム (`session.send(payload)`)**: `outgoing` スキーマに対して同期的に検証され、`.alias()` とコーデックが適用され、`JSON.stringify` でシリアライズされます。`open` 状態では即座に送信され、`reconnecting`（再接続中）状態では `maxOutgoingQueueSize > 0` の場合にキューイングされます。ペイロードが無効な場合、キューが無効または満杯の場合、あるいはセッションがクローズされている場合は、同期的に例外が throw されます。

## 3. セッションの状態とオブザーバー

| メンバー             | 説明                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `state`              | `'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'` |
| `connection`         | 最新の物理ソケットのライブスナップショット（`generation`、`url`、`protocol`、`extensions`）           |
| `bufferedAmount`     | アクティブな物理ソケット上の未送信バイト数（切断時は `0`）                                            |
| `receive`            | 検証済み `incoming` メッセージの単一コンシューマー向け非同期イテラブル                                |
| `onStateChange(fn)`  | 状態遷移を購読。`unsubscribe` 関数を返します                                                          |
| `onRuntimeError(fn)` | 接続確立後のフレームパースエラーなどを購読。`unsubscribe` 関数を返します                              |
| `closed`             | 最終的な結果（`kind: 'closed' \| 'aborted' \| 'error'`）へと解決される Promise                        |

## 4. 再接続、ハートビート、キューの制御

再接続とハートビートは、クライアントオプション（`withWebSocketReconnect`、`withWebSocketHeartbeat`）または呼び出しごとの一時クライアントオプション（`client({ reconnect, heartbeat })`）を通じたオプトイン設定です。

- **再接続**: 有効時のデフォルト値は `attempts: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0` です。物理的な `open` が完了するたびに試行回数の予算がリセットされます。`beforeConnect({ attempt, signal })` は、初回接続および再接続試行の直前に実行されます。
- **ハンドシェイクのタイムアウト (`connectTimeoutMs`)**: 渡したときは、有限の正の数であり、2147483647（タイマー上限）以下でなければなりません。そうでなければ、操作は `REQ_OPTIONS_INVALID` を返します。構築から `open` までを区切り、ハンドシェイクのあとで解除されます。
- **ハートビート**: `outgoing` struct を通じて定期的に `message()` を送信し、最大 `timeoutMs` の間 `isAck(msg)` に一致するフレームの到着を待機します。合致した ACK フレームはハートビートモニターによって消費され、`session.receive` には転送されません。ACK を受信できなければ論理セッションにとって致命的となり、`closed.kind` は `"error"`、`closed.cause` は通常の `Error("WebSocket heartbeat timeout")` になります。再接続は開始しません。ハートビートのシリアライズ失敗も、元の cause を保持して同じ致命的な終了経路をたどります。
- **キューの制限**:
  - `maxIncomingQueueSize`（必須の正の整数）: デコード待ちの生フレームと、コンシューマー待ちのデコード済みメッセージの両方を制限します。オーバーフロー時は `CAP_QUEUE_OVERFLOW` Fault を `closed.cause` としてセッションが終了し、同じ cause が `onRuntimeError` に通知され、`session.receive` を reject します。セッションが開いている間は、`session.receive` から継続的にメッセージを消費してください。
  - `maxOutgoingQueueSize`（任意の非負整数、デフォルトは `0`）: `state === 'reconnecting'` の間のみ `session.send()` の呼び出しをバッファリングし、次の `open` 状態が公開される直前にフラッシュ（送信）します。

`shouldReconnect` はネイティブのクローズコードと `wasClean` を受け取ります。サーバーはアプリケーションエラーコード `1011` でも正常なクローズハンドシェイクを完了できるため、`wasClean === true` はアプリケーションの成功を意味しません。サンプルは `1011` を明示的に許可しています。`!wasClean` だけに頼らず、プロトコルに応じてアプリケーションのコードを選んでください。

## 5. サブプロトコルと認証 [#protocols-and-authentication]

ブラウザの WebSocket API は任意のハンドシェイクヘッダーをサポートしていないため、WebSocket の `builder` 関数は `{ path?, query? }` のみを返します。

- **サブプロトコルの優先順位**: `client({ protocols })` が `withWebSocketProtocols(...)` を上書きし、それが `defineWebSocket({ protocols })` を上書きします。
- **URL の自動変換**: Defjs は、解決されたエンドポイントのスキームを自動的に `http:` → `ws:`、`https:` → `wss:` へと変換します。
- **認証情報**: `withCredentials(true)` は Fetch（HTTP/SSE）のみに適用されます。WebSocket の認証は、Cookie／セッションポリシー、サブプロトコル、または短寿命の接続トークン（チケット）を使用して行います（クエリ文字列に長寿命のシークレットを配置することは避けてください）。
- **`beforeConnect` はリクエストを書き換えるフックではありません**: 入力のパース、同期的な純粋関数である `builder`、インターセプターチェーンは、操作ごとに 1 回だけ実行されます。インターセプターがベースエンドポイントを置き換えていないリクエストでは、各再接続でエンドポイントを選び直し、そのエンドポイントで URL を再構築しますが、構築済みの path/query と取り込んだプロトコル一覧は再利用します。同じエンドポイントでもフェイルオーバー後でも、URL はその試行の `beforeConnect` が実行される前に確定します。フック内でクロージャ変数、input、プロトコル配列を変更しても、現在のハンドシェイクに新しいチケットを渡すことはできません。1 つのセッション内での URL／サブプロトコル認証情報の更新は未対応です。新しい認証情報を先に取得し、新たな操作に input またはクライアント設定として渡して、置き換えたセッションのクリーンアップを管理してください。

## 6. クローズと所有権

`session.close(code?, reason?)`（`code` は `1000` または `3000..4999`、`reason` は 123 バイト以下の UTF-8 文字列）を呼び出して `await session.closed` を待つか、`await using` を使用します。

<include cwd lang="typescript">
  examples/web-socket/closure-and-ownership.ts#example
</include>

1 回の障害に対する再接続の試行回数を使い切ると、セッションは `closed.kind: "error"` で終了し、ネイティブのクローズスナップショット（アップグレード失敗では多くの場合コード `1006`）を保持し、通常のトランスポートエラーを `closed.cause` とします。試行回数の枯渇を表す専用の安定したコードは公開しません。コンポーネントやワーカーの処理が終わったら、`onStateChange` と `onRuntimeError` のリスナーを必ず解除してください。
