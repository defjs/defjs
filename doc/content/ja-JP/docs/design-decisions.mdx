# コアアーキテクチャ

Defjs は、1 つの根本的な境界線に基づいて構築されています。それは、**「SDK は通信契約（wire contract）を定義し、利用側アプリケーションが実行を所有する」** という設計原則です。`@defjs/core` のすべての設計方針は、この分離から導かれています。

## 1. 定義と実行の分離

SDK パッケージは、各操作（`defineRequest`、`defineEventStream`、`defineWebSocket`）とデータ契約（`struct`）を export します。`createClient` を呼び出したり、シングルトンクライアントを保持したり、環境変数を直接読み込んだりすることは決してありません。

`getOrder` はクライアントの状態を一切保持しないため、次のことが可能です。

- ブラウザ UI、バックグラウンドジョブ、SSR リクエストハンドラー、ユニットテストのすべてが、異なる `Client` 構成を用いて同じ `getOrder` 操作を呼び出せます。
- フレームワークプラグイン（`@defjs/react`、`@defjs/vue`）や可観測性ミドルウェアプラグイン（`@defjs/opentelemetry-server`）はアプリケーション側の `Client` にアタッチされるため、公開される SDK パッケージは外部依存ゼロのまま保たれます。

## 2. 明示的な入力配置と双方向エイリアス

Defjs では、`input` が呼び出し元から渡される値を宣言し、`struct` が値のエンコード／デコード方法を制御し、`builder` が各値をリクエストの構成要素（`path`、`query`、`headers`、`body`）へと配置します。

- **推測による暗黙の自動配置を行わない**: 操作で `input` を宣言した場合、同期的で純粋な関数である明示的な `builder` が必須となります。フィールド名から配置場所が自動推測されることはありません。
- **双方向の `.alias(wireName)`**: struct フィールドに `.alias("customer_name")` を指定すると、TypeScript 上では型安全な camelCase の `customerName` を維持したまま、ネットワーク電送上では自動的に `"customer_name"` との間で相互変換されます。

## 3. 宣言はアサーション（保証）である [#declaration-is-an-assertion]

Defjs が HTTP レスポンスを読み取る際には、6 つの厳格なルールが適用されます。

### ルール 1: 宣言したものがそのまま保証となる

`output` は `2xx` レスポンスボディの形状をアサート（保証）します。`error` は `2xx` 以外のボディの形状をアサートします。ここでの宣言はベストエフォートの推測ではなく、実行時の厳格な保証です。

### ルール 2: 分岐は `ok` (`200..299`) のみ

`2xx` レスポンスは `output` のみを用いてデコードされます。それ以外のすべてのステータス（`3xx`、`4xx`、`5xx`）は `error` のみを用いてデコードされます。一方が失敗したからといって、Defjs がもう一方へフォールバックすることはありません。

### ルール 3: アサーションからの逸脱は明確な Fault になる

Defjs は `response.ok` で応答の側を選びます。`2xx` は `output`、非 `2xx` は `error` です。その側に宣言された JSON struct だけがデコードを起こし、`RES_MEDIA_TYPE_INVALID` または `RES_DECODE_FAILED` を生み得ます。その `Content-Type` はボディのバイト列を読む**前**に検証されます。非 `2xx` の HTML ゲートウェイページが `RES_MEDIA_TYPE_INVALID` になるのは、JSON の `error` struct が宣言されているときだけです。有効な側に宣言がなければボディは読まれず、非 `2xx` のレスポンスは未デコードの `HTTP_STATUS` を返します。

| レスポンス読み取り時の失敗要因                              | 返される Fault コード                                                     |
| ----------------------------------------------------------- | ------------------------------------------------------------------------- |
| メディアタイプが宣言された JSON 表現と一致しない            | `RES_MEDIA_TYPE_INVALID`（ボディの読み取りは一切行われません）            |
| バイト列を宣言された表現としてデコードできない              | `RES_DECODE_FAILED`                                                       |
| デコードされた値が `struct` の検証にパスしない              | `RES_STRUCT_MISMATCH`（HTTP） / `RES_DECODE_FAILED`（SSE ハンドシェイク） |
| 非 `2xx` ステータスで `error` struct が正常にデコードされた | `HTTP_STATUS`（型付けされた `error.data` が格納されます）                 |
| 非 `2xx` ステータスで `error` の宣言が省略されていた        | `HTTP_STATUS`（`error.data` は `undefined`）                              |

### ルール 4: デコードに失敗したレスポンスにはボディが存在しない

ボディは、デコードと検証を通過した後にのみ存在します。デコードに失敗した場合、Fault の `response` は `HttpMeta` 型（`body` プロパティを持たない型）となり、パースや検証のエラー詳細は `fault.cause` に格納されます。

### ルール 5: 宣言の省略は読み取りの明示的なスキップを意味する

`output` を省略した場合、`2xx` レスポンスのボディは一切読み取られません。同様に `error` を省略した場合、非 `2xx` レスポンスのボディは一切読み取られません（たとえサーバーが `500` で不正な JSON を返したとしてもエラーにはならず無視されます）。

### ルール 6: `3xx` は成功ステータスではない

`ok` とは厳密に `200 <= status < 300` を意味します。`304 Not Modified` は非 `2xx` です。`error` を未宣言のままにして `HTTP_STATUS` として扱うか（または ETag インターセプターで `304` を処理するか）、空のテキストボディを期待して `struct.string()` を宣言してください。

## 4. トランスポートに応じた結果タプル

3 つのトランスポートはすべて、呼び出し元で例外を throw するのではなく、3 要素のエラーファーストタプルを返します。

- **HTTP** → `[error, data, response]` — デコード済みペイロード + `DecodedResponse<T>`（`output` 省略時は `HttpMeta`）
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + 初回ハンドシェイクのスナップショット
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + 初回接続のスナップショット

クライアントは設定を保持するだけであり、アクティブな接続を抱え込むことはありません。HTTP リクエスト、SSE ストリーム、または WebSocket セッションを開始した呼び出し元が、キャンセルやクローズの責任を負います（HTTP の場合は `AbortSignal`、SSE や WebSocket の場合は `await using` または `.close()` + `await .closed`）。
