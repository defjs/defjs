# 設計上の判断

Defjs は、SDK の設計を扱いやすくするためにあります。`def` は `define` です。チームはサービスの API を記述して再利用できる定義を公開し、利用する各アプリケーションがどう呼ぶかを決めます。残りの設計は、この分離から続きます。

## SDK の作成とアプリケーションの実行

SDK の作成者は、操作、入力契約、リクエストの配置、レスポンスのデコード、宣言されたサービスのエラーを所有します。アプリケーションは、クライアント設定、現在の認証情報、呼び出しのタイミング、結果の扱い、リソースの寿命を所有します。export されたエンドポイントは、SDK に特定のアプリケーション環境を埋め込まずに、異なるクライアントから使えます。

クライアントを渡して操作を呼ぶと、その処理が始まります。定義は、クライアント中立の交換形式ではなく、Struct と builder を持つ実行可能な Defjs モジュールです。SDK の作成者は互換性のある Core 依存を宣言し、JavaScript と TypeScript の型宣言を配布します。[SDK の作成と公開](/ja-JP/recipes/publish-http-sdk) が、パッケージでのこの境界を示します。

任意のファクトリや便利なメソッドは、既定値やドメイン固有の振る舞いを提供できます。エンドポイントを公開したままにしておくと、それらの既定が合わないときにアプリケーションが制御を保てます。フレームワークのプラグインとテレメトリは利用側のクライアントに付くので、定義パッケージは React、Vue、アプリケーションの可観測性の構成から独立したままでいられます。

この分離はテストも現実的にします。クライアントローカルのハンドルを通して実際の SDK 定義を呼び、リクエストとデコード結果を観測します。実行時検証、明示的なエラー、呼び出し側が所有するクリーンアップが、頼れる SDK 契約を支えます。

## 宣言は断言である [#declaration-is-an-assertion]

この六条が、レスポンスの読み方に関するあらゆる問いを決めます。後の議論で導出を繰り返さずに参照できるよう、番号を振ってあります。

### 1. 宣言したものが、あなたの断言

`output` は「`ok` が true のとき、ボディは**この形である**」という意味です。`error` は「`ok` が false のとき、ボディは**この形である**」。宣言はヒントでも、うまくいけばという願望でもなく、何が届くかについての主張です。

### 2. `ok` だけが分岐点で、読むのは常に片側だけ

2xx は `output` で読みます。それ以外はすべて `error` で読みます。両方試すことはなく、もう一方をフォールバックにすることもありません。

### 3. 断言と違う現実は失敗であり、はっきり報告する

フォーマットの推測なし、弱いものへの格下げなし、沈黙なし。バックエンドが変わったのか、ゲートウェイが介入したのか、誰かがレスポンスを改竄したのか——**結論は変わりません**。ライブラリには見分けられませんし、見分けられるふりをするべきでもありません。

これは最も「緩めてほしい」と言われる条なので、はっきり述べておきます。あなたのページが `output` で読もうとしていた `200` を攻撃者が書き換えられるとして、代わりに `3xx`、`4xx`、`5xx` が届いたとします。失敗するのは不便ではなく、唯一安全な帰結です。「念のため」に生のボディを渡すことは、レスポンスを注入できる者に、あなたが要求した検証を回避する道を与えることになります。

### 4. デコードに失敗したなら、ボディは存在しない

ボディ**とは**デコード済みの値です。デコードに失敗したなら値はありません——検査できる半端なボディなど存在しません。問題の詳細は `cause` に載り、レスポンスはメタデータだけを保ちます。

この条は規約ではなく型システムが強制します。デコード fault の `response` は `HttpMeta` で、`body` フィールドがそもそも無いので、触ろうとするとコンパイルエラーになります。

### 5. 断言に縛られたくないなら、宣言しない

`output` を省くのは「2xx のボディには関心がない」という意味で、それは読まれません。`error` を省けば、それ以外についても同じです。これは見落としではなく明示的な opt-out で、しかも徹底しています。opt out した側のボディが読めなかったとして、それはあなたの関心事ではありません。「読めなかった」という事実すら含めて。

### 6. 3xx は成功の範囲ではない

`ok` は 2xx を意味するので、3xx のレスポンス（典型的には `304 Not Modified`）は `error` で読まれ、`output` では決して読まれません。エンドポイントが契約の一部として 3xx の status を返すなら、`error` を宣言せずに `HTTP_STATUS` フォールトを処理するか、空のボディを受け付けるテキストの `error`（`struct.string()`）を宣言してください。JSON の `error` Struct はボディの無いレスポンスを受け付けられません。それは失敗であり、抜けではなく想定どおりの結果です。

## 明示的なクライアント

`createClient(...)` はエンドポイント設定を明示的な値にします。環境やリクエストスコープが違えば、エンドポイント・資格情報・インターセプター・シリアライザ・トランスポートハンドルも違います。

代償は、プロセス全体のデフォルトがないことです。その代償はサーバーで効きます — options やクロージャが認証・cookie・ユーザー・テナント・リクエストメタデータを掴むなら、クライアントをリクエスト境界の中で作ります。明示的なクライアントでも、インターセプターが掴んだ状態は隔離されません。クライアントの同一性そのものがセキュリティ境界ではありません。

クライアントは設定を運びます。進行中の作業は所有しません。HTTP リクエスト・SSE ストリーム・WebSocket セッションを始めた側が、キャンセルまたは close し、終端の promise を await する必要があります。

## 定義と操作

定義は安定した契約です。method、path、入力 struct、`ok` の両側をデコードする struct、トランスポートの上限。`defineRequest` は操作を返します。クライアントを渡して呼ぶとその呼び出しが始まります。同じクライアント値を多くの操作に渡せます。

## トランスポート固有の結果

3 つのトランスポートともエラーファーストのタプルを使います。汎用の単一「レスポンス」だと、ライフサイクルの事実が消えてしまいます。

- HTTP → `[err, data, response]` — デコード済み出力 + それを生んだレスポンス
- SSE → `[err, stream, open]` — 1 つの論理ストリーム + 起動時のレスポンススナップショット
- WebSocket → `[err, session, connection]` — 論理セッション + 起動時の接続スナップショット

成功時、3 番目の値は常にあります。HTTP の失敗は `[error, undefined, undefined]` です。fault がすでにレスポンスのメタデータを抱えており、ハンドラーに渡すもの、ログに出すもの、再 throw するものは、その fault です。SSE と WebSocket の起動失敗では、スナップショットを捕捉できていれば、open または connection がまだ含まれることがあります。

SSE と WebSocket では、3 番目の値はスナップショットであり、将来の再接続が同じ物理接続を保つという保証ではありません。起動後のライフサイクル制御は、返されたハンドルまたはセッションに属します。

## 実行時デコード

TypeScript の推論は期待するものを記述しますが、サーバーレスポンスを実行時に検査はできません。Struct のパースが契約のもう半分です。Defjs はリクエスト組み立ての前に操作の入力を検証し、表現を確かめ、`ok` のどちら側が当てはまるかに応じて struct をパースします。

HTTP では、Struct は**一度だけ、インターセプターチェーンの後で**適用されます。インターセプターが `makeResponse(...)` で作ったレスポンスは、回線から来たものと同じメディアタイプ確認、表現の変換、Struct を通ります。レスポンスがどこから来たかは読み方を変えないので、「インターセプターを信頼する」という別経路を考える必要はありません。組み込みの Fetch トランスポートは、宣言されたボディを JSON、テキスト、`Blob`、バイト列として読んでからチェーンへ返します。JSON のメディアタイプと `JSON.parse` が必要なのは JSON 表現だけで、非 JSON のテキスト、blob、バイト列も、宣言した表現として有効です。インターセプターが見るのはその表現であり、Struct でデコードされた値ではまだありません。読み取り失敗はすべての表現で起こり得ます。そこでの読み取りまたはパースの失敗は、同じ `RES_*` か `NET_BODY_INCOMPLETE` フォールトとして現れます。

順序は、メディアタイプ（JSON の場合）、次に表現、次に struct です。

| 守られなかったもの                       | Fault                                               |
| ---------------------------------------- | --------------------------------------------------- |
| メディアタイプが宣言した表現の要求と違う | `RES_MEDIA_TYPE_INVALID` — ボディを読む**前**に報告 |
| バイト列がその表現ではない               | `RES_DECODE_FAILED`                                 |
| 値がその struct に合わない               | `RES_STRUCT_MISMATCH`（HTTP のみ）                  |
| non-2xx で `error` がデコードできた      | 型付き `data` を伴う `HTTP_STATUS`                  |
| non-2xx で `error` を宣言していない      | `data: undefined` の `HTTP_STATUS`                  |

メディアタイプを先に確かめることが、「JSON を要求して HTML が届いた」をパーサーエラーではなく一つの正確な fault に変えます。しかも読み取り・パース・struct をまとめて省きます。

## ビルダー、エンコーダ、エイリアス

struct は両方向のフィールド契約です。`.alias(name)` がワイヤ名です。struct が値のエンコード方法を決め、`builder` がその値の行き先を決めます。

`builder` は同期的な純粋関数です。受け取るのはパース済みの入力 — 束縛ビューではなく実値 — で、返すのはリクエストの `path`、`query`、`headers`、`body` です。操作が呼ばれたときに走ります。throw するとタプル上の `REQ_BUILD_FAILED` になります。操作を呼ぶこと自体は throw しません。`input` を宣言した定義では、明示的な `builder` が必須です。`input` は引数を定義するだけで、各値をどこに置くかは builder だけが決めます。`builder` を省略できるのは `input` がない定義だけです。

<include cwd lang="typescript">
  examples/design-decisions/builder-encoder-alias.ts#example
</include>

既定の道は、型付きの値をそのまま渡すことです。`body: { orders: input.orders }` は各注文のエイリアスを保つので、ワイヤのフィールドは `customer_name` です。自分で書いたキー（`account_id`、`x-api-version`）はリテラルです。型付きオブジェクトをスプレッドするとその struct が保たれます。論理フィールドの横にワイヤキーを足すと `REQ_BUILD_FAILED` です。

query の入れ子はバックエンドの性質なので、クライアント側に置きます。`withQuerySerializer((query) => string)` はエンコード済みのワイヤオブジェクトを見ます。エイリアスも含まれます。query が無いときは呼ばれません。ビルダーが返した `URLSearchParams` はこれを飛ばします。シリアライザが無ければ、配列はキーを繰り返し、入れ子オブジェクトは失敗します。インターセプターが見る `queryParams` は `new URLSearchParams(queryString)` です。

ボディの種類は値から決まり、最初に一致したものが勝ちます。

- `body` が無い → 何も送らない
- ボディのルートに `urlencoded` または `formData` のコーデックがある → そのフォームエンコード。値が JSON の中にネストしているときは、このタグは適用されません
- `FormData`、`URLSearchParams`、`Blob`、`File`、バイト列、`ReadableStream` → そのまま送る
- 文字列 → `text/plain;charset=UTF-8`
- プレーンオブジェクト、配列、数値、真偽値、`null`、`Date`、`bigint` → JSON。`JSON.stringify` が省略または平坦化する値（`Map`、`Set`、`toJSON` のないクラスインスタンス、関数、`NaN`、Node のストリーム）→ `REQ_BUILD_FAILED`

`undefined` のフィールドは省略されます。nullable なフィールドの `null` は送られます。文字列は、自分で文字列化して `content-type` を立てない限り JSON ではありません。自分でシリアライズする（`JSON.stringify`、qs、protobuf）と struct エンコーダから外れるので、エイリアスは適用されません。公開された `struct.encode` はありません。

`GET` と `HEAD` はボディを運べません。WebSocket のビルダーは headers も body も返せません。静的な WebSocket サブプロトコルはビルダーではなく定義の `protocols` に置きます。不正な WebSocket フレームはセッションのランタイムエラーリスナーへ行きます。SSE の `error` struct は起動時の fault に型を付け、ハンドシェイクのボディは HTTP ボディと同じ kind 規則に従います。`string` はテキスト、blob と file は blob、`arrayBuffer` はバイト列、それ以外は JSON です。表現の選択は共通ですが、フォールトへの対応付けは異なります。SSE のハンドシェイクで読み取り、パース、Struct が失敗すると `RES_DECODE_FAILED` になり、Struct の失敗では `cause` に `StructError` が入ります。HTTP は Struct の失敗を `RES_STRUCT_MISMATCH` として報告します。

## オブザーバーと方針の置き場所

インターセプターはトランスポート全体の方針向けです。認証、トレーシング、ショートサーキット、レビュー済みリトライ。自分のトランスポートだけ動き、オニオン順で合成されます。派生したクライアントのリクエスト options は、作業固有の寿命向けです。`signal`、WebSocket のハートビート、オプトインの再接続です。

オブザーバーは、起きたことを報告するだけで、第二の所有者にはなりません。SSE の `onInvalidEvent`、WebSocket の状態リスナー、ランタイムエラーリスナーは、範囲を限定した診断とメトリクス向けです。返されたストリーム/セッションが、反復・close・購読解除・終端待ちを所有したままです。キャッシュ、古い結果の抑制、冪等性、ドメインエラーの写像は、操作の呼び出しの周りに置き、アプリ自身の方針と状態が見える場所にしてください。

## OpenAPI、ソースマップ、テレメトリ

Defjs は第二の OpenAPI 契約を生成したり同期したりしません。OpenAPI がすでに権威なら、それを保ち、アプリ境界で実行時検証を足します。新しいサービスなら、エンドポイント定義と Struct を直接のワイヤ契約にしてよいです — 第二の単一情報源は不要です。

`withOpenTelemetryServer(...)` はクライアントに **アウトバウンド** の Defjs 計測を足します。OpenTelemetry SDK の初期化はしません。`tracer`・`meter`・`logger` はいずれも任意（`tracer` を省くとローカルのスパンとスパンフックは無効になります）、3 トランスポートはデフォルト有効、WebSocket の query 伝播はデフォルト無効です。operation 名は静的で低カーディナリティに保ってください。伝播・フック・URL・ヘッダー・ペイロード・cause・保持期間は、機微になり得るものとして見直してください。

ソースマップはデプロイの判断であり、Defjs の振る舞いではありません。`sourcesContent` 付きの公開マップはソースを晒します。隠したマップでもソースとパスは入ります。マップを無効にするとソースレベルでのシンボル化は失われます。非公開マップは、明示的なアクセスと保持ルール付きの、デプロイ可能なデバッグ成果物として扱ってください。
