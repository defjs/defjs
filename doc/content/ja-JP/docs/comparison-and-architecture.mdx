# 比較とハイブリッドアーキテクチャ

Defjs は、**ブラウザ／Node 向け HTTP クライアント**（`fetch`、`ky`、`ofetch`、`axios`、`openapi-fetch`）と **契約ファーストの RPC フレームワーク**（`oRPC`、tRPC）という 2 つのエコシステムの交差点に位置しています。このガイドでは、各ツールの適した用途、Defjs が過剰なオーバーヘッドになる場面、そして本番環境でチームがこれらをどう組み合わせているかを整理します。

## エコシステム比較

| 機能・特性                               | 生の `fetch`                           | `ky` / `ofetch`                           | `openapi-fetch`                            | `oRPC`                                          | Defjs (`@defjs/core`)                                                              |
| ---------------------------------------- | -------------------------------------- | ----------------------------------------- | ------------------------------------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------- |
| 主な設計思想                             | プラットフォームプリミティブ           | アプリ向け HTTP ラッパー                  | 型付き OpenAPI Fetch クライアント          | フルスタック TS RPC フレームワーク              | SDK 定義 + 高レジリエンスクライアントキット                                        |
| 定義とクライアントの分離                 | 手動                                   | ベース URL ごとにインスタンスを結合       | パス型は共有、クライアントが呼び出しを所有 | ルーターとクライアントが RPC 契約で結合         | 第一級（`define*` データ vs `Client`）                                             |
| 統合されたトランスポート                 | HTTP のみ                              | HTTP のみ                                 | HTTP のみ                                  | HTTP + SSE/イベントイテレータ（サーバー側所有） | 単一クライアントで HTTP、SSE、WebSocket を統一                                     |
| 実行時ワイヤ契約とエイリアス             | なし                                   | なし                                      | 任意のミドルウェア                         | 外部バリデーター（Zod/Valibot/ArkType）         | 依存関係ゼロの `struct` と双方向 `.alias()`                                        |
| 失敗セマンティクス                       | ネットワークエラーで reject、`!res.ok` | `HTTPError` を throw                      | `{ data, error }`（throw または reject）   | セーフ／スロー可能な RPC エラー                 | 例外を投げない `[err, value, meta]` Go スタイルタプル                              |
| マルチアップストリームロードバランシング | なし                                   | なし                                      | なし                                       | Link プラグイン（組み込み P2C EWMA なし）       | 組み込み `p2cBalancer` + `outlierDetection`（`halfOpen`, `maxEjectionPercent`）    |
| `429` + `Retry-After` + 相関 ID          | 手動                                   | `ky` は `Retry-After` 対応、単一 URL のみ | 組み込みなし                               | クライアントリトライプラグイン                  | ネイティブ `429`/RFC `Retry-After`、リトライバジェット、`correlationId`            |
| 構造化並行処理                           | 生の `Promise.all`                     | 生の `Promise.all`                        | 生の `Promise.all`                         | バッチプラグイン / `Promise.all`                | クライアントおよびキャンセルに紐付く `@defjs/core/concurrent`                      |
| OpenAPI コード生成                       | なし                                   | なし                                      | `openapi-typescript` による型生成のみ      | oRPC ルーターからの OpenAPI 仕様出力            | `@defjs/cli` によるステートレス ESM + `struct` 生成                                |
| 境界を越えるプロキシ                     | 手動 `postMessage`                     | 手動                                      | 手動                                       | MessagePort / ワーカーアダプター                | `@defjs/core/port` + `/webext`（HTTP, SSE, WS + デフォルト拒否のオリジンポリシー） |

### 代替手段を選ぶべきケース

- **生の `fetch`、`ofetch`、または `ky` を選ぶケース**: アプリが少数の同一オリジンエンドポイントを呼び出すだけで、SDK の公開も、マルチアップストリームのフェイルオーバーも、実行時スキーマ検証も不要な場合（~4–10 KB brotli）。
- **`openapi-fetch` を選ぶケース**: すでに `openapi-typescript` の型定義を運用しており、実行時のワイヤデコードは不要で、最小限の Fetch ラッパーにコンパイル時の型付けだけを載せたい場合。
- **`oRPC`（または Hono RPC）を選ぶケース**: チームが TypeScript サーバーとブラウザクライアントの両方を所有し、独立した HTTP 契約を維持せずにエンドツーエンドのプロシージャ型推論を得たい **ファーストパーティのフロントエンド ↔ BFF / フルスタック RPC**。

## ハイブリッド BFF ブループリント: エッジに oRPC / Hono、下流に Defjs

大規模な本番構成では、Defjs と `oRPC` / `Hono` を競合させるのではなく、信頼境界（trust boundary）の両側で組み合わせるのが最も一般的なパターンです。

```txt
┌──────────────┐   First-party RPC (oRPC / Hono)   ┌─────────────────────────────────┐
│ Browser /    │ ────────────────────────────────▶ │ BFF (Hono / oRPC Server)        │
│ Mobile App   │ ◀──────────────────────────────── │                                 │
└──────────────┘                                   │  @defjs/core Client:            │
                                                   │  • undici.Pool handle           │
                                                   │  • p2cBalancer({                │
                                                   │      outlierDetection: {        │
                                                   │        halfOpen: true           │
                                                   │      }                          │
                                                   │    })                           │
                                                   │  • withRetry (429 / 503)        │
                                                   │  • bulkhead + idempotency       │
                                                   │  • @defjs/opentelemetry-server  │
                                                   └────────────────┬────────────────┘
                                                                    │
                                        Downstream REST / SSE / WS  │
                               ┌────────────────────────────────────┴────────┐
                               ▼                                             ▼
                    Third-party SaaS APIs                        Internal Microservices
                    (generated via @defjs/cli)                   (Nodes A, B, C failover)
```

この役割分担は次のようになります。

1. **ブラウザ ↔ BFF**: ファーストパーティ RPC の迅速な開発のため、`oRPC` または `Hono` を使用します。
2. **BFF ↔ 下流 API**: `@defjs/core`（多くの場合、ベンダーの OpenAPI 仕様から `@defjs/cli` で操作定義を生成し、[`undici.Pool`](/ja-JP/recipes/undici-pool) でコネクションプールを共有）を使用します。これにより、1 台の低速な下流インスタンス（`B`）やレート制限（`429` / `503`）を受けたインスタンス（`C`）があっても、BFF ワーカーの処理能力を枯渇させる前に `p2cBalancer` + `outlierDetection` で即座に隔離できます。

## 再現可能なベンチマーク結果

以下の数値はすべて、[`bench/`](https://github.com/defjs/defjs/blob/main/bench/REPORT.md) に含まれる独立したロックファイル固定のベンチマークスイート（`bun run build && cd bench && bun install --frozen-lockfile && bun run all`、Apple M1 Max、Bun `1.4.5`、Node `v26.13.1`、決定論的シード `SEED=20261124`）から計測されたものです。

| 評価軸                           | シナリオ                                                                                                                                              | 主な結果                                                                                                                                                                                                                                                        | 計測手法・公平性に関する注記                                                                                                                                                                                                         |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| マルチアップストリームの耐障害性 | 正常ノード `A`（5 ms）、ロングテールノード `B`（40% 300 ms）、不安定ノード `C`（40% `503`, 40% `429` + `Retry-After: 1`）へ並列度 8 で 200 回呼び出し | `@defjs/core`（`p2c` + `outlierDetection` + `withRetry`）：**100.0% 成功率**、**1.03x** 通信増幅率、**11.01 ms p95**（`A:195 / B:3 / C:9`）対 `ky`：**81.5%**、**1.49x**、**1626.30 ms p95**（`A:67 / B:67 / C:163`）、生 `fetch`：**71.0%**、**302.18 ms p95** | 各クライアント実行前に PRNG 状態とアップストリームカウンターを同一に初期化しています。`@defjs/core` は `struct` によるレスポンス検証も実行しています。                                                                               |
| ESM ブラウザバンドルサイズ       | `esbuild` minify + tree-shake（brotli-11 / gzip-9）                                                                                                   | 最小構成 `@defjs/core`（`defineRequest` + `struct`）：**16.69 KB br / 18.75 KB gzip**、フル構成（`p2c` + `outlierDetection` + `withRetry` + ミドルウェア）：**17.78 KB br / 20.00 KB gzip**                                                                     | `ofetch`（**3.62 KB br**）と `ky`（**9.66 KB br**）はスキーマデコードを含みません。`openapi-fetch + zod`（**76.79 KB br**）と `@orpc/client + zod`（**81.51 KB br**）は Zod をバンドルします。                                       |
| HTTP keep-alive オーバーヘッド   | ローカルループバック Hono サーバー、5,000 リクエスト（並列度 16 / 逐次）                                                                              | `@defjs/core`（`fetch` + `struct`）：並列度 16 で **23,481 req/s**（`0.57 ms` p50）、逐次で **9,926 req/s**（`0.09 ms` p50）                                                                                                                                    | 両方の `@defjs/core` バリアントは全レスポンスで完全な `struct` 出力検証を実行しています。並列度 16 において、`ky`（**21,310 req/s**）、`ofetch`（**28,921 req/s**）、`openapi-fetch`（**34,393 req/s**）は未検証の JSON を返します。 |
| スキーマ早期失敗デコード         | インデックス `0` が不正な 1,000 要素配列（`mitata`）                                                                                                  | `@defjs/core`：**506.5 ns**（`1,974,438 ops/s`）対 `zod`：**51.25 us**、`valibot`：**70.82 us**、`arktype`：**334.86 us**                                                                                                                                       | `@defjs/core` は最初の構造違反で即座に中断します。正常な入力（`flat-6-fields`、`array-1000-items`）では、ArkType JIT、Zod v4、Valibot の方が高速に実行されます。                                                                     |
