## インターセプターごとに 1 つの責務 [#one-concern]

各インターセプターには 1 つの仕事だけを与えます。認証の付与、トレースヘッダーの追加、時間の記録、承認済みケースのショートサーキットです。認証し、ボディを書き換え、リトライし、ログも出すミドルウェアは、テストしにくく、推論しにくくなります。

推奨:

```ts
const auth = createHttpInterceptor(async (request, next) => {
  const response = await next(request);
  return response;
});
```

無関係なリクエストの複数箇所を変える単一のインターセプターは避けてください。

## 順序は方針 [#order]

インターセプターは登録順に実行されます。最初に登録したインターセプターが最も外側で、リクエストを最初に見て、レスポンスを最後に見ます。試行全体を包む必要のある方針は最も外側に、トランスポートに最も近い必要のある方針は最も内側に置きます。

```ts
const client = createClient(
  withEndpoint("https://api.example.com"),
  withInterceptors(trace, auth),
);
```

`trace` が `auth` を包み、`auth` はトランスポートの前に実行されます。

## 意図してショートサーキットする [#short-circuit]

インターセプターは `next` を呼ばずに、`makeResponse` でレスポンスを返せます。承認済みのキャッシュ、メンテナンス用のレスポンス、ローカルテストに使います。レスポンスはそれでも操作の宣言済み出力を満たす必要があり、失敗を成功に変えてはいけません。

## 契約を書き換えない [#contract]

ミドルウェアは、ライブラリの検証規則の範囲内でヘッダー、トレースコンテキスト、リクエスト URL を調整できます。宣言済みの入力や出力の意味を変えてはいけません。認証とトレーシングはここに属し、`builder` には属しません。

## ステートレスに保つ [#stateless]

リクエストごとのデータを共有クライアントやモジュールに保存しないでください。値はリクエスト、クライアント設定、またはそのクライアント用に作ったクロージャを通して渡します。共有状態を変更するミドルウェアは、同時呼び出しの間で漏れます。

## 境界で失敗を処理する [#failures]

ミドルウェアの throw は失敗です。レスポンスを返すのは、ミドルウェアが意図的にリクエストを処理したときだけです。フォールトをログに出すためだけに catch して `undefined` で続行してはいけません。ログにはアプリケーションのテレメトリーフックかインターセプターを使い、定義はどちらも持たないようにします。
