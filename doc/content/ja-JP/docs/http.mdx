## URL を解決する

`withEndpoint(...)` には有効な絶対 URL が要ります。エンドポイントの pathname はディレクトリとして残り、query と hash はコマンド解決の前に捨てられます。ベースエンドポイントの欠落、相対 URL、無効な URL は、インターセプターやトランスポートが実行される前のリクエスト組み立て中に `REQ_BUILD_FAILED` になります。インターセプターがリクエストをショートサーキットする場合でも同じです。HTTP、SSE、WebSocket で共通の規則です。

<include cwd>examples/http/resolve-url.ts#example</include>

path のプレースホルダは生のスカラーで、ちょうど一度だけエンコードされます。空の値と `.` / `..` は拒否されます。1 つのプレースホルダの中のスラッシュ、`?`、`#`、`%`、空白、Unicode は、エンコードされた 1 セグメントのままです — 事前エンコードしないでください。

プレースホルダ名は `:` から始まり、次の `/` または path の末尾まで続きます。`/files/:name.json` のパラメータ名は `name.json` で、`name` ではありません。静的セグメント内のリテラルのコロンには対応していません。

定義の path は、先頭に空白がある場合も含め、スキームらしき形式やプロトコル相対にはできず、C0 制御文字（タブ、CR、LF を含む）、バックスラッシュ、`?`、`#` も含められません。パス内部の普通の空白は許可され、`%20` として送られます。解決後の URL はベースのオリジンを保ち、そのディレクトリ内に収まる必要があります。`../users` のような path で外へ出ることはできません。不正な path はトランスポートの前、組み立て中に `REQ_BUILD_FAILED` で失敗します。インターセプターの最終的な `req.endpoint` は、最終的な `req.baseEndpoint` に対して同じ規則で検証されます。インターセプターが意図的に別の有効な絶対 URL をベースにすることは許可されます。決定的な URL エラーは決してリトライされません。

デフォルトの query エンコーダはスカラーとスカラーの配列を受け付けます（配列はキーを繰り返します）。入れ子オブジェクトは、クライアントに `withQuerySerializer(...)` が無ければ `REQ_BUILD_FAILED` で失敗します。`path`、`query`、`headers` の `null` も同じように失敗します。`undefined` は省略されます。

## 入力を配置する

struct が値をエンコードします。ビルダーがそれを配置します。`input` を宣言した定義では、入力がすでにリクエストの形でも、明示的な `builder` が必須です。`builder` を省略できるのは `input` がない定義だけです。

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

そのボディは `application/json` の `{"display_name":"Ada"}` です。ヘッダーのワイヤ名は `x-request-id` です。呼び出し側とパース結果は `displayName` のままです。

ワイヤキーを自分で書くより、型付きの値を渡す方を選んでください。エイリアスはフィールドに一度宣言すれば両方向に効きます。`output` / `error` / イベント / 受信フレームは `display_name` を `displayName` にデコードし、`body: input.order` は木全体を書き換えます。同じ `User` struct を作成ボディにも取得の output にも使えます。手書きのキーは例外です。親オブジェクトが匿名なので、エイリアスは走りません。

| ビルダー式                                      | ワイヤ上                                                        |
| ----------------------------------------------- | --------------------------------------------------------------- |
| `body: input.profile`                           | 型付きオブジェクト。エイリアスと `Date` / `bigint` のエンコード |
| `body: { profile: input.profile }`              | 外側のキーはリテラル。内側のオブジェクトは型付きのまま          |
| `body: { ...input.profile, role: 'admin' }`     | スプレッドは struct を保つ。追加キーはリテラル                  |
| `body: { name: input.profile.displayName }`     | 匿名の親。エイリアスは適用されない                              |
| `query: input.query` / `headers: input.headers` | 型付きのフラットなオブジェクト。エイリアスがワイヤキーになる    |

型付きオブジェクトをスプレッドしつつ、そのワイヤキーも置く（`displayName` の隣に `display_name`）と `REQ_BUILD_FAILED` です。`path` や `headers` の入れ子オブジェクトも同じように失敗します。

ガイドはルートだけでなく、各ノードで決まります。匿名の親の下に新しく書いたオブジェクトは、書いたキーのままです。型付きの親の下では、同じオブジェクトがそのフィールドの struct を使います。

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

union のガイドが複数の分岐に一致したら、分岐ごとにエンコードして比較します。ワイヤ結果が同じならそれを採用し、違えば `REQ_BUILD_FAILED` です。

非 object 部分を含む混合 intersection は、解析時に一致した各部分のタグの連言をタグとして付け、解析せず新しく書いた値は匿名オブジェクトとして扱います。

### Query

入れ子の query 形（`a[b]`、`a.b`、カンマ区切り）はバックエンドの規約なので、フックはクライアントにあります。

<include cwd>examples/http/query-serializer.ts#example</include>

ここでの `query` はエンコード済みのワイヤオブジェクトです。エイリアスはすでに適用されているので、`qs` のようなシリアライザがそれらを落としません。戻り値の文字列が query 文字列です。Defjs は `qs` に依存しません。

シリアライザが無ければ、配列はキーを繰り返し、入れ子オブジェクトは `REQ_BUILD_FAILED` です。ビルダーが `URLSearchParams` を返すと、その値がそのまま使われ、シリアライザは飛ばされます。query が無いときシリアライザは呼ばれません。そのあとインターセプターが見る `queryParams` は `new URLSearchParams(queryString)` です。

### Body

最初に一致したものが勝ちます。

| `body` の値                                                                | 送られるもの                                                         | デフォルトの content type                              |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------ |
| 省略 / `undefined`                                                         | ボディなし                                                           | —                                                      |
| ルートに `urlencoded` または `formData` コーデックがある型付きオブジェクト | `URLSearchParams` / `FormData`。キーはワイヤ名。配列はキーを繰り返す | フォームの型 / プラットフォームの boundary             |
| `FormData`、`URLSearchParams`                                              | そのまま                                                             | 同じ。Defjs は `FormData` の古い `Content-Type` を消す |
| `Blob` / `File`                                                            | そのまま                                                             | `blob.type`、または `application/octet-stream`         |
| `ArrayBuffer`、`TypedArray`、`DataView`                                    | そのまま                                                             | `application/octet-stream`                             |
| `ReadableStream`                                                           | ストリーム（ランタイムが許すとき `duplex: 'half'`）                  | `application/octet-stream`                             |
| `string`                                                                   | そのまま                                                             | `text/plain;charset=UTF-8`                             |
| プレーンオブジェクト、配列、数値、真偽値、`null`、`Date`、`bigint`         | エンコードしてから `JSON.stringify`                                  | `application/json`                                     |

HTTP は、ビルダーのボディから推論した型をプレーンなフィールド `request.bodyContentType` に保持し、`{ ...req }` のコピー後も残します。その推論を `request.headers` に書き込むことはありません。明示的な `content-type` ヘッダーは、ビルダー、クライアントのデフォルト、インターセプター、生の `fetchHandler` リクエストのどれが設定しても常に優先され、アップロード進捗のためにボディがストリームへ変換される場合も同じです。`bodyContentType` が効くのは `body` がビルダーの値のままのあいだだけです。差し替えたボディは再検出されるので、インターセプターはその型を `content-type` ヘッダーで宣言します。`body: undefined` では、ライブラリが推論した Content-Type は送られません。FormData は例外で、content type には実際のシリアライズで使われた boundary が必要です。コーデックのタグが効くのはボディのルートだけです。`body: { meta: input.form }` は JSON になり、フォームのフィールドは普通の JSON フィールドです。文字列は生テキストです。`"abc"` のような JSON 文字列には `JSON.stringify` と `application/json` が要ります。`undefined` のフィールドは省略されます。`nullable` なフィールドを `null` で送ると JSON の `null` になります。

JSON は、ネストした値も含めて、すべて JSON データでなければなりません。プレーンオブジェクト、配列、文字列、有限の数値、真偽値、`null`、そして `toJSON()` がそれらを返す値、たとえば `Date` や `URL` です。それ以外の値は、ルートにあってもネストされていても、何も送られる前に `REQ_BUILD_FAILED` で失敗します。`{}` や `null` として送られたり、ボディなしになったりすることはありません。該当するのは、`Map` や `Set`、`toJSON` のないクラスインスタンス、関数、`NaN`、Node の `Readable`、イテラブルまたは非同期イテラブル（`Symbol.iterator` または `Symbol.asyncIterator` メソッドを持つオブジェクトリテラルを含む）などです。エラーメッセージには該当するフィールド名が含まれます。`query` または `headers` として渡したイテラブルオブジェクトは、捨てられずに同じように失敗します。ヘッダーのペアは配列として渡してください。ストリームは Web の `ReadableStream` として送ってください。`ReadableStream.from(iterable)` または `Readable.toWeb(readable)` を使います。`body` 型はこれらの大半をコンパイル時に拒否します。`interface` の値やクラスインスタンスには `{ ...value }` が必要です。

`GET` と `HEAD` はボディを返せません — それは型エラーです。WebSocket のビルダーは `headers` も `body` も返せません。

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

自分で走らせる `JSON.stringify`、`qs`、protobuf が見るのは論理名です。その経路ではエイリアスは適用されません。公開された `struct.encode` はありません。

ビルダーは実入力で分岐し、場合ごとに違うボディ（JSON のレコード、`File`、`URLSearchParams`）を返せます。ネイティブの `Headers` もそのまま渡され、再エンコードされません。

## ボディの読み方

`output` は 2xx ボディ用の struct 1 つ、`error` はそれ以外すべて用の struct 1 つです。表現を選ぶのは struct の kind です。`string` は生テキスト、`blob` / `file` は blob、`arrayBuffer` はバイト列、それ以外の kind は JSON です。どちらも宣言しなければ、ボディは読まれません。

処理の順序は次のとおりです。

1. `ok` が側を選びます。2xx は `output`、それ以外は `error`。両方読むことはありません。
2. その側に何も宣言が無い → ボディは読まれません。2xx は `data === undefined` で成功します。non-2xx は `data === undefined` の `HTTP_STATUS` です。宣言していない側の読めないボディは、読めなかったという事実も含めて無視されます。
3. メディアタイプはボディを読む**前**に確認されます。不一致は `RES_MEDIA_TYPE_INVALID` で、パースもデコードもされません。
4. 表現を読みます。失敗は `RES_DECODE_FAILED` です。トランスポートからの JSON は一度だけパースされます。その値の文字列は JSON の文字列ルートであり、もう一度パースされません。バイトと blob は生のままで、一度だけパースされます。
5. Struct が値をパースします。失敗は `RES_STRUCT_MISMATCH` です。
6. 2xx → 結果と型付きの `response.body`。non-2xx → `HTTP_STATUS` 上の型付き `data`。

組み込みの Fetch トランスポートは、宣言された側については手順 3 と 4 を、レスポンスがまだインターセプターチェーンの中にあるうちに行います。そのためインターセプターが受け取るレスポンスの `body` は、すでにパース済みの JSON、テキスト、`Blob`、バイトです。これらの手順での失敗は、同じ `RES_*` フォールト、またはボディストリームが壊れたときは `NET_BODY_INCOMPLETE` として現れます。手順 5 はチェーンの後で一度だけ実行されます。したがってインターセプターが `makeResponse(...)` で作ったレスポンスも、回線から来たものと同じメディアタイプ確認、表現の変換、Struct を通ります。JSON 表現では、文字列の body は JSON の文字列ルートです。

成功したレスポンスは `DecodedResponse<T>` です。`url`、`status`、`statusText`、`headers`、`ok`、型付きの `body` を持ちます。何もデコードされなかった場所では `HttpMeta` になります — 同じフィールドから `body` を除いたものです。`ok` は `200 <= status < 300` だけを意味します。どちらもネイティブの `Response` ではありません。トランスポート失敗は fault なので、その代わりを務める status 0 のレスポンスはありません。

## 作業をキャンセルする

実行 options は `signal` に加えて `abort` か `timeout` のどちらかを取ります。**`abort` と `timeout` は同時に使えません。** `signal` はどちらとも組み合わせられます。

<include cwd>examples/http/cancel.ts#example</include>

`timeout` は `1..2_147_483_647` の正の安全な整数である必要があります。`timeout` を省いた呼び出しには、クライアントの `withTimeout` のデフォルトが適用されます。認識されたキャンセル → `NET_ABORTED`。実行タイムアウト → `NET_TIMEOUT`。インターセプターの `throw` → `EXT_INTERCEPTOR_FAILED`（ただし `ERR_ABORTED` / `ERR_TIMEOUT` は `NET_ABORTED` / `NET_TIMEOUT` になります）。その他の Fetch 失敗 → `NET_UNREACHABLE`。サーバーが書き込みを受け入れたあとのキャンセルは、書き込みがロールバックしたことの**証明にはなりません**。

## 資格情報と XSRF

`withCredentials(true)` は HTTP と SSE の Fetch に `credentials: 'include'` を設定します。`Authorization` は作らず、WebSocket 認証も設定しません。`false` は credentials を未指定のままにします。

`withXSRF(...)` は HTTP 専用です。デフォルトは `cookieName: 'XSRF-TOKEN'`、`headerName: 'X-XSRF-TOKEN'` です。ヘッダーを注入するのは非安全メソッドだけで、呼び出し側がすでに設定していないときだけです。Worker を含め、`location` が存在する場合は、解決済みリクエスト URL のオリジンが `location.origin` と一致しなければなりません。クロスオリジンのリクエストでは `tokenProvider` は呼ばれません。cookie の参照には、別途 `document` が必要です。`GET`、`HEAD`、`OPTIONS`、`TRACE` は飛ばします。Worker やサーバーで注入が要るなら、同期的でリクエストスコープの `tokenProvider` を渡してください。

資格情報、XSRF トークン、query 文字列は日常のログに出さないでください。query パラメータを一般的な資格情報の通り道にしないでください。

## 進捗と Fetch 境界

`onDownloadProgress` は、宣言されたレスポンスボディを読んでいるあいだ動きます。`loaded` はレスポンスストリームから読んだバイト数を数え、そのストリームは Fetch がすでに展開済みの場合があります。`lengthComputable` が true になるのは、正の `Content-Length` があり、`Content-Encoding` が無いか `identity` のときだけです。gzip や br を含むその他のエンコードでは `total: 0`、`lengthComputable: false` と報告するので、展開済みバイト数を圧縮されたワイヤ上の長さと比較することはありません。その側に struct が無い → ボディは読まれない → ボディ読み取りの進捗もありません。

`onUploadProgress` は、Fetch が `ReadableStream<Uint8Array>` のボディを読む際の進捗を報告し、サーバーが受領を確認した時点の進捗ではありません。アップロードの進捗が報告されるのは、リクエストボディのストリーミングに対応するランタイムに限られます。Bun、Node、Deno では、Defjs は `Blob` / `File`、`ArrayBuffer`、`FormData` のボディもストリームに変換するので、それらも進捗を報告します。サーバーランタイムでは、`onUploadProgress` 付きの FormData はシリアライズされたストリームを直接使い、multipart boundary を保ち、ライブラリが生成した `Content-Length` なしで送られます（HTTP/1.1 では chunked）。そのため、ボディ全体をバッファせずに進捗、タイムアウト、中止が働きます。有効な明示的 `Content-Length` が無ければ、全体の長さは不明です。一部の事前署名アップロード先のように `Content-Length` を要求するエンドポイントでは、`onUploadProgress` を省いてください。その場合、プラットフォームの Fetch が FormData を長さ付きで送ります。キャンセルするとラップされたストリームを解放します。Chromium はリクエストボディを HTTP/2 以降でしかストリームせず、Firefox はまったくストリームできないため、Worker を含むブラウザーは除外されます。ブラウザーではそれらのボディはそのまま送られ、`onUploadProgress` は呼び出されません。JSON、テキスト、`URLSearchParams`、型付き配列のボディはまとめて送られ、イベントは出ません。長さが分からないストリームでは `total` は `0`（つまり `lengthComputable` は `false`）です。ストリームのリクエストを送れないランタイム（Firefox など）での `ReadableStream` ボディは、何も送られる前に `ENV_UNSUPPORTED` で失敗し、cause のメッセージは `ERR_STREAMING_REQUEST_UNSUPPORTED` です。Chromium では `ReadableStream` ボディに HTTP/2 以降が必要で、HTTP/1.1 では呼び出しが `NET_UNREACHABLE` で失敗します。`onDownloadProgress` はどのランタイムでも同じように振る舞います。

進捗コールバックが例外を投げるか、返したプロミスが拒否されると、ダウンロードでもアップロードでも、投げられた値を `cause` として呼び出しが `EXT_OBSERVER_FAILED` で失敗します。呼び出し側のキャンセルと `timeout` は引き続き `NET_ABORTED` / `NET_TIMEOUT` を報告します。

`fetchHandler(httpRequest, fetchImpl?)` はより低レベルの Fetch 境界です。URL を解決し、Fetch を呼び、表現を読み、`HttpResponse` を返します。デフォルトの HTTP と SSE のハンドルは呼び出しごとに `globalThis.fetch` を解決するので、import 後に差し替えた Fetch も使われます。HTTP が `(url, init)` を使うのは、変更されていないプラットフォームの Fetch だけです。差し替えたグローバル Fetch やカスタムハンドルにはネイティブの `Request` が渡されます。Fetch が無くても Core の import は可能です。Fetch が無いままデフォルトの HTTP/SSE を実行すると `ENV_UNSUPPORTED` で失敗しますが、カスタムハンドルは使えます。この境界はコマンド入力の検証も、`output` の振り分けも、インターセプターの実行も**しません**。注入したトランスポートのテストには便利ですが、`client.execute` の代わりにはなりません。

## 再送の限界

Defjs は HTTP を**自動リトライしません**。読み取りのリトライにも、レビュー済みのタイムアウト/ネットワーク/重複方針が要ります。ミューテーションのリトライには、再送可能なバイト、サーバー側の対応、認証スコープとリクエストバイトに束縛された冪等キー、受信側の重複方針が要ります。

クライアント/コマンド/Fetch 境界には、失敗した書き込みがコミットしたかどうかは分かりません。再送の判断はアプリか、レビュー済みインターセプターに置いてください。インターセプターは低レベルリクエストをショートサーキットしたり差し替えたりできます。最終的な status とボディは、それでもコマンドの契約を満たす必要があります。
