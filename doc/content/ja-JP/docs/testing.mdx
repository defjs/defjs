# テスト

`@defjs/core` はライブラリ自身のトランスポート層やコーデックをすでにテストしています。アプリケーションや SDK パッケージで Defjs を使うときに書くべきテストは、**あなた自身がプロジェクト内で書いたコード**——`src/api/request/` と `src/api/schema/` の操作定義とスキーマ、`src/api/client.ts` のカスタムインターセプター、`src/checkout.ts` の業務ヘルパー、そして React / Vue コンポーネントの振る舞いです。

## プロジェクトの何をテストすべきか（`vi.mock` を使わない理由）

エクスポートした `defineRequest`、`defineEventStream`、`defineWebSocket` 関数をスタブ化したり `vi.mock(...)` で差し替えたり**しないでください**。操作をモックすると、`builder` のパラメータ配置、`.alias()` の変換、カスタムインターセプター、ステータス振り分け、`struct` デコードが丸ごとスキップされてしまいます。

代わりにテストごとに `withHTTPHandle`・`withSSEHandle`・`withWebSocketHandle` を注入したテスト用 `Client` を作成し、自分の定義と業務ロジックをインメモリで通して検証します：

| プロジェクト内のレイヤー                                                 | テストで検証する対象                                                                           | テスト用 `Client` の渡し方                                                                    |
| :----------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------- |
| 操作定義とスキーマ（`src/api/request/`、`src/api/schema/`）              | `builder` のパラメータ配置（`path`, `query`, `headers`, `body`）、`.alias()`、`output`/`error` | 本番と同じ操作をインポートし、`withHTTPHandle` を付けた `Client` を渡す                       |
| ビジネスヘルパーとカスタムインターセプター（`checkout.ts`, `client.ts`） | 認証ヘッダー注入、`401` 再認証リプレイ、複数ステップ業務フロー、ドメインエラー変換             | `withInterceptors(...)` を付けたテスト用 `Client` を業務関数へそのまま渡す                    |
| SSE・WebSocket コンシューマー（`src/events/`, `src/quotes/`）            | ストリームデータの変換処理、送信フレーム、`await using` クリーンアップ                         | `withSSEHandle` / `withWebSocketHandle` で模擬フレームをインメモリ供給する                    |
| React / Vue コンポーネント（`OrderCard.tsx`, `OrderView.vue`）           | ローディング表示、取得結果の描画、エラー表示、アンマウント時の `AbortController` キャンセル    | `<ClientProvider client={testClient}>` で囲む、または `createClientPlugin(testClient)` を登録 |

## 1. プロジェクト内の操作定義とスキーマをテストする（`withHTTPHandle`）

プロジェクトから実際の `defineRequest` をインポートし、`withEndpoint("https://fixture.invalid")` と `withHTTPHandle(...)` を持つテスト用 `Client` を作成します：

- **`https://fixture.invalid` を指定する理由**：`createClient` は `withHTTPHandle` に渡る前に URL を検証します。`.invalid` は RFC 予約ドメインのため誤って公開 DNS に飛ぶ心配がありません。
- **プロトコルごとに専用のハンドルを使用**：`withHTTPHandle` は HTTP（`defineRequest`）のみを扱います。SSE は `withSSEHandle`、WebSocket は `withWebSocketHandle` を使います。
- **リトライの既定値と `withRetry(undefined)` の罠**：`withRetry` を省略するとリトライは無効になります。通常の単体テストでは省略し、`502`/`503`/`504` やネットワークエラーが `1s + 2s + 4s` のバックオフを待たず 1 回で返るようにしてください。なお `withRetry()` や `withRetry(undefined)` は既定の **3 回リトライを有効にする**ため、明示的にオフにする場合は `withRetry({ maxRetries: 0 })` を渡してください。

### 3 つの要点：テスト分離・送信内容の確認・3 パターンの応答

- **テストごとに `Client` を作り直す**：リトライ予算やクロージャ状態が別テストへ漏れないよう、各 `test(...)` やヘルパー内で新しく `createClient(...)` を生成します。
- **実際の送信内容を検証する**：`withHTTPHandle(async (input, init) => ...)` 内で `const request = new Request(input, init)` を作り、`request.method`・`request.url`・`request.headers`・`await request.text()`（または `json()`）で `builder` と `.alias()` を確認します。
- **よくある 3 種類の HTTP 結果を再現・アサートする**：
  - **`2xx` 成功**：`expect(err).toBeNull()` の直後に `if (err) throw err;` を置いてからデコード済み `data` を検証します。
  - **`4xx` / `5xx` エラー**：`Response.json(..., { status: 422 })` を返し、`if (err)` 内で `err.code === "HTTP_STATUS"` に絞って `err.status`・`err.data`・`err.response` を検証し、`return` のあとに `expect.unreachable(...)` を置きます（`bun:test` では代わりに `throw new Error("expected fault")` を使います）。
  - **ネットワーク障害（`NET_UNREACHABLE`）**：`Response.error()` は**使わないでください**。ステータス `0` でも `Response` オブジェクトを返すと Defjs は HTTP 応答として `HTTP_STATUS` を返します。断線や `fetch` 失敗を再現するには `Promise.reject(new TypeError("fetch failed"))`（または `throw`）を使います：

```ts
import { createClient, withEndpoint, withHTTPHandle } from "@defjs/core";
import { expect, test } from "vitest";
import { createOrder } from "./sdk/orders.ts";

test("fetch が拒否された場合は NET_UNREACHABLE を返す", async () => {
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withHTTPHandle(() => Promise.reject(new TypeError("fetch failed"))),
  );

  const [err] = await createOrder(client, { sku: "book", quantity: 1 });
  if (err) {
    expect(err.code).toBe("NET_UNREACHABLE");
    return;
  }

  expect.unreachable("expected NET_UNREACHABLE fault");
});
```

### `withRetry` 復旧と `401` トークン更新リプレイのテスト

- **一時的な `503` からの `withRetry` 復旧**：`withHTTPHandle` の外に `let attempts = 0` を置き、`withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] })` を設定すれば待ち時間なしで検証できます。注意：`methods` を指定すると既定の安全メソッド一覧（`["GET", "HEAD", "OPTIONS", "TRACE", "PUT", "DELETE"]`）が**上書き**されるため、同じテストクライアントで `GET` もリトライする場合は `methods: ["GET", "POST"]` としてください。
- **インターセプターでの `401` 更新・再送**：`next(...)` を再度呼ぶリプレイは `withRetry` を使いません。状態付き `withHTTPHandle` カウンターでそのままテストできます。なお `401` で `err.data` を読む場合は操作定義に `error: struct(...)` が必要です。

```ts
import {
  createClient,
  createHttpInterceptor,
  withEndpoint,
  withHTTPHandle,
  withInterceptors,
  withRetry,
} from "@defjs/core";
import { expect, test } from "vitest";
import { submitOrder } from "./src/checkout.ts";

test("methods に POST を含めると一時的な 503 から withRetry で復旧する", async () => {
  let attempts = 0;
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] }),
    withHTTPHandle(async () => {
      attempts += 1;
      if (attempts === 1) {
        return Response.json({ message: "try again" }, { status: 503 });
      }
      return Response.json({ id: "ord_2" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "pen", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_2");
});

test("401 時にトークンを更新してインターセプター内から next() を再送する", async () => {
  let token = "expired-token";
  let attempts = 0;

  const refreshAuth = createHttpInterceptor(async (req, next) => {
    const first = await next({
      ...req,
      headers: { ...req.headers, authorization: `Bearer ${token}` },
    });
    if (first[0]?.code === "HTTP_STATUS" && first[0].status === 401) {
      token = "fresh-token";
      return next({
        ...req,
        headers: { ...req.headers, authorization: `Bearer ${token}` },
      });
    }
    return first;
  });

  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withInterceptors(refreshAuth),
    withHTTPHandle(async (input, init) => {
      attempts += 1;
      const auth = new Request(input, init).headers.get("authorization");
      if (auth === "Bearer expired-token") {
        return new Response(null, { status: 401 });
      }
      expect(auth).toBe("Bearer fresh-token");
      return Response.json({ id: "ord_3" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "mug", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_3");
});
```

## 3. リアルタイムストリームの消費コードをテストする（SSE / WebSocket）

`defineEventStream` や `defineWebSocket` を使うストリーム消費ヘルパーがある場合は、`withSSEHandle` または `withWebSocketHandle` で模擬フレームをメモリ上から供給します：

- **SSE（`withSSEHandle`）**：`ReadableStream<Uint8Array>` と `"content-type": "text/event-stream"` を含む `Response` を返します。途中切断を再現するにはチャンク送信後に `controller.error(new TypeError("stream dropped"))` を呼びます（ハンドシェイク失敗は `{ status: 500 }` を返します）。
- **WebSocket（`withWebSocketHandle`）**：`EventTarget` を継承し `WebSocketHandle`（`static readonly OPEN = 1` と `readyState`）を実装したスタブを渡します。`FakeQuoteSocket` が `queueMicrotask` で `open` とメッセージを送るのは、操作呼び出しの直後にリスナーや `for await` が登録されるため（同期送信だとリスナー登録前に発火してしまうため）です。異常終了を試すときは `new Event("error")` に続けて `new CloseEvent("close", { code: 1011, reason: "boom" })` を発火させます。

## 4. テストしやすいプロジェクト構造の作り方

[アプリケーション API レイヤー](/ja-JP/docs/application-api) の構成に従うと、`vi.mock` なしで全レイヤーをテストできます：

- **`src/api/request/*.ts` にグローバルクライアントを持ち込まない**：操作定義だけをエクスポートし、本番 `apiClient` をインポートしないでおきます。
- **業務関数は `Client`（または `DerivableClient`）を引数で受け取る**：
  - **`Client` と `DerivableClient` の使い分け**：`createClient(...)` は `DerivableClient` を返し、`Client` 引数にもそのまま渡せます。ただし関数内で `client({ signal })` のように呼び出し単位のオプションを派生する場合は、引数型を **`DerivableClient`** にする必要があります。
  - **引数配置と SSR ファクトリ**：第 1 引数（`placeOrder(client: DerivableClient, input: ...)`）またはデフォルト付き末尾引数（`placeOrder(input: PlaceOrderInput, client: Client = apiClient)`）として受け取り、`src/api/client.ts` からインターセプターや `createServerApiClient(token, ...options: ClientOption[])` をエクスポートします。
  - **Node / Bun テストでの `withXSRF()` の注意点**：`withXSRF()` はブラウザ専用グローバル（`globalThis.location` 等）を参照します。`src/api/client.ts` のモジュールトップレベルで無条件に `export const apiClient = createClient(..., withXSRF())` を実行すると、`= apiClient` をデフォルト引数に持つ関数をテストファイルがインポートした時点でロードエラーになります。`typeof window !== "undefined"` で分岐するかブラウザ専用ファクトリ内に閉じ込めてください。
- **React / Vue コンポーネントに `testClient` を注入する**：

## 5. タイムアウトとタイマー依存の振る舞いをテストする

リトライバックオフ、再接続待機、ハートビートのテストには、Vitest で `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })`（Bun test では `jest.useFakeTimers()`）を使います。`toFake` を絞ることで Promise とマイクロタスクが止まらず `async`/`await` がそのまま動きます。

なお **Vitest のフェイクタイマーはネイティブの `AbortSignal.timeout` を進めません**（JS の `setTimeout` ではなくランタイム固有タイマーを使うため）：

- Vitest で `client({ signal })` の期限切れテストを行うには、制御された `setTimeout` から `AbortController` を `new DOMException("request deadline", "TimeoutError")` で中断してください。`await ready` でハンドル側の `setTimeout` 登録を待ってから `advanceTimersByTimeAsync` を呼ぶのがポイントです：

<include cwd lang="typescript">
  examples/testing/deadline.ts#example
</include>

- あるいは `withRetry({ maxRetries: 0, attemptTimeoutMs: 500 })` を設定すれば Defjs 内部で JS `setTimeout` が使われるため、`vi.advanceTimersByTimeAsync(500)` だけで直接 `NET_TIMEOUT` を発生させられます。
- **Bun test** では `jest.useFakeTimers()` と `jest.advanceTimersByTime()` が `AbortSignal.timeout` も制御します。状態遷移や試行回数をアサートし、`finally` で必ず本物のタイマーに戻してください。
