# テスト

`@defjs/core` はライブラリ自身のトランスポート層やコーデックをすでにテストしています。アプリケーションや SDK パッケージで Defjs を使うときに書くべきテストは、**あなた自身がプロジェクト内で書いたコード**——`src/api/request/` と `src/api/schema/` の操作定義とスキーマ、`src/api/client.ts` のカスタムインターセプター、`src/checkout.ts` の業務ヘルパー、そして React / Vue コンポーネントの振る舞いです。

## プロジェクトの何をテストすべきか（`vi.mock` を使わない理由）

エクスポートした `defineRequest`、`defineEventStream`、`defineWebSocket` 関数をスタブ化したり `vi.mock(...)` で差し替えたり**しないでください**。テストごとに `withHTTPHandle`、`withSSEHandle`、`withWebSocketHandle` を注入したテスト用 `Client` を作成すれば、ネットワークソケットを開かずに自分の操作定義と業務ロジックをインメモリで丸ごと検証できます。

| プロジェクト内のレイヤー                                                 | テストで検証する対象                                                                                  | テスト用 `Client` の渡し方                                                                    |
| :----------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------- |
| 操作定義とスキーマ（`src/api/request/`、`src/api/schema/`）              | `builder` のパラメータ配置（`path`, `query`, `headers`, `body`）、`.alias()`、`output`/`error`        | 本番と同じ操作をインポートし、`withHTTPHandle` を付けた `Client` を渡す                       |
| ビジネスヘルパーとカスタムインターセプター（`checkout.ts`, `client.ts`） | 認証ヘッダーの注入、複数ステップの業務フロー、ドメインエラー変換、リトライ方針                        | `withInterceptors(...)` を付けたテスト用 `Client` を業務関数へそのまま渡す                    |
| SSE・WebSocket コンシューマー（`src/events/`, `src/quotes/`）            | ストリームから読み取ったデータの業務変換、送信フレーム、`await using` によるクリーンアップ            | `withSSEHandle` / `withWebSocketHandle` で模擬フレームをインメモリ供給する                    |
| React / Vue コンポーネント（`OrderCard.tsx`, `OrderView.vue`）           | ローディング表示、取得結果の描画、エラー表示、アンマウント時の `AbortController` によるキャンセル処理 | `<ClientProvider client={testClient}>` で囲む、または `createClientPlugin(testClient)` を登録 |

## 1. プロジェクト内の操作定義とスキーマをテストする（`withHTTPHandle`）

プロジェクトから実際の `defineRequest` をインポートし、予約ドメイン（例：`https://fixture.invalid`）と `withHTTPHandle(...)` を持つ独立したテスト用 `Client` を作って、送信される `Request` がバックエンドの仕様どおりかを検証します。`withRetry` を設定しない限りリトライは無効です。通常のユニットテスト用クライアントでは `withRetry` を省略し、`502`/`503`/`504` やネットワークエラーのテストがバックオフ待ちなしで 1 回目の試行後に即座に返るようにしてください。

### テスト分離・送信フォーマット検証・エラーファーストタプル

- **テストごとに `Client` を分離する**: 各 `test(...)` やテストヘルパーの中で新しく `createClient(...)` を作り、リトライ予算やハンドル状態がテスト間で漏れないようにします。
- **実際の送信フォーマットを検証する**: `withHTTPHandle(async (input, init) => ...)` 内で `const request = new Request(input, init)` を作り、`request.method`、`request.url`、`request.headers`、`await request.text()`（または `await request.json()`）をアサートして、`builder` と `.alias()` が API 仕様どおりのワイヤ表現を出力しているか確かめます。
- **`[err, data, response]` タプルを検証する**:
  - `2xx` 正常系では `expect(err).toBeNull()` に続けて `if (err) throw err;` を書き、その後デコードされた `data` フィールド（`.alias()` 変換後の論理フィールドを含む）を検証します。
  - エラー系ではまず `if (err)` でガードし、その内側で `if (err.code === "HTTP_STATUS")` に絞り込んで `err.status`、`err.data`、`err.response` を検証（デコード／事前検証エラーやラップ済みビジネス `Error` では `err.cause` を確認）し、`if (err)` ブロック内から `return` したうえで末尾に `expect.unreachable(...)` を置きます。

## 2. ビジネスロジックとカスタムインターセプターをテストする

`src/checkout.ts` のような業務ヘルパーと `createHttpInterceptor` で書いたカスタムインターセプターをテストするときは、業務関数にテスト用 `Client` を渡し、テストクライアントへ `withInterceptors(bearerAuth(...))` を装着します。1 本のインメモリテストで、インターセプターの認証ヘッダー付与、`submitOrder` の `.alias()` エンコード、そして成功レスポンスや `409` 競合などのドメインエラー変換をまとめて確認できます。

一時的な `503` に対する `withRetry` の復旧を実時間待ちなしでテストするには、`withHTTPHandle` 内にカウンター（`let attempts = 0`）を持ち、`withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] })` を設定します（`submitOrder` のような `POST` 操作をリトライする場合は `methods: ["POST"]` が必要です）。インターセプターレベルの再送（`401` 応答後にインターセプター内から `next(...)` でトークン更新・再送する場合など）は `withRetry` を使わないため、状態を持つ `withHTTPHandle` カウンターだけでそのままテストできます。

## 3. リアルタイムストリームの消費コードをテストする（SSE / WebSocket）

プロジェクト内に `defineEventStream` や `defineWebSocket` をラップしたストリーム消費ヘルパーがある場合は、`withSSEHandle` や `withWebSocketHandle` で模擬フレームをメモリ上から流し込み、業務ロジックの出力やリソース解放を検証します。

- **SSE（`withSSEHandle`）**: `ReadableStream<Uint8Array>` と `content-type: "text/event-stream"` を持つ `Response` を返します。
- **WebSocket（`withWebSocketHandle`）**: `EventTarget` を継承して `WebSocketHandle` を実装（`static readonly OPEN = 1` を定義）した軽量スタブクラスを渡し、送信データを記録して `open`、`MessageEvent("message")`、`CloseEvent("close")` をディスパッチします。

## 4. テストしやすいプロジェクト構造の作り方

[アプリケーション API レイヤー](/ja-JP/docs/application-api) の構成に従うと、`vi.mock` なしで全レイヤーをきれいにテストできます。

- **`src/api/request/*.ts` にグローバルクライアントを持ち込まない**: `defineRequest`・`defineEventStream`・`defineWebSocket` の定義だけをエクスポートし、本番用 `apiClient` をインポートしないことで、どのテストからもテスト用 `Client` をそのまま渡せます。
- **業務関数は `Client`（または `DerivableClient`）を引数で受け取る**：`client` を明示的な第 1 引数（そのまま渡す場合は `client: Client`、`client({ signal })` のように呼び出し単位の派生を行う場合は `client: DerivableClient`）にして `export async function placeOrder(client: Client, input: ...)` と書くか、デフォルト値付きクライアントを末尾引数に置いて `export async function placeOrder(input: PlaceOrderInput, client: Client = apiClient)` と書きます。後者なら本番コードは `placeOrder(input)` と呼べ、テストでは `placeOrder(input, testClient)` を渡せます。`src/api/client.ts` からはカスタムインターセプターや末尾の `ClientOption` を `createClient(...)` へ転送する SSR ファクトリ（例：`createServerApiClient(token, ...options: ClientOption[])`）もエクスポートし、テストで `withHTTPHandle` を付けられるようにします。
- **React / Vue コンポーネントには Provider / Plugin で `testClient` を注入する**:
  - **React（`@defjs/react`）**: テスト対象コンポーネントを `<ClientProvider client={testClient}>` で囲みます（`useClient(overrideClient)` を使う構成なら引数に `testClient` を直接渡せます）。
  - **Vue（`@defjs/vue`）**: テストでコンポーネントをマウントする際に `app.use(createClientPlugin(testClient))` を適用するか、`provide(HTTP_CLIENT, testClient)` で注入します。

## 5. タイムアウトとタイマー依存の振る舞いをテストする

リトライバックオフ、SSE/WebSocket の再接続待機、ハートビートなどのタイマー処理をテストするには、Vitest では `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })`（Bun test では `jest.useFakeTimers()`）を使います。Vitest のフェイクタイマーはネイティブの `AbortSignal.timeout` を進めないため、Vitest で期限切れテストを再現したい場合は、制御された `setTimeout` から `AbortController` を `TimeoutError` で中断します。
