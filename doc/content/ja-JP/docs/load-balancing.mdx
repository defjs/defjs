# ロードバランシングとフェイルオーバー

アプリケーションが `withEndpoint(...urls)` を使用して複数のベース URL を構成すると、Defjs はリクエストをレプリカ群に分散させ、パッシブサーキットブレイクやアクティブヘルスチェックにより異常なホストを除外し、安全な HTTP メソッドを同一呼び出し内で必要に応じてフェイルオーバーさせることができます。

## 1. ロードバランサー戦略の選択

| 戦略                                                                              | 最適な用途                                                                | デフォルトのヘルスフィルタリング                      |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------- |
| [`pickFirstBalancer(options?)`](/ja-JP/api/core/pickfirstbalancer) _(デフォルト)_ | プライマリとバックアップのリージョン一覧を持つブラウザアプリ              | オフ（`outlierDetection` オプションでオプトイン可能） |
| [`roundRobinBalancer(options?)`](/ja-JP/api/core/roundrobinbalancer)              | 対等なレプリカ群に対するサーバー間通信（任意の `weights` 重み付けに対応） | 有効（`5` 回の連続失敗で発動）                        |
| [`p2cBalancer(options?)`](/ja-JP/api/core/p2cbalancer)                            | レプリカごとのレイテンシや処理中負荷が変動するサーバー間通信              | 有効（`5` 回の連続失敗で発動）                        |

### `pickFirstBalancer` と `p2cBalancer` の動作原理

- **`pickFirstBalancer`**: 最初の URL に留まり、`NET_UNREACHABLE` または `NET_UNAVAILABLE`（HTTP 502、503、504）で進みます。順序と固定エンドポイントはクライアントの全エンドポイントリスト（`members`）に従い、HTTP リトライが固定エンドポイントを動かすことはありません。最初のエンドポイントでタイムアウトして 2 番目でリトライされても、後続の呼び出しは最初のエンドポイントに留まり、フェイルバックは有効なままです。`failbackMs: 30_000` を設定すると、バックアップでその時間を過ごしたあと、プライマリへフェイルバックするために再プローブします。同時に実行できるプライマリのプローブは 1 つだけです。プローブはピアの応答が始まった時点（HTTP レスポンスヘッダー、SSE ハンドシェイク、または WebSocket の open）で判定されるため、プローブとなった長寿命のストリームがクライアント全体のフェイルバックを妨げ続けることはありません。その時点に達しなかった試行は、完了時に判定されます。フェイルオーバー後の最初のプライマリプローブには、間隔が経過し、かつプライマリを離れてから代替エンドポイントが少なくとも 1 回選ばれている必要があります。プローブに失敗すると、両方の条件がリセットされます。次のプローブまでに、代替エンドポイントをもう一度選択し、さらに間隔が経過している必要があります。SSE/WebSocket の再接続バックオフが `failbackMs` より長い場合でも、この要件は変わりません。そのため、再接続のたびに障害が発生しているプライマリへ向かうのではなく、正常なバックアップにも順番が回ります。
- **`roundRobinBalancer` の重み**: 未指定の重みは `1` で、設定する重みは有限の正の数でなければなりません。スムーズ加重ラウンドロビンは選択比率を維持します（たとえば `3:1` なら、重みの大きいピアが 4 回中 3 回選ばれます）。極端な大きさの値はオーバーフローを避けるためにスケーリングされ、浮動小数点精度を下回る比率はゼロに丸められる場合があります。選択と古い現在値のクリーンアップには、選択ごとに O(候補数) の処理が必要です。
- **`p2cBalancer` (Power of Two Choices)**: 候補から重複なしで 2 つをランダムサンプリングし、スコア（`PeakEwma RTT × (pending + 1)`、または `load: "pending"` 指定時は処理中の `pending` 数）が低いほうを選択します。デフォルト値（`defaultRttMs: 30`、`decayMs: 10000`）は Linkerd / tower の規約に従っています。pending は `pick` がエンドポイントを選んだ時点で確保されるため、同じ tick 内の連続呼び出しも複数のエンドポイントに分散されます。解放されるのは、ピアの応答が始まったとき（HTTP レスポンスヘッダー、SSE ハンドシェイク、WebSocket の open）、または応答が始まらなかった場合は試行の完了時です。そのため SSE と WebSocket では、p2c が分散するのはハンドシェイクであり、開いている接続の数ではありません。

バランサーの状態（固定されたエンドポイント、隔離状態、p2c の負荷）とリトライバジェットはクライアントに属します。クライアントはアプリケーションごとに 1 回だけ作成し、呼び出しごとのクライアントは `client(options)` で派生してください。派生クライアントは、バランサーの状態とリトライバジェットの両方を引き継ぎます。1 つのバランサー値を `withBalancer` で複数のクライアントに渡すと共有されるのはバランサーの状態だけで、リトライバジェットはクライアントごとに別です。リクエストごとに新しい `createClient` を作ると、両方が最初からになります。

## 2. 同一呼び出し内の HTTP リトライ

リトライは 3 つの別々の判断で決まります。**もう一度試すか**（`withRetry`）、**どこへ送るか**（ランタイムがバランサーに、試行済みのエンドポイントを除いて再選択させます）、**どれだけ待つか**（バックオフ）です。HTTP の `withRetry`、SSE の `withSSEReconnect`、WebSocket の `withWebSocketReconnect` は、対称なトランスポート単位のポリシーです。フラットなバックオフフィールドは、名前も検証も遅延の計算も同じです。バランサーはリトライポリシーを知りません。カスタムバランサーに特別な協力は要りません。

同一呼び出し内の HTTP リトライは**デフォルトでオフ**です。`withRetry` を省くと、呼び出しごとに試行は 1 回だけで、リトライバジェットは作られず、クレジットも計上されません。後続の呼び出しでの選択は変わりません。失敗した呼び出しのあとでも、`pickFirstBalancer` は先へ進むことができます。`withRetry()` は `withRetry({})` と同等で、`GET`、`HEAD`、`OPTIONS`、`TRACE` の接続失敗に対して、合計 2 回の試行を有効にします。

これは Go のエコシステムに従います。[gRPC は `retryPolicy` をサービス構成に置き](https://grpc.io/docs/guides/retry/)、ロードバランシングの構成と並べます。[go-kit の `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) はバランサーを明示的に包みます。どちらも、アプリケーションのリトライポリシーをデフォルトでは適用しません。gRPC のリトライポリシーはバックオフの設定を必須とし、±0.2 のジッターを使います。[Envoy のデフォルトは 25 ミリ秒の基数で、上限はその基数の 10 倍です](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff)。Defjs は 25 ミリ秒、係数 2、250 ミリ秒の上限、±20% のジッターを使います。gRPC は低レベルの競合に対して透過的なリトライを行うことがあります。Defjs はそれらを模倣しません。

- **試行回数の合計 (`maxAttempts`)**: 最初の試行を含み、gRPC の `retryPolicy.maxAttempts` および go-kit `lb.Retry` の `max` と一致します。値は 1 以上の安全な整数でなければなりません。`1` はリトライしないことを意味します。設定上の上限はありませんが、バランサーの各選択では、その呼び出しですでに選ばれたエンドポイントを除外します。数えるのは外側の試行であり、アプリケーションのインターセプター内の実際の送信回数ではありません。`next()` をループで呼ぶインターセプターは、同じエンドポイントへ何度も送信できます。たとえば `maxAttempts: 2` で、障害が発生しているプライマリへインターセプターが 3 回送信し、外側のリトライで正常なバックアップへ 1 回送信すると、ネットワークリクエストは 4 回になります。`builder` とインターセプターチェーンの外側の認証層は、4 回ではなく 2 回実行されます。ストリーミングのリクエストボディはリトライしません。`methods` は大文字と小文字を区別しません。`methods: []` はすべてのメソッドのリトライを無効にします。
- **リトライ条件 (`on`)**: デフォルトは `["connect-failure"]` です。`"gateway-error"` は `NET_UNAVAILABLE`（HTTP `502`/`503`/`504`）を加えます。これには、`RES_*` のデコードで拒否されたゲートウェイのエラーボディも含みます。`attemptTimeoutMs` を設定しているときは `"attempt-timeout"` も追加できます。条件を満たすリトライはリクエストを作り直し、インターセプターチェーン全体を一番外側から再実行します。
- **バックオフ (`delayMs`、`factor`、`jitter`、`maxDelayMs`)**: n 回目のリトライの前に、`delayMs × factor^(n−1)` を乗法ジッター付きで待ち、ジッターと丸めのあとで上限を適用します。デフォルトは `25`、`2`、`0.2`、`250` です。`delayMs: 0` は待ちを省きます。再接続と同じく、`delayMs` は有限で非負、`factor` は有限で正、`jitter` は `[0, 1]` の有限値、`maxDelayMs` は非負の有限値か正の `Infinity` でなければなりません。プラットフォームのタイマー上限は引き続き適用されます。
  Core の `withRetry` は `Retry-After` を読みません。このヘッダーの処理や遅延の上限は、[アプリケーションのインターセプターポリシー](/ja-JP/docs/interceptors) であり、このバックオフには含まれません。
  構成されたエンドポイントが 1 つだけのとき、`withRetry` はリクエストを再送しません。各リトライが、すでに試したエンドポイントを除外するからです。

- **試行ごとと呼び出し全体のタイムアウト**: `attemptTimeoutMs` は有限の正の数であり、2147483647（タイマー上限）以下でなければなりません。そうでなければ、操作は `REQ_OPTIONS_INVALID` を返します。それは、選択されたエンドポイントへ送られる各 Fetch を、呼び出しからレスポンスボディの読み取り完了まで計測します。送信の前後のインターセプター処理（たとえば `401` のあとのトークン更新）と struct のデコードは計測対象外で、エンドポイントの責任としてカウントされることもありません。送信が完了したあとのインターセプター処理中に呼び出し元の期限が切れても、バランサーには `NET_TIMEOUT` ではなくエンドポイント自身の結果が報告されます。呼び出し元の `client({ signal: AbortSignal.timeout(ms) })` は、すべての試行**とバックオフの待ち**を対象にします。待ちのあいだにキャンセルすると、呼び出し元のキャンセル Fault が返り、次の pick は行われません。
- **リトライで使えるエンドポイントがない場合**: リトライのラウンドで使えるエンドポイントがない場合（バランサーの pick が失敗した、または次のエンドポイントの URL が解決できない）、呼び出しは `REQ_BUILD_FAILED` ではなく、直前の試行の Fault（たとえば `NET_UNREACHABLE`）を返します。
- **Finagle / Linkerd のリトライバジェット (`budget`)**: 各クライアント構成がバジェットを所有し、同じ構成を使う派生クライアントだけがそれを共有します。バランサーを共有するクライアントは共有しません。デフォルトは `percentCanRetry: 0.2`、`minRetriesPerSecond: 10`、`ttlMs: 10000` で、元のトラフィックの 20% に予約分を加えたものです。クレジットとデビットは、10 個の TTL/10 スライスで遅延して期限切れになります。リトライは待つ前に引き出します。バジェットを使い切ると、待たず、リトライもしません。上限を外すには `budget: false` を設定します。
- **ブラウザのオフライン検知**: `navigator.onLine === false` の場合、接続失敗は `{ attempted: false }` と報告され、バランサーは進まず、リトライも起きません。

### ブラウザへのデプロイ時の境界

- ブラウザの CORS 失敗は Fetch に接続失敗として渡り、ホスト停止と区別できない `NET_UNREACHABLE` として報告されます。エンドポイント選択を進め、オプトインされた安全なメソッドのリトライを起こす可能性があるため、フェイルオーバーの成功がプライマリリージョンの CORS 設定ミスを隠すことがあります。
- レスポンスに必要な CORS ヘッダーがなくても、POST はサーバーですでに処理されている場合があります。その場合、アプリケーションは書き込みが成功したか分からないまま `NET_UNREACHABLE` を受け取ります。POST はデフォルトでは再送されません。書き込みのリトライを明示的に有効にするには、レプリカ間でアプリケーションレベルの冪等性が必要です。
- ブラウザでは、サーバーに拒否された WebSocket アップグレード（たとえば `401`）は到達不能なエンドポイントと区別できず、`NET_UNREACHABLE` として報告されます。そのため、期限切れの認証情報によってエンドポイントが隔離されることがあります。
- Cookie のスコープはポートではなくホスト単位です。`localhost` の異なるポートにある 2 つのエンドポイントは Cookie を共有できますが、`localhost` と `127.0.0.1` は共有しません。複数オリジンのエンドポイント集合では、Cookie／トークンと CORS の認証情報ポリシーを意図的に設計する必要があります。`withCredentials(true)` は Cookie のスコープを変更しません。
- 明示的なオフラインヒント（`navigator.onLine === false`）は、エンドポイントへの帰属と接続失敗によるリトライを抑制します。これはブラウザのヒントにすぎず、信頼できる到達性チェックではありません。

後から渡した `withRetry` はポリシーを置き換えます。`withRetry()` と `withRetry(undefined)` は `withRetry({})` と同じように振る舞います。有効にしたあとリトライを無効にするには、`withRetry({ maxAttempts: 1 })` を渡します。無効なリトライ設定は、HTTP 操作の実行時に `Invalid retry options` を伴う `REQ_OPTIONS_INVALID` を返します。

## 3. パッシブサーキットブレイクとアクティブヘルスチェック (`outlierDetection`)

`roundRobinBalancer()` および `p2cBalancer()` は、デフォルトで候補の選択処理を [`outlierDetection`](/ja-JP/api/core/outlierdetection) でラップしています。

1. **連続失敗による隔離**: デフォルトの分類子は、code を持つ結果をすべて失敗として数えます（`NET_UNREACHABLE`、`NET_UNAVAILABLE`、`NET_SERVER_ERROR`、`NET_TIMEOUT`、`NET_BODY_INCOMPLETE`）。試行されたが code のない結果は連続回数をリセットし、帰属できない試行や破棄されたサンプルは連続回数を変えません。数えられる結果が `consecutiveFailures` 回（デフォルト `5` 回）連続すると、そのエンドポイントは `min(minPenaltyMs × 2^level, maxPenaltyMs)`（`1000ms` から `60000ms`）に、最大 `50%` の一様な正のジッターを加えた期間だけ隔離されます。基本時間とジッターの合計が `maxPenaltyMs` を超えることはありません。
2. **単一プローブによる復旧（Single-probe recovery）**: ペナルティ期間が満了すると、単一のリクエストがプローブとしてホストに送られます。ピアの応答が、数えられる失敗なしに `end` で始まれば、通常のトラフィックはすぐに再開し、ペナルティレベルは `0` に戻ります。失敗すれば（タイムアウトを含む）エンドポイントは再び隔離され、ペナルティは倍になります。
3. **履歴の上限**: ヘルス履歴は、派生クライアントや呼び出しごとの候補除外をまたいで、少なくとも 256 エンドポイント、かつ少なくとも現在のメンバー数を保持します。まず問題のないエントリや期限切れエントリを最終使用が古い順に削除し、次に部分的な失敗シーケンスを削除します。未期限切れのペナルティや進行中のプローブを持つエントリを削除するのは、保持中の全エントリが保護対象の場合だけで、そのときは最も古いエントリを削除します。ある呼び出しでエンドポイントを省くだけでは、そのペナルティはリセットされません。P2C の負荷履歴も少なくとも 256 件、かつ少なくとも現在のメンバー数を保持するため、256 エンドポイントを超えるリストでもすべての推定値が残ります。処理中のエントリより先にアイドル状態のエントリを削除します。忘れられたエンドポイントは `defaultRttMs` から再開します。Pick-first のシャッフルキーは少なくとも 256 件（および少なくとも現在のメンバー）を LRU キャッシュに保持するため、忘れられたエンドポイントが戻ると新しいキーを受け取ります。加重ラウンドロビンはクライアントのメンバーの現在値を保持します。1 回の選択から外れたエンドポイント（HTTP リトライやヘルスフィルタによる選択）も、nginx がダウンしたピアをスキップするのと同様に値を保ち、メンバーから外れたエンドポイントの値だけが破棄されます。コピーした重み設定は構築時に固定されます。時間の計測には、利用可能ならプラットフォームの単調な Performance クロックを使い、`Date.now()` はフォールバックとしてのみ使用します。
4. **パニックモード（フェイルオープン）**: `isHealthy` が、隔離されていないすべてのエンドポイントを不健全と判定した場合、バランサーは `isHealthy` を無視して、隔離されていないエンドポイントから選びます。設定されたすべてのエンドポイントが隔離されている場合にのみ、ローカルでトラフィックをすべて破棄するのではなく、クライアントの候補リスト全体へフェイルオープンします。

## 4. トランスポートのアカウンティングライフサイクル (`pick` → `start` → `end` → `done`)

カスタムバランサーは `info.endpoints` に含まれる文字列のいずれかを完全一致で選ぶ必要があります。候補外を選ぶと、機密情報を含まない cause メッセージ `Balancer selected an endpoint outside the candidate set` を伴う `REQ_BUILD_FAILED` タプルが返ります。トランスポートは開始されず、その選択の `done` が `{ attempted: false }` で 1 回実行されます。この規則により、ヘルスフィルタリングと呼び出しごとのリトライ除外が維持されます。

カスタムバランサーは、同期の `pick(info)` と、任意の `start()`、`end(info)`、`done(info)` を実装します。`PickInfo` には、1 回の pick の候補 `endpoints`（リトライやラッパーによるフィルタで短くなります）、`members`（クライアントの全エンドポイントリストで、どの試行でも同じです。状態を持つバランサーは順序と状態をこれをキーに管理します）、定義の任意の `operation` があり、トランスポートを区別するフィールドはありません。トランスポートは自身の情報を中立な `DoneInfo.code` へ変換します。組み込みバランサーは `status` を読みません。この生のレスポンス情報は、カスタムバランサーのためだけに残されます。`start` は試行の前、`end` はピアの応答が始まるときか応答前の失敗のとき、`done` は完了時に実行されます。したがって、後から発生するボディの失敗は、それ以前の `end` のサンプルを変えずに、最終的な code を変えることがあります。

| 物理トランスポートの結果                                                                  | 最終的な `done(info)` サンプル                             |
| ----------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| HTTP/SSE のレスポンスステータス 502、503 または 504                                       | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| HTTP/SSE のその他の 500 以上のレスポンスステータス                                        | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP/SSE のレスポンスステータス 2xx、3xx または 4xx（429 を含む）                         | `{ attempted: true, status }`                              |
| HTTP レスポンスボディがストリーム途中で切断                                               | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE ハンドシェイクに成功後、ストリームの `reader.read()` が reject                        | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| SSE の正常な EOF、ハンドシェイク成功後のデコード失敗、またはキュー上限超過                | `{ attempted: true, status }`                              |
| 接続済み WebSocket がコード `1006` または `1015` で切断（クローズフレームが届かなかった） | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 接続済み WebSocket がコード `1012` または `1013` で切断                                   | `{ attempted: true, code: "NET_UNAVAILABLE" }`             |
| WebSocket のハートビート ACK がタイムアウト                                               | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 接続済み WebSocket がそれ以外のコードでクローズ（`wasClean` の値は問わない）              | `{ attempted: true }`                                      |
| 呼び出し元のキャンセル、またはストリーム／ソケットの手動クローズ                          | `{ attempted: false }`                                     |
| 試行開始後に呼び出し元の期限が超過                                                        | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

ハンドシェイクのデコード失敗は、ハンドシェイクのステータスから導いた中立な結果を残します（たとえばステータス `503` の `NET_UNAVAILABLE`）。不完全な HTTP ボディは、ゲートウェイ応答であっても、代わりに `NET_BODY_INCOMPLETE` とその生の status を残します。他の code 付きの結果と同様、デフォルトの外れ値検出ではこれも失敗としてカウントされます。送信できなかったハートビート（`message()` の throw やシリアライズ失敗）はローカルの事象で、中立です。
