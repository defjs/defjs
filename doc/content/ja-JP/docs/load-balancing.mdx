# ロードバランシングとフェイルオーバー

アプリケーションが `withEndpoint(...urls)` を使用して複数のベース URL を構成すると、Defjs はリクエストをレプリカ群に分散させ、しばらく失敗し続けるホストを隔離し、独自のヘルス関数が拒否するホストをスキップし、失敗した呼び出しを別のエンドポイントで必要に応じてリトライできます。何が健全かを決めるのは Defjs ではなく、利用者が渡す関数だけがエンドポイントを不健全と判定できます。

## 1. ロードバランサー戦略の選択

| 戦略                                                                              | 最適な用途                                                                | デフォルトのヘルスフィルタリング            |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------- |
| [`pickFirstBalancer(options?)`](/ja-JP/api/core/pickfirstbalancer) _(デフォルト)_ | プライマリとバックアップのリージョン一覧を持つブラウザアプリ              | オフ（`outlierDetection: {}` でオプトイン） |
| [`roundRobinBalancer(options?)`](/ja-JP/api/core/roundrobinbalancer)              | 対等なレプリカ群に対するサーバー間通信（任意の `weights` 重み付けに対応） | オフ（`outlierDetection: {}` でオプトイン） |
| [`p2cBalancer(options?)`](/ja-JP/api/core/p2cbalancer)                            | レプリカごとのレイテンシや処理中負荷が変動するサーバー間通信              | オフ（`outlierDetection: {}` でオプトイン） |

### `pickFirstBalancer` と `p2cBalancer` の動作原理

- **`pickFirstBalancer`**: 最初の URL に留まり、`NET_UNREACHABLE` または `NET_UNAVAILABLE`（HTTP 502、503、504）で進みます。順序と固定エンドポイントはクライアントの全エンドポイントリスト（`members`）に従います。リトライはすべてのエンドポイントから選び直すため、同じ規則に従います。接続拒否、または 502、503、504 のあとは次のエンドポイントに達し、pick-first を進めないタイムアウトのあとは同じエンドポイントをもう一度試します。`failbackMs: 30_000` を設定すると、時間だけで最初のエンドポイントに戻ります。固定エンドポイントが最初のエンドポイントからそれだけの時間離れると、候補に最初のエンドポイントを含む次の pick がそれを選び、再び固定します。最初のエンドポイントが復旧したかどうかは、何も判断しません。再び失敗すれば、上の進行規則がそこから離れ、時間は最初からになります。`failbackMs` は pick の間隔より長くしてください。たとえば SSE や WebSocket の再接続遅延です。そうでなければ、すべての pick が最初のエンドポイントに戻ります。
- **重みなしの `roundRobinBalancer`**: カウンターはランダムな `uint32` から始まり、リトライやストリーム再接続のための pick を含め、すべての `pick` で進みます。`outlierDetection` がなく、呼び出しが一つずつ実行されるとき、持続的に失敗するエンドポイントは最初の試行の 1/n より多くを受け取ります。エンドポイントがちょうど 2 つでリトライが有効なら、そのすべてを受け取るので、すべての呼び出しに 1 回のリトライが必要です。並行する呼び出しは pick を交互に挟み、このパターンを崩します。`outlierDetection: {}` を付けると、失敗しているエンドポイントはしばらく隔離されます。
- **`roundRobinBalancer` の重み**: 未指定の重みは `1` で、設定する重みは正の有限数です。スムーズ加重ラウンドロビンは選択比率を維持します（たとえば `3:1` なら、重みの大きいピアが 4 回中 3 回選ばれます）。極端な大きさの値はオーバーフローを避けるためにスケーリングされ、浮動小数点精度を下回る比率はゼロに丸められる場合があります。選択と古い現在値のクリーンアップには、選択ごとに O(メンバー数 + 候補数) の処理が必要です。
- **`p2cBalancer` (Power of Two Choices)**: 候補から重複なしで 2 つをランダムサンプリングし、スコア（`PeakEwma RTT × (pending + 1)`、または `load: "pending"` 指定時は処理中の `pending` 数）が低いほうを選択します。デフォルト値（`defaultRttMs: 30`、`decayMs: 10000`）は Linkerd / tower の規約に従っています。pending は `pick` がエンドポイントを選んだ時点で確保されるため、同じ tick 内の連続呼び出しも複数のエンドポイントに分散されます。解放されるのは、ピアの応答が始まったとき（HTTP レスポンスヘッダー、SSE ハンドシェイク、WebSocket の open）、または応答が始まらなかった場合は試行の完了時です。そのため SSE と WebSocket では、p2c が分散するのはハンドシェイクであり、開いている接続の数ではありません。

バランサーの状態（固定されたエンドポイント、隔離状態、p2c の負荷）とリトライバジェットはクライアントに属します。クライアントはアプリケーションごとに 1 回だけ作成し、呼び出しごとのクライアントは `client(options)` で派生してください。派生クライアントは、バランサーの状態とリトライバジェットの両方を引き継ぎます。1 つのバランサー値を `withBalancer` で複数のクライアントに渡すと共有されるのはバランサーの状態だけで、リトライバジェットはクライアントごとに別です。リクエストごとに新しい `createClient` を作ると、両方が最初からになります。

## 2. リトライ [#retries]

リトライは 3 つの別々の判断で決まります。**もう一度試すか**（`withRetry`）、**どこへ送るか**（ランタイムがバランサーに、すべてのエンドポイントから再選択させます）、**どれだけ待つか**（バックオフ）です。1 つの `withRetry(options)` が HTTP、SSE、WebSocket を対象とし、`config.retry` に保存されます。リクエストオプションの `retry` は、1 回の呼び出しについてそれを置き換えます。3 つのトランスポートはオプション、判断の順序、バックオフの計算を共有し、デフォルトでどの失敗をリトライするかだけが異なります。バランサーはリトライポリシーを知りません。カスタムバランサーに特別な協力は要りません。

リトライは**デフォルトでオフ**です。`withRetry` を省くと、呼び出しごとに試行は 1 回だけで、バックオフはなく、HTTP ではリトライバジェットも作られず、クレジットも計上されません。後続の呼び出しでの選択は変わりません。失敗した呼び出しのあとでも、`pickFirstBalancer` は先へ進むことができます。`withRetry()` は `withRetry({})` と同等です。最初の試行のあとに最大 `maxRetries: 3` 回のリトライ、リトライごとに倍になる `1000` ms の遅延（上限 `30000` ms）、±20% のジッターです。

これは Go のエコシステムに従います。[gRPC は `retryPolicy` をサービス構成に置き](https://grpc.io/docs/guides/retry/)、ロードバランシングの構成と並べます。[go-kit の `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) はバランサーを明示的に包みます。どちらも、アプリケーションのリトライポリシーをデフォルトでは適用しません。gRPC のリトライポリシーはバックオフの設定を必須とし、±0.2 のジッターを使います。最初の試行を除いたリトライ回数（`maxRetries`）は ky、got、undici、および Go の `go-retryablehttp` と一致し、gRPC の `maxAttempts` は最初の試行を数えます。gRPC は低レベルの競合に対して透過的なリトライを行うことがあります。Defjs はそれらを模倣しません。

失敗した試行のあとの流れは、どのトランスポートでも同じで、次の順序です。

1. 呼び出し元の abort、手動の `close()`、致命的なエラー、`ReadableStream` のリクエストボディは、呼び出しを終了します。`shouldRetry` は呼ばれません。
2. `maxRetries` 回のリトライを終えると、呼び出しは終わります。`shouldRetry` は呼ばれません。
3. `shouldRetry(context)` が判断します。なければ `context.retryable` が判断します。関数は非同期でもよく、`transport` で絞られた [`RetryContext`](/ja-JP/api/core/retrycontext-type) を受け取ります。デフォルトを保ったうえで独自の規則を足すには、`context.retryable` を返してください。
4. HTTP のみ: バジェットがリトライの費用を払うか、呼び出しが終わります。
5. 呼び出しはバックオフの遅延を待ち、そのあとバランサーが再び選びます。

- **リトライ回数 (`maxRetries`)**: 最初の試行のあとのリトライ回数で、デフォルトは `3` です。`0` はリトライしません。`maxRetries: 0` と `attemptTimeoutMs` を指定した呼び出しは、各試行の時間を制限するだけです。SSE と WebSocket では、接続が再び確立されたとき（成功したハンドシェイクまたは `open`）に回数がやり直されるため、制限されるのはセッションではなく各障害です。接続を受け入れてすぐに切るサーバーは、そのためリトライされ続けます。止めるには `shouldRetry` を使います。設定上の上限はありません。数えるのは外側の試行であり、アプリケーションのインターセプター内の実際の送信回数ではありません。`next()` をループで呼ぶインターセプターは、同じエンドポイントへ何度も送信できます。たとえば `maxRetries: 1` で、障害が発生しているプライマリへインターセプターが 3 回送信し、外側のリトライで正常なバックアップへ 1 回送信すると、ネットワークリクエストは 4 回になります。ビルダーとインターセプターチェーンの外側の認証層は、4 回ではなく 2 回実行されます。
- **デフォルトでリトライされる失敗**: HTTP は、`methods` に含まれるメソッドで、応答がなかったとき（`NET_UNREACHABLE`）、`502`、`503`、`504` だったとき（`NET_UNAVAILABLE`）、または `attemptTimeoutMs` を使い切ったときにリトライします。SSE は、`methods` に含まれるメソッドで、ハンドシェイクのネットワーク失敗、`502`/`503`/`504` のハンドシェイク、試行タイムアウト、開いたストリーム上のネットワークエラーのあとにリトライします。ストリームの正常終了は呼び出しを終えます。WebSocket は、`session.close()` が要求していないすべての close をリトライします。開かなかった接続と、応答のないハートビートを含み、throw するコンストラクターは含みません。`429` や `500` のようなステータスはデフォルトではリトライされません。`shouldRetry` は `retryable: false` と `status` とともにそれを受け取り、`true` を返せます。`methods` のデフォルトは `GET`、`HEAD`、`OPTIONS`、`TRACE`、`PUT`、`DELETE` で、大文字小文字を区別せずに比較します。HTTP は、インターセプターによる書き換えのあと、試行が送ったすべてのメソッドがそれに含まれている必要があります。POST がリトライされるのは、`methods` に加えるか、`shouldRetry` が `true` を返すときだけで、それにはレプリカ間のアプリケーションレベルの冪等性が必要です。条件を満たす HTTP リトライはリクエストを作り直し、インターセプターチェーン全体を一番外側から再実行します。SSE は構築済みのリクエストを再利用して URL だけを差し替え、WebSocket は `beforeConnect` を再実行します。
- **バックオフ (`delayMs`、`factor`、`jitter`、`maxDelayMs`)**: n 回目のリトライの前に、`delayMs × factor^(n−1)` を乗法ジッター付きで待ち、ジッターと丸めのあとで上限を適用します。デフォルトは `1000`、`2`、`0.2`、`30000` です。`delayMs: 0` は待ちを省きます。`maxDelayMs: Infinity` は上限を外します。プラットフォームのタイマー上限は引き続き適用されます。SSE では、数字だけのサーバーの `retry:` フィールドが、以降の試行で `delayMs` を置き換えます。Core は `Retry-After` を読みません。このヘッダーの処理や遅延の上限は、[アプリケーションのインターセプターポリシー](/ja-JP/docs/interceptors) であり、このバックオフには含まれません。
- **単一のエンドポイント**: リトライは、直前に失敗したものを含め、すべてのエンドポイントから選びます。そのため単一のエンドポイントは、バックオフの遅延のあとにもう一度試されます。リトライバジェットと `maxRetries` が嵐を抑えます。
- **試行ごとと呼び出し全体のタイムアウト**: `attemptTimeoutMs` は 1 回の試行を区切ります。HTTP は、選択されたエンドポイントへ送られる各 Fetch を、呼び出しからレスポンスボディの読み取り完了まで計測します。SSE はレスポンスヘッダーで止まり、WebSocket は `open` で止まります。HTTP 送信の前後のインターセプター処理（たとえば `401` のあとのトークン更新）と struct のデコードは計測対象外で、エンドポイントの責任としてカウントされることもありません。送信が完了したあとのインターセプター処理中に呼び出し元の期限が切れても、バランサーには `NET_TIMEOUT` ではなくエンドポイント自身の結果が報告されます。呼び出し元の `client({ signal: AbortSignal.timeout(ms) })` は、すべての試行**とバックオフの待ち**を対象にします。待ちのあいだにキャンセルすると、呼び出し元のキャンセル Fault が返り、次の pick は行われません。オプションは実行時には検証されません。
- **リトライで使えるエンドポイントがない場合**: リトライのラウンドで使えるエンドポイントがない場合（バランサーの pick が失敗した、または次のエンドポイントの URL が解決できない）、HTTP の呼び出しは `REQ_BUILD_FAILED` ではなく、直前の試行の Fault（たとえば `NET_UNREACHABLE`）を返します。
- **Finagle / Linkerd のリトライバジェット (`budget`)**: HTTP のみです。各クライアント構成がバジェットを所有し、同じ構成を使う派生クライアントだけがそれを共有します。バランサーを共有するクライアントは共有しません。デフォルトは `percentCanRetry: 0.2`、`minRetriesPerSecond: 10`、`ttlMs: 10000` で、元のトラフィックの 20% に予約分を加えたものです。クレジットとデビットは、10 個の TTL/10 スライスで遅延して期限切れになります。リトライは待つ前に引き出します。バジェットを使い切ると、待たず、リトライもしません。上限を外すには `budget: false` を設定します。SSE と WebSocket にバジェットはありません。HTTP のバジェットを共有すると、HTTP リトライのバーストが再接続を妨げるためです。
- **ブラウザのオフライン検知**: `navigator.onLine === false` の場合、接続失敗は `{ attempted: false }` と報告され、バランサーは進まず、HTTP のリトライも起きません。

後から渡した `withRetry` はポリシーを置き換えます。`withRetry()` と `withRetry(undefined)` は `withRetry({})` と同じように振る舞います。有効にしたあとリトライを無効にするには、`withRetry({ maxRetries: 0 })` を渡します。

### `withSSEReconnect` と `withWebSocketReconnect` からの移行

`withSSEReconnect` と `withWebSocketReconnect` は廃止され、別名はありません。`withRetry` が SSE と WebSocket を担い、リクエストオプションの `reconnect` は `retry` になりました。

- `attempts: N` は `maxRetries: N` になります。
- `shouldReconnect` は `shouldRetry` になります。コンテキストに `transport` と `retryable` が加わり、呼ばれるのはリトライが残っているあいだだけです。`shouldReconnect` と同様、メソッドの規則を含むデフォルトの規則を置き換えるため、`true` を返す関数は `POST` のストリームもリトライします。
- デフォルトが変わりました。SSE の `factor` は `1` から `2` へ、SSE の `maxDelayMs` は無制限から `30000` へ、`jitter` は両方のトランスポートで `0` から `0.2` になります。
- SSE のハンドシェイク: 0.6 では、2xx 以外のハンドシェイクはすべて、`shouldReconnect` を聞かずにストリームを終了していました。いまは `502`、`503`、`504` のハンドシェイクが接続拒否と同様にリトライされ、それ以外の 2xx 以外のハンドシェイクは `retryable: false` で `shouldRetry` に届きます。
- Fault コード: 2xx 以外のステータスで SSE ストリームを終える再接続ハンドシェイクは、いま `closed.code` に `HTTP_STATUS` を報告します。0.6 は `RES_DECODE_FAILED` を報告していましたが、`EventStreamFaultCode` にはもうありません。throw する `shouldRetry` は、どのトランスポートでも投げられた値を `cause` として `EXT_HOOK_FAILED` で呼び出しを終えます。throw する `shouldReconnect` は、SSE ストリームを `NET_UNREACHABLE` で終えていました。
- WebSocket のハートビート: 0.6 では、応答のないハートビートはエラーでセッションを終え、`shouldReconnect` には届きませんでした。いまは他と同じ中断です。`shouldRetry` は `retryable: true` と `cause` を受け取り、close の `code` はなく、`false` を返すと以前と同じようにそのエラーでセッションを終えられます。
- `withRetry` は HTTP もリトライします。HTTP の呼び出しを 1 回の試行に保つには、`context.transport === "http"` に対して `false` を返してください。

```ts
// Before
createClient(
  withEndpoint(url),
  withSSEReconnect({ attempts: 3, delayMs: 1000 }),
  withWebSocketReconnect({
    attempts: 3,
    shouldReconnect: ({ code }) => code !== 1008,
  }),
);
// After
createClient(
  withEndpoint(url),
  withRetry({
    maxRetries: 3,
    shouldRetry: (context) => {
      if (context.transport === "http") return false;
      if (context.transport === "websocket" && context.code === 1008)
        return false;
      return context.retryable;
    },
  }),
);
```

### ブラウザへのデプロイ時の境界

- ブラウザの CORS 失敗は Fetch に接続失敗として渡り、ホスト停止と区別できない `NET_UNREACHABLE` として報告されます。エンドポイント選択を進め、オプトインされた安全なメソッドのリトライを起こす可能性があるため、リトライの成功がプライマリリージョンの CORS 設定ミスを隠すことがあります。
- レスポンスに必要な CORS ヘッダーがなくても、POST はサーバーですでに処理されている場合があります。その場合、アプリケーションは書き込みが成功したか分からないまま `NET_UNREACHABLE` を受け取ります。POST はデフォルトでは再送されません。書き込みのリトライを明示的に有効にするには、レプリカ間でアプリケーションレベルの冪等性が必要です。
- ブラウザでは、サーバーに拒否された WebSocket アップグレード（たとえば `401`）は到達不能なエンドポイントと区別できず、`NET_UNREACHABLE` として報告されます。そのため、期限切れの認証情報によってエンドポイントが隔離されることがあります。
- Cookie のスコープはポートではなくホスト単位です。`localhost` の異なるポートにある 2 つのエンドポイントは Cookie を共有できますが、`localhost` と `127.0.0.1` は共有しません。複数オリジンのエンドポイント集合では、Cookie／トークンと CORS の認証情報ポリシーを意図的に設計する必要があります。`withCredentials(true)` は Cookie のスコープを変更しません。
- 明示的なオフラインヒント（`navigator.onLine === false`）は、エンドポイントへの帰属と接続失敗によるリトライを抑制します。これはブラウザのヒントにすぎず、信頼できる到達性チェックではありません。

## 3. 失敗による隔離と独自のヘルス関数 (`outlierDetection`)

Defjs には、健全なエンドポイントという組み込みの概念はありません。[`outlierDetection`](/ja-JP/api/core/outlierdetection) が行う処理は 2 つで、どちらも任意です。すべての組み込みバランサーは `outlierDetection` オプションでそれを受け取ります（`pickFirstBalancer`、`roundRobinBalancer`、`p2cBalancer` は、オブジェクトを渡さない限りオフです。デフォルトにするには `{}` です）。分類された失敗を数えてエンドポイントをしばらく隔離し、`isHealthy` 関数が拒否するエンドポイントをスキップします。

1. **失敗のカウント**: デフォルトの `isFailure` 規則は、code を持つ結果をすべて失敗として数えます（`NET_UNREACHABLE`、`NET_UNAVAILABLE`、`NET_SERVER_ERROR`、`NET_TIMEOUT`、`NET_BODY_INCOMPLETE`）。それが決めるのは、どの結果を隔離のカウントに入れるかだけであり、健全さの判断ではありません。`isFailure` を渡して置き換えられます。試行されたが code のない結果は連続回数をリセットし、帰属できない試行は連続回数を変えません。数えられる結果が `consecutiveFailures` 回（デフォルト `5` 回）連続すると、そのエンドポイントは隔離されます。カウントを止めるには `consecutiveFailures: 0` を設定します。
2. **時間による隔離**: エンドポイントは `min(minPenaltyMs × level, maxPenaltyMs)`（`1000ms` から `60000ms`）に、最大 `50%` の一様な正のジッターを加えた期間だけ隔離されます。基本時間とジッターの合計が `maxPenaltyMs` を超えることはありません。`level` は gRPC の外れ値検出（gRFC A50）の隔離倍率です。隔離のたびに 1 加算され、成功では決してクリアされず、隔離が終わった時点から数えて、隔離のない `10` 秒ごとに 1 減ります。時間が来るとエンドポイントは再び選択可能になります。それをプローブしたり、復旧したと判断したりするものはありません。それでも失敗すれば、数えられる結果がさらに `consecutiveFailures` 回続いたあと、より長い時間だけ再び隔離されます。そのため、接続を受け入れてから切るエンドポイントは、失敗が 1 レベルの減衰より速く返る限り、1 秒、2 秒、3 秒と、`maxPenaltyMs` まで隔離されます。隔離の前、または隔離されているあいだに始まった試行の結果は、エンドポイントが再び選択可能になったあとに届いても無視されるため、遅れた結果が新たに隔離することはありません。隔離の終了は次の pick で時計と照合され、タイマーは動きません。
3. **`isHealthy`**: 唯一の健全さの判断です。同期で、現在隔離されていない各エンドポイントについて pick のたびに実行されます（隔離中のエンドポイントには聞かれません）。そのため、2 つ目のタブのように、アプリケーションが維持する状態を安く読む処理にしてください。`false` を返したエンドポイントは選ばれません。`true` を返しても隔離は終わりません。エンドポイントが選択可能なのは、隔離されておらず、かつ `isHealthy` が拒否しないときだけです。throw は Defjs が捕捉しません。pick は `REQ_BUILD_FAILED` で失敗し、投げられた値が `cause` になります。
4. **履歴の上限**: ヘルス履歴は、派生クライアントをまたいで、少なくとも 256 エンドポイント、かつ少なくとも現在のメンバー数を保持します。まず問題のないエントリや期限切れエントリを最終使用が古い順に削除し、次に部分的な失敗シーケンスを削除します。未期限切れの隔離を削除するのは、保持中の全エントリが隔離されている場合だけで、そのときは最も古いエントリを削除します。ある呼び出しでエンドポイントを省くだけでは、そのペナルティはリセットされません。P2C の負荷履歴も少なくとも 256 件、かつ少なくとも現在のメンバー数を保持するため、256 エンドポイントを超えるリストでもすべての推定値が残ります。処理中のエントリより先にアイドル状態のエントリを削除します。忘れられたエンドポイントは `defaultRttMs` から再開します。Pick-first のシャッフルキーは少なくとも 256 件（および少なくとも現在のメンバー）を LRU キャッシュに保持するため、忘れられたエンドポイントが戻ると新しいキーを受け取ります。加重ラウンドロビンはクライアントのメンバーの現在値を保持します。1 回の選択から外れたエンドポイント（ヘルスフィルタによる選択）も、nginx がダウンしたピアをスキップするのと同様に値を保ち、メンバーから外れたエンドポイントの値だけが破棄されます。コピーした重み設定は構築時に固定されます。時間の計測には、利用可能ならプラットフォームの単調な Performance クロックを使い、`Date.now()` はフォールバックとしてのみ使用します。
5. **パニックモード（フェイルオープン）**: `isHealthy` が、隔離されていないすべてのエンドポイントを不健全と判定した場合、バランサーは `isHealthy` を無視して、隔離されていないエンドポイントから選びます。設定されたすべてのエンドポイントが隔離されている場合にのみ、ローカルでトラフィックをすべて破棄するのではなく、クライアントの候補リスト全体へフェイルオープンします。

## 4. トランスポートのアカウンティングライフサイクル (`pick` → `start` → `end` → `done`)

カスタムバランサーは `info.endpoints` に含まれる文字列のいずれかを完全一致で選ぶ必要があります。これによりヘルスフィルタリングが維持されます。

カスタムバランサーは、同期の `pick(info)` と、任意の `start()`、`end(info)`、`done(info)` を実装します。ランタイムはこれらのコールバックをレシーバーなしで呼ぶため、`this` は `undefined` です。状態はクロージャ、アロー関数、または束縛した関数に置いてください。同期的な throw は試行を変えません。ランタイムが `reportError` を定義している場合はそれで報告され、処理されない報告は、エラーハンドラーのない Bun や Deno のプロセスを終了させることがあります。Node.js は `reportError` を定義しないため、そこでは throw が内部に留まります。`PickInfo` には、1 回の pick の候補 `endpoints`（ラッパーによるフィルタで短くなります）、`members`（クライアントの全エンドポイントリストで、どの試行でも同じです。状態を持つバランサーは順序と状態をこれをキーに管理します）、定義の任意の `operation` があり、トランスポートを区別するフィールドはありません。トランスポートは自身の情報を中立な `DoneInfo.code` へ変換します。組み込みバランサーは `status` を読みません。この生のレスポンス情報は、カスタムバランサーのためだけに残されます。`start` は試行の前、`end` はピアの応答が始まるときか応答前の失敗のとき、`done` は完了時に実行されます。したがって、後から発生するボディの失敗は、それ以前の `end` のサンプルを変えずに、最終的な code を変えることがあります。

| 物理トランスポートの結果                                                                  | 最終的な `done(info)` サンプル                             |
| ----------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| HTTP/SSE のレスポンスステータス 502、503 または 504                                       | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| HTTP/SSE のその他の 500 以上のレスポンスステータス                                        | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP/SSE のレスポンスステータス 2xx、3xx または 4xx（429 を含む）                         | `{ attempted: true, status }`                              |
| HTTP レスポンスボディがストリーム途中で切断                                               | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE ハンドシェイクに成功後、ストリームの `reader.read()` が reject                        | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| SSE の正常な EOF、イベントストリームではない 2xx ハンドシェイク、またはバッファ上限       | `{ attempted: true, status }`                              |
| 接続済み WebSocket がコード `1006` または `1015` で切断（クローズフレームが届かなかった） | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 接続済み WebSocket がコード `1012` または `1013` で切断                                   | `{ attempted: true, code: "NET_UNAVAILABLE" }`             |
| WebSocket のハートビート ACK がタイムアウト                                               | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 接続済み WebSocket がそれ以外のコードでクローズ（`wasClean` の値は問わない）              | `{ attempted: true }`                                      |
| 呼び出し元のキャンセル、またはストリーム／ソケットの手動クローズ                          | `{ attempted: false }`                                     |
| `fetch` がストリーミング HTTP リクエストボディをネットワークエラーで reject               | `{ attempted: false }`                                     |
| 試行開始後に呼び出し元の期限が超過                                                        | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

ストリーミングの HTTP リクエストボディは、呼び出し元が渡す `ReadableStream` です。`fetch` は、接続が拒否された場合も HTTP/1.1 の場合も、リダイレクトがストリームを再送できない場合も、CORS プリフライトが失敗した場合も、元のストリームが throw した場合も、同じネットワークエラーで reject します。そのため、そのエラーはエンドポイントが停止していることを確実には示しません。呼び出しはそれでも `NET_UNREACHABLE` で失敗しますが、バランサーが受け取るのは `{ attempted: false }` です。throw する進捗コールバック（`EXT_OBSERVER_FAILED`）と同じです。その代償として、ストリーミングアップロードだけでは停止したエンドポイントを検出できません。`pickFirst` をそこから切り替えず、`outlierDetection` にも数えられず、拒否されたストリーミングアップロードはリトライされません。`ReadableStream` ボディは、`shouldRetry` が聞かれる前にリトライの流れを終えるからです。ハンドシェイクのデコード失敗は、ハンドシェイクのステータスから導いた中立な結果を残します（たとえばステータス `503` の `NET_UNAVAILABLE`）。不完全な HTTP ボディは、ゲートウェイ応答であっても、代わりに `NET_BODY_INCOMPLETE` とその生の status を残します。他の code 付きの結果と同様、デフォルトの外れ値検出ではこれも失敗としてカウントされます。送信できなかったハートビート（`message()` の throw やシリアライズ失敗）はローカルの事象で、中立です。
