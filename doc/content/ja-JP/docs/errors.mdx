# エラーハンドリング

Defjs では、リクエスト、トランスポート、デコードの各処理において、呼び出し元で例外を throw することはありません。すべての操作はエラーファーストのタプル（`[error, ...]`）を返し、`error` は `null` または型付けされた `Fault`（`error.code` で判別可能なネイティブの `Error` インスタンス）になります。

TypeScript が拒否する呼び出しは例外です。結果は規定されておらず、`Fault` でもありません。実際には、通常はプラットフォームの `TypeError` で reject します。

### HTTP 失敗時に `error` がレスポンスメタデータを保持する理由

HTTP 通信の失敗時、返されるタプルは `[error, undefined, undefined]` になります。受信できたレスポンスメタデータ（`status`、`statusText`、`headers`、`url`）はすべて `error.response` に直接格納されるため、コンテキストを損なうことなく `error` 単体をロガーやエラーハンドラーへ渡すことができます。

## 2. Fault クラスと網羅的な Fault コード体系

最初のアンダースコア `_` の前にあるプレフィックスが Fault クラス（`HTTP`、`REQ`、`NET`、`RES`、`EXT`、`CAP`、`ENV`）を表し、完全な `code` は TypeScript の網羅的な `switch` 分岐が可能な閉じた union 型を形成しています。

| クラス | Fault コード                                                           | 意味と対処法                                                                                                                                                                                                                                                                                      |
| ------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HTTP` | `HTTP_STATUS`                                                          | サーバーが非 `2xx` ステータス（`3xx`、`4xx`、`5xx`）を返し、宣言された `error` struct のデコードに成功。                                                                                                                                                                                          |
| `REQ`  | `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`                                | 入力値の検証失敗、URL/パスの不正、`builder` 内での例外、またはリクエストを構築できなかった場合（HTTP: 使用済みのボディストリーム、不正または禁止されたメソッド、GET/HEAD のボディ、不正な `Content-Type`。HTTP と SSE: 認証情報を含む URL、プラットフォームが拒否するヘッダー値）。リトライ不可。 |
| `RES`  | `RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED`, `RES_STRUCT_MISMATCH`   | サーバーのレスポンスが、宣言されたメディアタイプ、データ表現、または `struct` スキーマ契約に違反。                                                                                                                                                                                                |
| `NET`  | `NET_ABORTED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `NET_BODY_INCOMPLETE` | 呼び出し元の中止（`NET_ABORTED`）、期限切れ（`NET_TIMEOUT`）、接続失敗、またはストリームの途中切断。                                                                                                                                                                                              |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`     | アプリケーションのインターセプター、フック、または進捗／状態オブザーバーが自身のエラーを throw したか、インターセプターが `AbortSignal` ではない `signal` を `next()` に渡した。                                                                                                                  |
| `CAP`  | `CAP_BUFFER_EXCEEDED`                                                  | SSE フレームバッファが設定上限を超過。                                                                                                                                                                                                                                                            |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | 実行環境（ホストランタイム）に必要な Web API が不足（例: Firefox でのリクエストボディのストリーミング）。                                                                                                                                                                                         |

コードが表すのは、何が失敗したかであり、その値を誰が渡したかではありません。HTTP では、プラットフォームが構築できないリクエストは、不正な値が `builder`、クライアント構成、インターセプターのどれから来ても `REQ_BUILD_FAILED` になります。SSE は、ヘッダー値、不正な URL、認証情報を含む URL に同じ規則を適用し、初回の試行とすべての再接続で適用します。最後のものはライブラリ自身が検査します。Bun はそのような URL を受け入れ、リクエストを送ってしまうためです。プラットフォームが拒否し得るその他の値は、SSE と WebSocket ではライブラリが検査しません（SSE では不正なメソッド、WebSocket では認証情報を含む URL、不正なサブプロトコル、未対応のスキーム）。そこでの拒否は、プラットフォームのエラーを `cause` とする `NET_UNREACHABLE` として報告され、その値を受け入れるランタイム（不正な SSE メソッドに対する Bun）はリクエストを送ります。`EXT_INTERCEPTOR_FAILED` が対象とするのはインターセプター自身の振る舞いです。インターセプターが投げるエラー、または `AbortSignal` ではない `signal`（リクエストの内容ではなく、キャンセルの経路）です。

### Fault コードごとの Fault プロパティ

| Fault コード   | `status` | `response`                                              | `data`                                            | `cause`                            |
| -------------- | -------- | ------------------------------------------------------- | ------------------------------------------------- | ---------------------------------- |
| `HTTP_STATUS`  | `number` | `DecodedResponse<TErr>` または `HttpMeta`               | デコードされた `error` struct、または `undefined` | 根本原因（存在する場合）           |
| `RES_*`        | `number` | `HttpMeta`（**`body` フィールドなし**）                 | なし                                              | `StructError` またはパーサーエラー |
| その他のコード | なし     | ヘッダー受信済みなら `HttpMeta`、それ以外は `undefined` | なし                                              | 根本の `Error` / 中止理由          |

## 4. SSE と WebSocket における接続開始前エラー vs 接続後エラー

長時間接続されるトランスポートでは、操作の戻り値タプルは **接続開始前（startup）** の失敗（ストリームやソケットが開く前）を報告します。接続が確立された後のランタイムエラーは、ハンドルやセッションのライフサイクルを通じて通知されます。

| トランスポート | 接続開始前の失敗（タプルで返却）                                                                                                                                                  | 接続確立後の失敗（タプル解決後）                                                                                                                                                                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **HTTP**       | すべての失敗が操作のタプルを 1 回だけ確定させます。                                                                                                                               | 該当なし                                                                                                                                                                                                                                                                 |
| **SSE**        | 非 `2xx`（`HTTP_STATUS`、または宣言された `error` ボディをデコードできないときのデコード Fault）、または不正なメディアタイプの `2xx` ハンドシェイク（`RES_MEDIA_TYPE_INVALID`）。 | 非同期イテレーターが拒否され、`stream.closed` が `{ kind: 'error', code }` で確定します。                                                                                                                                                                                |
| **WebSocket**  | 接続確立前のクローズ、コンストラクターの失敗、またはハンドシェイク中のアボート。                                                                                                  | 致命的でないフレームエラーは `session.onRuntimeError` を発火。致命的エラーは `session.receive` を拒否し、`session.closed` が `{ kind: 'error', cause }` で確定します。ハートビートのタイムアウトやリトライ回数の使い切りでは、通常の実行時 `Error` が cause のままです。 |
