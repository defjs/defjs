# インターセプター

インターセプターは、SDK の操作定義に手を加えることなく、認証ヘッダーの付与、リクエストの署名、メンテナンスモード時の短絡応答、`Retry-After` の処理といった横断的な実行ポリシーをアプリケーション側の `Client` にアタッチします。

入力値の検証と `builder` による配置はインターセプターチェーンの実行 **前** に行われ、HTTP ステータスに応じた振り分けと `output` / `error` の struct バリデーションはチェーンの実行 **後** に行われます。[操作インターセプター](#operation-interceptors)は、そのすべてを包みます。

## 1. インターセプターの作成と登録

各トランスポートごとに専用の型付きファクトリ（`createHttpInterceptor`、`createSSEInterceptor`、`createWebSocketInterceptor`）が用意されています。これらを任意の組み合わせで `withInterceptors(...)` に渡します。

### インターセプターパイプラインのルール

- **オニオン構造の実行順序**: インターセプターは、往路（`before next(req)`）では登録された順序で実行され、復路（`after await next(req)`）では逆順で実行されます。広範なロギングやトレーシングのインターセプターは、特定の認証やリトライのインターセプターよりも外側に配置してください。
- **リクエストを不変に保つ原則**: 必ず `req.headers` を複製し（`new Headers(req.headers)`）、新しいリクエストオブジェクト（`{ ...req, headers }`）を `next(...)` に渡してください。これにより、外側のリトライ処理が常にクリーンな初期ヘッダーを参照できます。
- **`content-type` と `bodyContentType`**: Defjs は推論されたボディの Content-Type を、`req.headers` を変更することなく `req.bodyContentType` に保持します。リクエスト署名処理では、`req.headers.get("content-type") ?? req.bodyContentType` を参照してください。インターセプターが `req.body` を別の形式に置き換える場合は、明示的に `content-type` ヘッダーを設定してください。

## 2. `makeResponse` によるリクエストの短絡（ショートサーキット）

HTTP インターセプターは、`next(req)` を呼び出さずに `makeResponse(...)` で生成した擬似レスポンスを返すことができます。

<include cwd lang="typescript">

</include>

`makeResponse` はバリデーションをバイパスするものでは **ありません**。生成されたレスポンスに対しても、操作で定義されたメディアタイプのチェック、ステータス分岐（`2xx` vs 非 `2xx`）、および `output` / `error` の struct バリデーションが通常どおり厳格に適用されます。

## 3. リトライと `Retry-After`

HTTP リトライはデフォルトで無効です。接続失敗、タイムアウト、または `statusCodes` に含まれるステータス（デフォルトでは `429`、`502`、`503`、`504`）を、`429` と `503` に対するネイティブの RFC 9110 `Retry-After` 対応（`retryAfter: true`、`maxRetryAfterMs: 60_000`）付きでリトライするには、[`withRetry()`](/ja-JP/docs/load-balancing#retries) を使います。遅延のあと、バランサーに選び直させ、リクエストを再構築して、インターセプターチェーン全体を再実行します。

`builder` や外側のインターセプターを再実行せず選択済みエンドポイント上でリトライしたい場合、`Retry-After` がないときにフォールバック遅延を補いたい場合、あるいはフェイルファストせず待機時間に上限を設けたい場合など、アプリケーションが**同一エンドポイント上のカスタム**ステータス処理を必要とするときは、インターセプターで直接 `next(request)` をループできます。

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **2 層のリトライ**: この `next(request)` ループは選択済みのエンドポイントに留まり、`builder` や外側のインターセプターを再実行しません。接続失敗、エンドポイント間のフェイルオーバー、およびデフォルトの `429`/`502`/`503`/`504` ポリシーは `withRetry` が担います。
- **組み込み vs カスタムの `Retry-After` ポリシー**: Core の `withRetry()` はデフォルトで `429` と `503` に対して RFC 9110 の `Retry-After` に従います（サーバーが要求する遅延が `maxRetryAfterMs` を超えると、リトライせず即座にフェイルファストします）。上のレシピのようなカスタムインターセプターで `429` を処理する場合は、二重リトライを防ぐため `withRetry({ retryAfter: false })` を構成する（または `statusCodes` から `429` を外す）ようにしてください。レシピの 30 秒の上限と 250 ms のフォールバックはアプリケーション側の選択であり、より長いサーバー指定の遅延に上限をかけると、要求より早くリトライする可能性があります。
- **401 と書き込み**: [Bearer 更新レシピ](/ja-JP/recipes/refresh-bearer-once) は JSON POST を 2 回送信する場合があります。業務処理前の認証拒否と、安定した冪等性キーによるサーバー側の重複排除を必須とするか、書き込みの自動再送を行わないでください。ストリームのリクエストボディは再送されません。
- **トランスポート例外のハンドリング**: ネットワークエラーが発生した場合、`next(request)` は reject されます（ステータス 0 のレスポンスは存在しません）。この拒否を捕捉して再度 throw することで、元の `NET_*` Fault コードが保持されます。
- **送れないリクエスト**: HTTP インターセプターでは、プラットフォームがリクエストを拒否したとき（不正または禁止されたメソッド、GET または HEAD のボディ、認証情報を含む URL、不正な `Content-Type`）、または `finalizeHeaders` フックが throw したとき、`next(request)` はライブラリの `BodyFailure` ラッパーではなく、プラットフォーム自身のエラー（`TypeError`）またはフックが投げた値で reject します。それを再 throw すると Fault コード（`REQ_BUILD_FAILED` または `EXT_HOOK_FAILED`）が保たれ、別のエラーを throw すると失敗は自分のものになります（`EXT_INTERCEPTOR_FAILED`）。トランスポートの周囲で見つかるその他の失敗は、引き続き `BodyFailure` として `next(request)` に届きます。読めない、デコードできない、またはメディアタイプに合わないレスポンスボディ、途中で切れたボディ、throw するアップロード進捗オブザーバー（`EXT_OBSERVER_FAILED`）です。後者はリクエストが送られる前に起き得ます。
- **インターセプター内での例外 throw**: インターセプター自身のハンドルされていない例外が throw された場合（または `AbortSignal` ではない `signal` を `next()` に渡した場合）、操作のタプルは `EXT_INTERCEPTOR_FAILED` になり、`err.cause` にその原因が設定されます。`ERR_ABORTED` または `ERR_TIMEOUT` を throw した場合は、それぞれ `NET_ABORTED` または `NET_TIMEOUT` になります。

SSE では、`next()` を繰り返し呼ぶインターセプターより `withRetry` を優先してください。インターセプターの `next()` を複数回呼ぶと、置き換えられたストリームのエンドポイント帰属と再選択が無効になります。これは、イテレーターの `next()` でイベントを消費することとは無関係です。

## 4. WebSocket セッションのラップ

WebSocket インターセプターが `next(req)` を呼び出せるのは **最大 1 回** です。返された `WebSocketSessionLike` をラップする際は、一過性のスナップショットをオブジェクトスプレッド展開するのではなく、ライブゲッター（`state`、`connection`、`bufferedAmount`）、`close`、`closed`、`receive`、`[Symbol.asyncDispose]()` を適切に委譲（delegate）してください。

## 5. 操作呼び出し全体の観測 [#operation-interceptors]

トランスポートインターセプターが見るのは一度に 1 つのリクエストだけです。検証に失敗した入力はそこに届かず、リトライのたびに再実行され、レスポンスのデコードはそれが返ったあとに行われます。`getOrder(client, input)` が呼ばれた瞬間からタプルが解決されるまで、呼び出しそのものを観測するには `createOperationInterceptor` を使います。

<include cwd lang="typescript">
  examples/api/create-operation-interceptor.ts#example
</include>

- **見えるもの**: `call` は定義を表し、`transport`（`"http"`、`"sse"`、`"websocket"`）、`method`、`path` テンプレート、`meta` を持ちます。入力もリクエストも持ちません。どちらもまだ存在しないためです。`next()` は操作のタプルで解決されるので、`err` は最終的な Fault です。`REQ_INPUT_INVALID`、`REQ_BUILD_FAILED`、`HTTP_STATUS`、`RES_STRUCT_MISMATCH` などです。
- **観測するだけで、変更はしない**: `next()` は引数を取らず、2 回目の `next()` は呼び出しを再実行せずに同じ promise を返し、関数は `next()` が解決した値でしか解決できません。リクエストやレスポンスの変更はトランスポートインターセプターで行ってください。
- **順序**: 操作インターセプターはすべてのトランスポートインターセプターの外側で、登録順に実行されます。`next()` の前後で動くコード（たとえば OpenTelemetry の `context.with`）は、トランスポートインターセプターを含む呼び出し全体で有効です。
- **ストリームとセッション**: SSE や WebSocket の呼び出しは、ストリームまたはセッションが開いた時点で解決されます。そのあとに起きることは、その `closed` を通じて観測します。
- **失敗**: throw や reject があると、操作は `EXT_INTERCEPTOR_FAILED` で解決され、投げられた値が `cause` になります。呼び出しがすでに開いていたストリームやセッションは閉じられます。

## 6. 組み込みファクトリとヘルパー

| エクスポート                                   | トランスポート | 説明                                                                                                                                                              |
| ---------------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP           | `(req, next) => Promise<HttpResponse<unknown>>` をラップ                                                                                                          |
| `createSSEInterceptor(fn)`                     | SSE            | `(req, next) => Promise<EventStreamHandle<unknown>>` をラップ                                                                                                     |
| `createWebSocketInterceptor(fn)`               | WebSocket      | `(req, next) => Promise<WebSocketSessionLike>` をラップ                                                                                                           |
| `createOperationInterceptor(fn)`               | すべて         | 操作呼び出し全体を包む `(call, next) => Promise<result>` をラップ                                                                                                 |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP           | リクエストごとに呼ばれる同期の認証情報プロバイダーから `Authorization: Basic ...` を注入                                                                          |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE            | SSE ハンドシェイク時に `Authorization: Basic ...` を注入                                                                                                          |
| `concurrencyLimitHttpInterceptor(options)`     | HTTP           | バケットごとに同時実行中の試行数を制限（`ConcurrencyLimitInterceptorOptions`）。`maxQueue` まで FIFO キューイングし、超過時は `BulkheadOverflowError` で拒否      |
| `idempotencyKeyHttpInterceptor(options?)`      | HTTP           | 状態変更メソッド（`POST`、`PATCH`）に冪等性キーヘッダー（`IdempotencyKeyInterceptorOptions`、デフォルト `Idempotency-Key`）を注入し、`req.correlationId` を再利用 |

`concurrencyLimitHttpInterceptor` は `withRetry` のバックオフ待機中にパーミットを解放するため、リトライがバルクヘッドをデッドロックさせることはなく、`maxQueue` を超えた場合は `BulkheadOverflowError` をスローします（`{ attempted: false }` 付きの `EXT_INTERCEPTOR_FAILED` として返ります）。詳細は [Interceptors API リファレンス](/ja-JP/api/interceptors) を参照してください。
