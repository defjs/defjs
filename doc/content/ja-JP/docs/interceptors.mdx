# インターセプター

インターセプターは、SDK の操作定義に手を加えることなく、認証ヘッダーの付与、リクエストの署名、メンテナンスモード時の短絡応答、`Retry-After` の処理といった横断的な実行ポリシーをアプリケーション側の `Client` にアタッチします。

入力値の検証と `builder` による配置はインターセプターチェーンの実行 **前** に行われ、HTTP ステータスに応じた振り分けと `output` / `error` の struct バリデーションはチェーンの実行 **後** に行われます。

## 1. インターセプターの作成と登録

各トランスポートごとに専用の型付きファクトリ（`createHttpInterceptor`、`createSSEInterceptor`、`createWebSocketInterceptor`）が用意されています。これらを任意の組み合わせで `withInterceptors(...)` に渡します。

### インターセプターパイプラインのルール

- **オニオン構造の実行順序**: インターセプターは、往路（`before next(req)`）では登録された順序で実行され、復路（`after await next(req)`）では逆順で実行されます。広範なロギングやトレーシングのインターセプターは、特定の認証やリトライのインターセプターよりも外側に配置してください。
- **リクエストを不変に保つ原則**: 必ず `req.headers` を複製し（`new Headers(req.headers)`）、新しいリクエストオブジェクト（`{ ...req, headers }`）を `next(...)` に渡してください。これにより、外側のリトライ処理が常にクリーンな初期ヘッダーを参照できます。
- **`content-type` と `bodyContentType`**: Defjs は推論されたボディの Content-Type を、`req.headers` を変更することなく `req.bodyContentType` に保持します。リクエスト署名処理では、`req.headers.get("content-type") ?? req.bodyContentType` を参照してください。インターセプターが `req.body` を別の形式に置き換える場合は、明示的に `content-type` ヘッダーを設定してください。

## 2. `makeResponse` によるリクエストの短絡（ショートサーキット）

HTTP インターセプターは、`next(req)` を呼び出さずに `makeResponse(...)` で生成した擬似レスポンスを返すことができます。

<include cwd lang="typescript">

`makeResponse` はバリデーションをバイパスするものでは **ありません**。生成されたレスポンスに対しても、操作で定義されたメディアタイプのチェック、ステータス分岐（`2xx` vs 非 `2xx`）、および `output` / `error` の struct バリデーションが通常どおり厳格に適用されます。

## 3. リトライと `Retry-After`

HTTP リトライはデフォルトで無効です。接続失敗、タイムアウト、または `502`、`503`、`504` を別のエンドポイントでリトライするには、[`withRetry()`](/ja-JP/docs/load-balancing#retries) を使います。バックオフの遅延のあと、バランサーに選び直させ、リクエストを再構築して、インターセプターチェーン全体を再実行します。

代わりにアプリケーションのインターセプターで、`429` や `Retry-After` など、同じエンドポイントに対するステータス処理を実装することもできます。

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **2 層のリトライ**: この `next(request)` ループは選択済みのエンドポイントに留まり、`builder` や外側のインターセプターを再実行しません。接続失敗と `502`/`503`/`504` は `withRetry` に任せます。
- **`Retry-After` ポリシー**: Core の `withRetry` はこのヘッダーを読みません。レシピの 30 秒の上限と 250 ms のフォールバックはアプリケーション側の選択です。サーバーが求める遅延がより長い場合、上限によって指定より早くリトライする可能性があります。それを許容できなければ、指定された遅延全体を待つか、そのままレスポンスを返してください。
- **401 と書き込み**: [Bearer 更新レシピ](/ja-JP/recipes/refresh-bearer-once) は JSON POST を 2 回送信する場合があります。業務処理前の認証拒否と、安定した冪等性キーによるサーバー側の重複排除を必須とするか、書き込みの自動再送を行わないでください。ストリームのリクエストボディは再送されません。
- **トランスポート例外のハンドリング**: ネットワークエラーが発生した場合、`next(request)` は reject されます（ステータス 0 のレスポンスは存在しません）。この拒否を捕捉して再度 throw することで、元の `NET_*` Fault コードが保持されます。
- **送れないリクエスト**: HTTP インターセプターでは、プラットフォームがリクエストを拒否したとき（不正または禁止されたメソッド、GET または HEAD のボディ、認証情報を含む URL、不正な `Content-Type`）、または `finalizeHeaders` フックが throw したとき、`next(request)` はライブラリの `BodyFailure` ラッパーではなく、プラットフォーム自身のエラー（`TypeError`）またはフックが投げた値で reject します。それを再 throw すると Fault コード（`REQ_BUILD_FAILED` または `EXT_HOOK_FAILED`）が保たれ、別のエラーを throw すると失敗は自分のものになります（`EXT_INTERCEPTOR_FAILED`）。トランスポートの周囲で見つかるその他の失敗は、引き続き `BodyFailure` として `next(request)` に届きます。読めない、デコードできない、またはメディアタイプに合わないレスポンスボディ、途中で切れたボディ、throw するアップロード進捗オブザーバー（`EXT_OBSERVER_FAILED`）です。後者はリクエストが送られる前に起き得ます。
- **インターセプター内での例外 throw**: インターセプター自身のハンドルされていない例外が throw された場合（または `AbortSignal` ではない `signal` を `next()` に渡した場合）、操作のタプルは `EXT_INTERCEPTOR_FAILED` になり、`fault.cause` にその原因が設定されます。`ERR_ABORTED` または `ERR_TIMEOUT` を throw した場合は、それぞれ `NET_ABORTED` または `NET_TIMEOUT` になります。

SSE では、`next()` を繰り返し呼ぶインターセプターより `withRetry` を優先してください。インターセプターの `next()` を複数回呼ぶと、置き換えられたストリームのエンドポイント帰属と再選択が無効になります。これは、イテレーターの `next()` でイベントを消費することとは無関係です。

## 4. WebSocket セッションのラップ

WebSocket インターセプターが `next(req)` を呼び出せるのは **最大 1 回** です。返された `WebSocketSessionLike` をラップする際は、一過性のスナップショットをオブジェクトスプレッド展開するのではなく、ライブゲッター（`state`、`connection`、`bufferedAmount`）、`close`、`closed`、`receive`、`[Symbol.asyncDispose]()` を適切に委譲（delegate）してください。

## 5. 組み込みファクトリとヘルパー

| エクスポート                                   | トランスポート | 説明                                                                                     |
| ---------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP           | `(req, next) => Promise<HttpResponse<unknown>>` をラップ                                 |
| `createSSEInterceptor(fn)`                     | SSE            | `(req, next) => Promise<EventStreamHandle<unknown>>` をラップ                            |
| `createWebSocketInterceptor(fn)`               | WebSocket      | `(req, next) => Promise<WebSocketSessionLike>` をラップ                                  |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP           | リクエストごとに呼ばれる同期の認証情報プロバイダーから `Authorization: Basic ...` を注入 |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE            | SSE ハンドシェイク時に `Authorization: Basic ...` を注入                                 |
