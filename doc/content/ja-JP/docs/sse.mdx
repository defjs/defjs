# SSE イベントストリーム

SDK は、`defineEventStream` を使用して Server-Sent Events（SSE）エンドポイントを宣言します。パス、任意の入力と builder、struct で型付けされた `events` 辞書、バッファやキューの制限を指定します。利用側アプリケーションはクライアント側で認証やオプトイン方式の再接続を設定し、ストリームを開いて型付けされたイベントを反復処理し、終了処理の責務を負います。

## 1. イベントストリームの定義と受信

開いた `EventStreamHandle` は、必ず `await using`（または `finally` ブロック内での `stream.close()` + `await stream.closed`）によって確実に解放してください。

<Tabs items={["sdk/orders-stream.ts", "app/watch-orders.ts", "Single-file quick look"]}>
<Tab value="sdk/orders-stream.ts">

```ts
import { defineEventStream, struct } from "@defjs/core";

export const watchOrders = defineEventStream({
  path: "/orders/events",
  operation: "orders.watch",
  events: {
    updated: struct.object({
      id: struct.number(),
      status: struct.string(),
    }),
  },
});
```

</Tab>
<Tab value="app/watch-orders.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { watchOrders } from "../sdk/orders-stream.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, stream] = await watchOrders(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = stream;
  for await (const event of active) {
    console.log(event.event, event.data.id, event.data.status);
    break;
  }
}

void main();
```

## 2. 接続ハンドシェイクとタプルの構造

操作を呼び出すと、初回の HTTP レスポンスが `2xx` であり、メディアタイプが `text/event-stream`、かつボディが読み取り可能であることを確認した後にのみ `[error, stream, startupOpen]` が解決されます。

- **非 `2xx` のハンドシェイク**: `HTTP_STATUS` を返します（定義で `error` struct が宣言されている場合は、デコードされた `error.data` が格納されます）。
- **不正なメディアタイプまたはボディ読み取り不可**: `RES_MEDIA_TYPE_INVALID` または `RES_DECODE_FAILED` を返します。
- **`startupOpen` と `stream.open` の違い**: タプルの 3 番目の要素（`startupOpen`）は初回の接続レスポンスのスナップショットです。ストリームが後に再接続した場合、`stream.open` は最新の接続情報へと動的に更新されます。

## 3. イベントのディスパッチとデコード

SSE フレームが到着したとき（WHATWG 仕様に基づき空行で区切られます）:

1. **イベントのルーティング**: 受信した `event:` フィールドに基づいて `events[eventName]` を選択します。マッチしない場合は、宣言されていれば `events.default` にフォールバックします。`event:` フィールドが省略されている場合は `"message"` がデフォルトになります。未宣言かつ `events.default` もないイベントは破棄されます。
2. **ペイロードのデコード**: `struct.string()` スキーマは生のテキスト `data:` をそのまま受け取ります。その他のすべての struct は、`data:` をまず JSON としてパースした上で struct バリデーションを実行します。
3. **無効なイベントの検知**: 無効なイベントや未宣言のイベントは、ストリームを中断することなく破棄されます。診断のためにクライアントへ `withSSEOnInvalidEvent(...)` をアタッチして安全に監視できます。

## 4. 再接続と Last-Event-ID [#reconnect]

SSE の自動再接続は **オプトイン（明示的な有効化）** です。`withSSEReconnect(...)` を設定しない限り、ネットワークの切断やストリーム読み取りエラーが発生するとストリームは即座に終了します。

<include cwd>examples/sse/reconnect.ts#example</include>

- **リトライ回数の上限 (`attempts`)**: `withSSEReconnect` にオプションオブジェクトを渡した場合、デフォルトは `3` 回です。ハンドシェイクが成功すると、試行回数カウンターとバックオフ指数はリセットされます。サーバーからの正常な EOF による切断は失敗とはみなされず、再接続はトリガーされません。
- **カーソルの追跡 (`Last-Event-ID`)**: イベントを区切る終端の空行が正常にパースされた時点でカーソルがコミットされ、再接続時に自動的に `Last-Event-ID` ヘッダーとして送信されます。
- **冪等性の安全性保護**: デフォルトでは、冪等な HTTP メソッド（`GET`、`HEAD`、`OPTIONS`、`PUT`、`DELETE`）のみが自動再接続されます。非冪等なメソッド（LLM のストリーミングリクエストなどの `POST` や `PATCH`）は、カスタムの `shouldReconnect` コールバックが明示的に `true` を返した場合にのみ再接続されます。`ReadableStream` のリクエストボディは初回の試行で消費されるため、再接続されることはありません。
- **ハンドシェイクのタイムアウト (`connectTimeoutMs`)**: Fetch の呼び出しからレスポンスヘッダー受信までの各接続ハンドシェイクに制限時間を設定します。すでに確立されたストリームの接続維持時間を制限するものではありません。

## 5. バッファとキューの制限

どちらの制限値も正の安全な整数である必要があります。いずれかの制限を超過すると致命的エラーとなります（`stream.closed` は `kind: "error"` で解決され、イテレーターは例外を拒否します。イベントが暗黙的に破棄されることはありません）。

| 定義オプション  | 制限対象                                                                     | 発生する致命的 Fault コード |
| --------------- | ---------------------------------------------------------------------------- | --------------------------- |
| `maxBufferSize` | 空行で区切られる前の未完了または過大な SSE フレームのバイトサイズ            | `CAP_BUFFER_EXCEEDED`       |
| `maxQueueSize`  | `for await` コンシューマーによる消費を待つ検証済みイベントのキューイング件数 | `CAP_QUEUE_OVERFLOW`        |

## 6. クローズと破棄 [#close-and-dispose]

ストリームを開いた呼び出し元が、リソース解放の責任を持ちます。`for await` ループを `break`、`return`、または throw で抜けるとストリームは自動的にクローズされます。あるいは、`await using` または `stream.close()` を明示的に使用できます。
