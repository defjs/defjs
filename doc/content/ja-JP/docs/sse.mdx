# SSE イベントストリーム

SDK は、`defineEventStream` を使用して Server-Sent Events（SSE）操作を宣言します。パス、任意の `input` と `builder`、struct で型付けされた `events` 辞書、バッファやキューの制限を指定します。利用側アプリケーションはクライアント側で認証やオプトイン方式の再接続を設定し、ストリームを開いて型付けされたイベントを反復処理し、ストリームのクローズを所有します。

## 2. 接続ハンドシェイクとタプルの構造

操作を呼び出すと、初回の HTTP レスポンスが `2xx` で、メディアタイプが `text/event-stream`、かつボディが読み取り可能であることを確認した後にのみ、`[error, stream, startupOpen]` が返されます。

- **非 `2xx` のハンドシェイク**: `HTTP_STATUS` を返します（定義で `error` struct が宣言されている場合は、デコードされた `error.data` が格納されます）。これは現在の操作に対する致命的な失敗であり、`shouldReconnect` は呼ばれません。ただし、`withSSEReconnect` を設定している場合の `502`、`503`、`504` のハンドシェイクは例外で、接続拒否と同様に第 4 節の再接続ルールでリトライされ、`shouldReconnect` が設定されていればそれが参照されます。リトライを使い切ると `HTTP_STATUS` で終了します。次の操作ではエンドポイントを新たに選択するため、バランサーが別のエンドポイントを選ぶ場合があります。
- **不正なメディアタイプまたはボディ読み取り不可**: `RES_MEDIA_TYPE_INVALID` または `RES_DECODE_FAILED` を返します。
- **`startupOpen` と `stream.open` の違い**: タプルの 3 番目の要素（`startupOpen`）は初回ハンドシェイクのレスポンスのスナップショットです。ストリームが後に再接続した場合、`stream.open` は動的に更新されます。再接続のハンドシェイクが 2xx 以外のステータスでストリームを終了させると、イテレーターは reject され、`stream.closed` は `HTTP_STATUS` を報告しますが、`stream.open.response.status` はそのステータスのままです。その最新のレスポンスステータスは `stream.open` で確認してください。

## 3. イベントのディスパッチとデコード

SSE フレームが到着したとき（WHATWG 仕様に基づき空行で区切られます）:

1. **イベントのルーティング**: ワイヤーの `event:` フィールドに基づいて `events[eventName]` を選択します。マッチしない場合は、宣言されていれば `events.default` にフォールバックします。`event:` フィールドが省略されている場合は `"message"` がデフォルトになります。未宣言かつ `events.default` もないイベントは破棄されます。
2. **ペイロードのデコード**: `struct.string()` スキーマは生のテキスト `data:` をそのまま受け取ります。その他のすべての struct は、`data:` をまず JSON としてパースした上で struct バリデーションを実行します。
3. **無効なイベントの検知**: 無効なイベントや未宣言のイベントは、ストリームを中断することなく破棄されます。件数を制限した診断のために、クライアントへ `withSSEOnInvalidEvent(...)` をアタッチできます。

## 4. 再接続と `Last-Event-ID` [#reconnect]

SSE の自動再接続は **オプトイン（明示的な有効化）** です。`withSSEReconnect(...)` を設定しない限り、ネットワークの切断やストリーム読み取りエラーが発生するとストリームは即座に終了します。

<include cwd>examples/sse/reconnect.ts#example</include>

- **試行回数の上限 (`attempts`)**: `withSSEReconnect` にオプションオブジェクトを渡した場合、デフォルトは `3` 回です。ハンドシェイクが成功するたびに試行回数カウンターとバックオフ指数がリセットされるため、`attempts: 1` でも各接続が正常に開けば、長時間のセッションで何度も物理接続を確立できます。サーバーからの正常な EOF は失敗では **なく**、再接続はトリガーされません。
- **カーソルの追跡 (`Last-Event-ID`)**: イベントを区切る終端の空行が正常にパースされた時点でカーソルがコミットされ、再接続時に自動的に `Last-Event-ID` ヘッダーとして送信されます。接続が正常終了した場合も失敗した場合も、部分的なフレームの `id` はコミットされません。再接続可能な読み取り／ネットワーク障害からの再開は、最後にコミットされた id から始まります。サーバー側で、そのカーソルからのリプレイを実装する必要があります。
- **冪等性の安全性保護**: デフォルトでは、冪等な HTTP メソッド（`GET`、`HEAD`、`OPTIONS`、`PUT`、`DELETE`）のみが自動再接続されます。非冪等なメソッド（LLM のストリーミングリクエストなどの `POST` や `PATCH`）は、カスタムの `shouldReconnect` コールバックが明示的に `true` を返した場合にのみ再接続されます。`ReadableStream` のリクエストボディは初回の試行で消費されるため、再接続されることはありません。
- **ゲートウェイのハンドシェイク**: `502`、`503`、`504` を返すハンドシェイクは、初回のオープンでも再接続でも、同じ再接続ルール（メソッド、`shouldReconnect`、`attempts`、`ReadableStream` ボディ）のもとで、接続拒否と同様にリトライされます。それ以外の 2xx 以外のハンドシェイクは引き続き致命的です。リトライを使い切った場合と、致命的な再接続ハンドシェイクは `HTTP_STATUS` で終了します。
- **ハンドシェイクのタイムアウト (`connectTimeoutMs`)**: 渡したときは、有限の正の数であり、2147483647（タイマー上限）以下でなければなりません。そうでなければ、操作は `REQ_OPTIONS_INVALID` を返します。Fetch の呼び出しからレスポンスヘッダー受信までの各接続ハンドシェイクに制限時間を設定します。すでに確立されたストリームの接続維持時間を制限するものではありません。このオプションは `withSSEReconnect({...})` のオプションオブジェクトの中にしか存在しません。このオブジェクトを渡すとデフォルトの `attempts: 3` で自動再接続が有効になるため、`connectTimeoutMs` だけを指定しても再接続が有効になります。ハンドシェイクだけに期限を設けたい場合は、`attempts: 0` を併せて指定してください。

## 5. バッファとキューの制限

デフォルトは `maxBufferSize: 64 * 1024` バイトと `maxQueueSize: 1024` イベントです。どちらの制限値も正の安全な整数である必要があります。デフォルトのハンドシェイク期限はなく、保留中の Fetch はプラットフォーム、呼び出し元のキャンセル、または明示的に設定された `connectTimeoutMs` を待ちます。いずれかの容量制限を超過すると致命的な失敗になります（`stream.closed` は `kind: "error"` で確定し、イテレーターは reject されます。イベントが暗黙的に破棄されることはありません）。

| 定義オプション  | 制限対象                                                                     | 最終的な Fault コード |
| --------------- | ---------------------------------------------------------------------------- | --------------------- |
| `maxBufferSize` | 空行で区切られる前の未完了または過大な SSE フレームのバイトサイズ            | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`  | `for await` コンシューマーによる消費を待つ検証済みイベントのキューイング件数 | `CAP_QUEUE_OVERFLOW`  |

## 6. クローズと解放 [#close-and-dispose]

ストリームを開いた呼び出し元が、リソース解放の責任を持ちます。`for await` ループを `break`、`return`、または throw で抜けるとストリームは自動的にクローズされます。あるいは、`await using` または `stream.close()` を明示的に使用できます。

`client({ signal })` 経由で渡された `signal` は、ストリームのライフタイム全体を制御します。確立済みのストリームを切断することなく初回の接続ハンドシェイクのみに制限時間を設けるには、上記サンプルの 2 つ目のタブのように `await watchOrders(...)` が返された直後にタイマーを解除するか、`withSSEReconnect` で `connectTimeoutMs` と `attempts: 0` を併せて指定してください（`connectTimeoutMs` だけでは 3 回の自動再接続も有効になります）。
