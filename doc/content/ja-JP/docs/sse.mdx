# SSE イベントストリーム

SDK は、`defineEventStream` を使用して Server-Sent Events（SSE）操作を宣言します。パス、任意の input と builder、struct で型付けされた `events` 辞書、バッファの制限を指定します。利用側アプリケーションはクライアント側で認証やオプトイン方式のリトライ（`withRetry`）を設定し、ストリームを開いて型付けされたイベントを反復処理し、ストリームのクローズを所有します。

## 2. 接続ハンドシェイクとタプルの構造

操作を呼び出すと、初回の HTTP レスポンスが `2xx` で、メディアタイプが `text/event-stream` であることを確認した後にのみ、`[error, stream, startupOpen]` が返されます。

- **非 `2xx` のハンドシェイク**: `HTTP_STATUS` を返します。`error` struct が宣言されていれば、`error.data` はデコードされたボディです。そのボディをデコードできないときは、HTTP と同じく、代わりにデコードの Fault になります。JSON の宣言が別のメディアタイプに出会ったときは `RES_MEDIA_TYPE_INVALID`（たとえばゲートウェイからの HTML の `503`）、読めないまたはパースできないボディは `RES_DECODE_FAILED`、struct に合わないボディは `RES_STRUCT_MISMATCH` です。その `status` と `response` はメタデータとしてハンドシェイクのステータスを持ち、`cause` が理由を持ちます。インターセプター、`shouldRetry`、再接続で失敗したストリームの `closed` は、そのレスポンスについて引き続き `HTTP_STATUS` を受け取り、その `cause` は同じ理由です。そのためゲートウェイの `503` は、ボディがどう見えてもリトライされます。`error` を宣言すると、クライアントは Fault を報告する前にハンドシェイクのボディを終わりまで読むので、サーバーは非 `2xx` のレスポンスをすべて終えるべきです。内容のないステータス（`304`）のとき、または JSON の宣言が JSON ではないメディアタイプに出会ったときは、ボディは読まれません。読まれて終わらないボディは、呼び出し元の `signal` が abort するか、プラットフォームが接続を切るまで、呼び出しを保留したままにします。切れた接続は読めないボディなので、呼び出しはプラットフォームの失敗を `cause` とする `RES_DECODE_FAILED` を返します。`attemptTimeoutMs` はその読み取りを区切りません。`error` の宣言がなければ、ボディは読まれずにキャンセルされます。`withRetry` がなければ、これで現在の操作は終わります。あれば、`502`、`503`、`504` のハンドシェイクは第 4 節の規則のもとで接続拒否と同様にリトライされ、それ以外のステータスは `retryable: false` とその `status` とともに `shouldRetry` に渡されるため、関数が別のことを言わない限りストリームは終わります。使い切った、または辞退されたリトライは `HTTP_STATUS` で終わります。次の操作ではエンドポイントを新たに選択するため、バランサーが別のエンドポイントを選ぶ場合があります。
- **不正なメディアタイプ**: メディアタイプが `text/event-stream` ではない `2xx` のハンドシェイクは `RES_MEDIA_TYPE_INVALID` を返します。`204` と `205` も含みます。
- **ボディがない場合**: `text/event-stream` でボディがない `2xx` のハンドシェイク（Node.js と Bun は `204` または `205` を null ボディとして公開します）は空のイベントストリームです。呼び出しは成功し、ストリームはすぐに `kind: "eof"` で終わり、リトライされることはありません。
- **`startupOpen` と `stream.open` の違い**: タプルの 3 番目の要素（`startupOpen`）は初回ハンドシェイクのレスポンスのスナップショットです。ストリームが後に再接続した場合、`stream.open` は動的に更新されます。再接続のハンドシェイクが 2xx 以外のステータスでストリームを終了させると、イテレーターは reject され、`stream.closed` は `HTTP_STATUS` を報告しますが、`stream.open.response.status` はそのステータスのままです。その最新のレスポンスステータスは `stream.open` で確認してください。

## 3. イベントのディスパッチとデコード

SSE フレームが到着したとき（WHATWG 仕様に基づき空行で区切られます）:

1. **イベントのルーティング**: ワイヤーの `event:` フィールドに基づいて `events[eventName]` を選択します。マッチしない場合は、宣言されていれば `events.default` にフォールバックします。`event:` フィールドが省略されている場合は `"message"` がデフォルトになります。未宣言かつ `events.default` もないイベントは破棄されます。
2. **ペイロードのデコード**: `struct.string()` スキーマは生のテキスト `data:` をそのまま受け取ります。その他のすべての struct は、`data:` をまず JSON としてパースした上で struct バリデーションを実行します。
3. **無効なイベントの検知**: 無効なイベントや未宣言のイベントは、ストリームを中断することなく破棄されます。件数を制限した診断のために、クライアントへ `withSSEOnInvalidEvent(...)` をアタッチできます。

## 4. リトライと `Last-Event-ID` [#reconnect]

SSE のリトライは **オプトイン（明示的な有効化）** で、HTTP と WebSocket と同じ `withRetry` ポリシーを使います。`withRetry(...)` を設定しない限り、ネットワークの切断やストリーム読み取りエラーが発生するとストリームは即座に終了します。リクエストオプションの `retry` は、1 回の呼び出しについてクライアントのポリシーを置き換えます。

<include cwd>examples/sse/reconnect.ts#example</include>

- **障害ごとの予算 (`maxRetries`)**: デフォルトは `3` です。ハンドシェイクが成功するたびにリトライ回数とバックオフ指数がリセットされるため、`maxRetries: 1` でも各接続が正常に開けば、長時間のセッションで何度も物理接続を確立できます。不安定に開閉するサーバーは `shouldRetry` で止めてください。サーバーからの正常な EOF は失敗では **なく**、リトライはトリガーされません。
- **カーソルの追跡 (`Last-Event-ID`)**: イベントを区切る終端の空行が正常にパースされた時点でカーソルがコミットされ、再接続時に自動的に `Last-Event-ID` ヘッダーとして送信されます。接続が正常終了した場合も失敗した場合も、部分的なフレームの `id` はコミットされません。再接続可能な読み取り／ネットワーク障害からの再開は、最後にコミットされた id から始まります。サーバー側で、そのカーソルからのリプレイを実装する必要があります。自身の `id:` フィールドを持たないイベントは、同じ接続でも再接続のあとでも、直近にコミットされた id を持ちます。空の `id:` フィールドはそれを消します。以降のイベントには `id` がなく、以降の再接続は `Last-Event-ID` を省きます。
- **冪等性の安全性保護**: デフォルトでは、`methods` に含まれるメソッド（`GET`、`HEAD`、`OPTIONS`、`TRACE`、`PUT`、`DELETE`）だけが自動的にリトライされます。それ以外のメソッド（LLM のストリーミングリクエストなどの `POST` や `PATCH`）がリトライされるのは、`methods` に加えるか、`shouldRetry` が `true` を返すときだけです。`context.retryable` を返す関数はデフォルトを保ちます。`ReadableStream` のリクエストボディは初回の試行で消費されるため、リトライされることはありません。
- **ゲートウェイのハンドシェイク**: `502`、`503`、`504` を返すハンドシェイクは、初回のオープンでも再接続でも、同じ規則（メソッド、`shouldRetry`、`maxRetries`、`ReadableStream` ボディ）のもとで、接続拒否と同様にリトライされます。それ以外の 2xx 以外のハンドシェイクは `retryable: false` で `shouldRetry` に渡され、デフォルトではストリームを終えます。使い切ったリトライと辞退されたリトライは `HTTP_STATUS` で終わります。この 3 つのステータスをリトライするのは、HTML 標準からの意図的な逸脱です。`EventSource` は、`200` のイベントストリームではない応答を失敗した接続として扱い、二度と試しません。Defjs は、一時的に使えないゲートウェイを、接続拒否と同じように扱います。
- **ハンドシェイクのタイムアウト (`attemptTimeoutMs`)**: 渡したときは、Fetch の呼び出しからレスポンスヘッダー受信までの各接続ハンドシェイクに制限時間を設定します。すでに確立されたストリームの接続維持時間を制限するものではありません。これは `withRetry` のオプションなので、`withRetry({ attemptTimeoutMs })` はデフォルトの `maxRetries: 3` でリトライもします。ハンドシェイクだけに期限を設けるには、`withRetry({ maxRetries: 0, attemptTimeoutMs })` と書いてください。期限が切れた試行は、リトライが別のエンドポイントを選べるよう、バランサーへ `NET_UNREACHABLE` を報告し、リトライを使い切ると `NET_TIMEOUT` で終わります。

### Node.js でのアイドルストリーム [#idle-streams]

Node.js 組み込みの `fetch`（undici）は、すべてのレスポンスボディに `bodyTimeout` を適用します。デフォルトは 300 秒で、データのチャンクとチャンクのあいだで測られます。それだけのあいだ沈黙した SSE ストリームは、サーバーが健全でもランタイムによって切られます。

- **見えるもの**: イテレーターはランタイム自身のエラーで reject します。メッセージが `terminated` の `TypeError` で、`cause.code` は `UND_ERR_BODY_TIMEOUT` です。`stream.closed` は `kind: "error"`、`code: "NET_UNREACHABLE"`、その `TypeError` を `cause` として解決します。`withRetry(...)` がなければ、ストリームはそこで終わります。あれば、ストリームは [リトライの規則](#reconnect) に従って `Last-Event-ID` を使って再開し、切られるたびにエンドポイントバランサーへ `NET_UNREACHABLE` の結果を 1 件報告します（[ロードバランシング](/ja-JP/docs/load-balancing) を参照）。
- **サーバー側の対処**: 300 秒を大きく下回る間隔で、`: keepalive` のようなコメント行を送ってください。HTML 標準の執筆上の注意は、古いプロキシがアイドル接続を切らないよう、およそ 15 秒ごとを提案しています。パーサーはコメント行を無視しますが、そのバイト列はタイマーをリセットします。
- **クライアント側の設定はない**: Defjs に独自のアイドルタイムアウトのオプションはありません。サーバーがコメント行を送れない場合、沈黙したままのストリームは、ランタイムの上限に達したときに切られます。

他のランタイムでのアイドル時の振る舞いは異なり、ここでは扱いません。

## 5. バッファとキューの制限

定義オプションは `maxBufferSize` の 1 つで、デフォルトは `64 * 1024` バイトです。イベントキューは設定できません。ライブラリが `for await` のコンシューマーを待って保持するのは、検証済みイベントが最大 1024 件です。デフォルトのハンドシェイク期限はなく、保留中の Fetch はプラットフォーム、呼び出し元のキャンセル、または明示的に設定された `attemptTimeoutMs` を待ちます。

| 制限                          | 制限対象                                                          | 上限に達したとき                                                                                             |
| ----------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `maxBufferSize`（オプション） | 空行で区切られる前の未完了または過大な SSE フレームのバイトサイズ | 致命的: `stream.closed` は `kind: "error"` と `CAP_BUFFER_EXCEEDED` で確定し、イテレーターは reject される   |
| イベントキュー（固定 1024）   | `for await` コンシューマーを待つ検証済みイベント                  | コンシューマーがイベントを取るまでレスポンスの読み取りが止まり、空きがないからイベントが捨てられることはない |

- **遅いコンシューマーが遅くするのはサーバーであり、ストリームではありません。** `Last-Event-ID` のリプレイのようにキューより大きいバーストも、すべて届けられます。キューが満杯のあいだライブラリはレスポンスの読み取りを止めるので、滞留は捨てられたりストリームを失敗させたりせず、接続の中に残ります。キューが保持するのは最大 1024 イベントに、空きを待つパース済みイベントが 1 つ加わります。
- **誰も見ていないストリームは読み取りを止めます。** 誰も反復しないストリームは、キューが満杯になると読み取りを止め、レスポンスの終わりまで読み進むまでは `stream.closed` が勝手に解決することはありません。`stream.close()`、abort、タイムアウトはそれでも解決し、close または abort はキューにあるイベントを捨てます。ストリームがもう不要なら、`stream.close()` を呼ぶか `await using` を使ってください。
- **失敗は、すでに受け取ったものを残します。** ストリームがエラーまたはタイムアウトで終わるとき、すでにキューにあったイベントは届けられ、呼び出し元が先にストリームを止めない限り（第 6 節を参照）、イテレーターは最後の 1 件のあとに reject します。`stream.closed` は接続が終わったときに解決し、それはイテレーターがすべてのイベントを読む前であり得ます。接続が失敗したときにレスポンスボディにまだ読まれていないバイトは届けられず、`Last-Event-ID` も進めないため、リトライが有効ならサーバーはコミット済みのカーソルからリプレイしなければなりません。

## 6. クローズと解放 [#close-and-dispose]

ストリームを開いた呼び出し元が、リソース解放の責任を持ちます。`for await` ループを `break`、`return`、または throw で抜けるとストリームは自動的にクローズされます。あるいは、`await using` または `stream.close()` を明示的に使用できます。

`stream.close()`、解放、呼び出し元の `signal` の abort は、呼び出し元がストリームを止めることです。`EventSource.close()` と同じく、すぐに終わり、まだ誰も読んでいないイベントを捨てます。これはストリームがすでに終わっていたかどうかにはよりません。そのため、レスポンスが終わったとき、またはストリームが失敗したときにまだ読まれていないイベントも捨てられます。失敗のあと、停止が変えるのはそれだけです。`stream.closed` は値を保ち、未読がなくなればイテレーターは引き続きその失敗で reject します。正常に終わるレスポンスと、エラーまたはタイムアウトで失敗するストリームは、呼び出し元がストリームを止めない限り、すでにキューにあったイベントを先に届けます（第 5 節を参照）。ストリームが動いているあいだに、`AbortSignal.timeout(ms)` のように期限が切れる `signal` はタイムアウトであり、呼び出し元による停止ではなく、その後者のグループに属します。ストリームが終わったあとに期限が切れるものは停止です。

`client({ signal })` 経由で渡された `signal` は、ストリームのライフタイム全体を制御します。確立済みのストリームを切断することなく初回の接続ハンドシェイクのみに制限時間を設けるには、上記サンプルの 2 つ目のタブのように `await watchOrders(...)` が返された直後にタイマーを解除するか、`withRetry({ maxRetries: 0, attemptTimeoutMs })` と書いてください。`maxRetries: 0` がなければ、`withRetry` はデフォルトの 3 回のリトライを保ちます。
