# WebSocket 會話

`defineWebSocket` 用嚟喺你嘅 SDK 入面宣告雙向 WebSocket 契約：包括路徑模板、可選嘅 `input` 同 `builder`（僅限 `path` 同 `query`）、`incoming` 同 `outgoing` 訊息 struct、佇列上限，以及靜態子協議（subprotocols）。使用方應用程式則喺自己嘅 client 設定心跳偵測（heartbeat）、重試（`withRetry`）同生命週期釋放。

## 2. 訊息驗證與方向規則

- **傳入 frame（`session.receive`）**：文字、`ArrayBuffer`、typed array 同 `Blob` frame 都會解碼成 UTF-8，解析為 JSON，並用 `incoming` struct 驗證。損壞嘅 JSON 或 schema 結構唔吻合會被回報到 `session.onRuntimeError` 並丟棄，唔會中斷會話。`session.receive` 係單一消費者模式；請求第二個 iterator 會拋出 `TypeError`。當傳輸失敗時，已經收到嘅訊息會先送出，然後 `receive` 以 `closed.cause` reject，心跳逾時都包括在內。呼叫端取消（abort `signal`）、`session.close()` 同釋放會丟棄未讀訊息，無論會話係咪已經結束。對於開着嘅會話，`session.close()` 或者釋放之後 `receive` 會即時結束，abort 之後就會以 abort 原因（預設係 `AbortError`）reject；`session.close()` 之後先到嘅 frame 亦會被丟棄。會話開着期間到期嘅 `signal`，例如 `AbortSignal.timeout(ms)`，係逾時：會話以錯誤結束，並先送出已排隊嘅訊息。會話結束之後先到期嘅就係停止，會丟棄佢哋。
- **傳出 frame（`session.send(payload)`）**：會同步通過 `outgoing` 驗證、套用 `.alias()` 同 codec，然後以 `JSON.stringify` 序列化。喺 `open` 狀態下會即時發送；喺 `reconnecting` 狀態下會排入佇列（若 `maxOutgoingQueueSize > 0`）；如果 payload 無效、佇列已滿／關閉，或會話已終止，則會同步拋出例外。

## 3. 會話狀態與監聽器

| 成員                 | 描述                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `state`              | `'idle' \| 'connecting' \| 'open' \| 'reconnecting' \| 'closing' \| 'closed' \| 'aborted' \| 'error'` |
| `connection`         | 最新實體 socket 嘅即時快照（`generation`、`url`、`protocol`、`extensions`）                           |
| `bufferedAmount`     | 當前活躍實體 socket 上未送出嘅位元組數（斷線時為 `0`）                                                |
| `receive`            | 單一消費者模式嘅非同步迭代器，輸出通過驗證嘅 `incoming` 訊息                                          |
| `onStateChange(fn)`  | 訂閱狀態轉換；回傳 `unsubscribe` 函式                                                                 |
| `onRuntimeError(fn)` | 訂閱非啟動階段嘅 frame／解析錯誤；回傳 `unsubscribe` 函式                                             |
| `closed`             | Promise 解析出最終終止狀態（`kind: 'closed' \| 'aborted' \| 'error'`）                                |

## 4. 重試、心跳與佇列

重連同心跳機制都係 opt-in 嘅，可透過 client 選項（`withRetry`、`withWebSocketHeartbeat`）或單次衍生 client 選項（`client({ retry, heartbeat })`）配置。重連用同 HTTP 同 SSE 一樣嘅 `withRetry` 策略：

- **重試**：設定重試策略時，預設值係 `maxRetries: 3`、`delayMs: 1000`、`factor: 2`、`maxDelayMs: 30000`、`jitter: 0.2`。`session.close()` 冇要求嘅每一次關閉預設都會重試，包括從未開啟嘅連線。建構函式拋出例外係重試只會重複嘅本地失敗，所以該次呼叫會結束，而且唔會詢問 `shouldRetry`。每次實體連線成功變成 `open` 都會重設斷線次數。`shouldRetry` 可以推翻預設，亦可以係 async；手動關閉、呼叫端 abort，或者已經做咗 `maxRetries` 次重試之後，都唔會呼叫佢。被拒絕或者用盡嘅重試會令會話如同冇策略一樣結束：連線錯誤係 `closed.kind: "error"`，對端嘅 close frame 係 `"closed"`。`beforeConnect({ attempt, signal })` 會喺初始連線同每次重試前執行。已開啟嘅 socket 報畀 balancer 嘅結果只取決於關閉代碼，同 `wasClean` 無關：`1006` 或 `1015`（冇收到 close frame）係 `NET_UNREACHABLE`，`1012` 或 `1013` 係 `NET_UNAVAILABLE`，其他代碼都唔算失敗。
- **嘗試逾時（`attemptTimeoutMs`）**：如果提供咗，佢限制由建立連線到 `open` 嘅時間，handshake 之後會被清走。佢係 `withRetry`（或者 `retry` 請求選項）嘅選項，所以 `withRetry({ attemptTimeoutMs })` 亦會重試，並用預設嘅 `maxRetries: 3`。如果只想限制 handshake，請寫 `withRetry({ maxRetries: 0, attemptTimeoutMs })`。到期會向 balancer 報告 `NET_UNREACHABLE`，而重試用盡就以 `NET_TIMEOUT` 結束。
- **心跳偵測**：Defjs 冇定義心跳格式、間隔或逾時：`message` 同 `isAck` 係你嘅函式，而型別要求 `message`，並且只允許 `timeoutMs` 同 `isAck` 一齊出現。瀏覽器 `WebSocket` 介面冇辦法送出協議層級嘅 ping，所以應用程式層級嘅訊息先係唯一可移植嘅心跳。每隔 `intervalMs` 佢會透過 `outgoing` struct 以 JSON 文字送出 `message()`，所以端點要宣告 `outgoing` struct，而裸文字或二進位 ping 係唔可能嘅。佢最多等 `timeoutMs` 嚟接收吻合 `isAck(msg)` 嘅已解碼 frame；通唔過 `incoming` struct 嘅 frame 會報去 `onRuntimeError`，而且永遠到唔到 `isAck`。吻合嘅 ack frame 會由心跳監控器消費，唔會轉發畀 `session.receive`。收唔到 ack 算係連線失敗：socket 會被關閉，錯過嘅 ack 會以 `NET_UNREACHABLE` 報畀 balancer，歸於該端點，而呢次嘗試會同其他關閉一樣進入重試流程。冇重試策略，或者重試用盡之後，`closed.kind` 係 `"error"`，`closed.cause` 係一般嘅 `Error("WebSocket heartbeat timeout")`。心跳序列化失敗，或者 `message()` throw，屬於本地事件：佢哋會以原始 cause 結束會話，唔會重試，亦唔會歸於端點。
- **佇列上限**：
  - 傳入訊息：冇選項，亦冇數量上限。函式庫會將平台送達嘅每條訊息排隊，直至 `session.receive` 讀走，所以永遠唔讀嘅消費者會令佇列無限增長；請喺會話開啟期間消費 `session.receive`，或者關閉會話。
  - `maxOutgoingQueueSize`（可選，預設 `0`）：淨係會喺 `state === 'reconnecting'` 期間緩衝 `session.send()` 呼叫，並喺下次發佈 `open` 狀態前將佢哋一次過 flush 送出。

`shouldRetry` 會喺 WebSocket context 入面收到原生關閉 `code`、`reason` 同 `wasClean`，而嗰度嘅 `retryable` 永遠係 `true`。伺服器可以用應用程式錯誤碼 `1011` 完成正常嘅關閉握手，所以 `wasClean === true` 唔代表應用程式處理成功。範例按 `code` 決定；請根據自己嘅協議揀選應用程式代碼，唔好淨係依賴 `!wasClean`。

## 5. 子協議與身分認證 [#protocols-and-authentication]

瀏覽器環境嘅 WebSocket 唔支援自訂握手 headers，因此 WebSocket 嘅 `builder` 函式只可以回傳 `{ path?, query? }`。

- **子協議優先級**：`client({ protocols })` 優於 `withWebSocketProtocols(...)`，而後者又優於 `defineWebSocket({ protocols })`。
- **URL 自動轉換**：Defjs 會自動將已解析端點嘅 `http:` 轉為 `ws:`，`https:` 轉為 `wss:`。
- **憑證傳遞**：`withCredentials(true)` 僅適用於 Fetch（HTTP/SSE）。WebSocket 認證應透過 Cookie／會話策略、子協議或短期 connection ticket 完成——避免將長期敏感密鑰放入 query string。
- **`beforeConnect` 唔係 request mutator**：input 解析、同步純函式 `builder` 同攔截器鏈每次操作只執行一次。如果 request 嘅 base endpoint 冇俾攔截器取代，每次重連都會重新揀選端點並用嗰個端點重建 URL，但會重用已建構嘅 path/query 同擷取嘅協議清單。無論仍然用同一端點定已經故障轉移，URL 都會喺嗰次嘗試嘅 `beforeConnect` 執行之前確定。喺 hook 入面改閉包變數、input 或協議陣列，唔可以為目前握手提供新 ticket。同一個會話內唔支援輪換 URL/子協議憑證；請先取得新憑證，再透過 input 或 client 設定開始新操作，並負責替代會話嘅清理。

## 6. 關閉與生命週期管理

呼叫 `session.close(code?, reason?)`（其中 `code` 須為 `1000` 或 `3000..4999`，`reason` 唔超過 123 個 UTF-8 位元組）並等待 `await session.closed`，或者直接用 `await using`：

<include cwd lang="typescript">
  examples/web-socket/closure-and-ownership.ts#example
</include>

曾經開着、之後冇 close frame 就斷線嘅連線（代碼 `1006`，`wasClean: false`）永遠以 `closed.kind: "error"` 結束，`closed.cause` 係 `Error("WebSocket connection error")`，無論 runtime 有冇觸發原生 `error` 事件。

一次斷線嘅重試用盡 `maxRetries` 之後，會話會以 `closed.kind: "error"` 結束，保留原生關閉 snapshot（升級失敗時通常係代碼 `1006`），並用一般傳輸層錯誤做 `closed.cause`；唔會提供獨立而穩定嘅用盡錯誤碼。會話以 `closed.kind: "error"` 結束時，已經排咗隊嘅訊息仍然會送出，`session.receive` 會喺最後一條之後以 `closed.cause` reject；對端嘅關閉亦會先送出已排隊嘅訊息，然後 `session.receive` 先結束。呼叫端停止會話時，未讀訊息會被丟棄：呼叫端 abort（`closed.kind: "aborted"`）、手動 `session.close()`，以及用 `await using` 釋放，都會咁做，會話已經結束之後亦一樣。對於開着嘅會話，`session.close()` 或者釋放之後 `session.receive` 會即時結束，呼叫端 abort 之後就會以 `closed.cause`（即係 abort 原因）reject。會話結束之後嘅停止會丟棄未讀訊息，而且唔會改變其他嘢：`closed` 保持原值，`session.receive` 仍然會喺冇未讀內容剩低嗰陣以 `closed.cause` reject。當元件或背景 worker 結束工作時，記得取消訂閱 `onStateChange` 同 `onRuntimeError` 監聽器。
