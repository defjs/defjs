# 攔截器

攔截器可以將橫切嘅執行策略——例如認證 headers、請求簽名、維護模式嘅快速短路（short-circuiting），或者 `Retry-After` 處理——掛載到應用程式嘅 `Client`，完全唔使改動 SDK 嘅操作定義。

呼叫流程中，input 驗證同 `builder` 映射會喺攔截器鏈**之前**執行；而 HTTP 狀態碼分發以及 `output` / `error` struct 驗證則會喺攔截器鏈**之後**執行。[操作攔截器](#operation-interceptors)會包住以上所有步驟。

### 攔截器管線規則

- **洋蔥模型順序**：攔截器喺傳出請求時會按註冊順序執行（`before next(req)`）；喺回應返回時則會按相反順序執行（`after await next(req)`）。請將廣泛嘅日誌／追蹤攔截器放喺最外層，而將較具體嘅認證或重試攔截器放喺內層。
- **不可變 Request 慣例**：記得一定要複製 `req.headers`（`new Headers(req.headers)`），並將全新嘅 request 物件（`{ ...req, headers }`）傳畀 `next(...)`，等外層嘅重試邏輯可以見到乾淨嘅原始 headers。
- **`content-type` 與 `bodyContentType`**：Defjs 會將推斷出嚟嘅 body content type 存喺 `req.bodyContentType`，唔會直接修改 `req.headers`。請求簽名邏輯應讀取 `req.headers.get("content-type") ?? req.bodyContentType`。如果攔截器將 `req.body` 替換成全新格式，請明確設定 `content-type` header。

## 3. 重試同 `Retry-After`

HTTP 重試預設關閉。要使用對 `429` 同 `503` 嘅原生 RFC 9110 `Retry-After` 支援（`retryAfter: true`、`maxRetryAfterMs: 60_000`）去重試連線失敗、逾時，或者 `statusCodes` 入面嘅狀態碼（預設為 `429`、`502`、`503` 或 `504`），請用 [`withRetry()`](/zh-Hant-HK/docs/load-balancing#retries)。經過延遲之後，佢會再俾 balancer 揀一次、重新建構 request，並重新執行完整嘅攔截器鏈。

當應用程式需要**自訂同端點**狀態處理——例如喺已揀選嘅端點上重試而唔重新執行 `builder` 或外層攔截器、喺冇 `Retry-After` 時改用後備延遲，或者封頂等待而唔係快速失敗——攔截器可以直接對 `next(request)` 做迴圈：

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **兩層重試**：呢個 `next(request)` 迴圈會留喺選中嘅端點，唔會重新執行 builder 或外層攔截器。連線失敗、跨端點故障轉移以及預設 `429`/`502`/`503`/`504` 策略交畀 `withRetry`。
- **內建 vs. 自訂 `Retry-After` 策略**：Core 嘅 `withRetry()` 預設會對 `429` 同 `503` 遵循 RFC 9110 `Retry-After`（如果伺服器要求嘅延遲超過 `maxRetryAfterMs`，就會直接快速失敗而唔再重試）。如果你喺上面配方嗰類自訂攔截器入面處理 `429`，請設定 `withRetry({ retryAfter: false })`（或者喺 `statusCodes` 中省略 `429`）以避免雙重重試；配方入面嘅 30 秒上限同 250 ms 後備值係應用程式嘅選擇，而對更長嘅伺服器延遲封頂可能會比要求更早重試。
- **401 寫入**：[Bearer 更新配方](/zh-Hant-HK/recipes/refresh-bearer-once) 可能傳遞同一個 JSON POST 兩次。必須確保認證喺業務處理前拒絕 request，並使用穩定嘅冪等鍵同伺服器端去重，否則唔好自動重播寫入。串流 request body 唔會重播。
- **處理傳輸層拒絕**：當發生網絡錯誤時，`next(request)` 會直接 reject（絕唔存在狀態碼為 0 嘅 response 物件）。Catch 之後再重新 throw 該 rejection，可以完整保留原始嘅 `NET_*` fault code。
- **送唔出嘅請求**：喺 HTTP 攔截器入面，當平台拒絕呢個 request（無效或被禁止嘅 method、GET 或 HEAD 帶 body、帶憑證嘅 URL、無效嘅 `Content-Type`），或者 `finalizeHeaders` hook 拋出例外，`next(request)` 會以平台自己嘅錯誤（`TypeError`）或者 hook 拋出嘅值 reject，而唔係函式庫嘅 `BodyFailure` wrapper。再 throw 佢會保留 fault code（`REQ_BUILD_FAILED` 或 `EXT_HOOK_FAILED`）；throw 另一個錯誤就會變成你自己嘅失敗（`EXT_INTERCEPTOR_FAILED`）。傳輸層附近嘅其他失敗仍然會以 `BodyFailure` 到達 `next(request)`：讀唔到、解碼唔到或者 media type 對唔上嘅 response body、被截斷嘅 body，以及拋出例外嘅上傳進度 observer（`EXT_OBSERVER_FAILED`），而後者可以喺 request 送出之前發生。
- **喺攔截器入面拋出例外**：攔截器自己未處理嘅 throw（或者傳俾 `next()` 嘅 `signal` 唔係 `AbortSignal`）會令操作 tuple 以 `EXT_INTERCEPTOR_FAILED` 失敗，並將原因記錄喺 `err.cause`。若拋出 `ERR_ABORTED` 或 `ERR_TIMEOUT`，則會分別結算為 `NET_ABORTED` 或 `NET_TIMEOUT`。

對於 SSE，優先用 `withRetry`，而唔係反覆呼叫 `next()` 嘅攔截器。多次呼叫攔截器嘅 `next()` 會停用呢啲替代串流嘅端點歸因同重新揀選；呢件事同用 iterator 嘅 `next()` 消費 events 無關。

## 4. 包裝 WebSocket 會話

## 5. 觀察成個操作呼叫 [#operation-interceptors]

傳輸攔截器一次只見到一個 request：驗證唔通過嘅 input 永遠去唔到佢度，每次重試都會再執行一次，而 response 係喺佢回傳之後先解碼。想觀察呼叫本身，由 `getOrder(client, input)` 被呼叫嗰一刻直至 tuple 結算，就用 `createOperationInterceptor`：

<include cwd lang="typescript">
  examples/api/create-operation-interceptor.ts#example
</include>

- **佢見到乜**：`call` 描述定義：`transport`（`"http"`、`"sse"` 或 `"websocket"`）、`method`、`path` 模板同 `meta`。佢唔帶 input 或 request，因為兩者都未存在。`next()` 會以操作嘅 tuple resolve，所以 `err` 係最終嘅 fault：`REQ_INPUT_INVALID`、`REQ_BUILD_FAILED`、`HTTP_STATUS`、`RES_STRUCT_MISMATCH` 等等。
- **只觀察，唔改動**：`next()` 唔接受參數，第二次呼叫 `next()` 會回傳同一個 promise，唔會再執行呼叫，而函式只可以用 `next()` resolve 嘅結果去 resolve。要改 request 同 response，請喺傳輸攔截器入面做。
- **次序**：操作攔截器喺所有傳輸攔截器外面，按註冊次序執行。喺 `next()` 前後執行嘅程式碼，例如 OpenTelemetry 嘅 `context.with`，對整個呼叫都有效，包括傳輸攔截器。
- **串流同會話**：SSE 或 WebSocket 呼叫會喺串流或會話開啟之後結算；之後喺佢上面發生嘅事，要透過佢嘅 `closed` 去觀察。
- **失敗**：throw 或者 rejection 會令操作以 `EXT_INTERCEPTOR_FAILED` 結算，並將被拋出嘅值作為 `cause`。呼叫已經開啟嘅串流或者會話會被關閉。

## 6. 內建工廠函式與輔助工具

| 匯出名稱                                       | 傳輸層    | 描述                                                                                                                                             |
| ---------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createHttpInterceptor(fn)`                    | HTTP      | 包裝 `(req, next) => Promise<HttpResponse<unknown>>`                                                                                             |
| `createSSEInterceptor(fn)`                     | SSE       | 包裝 `(req, next) => Promise<EventStreamHandle<unknown>>`                                                                                        |
| `createWebSocketInterceptor(fn)`               | WebSocket | 包裝 `(req, next) => Promise<WebSocketSessionLike>`                                                                                              |
| `createOperationInterceptor(fn)`               | 全部      | 喺整個操作呼叫外面包裝 `(call, next) => Promise<result>`                                                                                         |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP      | 從每個 request 都會呼叫嘅同步憑證提供者注入 `Authorization: Basic ...`                                                                           |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE       | 喺 SSE 握手請求中注入 `Authorization: Basic ...`                                                                                                 |
| `concurrencyLimitHttpInterceptor(options)`     | HTTP      | 按 bucket 限制並發進行中嘅嘗試次數（`ConcurrencyLimitInterceptorOptions`）；以 FIFO 排隊至 `maxQueue`，超出則拋出 `BulkheadOverflowError`        |
| `idempotencyKeyHttpInterceptor(options?)`      | HTTP      | 喺會變更狀態嘅方法（`POST`、`PATCH`）注入冪等鍵 header（`IdempotencyKeyInterceptorOptions`，預設 `Idempotency-Key`），並重用 `req.correlationId` |

`concurrencyLimitHttpInterceptor` 會喺 `withRetry` 退避等待期間釋放許可，避免重試將隔艙鎖死，並會喺超過 `maxQueue` 時拋出 `BulkheadOverflowError`（以 `EXT_INTERCEPTOR_FAILED` 連同 `{ attempted: false }` 浮現）。請參閱 [Interceptors API 參考](/zh-Hant-HK/api/interceptors)。
