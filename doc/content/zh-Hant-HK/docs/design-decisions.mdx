# 核心架構

Defjs 圍繞住一個基本邊界建立：**SDK 負責定義網絡契約；使用方應用程式負責掌握執行。** `@defjs/core` 入面嘅每項設計規則，都係由呢個核心分離原則延伸出嚟。

## 1. 定義 vs. 執行

SDK 套件匯出操作（`defineRequest`、`defineEventStream`、`defineWebSocket`）同埋資料契約（`struct`）。佢永遠唔會呼叫 `createClient`、唔會保留單例 client，亦唔會直接讀取環境變數。

正因為 `getOrder` 完全冇捕獲任何 client 狀態：

- 無論係瀏覽器 UI、背景工作、SSR 請求處理常式，定係單元測試，都可以用唔同嘅 `Client` 設定呼叫同一個 `getOrder` 操作。
- 框架外掛（`@defjs/react`、`@defjs/vue`）同可觀測性中介層外掛（`@defjs/opentelemetry-server`）只會掛落應用程式嘅 `Client`，令發佈出去嘅 SDK 套件保持 100% 零第三方依賴。

## 2. 明確嘅 Input 放置與雙向 Alias

喺 Defjs 入面，`input` 宣告呼叫端要傳入乜嘢，`struct` 控制資料點樣編碼／解碼，而 `builder` 則負責將各個值放到請求嘅正確位置（`path`、`query`、`headers`、`body`）。

- **唔會胡亂猜測**：如果一個操作宣告咗 `input`，就一定要提供明確、同步而且純粹嘅 `builder`。Defjs 絕唔會單憑參數名稱走去估佢應該放喺邊。
- **雙向 `.alias(wireName)`**：喺 struct 欄位宣告 `.alias("customer_name")`，可以令 TypeScript 程式碼保持使用 `customerName`，同時喺網絡傳輸時自動雙向映射到 `"customer_name"`。

## 3. 宣告即斷言 [#declaration-is-an-assertion]

Defjs 遵循六條嚴格規則嚟讀取 HTTP 回應：

### 規則 1：有宣告先有斷言

`output` 斷言 `2xx` 回應 body 嘅形狀。`error` 斷言非 `2xx` 回應 body 嘅形狀。宣告係執行時嘅強制保證，而唔係「盡力而為」嘅參考建議。

### 規則 2：`ok` (`200..299`) 係唯一嘅分水嶺

`2xx` 回應只會用 `output` 嚟解碼。其他所有狀態碼（`3xx`、`4xx`、`5xx`）都只會用 `error` 解碼。Defjs 絕唔會由一邊 fallback 返去另一邊。

### 規則 3：任何偏離斷言嘅行為都會即刻報錯

Defjs 用 `response.ok` 揀回應邊一邊：`2xx` 用 `output`，非 `2xx` 用 `error`。只有喺嗰一邊宣告咗 JSON struct，先會觸發 decode，並可能產生 `RES_MEDIA_TYPE_INVALID` 或 `RES_DECODE_FAILED`；佢嘅 `Content-Type` 會**最先**檢查，早過讀取或者查詢 body。冇內容嘅回應（`HEAD`、`204`、`205`、`304`）都要過同一項檢查：宣告咗 JSON representation 但 `Content-Type` 唔係 JSON，就會以 `RES_MEDIA_TYPE_INVALID` 失敗；如果係 JSON，就會解析空 bytes，並以 `RES_DECODE_FAILED` 失敗。非 `2xx` 嘅 HTML 網關頁只有喺宣告咗 JSON `error` struct 時先會產生 `RES_MEDIA_TYPE_INVALID`。生效嗰一邊冇宣告，就唔會讀 body；非 `2xx` 回應會返回未解碼嘅 `HTTP_STATUS`。SSE 握手跟同一套規則：非 `2xx` 握手如果宣告咗嘅 `error` body 解碼唔到，啟動時會回傳嗰個 decode fault，狀態放喺佢嘅 metadata；而攔截器、重連策略同重連嘅 `closed` 仍然見到 `HTTP_STATUS`。

| 讀取回應時出錯嘅情況                       | 回傳嘅 Fault                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------- |
| Media type 唔符合宣告嘅 JSON 格式          | `RES_MEDIA_TYPE_INVALID`（最先檢查；body 根本唔會被讀，有冇內容都冇分別） |
| Bytes 無法解碼成宣告嘅資料格式             | `RES_DECODE_FAILED`（包括空嘅 JSON bytes）                                |
| 解碼後嘅值無法通過 `struct` 驗證           | `RES_STRUCT_MISMATCH`                                                     |
| 非 `2xx` 狀態碼，並成功解碼 `error` struct | `HTTP_STATUS`，帶有具型別嘅 `error.data`                                  |
| 非 `2xx` 狀態碼，但冇宣告 `error`          | `HTTP_STATUS`，且 `error.data: undefined`                                 |

### 規則 4：解碼失敗就冇 Body

只有喺通過解碼同驗證之後，body 先會存在。解碼失敗嗰陣，fault 嘅 `response` 型別只會係 `HttpMeta`（完全冇 `body` 屬性），而解析器或驗證錯誤會附帶喺 `fault.cause`。

### 規則 5：冇宣告嗰邊就代表放棄讀取

冇宣告 `output` 代表根本唔會讀取 `2xx` 嘅 body。冇宣告 `error` 則代表完全唔會讀取非 `2xx` 嘅 body——就算伺服器喺 `500` 時送出咗無效 JSON 亦都唔會報解碼錯。

### 規則 6：`3xx` 唔算係成功狀態

`ok` 指嘅係 `200 <= status < 300`。`304 Not Modified` 屬於非 `2xx`：你可以唔宣告 `error` 並直接處理 `HTTP_STATUS`（參閱 [ETag 條件請求](/zh-Hant-HK/recipes/etag-revalidate)）；若預期空文字 body 亦可宣告 `struct.string()`。

## 4. 各傳輸層專屬嘅結果 tuple

三種傳輸層都會回傳三項式 error-first tuple，而唔會喺呼叫處直接 throw：

- **HTTP** → `[error, data, response]` — 解碼後嘅 payload + `DecodedResponse<T>`（未宣告 `output` 時為 `HttpMeta`）。
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + 初始握手 snapshot。
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + 初始連線 snapshot。

Client 只負責帶住設定，唔會持有活躍連線。發起 HTTP 請求、SSE 串流或 WebSocket 會話嘅呼叫端，負責取消或者關閉資源（HTTP 用 `AbortSignal`；SSE 同 WebSocket 則用 `await using` 或 `.close()` + `await .closed`）。
