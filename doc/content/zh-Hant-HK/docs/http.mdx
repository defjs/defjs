# HTTP 操作

SDK 作者用 `defineRequest` 嚟定義每個 HTTP 操作：包括佢嘅 HTTP method、路徑模板、`input` schema、同步純函式 `builder`，以及對應成功或錯誤嘅 `output` / `error` response schema。使用方應用程式匯入呢啲操作之後，傳入自己設定好嘅 `Client`，並處理回傳嘅 `[err, data, response]` tuple。

### SDK 設計最佳實踐

- **一個定義對應一個操作**：將每個 method、路徑同契約分開獨立定義，等應用程式可以 tree-shake 走用唔著嘅操作。
- **攔截器需要上下文時附加 `meta`**：`meta` 係 `{ [key: string]: unknown }`，由應用程式自行定義，例如 `{ operation: "orders.read" }`。佢會傳到攔截器同負載平衡器（`request.meta`、`PickInfo.meta`）；每個定義只有一個唯讀物件，由每次呼叫、每次 attempt 同每個 client 共用。唯讀類型係淺層嘅，所以每次呼叫嘅狀態要放喺攔截器嘅 closure 入面，而唔係放喺 `meta` 或者佢嘅巢狀物件入面。為 `meta` 定義嘅具名型別必須係 `type` alias：TypeScript 唔會將 `interface` 指派俾 index signature。Defjs core 從來唔會讀取或複製 `meta`，亦唔會隨請求送出；URL、headers 或 body 嘅值要經 `builder` 傳入。`@defjs/opentelemetry-server` 會將每個 key 作為 `defjs.meta.<key>` 屬性上報到 span 同失敗日誌，所以唔好將機密資料同個人資料放入 `meta`。
- **切忌喺 SDK 入面嵌入 Client**：SDK 只應該匯出定義、`struct` schema 同型別宣告。

## 2. URL 解析與路徑參數

`withEndpoint(...)` 需要一個有效嘅絕對 URL。佢嘅 pathname 會被當成 base 目錄（base endpoint 上面嘅任何 query string 或 hash 都會被自動忽略）。

<include cwd>examples/http/resolve-url.ts#example</include>

- **路徑佔位符（`:name`）**：會嚴格編碼一次作為單一 path segment。斜線、`?`、`#`、`%`、空白同 Unicode 字元都會留喺該 segment 入面——千祈唔好預先手動 encode 值。空字串、`.` 同 `..` 都會直接觸發 `REQ_BUILD_FAILED`。
- **Origin 與目錄約束**：定義中嘅 path 唔可以係絕對 URL、協議相對 URL（`//...`），亦唔可以包含 C0 控制字元、反斜線、`?`、`#`，或者跳出 base endpoint 嘅目錄範圍（`../`）。任何違規都會喺攔截器或傳輸層執行前，即時以 `REQ_BUILD_FAILED` 報錯。

## 3. 用 `builder` 放置 Input

只要操作宣告咗 `input`，就**必須**提供一個同步且純粹嘅 `builder`，回傳 `{ path?, query?, headers?, body? }`。只有完全冇宣告 `input` 嘅操作先可以省略 `builder`。

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

### `builder` 點樣編碼欄位別名（alias）

| builder 表達式                                 | 網絡傳輸輸出                                                      |
| ---------------------------------------------- | ----------------------------------------------------------------- |
| `body: input.profile`                          | 帶型別 struct：`.alias()` 以及 `Date` / `bigint` codec 會自動生效 |
| `body: { profile: input.profile }`             | 外層 key `profile` 保持原樣；內層物件保留其 struct 別名           |
| `body: { ...input.profile, role: "admin" }`    | 物件展開會保留 struct 別名；`role` 保持原樣字面值                 |
| `body: { name: input.profile.customerName }`   | 匿名物件：所有 key 均為字面值                                     |
| `query: input.filter` / `headers: input.trace` | 扁平帶型別物件：欄位嘅 `.alias()` 會自動轉成 wire key             |

### 自訂 Query 序列化

預設情況下，query 嘅純量值（scalar）同純量陣列（重複 key）會直接編碼，而巢狀 query 物件會以 `REQ_BUILD_FAILED` 失敗。如果後端需要特殊嘅巢狀 query 語法（例如 `filter[status]=paid`），可以喺 client 配置 `withQuerySerializer`：

<include cwd>examples/http/query-serializer.ts#example</include>

你回傳嘅字串會被解析成請求嘅 `query`，所以請求送出嘅係 `query.toString()`，即係 URL Standard 嘅 application/x-www-form-urlencoded 序列化。空格係 `+`，`filter[status]=paid` 入面嘅方括號會以 `filter%5Bstatus%5D=paid` 送出，表單解碼器會將佢讀返做同一個名。

### Request Body 格式

`GET` 同 `HEAD` 唔可以帶 body。對於其他 HTTP method，body 嘅格式會根據 `builder` 回傳嘅值自動判斷：

| `body` 值                                                 | 網絡傳輸形式                                 | 預設 `Content-Type`                       |
| --------------------------------------------------------- | -------------------------------------------- | ----------------------------------------- |
| `undefined` / 省略                                        | 冇 body                                      | —                                         |
| 帶有 `urlencoded` / `formData` 編碼嘅根 struct            | `URLSearchParams` / `FormData`（已套用別名） | 表單類型 / multipart boundary             |
| 原生 `FormData` 或 `URLSearchParams`                      | 原樣透傳                                     | Multipart boundary / urlencoded           |
| `Blob` / `File`                                           | 原樣透傳                                     | `blob.type` 或 `application/octet-stream` |
| `ArrayBuffer`、TypedArray、`DataView`、`ReadableStream`   | 原始位元組 / 串流                            | `application/octet-stream`                |
| `string`                                                  | UTF-8 文字                                   | `text/plain;charset=UTF-8`                |
| 純物件、陣列、有限數值、boolean、`null`、`Date`、`bigint` | 經 Struct 編碼嘅 JSON                        | `application/json`                        |

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

任何無法喺 JSON 中合法表達嘅值（例如 `NaN`、`±Infinity`、`Map`、`Set`、函式、冇 `toJSON()` 嘅 class 實例，或原生 iterable），都會令呼叫即刻以 `REQ_BUILD_FAILED` 失敗，而唔會靜雞雞序列化成 `{}` 或 `null`。

## 4. 回應點樣被解碼

`output` 用嚟驗證 `2xx` 成功回應；`error` 則用嚟驗證非 `2xx` 回應（`3xx`、`4xx`、`5xx`）。Struct 嘅種類決定咗回應串流點樣被讀取（`struct.string()` → 文字、`struct.blob()` / `struct.file()` → `Blob`、`struct.arrayBuffer()` → `ArrayBuffer`，其他全部 → JSON）：

1. **按狀態碼 `ok` (`200..299`) 揀選對應側**：`2xx` 走 `output`，非 `2xx` 走 `error`。
2. **未宣告則放棄讀取**：如果嗰一邊冇宣告 struct，回應 body 根本唔會被讀取（`2xx` resolve 出 `data: undefined` + `HttpMeta`；非 `2xx` resolve 出 `HTTP_STATUS` 且 `data: undefined`）。
3. **優先驗證 JSON media type**：對於宣告 JSON 嘅 struct，如果伺服器回傳非 JSON 嘅 `Content-Type`，呼叫會喺讀取或者查詢 body 之前以 `RES_MEDIA_TYPE_INVALID` 失敗。冇內容嘅回應（`HEAD`、`204`、`205`、`304`）都要同其他回應一樣符合宣告。
4. **讀取與解析**：無法讀取串流或 JSON 損壞會報 `RES_DECODE_FAILED`（如果中途被截斷則報 `NET_BODY_INCOMPLETE`）。
   冇內容嘅回應（`HEAD`、`204`、`205`、`304`）冇 body 可以讀：`struct.string()` 得到 `''`，`struct.arrayBuffer()` 得到空嘅 `ArrayBuffer`，`struct.blob()` 得到空嘅 `Blob`。通過第 3 步嘅 JSON struct 會解析呢啲空 bytes，並以 `RES_DECODE_FAILED` 失敗。
5. **用 `struct` 進行驗證**：schema 結構唔吻合會令呼叫以 `RES_STRUCT_MISMATCH` 失敗。

## 6. 憑證、XSRF 與傳輸進度

- **`withCredentials(true)`**：為 HTTP 同 SSE 請求設定 Fetch 嘅 `credentials: "include"`。
- **`withXSRF(options?)`**：來自 `@defjs/core/xsrf`。喺瀏覽器入面，讀取 XSRF cookie（預設為 `XSRF-TOKEN`），並喺同源嘅變更類 HTTP 方法（`POST`、`PUT`、`PATCH`、`DELETE`）上自動注入 header（`X-XSRF-TOKEN`）。呼叫 `withXSRF()` 時，如果缺少 `location` 或者 `document`（包括 Worker）會拋錯。同構程式只喺瀏覽器入面加呢個 option。令牌嚟自別處時，用攔截器設定。同源檢查適用於函式庫建構出嚟嘅 URL；Fetch 自己跟住 redirect，redirect 去另一個來源之後只會移除 `Authorization`，所以呢個 header 會一路跟住。想拒絕呢種情況，請睇 [`withXSRF`](/zh-Hant-HK/api/core/withxsrf)。
- **`onDownloadProgress` / `onUploadProgress`**：透過 `client({ onDownloadProgress, onUploadProgress })` 傳入。下載進度淨係喺 `Content-Length` 為正數而且冇 `Content-Encoding`（或為 `identity`）嗰陣，先會報告 `lengthComputable: true`。上傳進度淨係喺你傳入嘅 request body 係 `ReadableStream` 嗰陣先會報告；其他所有 body（`Blob`、`File`、`ArrayBuffer`、`FormData`、字串、`URLSearchParams`）都會按組裝好嘅原樣送出，而且喺每個 runtime 都唔會呼叫 `onUploadProgress`。`ReadableStream` body 會跟 Fetch 對串流 request body 嘅規則，有冇 `onUploadProgress` 都一樣：Chromium 同 WebKit 只接受 HTTP/2 或更新版本，所以喺 HTTP/1.1 上呼叫會以 `NET_UNREACHABLE` 失敗（Node.js 同 Bun 接受 HTTP/1.1）；Firefox 無法串流 request body，會以 `ENV_UNSUPPORTED` 失敗；喺瀏覽器入面，跨來源請求需要 CORS preflight，除非瀏覽器已經持有快取咗嘅 preflight 結果；而 301、302、307 或 308 redirect 會失敗。瀏覽器唔會送 `Content-Length`。負載平衡器對呢啲失敗，以及來源串流拋出例外，都會收到 `{ attempted: false }`，因為 `fetch` 將佢哋報成同連唔到端點一樣嘅網絡錯誤；所以單靠串流上傳偵測唔到故障端點。詳情請睇 API 參考入面嘅 `HttpProgressFn` 條目。如果進度 callback 拋出例外，成個呼叫會以 `EXT_OBSERVER_FAILED` 失敗。
