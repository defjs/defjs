# 錯誤處理

處理 404、timeout 或者讀唔出嘅 body，靠嘅係讀 error-first tuple，而唔係 catch 拋出嘅錯誤。`Fault` 係原生 `Error`（`instanceof Error` 為真），由一個 field 判別：`code`。

冇 `kind`。失敗嘅類別就係 code 裡面第一個 `_` 之前嗰一段，所以 `NET_TIMEOUT` 係 `NET` 類失敗，`RES_STRUCT_MISMATCH` 係 `RES` 類失敗。粗分睇 prefix，精確判斷睇成個 code。

## 穩定嘅 code

| 類別   | Code                                                                   | 邊個要改                       |
| ------ | ---------------------------------------------------------------------- | ------------------------------ |
| `HTTP` | `HTTP_STATUS`                                                          | 對端回咗非 2xx；當業務邏輯處理 |
| `REQ`  | `REQ_INPUT_INVALID`、`REQ_OPTIONS_INVALID`、`REQ_BUILD_FAILED`         | 呢次 call，或者 endpoint 聲明  |
| `NET`  | `NET_ABORTED`、`NET_TIMEOUT`、`NET_UNREACHABLE`、`NET_BODY_INCOMPLETE` | 冇人，或者 retry               |
| `RES`  | `RES_MEDIA_TYPE_INVALID`、`RES_DECODE_FAILED`、`RES_STRUCT_MISMATCH`   | 聲明同對端要對得上             |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`、`EXT_HOOK_FAILED`、`EXT_OBSERVER_FAILED`     | 你掛上 pipeline 嘅 code        |
| `CAP`  | `CAP_BUFFER_EXCEEDED`、`CAP_QUEUE_OVERFLOW`                            | 聲明嘅上限，或者消費方嘅節奏   |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | Host runtime                   |

集合係故意封閉嘅：呢個正係 `switch` 可以窮盡嘅原因。Extension 要報自己嘅細節就走 `cause`，唔係加新 code。

HTTP、SSE 同 WebSocket 都需要有效嘅絕對 client `endpoint`。URL 解析之後，path 必須留喺 base endpoint 嘅 origin 同目錄之內。絕對 URL、protocol-relative paths、C0 控制字元（包括 tab、CR 同 LF）、反斜線、`?`、`#`，以及逃出目錄嘅路徑都會被拒絕。形似 scheme 同 protocol-relative 嘅形式，就算前面有空格都會被拒絕；路徑入面嘅普通空格允許，並會以 `%20` 送出。缺少、相對或無效嘅 endpoint，以及非法 path，都會喺 request construction 時產生 `REQ_BUILD_FAILED`，早於 interceptors 執行；short-circuit interceptor 亦唔可以繞過呢個檢查。Transport 執行之前，interceptor 最終嘅 `req.endpoint` 會按最終嘅 `req.baseEndpoint` 用同一套規則檢查；容許明確切換到另一個有效嘅絕對 base。呢啲確定嘅 URL faults 唔可以重試。

### 各形狀帶咩 field

| Code          | `status` | `response`                                         | `data`                                |
| ------------- | -------- | -------------------------------------------------- | ------------------------------------- |
| `HTTP_STATUS` | 一直有   | 一直有；只有聲明過 `error` 而又解碼成功才帶 `body` | 解碼後嘅 `error` body，或 `undefined` |
| `RES_*`       | 一直有   | 一直有，只有 metadata——**冇 `body`**               | 冇                                    |
| 其餘一切      | 冇       | 只有 transport 當時已經拿到 metadata 才有          | 冇                                    |

`cause` 帶住底層嘅值：struct 唔匹配就係 `StructError`，representation 讀唔出就係 parser 嘅失敗，extension 拋咩就係咩。

HTTP 失敗時第三項係 `undefined`：當時存在嘅 response metadata 已經由 fault 帶住。呢點重要，因為你傳俾 handler、寫 log、重新拋出嘅就係 fault，所以 metadata 要跟住佢走，而唔係擺喺佢隔籬。

SSE 同 WebSocket 嘅第三項係啟動快照，就算啟動失敗都可能有。Handle 或 session 返嚟之後，後續嘅失敗活喺佢自己嘅生命週期上——佢哋絕對唔會改寫已經定咗嘅啟動 tuple。

## body 點讀

`ok` 係唯一分流點，而且只有一邊會解碼。`output` 讀 2xx body；`error` 讀其餘一切。唔寫邊個，嗰個 body 就根本唔會被讀。

| 情況                                    | 結果                                            |
| --------------------------------------- | ----------------------------------------------- |
| 2xx，聲明過 `output`，body 解碼成功     | 成功；`data` 同 `response.body` 都有 type       |
| 2xx，冇寫 `output`                      | 成功；`data` 係 `undefined`，response 冇 `body` |
| 非 2xx，聲明過 `error`，body 解碼成功   | `HTTP_STATUS`，`data` 有 type                   |
| 非 2xx，冇寫 `error`                    | `HTTP_STATUS`，`data: undefined`                |
| Media type 唔係嗰個 representation 要嘅 | `RES_MEDIA_TYPE_INVALID`，讀 body **之前**就報  |
| Bytes 唔係嗰個 representation           | `RES_DECODE_FAILED`                             |
| 值唔符合嗰個 struct                     | `RES_STRUCT_MISMATCH`（只限 HTTP）              |
| 你**冇**聲明嗰一邊嘅 body 讀唔出        | 完全忽略——睇下面                                |

最後一行值得記住。如果你聲明咗 `output` 而冇聲明 `error`，咁一個 body 係壞 JSON 嘅 500，報出嚟就係 `HTTP_STATUS` 加 `status: 500`。你講過你唔關心 error body，呢個亦包括唔關心佢讀唔出呢件事。

對 HTTP 嚟講，Struct 只會套用一次，而且喺 interceptor chain 之後。Interceptor 用 `makeResponse(...)` 造嘅 response，同線上嚟嘅走同一套 media type 檢查、representation 轉換同 Struct。內置 Fetch transport 會先將已聲明嘅 body 讀成 JSON、text、`Blob` 或 bytes，再交返俾 chain。只有 JSON representation 需要 JSON media type 同 `JSON.parse`；非 JSON text、blobs 同 bytes，只要符合聲明嘅 representation 就有效。讀取失敗適用於所有 representation；嗰度嘅讀取或解析失敗，會報成同一個 `RES_*` 或者 `NET_BODY_INCOMPLETE` fault。

`HttpResponse.ok` 只表示 `200 <= status < 300`。Transport failure 係 fault，絕對唔係 response——唔存在代表佢嘅 status-0 response。

## 啟動期同開啟之後

SSE 喺 resolve handle 之前會驗證 status、`text/event-stream` 同 body 存唔存在。非 2xx → 冇聲明 `error` 或者佢嘅 body 解碼成功時係 `HTTP_STATUS`。已聲明嘅 handshake body 讀唔到、解析唔到，或者通唔過 Struct，都會產生 `RES_DECODE_FAILED`；Struct 失敗會以 `StructError` 作為 `cause`。Media type 唔對 → `RES_MEDIA_TYPE_INVALID`。成功 handshake 冇 body → `RES_DECODE_FAILED`。開啟快照照樣可能落喺 tuple 第三項。

WebSocket 嘅啟動期覆蓋 handshake 加第一次物理 open。Constructor 失敗、open 之前就 close、timeout 或者取消，全部都會產出一個啟動 tuple。就算 socket 從來冇到過 `open`，connection 快照都可能存在。

| Transport | 啟動之後                                                                                                                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSE       | 致命錯誤時 iterator reject；`stream.closed` 以 `kind: 'error'` 同對應嘅 fault `code` resolve                                                                                              |
| WebSocket | 訊息／queue／heartbeat 失敗走 `onRuntimeError`；終止性錯誤令 `receive` 失敗；`session.closed` → `kind: 'closed' \| 'aborted' \| 'error'`                                                  |
| HTTP      | Execute 嘅 promise 只 settle 一次，結果係 tuple。如果 interceptor 或者 progress callback 拋出錯誤，嗰個錯誤就會變成 tuple 入面嘅 fault（`EXT_INTERCEPTOR_FAILED`、`EXT_OBSERVER_FAILED`） |

`NET_ABORTED` / `NET_TIMEOUT` 描述嘅係 caller 喺啟動期睇到咩。回俾你嘅 stream 或 session，你照樣要關掉並 await 佢嘅終態 promise。

## 原生 Error 嘅 log 同 cause

Fault 係原生 `Error` instance，所以唔需要診斷 adapter。`String(fault)` 會俾出穩定嘅原生形式 `DefjsFault: <message>`。`code` 同各變體 field——`status`、`response`、`data`——保持可枚舉，方便做結構化 log；`name` 同原生 `cause` chain 係唔可枚舉嘅。

<include cwd lang="typescript">
  examples/errors/log-fault.ts#example
</include>

Call `format()`、`flatten()` 或者 `prettify()` 之前，先用 `fault.cause instanceof StructError` 收窄 type。呢啲 helper 喺 Struct 嘅 cause 上面，唔會被複製到 fault 上面。唔好叫 control flow 去 parse `message` 或者 `String(fault)`——contract 係 `code` 同一個審過嘅 `status`。

預設 Struct 訊息只會寫收到嘅種類，永遠唔會包含值：`Expected number at email, received string`。同一段訊息會出現喺 `prettify()` 同 `String(fault)`。當 `RES_DECODE_FAILED` 由 JSON `SyntaxError` 引起，fault 訊息會係 `Response body could not be decoded`；原始 parser error 仍然保留喺 `cause`。原始 `StructIssue.received` 值同 parser causes 仍然可能包含敏感資料，而自訂 `errorMap` 訊息會原樣使用，所以寫 log 前要檢查自訂文字。

## 參考

| 分支                   | Control-flow 判斷                  | 好用嘅穩定 field                       | 通常冇／敏感                |
| ---------------------- | ---------------------------------- | -------------------------------------- | --------------------------- |
| HTTP status 策略       | `fault.code === 'HTTP_STATUS'`     | `fault.status`、審過嘅 `fault.data`    | Body、headers、URL、`cause` |
| Caller 取消            | `fault.code === 'NET_ABORTED'`     | `code`                                 | 取消原因同 stack            |
| Timeout                | `fault.code === 'NET_TIMEOUT'`     | `code`                                 | Request URL 同底層 cause    |
| Contract 爆咗          | `fault.code.startsWith('RES_')`    | `code`、審過嘅 `fault.response.status` | Struct issue、body、輸入值  |
| 你自己嘅 code 拋咗     | `fault.code.startsWith('EXT_')`    | `code`、`cause`                        | Extension 掛上嚟嘅任何嘢    |
| Stream／session 執行期 | `stream.closed` / `session.closed` | 終態 `kind` 同 `code`                  | 事件 payload、frame、cause  |

將 `cause`、`data`、response headers 同 bodies、URLs、`StructIssue.received`、input 值、自訂訊息同 stacks 當成敏感資料。Issue path 係結構性嘅，會保留 record 嘅 key：`struct.record(...)` 可以產生 `Expected number at alice@example.com, received string`，所以 key 喺預設訊息、`prettify()` 同 `String(fault)` 入面仍然可能敏感。預設 Struct 訊息同 `prettify()` 唔會包含收到嘅值；但記錄完整 issue 或 JSON parser cause 仍然可能洩露佢哋。一個保守嘅 summary：

  examples/errors/summarize-fault.ts#example
</include>

`createNetworkFault`、`createPreflightFault`、`createDecodeFault`、`createHttpStatusFault` 同 `createUndecodedHttpStatusFault` 構造呢啲原生 Error 值。普通嘅 request 失敗照樣喺 tuple 裡面回傳佢哋；唔會因為佢哋繼承咗原生 Error 行為就被拋出。`ERR_ABORTED` 同 `ERR_TIMEOUT` 係 transport normalizer 認得出嘅共享 causes。佢哋帶有不可枚舉嘅 `Symbol.for('defjs.cause.aborted')` 同 `Symbol.for('defjs.cause.timeout')` brands，所以取消分類唔使比較 object identity，亦可以跨 Core 副本運作。[`isAbortCause`](/zh-Hant-HK/api/core/isabortcause) 同 [`isTimeoutCause`](/zh-Hant-HK/api/core/istimeoutcause) 提供呢啲檢查同支援嘅平台錯誤檢查；分類 fault 嘅 cause 時，請傳入底層嘅 `fault.cause`。OpenTelemetry 會跨副本抑制 caller 取消操作嘅 logs，同時繼續記錄 timeout。
