# WebSocket

소켓을 선언하고, 클라이언트로 작업을 호출하고, 타입이 있는 메시지를 보내고 받은 뒤 닫아요.

## defineWebSocket()

<ApiSignature name="defineWebSocket" />

- **definition** — `path`와 `incoming` struct 하나, 선택 `outgoing`과 `input` struct, `operation`, 정적 `protocols`, `maxOutgoingQueueSize`예요. `input`을 선언하면 명시적인 `builder`가 반드시 필요해요. `input`은 인자만 정의하고, 각 값을 어디에 둘지는 `builder`만 정해요. `input`이 없는 정의만 `builder`를 생략할 수 있어요. 이 `definition` 멤버는 [`WebSocketDefinition`](/ko-KR/api/core/websocketdefinition-type)에 적혀 있어요. `builder`는 `input`을 선언했을 때만 필요해요.
- **반환** 작업이에요. 첫 인자는 [`Client`](/ko-KR/api/core/client-type)예요. 그 뒤 인자는 입력뿐이에요. 호출하면 세션이 열려요.

<include cwd>examples/api/define-web-socket.ts#example</include>

호출은 `[null, session, connection]` 또는 `[error, undefined, connection?]`을 돌려줘요. 호출별 옵션은 [`RequestOptions`](/ko-KR/api/core/requestoptions-type)로 클라이언트를 파생해서 넘기세요. WebSocket은 `signal`, `beforeConnect`, `heartbeat`, `protocols`, `retry`를 읽고, HTTP 진행률 필드는 무시해요.

`beforeConnect`, `heartbeat`, `protocols`, `retry`는 각각 그 호출에 한해 대응하는 클라이언트 수준 옵션을 통째로 바꿔요. 프로토콜 우선순위는 파생 클라이언트, `withWebSocketProtocols`, 정의의 `protocols` 순서예요. `heartbeat.timeoutMs`는 확인 대기이지, 요청 데드라인이 아니에요.

## WebSocketSession

<ApiSignature name="WebSocketSession" />

소유한 범위를 정리할 때는 `await using ownedSession = session`을 선호해요. 수동 `session.close()`와 `await session.closed`도 그대로 쓸 수 있어요.

<include cwd lang="typescript">
  examples/api/consume-web-socket.ts#consume
</include>

`closed`는 논리적인 종료 상태를 보고해요. 비동기 디스포저는 네이티브 close를 요청하고 Defjs가 소유한 정리 작업을 기다리지만, close 이벤트가 없으면 1초에서 끊고 `TimeoutError`라는 이름의 `DOMException`으로 reject할 수 있어요. 물리 TCP 연결이 닫혔다는 증명까지는 못 해요. `session.close()`가 실행되는 동안 네이티브 `close()`가 throw하면 `session.close()`가 그 오류를 throw하고, 세션은 그 원인과 함께 `closed.kind: "error"`로 끝나요.

### WebSocketState

`'idle' | 'connecting' | 'open' | 'closing' | 'closed' | 'reconnecting' | 'aborted' | 'error'`

### WebSocketConnectionInfo

`generation`(열릴 때마다 증가)과, 알려진 뒤에는 `url`, `protocol`, `extensions`가 있어요.

### WebSocketCloseInfo

<ApiSignature name="WebSocketCloseInfo" />

`kind`는 `closed`, `aborted`, `error` 중 하나예요. `cause`는 `closed`에는 없고, `aborted`에서는 선택, `error`에서는 필수예요. `error`에서는 이미 큐에 들어간 메시지 뒤에 같은 cause가 `receive`를 reject하고 `onRuntimeError`에도 전달돼요. 읽지 않은 메시지는 세션이 `aborted`로 끝날 때, 그리고 호출자가 `session.close()`나 폐기로 끝낼 때 버려져요. 호출자의 중단(`session.close()`, 폐기, `signal`의 abort)은 세션이 끝난 뒤에도 그 메시지를 버리며, `closed`나 `receive`의 reject는 바꾸지 않아요. 하트비트 타임아웃과 재시도 소진은 별도의 안정적인 코드 없이 일반 런타임 `Error`를 cause로 유지해요. 한 번 열린 뒤 close 프레임 없이 끊긴 연결(코드 `1006`)은 모든 런타임에서 `error`예요. `code`, `reason`, `wasClean`은 모든 변형에 있을 수 있어요. 수동 `session.close()`는 close 이벤트가 그 값을 주지 않을 때 `{ kind: "closed" }`의 `code`와 `reason`을 채워요.

## WebSocketExecuteOptions

<ApiSignature name="WebSocketExecuteOptions" />

`WebSocketExecuteOptions`는 [`UseWebSocketConfig`](/ko-KR/api/core/usewebsocketconfig-type)예요. `beforeConnect`, `heartbeat`, `protocols`, `retry`, `signal`이에요. `WebSocketHeartbeatConfig`: `intervalMs`와 `message`는 필수이고, `timeoutMs`는 `isAck`와 함께일 때만 허용돼요. `timeout`이나 `abort` 필드는 없어요.

`signal`은 열린 뒤를 포함해 세션 전체를 덮어요. 데드라인은 `AbortSignal.timeout(ms)`이고 `NET_TIMEOUT`으로 분류돼요. 수동 취소는 `NET_ABORTED`예요. 클라이언트 기본 데드라인은 없어요. 연결만의 데드라인은 `retry: { maxRetries: 0, attemptTimeoutMs }`이고, `open`에서 끝나요. `signal`은 그 호출의 신호예요. 신호는 애플리케이션 코드에서 `AbortSignal.any`로 합치세요. `heartbeat`는 통째로 바뀌고, 그 `timeoutMs`는 확인을 기다리는 시간이지 요청 데드라인이 아니에요.

`builder`와 인터셉터 체인은 작업마다 한 번만 실행돼요. 재연결은 만들어 둔 `path`/`query`와 캡처한 프로토콜 목록을 재사용하고, `beforeConnect` 전에 URL을 구성해요. 인터셉터가 요청의 기본 엔드포인트를 바꾸지 않았다면 재연결 시 새로 선택한 엔드포인트도 대입해요. 이 훅으로 세션 안에서 URL이나 서브프로토콜 인증 정보를 갱신할 수는 없어요. 새 `input`이나 클라이언트 설정으로 새 작업을 시작하세요.

재시도 정책(`withRetry`)이 있으면 `maxRetries` 기본값은 단절마다 3이고, `0`은 꺼요. `session.close()`가 요청하지 않은 모든 close는 기본으로 재시도돼요. 한 번도 열리지 않은 연결과 응답 없는 하트비트도 포함되고, `shouldRetry`가 이를 뒤집을 수 있어요. WebSocket 생성자가 throw하는 경우(예를 들어 플랫폼이 거부하는 서브프로토콜)는 재시도해도 반복될 뿐인 로컬 실패라, `shouldRetry`에 묻지 않고 호출이 끝나요. `open`이 성공하면 횟수와 백오프 지수가 초기화되어, 다음 단절은 재시도 1부터 시작해요. 기본값과 결정 순서는 [Client](/ko-KR/api/client#withretry)를 보세요.

## 메시지

`incoming`은 struct 하나예요. 텍스트, `ArrayBuffer`, typed-array, `Blob` 프레임은 UTF-8로 읽고, JSON 파싱한 뒤 그 struct와 맞춰 봐요. JSON 파싱이나 struct에 실패한 프레임은 `session.onRuntimeError`로 보고되고 큐에 들어가지 않아요. 잘못된 프레임을 보는 클라이언트 옵션은 없어요.

`outgoing`은 struct 하나예요. `session.send`는 그 struct의 `StructInput`을 받고, 별칭을 인코딩한 뒤 `JSON.stringify`해요. 인코딩 뒤에 JSON이 충실히 표현할 수 없는 값은 보내거나 재연결 큐에 넣기 전에 `TypeError`를 throw해요. 유한하지 않은 수, 함수, symbol, `Map`, `Set`, 스트림, JSON 표현이 없는 클래스 인스턴스가 여기 포함돼요. 중첩 값도 HTTP JSON 본문과 같은 가드를 써요. 하트비트도 그 가드를 쓰고, 하트비트 직렬화 실패는 세션을 끝내요. 메시지 종류가 여러 개면 `struct.discriminatedUnion`이에요.

## WebSocketDefinition

`path`, `incoming`, 선택 `outgoing` / `input` / `operation` / `protocols` / `maxOutgoingQueueSize`예요. `builder`는 `path`와 `query`만 돌려줄 수 있어요. `input`을 선언하면 명시적인 `builder`가 반드시 필요해요. `input`은 인자만 정의하고, 각 값을 어디에 둘지는 `builder`만 정해요. `input`이 없는 정의만 `builder`를 생략할 수 있어요.

## WebSocketEndpoint

`defineWebSocket`이 돌려줘요. 첫 인자는 클라이언트예요. 그 뒤 인자는 입력뿐이에요.

## WebSocketRequestShape

`path`와 `query`만 있어요. `headers`와 `body`는 `never`예요.

## UseWebSocketConfig

`beforeConnect`, `heartbeat`, `protocols`, `retry`, `signal`이에요. `WebSocketExecuteOptions`가 이 조각이에요. `abort` 필드는 없어요.

## SocketAwaitResult

`[null, session, connection]` 또는 `[error, undefined, connection?]`예요.

## ManualSocketCloseReason

`session.close()`로 세션을 닫을 때 기록되는 이유예요.

## WebSocketHeartbeatConfig

`intervalMs`와 `message`는 필수예요. `isAck`는 확인을 알아보고, `timeoutMs`는 `isAck`와 함께일 때만 허용돼요. 유니온 타입이 이를 강제하고, 런타임에는 아무것도 검사하지 않아요. Defjs는 하트비트 형식을 정의하지 않아요. 모든 값은 함수에서 와요. 페이로드는 `outgoing` struct를 통해 JSON 텍스트로 보내요. 응답 없는 하트비트는 소켓을 닫고 `withRetry`의 재시도 흐름으로 들어가요. 재시도 정책이 없으면 세션은 `error`로 끝나요.

## WebSocketIncomingData

디코딩된 들어오는 프레임이에요. `incoming` struct의 `Infer`예요.

## WebSocketOutgoingData

`session.send`가 받는 값이에요. `outgoing` struct의 `StructInput`이고, 선언이 없으면 `never`예요.

## SocketLifecycleOutcome

연결 시도 한 번의 결과(`closeInfo`, `connection`, `cause`, `opened`)이며 재시도 로직이 써요. 세션의 최종 결과가 아니에요. 최종 결과는 `WebSocketCloseInfo`를 보세요.
