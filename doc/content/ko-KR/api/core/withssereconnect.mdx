<ApiReference identity="@defjs/core:withSSEReconnect" />

```ts
function withSSEReconnect(options: ClientSSEOptions['reconnect']): ClientOption
```

SSE 스트림이 실패한 뒤의 자동 재연결을 설정해요. 재연결은 opt-in이에요. 이 옵션이 없으면 실패한 스트림을 재시도하지 않아요. `undefined`를 넘기면 이전 설정이 지워져요.

```ts
type SSEReconnect = {
  attempts?: number
  delayMs?: number
  factor?: number
  jitter?: number
  maxDelayMs?: number
  shouldReconnect?: (context: {
    attempt: number
    cause?: unknown
    lastEventId: string
    method: string
    open?: { response: { status: number; statusText: string; url: string }; url: string }
  }) => boolean | Promise<boolean>
}
```

- `attempts`는 단절마다의 재시도 예산이에요. `reconnect`를 설정하면 기본값은 `3`이고, `0`은 재시도를 꺼요. 핸드셰이크가 성공하면 예산, 콜백 `attempt`, 백오프 지수가 초기화돼요. 생략해도 한 단절 안에서 무제한 재시도가 되지는 않아요. 스트림 열기에 성공한 직후 재시도 가능한 스트림 실패가 반복되면, 매번 스트림이 열릴 때 예산이 초기화되므로 현재 기준 지연(jitter와 상한 적용)으로 계속 재연결할 수 있어요. 이를 중단하려면 `shouldReconnect`를 쓰세요. 정상 EOF는 여전히 종료로 처리돼요.
- `shouldReconnect`가 없으면 `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`만 재연결해요. 있으면 그 결과가 `POST`를 포함한 모든 메서드의 재연결 여부를 결정해요. 컨텍스트의 `method`로 엔드포인트를 구분할 수 있어요. 이번 실패에 대한 재시도를 멈추려면 `false`를 돌려주세요. attempts 한도를 확인하기 전에 실행돼요.
- `ReadableStream` body가 있는 요청은 재연결하지 않고, 그 요청에 대해 `shouldReconnect`도 호출되지 않아요.
- `delayMs`, `factor`, `jitter` (0에서 1), `maxDelayMs`가 백오프를 정해요. `factor`의 기본값은 `1`이고 `jitter`의 기본값은 `0`이에요. `maxDelayMs`는 jitter와 반올림 뒤의 최종 지연을 제한해요. 설정한 상한이 없어도 플랫폼 타이머 한계인 `2_147_483_647` ms는 그대로 적용돼요. 기준이 0이면 0으로 남고, 유효한 숫자의 오버플로는 상한에서 포화돼요.
- `delayMs`는 시작 기준 지연(기본값 `1000`)일 뿐이에요. 서버의 `retry:` 필드(숫자만, 밀리초)가 있으면 이후 시도에서는 그 값으로 바뀌어요.
- 마지막 이벤트 id는 다음 시도에서 UTF-8 바이트로 `Last-Event-ID`에 다시 전송돼요. 빈 `id:`는 헤더를 지우고, NUL이 들어 있는 ID는 무시해요.
- 재연결 옵션은 인터셉터나 Fetch보다 먼저 검증돼요. `attempts`는 음이 아닌 안전한 정수여야 하고, `delayMs`와 명시한 `maxDelayMs`는 유한하고 음이 아니어야 하며, `factor`는 유한하고 양수여야 하고, `jitter`는 유한하고 0–1 범위여야 해요. 잘못된 값은 실행 시점에 `REQ_OPTIONS_INVALID`를 반환해요.

스트림 핸들은 [SSE](/ko-KR/api/sse)를 보세요.
