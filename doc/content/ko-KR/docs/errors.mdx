# 오류 처리

Defjs에서는 요청, 전송, 디코딩 실패가 발생해도 호출 지점에서 예외(throw)를 던지지 않습니다. 모든 작업은 error-first 튜플(`[error, ...]`)을 반환하며, `error`는 `null`이거나 `error.code`로 구분되는 표준 `Error` 인스턴스인 타입화된 `Fault` 객체입니다.

프로그래밍 오용은 예외입니다. 보통 `Fault`를 반환하는 대신 `TypeError`로 reject됩니다. `AbortSignal`이 아닌 `signal` 옵션, `struct`가 아닌 `output`이나 `error`를 가진 HTTP 작업, 클라이언트 없이 작업을 호출하는 경우가 그렇습니다.

### HTTP 실패 시 `error`가 응답 메타데이터를 담는 이유

HTTP 실패 시 반환되는 튜플은 `[error, undefined, undefined]`입니다. 수신된 응답 메타데이터(`status`, `statusText`, `headers`, `url`)는 모두 `error.response`에 직접 첨부되므로, 로거나 오류 처리 함수에 `error` 객체 하나만 전달해도 컨텍스트를 잃지 않고 안전하게 처리할 수 있습니다.

## 2. 결함 클래스 및 닫힌 코드 유니온

첫 번째 밑줄(`_`) 앞의 접두사는 결함의 대분류(`HTTP`, `REQ`, `NET`, `RES`, `EXT`, `CAP`, `ENV`)를 나타내며, 전체 `code`는 철저한(exhaustive) `switch` 문 검사를 지원하는 닫힌 유니온을 형성합니다:

| 분류   | 결함 코드                                                              | 의미 및 해결 방법                                                                                                                                                                                                                                                           |
| ------ | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HTTP` | `HTTP_STATUS`                                                          | 서버가 비`2xx` 상태 코드(`3xx`, `4xx`, `5xx`)로 응답했으며, 선언된 `error` struct가 디코딩되었습니다.                                                                                                                                                                       |
| `REQ`  | `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`                                | 호출자 입력값 검증 실패, 잘못된 URL/경로, `builder` 예외, 또는 요청을 구성할 수 없음(HTTP: 이미 사용된 본문 스트림, 잘못되었거나 금지된 메서드, GET/HEAD 본문, 잘못된 `Content-Type`. HTTP와 SSE: 자격 증명이 있는 URL, 플랫폼이 거부하는 헤더 값). 절대 재시도하지 마세요. |
| `RES`  | `RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED`, `RES_STRUCT_MISMATCH`   | 서버 응답이 선언된 미디어 타입, 표현 형식, 또는 `struct` 계약을 위반했습니다.                                                                                                                                                                                               |
| `NET`  | `NET_ABORTED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `NET_BODY_INCOMPLETE` | 호출자의 취소(`NET_ABORTED`), 마감 시간 초과(`NET_TIMEOUT`), 네트워크 연결 실패, 또는 스트림 중간 끊김.                                                                                                                                                                     |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`     | 애플리케이션 인터셉터, 훅, 또는 진행률/상태 옵저버가 자기 오류를 던졌거나, 인터셉터가 `AbortSignal`이 아닌 `signal`을 `next()`에 넘겼습니다.                                                                                                                                |
| `CAP`  | `CAP_BUFFER_EXCEEDED`                                                  | SSE 프레임 버퍼가 설정된 한도를 초과했습니다.                                                                                                                                                                                                                               |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | 호스트 런타임에 필요한 웹 표준 API가 없습니다 (예: Firefox 환경에서의 스트리밍 요청 본문 등).                                                                                                                                                                               |

코드는 무엇이 실패했는지를 나타내며, 그 값을 누가 넣었는지는 나타내지 않습니다. HTTP에서 플랫폼이 만들 수 없는 요청은 잘못된 값이 `builder`, 클라이언트 설정, 인터셉터 중 어디서 왔든 `REQ_BUILD_FAILED`입니다. SSE는 헤더 값, 잘못된 URL, 자격 증명이 있는 URL에 같은 규칙을 첫 시도와 모든 재연결에 적용합니다. 라이브러리가 마지막 항목을 직접 검사하는 이유는 Bun이 그런 URL을 받아들이고 요청을 보내기 때문입니다. 플랫폼이 거부할 수 있는 다른 값은 SSE와 WebSocket에서 라이브러리가 검사하지 않습니다(SSE의 잘못된 메서드, WebSocket의 자격 증명이 있는 URL, 잘못된 서브프로토콜, 지원하지 않는 스킴). 그래서 그곳의 거부는 플랫폼 오류를 `cause`로 한 `NET_UNREACHABLE`로 보고되고, 그 값을 받아들이는 런타임(잘못된 SSE 메서드에 대한 Bun)은 요청을 보냅니다. `EXT_INTERCEPTOR_FAILED`는 인터셉터 자신의 동작을 뜻합니다. 인터셉터가 던진 오류, 또는 `AbortSignal`이 아닌 `signal`(요청 내용이 아니라 취소 채널)입니다.

### 코드별 결함 프로퍼티

| 결함 코드     | `status` | `response`                                 | `data`                                    | `cause`                      |
| ------------- | -------- | ------------------------------------------ | ----------------------------------------- | ---------------------------- |
| `HTTP_STATUS` | `number` | `DecodedResponse<TErr>` 또는 `HttpMeta`    | 디코딩된 `error` struct, 또는 `undefined` | 원인이 있으면 포함           |
| `RES_*`       | `number` | `HttpMeta` (**`body` 필드 없음**)          | 없음                                      | `StructError` 또는 파서 오류 |
| 기타 코드     | 없음     | 헤더 수신 시 `HttpMeta`, 그 외 `undefined` | 없음                                      | 기반 `Error` / abort 사유    |

## 4. SSE 및 WebSocket의 시작 단계 vs. 연결 후 오류

오래 유지되는 연결의 경우, 작업 반환 튜플은 스트림이나 소켓이 열리기 전의 **시작(startup)** 실패만을 보고합니다. 연결이 수립된 후 발생하는 런타임 오류는 핸들이나 세션의 수명 주기를 통해 전달됩니다:

| 전송 방식     | 시작 단계 실패 (튜플로 반환됨)                                                                                                                              | 연결 수립 후 실패 (튜플 해결 이후)                                                                                                                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HTTP**      | 모든 실패가 작업 튜플을 한 번 확정합니다.                                                                                                                   | 해당 없음                                                                                                                                                                                                                                                 |
| **SSE**       | 비`2xx`(`HTTP_STATUS`, 또는 선언된 `error` 본문을 디코딩할 수 없을 때의 디코딩 결함), 또는 잘못된 콘텐츠 타입의 `2xx` 핸드셰이크(`RES_MEDIA_TYPE_INVALID`). | 비동기 이터레이터가 reject되고, `stream.closed`가 `{ kind: 'error', code }`로 해결됩니다.                                                                                                                                                                 |
| **WebSocket** | 연결 열리기 전 닫힘, 생성자 실패, 또는 핸드셰이크 중단.                                                                                                     | 치명적이지 않은 프레임 오류는 `session.onRuntimeError`를 발생시키며, 치명적 오류는 `session.receive`를 reject하고 `session.closed`를 `{ kind: 'error', cause }`로 해결합니다. 하트비트 타임아웃과 재시도 소진은 일반 런타임 `Error`를 cause로 유지합니다. |
