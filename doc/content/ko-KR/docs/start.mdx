# 시작하기: 첫 SDK 작업 [#getting-started-one-http-request]

이 예제에서는 SDK 작성자로서 `GET /orders/:id`의 타입이 있는 정의를 export하고, 사용하는 앱의 입장에서 별도 파일에 Defjs Client를 만듭니다. 먼저 로컬 Fetch 핸들로 `200`과 선언된 `404`를 확인합니다. 실제 API로 전환할 때는 앱의 Client 설정을 바꾸고 같은 정의를 사용합니다.

## 모범 사례

정의는 client와 독립입니다. 애플리케이션의 client로 작업을 호출합니다. `getOrder(client, { id: 7 })`처럼요. 세 번째 옵션 인자는 없습니다. 작업을 호출하면 시작되고, `await`는 기다리기만 합니다. 서비스 주소와 자격 증명도 애플리케이션의 것입니다. error-first 튜플을 먼저 확인합니다. `error`가 있으면 `error.code`를 보고하고, 성공 값을 읽기 전에 함수에서 return 합니다.

## Step 1 — 설치

`@defjs/core`는 ESM이고 Node.js, Bun에서 돌아요. Node.js 22.18+ (또는 24+)는 type stripping으로 `.ts` 파일을 그대로 실행하고, 그보다 낮은 22.x는 `--experimental-strip-types`가 필요해요. package.json에 `"type": "module"`을 두세요. 브라우저에서는 여전히 번들러와 Fetch가 필요해요.

```sh
bun add @defjs/core
```

## Step 2 — 요청 정의하기

`src/define-request.ts`를 만듭니다. 이 모듈은 SDK 작성자의 것이며, client를 만들지 않고 `getOrder`를 export합니다. 입력 Struct는 호출자가 전달할 값을 선언하고, `builder`는 요청에서 그 값을 배치할 위치를 정합니다. 여기서는 입력 전체를 path 객체로 전달하므로 alias가 없는 스칼라 필드가 `:id`를 채웁니다. 정의에는 환경별 URL이나 인증 정보를 넣지 않습니다.

<include cwd meta="define-request.ts">
  examples/start/define-request.ts#example
</include>

`output`은 2xx body예요. `error`는 그 밖의 모든 status예요. 각각 struct 하나예요. body가 달라지면 `struct.or(...)`나 discriminated union을 쓰세요.

`defineRequest(...)`는 작업을 돌려줘요. `getOrder(client, input)`을 호출하면 요청이 시작돼요. 위의 `builder`는 입력을 배치하는 함수이지, 작업이 아니에요. `input`을 선언했다면 `builder`는 필수이고, 동기적인 순수 함수예요.

## Step 3 — 로컬에서 호출하기

같은 디렉터리에 `src/execute-locally.ts`를 만들고 `./define-request.ts`에서 정의를 import합니다. 앱은 Client의 endpoint, 인증, 인터셉터, 전송 수단을 선택합니다. 이 예제에서는 로컬 Fetch 핸들을 설정해 네트워크 없이 입력 검증, `Request` 생성, status 분기, body 파싱을 실행합니다.

<include cwd meta="execute-locally.ts">
  examples/start/execute-locally.ts#example
</include>

실행해요:

```sh
bun src/execute-locally.ts
```

```txt
Loaded paid from 200
```

없는 주문을 시험해 보려면 path id를 `8`로 바꾸고 다시 실행해요:

```txt
Order not found
```

성공하면 `error`는 `null`이고, `order`는 `200` Struct 출력이고, `response`는 `DecodedResponse<Order>`예요. 선언된 `404`에서는 `error.code`가 `'HTTP_STATUS'`이고, `error.status`는 `404`이고, `error.data`는 타입이 잡힌 `NotFound`예요. 실패하면 튜플의 두 번째 항목은 `undefined`예요.

## Step 4 — 실제 API로 연결하기

`src/real-api.ts`에서 같은 `getOrder`를 import하고, 서비스의 base URL로 client를 만듭니다. 예제 주소를, 그 body 계약으로 `GET /v1/orders/:id`를 구현한 서비스로 바꾼 뒤에만 이 버전을 실행하세요.

<include cwd>examples/start/real-api.ts#example</include>

API 정의는 SDK 모듈에 남습니다. 서비스 주소, 자격 증명, 인터셉터, 실행 수명은 애플리케이션이 가집니다. 두 client는 같은 Defjs 엔드포인트 계약을 사용합니다.

## 정의 배포하기

더 많은 애플리케이션이 이 정의를 필요로 하면 SDK 패키지로 옮깁니다. `getOrder`를 export하고, TypeScript 선언을 넣으며, 호환되는 Core 버전을 선언합니다. 사용하는 쪽은 `./define-request.ts`가 아니라 패키지에서 import합니다. client 설정은 그대로 그쪽의 것입니다. 패키지 구성 전체는 [SDK 작성과 배포](/ko-KR/recipes/publish-http-sdk)를 따르세요.

## 결과가 달라질 때

- 잘못된 입력 → `REQ_INPUT_INVALID`. 실패하는 `builder` → `REQ_BUILD_FAILED`
- non-2xx status → `HTTP_STATUS`. `error`를 선언했고 그 body가 디코딩되면 타입이 있는 `error.data`
- 선언된 JSON body인데 다른 미디어 타입 → `RES_MEDIA_TYPE_INVALID`. body를 읽기 전에 보고돼요
- 선언된 body (2xx는 `output`, 그 밖은 `error`)가 디코딩되지 않음 → status와 관계없이 `RES_DECODE_FAILED` 또는 `RES_STRUCT_MISMATCH`
- Fetch 실패 / 취소 / 데드라인 → `NET_UNREACHABLE` / `NET_ABORTED` / `NET_TIMEOUT`

데드라인은 `client({ signal: AbortSignal.timeout(ms) })`이고 `NET_TIMEOUT`으로 분류돼요. 수동 취소는 `NET_ABORTED`예요. 클라이언트 기본 데드라인은 없어요. 호출 하나에 자기 `signal`이 필요하면 클라이언트를 파생하세요. [클라이언트](/ko-KR/docs/client)를 보세요. 취소는 호출자가 본 것을 알려 줄 뿐, 서버 쓰기가 커밋됐는지는 알려 주지 않아요.
