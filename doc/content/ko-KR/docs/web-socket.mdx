# WebSocket

시작 → 수신 → 송신 → `await using`으로 놓기. unsubscribe와 disposal은 호출하는 쪽이 소유해요. 수동 `close()` / `closed`도 그대로 쓸 수 있어요. 클라이언트, provider, interceptor는 세션을 자동으로 닫지 않아요.

## 방향마다 struct 하나

`incoming`은 모든 텍스트 프레임을 위한 struct 하나예요. `outgoing`은 `session.send(...)`를 위한 struct 하나예요. 종류가 여러 개면 `struct.discriminatedUnion`으로 모델링해요. 그 필드의 alias가 양방향의 와이어 이름이에요. 따로 있는 type envelope도 없고 normalizer도 없어요.

```json
{ "type": "message", "text": "Hello" }
```

들어오는 텍스트, `ArrayBuffer`, typed-array, `Blob` 프레임은 UTF-8로 읽고, JSON 파싱한 뒤 `incoming`과 맞춰 봐요. 잘못된 JSON과 struct 실패는 `session.onRuntimeError`로 가고 큐에 들어가지 않아요. 세션은 그대로 있어요. 텍스트, 바이트, `Blob`이 아닌 프레임은 무시돼요. `withWebSocketOnInvalidEvent`는 없어요.

`session.send(...)`는 동기적으로 검증하고 직렬화해요. struct 인코딩 다음 `JSON.stringify`예요. open이면 바로 보내고, outgoing 큐가 켜져 있으면 `reconnecting` 동안 큐에 넣고, 쓸 수 없으면 `InvalidStateError`를 throw해요. outgoing struct가 없거나, payload가 struct에 실패하거나, outgoing 큐가 꺼져 있거나 가득 찼거나, 네이티브 send가 실패해도 throw해요. 정의의 정적 `protocols` 목록이 엔드포인트 계약이에요 (예를 들어 `graphql-transport-ws`). 실행 옵션과 `withWebSocketProtocols`는 여전히 그걸 덮어쓸 수 있어요. 서브프로토콜은 그 옵션들만 정해요. builder, `beforeConnect`, interceptor는 바꿀 수 없으므로, 서브프로토콜 안의 토큰은 그 호출의 execute `protocols` 옵션으로 넘겨요. builder는 `path`와 `query`만 돌려줄 수 있어요.

`receive`는 소비자 하나예요. 두 번째 iterator를 요청하면 `TypeError`를 throw해요.

## 상태 스냅샷

| 멤버                       | 의미                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------- |
| `state`                    | `idle`, `connecting`, `open`, `reconnecting`, `closing`, `closed`, `aborted`, `error` |
| `connection`               | 최신 물리 연결. `generation`, URL, 협상된 프로토콜, 있으면 extensions                 |
| `bufferedAmount`           | 네이티브 미전송 바이트 수. 물리 소켓이 없으면 `0`                                     |
| `receive`                  | 검증된 들어오는 메시지의 소비자 하나짜리 async iterable                               |
| `onStateChange(listener)`  | 논리 상태 전이를 구독해요. unsubscribe를 돌려줘요                                     |
| `onRuntimeError(listener)` | 시작 이후의 런타임 오류를 구독해요. unsubscribe를 돌려줘요                            |
| `closed`                   | 논리적인 종료 close 결과의 프로미스                                                   |

`open`은 물리 소켓이 열린 상태예요. `reconnecting`은 교체 전의 준비와 지연을 포함해요. `connection.generation`은 `open`에 도달한 물리 소켓마다 증가해요. 튜플의 `startupConnection`은 첫 성공 스냅샷으로 남고, `session.connection`은 앞으로 움직여요.

시작 실패는 `[error, undefined, connection?]`예요. open 전의 생성자 실패는 connection이 없을 수 있고, 시작 중의 timeout/close는 스냅샷을 줄 수 있어요. 세션이 돌아온 뒤의 런타임 오류는 옵저버, `receive`, `closed`로 이동해요. 두 번째 execute 튜플이 아니에요.

## 재연결

재연결은 opt-in이에요. `reconnect` 객체가 없으면 물리 close가 논리 세션을 끝내요. 설정하면 기본값은 `attempts: 3`, `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000`, `jitter: 0`이에요. `attempts`는 처음 시도 뒤의 재시도 횟수예요. `attempts: 0`은 꺼요. 기본 predicate는 모든 close 결과를 받아요.

<include cwd>examples/web-socket/reconnect.ts#example</include>

`shouldReconnect`는 다음 재시도 횟수, close cause, code, reason, `wasClean`을 받아요. 수동 `session.close(...)`는 predicate에 들어가지 않아요. 준비/정책이 throw하면 논리 세션이 오류로 끝나요.

WebSocket backoff jitter는 **곱셈**이에요 (`jitter: 0.2` → 지연이 `0.8x`와 `1.2x` 사이). SSE jitter는 WebSocket과 같은 0–1 곱셈 계수예요. delay/factor/jitter/attempt 값은 생성자 전에 검증돼요. 타이머 지연은 `2_147_483_647` ms를 넘을 수 없어요.

`beforeConnect({ attempt, signal })`는 처음 생성자와 모든 재연결 전에 돌아요. 취소가 준비와 연결을 모두 멈추게 하려면 그 signal을 토큰 갱신에 넘기세요.

## Heartbeat

실행 범위나 클라이언트 범위에서 opt-in이에요. 간격마다 `message()`를 outgoing struct로 보내요. 선택 `isAck(message)`가 ack를 알아보면 그 메시지는 timeout을 지우고 `receive`로 **전달되지 않아요**.

<include cwd>examples/web-socket/heartbeat.ts#example</include>

`intervalMs`와 `timeoutMs`는 `2_147_483_647` 이하의 양의 유한 타이머여야 해요. heartbeat 메시지는 outgoing struct에 유효해야 해요. 직렬화, 네이티브 send, ack 분류, timeout 실패는 논리 세션에 치명적이에요. 평범한 재연결이 되지 않아요.

## 큐

| 설정                   | 필요한 값                              | 동작                                                                                                     |
| ---------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `maxIncomingQueueSize` | 양의 안전 정수                         | `receive`를 기다리는 파싱된 메시지와 transform을 기다리는 raw 프레임을 제한해요. 넘치면 `state: 'error'` |
| `maxOutgoingQueueSize` | 선택적인 음이 아닌 안전 정수. 기본 `0` | `state === 'reconnecting'`일 때만 FIFO. 가득 찼거나 꺼져 있으면 `send(...)`가 throw해요                  |

큐에 있던 outgoing 프레임은 교체 소켓이 `open`을 발표하기 전에 flush돼요. 이전 소켓에서 이미 보낸 프레임은 자동으로 다시 보내지지 않아요. 재연결 큐는 재연결하는 동안 보내는 메시지용이지, 앱 상태를 다시 만드는 용도가 아니에요.

들어오는 쪽이 넘치면 대기 순서를 지우고, `receive`를 실패시키고, 세션을 멈추고, `session.closed`를 `kind: 'error'`로 resolve해요. 소비자를 충분히 빠르게 두거나, 측정한 크기/메모리로 한도를 올리세요.

## 프로토콜과 인증

정의 `protocols`, 클라이언트 `withWebSocketProtocols(...)`, 실행 `protocols`가 생성자 서브프로토콜 목록을 설정해요. 우선순위는 실행 → 클라이언트 → 정의예요. 처음 정의된 목록이 논리 세션용으로 복사되고 재연결에서 재사용돼요.

브라우저 WebSocket 생성자는 임의 handshake 헤더를 받지 않고, builder는 `headers`나 `body`를 돌려줄 수 없어요. Defjs는 `http:`를 `ws:`로, `https:`를 `wss:`로 바꾸고, path placeholder를 한 번 인코딩하고, HTTP와 같은 query 규칙을 써요. 기본은 스칼라와 반복 키이고, 중첩 객체는 `withQuerySerializer`이고, query가 없으면 serializer를 호출하지 않아요.

`withCredentials(true)`는 HTTP/SSE의 Fetch credentials예요. WebSocket 인증이 아니에요. 검토된 쿠키/세션 정책, 서브프로토콜, 또는 짧은 수명의 연결 티켓을 쓰세요. 일반적인 자격 증명이나 오래 사는 비밀을 query 문자열에 넣지 마세요.

## 종료와 소유권

`session.close(code?, reason?)`는 종료를 요청하고 heartbeat를 멈춰요. code는 `1000` 또는 `3000..4999`여야 하고, reason은 UTF-8 123바이트 이하여야 해요. 잘못된 close 인자는 상태를 바꾸기 전에 throw해요. 수동 close 이유나 논리 종료 결과가 필요하면 `await session.closed`와 함께 쓰세요.

`execute`에 넘긴 `signal`이나 `abort`는 열린 세션에 계속 붙어 있어요. 나중에 abort하면 세션은 `'aborted'`로 끝나고 `receive`는 `AbortError`로 reject돼요. `timeout`은 시작 시점의 마감일 뿐이에요.

</include>

`session.closed`는 논리 종료 스냅샷이에요. `'closed'`, `'aborted'`, `'error'`이고, 선택 네이티브 `code` / `reason` / `wasClean`과 aborted/error의 `cause`가 있어요. 관찰된 네이티브 close 필드가 소유자가 요청한 fallback보다 우선해요.

표준 async disposer는 최선을 다한 네이티브 close를 요청한 뒤, Defjs가 소유한 lifecycle, 메시지 펌프, 타이머, 리스너, 큐, 소켓 참조 teardown을 기다려요. close 이벤트가 1초 안에 관찰되지 않으면 teardown을 강제하고, disposer는 `TimeoutError`라는 이름의 `DOMException`으로 reject할 수 있어요. 물리 TCP 연결이 닫혔다는 증명은 아니에요. 반복된 disposer 호출은 같은 teardown을 공유해요. 커스텀 구조적 세션 구현은 이제 같은 `[Symbol.asyncDispose](): PromiseLike<void>` 계약을 제공해야 해요.

## GraphQL 경계

Defjs는 incoming struct 하나, outgoing struct 하나, 논리 세션 수명을 제공해요. WebSocket 애플리케이션 프로토콜을 구현하지는 **않아요**. GraphQL-over-WebSocket 기능 — connection init, operation ID, `next`/`error`/`complete`, disposal, subscription 재전송 — 은 core 계약 밖이에요.

서버가 그 프로토콜을 요구하면 `graphql-ws` 같은 프로토콜 클라이언트를 쓰거나, `defineWebSocket(...)`으로 프레임을 모델링하세요. `graphql-transport-ws` 같은 정적 서브프로토콜은 `protocols`에 두세요. struct만으로는 GraphQL 의미를 협상하지 않아요.
