# 로드 밸런싱 및 장애 조치

애플리케이션이 `withEndpoint(...urls)`를 사용해 여러 기본 URL을 구성하면, Defjs는 여러 레플리카에 요청을 분산하고, 수동 서킷 브레이킹이나 능동 헬스 체크를 통해 비정상 호스트를 제외하며, 안전한 HTTP 메서드를 동일 호출 내에서 선택적으로 다른 엔드포인트로 장애 조치(failover)할 수 있습니다.

## 1. 로드 밸런서 전략 선택

| ----------------------------------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------- |
| [`pickFirstBalancer(options?)`](/ko-KR/api/core/pickfirstbalancer) _(기본값)_ | 순서가 지정된 기본/백업 리전 목록을 사용하는 브라우저 앱              | 꺼짐 (`outlierDetection` 옵션으로 선택 활성화) |
| [`roundRobinBalancer(options?)`](/ko-KR/api/core/roundrobinbalancer)          | 동일한 사양의 레플리카 간 서버 간 호출 (선택적 `weights` 가중치 지원) | 활성화 (`5`회 연속 실패 시)                    |

### `pickFirstBalancer`와 `p2cBalancer`의 동작 방식

- **`pickFirstBalancer`**: 첫 번째 URL을 유지하고, `NET_UNREACHABLE` 또는 `NET_UNAVAILABLE`(HTTP 502, 503, 504)에서 다음으로 진행합니다. `failbackMs: 30_000`을 설정하면 백업에서 그 시간만큼 머문 뒤 기본 엔드포인트를 다시 프로브합니다.
- **`p2cBalancer` (Power of Two Choices)**: 복원 추출 없이 무작위로 두 개의 후보를 뽑아 더 낮은 점수를 가진 엔드포인트를 선택합니다: `PeakEwma RTT × (pending + 1)` (또는 `load: "pending"`인 경우 진행 중인 요청 수). 기본값(`defaultRttMs: 30`, `decayMs: 10000`)은 Linkerd/tower 관례를 따릅니다.

## 2. 동일 호출 내 HTTP 재시도

재시도는 세 가지 결정으로 나뉩니다. **다시 시도할지**(`withRetry`), **어디로 보낼지**(런타임이 밸런서에게 다시 pick하도록 하고, 이미 시도한 엔드포인트는 제외합니다), **얼마나 기다릴지**(백오프)입니다. HTTP의 `withRetry`, SSE의 `withSSEReconnect`, WebSocket의 `withWebSocketReconnect`는 대칭적인 전송 계층 정책입니다. 평탄한 백오프 필드는 이름, 검증, 지연 계산이 같습니다. 밸런서는 재시도 정책을 알지 못하며, 커스텀 밸런서에 특별한 협조가 필요하지 않습니다.

동일 호출 내 HTTP 재시도는 **기본적으로 꺼져 있습니다**. `withRetry`를 생략하면 호출당 시도는 한 번이며, 재시도 예산은 만들어지지도 적립되지도 않습니다. 이후 호출의 선택은 바뀌지 않습니다. `pickFirstBalancer`는 실패한 호출 뒤에도 여전히 다음으로 진행할 수 있습니다. `withRetry()`는 `withRetry({})`와 같으며, `GET`, `HEAD`, `OPTIONS`, `TRACE`의 연결 실패에 대해 총 두 번의 시도를 켭니다.

이것은 Go 생태계를 따릅니다. [gRPC는 `retryPolicy`를 서비스 설정에 둡니다](https://grpc.io/docs/guides/retry/). 로드 밸런싱 설정과 나란히 두며, [go-kit `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry)는 밸런서를 명시적으로 감쌉니다. 어느 쪽도 애플리케이션 재시도 정책을 기본으로 적용하지 않습니다. gRPC의 재시도 정책은 백오프 설정이 필요하며 ±0.2 지터를 씁니다. [Envoy의 기본값은 25ms 기수와, 그 기수의 최대 열 배입니다](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff). Defjs는 25ms, factor 2, 250ms 상한, ±20% 지터를 씁니다. gRPC는 저수준 경합에 대해 투명 재시도를 할 수 있지만, Defjs는 그것을 흉내 내지 않습니다.

- **총 시도 횟수 (`maxAttempts`)**: 최초 시도를 포함하며, gRPC `retryPolicy.maxAttempts` 및 go-kit `lb.Retry`의 `max`와 같습니다. 값은 1 이상의 안전한 정수여야 하고, `1`은 재시도가 없음을 뜻합니다. 설정된 상한은 없지만, 각 엔드포인트는 최대 한 번만 시도합니다. 스트리밍 요청 본문은 재시도하지 않습니다. `methods`는 대소문자를 구분하지 않으며, `methods: []`는 모든 메서드의 재시도를 끕니다.
- **재시도 조건 (`on`)**: 기본값은 `["connect-failure"]`입니다. `NET_UNAVAILABLE`(HTTP `502`/`503`/`504`)에는 `"gateway-error"`를 더합니다. `RES_*` 디코딩이 거절한 게이트웨이 오류 본문도 포함합니다. `attemptTimeoutMs`가 설정된 경우 `"attempt-timeout"`도 더할 수 있습니다. 재시도 자격이 되면 요청을 다시 만들고, 인터셉터 체인 전체를 가장 바깥 계층부터 다시 실행합니다.
- **백오프 (`delayMs`, `factor`, `jitter`, `maxDelayMs`)**: n번째 재시도 전에는 `delayMs × factor^(n−1)`만큼 기다리며, 곱셈 지터를 적용하고 지터와 반올림 뒤에 상한을 둡니다. 기본값은 `25`, `2`, `0.2`, `250`입니다. `delayMs: 0`은 기다리지 않습니다. 재연결과 같이 `delayMs`는 유한한 0 이상, `factor`는 유한한 양수, `jitter`는 `[0, 1]`의 유한한 값, `maxDelayMs`는 0 이상의 유한한 값 또는 양의 `Infinity`여야 합니다. 플랫폼 타이머 상한은 그대로 적용됩니다.
  설정된 엔드포인트가 하나뿐이면, 각 재시도가 이미 시도한 엔드포인트를 제외하므로 `withRetry`는 요청을 다시 보내지 않습니다.

- **시도별 vs. 전체 호출 타임아웃**: `attemptTimeoutMs`는 유한한 양수여야 하고 2147483647(타이머 상한)을 넘지 않아야 합니다. 그렇지 않으면 작업은 `REQ_OPTIONS_INVALID`를 반환합니다. 그것은 Fetch 호출부터 본문 디코딩까지 단일 시도의 시간을 제한합니다. 호출자의 `client({ signal: AbortSignal.timeout(ms) })`는 모든 시도와 **백오프 대기**를 아우릅니다. 대기 중 취소는 다시 pick하지 않고 호출자의 취소 오류를 반환합니다.
- **Finagle / Linkerd 재시도 예산 (`budget`)**: 각 클라이언트 설정이 예산을 소유하며, 그 설정을 쓰는 파생 클라이언트만 공유합니다. 밸런서를 공유하는 클라이언트끼리는 공유하지 않습니다. 기본값은 `percentCanRetry: 0.2`, `minRetriesPerSecond: 10`, `ttlMs: 10000`이며, 원래 트래픽의 20%에 예비분을 더한 값입니다. 크레딧과 데빗은 TTL/10 슬라이스 열 개에서 지연해서 만료됩니다. 재시도는 기다리기 전에 인출하고, 예산이 소진되면 기다리지도 재시도하지도 않습니다. 상한을 없애려면 `budget: false`로 설정하세요.
- **브라우저 오프라인 힌트**: `navigator.onLine === false`인 경우 연결 실패는 `{ attempted: false }`로 보고되며, 밸런서를 다음으로 넘기거나 재시도를 트리거하지 않습니다.

이후 `withRetry`는 정책을 대체합니다. `withRetry()`와 `withRetry(undefined)`는 `withRetry({})`와 같이 동작합니다. 재시도를 켠 뒤 끄려면 `withRetry({ maxAttempts: 1 })`를 전달합니다. 잘못된 재시도 설정은 HTTP 작업이 실행될 때 `Invalid retry options`와 함께 `REQ_OPTIONS_INVALID`를 반환합니다.

## 3. 수동 서킷 브레이킹 및 능동 헬스 체크 (`outlierDetection`)

`roundRobinBalancer()`와 `p2cBalancer()`는 기본적으로 후보 선택 로직을 [`outlierDetection`](/ko-KR/api/core/outlierdetection)으로 감싸서 제공합니다:

1. **연속 실패**: 기본 분류기는 `NET_UNREACHABLE`, `NET_UNAVAILABLE`, `NET_SERVER_ERROR`를 셉니다. 그렇게 센 결과가 `consecutiveFailures`(기본값 `5`)만큼 연속되면, 해당 엔드포인트는 `min(minPenaltyMs × 2^level, maxPenaltyMs)`(`1000ms` ~ `60000ms`)에 최대 `50%`의 균등 양수 지터가 더해진 시간 동안 제외됩니다.
2. **단일 프로브 복구**: 패널티 기간이 만료되면 단 하나의 요청이 해당 호스트를 프로브합니다. 피어 응답이 시작될 때(`end`) 센 실패가 없으면 즉시 정상 트래픽을 재개하고 패널티 레벨을 `0`으로 초기화합니다. 실패하면 패널티 시간이 두 배가 됩니다.
3. **패닉 모드 오픈(Fail-open)**: 설정된 모든 엔드포인트가 격리되거나 비정상으로 판정되면, 밸런서는 로컬에서 모든 트래픽을 즉시 드롭하는 대신 클라이언트의 전체 후보 목록을 개방(fail-open)하여 요청을 시도합니다.

## 4. 전송 통계 수명 주기 (`pick` → `start` → `end` → `done`)

커스텀 밸런서는 동기 `pick(info)`와 선택적 `start()`, `end(info)`, `done(info)` 콜백을 구현합니다. `PickInfo`에는 후보 `endpoints`와 선택인 정의 `operation`만 있으며, 전송 구분자는 없습니다. 전송은 자신의 사실을 중립적인 `DoneInfo.code` 결과로 옮깁니다. 내장 밸런서는 `status`를 읽지 않으며, 이 원시 응답 정보는 커스텀 밸런서만을 위해 남깁니다. `start`는 시도 전에, `end`는 피어 응답이 시작되거나 응답 전 실패가 있을 때, `done`은 완료 때 실행됩니다. 따라서 이후의 본문 실패는 앞선 `end` 표본을 바꾸지 않은 채 최종 코드를 바꿀 수 있습니다.

| 물리적 전송 결과                                              | 최종 `done(info)` 샘플                                     |
| ------------------------------------------------------------- | ---------------------------------------------------------- |
| HTTP/SSE 응답 상태 502, 503 또는 504                          | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| HTTP/SSE의 그 외 500 이상 응답 상태                           | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| HTTP/SSE 응답 상태 2xx, 3xx 또는 4xx(429 포함)                | `{ attempted: true, status }`                              |
| HTTP 응답 본문이 스트림 도중 끊김                             | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| SSE 핸드셰이크 성공 후 스트림 `reader.read()`가 거부          | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| SSE 정상 EOF, 성공한 핸드셰이크의 디코딩 실패, 또는 큐 한도   | `{ attempted: true, status }`                              |
| 열린 WebSocket이 코드 `1006` 또는 `wasClean === false`로 종료 | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| 열린 WebSocket이 정상적으로 닫힘                              | `{ attempted: true }`                                      |
| 호출자 취소 또는 수동 스트림/소켓 종료                        | `{ attempted: false }`                                     |
| 시도 시작 후 호출자 마감 시간 만료                            | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

핸드셰이크 디코딩 실패는 핸드셰이크 상태에서 나온 중립 결과를 유지합니다(예를 들어 status `503`의 `NET_UNAVAILABLE`). 불완전한 HTTP 본문은 게이트웨이 응답이어도 `NET_BODY_INCOMPLETE`와 원시 status를 유지하며, 기본 outlier detection은 그것을 세지 않습니다.
