# 인터셉터

인터셉터는 SDK 작업 정의를 수정하지 않고도 애플리케이션의 `Client`에 인증 헤더 추가, 요청 서명, 유지보수 모드 단락(short-circuit), `Retry-After` 처리 등 횡단 관심사 실행 정책을 연결할 수 있게 해줍니다.

입력값 검증 및 `builder` 매핑은 인터셉터 체인이 실행되기 **전에** 수행되며, HTTP 상태 코드 분기 및 `output` / `error` struct 유효성 검증은 인터셉터 체인이 실행된 **후에** 수행됩니다. [작업 인터셉터](/ko-KR/docs/interceptors#operation-interceptors)는 이 모든 것을 감쌉니다.

### 인터셉터 파이프라인 규칙

- **양파 껍질 순서**: 요청이 나갈 때는 등록된 순서대로 실행되고(`before next(req)`), 응답이 돌아올 때는 등록 역순으로 실행됩니다(`after await next(req)`). 전역 로깅이나 추적 인터셉터는 인증이나 재시도 같은 구체적인 인터셉터의 바깥쪽에 배치하세요.
- **불변 요청 객체 규칙**: 외부 재시도 로직이 깨끗한 헤더 상태를 참조할 수 있도록, 항상 `req.headers`를 복제(`new Headers(req.headers)`)하여 새로운 요청 객체(`{ ...req, headers }`)를 `next(...)`에 전달하세요.
- **`content-type`과 `bodyContentType`**: Defjs는 추론된 본문 콘텐츠 타입을 `req.headers`를 직접 변경하지 않고 `req.bodyContentType`에 저장합니다. 요청 서명 모듈은 `req.headers.get("content-type") ?? req.bodyContentType`을 읽어야 합니다. 인터셉터가 `req.body`를 새로운 형식으로 교체하는 경우 명시적인 `content-type` 헤더를 설정하세요.

## 2. `makeResponse`를 통한 요청 단락(Short-circuit)

HTTP 인터셉터는 `makeResponse(...)`를 사용하여 합성 응답을 만들어 `next(req)`를 호출하지 않고 즉시 반환할 수 있습니다:

<include cwd lang="typescript">

`makeResponse`는 검증 과정을 우회(bypass)하는 것이 **아닙니다**. 합성된 응답 역시 해당 작업의 미디어 타입 확인, 상태 코드 분기(`2xx` vs 비`2xx`), `output` / `error` struct 유효성 검증을 거칩니다.

## 3. 재시도와 `Retry-After`

HTTP 재시도는 기본적으로 꺼져 있습니다. 연결 실패, 타임아웃, 또는 `502`, `503`, `504`를 다른 엔드포인트에서 재시도하려면 [`withRetry()`](/ko-KR/docs/load-balancing#retries)를 사용하세요. 백오프 지연 뒤에 밸런서가 다시 고르게 하고, 요청을 다시 빌드하며, 전체 인터셉터 체인을 다시 실행합니다.

대신 애플리케이션 인터셉터가 `429`와 `Retry-After`처럼 같은 엔드포인트의 상태 처리를 구현할 수도 있습니다:

<include cwd lang="typescript">
  examples/interceptors/honor-retry-after.ts#example
</include>

- **두 재시도 계층**: 이 `next(request)` 루프는 선택된 엔드포인트를 유지하며 `builder`나 외부 인터셉터를 다시 실행하지 않습니다. 연결 실패와 `502`/`503`/`504`는 `withRetry`에 맡기세요.
- **`Retry-After` 정책**: Core의 `withRetry`는 이 헤더를 읽지 않습니다. 레시피의 30초 상한과 250 ms 대체값은 애플리케이션의 선택입니다. 서버가 요구한 지연이 더 길 때 상한을 적용하면 요청된 시간보다 일찍 재시도할 수 있습니다. 이를 허용할 수 없다면 전체 지연을 기다리거나 응답을 그대로 반환하세요.
- **401 쓰기**: [Bearer 갱신 레시피](/ko-KR/recipes/refresh-bearer-once)는 JSON POST를 두 번 전달할 수 있습니다. 비즈니스 처리 전에 인증이 요청을 거부하고, 안정적인 멱등성 키로 서버 측 중복을 제거하도록 보장해야 합니다. 그렇지 않으면 쓰기를 자동 재전송하지 마세요. 스트림 요청 본문은 재전송하지 않습니다.
- **전송 계층 거부(rejection) 처리**: 네트워크 오류가 발생하면 `next(request)`는 상태 코드 0 응답 대신 reject됩니다. 이 거부를 잡아서 다시 throw하면 원래의 `NET_*` 결함 코드가 보존됩니다.
- **보낼 수 없는 요청**: HTTP 인터셉터에서 플랫폼이 요청을 거부하거나(잘못되었거나 금지된 메서드, GET 또는 HEAD 본문, 자격 증명이 있는 URL, 잘못된 `Content-Type`) `finalizeHeaders` 훅이 throw하면, `next(request)`는 라이브러리의 `BodyFailure` 래퍼가 아니라 플랫폼 자신의 오류(`TypeError`)나 훅이 던진 값으로 reject됩니다. 그것을 다시 throw하면 결함 코드(`REQ_BUILD_FAILED` 또는 `EXT_HOOK_FAILED`)가 유지되고, 다른 오류를 던지면 실패는 자신의 것(`EXT_INTERCEPTOR_FAILED`)이 됩니다. 전송 주변에서 발견되는 다른 실패는 여전히 `BodyFailure`로 `next(request)`에 닿습니다. 읽거나 디코딩하거나 미디어 타입에 맞출 수 없는 응답 본문, 잘린 본문, throw하는 업로드 진행률 옵저버(`EXT_OBSERVER_FAILED`)가 그에 해당하며, 그 옵저버는 요청을 보내기 전에도 throw할 수 있습니다.
- **인터셉터 내부 예외 발생 시**: 인터셉터 자신의 처리되지 않은 예외가 발생하면(`next()`에 `AbortSignal`이 아닌 `signal`을 넘기는 경우 포함) 작업 튜플은 `EXT_INTERCEPTOR_FAILED`로 해결되고 원인이 `err.cause`에 담깁니다. `ERR_ABORTED`나 `ERR_TIMEOUT`을 던지면 `NET_ABORTED`나 `NET_TIMEOUT`으로 해결됩니다.

SSE에서는 `next()`를 반복 호출하는 인터셉터보다 `withRetry`를 우선 사용하세요. 인터셉터의 `next()`를 두 번 이상 호출하면 대체 스트림의 엔드포인트 귀속과 재선택이 비활성화됩니다. 이 동작은 이터레이터의 `next()`로 이벤트를 소비하는 것과는 무관합니다.

## 4. WebSocket 세션 래핑

## 5. 작업 호출 전체 관찰하기 [#operation-interceptors]

전송 인터셉터는 한 번에 요청 하나만 봅니다. 검증에 실패한 입력은 인터셉터에 닿지 않고, 재시도마다 인터셉터가 다시 실행되며, 응답은 인터셉터가 반환된 뒤에 디코딩됩니다. `getOrder(client, input)`을 호출한 순간부터 튜플이 해결될 때까지 호출 자체를 관찰하려면 `createOperationInterceptor`를 사용하세요:

<include cwd lang="typescript">
  examples/api/create-operation-interceptor.ts#example
</include>

- **볼 수 있는 것**: `call`은 정의를 설명합니다. `transport`(`"http"`, `"sse"`, `"websocket"`), `method`, `path` 템플릿, `meta`입니다. 입력과 요청은 아직 존재하지 않으므로 담기지 않습니다. `next()`는 작업의 튜플로 해결되므로 `err`는 최종 결함입니다. `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`, `HTTP_STATUS`, `RES_STRUCT_MISMATCH` 등이 그에 해당합니다.
- **관찰만 하고 바꾸지 않습니다**: `next()`는 인자를 받지 않고, 두 번째 `next()`는 호출을 다시 실행하지 않고 같은 Promise를 반환하며, 함수는 `next()`가 해결한 값으로만 해결할 수 있습니다. 요청과 응답은 전송 인터셉터에서 바꾸세요.
- **순서**: 작업 인터셉터는 모든 전송 인터셉터의 바깥쪽에서 등록 순서대로 실행됩니다. OpenTelemetry의 `context.with`처럼 `next()` 주변에서 실행되는 코드는 전송 인터셉터를 포함한 호출 전체에 적용됩니다.
- **스트림과 세션**: SSE나 WebSocket 호출은 스트림이나 세션이 열리면 해결됩니다. 그 뒤에 일어나는 일은 `closed`를 통해 관찰합니다.
- **실패**: throw나 reject는 작업을 `EXT_INTERCEPTOR_FAILED`로 해결하고 던진 값을 `cause`로 담습니다. 호출이 이미 열어 둔 스트림이나 세션은 닫힙니다.

## 6. 내장 팩토리 및 헬퍼

| Export                                         | 전송 방식 | 설명                                                                          |
| ---------------------------------------------- | --------- | ----------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP      | `(req, next) => Promise<HttpResponse<unknown>>` 래핑                          |
| `createSSEInterceptor(fn)`                     | SSE       | `(req, next) => Promise<EventStreamHandle<unknown>>` 래핑                     |
| `createWebSocketInterceptor(fn)`               | WebSocket | `(req, next) => Promise<WebSocketSessionLike>` 래핑                           |
| `createOperationInterceptor(fn)`               | 모두      | 작업 호출 전체를 `(call, next) => Promise<result>`로 래핑                     |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP      | 요청마다 호출되는 동기 자격 증명 제공자로부터 `Authorization: Basic ...` 주입 |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE       | SSE 핸드셰이크 시 `Authorization: Basic ...` 주입                             |
