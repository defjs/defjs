## URL 해석하기

`withEndpoint(...)`에는 유효한 절대 URL이 필요해요. endpoint pathname은 디렉터리로 남고, query와 hash는 명령을 해석하기 전에 버려져요. 없거나 상대적이거나 잘못된 base endpoint는 요청을 만드는 동안, interceptor나 전송이 돌기 전에 `REQ_BUILD_FAILED`로 실패해요. interceptor가 요청을 단축하더라도 마찬가지예요. HTTP, SSE, WebSocket이 이 규칙을 공유해요.

<include cwd>examples/http/resolve-url.ts#example</include>

path placeholder는 raw 스칼라라서 정확히 한 번만 인코딩돼요. 빈 값과 `.` / `..`는 거부돼요. 슬래시, `?`, `#`, `%`, 공백, 유니코드가 한 placeholder 안에 있으면 인코딩된 세그먼트 하나로 남아요. 미리 인코딩하지 마세요.

placeholder 이름은 `:`에서 시작해 path의 다음 `/` 또는 끝까지예요. `/files/:name.json`의 매개변수 이름은 `name`이 아니라 `name.json`이에요. 정적 세그먼트의 리터럴 콜론은 지원하지 않아요.

정의 path는 앞에 공백이 있더라도 스킴 형태나 프로토콜 상대 형식일 수 없고, C0 제어 문자(탭, CR, LF 포함), 백슬래시, `?`, `#`를 담을 수 없어요. 경로 내부의 일반 공백은 허용되고 `%20`으로 전송돼요. 해석 뒤 URL은 base origin을 유지하고 그 디렉터리 안에 머물러야 해요. `../users` 같은 path로 빠져나갈 수 없어요. 불법 path는 전송 전에, 만드는 동안 `REQ_BUILD_FAILED`로 실패해요. 인터셉터의 최종 `req.endpoint`는 최종 `req.baseEndpoint`에 같은 규칙으로 검사돼요. interceptor는 base를 다른 유효한 절대 URL로 일부러 바꿀 수 있어요. 결정적인 URL 오류는 재시도하지 않아요.

기본 query 인코더는 스칼라와 스칼라 배열을 받아요 (배열은 키를 반복해요). 중첩 객체는 클라이언트에 `withQuerySerializer(...)`가 없으면 `REQ_BUILD_FAILED`예요. `path`, `query`, `headers`의 `null`도 같은 방식으로 실패해요. `undefined`는 빠져요.

## 입력 배치하기

struct가 값을 인코딩하고, builder가 배치해요. `input`을 선언하면 입력이 이미 요청 모양이어도 명시적인 `builder`가 반드시 필요해요. `input`이 없는 정의만 `builder`를 생략할 수 있어요.

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

그 body는 `application/json`의 `{"display_name":"Ada"}`예요. 헤더 와이어 이름은 `x-request-id`예요. 호출자와 파싱 결과는 `displayName`을 유지해요.

와이어 키를 직접 적기보다 타입이 있는 값을 넘기는 편이 좋아요. alias는 필드에 한 번 선언되고 양방향으로 적용돼요. `output` / `error` / 이벤트 / 들어오는 프레임은 `display_name`을 `displayName`으로 디코딩하고, `body: input.order`는 트리 전체를 다시 써요. 같은 `User` struct가 create body이자 get output일 수 있어요. 손으로 쓴 키는 예외예요. 부모 객체가 익명이라 alias가 돌지 않아요.

| builder 식                                      | 와이어에서                                         |
| ----------------------------------------------- | -------------------------------------------------- |
| `body: input.profile`                           | 타입이 있는 객체. alias와 `Date` / `bigint` 인코딩 |
| `body: { profile: input.profile }`              | 바깥 키는 리터럴, 안쪽 객체는 여전히 타입이 있어요 |
| `body: { ...input.profile, role: 'admin' }`     | spread는 struct를 유지하고, 추가 키는 리터럴이에요 |
| `body: { name: input.profile.displayName }`     | 익명 부모. alias가 적용되지 않아요                 |
| `query: input.query` / `headers: input.headers` | 타입이 있는 평평한 객체. alias가 와이어 키가 돼요  |

타입이 있는 객체를 spread하면서 그 와이어 키도 같이 쓰면 (`displayName` 옆의 `display_name`) `REQ_BUILD_FAILED`예요. `path`나 `headers`의 중첩 객체도 같은 방식으로 실패해요.

가이드는 루트만이 아니라 각 노드에서 정해져요. 익명 부모 아래에 새로 쓴 객체는 직접 쓴 키를 유지해요. 타입이 있는 부모 아래에서는 같은 객체가 그 필드의 struct를 써요.

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

union 가이드가 둘 이상의 분기에 맞으면 분기마다 인코딩해서 비교해요. 와이어 결과가 같으면 그 값을 쓰고, 다르면 `REQ_BUILD_FAILED`예요.

object가 아닌 부분을 포함한 혼합 intersection은 파싱될 때 일치한 각 부분의 태그를 합친 연언을 태그로 달고, 파싱되지 않은 새로 쓴 값은 익명 객체로 다뤄요.

### Query

중첩 query 모양 (`a[b]`, `a.b`, 쉼표 목록)은 백엔드 관례라서 hook은 클라이언트에 있어요.

<include cwd>examples/http/query-serializer.ts#example</include>

여기 `query`는 인코딩된 와이어 객체예요. alias는 이미 적용돼 있어서 `qs` 같은 serializer가 그걸 버리지 않아요. 반환 문자열은 query 문자열이에요. Defjs는 `qs`에 의존하지 않아요.

serializer가 없으면 배열은 키를 반복하고, 중첩 객체는 `REQ_BUILD_FAILED`예요. builder가 `URLSearchParams`를 돌려주면 그 값을 그대로 쓰고 serializer를 건너뛰어요. query가 없으면 serializer는 호출되지 않아요. 그다음 interceptor가 보는 `queryParams`는 `new URLSearchParams(queryString)`이에요.

### Body

먼저 맞는 규칙이 이겨요.

| `body` 값                                                        | 보내는 형태                                                        | 기본 content type                                       |
| ---------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------- |
| 생략 / `undefined`                                               | body 없음                                                          | —                                                       |
| 루트에 `urlencoded` 또는 `formData` 코덱이 있는 타입이 있는 객체 | `URLSearchParams` / `FormData`. 키는 와이어 이름. 배열은 키를 반복 | form 타입 / 플랫폼 경계                                 |
| `FormData`, `URLSearchParams`                                    | 그대로                                                             | 같음. Defjs는 `FormData`의 낡은 `Content-Type`을 지워요 |
| `Blob` / `File`                                                  | 그대로                                                             | `blob.type`, 또는 `application/octet-stream`            |
| `ArrayBuffer`, `TypedArray`, `DataView`                          | 그대로                                                             | `application/octet-stream`                              |
| `ReadableStream`                                                 | 스트림 (`duplex: 'half'`, 런타임이 허용할 때)                      | `application/octet-stream`                              |
| `string`                                                         | 그대로                                                             | `text/plain;charset=UTF-8`                              |
| 평범한 객체, 배열, 숫자, 불리언, `null`, `Date`, `bigint`        | 인코딩한 뒤 `JSON.stringify`                                       | `application/json`                                      |

HTTP는 builder의 body에서 추론한 타입을 일반 `request.bodyContentType` 필드에 보관해요. 이 필드는 `{ ...req }`로 복사해도 유지되며, 추론한 타입을 `request.headers`에 쓰지는 않아요. builder, 클라이언트 기본값, 인터셉터, 원시 `fetchHandler` 요청 중 어디에서 설정했든 명시한 `content-type` 헤더가 항상 우선해요. 업로드 진행률이 body를 스트림으로 바꿀 때도 그래요. `bodyContentType`은 `body`가 builder의 값인 동안에만 적용돼요. 교체된 body는 다시 탐지하므로 인터셉터는 `content-type` 헤더로 그 타입을 선언해요. `body: undefined`는 라이브러리가 추론한 Content-Type을 보내지 않아요. 예외는 FormData예요. content type은 실제 직렬화의 boundary를 써야 해요. 코덱 태그는 body 루트에서만 적용돼요. `body: { meta: input.form }`은 JSON이고, form 필드는 평범한 JSON 필드예요. 문자열은 raw 텍스트예요. `"abc"` 같은 JSON 문자열은 `JSON.stringify`와 `application/json`이 필요해요. `undefined` 필드는 빠져요. `nullable` 필드를 `null`로 보내면 JSON `null`이에요.

JSON은 중첩된 값까지 모두 JSON 데이터여야 해요. 허용되는 값은 평범한 객체, 배열, 문자열, 유한한 숫자, 불리언, `null`, 그리고 `toJSON()`이 이런 데이터를 돌려주는 `Date`나 `URL` 같은 값이에요. 그 밖의 값은 루트에 있든 중첩되어 있든 아무것도 보내기 전에 `REQ_BUILD_FAILED`로 실패해요. `{}`나 `null`로 전송되거나 body가 아예 생략되는 일은 없어요. `Map`이나 `Set`, `toJSON`이 없는 클래스 인스턴스, 함수, `NaN`, Node `Readable`, 이터러블이나 비동기 이터러블(`Symbol.iterator` 또는 `Symbol.asyncIterator` 메서드가 있는 객체 리터럴 포함) 등이 여기에 해당해요. 오류 메시지에 해당 필드 이름이 표시돼요. `query`나 `headers`로 넘긴 이터러블 객체는 버려지는 대신 같은 방식으로 실패해요. 헤더 쌍은 배열로 넘기세요. 스트림은 Web `ReadableStream`으로 보내세요. `ReadableStream.from(iterable)` 또는 `Readable.toWeb(readable)`를 쓰면 돼요. `body` 타입은 이 중 대부분을 컴파일 타임에 거부해요. `interface` 값이나 클래스 인스턴스는 `{ ...value }`가 필요해요.

`GET`과 `HEAD`는 body를 돌려줄 수 없어요. 그건 타입 오류예요. WebSocket builder는 `headers`나 `body`를 돌려줄 수 없어요.

<include cwd lang="typescript">

</include>

직접 돌리는 `JSON.stringify`, `qs`, protobuf는 논리 이름을 봐요. 그 경로에서는 alias가 적용되지 않아요. 공개 `struct.encode`는 없어요.

builder는 실제 입력으로 분기해서 경우마다 다른 body를 돌려줄 수 있어요 (JSON 레코드, `File`, `URLSearchParams`). 네이티브 `Headers`도 그대로 통과하고 다시 인코딩되지 않아요.

## body를 읽는 방법

`output`은 2xx body를 위한 Struct 하나이고, `error`는 그 밖 전부를 위한 Struct 하나예요. struct kind가 표현을 골라요. `string`은 raw 텍스트, `blob` / `file`은 blob, `arrayBuffer`는 바이트, 그 밖의 kind는 JSON이에요. 어느 쪽도 선언하지 않으면 body는 읽히지 않아요.

처리 순서예요.

1. `ok`가 쪽을 골라요. 2xx는 `output`, 그 밖은 `error`. 양쪽을 모두 읽는 일은 없고, 다른 쪽을 fallback으로 쓰지도 않아요.
2. 그 쪽에 선언이 없으면 body는 읽히지 않아요. 2xx는 `data === undefined`로 성공하고, non-2xx는 `data === undefined`인 `HTTP_STATUS`예요. 선언하지 않은 쪽의 읽을 수 없는 body는 무시돼요. 읽을 수 없었다는 사실까지 포함해서요.
3. 미디어 타입은 body를 읽기 **전에** 검사해요. 불일치는 `RES_MEDIA_TYPE_INVALID`이고, 파싱도 디코딩도 하지 않아요.
4. 표현을 읽어요. 실패하면 `RES_DECODE_FAILED`예요. 전송의 JSON은 한 번만 파싱해요. 그 값의 문자열은 JSON 문자열 루트라서 다시 파싱하지 않아요. bytes와 blob은 원시 값이라 한 번만 파싱해요.
5. Struct가 값을 파싱해요. 실패하면 `RES_STRUCT_MISMATCH`예요.
6. 2xx → 결과와 타입이 있는 `response.body`. non-2xx → `HTTP_STATUS`의 타입이 있는 `data`.

내장 Fetch 전송은 선언된 쪽에 대해 3단계와 4단계를 응답이 아직 interceptor 체인 안에 있는 동안 수행해요. 그래서 interceptor는 `body`가 이미 파싱된 JSON, 텍스트, `Blob`, 바이트인 응답을 받아요. 이 단계에서의 실패는 여전히 같은 `RES_*` fault로 드러나고, body 스트림이 끊기면 `NET_BODY_INCOMPLETE`로 드러나요. 5단계는 체인 뒤에 한 번 실행돼요. 따라서 interceptor가 `makeResponse(...)`로 만든 응답도 와이어에서 온 응답과 같은 미디어 타입 검사, 표현 변환, Struct를 거쳐요. JSON 표현에서 문자열 body는 JSON 문자열 루트예요.

성공 응답은 `DecodedResponse<T>`예요. `url`, `status`, `statusText`, `headers`, `ok`, 그리고 타입이 있는 `body`예요. 아무것도 디코딩되지 않은 곳은 `HttpMeta`예요. 같은 필드에서 `body`만 없어요. `ok`는 `200 <= status < 300`만을 뜻해요. 둘 다 네이티브 `Response`가 아니에요. 전송 실패는 fault라서, 그걸 대신하는 status 0 응답은 없어요.

## 작업 취소하기

실행 옵션은 `signal`에 `abort` 또는 `timeout` 중 하나를 더해요. **`abort`와 `timeout`은 서로 배타적이에요.** `signal`은 어느 쪽과도 조합할 수 있어요.

<include cwd>examples/http/cancel.ts#example</include>

`timeout`은 `1..2_147_483_647` 범위의 양의 안전 정수여야 해요. `timeout`을 생략한 호출은 클라이언트의 `withTimeout` 기본값을 받아요. 알아보는 취소 → `NET_ABORTED`. 실행 타임아웃 → `NET_TIMEOUT`. interceptor `throw` → `EXT_INTERCEPTOR_FAILED`. 단 `ERR_ABORTED` / `ERR_TIMEOUT`은 각각 `NET_ABORTED` / `NET_TIMEOUT`이 돼요. 그 밖의 Fetch 실패 → `NET_UNREACHABLE`. 서버가 쓰기를 받아들인 뒤의 취소는 쓰기가 롤백됐다는 증명이 **아니에요**.

## 자격 증명과 XSRF

`withCredentials(true)`는 HTTP와 SSE에서 Fetch `credentials: 'include'`를 설정해요. `Authorization`을 만들지 않고, WebSocket 인증도 구성하지 않아요. `false`는 credentials를 지정하지 않은 채로 둬요.

`withXSRF(...)`는 HTTP 전용이에요. 기본값: `cookieName: 'XSRF-TOKEN'`, `headerName: 'X-XSRF-TOKEN'`. 헤더는 안전하지 않은 method에만, 호출자가 이미 설정하지 않았을 때만 들어가요. `location`이 있으면 Worker를 포함해 해석된 요청 URL이 `location.origin`과 같아야 하고, 교차 출처 요청은 `tokenProvider`를 호출하지 않아요. 쿠키 조회는 별도로 `document`가 필요해요. `GET`, `HEAD`, `OPTIONS`, `TRACE`는 건너뛰어요. Worker나 서버에서 주입이 필요하면 동기적이고 요청 범위의 `tokenProvider`를 넘기세요.

credentials, XSRF 토큰, query 문자열은 일상적인 로그에서 빼세요. query params를 일반적인 자격 증명 채널로 쓰지 마세요.

## 진행률과 Fetch 경계

`onDownloadProgress`는 선언된 응답 body를 읽는 동안 돌아요. `loaded`는 응답 스트림에서 읽은 바이트를 세고, Fetch가 이미 압축을 풀었을 수 있어요. `lengthComputable`은 양의 `Content-Length`가 있고 `Content-Encoding`이 없거나 `identity`일 때만 true예요. gzip과 br을 포함한 다른 인코딩은 `total: 0`과 `lengthComputable: false`를 보고하므로, 디코드된 바이트를 압축된 와이어 길이와 비교하지 않아요. 그 쪽에 struct가 없으면 body를 읽지 않으니 body 읽기 진행률도 없어요.

`onUploadProgress`는 Fetch가 `ReadableStream<Uint8Array>` body를 읽는 동안의 진행률을 보고해요. 서버가 확인한 시점이 아니에요. 업로드 진행률은 요청 body 스트리밍을 지원하는 런타임에서만 보고돼요. Bun, Node, Deno에서는 Defjs가 `Blob` / `File`, `ArrayBuffer`, `FormData` body도 스트림으로 변환하므로 이들도 진행률을 보고해요. 서버 런타임에서 `onUploadProgress`를 쓰는 FormData는 직렬화된 스트림을 직접 쓰고 multipart boundary를 유지하며, 라이브러리가 생성한 `Content-Length` 없이 전송돼요(HTTP/1.1에서는 청크 전송). 따라서 body 전체를 버퍼링하지 않고도 진행률, 타임아웃, 취소가 동작해요. 유효한 명시적 `Content-Length`가 없으면 total을 알 수 없어요. 일부 사전 서명된 업로드 대상처럼 `Content-Length`가 필요한 엔드포인트에서는 `onUploadProgress`를 생략하세요. 그러면 플랫폼 Fetch가 FormData를 길이와 함께 전송해요. 취소하면 감싼 스트림이 해제돼요. Chromium은 HTTP/2 이상에서만 요청 body 스트리밍을 지원하고 Firefox는 이를 전혀 지원하지 않으므로 Worker를 포함한 브라우저는 제외돼요. 브라우저에서는 그 body들이 그대로 보내지고 `onUploadProgress`는 호출되지 않아요. JSON, 텍스트, `URLSearchParams`, 형식화 배열 body는 통째로 보내져서 이벤트가 없어요. 길이를 알 수 없는 스트림은 `total`이 `0`이에요(그래서 `lengthComputable`은 `false`). 요청 스트리밍을 지원하지 않는 런타임(Firefox 등)에서 `ReadableStream` body는 아무것도 보내지기 전에 `ENV_UNSUPPORTED`로 실패하고, cause 메시지는 `ERR_STREAMING_REQUEST_UNSUPPORTED`예요. Chromium에서 `ReadableStream` body는 HTTP/2 이상이 필요하고, HTTP/1.1에서는 호출이 `NET_UNREACHABLE`로 실패해요. `onDownloadProgress`는 모든 런타임에서 같게 동작해요.

진행률 콜백이 예외를 던지거나 반환한 프로미스가 거부되면 다운로드와 업로드 모두 호출이 `EXT_OBSERVER_FAILED`로 실패하고, 던진 값이 `cause`가 돼요. 호출자의 취소와 `timeout`은 여전히 `NET_ABORTED` / `NET_TIMEOUT`을 보고해요.

`fetchHandler(httpRequest, fetchImpl?)`는 더 낮은 Fetch 경계예요. URL을 해석하고, Fetch를 호출하고, 표현을 읽고, `HttpResponse`를 돌려줘요. 기본 HTTP와 SSE handle은 호출마다 `globalThis.fetch`를 해석하므로, import 뒤에 설치한 교체본을 써요. HTTP는 손대지 않은 플랫폼 Fetch에만 `(url, init)`을 쓰고, 교체된 전역이나 사용자 지정 handle은 네이티브 `Request`를 받아요. Fetch 없이 Core를 import하는 것은 유효해요. Fetch가 여전히 없으면 기본 HTTP/SSE 실행은 `ENV_UNSUPPORTED`로 실패하고, 사용자 지정 handle은 그대로 쓸 수 있어요. 이 경계는 명령 입력을 검증하지 않고, `output`을 디스패치하지 않고, interceptor도 돌리지 **않아요**. 주입한 전송 테스트에는 쓸모 있지만 `client.execute`를 대신하지는 않아요.

## 재시도 한도

Defjs는 HTTP를 자동으로 재시도하지 **않아요**. 읽기를 재시도해도 검토된 timeout/네트워크/중복 정책이 필요해요. 변경을 재시도하려면 다시 보낼 수 있는 바이트, 서버 지원, 인증 범위와 요청 바이트에 묶인 멱등성 키, 수신 쪽 중복 정책이 필요해요.

실패한 쓰기가 커밋됐는지는 클라이언트/명령/Fetch 경계가 알 수 없어요. 재시도 결정은 앱이나 검토된 interceptor에 두세요. interceptor는 short-circuit하거나 저수준 요청을 바꿀 수 있어요. 최종 status와 body는 여전히 명령의 계약을 만족해야 해요.
