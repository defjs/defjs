# SDK 작성과 배포 [#publish-an-http-sdk-without-hiding-execute]

Defjs 기반 SDK는 순수한 작업 정의와 Struct 스키마만을 npm 패키지로 export하며, `createClient(...)`, 기본 엔드포인트 URL, 자격 증명, 인터셉터 설정은 사용하는 애플리케이션에 온전히 맡깁니다.

---

## 1. SDK 패키지 정의하기

작업 정의, 배럴(barrel) export, `package.json`, `tsconfig.json`을 전용 패키지 디렉터리에 구성하고, `@defjs/core`를 `peerDependency`로 선언하세요:

- `@defjs/core`는 사용하는 애플리케이션과 공유되는 외부 런타임 `peerDependency`로 유지됩니다.
- `"sideEffects": false`를 지정하면 애플리케이션이 작업 중 일부만 import할 때 번들러가 사용되지 않는 작업을 트리쉐이킹할 수 있습니다.

---

## 2. 빌드 및 Tarball 검증

`tsdown`을 사용해 `dist/index.js`와 `dist/index.d.ts`를 번들링한 뒤 배포 전에 패키지 내용을 점검하세요:

```sh
bun install
bun run build
bun pm pack --dry-run
bun pm pack
```

Tarball 내에 `dist/index.js`와 `dist/index.d.ts`가 정상적으로 포함되어 있는지 확인합니다.

---

## 3. 애플리케이션에서 SDK 사용하기

애플리케이션에 작성한 SDK와 `@defjs/core`를 함께 설치합니다:

```sh
bun add @company/orders-sdk @defjs/core@^0.7.0
```

애플리케이션은 자체 `Client`를 직접 생성하고, 이를 import한 작업 함수에 전달하여 호출합니다:

<include cwd meta='title="app.ts"'>
  examples/recipes/publish-http-sdk/app.ts#example
</include>

```txt
paid
```

실제 프로덕션 코드에서는 상대 경로 import인 `./src/orders.ts`를 `@company/orders-sdk`로 변경하고, `withHTTPHandle(...)`을 제거하여 플랫폼의 실제 `fetch`를 사용하도록 설정합니다.

---

## 4. 테스트 및 배포

요청 매핑, `output` 디코딩, 선언된 `HTTP_STATUS` 결함, 취소 동작을 포괄하는 [인메모리 핸들 테스트](/ko-KR/recipes/test-with-handle)로 export된 정의들을 철저히 검증하세요. 검증이 완료되면 패키지를 배포합니다:

```sh
bun publish --access public
```

자세한 내용은 [HTTP 작업](/ko-KR/docs/http), [Client](/ko-KR/docs/client), [테스트](/ko-KR/docs/testing), [핵심 아키텍처](/ko-KR/docs/design-decisions) 문서를 참조하세요.
