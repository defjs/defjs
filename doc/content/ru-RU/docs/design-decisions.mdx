# Архитектура ядра

Defjs строится вокруг одной фундаментальной границы: **SDK определяет сетевой контракт, а использующее приложение владеет выполнением.** Каждое архитектурное правило в `@defjs/core` напрямую вытекает из этого разделения.

## 1. Определение и выполнение

Пакет SDK экспортирует операции (`defineRequest`, `defineEventStream`, `defineWebSocket`) и структуры данных (`struct`). Он никогда не вызывает `createClient`, не хранит глобальный синглтон-клиент и не читает переменные окружения.

Поскольку `getOrder` не захватывает состояние клиента:

- Браузерный интерфейс, фоновая задача, SSR-обработчик и юнит-тест могут вызывать одну и ту же операцию `getOrder` с совершенно разными конфигурациями `Client`.
- Плагины для фреймворков (`@defjs/react`, `@defjs/vue`) и middleware-плагин наблюдаемости (`@defjs/opentelemetry-server`) подключаются к `Client` приложения, благодаря чему опубликованный пакет SDK остаётся абсолютно свободным от внешних зависимостей.

## 2. Явное размещение входа и двунаправленные алиасы

В Defjs `input` объявляет то, что передаёт вызывающий код, `struct` управляет кодированием и декодированием значений, а `builder` размещает каждое значение в запросе (`path`, `query`, `headers`, `body`).

- **Никакой магии и догадок**: если операция объявляет `input`, она обязана предоставить явную, синхронную и чистую функцию `builder`. Размещение полей никогда не угадывается по именам параметров.
- **Двунаправленные `.alias(wireName)`**: объявление `.alias("customer_name")` у поля структуры сохраняет имя `customerName` в коде TypeScript, автоматически преобразуя его в `"customer_name"` и обратно при сетевой передаче.

Когда `builder` передаёт типизированный объект `struct` в `body`, `query` или `headers`, алиасы его полей и кодеки `Date` / `bigint` применяются автоматически. Ключи, написанные в анонимном объекте-обёртке (например, `account_id` или `x-api-version` выше), передаются буквально.

## 3. Объявление — это утверждение [#declaration-is-an-assertion]

Шесть строгих правил определяют, как Defjs читает HTTP-ответы:

### Правило 1: Что объявили, то и утверждаете

`output` утверждает форму тела ответа для кодов `2xx`. `error` утверждает форму тела для всех остальных кодов, отличных от `2xx`. Объявление — это строгая гарантия во время выполнения, а не приблизительная подсказка.

### Правило 2: `ok` (`200..299`) — единственная развилка

Ответ с кодом `2xx` декодируется исключительно с помощью `output`. Любой другой статус (`3xx`, `4xx`, `5xx`) декодируется только с помощью `error`. Defjs никогда не переключается с одного на другой в качестве запасного варианта.

### Правило 3: Любое отклонение от утверждения — явный сбой

Defjs выбирает сторону ответа по `response.ok`: `output` для `2xx`, `error` для не-`2xx`. Только JSON-struct, объявленный на этой стороне, запускает декодирование и может дать `RES_MEDIA_TYPE_INVALID` или `RES_DECODE_FAILED`; его `Content-Type` проверяется **сначала**, до того как тело будет прочитано или его наличие проверено. Ответ без содержимого (`HEAD`, `204`, `205`, `304`) проходит ту же проверку: объявленное JSON-представление без JSON `Content-Type` завершается `RES_MEDIA_TYPE_INVALID`, а с ним разбирает пустые байты и завершается `RES_DECODE_FAILED`. HTML-страница шлюза со статусом не-`2xx` даёт `RES_MEDIA_TYPE_INVALID`, только если объявлен JSON-struct `error`. Без объявления для активной стороны тело не читается; ответ не-`2xx` возвращает недекодированный `HTTP_STATUS`. Хэндшейк SSE следует тем же правилам: не-`2xx` хэндшейк, чьё объявленное тело `error` не удаётся декодировать, возвращает этот сбой декодирования при запуске, со статусом в метаданных, тогда как перехватчики, политики переподключения и `closed` переподключения по-прежнему видят `HTTP_STATUS`.

| Причина сбоя при чтении ответа                                 | Возвращаемый сбой (Fault)                                                                                     |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Тип медиа не совпадает с объявленным JSON-представлением       | `RES_MEDIA_TYPE_INVALID` (проверяется первым; тело никогда не читается, и наличие содержимого роли не играет) |
| Байты невозможно декодировать в объявленное представление      | `RES_DECODE_FAILED` (включая пустые JSON-байты)                                                               |
| Декодированное значение не прошло валидацию `struct`           | `RES_STRUCT_MISMATCH`                                                                                         |
| Статус вне диапазона `2xx` с декодированной структурой `error` | `HTTP_STATUS` с типизированным `error.data`                                                                   |
| Статус вне диапазона `2xx` без объявления `error`              | `HTTP_STATUS` с `error.data: undefined`                                                                       |

### Правило 4: У неудавшегося декодирования нет тела

Тело существует только тогда, когда оно успешно прошло декодирование и валидацию. Если декодирование завершилось сбоем, `response` в объекте ошибки типизируется как `HttpMeta` (у которого вообще нет свойства `body`), а исходная ошибка парсера или валидации сохраняется в `fault.cause`.

### Правило 5: Пропуск стороны отключает её чтение

Если `output` не объявлен, тела ответов `2xx` никогда не читаются. Если `error` не объявлен, тела ответов вне `2xx` никогда не читаются — даже если сервер прислал невалидный JSON со статусом `500`.

### Правило 6: `3xx` — это не статус успеха

`ok` означает строго `200 <= status < 300`. Статус `304 Not Modified` находится вне диапазона `2xx`: оставьте `error` необъявленным и обработайте `HTTP_STATUS` (либо перехватите `304` в перехватчике ETag), или объявите `struct.string()`, если ожидается пустое текстовое тело.

## 4. Кортежи результатов под каждый транспорт

Все три транспорта возвращают error-first кортеж из трёх элементов вместо выбрасывания исключений в месте вызова:

- **HTTP** → `[error, data, response]` — декодированные данные + `DecodedResponse<T>` (`HttpMeta`, если `output` не объявлен).
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + начальный снимок хэндшейка.
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + начальный снимок соединения.

Клиенты несут конфигурацию, а не активные соединения. Вызывающий код, инициировавший HTTP-запрос, поток SSE или сессию WebSocket, сам управляет их отменой или закрытием (`AbortSignal` для HTTP; `await using` или `.close()` + `await .closed` для SSE и WebSocket).
