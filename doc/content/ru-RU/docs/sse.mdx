# Server-Sent Events

Открой стрим, итерируй, потом отпусти принадлежащий handle через `await using`. Ручные `close()` и `closed` остаются; клиенты и плагины не dispose’ят возвращённый стрим за тебя.

## Опиши стрим

`defineEventStream(...)` нуждается в `events`, положительном safe-integer `maxBufferSize`, положительном safe-integer `maxQueueSize` и относительном `path`. Method по умолчанию `GET`.

Форма запроса совпадает с HTTP: `builder`, возвращающий `path`, `query`, `headers` и `body`. `GET` / `HEAD` не могут вернуть тело. Объявленный struct `error` типизирует fault старта и декодирует non-2xx тело handshake по kind struct (`string` — текст, `blob` / `file` — blob, `arrayBuffer` — байты, иначе JSON). Defjs шлёт `Accept: text/event-stream`, если ты ещё не поставил `Accept`. При объявленном `input` всегда нужен явный `builder`, даже если входные данные уже имеют форму запроса. Опустить `builder` можно только в определениях без `input`. Для тела `ReadableStream` действуют правила HTTP: в среде выполнения без поддержки потоковой отправки тела запроса, например в Firefox, запуск завершается с ошибкой `ENV_UNSUPPORTED` до отправки каких-либо данных. В Chromium требуется HTTP/2 или более поздняя версия; по HTTP/1.1 запуск завершается с ошибкой `NET_UNREACHABLE`. Запрос с потоковым телом отправляется один раз, и переподключение для него никогда не выполняется (см. Reconnect).

Один логический стрим может охватить несколько физических Fetch-попыток **когда** ты opt-in’ишься в reconnect. Без `withSSEReconnect` преходящие сбои сети и чтения стрима заканчивают логический стрим. При успешном open ты всё равно получаешь один handle и один async iterator.

## Открой и посмотри

`client.execute(...)` резолвится только после того, как прошли проверки status, content-type и тела:

<include cwd lang="typescript">
  examples/sse/open-and-inspect.ts#example
</include>

Ответ должен быть успешным, essence media type — `text/event-stream`, и у него должно быть тело. Non-2xx на старте → `HTTP_STATUS`. Если объявлен `error`, этот fault несёт декодированное тело handshake; плохой media type — `RES_MEDIA_TYPE_INVALID`, а тело, которое нельзя прочитать как объявленный kind, — `RES_DECODE_FAILED`. Снимок ответа всё ещё может сидеть в третьем слоте кортежа, когда валидация падает уже после прихода ответа.

Отсутствующий, относительный или некорректный базовый эндпоинт либо недопустимый путь дают `REQ_BUILD_FAILED` при сборке, до запуска интерцепторов или транспорта, даже если интерцептор вернул бы результат без обращения к транспорту. Разрешённый URL должен сохранять origin базы и оставаться в её каталоге; управляющие символы C0 (включая табуляцию, CR и LF), обратные слеши, `?`, `#` и выход за пределы каталога запрещены. Похожие на схему и протокольно-относительные формы отклоняются даже с ведущими пробелами; обычный пробел внутри пути разрешён и отправляется как `%20`. Итоговый `req.endpoint` интерцептора проверяется относительно итогового `req.baseEndpoint` по тому же правилу; явная замена базы другим корректным абсолютным URL разрешена. Детерминированные ошибки URL никогда не приводят к повторной попытке.

`startupOpen` — начальный снимок именно этого выполнения; новый `execute` никогда не использует снимок предыдущего выполнения, даже если завершится с ошибкой до получения ответа. `stream.open` отражает текущее состояние и меняется при последующих физических открытиях. Сохраняй значение из кортежа, когда важен первый ответ. `startupOpen` — снимок первого успешного handshake соединения возвращённого handle только для нативного handle Defjs или обёртки, передающей тот же живой объект `open`; пользовательские handle и обёртки, переопределяющие `open`, сохраняют свой текущий публичный `open` даже после переподключения, поэтому общий `closed` не позволяет обойти очистку URL или фильтрацию заголовков, а Defjs не восстанавливает метаданные первого handshake из произвольных преобразований.

## Декодируй события

Имя события на проводе → `events[eventName]`; иначе `events.default`. Нет подходящего Struct → событие не доставляется. Нет поля SSE `event` → логическое имя `message`.

SSE `data` начинается как текст. Struct `string` оставляет этот текст. Любой другой kind — JSON: распарси текст, потом декодируй struct. `struct.object`, `struct.number`, `struct.boolean`, `struct.any` и `struct.unknown` — это JSON, не обрезанный текст. Голый токен вроде `ping` не удовлетворяет `struct.literal('ping')`; data должен быть JSON. Сервер, который шлёт JSON-строку `"abc"`, всё же удовлетворяет `struct.string()`: доставленное значение — этот сырой текст, включая кавычки, и оно не декодируется из JSON в `abc`.

Разбор следует правилам строк и полей WHATWG SSE: CR, LF и CRLF завершают строку; пустая строка отправляет событие с данными; несколько строк `data:` объединяются через `\n`. Комментарии и неизвестные поля игнорируются, а незавершённое событие при EOF не отправляется. Удаляется только один начальный UTF-8 BOM в начале каждого физического потока. U+FEFF внутри значений `data` или `id` сохраняется; встретившееся позже имя поля с префиксом BOM, например `﻿data`, считается неизвестным и игнорируется.

Испущенное значение: `event`, декодированный `data`, необязательный непустой `id`. С `default` неизвестные имена событий — `string` в выведенном union.

## Наблюдай invalid events

Невалидные и необъявленные события отбрасываются, не ставятся в очередь. `withSSEOnInvalidEvent(...)` может наблюдать сырые ID, имя, текстовые data, плюс `missing-struct` или `validation-failed` и необязательный cause.

## Reconnect

**Изменение поведения:** SSE reconnect — opt-in. Без `withSSEReconnect(...)` сбои сети и чтения стрима **не** ретраятся (как `attempts: 0`). Передай `withSSEReconnect({ attempts: 3 })` (или другой проверенный бюджет), чтобы ретраить эти сбои. Обычный EOF не ретраится. Валидация status/content-type, лимиты парсера, провалы transform сообщения, переполнение очереди и обычный EOF остаются терминальными для логического стрима.

<include cwd>examples/sse/reconnect.ts#example</include>

`attempts` — бюджет повторных попыток для каждого обрыва; при заданном объекте reconnect по умолчанию он равен `3`. Успешный handshake сбрасывает бюджет, номер попытки для колбэка и показатель степени backoff, поэтому отдельные обрывы не расходуют общий бюджет на всё время жизни стрима. `attempts: 0` отключает повторные попытки. Без `withSSEReconnect` они тоже отключены. `delayMs` — начальный интервал (по умолчанию `1000`); `factor` увеличивает его (по умолчанию `1`, постоянная задержка); `maxDelayMs` — жёсткий предел итоговой задержки после jitter и округления (по умолчанию предел не настроен). SSE `jitter` — **мультипликативный коэффициент 0–1**, как у WebSocket. Даже без настроенного предела платформенный таймер ограничен `2_147_483_647` мс. Нулевая база остаётся нулевой; переполнение при корректных числах ограничивается этими пределами. Поле стрима `retry:`, состоящее только из цифр, обновляет текущий базовый интервал, в том числе после восстановления соединения. Если колбэк политики возвращает false, выбрасывает исключение или возвращает отклонённый промис, логический стрим завершается. Повторяющиеся успешные открытия, за которыми сразу следуют повторяемые сбои стрима, могут продолжать reconnect с текущей базовой задержкой (с учётом jitter и пределов), потому что каждое открытие сбрасывает бюджет; останови их через `shouldReconnect`. Обычный EOF остаётся терминальным.

Опции reconnect проверяются до запуска интерцепторов или Fetch: `attempts` должен быть неотрицательным безопасным целым числом; `delayMs` и явно заданный `maxDelayMs` — конечными и неотрицательными; `factor` — конечным и положительным; `jitter` — конечным и в пределах 0–1. Некорректные значения возвращают `REQ_OPTIONS_INVALID` без открытия стрима.

Последний разобранный идентификатор события передаётся в заголовке `Last-Event-ID` при следующей попытке как байты UTF-8 на проводе, в том числе для ID с символами вне ASCII. Пустое поле `id:` очищает заголовок; ID, содержащий NUL, игнорируется. За исключением этого заголовка, при следующей попытке повторно отправляется запрос, собранный для первой: builder и интерцепторы выполняются один раз на вызов `execute`, поэтому метод, URL, заголовки и тело остаются прежними. Заголовок, который нужно обновлять при каждой попытке, например токен с коротким сроком действия, следует задавать в реализации Fetch, переданной в `withSSEHandle`: она вызывается один раз на попытку. Если срок действия учётных данных всё же истечёт, ответ не-2xx при переподключении уже открытого стрима завершит его с `RES_DECODE_FAILED`; статус смотри в `stream.open.response.status`. Ответ не-2xx при начальном handshake, напротив, возвращает стартовый fault `HTTP_STATUS`, если его объявленное тело ошибки декодируется.

При переподключении запрос отправляется повторно только тогда, когда это безопасно:

- `GET`, `HEAD`, `OPTIONS`, `PUT` и `DELETE` — идемпотентные методы (RFC 9110 §9.2.2); для запросов с этими методами переподключение выполняется в пределах лимита повторов.
- Для запросов с любым другим методом, например `POST` или `PATCH`, переподключение выполняется только тогда, когда `shouldReconnect` возвращает `true`. По сбою соединения нельзя определить, успел ли сервер выполнить действие: запрос `POST`, запускающий генерацию с помощью LLM, выполнится повторно, за него снова будет начислена плата, а новые события последуют за прежними в том же стриме. Передача `shouldReconnect` заменяет это правило по умолчанию для всех методов, поэтому проверяй `method` в его контексте, когда один клиент используется с обоими видами эндпоинтов.
- Тело `ReadableStream` считывается при первой попытке. Любой сбой до или после открытия стрима завершает его с исходной ошибкой; `shouldReconnect` не вызывается, ожидания перед переподключением нет. Если для запроса требуется переподключение, используй тело в виде строки, байтов, `Blob`, формы или JSON.

## Лимиты buffer и queue

Оба должны быть положительными safe integers. Переполнение фатально — старые события молча не выбрасываются.

| Лимит           | Что защищает                                                   | Терминальный код      |
| --------------- | -------------------------------------------------------------- | --------------------- |
| `maxBufferSize` | Неполная/слишком большая SSE-строка/событие при парсинге       | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`  | События производятся быстрее, чем читает единственный consumer | `CAP_QUEUE_OVERFLOW`  |

Фатальный стрим ещё чистит буферизованные события, отменяет активное тело, reject’ит iterator и резолвит `stream.closed` с `kind: 'error'`.

## Close и dispose

`EventStreamHandle`: один живой снимок открытия, один терминальный promise, один `close`, один async iterator и один стандартный async disposer.

<include cwd lang="typescript">
  examples/sse/close-and-dispose.ts#example
</include>

Терминальные значения (`closed.kind`): `eof`, `aborted` или `error`. Результат `error` ещё несёт `closed.code` — `EventStreamFaultCode`: `CAP_BUFFER_EXCEEDED`, `CAP_QUEUE_OVERFLOW`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `RES_DECODE_FAILED` или `RES_MEDIA_TYPE_INVALID`.

`close(reason)` отменяет активную попытку, закрывает очередь и завершает стрим как `aborted`, даже если причина — `TimeoutError`. Отмена через `signal` или `abort`, переданные в `execute`, после открытия стрима обычно штатно завершает итератор и сообщает `aborted`; если причина отмены — `TimeoutError` или `ERR_TIMEOUT` (например, `AbortSignal.timeout(...)`), итератор выбрасывает `ERR_TIMEOUT`, а `closed` сообщает `kind: 'error'` с `code: 'NET_TIMEOUT'`. Опция `timeout` вызова execute — только дедлайн старта и никогда не прерывает открытый стрим. `break` / `return` / throw в цикле вызывает возврат итератора и закрывает стрим с `iterator-return`. Код, который выполняет команду, отвечает за закрытие.

`await using` вызывает тот же путь закрытия, за который отвечает владелец, и ждёт остановки чтения/reconnect Defjs и освобождения блокировки активного reader. Ожидание намеренно ограничено на случай, если управляемый провайдером промис `ReadableStream.cancel()` никогда не завершится, поэтому завершение такого промиса не гарантируется. Явные `stream.close(reason)` плюс `await stream.closed` остаются допустимыми, когда нужна причина или терминальный результат.

Кастомные структурные реализации `EventStreamHandle` теперь должны предоставить `[Symbol.asyncDispose](): PromiseLike<void>` и связать его с тем же lifecycle. Для реализаторов это compile-time breaking change; потребители, которые только получают handle Defjs, в рантайме ничего нового звать не должны.

Поддерживаемый минимальный набор lib — `ES2022`, `ESNext.Disposable`, `DOM` и `DOM.Iterable`. Инструменты репозитория для работы с декларациями используют TypeScript 7, но автоматической проверки потребителя упакованных пакетов или минимального набора lib нет, а поддержка старых компиляторов не обещана. Этот набор предоставляет типы, а не полифиллы Web API для среды выполнения. Обычный HTTP-клиент не `AsyncDisposable`; каждым запросом управляй через его timeout или `AbortSignal`.

Держи credentials, данные событий, event ID, cause и URL стримов подальше от обычных логов. `withCredentials(true)` влияет на Fetch cookies для SSE; auth WebSocket он не настраивает.
