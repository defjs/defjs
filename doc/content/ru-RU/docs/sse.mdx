# Потоки событий SSE

SDK объявляет эндпоинт Server-Sent Events с помощью функции `defineEventStream`, указывая относительный путь, опциональные входные данные и `builder`, словарь структур `events` и лимиты буфера/очереди. Использующее приложение настраивает аутентификацию и опциональное автоматическое переподключение на клиенте, открывает поток, читает строго типизированные события и самостоятельно управляет закрытием потока.

## 1. Объявление потока событий и чтение данных

Всегда освобождайте открытый `EventStreamHandle` с помощью `await using` (или связки `stream.close()` + `await stream.closed` в блоке `finally`):

<Tabs items={["sdk/orders-stream.ts", "app/watch-orders.ts", "Single-file quick look"]}>
<Tab value="sdk/orders-stream.ts">

```ts
import { defineEventStream, struct } from "@defjs/core";

export const watchOrders = defineEventStream({
  path: "/orders/events",
  operation: "orders.watch",
  events: {
    updated: struct.object({
      id: struct.number(),
      status: struct.string(),
    }),
  },
});
```

</Tab>
<Tab value="app/watch-orders.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { watchOrders } from "../sdk/orders-stream.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, stream] = await watchOrders(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = stream;
  for await (const event of active) {
    console.log(event.event, event.data.id, event.data.status);
    break;
  }
}

void main();
```

## 2. Хэндшейк открытия и форма кортежа

Вызов операции возвращает кортеж `[error, stream, startupOpen]` только после того, как исходный HTTP-ответ возвращает статус `2xx`, тип медиа `text/event-stream` и читаемое тело ответа:

- **Хэндшейк не `2xx`**: возвращает сбой `HTTP_STATUS` (с декодированными данными `error.data`, если в определении была объявлена структура `error`). Это фатально для текущей операции; `shouldReconnect` не вызывается. Следующая операция заново выбирает эндпоинт, поэтому балансировщик может выбрать другой эндпоинт.
- **Неверный Content-Type или нечитаемое тело**: возвращает `RES_MEDIA_TYPE_INVALID` или `RES_DECODE_FAILED`.
- **`startupOpen` против `stream.open`**: третий элемент кортежа (`startupOpen`) содержит снимок первого успешного ответа хэндшейка; свойство `stream.open` обновляется вживую при последующих переподключениях потока. Если хэндшейк переподключения возвращает `503`, итератор завершается с ошибкой и `stream.closed` сообщает `RES_DECODE_FAILED`, а `stream.open.response.status` остаётся `503`; проверяйте `stream.open` для получения этого текущего статуса ответа.

## 3. Маршрутизация и декодирование событий

Когда поступает SSE-кадр (завершающийся пустой строкой по спецификации WHATWG):

1. **Маршрутизация событий**: сетевое поле `event:` выбирает соответствующую структуру из `events[eventName]`, откатываясь к `events.default`, если она определена. Пропущенное поле `event:` по умолчанию считается равным `"message"`. Необъявленные события при отсутствии `events.default` отбрасываются.
2. **Декодирование полезной нагрузки**: схема `struct.string()` получает сырой текст из `data:`. Все остальные типы структур сначала парсят `data:` как JSON, а затем валидируют полученное значение через структуру.
3. **Наблюдение за невалидными событиями**: невалидные или необъявленные события отбрасываются, не прерывая работу потока. Для ограниченной диагностики подключите `withSSEOnInvalidEvent(...)` на клиенте:

## 4. Переподключение и `Last-Event-ID` [#reconnect]

Автоматическое переподключение SSE является **строго опциональным**. Без указания `withSSEReconnect(...)` любой сетевой сбой или ошибка чтения потока немедленно завершают поток.

<include cwd>examples/sse/reconnect.ts#example</include>

- **Лимит попыток (`attempts`)**: По умолчанию равен `3`, если в `withSSEReconnect` передан объект опций. Каждый успешный хэндшейк сбрасывает счётчик попыток и экспоненту задержки, поэтому `attempts: 1` всё равно может создать много физических соединений за длительную сессию, если каждое успешно открывается. Обычный сигнал EOF от сервера **не** считается ошибкой и не запускает повторное подключение.
- **Отслеживание позиции (`Last-Event-ID`)**: фиксируется после разбора завершающей пустой строки события и автоматически отправляется в заголовке `Last-Event-ID` при переподключении. Неполный кадр никогда не фиксирует свой `id`, независимо от штатного завершения или сбоя соединения. Возобновление после допускающего переподключение сбоя чтения/сети начинается с последнего зафиксированного ID; сервер должен реализовать повторную выдачу с этой позиции.
- **Безопасность идемпотентности**: по умолчанию автоматически переподключаются только идемпотентные методы (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`). Неидемпотентные методы (`POST`, `PATCH`, часто используемые для стриминга LLM) переподключаются, только если колбэк `shouldReconnect` явно возвращает `true`. Потоковые тела запросов (`ReadableStream`) расходуются при первой попытке и никогда не переподключаются повторно.
- **Таймаут хэндшейка (`connectTimeoutMs`)**: если задан, он должен быть конечным, положительным и не больше 2147483647 (предел таймера); иначе операция возвращает `REQ_OPTIONS_INVALID`. Ограничивает время отдельного хэндшейка от вызова Fetch до получения заголовков ответа, не накладывая ограничений на длительность открытого потока.

## 5. Лимиты буфера и очереди

Значения по умолчанию — `maxBufferSize: 64 * 1024` байт и `maxQueueSize: 1024` событий. Оба лимита должны быть положительными безопасными целыми числами. Дедлайна хэндшейка по умолчанию нет: незавершённый Fetch ждёт платформу, отмену вызывающим кодом или явно заданный `connectTimeoutMs`. Превышение любого лимита ёмкости фатально (`stream.closed` завершается с `kind: "error"`, а итератор выбрасывает ошибку — события никогда не теряются молча):

| Опция определения | Что ограничивает                                                  | Код критического сбоя |
| ----------------- | ----------------------------------------------------------------- | --------------------- |
| `maxBufferSize`   | Размер неполных или избыточных байтов кадра до пустой строки      | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`    | Количество проверенных событий, ожидающих потребителя `for await` | `CAP_QUEUE_OVERFLOW`  |

## 6. Закрытие и освобождение ресурсов [#close-and-dispose]

Вызывающий код, открывший поток, полностью отвечает за его завершение. Выход из цикла `for await` через `break`, `return` или throw автоматически закрывает поток; также можно использовать `await using` или явный вызов `stream.close()`:

Сигнал `signal`, переданный через `client({ signal })`, управляет всей длительностью жизни потока. Чтобы ограничить по времени только первоначальный хэндшейк подключения и не обрывать уже открытый поток, очищайте таймер сразу после завершения `await watchOrders(...)` (как показано на второй вкладке выше) либо используйте параметр `connectTimeoutMs` в `withSSEReconnect`.
