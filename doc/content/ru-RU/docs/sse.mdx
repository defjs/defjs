# Потоки событий SSE

SDK объявляет операцию Server-Sent Events (SSE) с помощью функции `defineEventStream`, указывая относительный путь, опциональные входные данные и `builder`, словарь структур `events` и лимиты буфера/очереди. Использующее приложение настраивает аутентификацию и опциональное автоматическое переподключение на клиенте, открывает поток, читает строго типизированные события и самостоятельно управляет закрытием потока.

## 2. Хэндшейк открытия и форма кортежа

Вызов операции возвращает кортеж `[error, stream, startupOpen]` только когда исходный HTTP-ответ имеет статус `2xx`, тип медиа `text/event-stream` и читаемое тело:

- **Хэндшейк не `2xx`**: возвращает сбой `HTTP_STATUS` (с декодированными данными `error.data`, если в определении была объявлена структура `error`). Это фатально для текущей операции, и `shouldReconnect` не вызывается, за исключением хэндшейка с ответом `502`, `503` или `504`, когда настроен `withSSEReconnect`: он повторяется как отказ в соединении по правилам переподключения из раздела 4, и `shouldReconnect`, если задан, вызывается. Исчерпанные повторы завершаются с `HTTP_STATUS`. Следующая операция заново выбирает эндпоинт, поэтому балансировщик может выбрать другой эндпоинт.
- **Неверный Content-Type или нечитаемое тело**: возвращает `RES_MEDIA_TYPE_INVALID` или `RES_DECODE_FAILED`.
- **`startupOpen` против `stream.open`**: третий элемент кортежа (`startupOpen`) содержит снимок первого ответа хэндшейка; свойство `stream.open` обновляется вживую при последующих переподключениях потока. Если хэндшейк переподключения завершает поток с не-2xx статусом, итератор завершается с ошибкой и `stream.closed` сообщает `HTTP_STATUS`, а `stream.open.response.status` сохраняет этот статус; проверяйте `stream.open` для получения текущего статуса ответа.

## 3. Маршрутизация и декодирование событий

Когда поступает SSE-кадр (завершающийся пустой строкой по спецификации WHATWG):

1. **Маршрутизация событий**: сетевое поле `event:` выбирает соответствующую структуру из `events[eventName]`, откатываясь к `events.default`, если она определена. Пропущенное поле `event:` по умолчанию считается равным `"message"`. Необъявленные события при отсутствии `events.default` отбрасываются.
2. **Декодирование полезной нагрузки**: схема `struct.string()` получает сырой текст из `data:`. Все остальные типы структур сначала парсят `data:` как JSON, а затем валидируют полученное значение через структуру.
3. **Наблюдение за невалидными событиями**: невалидные или необъявленные события отбрасываются, не прерывая работу потока. Для ограниченной диагностики подключите `withSSEOnInvalidEvent(...)` на клиенте:

## 4. Переподключение и `Last-Event-ID` [#reconnect]

Автоматическое переподключение SSE является **строго опциональным**. Без указания `withSSEReconnect(...)` любой сетевой сбой или ошибка чтения потока немедленно завершают поток.

<include cwd>examples/sse/reconnect.ts#example</include>

- **Бюджет попыток (`attempts`)**: По умолчанию равен `3`, если в `withSSEReconnect` передан объект опций. Каждый успешный хэндшейк сбрасывает счётчик попыток и экспоненту задержки, поэтому `attempts: 1` всё равно может создать много физических соединений за длительную сессию, если каждое успешно открывается. Обычный сигнал EOF от сервера **не** считается ошибкой и не запускает повторное подключение.
- **Отслеживание курсора (`Last-Event-ID`)**: фиксируется после разбора завершающей пустой строки события и автоматически отправляется в заголовке `Last-Event-ID` при переподключении. Неполный кадр никогда не фиксирует свой `id`, независимо от штатного завершения или сбоя соединения. Возобновление после допускающего переподключение сбоя чтения/сети начинается с последнего зафиксированного ID; сервер должен реализовать повторную выдачу с этой позиции.
- **Безопасность идемпотентности**: по умолчанию автоматически переподключаются только идемпотентные методы (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`). Неидемпотентные методы (`POST`, `PATCH`, часто используемые для стриминга LLM) переподключаются, только если колбэк `shouldReconnect` явно возвращает `true`. Потоковые тела запросов (`ReadableStream`) расходуются при первой попытке и никогда не переподключаются повторно.
- **Хэндшейки шлюза**: хэндшейк с ответом `502`, `503` или `504` — начальное открытие или переподключение — повторяется как отказ в соединении по тем же правилам переподключения (метод, `shouldReconnect`, `attempts`, тело `ReadableStream`). Остальные не-2xx хэндшейки остаются фатальными. Исчерпанные повторы и фатальные хэндшейки переподключения завершаются с `HTTP_STATUS`.
- **Таймаут хэндшейка (`connectTimeoutMs`)**: если задан, он должен быть конечным, положительным и не больше 2147483647 (предел таймера); иначе операция возвращает `REQ_OPTIONS_INVALID`. Ограничивает время отдельного хэндшейка от вызова Fetch до получения заголовков ответа, не накладывая ограничений на длительность открытого потока. Параметр существует только внутри объекта параметров `withSSEReconnect({...})`; наличие этого объекта включает автоматическое переподключение со значением `attempts: 3` по умолчанию, поэтому один `connectTimeoutMs` тоже его включает. Чтобы ограничить только хэндшейк, добавьте `attempts: 0`.

## 5. Лимиты буфера и очереди

Значения по умолчанию — `maxBufferSize: 64 * 1024` байт и `maxQueueSize: 1024` событий. Оба лимита должны быть положительными безопасными целыми числами. Дедлайна хэндшейка по умолчанию нет: ожидающий Fetch ждёт платформу, отмену вызывающим кодом или явно заданный `connectTimeoutMs`. Превышение любого лимита ёмкости фатально (`stream.closed` завершается с `kind: "error"`, а итератор выбрасывает ошибку — события никогда не теряются молча):

| Опция определения | Что ограничивает                                                  | Финальный код сбоя    |
| ----------------- | ----------------------------------------------------------------- | --------------------- |
| `maxBufferSize`   | Размер неполных или избыточных байтов кадра до пустой строки      | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`    | Количество проверенных событий, ожидающих потребителя `for await` | `CAP_QUEUE_OVERFLOW`  |

## 6. Закрытие и освобождение ресурсов [#close-and-dispose]

Сигнал `signal`, переданный через `client({ signal })`, управляет всей длительностью жизни потока. Чтобы ограничить по времени только первоначальный хэндшейк подключения и не обрывать уже открытый поток, очищайте таймер сразу после завершения `await watchOrders(...)` (как показано на второй вкладке выше) либо задайте в `withSSEReconnect` параметр `connectTimeoutMs` вместе с `attempts: 0` (один `connectTimeoutMs` также включает автоматическое переподключение с тремя попытками).
