# Тестирование

`@defjs/core` уже тестирует собственный транспорт и движок кодеков. Когда вы используете Defjs в своём приложении или SDK, тесты проверяют **код, который написали вы**: раскладку `builder`, сетевые ключи `.alias()`, декодирование `struct`, перехватчики авторизации, бизнес-обработку ошибок и отмену запросов при размонтировании UI.

## Что тестировать в проекте — и почему не нужно использовать `vi.mock`

**Не** заменяйте заглушками и не мокируйте через `vi.mock(...)` экспортированные функции `defineRequest`, `defineEventStream` или `defineWebSocket`. Мок операции полностью обходит ваш `builder`, сериализацию `.alias()`, перехватчики, обработку статусов и декодирование `struct`.

Вместо этого создавайте изолированный тестовый `Client` на каждый тест с хэндлом в памяти (`withHTTPHandle`, `withSSEHandle` или `withWebSocketHandle`). Так ваши реальные определения и бизнес-логика выполняются в памяти без сетевых сокетов:

| Слой в вашем проекте                                        | Что проверяет тест                                                                                     | Как подключить тестовый `Client`                                                                  |
| :---------------------------------------------------------- | :----------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| Определения и схемы (`src/api/request/`, `src/api/schema/`) | Раскладка `builder` (`path`, `query`, `headers`, `body`), `.alias()`, `output`/`error`                 | Импортировать реальную операцию и передать свежий клиент с `withHTTPHandle`                       |
| Бизнес-хелперы и перехватчики (`checkout.ts`, `client.ts`)  | Заголовки авторизации, повтор после обновления `401`, многошаговые сценарии, отображение ошибок        | Передать `testClient` (с `withInterceptors(...)`) прямо в бизнес-функцию                          |
| Потребители SSE и WebSocket (`src/events/`, `src/quotes/`)  | Прикладная обработка входящих событий, исходящие сообщения, очистка `await using`                      | Подавать фреймы в памяти через `withSSEHandle` или `withWebSocketHandle`                          |
| Компоненты React / Vue (`OrderCard.tsx`, `OrderView.vue`)   | Состояние загрузки, отрисованные данные, UI ошибок, отмена через `AbortController` при размонтировании | Обернуть в `<ClientProvider client={testClient}>` или установить `createClientPlugin(testClient)` |

## 1. Тестирование определений запросов и схем (`withHTTPHandle`)

Импортируйте реальные операции `defineRequest` из проекта и создайте тестовый `Client` с `withEndpoint("https://fixture.invalid")` и `withHTTPHandle(...)`:

- **Зачем `https://fixture.invalid`**: `createClient` проверяет базовый URL до входа в `withHTTPHandle`; домен `.invalid` зарезервирован по RFC и никогда не уйдёт в реальный DNS даже при ошибке настройки.
- **Отдельный хэндл под каждый транспорт**: `withHTTPHandle` перехватывает только HTTP (`defineRequest`). Для `defineEventStream` используйте `withSSEHandle`, для `defineWebSocket` — `withWebSocketHandle`.
- **Повторы по умолчанию и ловушка `withRetry(undefined)`**: Без `withRetry` повторы отключены — не подключайте его в обычных тестах, чтобы `429`/`502`/`503`/`504` и сетевые ошибки возвращались сразу после первой попытки без ожидания `1s + 2s + 4s`. Осторожно: вызов `withRetry()` или `withRetry(undefined)` включает **3 повтора по умолчанию**. Чтобы явно отключить повторы в общей фабрике, передайте `withRetry({ maxRetries: 0 })`.

### Три основы: изоляция, проверка исходящего формата и три исхода HTTP

- **Изолируйте клиент на каждый тест**: Создавайте свежий `createClient(...)` в каждом `test(...)` или хелпере, чтобы бюджеты повторов и счётчики не протекали между тестами.
- **Проверяйте исходящий формат**: Внутри `withHTTPHandle(async (input, init) => ...)` соберите `const request = new Request(input, init)` и проверьте `request.method`, `request.url`, `request.headers` и `await request.text()` (или `await request.json()`).
- **Симулируйте и проверяйте три основных исхода HTTP**:
  - **Успех `2xx`**: Проверьте `expect(err).toBeNull()`, сразу после него `if (err) throw err;` для сужения `data`, затем проверьте поля.
  - **Ошибка API `4xx` / `5xx`**: Верните `Response.json(..., { status: 422 })`, сначала проверьте `if (err)`, внутри сузьте `if (err.code === "HTTP_STATUS")`, проверьте `err.status`, `err.data` и `err.response`, выполните `return` и поставьте `expect.unreachable(...)` после блока (в `bun:test` бросайте `new Error("expected fault")`).
  - **Сбой сети (`NET_UNREACHABLE`)**: **Не** возвращайте `Response.error()`. Любой возвращённый `Response` (даже со статусом `0`) проходит через обработку HTTP-статуса и даёт `HTTP_STATUS`. Вместо этого отклоните промис — например `Promise.reject(new TypeError("fetch failed"))` — чтобы получить `NET_UNREACHABLE`:

```ts
import { createClient, withEndpoint, withHTTPHandle } from "@defjs/core";
import { expect, test } from "vitest";
import { createOrder } from "./sdk/orders.ts";

test("возвращает NET_UNREACHABLE при отклонении fetch", async () => {
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withHTTPHandle(() => Promise.reject(new TypeError("fetch failed"))),
  );

  const [err] = await createOrder(client, { sku: "book", quantity: 1 });
  if (err) {
    expect(err.code).toBe("NET_UNREACHABLE");
    return;
  }

  expect.unreachable("expected NET_UNREACHABLE fault");
});
```

### Тестирование `withRetry` и повтора `next()` после обновления токена на `401`

- **Восстановление `withRetry` при `503`**: Храните `let attempts = 0` вне `withHTTPHandle` и укажите `withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] })` для мгновенного повтора. Внимание: параметр `methods` **перезаписывает** список по умолчанию (`["GET", "HEAD", "OPTIONS", "TRACE", "PUT", "DELETE"]`), поэтому пишите `methods: ["GET", "POST"]`, если тот же клиент должен повторять и `GET`.
- **Обновление токена при `401` внутри перехватчика**: Повторный вызов `next(...)` внутри перехватчика не использует `withRetry` — тестируйте его счётчиком в `withHTTPHandle`. Если код читает `err.data` на `401`, операция должна объявлять `error: struct(...)`.

```ts
import {
  createClient,
  createHttpInterceptor,
  withEndpoint,
  withHTTPHandle,
  withInterceptors,
  withRetry,
} from "@defjs/core";
import { expect, test } from "vitest";
import { submitOrder } from "./src/checkout.ts";

test("повторяет 503 для POST, если POST указан в methods", async () => {
  let attempts = 0;
  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] }),
    withHTTPHandle(async () => {
      attempts += 1;
      if (attempts === 1) {
        return Response.json({ message: "try again" }, { status: 503 });
      }
      return Response.json({ id: "ord_2" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "pen", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_2");
});

test("обновляет токен на 401 и повторяет next() в перехватчике", async () => {
  let token = "expired-token";
  let attempts = 0;

  const refreshAuth = createHttpInterceptor(async (req, next) => {
    const first = await next({
      ...req,
      headers: { ...req.headers, authorization: `Bearer ${token}` },
    });
    if (first[0]?.code === "HTTP_STATUS" && first[0].status === 401) {
      token = "fresh-token";
      return next({
        ...req,
        headers: { ...req.headers, authorization: `Bearer ${token}` },
      });
    }
    return first;
  });

  const client = createClient(
    withEndpoint("https://fixture.invalid"),
    withInterceptors(refreshAuth),
    withHTTPHandle(async (input, init) => {
      attempts += 1;
      const auth = new Request(input, init).headers.get("authorization");
      if (auth === "Bearer expired-token") {
        return new Response(null, { status: 401 });
      }
      expect(auth).toBe("Bearer fresh-token");
      return Response.json({ id: "ord_3" }, { status: 201 });
    }),
  );

  const [err, order] = await submitOrder(client, { sku: "mug", quantity: 1 });
  expect(err).toBeNull();
  if (err) throw err;

  expect(attempts).toBe(2);
  expect(order.id).toBe("ord_3");
});
```

## 3. Тестирование прикладных потребителей SSE и WebSocket

Если проект оборачивает `defineEventStream` или `defineWebSocket`, подавайте фреймы в памяти через `withSSEHandle` или `withWebSocketHandle`:

- **SSE (`withSSEHandle`)**: Верните `Response` с `ReadableStream<Uint8Array>` и заголовком `"content-type": "text/event-stream"`. Для симуляции обрыва в середине потока вызовите `controller.error(new TypeError("stream dropped"))` после нескольких чанков (для отказа при открытии верните `{ status: 500 }`).
- **WebSocket (`withWebSocketHandle`)**: Передайте подкласс `EventTarget`, реализующий `WebSocketHandle` (`static readonly OPEN = 1` и `readyState`). `FakeQuoteSocket` планирует `open` и первые сообщения через `queueMicrotask`, чтобы вызывающий код успел навесить слушатели или войти в `for await` до прихода событий; синхронная отправка в конструкторе уйдёт слишком рано. Для сбоя в середине сессии отправьте `new Event("error")`, а затем `new CloseEvent("close", { code: 1011, reason: "boom" })`.

## 4. Как организовать проект, чтобы каждый слой было легко тестировать

Схема организации из [Прикладного API-слоя](/ru-RU/docs/application-api) позволяет писать тесты без `vi.mock`:

- **Храните `src/api/request/*.ts` без клиента**: Экспортируйте только `defineRequest`, `defineEventStream` и `defineWebSocket` и никогда не импортируйте туда `apiClient`.
- **Принимайте `Client` (или `DerivableClient`) в бизнес-хелперах**:
  - **Выбор `Client` или `DerivableClient`**: `createClient(...)` возвращает `DerivableClient`, который совместим с `Client`. Но если хелпер сам вызывает `client({ signal })`, тип параметра обязан быть **`DerivableClient`**.
  - **Порядок аргументов и SSR-фабрики**: Передавайте `client` первым (`placeOrder(client: DerivableClient, input: ...)`) или последним со значением по умолчанию (`placeOrder(input: PlaceOrderInput, client: Client = apiClient)`), и экспортируйте перехватчики вместе с `createServerApiClient(token, ...options: ClientOption[])` из `src/api/client.ts`.
  - **Ловушка `withXSRF()` в тестах Node / Bun**: `withXSRF()` обращается к браузерным глобалам (`globalThis.location`). Если `src/api/client.ts` на верхнем уровне безусловно создаёт `apiClient = createClient(..., withXSRF())`, любой импорт хелпера с `= apiClient` упадёт при загрузке модуля в Node или Bun. Ограничьте `withXSRF()` проверкой `typeof window !== "undefined"` или создавайте клиент внутри фабрики.
- **Внедряйте `testClient` в компоненты React и Vue**:

import { createClient, withEndpoint, withHTTPHandle } from "@defjs/core";
import { ClientProvider } from "@defjs/react";
import { render, screen } from "@testing-library/react";
import { expect, test } from "vitest";
import { OrderCard } from "./OrderCard.tsx";

test("внедряет testClient через ClientProvider", async () => {
  const testClient = createClient(
    withEndpoint("https://fixture.invalid"),
    withHTTPHandle(async () => Response.json({ id: "ord_1", total: 1200 })),
  );

  const { unmount } = render(
    <ClientProvider client={testClient}>
      <OrderCard id="ord_1" />
    </ClientProvider>,
  );

  expect(await screen.findByText("ord_1")).toBeTruthy();
  unmount();
});

## 5. Детерминированное тестирование таймаутов и таймеров

Для бэкоффа повторов, пауз переподключения или heartbeat используйте `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })` в Vitest (`jest.useFakeTimers()` в Bun test). Ограничение `toFake` оставляет Promise и микротаски настоящими, чтобы `async`/`await` не зависал.

Учтите, что **фейковые таймеры Vitest не продвигают нативные часы `AbortSignal.timeout`**, так как те используют нативный таймер среды выполнения, а не JS `setTimeout`:

- Чтобы проверить дедлайн `client({ signal })` в Vitest, прервите `AbortController` из управляемого `setTimeout` с причиной `new DOMException("request deadline", "TimeoutError")`. Всегда дождитесь `await ready` перед вызовом `advanceTimersByTimeAsync`, чтобы `setTimeout` внутри хэндла уже был поставлен:

<include cwd lang="typescript">
  examples/testing/deadline.ts#example
</include>

- Альтернативно `withRetry({ maxRetries: 0, attemptTimeoutMs: 500 })` внутри использует JS `setTimeout`, поэтому `vi.advanceTimersByTimeAsync(500)` сразу вызывает `NET_TIMEOUT` в Vitest.
- В **Bun test** `jest.useFakeTimers()` и `jest.advanceTimersByTime()` управляют также `AbortSignal.timeout`. Проверяйте переходы состояний или счётчики попыток и всегда возвращайте настоящие таймеры в `finally`.
