# Тестирование

`@defjs/core` уже тестирует собственный транспорт и движок кодеков. Когда вы используете Defjs в своём приложении или SDK-пакете, тесты нужны для проверки **кода, который написали вы** — ваших определений запросов и схем `struct` (`src/api/request/`, `src/api/schema/`), ваших перехватчиков (`src/api/client.ts`), бизнес-логики (`src/checkout.ts`) и UI-компонентов.

## Что тестировать в проекте — и почему не нужно использовать `vi.mock`

**Не** заменяйте заглушками и не мокируйте через `vi.mock(...)` экспортированные функции `defineRequest`, `defineEventStream` или `defineWebSocket`. Вместо этого создавайте изолированный тестовый `Client` на каждый тест с `withHTTPHandle`, `withSSEHandle` или `withWebSocketHandle`. Так вы сквозным образом проверяете собственные определения и политики приложения в памяти, не открывая сетевых сокетов:

| Слой в вашем проекте                                        | Что проверяет тест                                                                                     | Как подключить тестовый `Client`                                                                  |
| :---------------------------------------------------------- | :----------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| Определения и схемы (`src/api/request/`, `src/api/schema/`) | Раскладка `builder` (`path`, `query`, `headers`, `body`), `.alias()`, `output`/`error`                 | Импортировать реальную операцию и передать свежий клиент с `withHTTPHandle`                       |
| Бизнес-хелперы и перехватчики (`checkout.ts`, `client.ts`)  | Заголовки авторизации, многошаговые сценарии, доменное отображение ошибок, повторы                     | Передать `testClient` (с `withInterceptors(...)`) прямо в бизнес-функцию                          |
| Потребители SSE и WebSocket (`src/events/`, `src/quotes/`)  | Прикладная обработка входящих событий, исходящие сообщения, очистка `await using`                      | Подавать фреймы в памяти через `withSSEHandle` или `withWebSocketHandle`                          |
| Компоненты React / Vue (`OrderCard.tsx`, `OrderView.vue`)   | Состояние загрузки, отрисованные данные, UI ошибок, отмена через `AbortController` при размонтировании | Обернуть в `<ClientProvider client={testClient}>` или установить `createClientPlugin(testClient)` |

## 1. Тестирование определений запросов и схем (`withHTTPHandle`)

Импортируйте реальные операции `defineRequest` из вашего проекта, создайте изолированный тестовый `Client` с зарезервированным базовым URL (например, `https://fixture.invalid`) и `withHTTPHandle(...)`, и проверьте исходящий `Request`. Повторы отключены, пока не настроен `withRetry`; опускайте `withRetry` в обычных тестовых клиентах, чтобы тесты для `502`/`503`/`504` и сетевых ошибок завершались сразу после одной попытки без ожидания бэкоффа.

### Изоляция, проверка исходящего формата и error-first кортеж

- **Изолируйте клиент на каждый тест**: Создавайте свежий `createClient(...)` в каждом `test(...)` или хелпере, чтобы бюджеты повторов и состояние хэндла не протекали между тестами.
- **Проверяйте исходящий сетевой формат**: Внутри `withHTTPHandle(async (input, init) => ...)` создайте `const request = new Request(input, init)` и проверьте `request.method`, `request.url`, `request.headers`, а также `await request.text()` (или `await request.json()`), чтобы убедиться, что `builder` и `.alias()` соответствуют контракту бэкенда.
- **Проверяйте кортеж `[err, data, response]`**:
  - Для ответов `2xx` проверяйте `expect(err).toBeNull()`, затем сразу `if (err) throw err;` перед чтением декодированных полей `data` (включая маппинг `.alias()`).
  - Для ошибок сначала ставьте защиту `if (err)`, внутри сужайте `if (err.code === "HTTP_STATUS")` для проверки `err.status`, `err.data` и `err.response` (а при ошибках декодирования, preflight или обёрнутых бизнес-исключениях `Error` проверяйте `err.cause`), выполняйте `return` внутри `if (err)` и ставьте `expect.unreachable(...)` после блока.

## 2. Тестирование бизнес-функций и своих перехватчиков

Передайте `Client` в бизнес-функции оркестрации (`checkout.ts`) и подключите ваши собственные `createHttpInterceptor`-хелперы (`withInterceptors(bearerAuth(...))`) к тестовому клиенту. В одном офлайн-тесте вы проверяете заголовки авторизации от перехватчика, JSON-кодирование `.alias()` в `submitOrder` и обработку как успешного результата, так и объявленных ошибок (например, `409` Conflict):

Чтобы протестировать восстановление через `withRetry` при временном `503` без реального ожидания таймеров, храните счётчик `let attempts = 0` внутри `withHTTPHandle` и задайте `withRetry({ maxRetries: 2, delayMs: 0, methods: ["POST"] })` (`methods: ["POST"]` требуется для повторов `POST`-операций вроде `submitOrder`). Повтор на уровне перехватчика (например, обновление токена при `401` с повторным вызовом `next(...)` внутри перехватчика) не использует `withRetry` — тестируйте его напрямую со счётчиком состояния в `withHTTPHandle`.

## 3. Тестирование прикладных потребителей SSE и WebSocket

Если в проекте есть функции-потребители или агрегаторы состояния поверх `defineEventStream` или `defineWebSocket`, подавайте симулированные фреймы в памяти через `withSSEHandle` или `withWebSocketHandle` и проверяйте результат бизнес-функции:

- **SSE (`withSSEHandle`)**: Верните `Response` с `ReadableStream<Uint8Array>` и заголовком `content-type: "text/event-stream"`.
- **WebSocket (`withWebSocketHandle`)**: Передайте лёгкий класс-наследник `EventTarget`, реализующий `WebSocketHandle` (`static readonly OPEN = 1`), который записывает отправленные сообщения и генерирует `open`, `MessageEvent("message")` и `CloseEvent("close")`.

## 4. Как организовать проект, чтобы каждый слой было легко тестировать

Схема организации из [Прикладного API-слоя](/ru-RU/docs/application-api) позволяет писать тесты полностью без `vi.mock`:

- **Храните `src/api/request/*.ts` без привязки к клиенту**: Экспортируйте только `defineRequest`, `defineEventStream` и `defineWebSocket`. Никогда не импортируйте боевой `apiClient` в файлы определений, чтобы любой тест мог вызывать операции напрямую с клиентом на базе `with*Handle`.
- **Принимайте `Client` (или `DerivableClient`) параметром в бизнес-хелперах**: передавайте `client` явно первым параметром (`export async function placeOrder(client: Client, input: ...)` при простой передаче или `client: DerivableClient`, если выводятся параметры на вызов вроде `client({ signal })`) либо выносите параметр со значением по умолчанию в конец (`export async function placeOrder(input: PlaceOrderInput, client: Client = apiClient)`), чтобы рабочий код вызывал `placeOrder(input)`, а тесты — `placeOrder(input, testClient)`. Экспортируйте свои перехватчики и SSR-фабрики (`createServerApiClient(token, ...options: ClientOption[])`, передающие конечные `ClientOption` в `createClient(...)`) из `src/api/client.ts`, чтобы подключать `withHTTPHandle` в тестах.
- **Внедряйте `testClient` в компоненты React и Vue**:
  - **React (`@defjs/react`)**: Оборачивайте тестируемый компонент в `<ClientProvider client={testClient}>` (или передавайте `testClient` в `useClient(overrideClient)`).
  - **Vue (`@defjs/vue`)**: Устанавливайте `app.use(createClientPlugin(testClient))` (или `provide(HTTP_CLIENT, testClient)`) при монтировании компонентов в тестах.

## 5. Детерминированное тестирование таймаутов и таймеров

Для бэкоффа повторов, пауз переподключения SSE/WebSocket или heartbeat WebSocket в политиках приложения используйте `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout", "Date"] })` в Vitest (`jest.useFakeTimers()` в Bun test). Фейковые таймеры Vitest **не** продвигают нативные часы `AbortSignal.timeout`; чтобы детерминированно проверить дедлайн запроса в Vitest, прервите `AbortController` из управляемого `setTimeout` с причиной `TimeoutError`:
