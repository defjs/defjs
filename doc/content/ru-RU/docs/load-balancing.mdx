# Балансировка нагрузки и отказоустойчивость

Когда приложение настраивает несколько базовых URL с помощью `withEndpoint(...urls)`, Defjs может распределять запросы между репликами, на время исключать узлы, которые продолжают падать, пропускать узлы, которые отвергает ваша собственная функция здоровья, и опционально повторять неудачный вызов на другом эндпоинте. Defjs не решает, что значит «здоровый»: только функция, которую предоставляете вы, может пометить эндпоинт как нездоровый.

## 1. Выбор стратегии балансировки нагрузки

| Стратегия                                                                           | Лучше всего подходит для                                                    | Фильтрация по доступности по умолчанию          |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------- |
| [`pickFirstBalancer(options?)`](/ru-RU/api/core/pickfirstbalancer) _(По умолчанию)_ | Браузерных приложений с упорядоченным списком «основной + резервный регион» | Выключена (opt-in через `outlierDetection: {}`) |
| [`roundRobinBalancer(options?)`](/ru-RU/api/core/roundrobinbalancer)                | Вызовов между серверами по равноправным репликам (поддерживает `weights`)   | Выключена (opt-in через `outlierDetection: {}`) |
| [`p2cBalancer(options?)`](/ru-RU/api/core/p2cbalancer)                              | Серверных вызовов с разбросом задержек реплик или нагрузки в процессе       | Выключена (opt-in через `outlierDetection: {}`) |

### Как работают `pickFirstBalancer` и `p2cBalancer`

- **`pickFirstBalancer`**: остаётся на первом URL и сдвигается на `NET_UNREACHABLE` или `NET_UNAVAILABLE` (HTTP 502, 503 или 504). Порядок и закреплённый эндпоинт следуют полному списку эндпоинтов клиента (`members`). Повтор выбирает снова из всех эндпоинтов и поэтому следует тому же правилу: после отказа в соединении или 502, 503 или 504 он доходит до следующего эндпоинта, а после таймаута, который pick-first не сдвигает, снова пробует тот же эндпоинт. Задайте `failbackMs: 30_000`, чтобы вернуться к первому эндпоинту по одному лишь времени: когда закреплённый эндпоинт был вдали от первого так долго, следующий выбор, среди кандидатов которого есть первый эндпоинт, выбирает его и снова делает закреплённым. Никто не судит, восстановился ли первый эндпоинт. Если он снова падает, правило сдвига выше уводит с него, и время начинается заново. Выбирайте `failbackMs` длиннее промежутка между выборами, например задержки переподключения SSE или WebSocket; иначе каждый выбор возвращается к первому эндпоинту.
- **`roundRobinBalancer` без весов**: счётчик начинается со случайного `uint32`, и каждый `pick` его продвигает, включая выбор для повтора или переподключения потока. Без `outlierDetection` и при вызовах, которые идут один за другим, эндпоинт, который падает постоянно, поэтому получает больше 1/n первых попыток. При ровно двух эндпоинтах и включённых повторах он получает их все, так что каждому вызову нужен один повтор. Одновременные вызовы перемежают свои выборы и ломают этот шаблон. С `outlierDetection: {}` падающий эндпоинт на время исключается.
- **Веса `roundRobinBalancer`**: отсутствующий вес равен `1`; заданные веса — положительные конечные числа. Сглаженный взвешенный round-robin сохраняет пропорции выбора (например, при `3:1` узел с большим весом получает три выбора из четырёх). Крайние величины масштабируются во избежание переполнения; отношения ниже точности чисел с плавающей точкой могут округляться до нуля. Выбор и очистка устаревших текущих значений требуют O(число участников + число кандидатов) работы на каждый выбор.
- **`p2cBalancer` (Power of Two Choices)**: случайным образом выбирает двух независимых кандидатов без повторений и берёт узел с меньшей оценкой: `PeakEwma RTT × (pending + 1)` (или только количество активных запросов `pending`, если указано `load: "pending"`). Значения по умолчанию (`defaultRttMs: 30`, `decayMs: 10000`) соответствуют соглашениям Linkerd и библиотеки tower. Pending резервируется в момент, когда `pick` выбирает эндпоинт, поэтому пачка вызовов в одном такте распределяется по эндпоинтам, и освобождается, когда начинается ответ узла (заголовки HTTP-ответа, хэндшейк SSE, открытие WebSocket) либо по завершении попытки, если ответ не начался. Для SSE и WebSocket это значит, что p2c балансирует хэндшейки, а не число открытых соединений.

Состояние балансировщика (закреплённый эндпоинт, исключения и нагрузка p2c) и бюджет повторов принадлежат клиенту. Создавайте клиент один раз на приложение, а клиенты для отдельных вызовов получайте через `client(options)`: производные клиенты сохраняют и состояние балансировщика, и бюджет повторов. Передача одного значения балансировщика нескольким клиентам через `withBalancer` разделяет только состояние балансировщика; у каждого клиента свой бюджет повторов. Новый `createClient` на каждый запрос начинает оба с нуля.

## 2. Повторы [#retries]

Повтором управляют три отдельных решения: **повторять ли** (`withRetry`), **куда отправить** (рантайм просит балансировщик выбрать снова из всех эндпоинтов) и **сколько ждать** (backoff). Один `withRetry(options)` покрывает HTTP, SSE и WebSocket и хранится в `config.retry`; опция запроса `retry` заменяет его для одного вызова. Три транспорта делят опции, порядок решения и расчёт backoff и различаются только тем, какие сбои они повторяют по умолчанию. Балансировщик ничего не знает о политике повтора; пользовательскому балансировщику не требуется особое взаимодействие.

Повторы **выключены по умолчанию**. Если опустить `withRetry`, на вызов приходится одна попытка, без backoff, а для HTTP бюджет повторов не создаётся и кредиты на него не начисляются. Выбор на последующих вызовах не меняется: `pickFirstBalancer` по-прежнему может сдвинуться после неудачного вызова. `withRetry()` эквивалентен `withRetry({})`: до `maxRetries: 3` повторов после первой попытки, задержка `1000` мс, которая удваивается с каждым повтором до `30000` мс, и джиттер ±20 %.

Это следует экосистеме Go: [gRPC помещает `retryPolicy` в service configuration](https://grpc.io/docs/guides/retry/), рядом с конфигурацией балансировки, а [go-kit `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) явно оборачивает балансировщик. Ни один из них не применяет политику повторов приложения по умолчанию. Политика повторов gRPC требует настроек backoff и использует джиттер ±0.2. Счётчики повторов, которые не включают первую попытку (`maxRetries`), совпадают с ky, got, undici и Go-библиотекой `go-retryablehttp`; `maxAttempts` в gRPC считает и исходную попытку. gRPC может делать прозрачные повторы для гонок низкого уровня; Defjs их не воспроизводит.

После каждой неудачной попытки поток один и тот же на каждом транспорте, в таком порядке:

1. Отмена вызывающим кодом, ручной `close()`, фатальная ошибка и тело запроса `ReadableStream` завершают вызов. `shouldRetry` не вызывается.
2. Когда сделано `maxRetries` повторов, вызов заканчивается. `shouldRetry` не вызывается.
3. Решает `shouldRetry(context)`; без неё решает `context.retryable`. Функция может быть асинхронной и получает [`RetryContext`](/ru-RU/api/core/retrycontext-type), суженный по `transport`. Верните `context.retryable`, чтобы сохранить правило по умолчанию и добавить своё сверху.
4. Только HTTP: бюджет оплачивает повтор, иначе вызов заканчивается.
5. Вызов ждёт задержку backoff, затем балансировщик выбирает снова.

- **Число повторов (`maxRetries`)**: повторы после первой попытки, по умолчанию `3`; `0` никогда не повторяет. Вызов с `maxRetries: 0` и `attemptTimeoutMs` лишь ограничивает время каждой попытки. Для SSE и WebSocket счётчик начинается заново, когда соединение снова установлено (успешный хэндшейк или `open`), поэтому он ограничивает каждый обрыв, а не сессию. Сервер, который принимает соединение и сразу его обрывает, поэтому продолжает повторяться; остановите его через `shouldRetry`. Настроенного верхнего предела нет. Считаются внешние попытки, а не физические отправки внутри перехватчика приложения: перехватчик с циклом `next()` может отправлять на один эндпоинт несколько раз. Например, три отправки перехватчика на сбойный основной узел плюс один внешний повтор на исправный резервный дают четыре сетевых запроса при `maxRetries: 1`; builder и внешний слой аутентификации цепочки перехватчиков выполняются дважды, а не четырежды.
- **Какие сбои повторяются по умолчанию**: HTTP повторяет метод из `methods`, когда попытка не получила ответа (`NET_UNREACHABLE`), получила `502`, `503` или `504` (`NET_UNAVAILABLE`) или исчерпала `attemptTimeoutMs`. SSE повторяет метод из `methods` после сетевого сбоя хэндшейка, хэндшейка `502`/`503`/`504`, таймаута попытки или сетевой ошибки на открытом потоке; штатный конец потока завершает вызов. WebSocket повторяет каждое закрытие, которого не запрашивал `session.close()`, включая соединение, которое так и не открылось, и heartbeat без ответа, но не конструктор, который бросает исключение. Статус вроде `429` или `500` по умолчанию не повторяется; `shouldRetry` получает его с `retryable: false` и `status` и может вернуть `true`. `methods` по умолчанию — `GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT` и `DELETE`, сравнение без учёта регистра; HTTP требует, чтобы каждый метод, который отправила попытка, после переписывания перехватчиками, был в этом списке. POST повторяется, только если вы добавите его в `methods` или вернёте `true` из `shouldRetry`, и для этого нужна идемпотентность на уровне приложения между репликами. Подходящий повтор HTTP заново собирает запрос и прогоняет всю цепочку перехватчиков с самого внешнего слоя. SSE повторно использует собранный запрос и только меняет URL, а WebSocket заново выполняет `beforeConnect`.
- **Backoff (`delayMs`, `factor`, `jitter`, `maxDelayMs`)**: перед повтором n ожидание равно `delayMs × factor^(n−1)` с мультипликативным джиттером, с потолком после джиттера и округления. Значения по умолчанию — `1000`, `2`, `0.2` и `30000`. `delayMs: 0` пропускает ожидание; `maxDelayMs: Infinity` снимает потолок. Потолок таймера платформы по-прежнему действует. Для SSE поле `retry:` сервера из одних цифр заменяет `delayMs` для последующих попыток. Core не читает `Retry-After`. Обработка этого заголовка, включая любой предел задержки, — [политика перехватчика приложения](/ru-RU/docs/interceptors), а не часть этого backoff.
- **Один эндпоинт**: повтор выбирает из всех эндпоинтов, включая тот, что только что упал, поэтому единственный эндпоинт пробуется снова после задержки backoff. Бюджет повторов и `maxRetries` ограничивают шторм.
- **Таймаут на попытку и общий таймаут вызова**: `attemptTimeoutMs` ограничивает одну попытку. HTTP измеряет каждый Fetch, отправленный на выбранный эндпоинт, от вызова до полного чтения тела ответа; SSE останавливается на заголовках ответа, а WebSocket — на `open`. Работа перехватчиков вокруг отправки HTTP (например, обновление токена после `401`) и декодирование структуры не учитываются и никогда не засчитываются против эндпоинта; дедлайн вызывающего, истёкший во время работы перехватчиков после завершения отправки, не сообщается балансировщику как `NET_TIMEOUT` — сообщается собственный исход эндпоинта. Сигнал вызывающего `client({ signal: AbortSignal.timeout(ms) })` покрывает каждую попытку **и ожидание backoff**. Отмена во время ожидания возвращает сбой отмены вызывающего и нового выбора не делает. Опции не проверяются во время выполнения.
- **Нет пригодного эндпоинта при повторе**: если раунд повтора не может использовать ни один эндпоинт (выбор балансировщика не удался или URL следующего эндпоинта не разрешается), HTTP-вызов возвращает сбой предыдущей попытки (например, `NET_UNREACHABLE`) вместо `REQ_BUILD_FAILED`.
- **Бюджет повторов Finagle / Linkerd (`budget`)**: только HTTP. У каждой конфигурации клиента свой бюджет, и его делят только производные клиенты с той же конфигурацией, а не клиенты с общим балансировщиком. Значения по умолчанию — `percentCanRetry: 0.2`, `minRetriesPerSecond: 10` и `ttlMs: 10000`: 20 % исходного трафика плюс резерв. И кредиты, и списания лениво истекают в десяти срезах по TTL/10. Повтор списывает до ожидания; исчерпанный бюджет ни ждёт, ни повторяет. Передайте `budget: false`, чтобы снять потолок. У SSE и WebSocket бюджета нет: общий с HTTP дал бы всплеску HTTP-повторов заблокировать переподключение.
- **Подсказка браузерного офлайна**: если `navigator.onLine === false`, сбои соединения помечаются как `{ attempted: false }`, не сдвигают балансировщики и не запускают HTTP-повторы.

Поздний `withRetry` заменяет политику. `withRetry()` и `withRetry(undefined)` ведут себя как `withRetry({})`. Чтобы выключить повторы после их включения, передайте `withRetry({ maxRetries: 0 })`.

### Переход с `withSSEReconnect` и `withWebSocketReconnect`

`withSSEReconnect` и `withWebSocketReconnect` исчезли, без алиаса. `withRetry` покрывает SSE и WebSocket, а опция запроса `reconnect` теперь называется `retry`.

- `attempts: N` становится `maxRetries: N`.
- `shouldReconnect` становится `shouldRetry`. Его контекст получает `transport` и `retryable`, и он вызывается, только пока повторы ещё остаются. Как и `shouldReconnect`, он заменяет правило по умолчанию, включая правило метода, поэтому функция, которая возвращает `true`, всё ещё повторяет поток `POST`.
- Значения по умолчанию изменились: `factor` у SSE с `1` на `2`, `maxDelayMs` у SSE с неограниченного на `30000`; `jitter` с `0` на `0.2` на обоих транспортах.
- Хэндшейки SSE: в 0.6 каждый не-2xx хэндшейк завершал поток, не спрашивая `shouldReconnect`. Теперь хэндшейк `502`, `503` или `504` повторяется как отказ в соединении, а любой другой не-2xx хэндшейк доходит до `shouldRetry` с `retryable: false`.
- Коды сбоев: хэндшейк переподключения, который завершает поток SSE статусом не-2xx, теперь сообщает `HTTP_STATUS` в `closed.code`; 0.6 сообщал `RES_DECODE_FAILED`, которого в `EventStreamFaultCode` больше нет. `shouldRetry`, который бросает исключение, завершает вызов с `EXT_HOOK_FAILED` и брошенным значением в `cause` на каждом транспорте; бросающий `shouldReconnect` завершал поток SSE с `NET_UNREACHABLE`.
- Heartbeat WebSocket: в 0.6 heartbeat без ответа завершал сессию ошибкой и никогда не доходил до `shouldReconnect`. Теперь это обрыв, как любой другой: `shouldRetry` получает его с `retryable: true`, `cause` и без `code` закрытия и может вернуть `false`, чтобы завершить сессию той же ошибкой, как раньше.
- `withRetry` также повторяет HTTP. Чтобы оставить HTTP-вызовам одну попытку, верните `false` для `context.transport === "http"`.

```ts
// Before
createClient(
  withEndpoint(url),
  withSSEReconnect({ attempts: 3, delayMs: 1000 }),
  withWebSocketReconnect({
    attempts: 3,
    shouldReconnect: ({ code }) => code !== 1008,
  }),
);
// After
createClient(
  withEndpoint(url),
  withRetry({
    maxRetries: 3,
    shouldRetry: (context) => {
      if (context.transport === "http") return false;
      if (context.transport === "websocket" && context.code === 1008)
        return false;
      return context.retryable;
    },
  }),
);
```

### Границы браузерного развёртывания

- Сбой CORS в браузере поступает в Fetch как сбой соединения и сообщается как `NET_UNREACHABLE`, неотличимый от недоступного хоста. Он может сдвинуть выбор эндпоинта и вызвать включённый повтор для безопасного метода; успешный повтор поэтому может скрыть неправильную настройку CORS основного региона.
- Сервер может обработать POST, даже если в ответе нет необходимых заголовков CORS. Приложение тогда получает `NET_UNREACHABLE`, не зная, удалась ли запись. POST по умолчанию не повторяется; явное включение повторов записей требует идемпотентности на уровне приложения между репликами.
- Отклонённое сервером обновление до WebSocket (например, с `401`) в браузерах неотличимо от недоступного эндпоинта и сообщается как `NET_UNREACHABLE`, поэтому просроченные учётные данные могут приводить к исключению эндпоинтов.
- Cookies привязаны к хосту, а не порту: два эндпоинта на `localhost` с разными портами могут использовать один cookie, а `localhost` и `127.0.0.1` — нет. Наборы эндпоинтов с несколькими origin требуют продуманной политики cookies/токенов и учётных данных CORS; `withCredentials(true)` не меняет область действия cookies.
- Явная подсказка офлайна (`navigator.onLine === false`) подавляет привязку к эндпоинту и повторы при сбое соединения. Это лишь подсказка браузера, а не надёжная проверка доступности.

## 3. Исключение по сбоям и ваша собственная функция здоровья (`outlierDetection`)

У Defjs нет встроенного понятия здорового эндпоинта. [`outlierDetection`](/ru-RU/api/core/outlierdetection) делает две необязательные вещи, и каждый встроенный балансировщик принимает его через опцию `outlierDetection` (`pickFirstBalancer`, `roundRobinBalancer` и `p2cBalancer` оставляют его выключенным, пока вы не передадите объект, `{}` — значения по умолчанию). Он считает классифицированные сбои и на время исключает эндпоинт, а также пропускает эндпоинт, который отвергает ваша функция `isHealthy`:

1. **Подсчёт сбоев**: правило `isFailure` по умолчанию считает сбоем любой исход с кодом: `NET_UNREACHABLE`, `NET_UNAVAILABLE`, `NET_SERVER_ERROR`, `NET_TIMEOUT` и `NET_BODY_INCOMPLETE`. Оно лишь решает, какие исходы идут в счёт исключения; это не суждение о здоровье, и его можно заменить, передав `isFailure`. Исход попытки без кода сбрасывает серию; неатрибутированные попытки оставляют её без изменений. После `consecutiveFailures` (по умолчанию `5`) учтённых исходов подряд эндпоинт исключается. Задайте `consecutiveFailures: 0`, чтобы выключить подсчёт.
2. **Исключение по времени**: эндпоинт исключается на `min(minPenaltyMs × level, maxPenaltyMs)` (от `1000ms` до `60000ms`) плюс до `50%` равномерного положительного джиттера; база вместе с джиттером никогда не превышает `maxPenaltyMs`. `level` — множитель исключения из outlier detection gRPC (gRFC A50): каждое исключение прибавляет единицу, успех его никогда не сбрасывает, и каждые `10` секунд без исключения снимают единицу, считая с момента окончания исключения. Когда время вышло, эндпоинт снова можно выбрать. Никто его не пробует и не решает, что он восстановился; если он всё ещё падает, ещё `consecutiveFailures` учтённых исходов исключают его снова на более долгий срок, поэтому эндпоинт, который принимает соединение и затем его обрывает, исключается на 1 с, 2 с, 3 с и так далее до `maxPenaltyMs`, пока сбои возвращаются быстрее, чем спадает один уровень. Исход попытки, начавшейся до исключения или пока эндпоинт был исключён, игнорируется, даже если он приходит после того, как эндпоинт снова можно выбрать, поэтому поздние результаты не исключают его заново. Конец исключения сверяется с часами при следующем выборе; таймер не запускается.
3. **`isHealthy`**: единственное суждение о здоровье. Она синхронна и выполняется при каждом выборе для каждого эндпоинта, который сейчас не исключён (исключённый эндпоинт не спрашивают), поэтому держите её дешёвым чтением состояния, которое ведёт ваше приложение, как на второй вкладке. Эндпоинт, для которого она возвращает `false`, не выбирается. Возврат `true` не заканчивает исключение: эндпоинт можно выбрать, только когда он не исключён и `isHealthy` его не отвергает. Брошенное исключение Defjs не перехватывает: выбор завершается с `REQ_BUILD_FAILED`, а брошенное значение — это `cause`.
4. **Ограниченная история**: История доступности хранит не менее 256 эндпоинтов и не менее текущего числа участников с учётом производных клиентов. Сначала вытесняются чистые или истёкшие записи, использованные наиболее давно, затем неполные последовательности сбоев. Запись с неистёкшим исключением вытесняется, только когда все сохранённые записи исключены; тогда удаляется самая старая. Само по себе отсутствие эндпоинта в одном вызове не сбрасывает его штраф. История нагрузки P2C также хранит не менее 256 записей и не менее текущего числа участников, поэтому списки длиннее 256 эндпоинтов сохраняют все оценки; простаивающие записи вытесняются раньше занятых; забытый эндпоинт начинает заново с `defaultRttMs`. Ключи перемешивания Pick-first хранятся в LRU-кеше не менее чем на 256 записей (и не менее текущих участников), поэтому забытый эндпоинт при возвращении получает новый ключ. Взвешенный round-robin хранит текущие значения для участников клиента: эндпоинт, не попавший в один выбор (выбор с фильтрацией по здоровью), сохраняет своё значение, как nginx пропускает недоступный узел, а значения отбрасываются только для эндпоинтов, покинувших список участников; скопированная конфигурация весов фиксируется при создании. Длительности используют монотонные часы Performance платформы, если они доступны, и `Date.now()` лишь как запасной вариант.
5. **Аварийный режим fail-open**: если `isHealthy` отклоняет все не исключённые эндпоинты, балансировщик игнорирует `isHealthy` и выбирает среди не исключённых эндпоинтов. Только когда исключены все настроенные эндпоинты, он переходит в режим fail-open на полный список кандидатов клиента вместо локального сброса всего трафика.

## 4. Жизненный цикл учёта транспорта (`pick` → `start` → `end` → `done`)

Пользовательские балансировщики должны выбирать одну из точных строк в `info.endpoints`; это сохраняет фильтрацию доступности.

Пользовательские балансировщики реализуют синхронный `pick(info)` и опциональные колбэки `start()`, `end(info)` и `done(info)`. Среда выполнения вызывает эти колбэки без получателя, поэтому `this` равен `undefined`; держите состояние в замыканиях, стрелочных функциях или привязанных функциях. Синхронный бросок исключения не меняет попытку; он сообщается через `reportError` там, где среда выполнения его определяет, и необработанный отчёт может завершить процесс Bun или Deno, у которого нет обработчика ошибок. Node.js не определяет `reportError`, поэтому там бросок остаётся перехваченным и наружу не выходит. `PickInfo` содержит кандидатов `endpoints` для одного выбора (список сокращается, когда обёртка фильтрует), `members` (полный список эндпоинтов клиента, одинаковый для всех попыток; балансировщики с состоянием привязывают к нему порядок и состояние) и необязательное поле `meta` из определения; дискриминатора транспорта нет. Транспорт переводит свои факты в нейтральные исходы `DoneInfo.code`. Встроенные балансировщики никогда не читают `status`; эта сырая информация об ответе сохраняется только для пользовательских балансировщиков. `start` выполняется до попытки, `end` — когда начинается ответ узла или случается сбой до ответа, а `done` — при завершении. Поэтому более поздний сбой тела может сменить итоговый код, не меняя более ранний замер `end`:

| Физический исход транспорта                                                             | Финальный замер `done(info)`                               |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Статус ответа HTTP/SSE 502, 503 или 504                                                 | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| Другой статус ответа HTTP/SSE не ниже 500                                               | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| Статус ответа HTTP/SSE 2xx, 3xx или 4xx (включая 429)                                   | `{ attempted: true, status }`                              |
| Тело HTTP-ответа оборвалось на середине                                                 | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| Хэндшейк SSE прошёл, затем `reader.read()` упал с ошибкой                               | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Обычный EOF у SSE, хэндшейк 2xx, который не является потоком событий, или предел буфера | `{ attempted: true, status }`                              |
| Открытый WebSocket закрылся с кодом `1006` или `1015` (кадр закрытия не пришёл)         | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Открытый WebSocket закрылся с кодом `1012` или `1013`                                   | `{ attempted: true, code: "NET_UNAVAILABLE" }`             |
| Таймаут подтверждения heartbeat у WebSocket                                             | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Открытый WebSocket закрылся с любым другим кодом, что бы ни сообщал `wasClean`          | `{ attempted: true }`                                      |
| Отмена пользователем или ручное закрытие потока/сокета                                  | `{ attempted: false }`                                     |
| `fetch` отклоняет потоковое тело HTTP-запроса сетевой ошибкой                           | `{ attempted: false }`                                     |
| Дедлайн вызывающего истёк после старта попытки                                          | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

Потоковое тело HTTP-запроса — это `ReadableStream`, который передаёт вызывающий код. `fetch` отклоняет его той же сетевой ошибкой, будь то отказ в соединении или HTTP/1.1, редирект, который не может повторить поток, неудачный CORS preflight или исходный поток, который бросает исключение, поэтому эта ошибка ненадёжно показывает, что эндпоинт недоступен. Вызов всё равно завершается с `NET_UNREACHABLE`, но балансировщик получает `{ attempted: false }`, как и для бросающего колбэка прогресса (`EXT_OBSERVER_FAILED`). Цена в том, что одни лишь потоковые загрузки не могут обнаружить упавший эндпоинт: они не уводят `pickFirst` от него и не идут в счёт `outlierDetection`, а отклонённая потоковая загрузка никогда не повторяется: тело `ReadableStream` завершает поток повторов до того, как будет спрошен `shouldRetry`. Ошибки декодирования хэндшейка сохраняют нейтральный исход, выведенный из статуса хэндшейка (например, `NET_UNAVAILABLE` со статусом `503`). Неполное тело HTTP вместо этого сохраняет `NET_BODY_INCOMPLETE` и сырой статус, даже у ответа шлюза; как и любой исход с кодом, он считается сбоем для обнаружения выбросов (`outlierDetection`) по умолчанию. Heartbeat, который не удалось отправить (бросающий `message()` или ошибка сериализации), локален и нейтрален.
