# Балансировка нагрузки и отказоустойчивость

Когда приложение настраивает несколько базовых URL с помощью `withEndpoint(...urls)`, Defjs может распределять запросы между репликами, временно исключать сбойные узлы через пассивный circuit breaker или активные проверки доступности (health checks), а также опционально переключать безопасные HTTP-запросы на резервный узел в рамках одного вызова.

## 1. Выбор стратегии балансировки нагрузки

| Стратегия                                                                           | Лучше всего подходит для                                                    | Фильтрация по доступности по умолчанию                |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------- |
| [`pickFirstBalancer(options?)`](/ru-RU/api/core/pickfirstbalancer) _(По умолчанию)_ | Браузерных приложений с упорядоченным списком «основной + резервный регион» | Отключена (включается через опцию `outlierDetection`) |
| [`roundRobinBalancer(options?)`](/ru-RU/api/core/roundrobinbalancer)                | Вызовов между серверами по равноправным репликам (поддерживает `weights`)   | Включена (`5` последовательных ошибок)                |
| [`p2cBalancer(options?)`](/ru-RU/api/core/p2cbalancer)                              | Серверных вызовов с разбросом задержек реплик или нагрузки в процессе       | Включена (`5` последовательных ошибок)                |

### Как работают `pickFirstBalancer` и `p2cBalancer`

- **`pickFirstBalancer`**: остаётся на первом URL и сдвигается на `NET_UNREACHABLE` или `NET_UNAVAILABLE` (HTTP 502, 503 или 504). Опция `failbackMs: 30_000` позволяет периодически проверять основной эндпоинт после пребывания на резервном узле указанное время.
- **`p2cBalancer` (Power of Two Choices)**: случайным образом выбирает двух независимых кандидатов без повторений и берёт узел с наименьшим весом: `PeakEwma RTT × (pending + 1)` (или только количество активных запросов `pending`, если указано `load: "pending"`). Значения по умолчанию (`defaultRttMs: 30`, `decayMs: 10000`) соответствуют соглашениям Linkerd и библиотеки tower.

## 2. Повтор HTTP в рамках одного вызова

Повтором управляют три отдельных решения: **повторять ли** (`withRetry`), **куда отправить** (рантайм просит балансировщик выбрать снова, исключая уже опробованные эндпоинты) и **сколько ждать** (backoff). `withRetry` у HTTP, `withSSEReconnect` у SSE и `withWebSocketReconnect` у WebSocket — симметричные политики уровня транспорта. Их плоские поля backoff носят те же имена, проходят ту же проверку и считают задержку одинаково. Балансировщик ничего не знает о политике повтора; пользовательскому балансировщику не нужно особое сотрудничество.

Повтор HTTP в рамках одного вызова **выключен по умолчанию**. Если опустить `withRetry`, на вызов приходится одна попытка, бюджет повторов не создаётся и кредиты на него не начисляются. Выбор на последующих вызовах не меняется: `pickFirstBalancer` по-прежнему может сдвинуться после неудачного вызова. `withRetry()` эквивалентен `withRetry({})` и включает две попытки всего при сбое соединения для `GET`, `HEAD`, `OPTIONS` и `TRACE`.

Это следует экосистеме Go: [gRPC помещает `retryPolicy` в service configuration](https://grpc.io/docs/guides/retry/), рядом с конфигурацией балансировки, а [go-kit `lb.Retry(max, timeout, balancer)`](https://pkg.go.dev/github.com/go-kit/kit/sd/lb#Retry) явно оборачивает балансировщик. Ни то ни другое не применяет политику повторов приложения по умолчанию. Политика повторов gRPC требует настроек backoff и использует джиттер ±0.2; [у Envoy по умолчанию база 25 мс и максимум в десять раз больше этой базы](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto#config-route-v3-retry-policy-retrybackoff). Defjs использует 25 мс, фактор 2, потолок 250 мс и джиттер ±20 %. gRPC может делать прозрачные повторы для гонок низкого уровня; Defjs их не воспроизводит.

- **Всего попыток (`maxAttempts`)**: включает исходную попытку, как `retryPolicy.maxAttempts` в gRPC и `max` у `lb.Retry` в go-kit. Значение должно быть безопасным целым числом не меньше 1; `1` означает, что повтора нет. Настроенного верхнего предела нет, но каждый эндпоинт пробуется не больше одного раза. Потоковые тела запроса никогда не повторяются. `methods` без учёта регистра; `methods: []` отключает повторы для всех методов.
- **Условия повтора (`on`)**: по умолчанию `["connect-failure"]`. Добавьте `"gateway-error"` для `NET_UNAVAILABLE` (HTTP `502`/`503`/`504`), включая тела ошибок шлюза, отклонённые декодированием `RES_*`, и `"attempt-timeout"`, если задан `attemptTimeoutMs`. Подходящий повтор заново собирает запрос и прогоняет всю цепочку перехватчиков с самого внешнего слоя.
- **Backoff (`delayMs`, `factor`, `jitter`, `maxDelayMs`)**: перед повтором n ожидание равно `delayMs × factor^(n−1)` с мультипликативным джиттером, с потолком после джиттера и округления. Значения по умолчанию — `25`, `2`, `0.2` и `250`. `delayMs: 0` пропускает ожидание. Как и у переподключения, `delayMs` должен быть конечным и неотрицательным, `factor` — конечным и положительным, `jitter` — конечным в `[0, 1]`, а `maxDelayMs` — неотрицательным конечным или положительным `Infinity`. Потолок таймера платформы по-прежнему действует.
- **Таймаут на попытку против общего таймаута вызова**: `attemptTimeoutMs` ограничивает одну попытку от вызова Fetch до декодирования тела. Сигнал вызывающего `client({ signal: AbortSignal.timeout(ms) })` покрывает каждую попытку **и ожидание backoff**. Отмена во время ожидания возвращает fault отмены вызывающего и нового выбора не делает.
- **Бюджет повторов Finagle / Linkerd (`budget`)**: у каждой конфигурации клиента свой бюджет, и его делят только производные клиенты с той же конфигурацией, а не клиенты с общим балансировщиком. Значения по умолчанию — `percentCanRetry: 0.2`, `minRetriesPerSecond: 10` и `ttlMs: 10000`: 20 % исходного трафика плюс резерв. И кредиты, и списания лениво истекают в десяти долях TTL/10. Повтор списывает до ожидания; исчерпанный бюджет ни ждёт, ни повторяет. Передайте `budget: false`, чтобы снять потолок.
- **Подсказка браузерного офлайна**: если `navigator.onLine === false`, сбои соединения помечаются как `{ attempted: false }`, не сдвигают балансировщики и не запускают повторы.

Поздний `withRetry` заменяет политику. `withRetry()` и `withRetry(undefined)` ведут себя как `withRetry({})`. Чтобы выключить повторы после их включения, передайте `withRetry({ maxAttempts: 1 })`. Недопустимые настройки повтора возвращают `REQ_OPTIONS_INVALID` с `Invalid retry options`, когда выполняется HTTP-операция.

1. **Последовательные ошибки**: классификатор по умолчанию считает `NET_UNREACHABLE`, `NET_UNAVAILABLE` и `NET_SERVER_ERROR`. После `consecutiveFailures` (по умолчанию `5`) подряд учтённых исходов эндпоинт исключается на период `min(minPenaltyMs × 2^level, maxPenaltyMs)` (от `1000ms` до `60000ms`) плюс до `50%` равномерного положительного джиттера.
2. **Восстановление через одну пробу**: по истечении штрафа ровно один запрос направляется на проверку хоста. Если ответ узла начинается (`end`) без учтённой ошибки, хост немедленно возвращается в строй, а уровень штрафа сбрасывается в `0`; при сбое штраф удваивается.
3. **Аварийный режим fail-open**: если все настроенные эндпоинты исключены или признаны нездоровыми, балансировщик переходит в режим fail-open, пропуская запросы ко всему списку кандидатов, вместо локального сброса всего трафика.

## 4. Жизненный цикл учёта транспорта (`pick` → `start` → `end` → `done`)

Пользовательские балансировщики реализуют синхронный `pick(info)` и опциональные колбэки `start()`, `end(info)` и `done(info)`. `PickInfo` содержит только кандидатов `endpoints` и необязательный `operation` определения; дискриминатора транспорта нет. Транспорт переводит свои факты в нейтральные исходы `DoneInfo.code`. Встроенные балансировщики никогда не читают `status`; эта сырая информация об ответе сохраняется только для пользовательских балансировщиков. `start` выполняется до попытки, `end` — когда начинается ответ узла или случается сбой до ответа, а `done` — при завершении. Поэтому более поздний сбой тела может сменить итоговый код, не меняя более ранний замер `end`:

| Физический исход транспорта                                                                | Финальный замер `done(info)`                               |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| Статус ответа HTTP/SSE 502, 503 или 504                                                    | `{ attempted: true, code: "NET_UNAVAILABLE", status }`     |
| Другой статус ответа HTTP/SSE не ниже 500                                                  | `{ attempted: true, code: "NET_SERVER_ERROR", status }`    |
| Статус ответа HTTP/SSE 2xx, 3xx или 4xx (включая 429)                                      | `{ attempted: true, status }`                              |
| Тело HTTP-ответа оборвалось на середине                                                    | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }` |
| Хэндшейк SSE прошёл, затем `reader.read()` упал с ошибкой                                  | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Обычный EOF у SSE, ошибка декодирования после успешного хэндшейка или переполнение очереди | `{ attempted: true, status }`                              |
| Открытый WebSocket закрылся с кодом `1006` или `wasClean === false`                        | `{ attempted: true, code: "NET_UNREACHABLE" }`             |
| Открытый WebSocket закрылся штатно                                                         | `{ attempted: true }`                                      |
| Отмена пользователем или ручное закрытие потока/сокета                                     | `{ attempted: false }`                                     |
| Дедлайн вызывающего истёк после старта попытки                                             | `{ attempted: true, code: "NET_TIMEOUT" }`                 |

Ошибки декодирования хэндшейка сохраняют нейтральный исход, выведенный из статуса хэндшейка (например, `NET_UNAVAILABLE` со статусом `503`). Неполное тело HTTP вместо этого сохраняет `NET_BODY_INCOMPLETE` и сырой статус, даже у ответа шлюза; outlier detection по умолчанию его не считает.
