# HTTP

Через `defineRequest` SDK экспортирует HTTP-операцию: метод, относительный путь, входные данные, `builder` и необязательные контракты `output` / `error`. Приложение импортирует эндпоинт и выполняет его команду своим клиентом. Оно настраивает базовый URL, аутентификацию и транспорт, обрабатывает кортеж результата и управляет отменой или таймаутом.

В следующих примерах обе стороны показаны вместе. Разделение пакета и приложения описано в рецепте [публикации SDK](/ru-RU/recipes/publish-http-sdk).

## Собери URL

`withEndpoint(...)` нужен корректный абсолютный URL. Pathname эндпоинта остаётся каталогом; query и hash отбрасываются до разрешения URL команды. Отсутствующий, относительный или некорректный базовый эндпоинт даёт `REQ_BUILD_FAILED` при сборке запроса, до запуска интерцепторов или транспорта, даже если интерцептор вернул бы результат без отправки запроса. Для HTTP, SSE и WebSocket действует одно правило.

<include cwd>examples/http/resolve-url.ts#example</include>

Placeholder’ы path — сырые скаляры, кодируются ровно один раз. Пустые значения и `.` / `..` отвергаются. Слэши, `?`, `#`, `%`, пробелы и Unicode в одном placeholder остаются одним закодированным сегментом — не прекодируй.

Имя параметра пути начинается с `:` и продолжается до следующего `/` или конца пути: `/files/:name.json` задаёт параметр `name.json`, а не `name`. Литеральное двоеточие в статическом сегменте не поддерживается.

Пути определения не могут быть похожими на схему или относительными к протоколу (в том числе с ведущими пробелами) и не могут содержать управляющие символы C0 (включая табуляцию, CR и LF), обратные слеши, `?` или `#`. Обычный пробел внутри пути разрешён и отправляется как `%20`. После разрешения URL должен сохранять origin базы и оставаться в её каталоге; путь вроде `../users` не может выйти за его пределы. Недопустимые пути дают `REQ_BUILD_FAILED` при сборке, до обращения к транспорту. Итоговый `req.endpoint` интерцептора проверяется относительно итогового `req.baseEndpoint` по тем же правилам; интерцептор может явно заменить базу другим корректным абсолютным URL. Детерминированные ошибки URL никогда не приводят к повторной попытке.

Encoder query по умолчанию принимает скаляры и массивы скаляров (массивы повторяют ключ). Вложенный объект падает с `REQ_BUILD_FAILED`, если у клиента нет `withQuerySerializer(...)`. `null` в `path`, `query` или `headers` падает так же. Значения `undefined` в query и headers опускаются. `undefined` или отсутствующий placeholder в path падает с `REQ_BUILD_FAILED` и не опускается.

## Разложи input

Struct кодирует значение. Builder его раскладывает. При объявленном `input` всегда нужен явный `builder`. `input` только описывает параметры; куда пойдёт каждое значение, решает только builder. Опустить `builder` можно только в определениях без `input`.

<include cwd lang="typescript">
  examples/http/place-input.ts#example
</include>

Это тело — `{"display_name":"Ada"}` с `application/json`. Wire-имя заголовка — `x-request-id`. Вызывающие и распарсенные результаты держат `displayName`.

Лучше провести типизированное значение, чем выписывать wire-ключи. Алиас объявляется один раз на поле и работает в обе стороны: `output` / `error` / события / входящие кадры декодируют `display_name` в `displayName`, а `body: input.order` переписывает всё дерево. Один и тот же struct `User` может быть телом create и output get. Ключ, написанный руками, — исключение: родительский объект анонимный, поэтому алиас не бежит.

| Выражение builder                              | На проводе                                                      |
| ---------------------------------------------- | --------------------------------------------------------------- |
| `body: input.profile`                          | Типизированный объект: алиас и кодирование `Date` / `bigint`    |
| `body: { profile: input.profile }`             | Внешние ключи литеральны, внутренний объект всё ещё типизирован |
| `body: { ...input.profile, role: 'admin' }`    | Spread сохраняет struct; лишний ключ литерален                  |
| `body: { name: input.profile.displayName }`    | Анонимный родитель: алиас не применяется                        |
| `query: input.filter` / `headers: input.trace` | Типизированные плоские объекты: алиас становится wire-ключом    |

Spread типизированного объекта и одновременная установка его wire-ключа (`display_name` рядом с `displayName`) — это `REQ_BUILD_FAILED`. Вложенный объект в `path` или `headers` падает так же.

Схема кодирования выбирается на каждом узле, а не только в корне. Новый объект под анонимным родителем сохраняет ключи, которые ты написал. Тот же объект под типизированным родителем использует struct этого поля.

```ts
body: { row: { id: '42' } }              // Anonymous root: emits id
body: { ...input, row: { id: '42' } }    // Typed root, row field declares alias: emits wire_id
```

Если схема кодирования union соответствует нескольким веткам, каждая ветка кодируется и сравнивается. Одинаковый wire-результат сохраняется; различие — это `REQ_BUILD_FAILED`.

Смешанное intersection, содержащее не-object часть, при разборе получает в качестве тега конъюнкцию тегов совпавших частей; заново написанное значение смешанного intersection, которое не разбиралось, обрабатывается как анонимный объект.

### Query

Вложенная форма query (`a[b]`, `a.b`, списки через запятую) — соглашение бэкенда, поэтому хук живёт на клиенте:

<include cwd>examples/http/query-serializer.ts#example</include>

Здесь `query` — уже закодированный wire-объект. Алиасы уже применены, так что serializer вроде `qs` их не теряет. Возвращённая строка сохраняется как `queryString`, затем присваивается в `URL.search`, который percent-encode’ит пробелы, `#`, кавычки и не-ASCII. Defjs от `qs` не зависит.

Без serializer массивы повторяют ключи, а вложенный объект — это `REQ_BUILD_FAILED`. `URLSearchParams`, возвращённый из builder, берётся как есть и serializer пропускает. Serializer не зовут, когда query нет. Дальше interceptors видят `queryParams` как `new URLSearchParams(queryString)`.

### Body

Побеждает первое совпадение:

| Значение `body`                                                           | Уходит как                                                                  | Content type по умолчанию                                  |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------- |
| опущено / `undefined`                                                     | тела нет                                                                    | —                                                          |
| типизированный объект, у корня которого кодек `urlencoded` или `formData` | `URLSearchParams` / `FormData`; ключи — wire-имена; массивы повторяют ключи | тип формы / multipart-разделитель платформы                |
| `FormData`, `URLSearchParams`                                             | как есть                                                                    | то же; Defjs снимает протухший `Content-Type` у `FormData` |
| `Blob` / `File`                                                           | как есть                                                                    | `blob.type` или `application/octet-stream`                 |
| `ArrayBuffer`, `TypedArray`, `DataView`                                   | как есть                                                                    | `application/octet-stream`                                 |
| `ReadableStream`                                                          | стримом (`duplex: 'half'`, если рантайм позволяет)                          | `application/octet-stream`                                 |
| `string`                                                                  | как есть                                                                    | `text/plain;charset=UTF-8`                                 |
| простой объект, массив, число, булево значение, `null`, `Date`, `bigint`  | кодируется, потом `JSON.stringify`                                          | `application/json`                                         |

HTTP хранит выведенный тип тела билдера в обычном поле `request.bodyContentType`, которое сохраняется при копировании `{ ...req }`; этот вывод никогда не записывается в `request.headers`. Явный заголовок `content-type` всегда важнее, задан ли он билдером, значениями клиента по умолчанию, интерцептором или сырым запросом `fetchHandler`, в том числе когда отслеживание прогресса отправки преобразует тело в поток. `bodyContentType` действует, только пока `body` остаётся значением билдера; тип заменённого тела определяется заново, поэтому интерцептор объявляет его заголовком `content-type`. При `body: undefined` библиотека не отправляет выведенный Content-Type. Исключение — FormData: его content type должен использовать multipart-разделитель из фактической сериализации. Тег кодека применяется только в корне тела: `body: { meta: input.form }` — это JSON, а поля формы — обычные JSON-поля. Строка — сырой текст; JSON-строка вроде `"abc"` нуждается в `JSON.stringify` плюс `application/json`. Поля `undefined` опускаются; `nullable` поле, отправленное как `null`, — это JSON `null`.

На любом уровне вложенности JSON должен содержать только JSON-данные: простые объекты, массивы, строки, конечные числа, булевы значения и `null`, а также значения, чей `toJSON()` возвращает данные этих типов, например `Date` или `URL`. Любое другое значение, в корне или во вложенных данных, приводит к ошибке `REQ_BUILD_FAILED` до отправки каких-либо данных, вместо того чтобы отправляться как `{}`, `null` или вообще без тела: `Map` или `Set`, экземпляр класса без `toJSON`, функция, `NaN`, `Readable` из Node или итерируемый или асинхронный итерируемый объект, включая литерал объекта с методом `Symbol.iterator` или `Symbol.asyncIterator`. В сообщении указано имя поля. Итерируемый объект, заданный как `query` или `headers`, приводит к той же ошибке, а не отбрасывается; пары заголовков передавай массивом. Для отправки потока используй `ReadableStream` из веб-API: `ReadableStream.from(iterable)` или `Readable.toWeb(readable)`. Тип `body` отклоняет большинство таких значений на этапе компиляции; для значения с типом, объявленным через `interface`, или экземпляра класса нужно использовать `{ ...value }`.

`GET` и `HEAD` не могут вернуть тело — это ошибка типа. WebSocket builder не может вернуть `headers` или `body`.

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

`JSON.stringify`, `qs` или protobuf, которые гоняешь сам, видят логические имена. На этом пути алиас не применяется. Публичного `struct.encode` нет.

Builder может ветвиться по настоящему input и возвращать разное тело на случай (JSON-записи, `File` или `URLSearchParams`). Нативные `Headers` тоже проходят насквозь и заново не кодируются.

## Как читается тело

`output` — один Struct для тела 2xx; `error` — один Struct для всего остального. Kind struct выбирает representation: `string` — сырой текст, `blob` / `file` — blob, `arrayBuffer` — байты, любой другой kind — JSON. Если не объявлена ни одна сторона, тело не читают.

Порядок:

1. `ok` выбирает сторону: `output` для 2xx, `error` для всего остального. Никогда обе.
2. Для этой стороны ничего не объявлено → тело не читают. 2xx успешен с `data === undefined`; non-2xx — это `HTTP_STATUS` с `data === undefined`. Нечитаемое тело на стороне, которую ты не объявил, игнорируется, включая сам факт, что его не прочитали.
3. Для JSON-представления media type проверяется **до** чтения тела. Несовпадение — `RES_MEDIA_TYPE_INVALID`, ничего не парсится и не декодируется. Текст, blob, file и bytes эту проверку пропускают.
4. Читается representation. Провал — `RES_DECODE_FAILED`. JSON от транспорта парсится один раз: строка в
   этом значении — JSON-строка как корень и повторно не парсится; байты и blob'ы сырые и парсятся один раз.
5. Struct парсит значение. Провал — `RES_STRUCT_MISMATCH`.
6. 2xx → результат и типизированный `response.body`; non-2xx → типизированный `data` на `HTTP_STATUS`.

Встроенный транспорт Fetch выполняет проверку media type для JSON и чтение representation внутри цепочки interceptor, поэтому interceptors получают ответ, у которого `body` уже разобран: JSON, текст, `Blob` или байты. Сбой там reject’ит `next()` как `BodyFailure` (`RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED` или `NET_BODY_INCOMPLETE`, когда поток обрывается). Валидация Struct выполняется один раз, после цепочки. `makeResponse(...)` пропускает это чтение внутри цепочки и декодируется только после неё.

Успешный ответ — это `DecodedResponse<T>`: `url`, `status`, `statusText`, `headers`, `ok` и типизированный `body`. Где ничего не декодировали, получаешь `HttpMeta` — те же поля без `body`. `ok` значит только `200 <= status < 300`. Ни то ни другое не нативный `Response`. Провал транспорта — это fault, так что status-0 ответа, стоящего вместо него, нет.

## Отмени работу

Опции выполнения принимают `{ signal }` отдельно, без `abort` или `timeout`. **`abort` и `timeout` взаимоисключающие.** `signal` сочетается с любым из них.

<include cwd>examples/http/cancel.ts#example</include>

`timeout` — положительное safe integer в `1..2_147_483_647`. Вызов без `timeout` получает значение по умолчанию из `withTimeout` клиента. Узнанная отмена → `NET_ABORTED`; timeout выполнения → `NET_TIMEOUT`; `throw` interceptor → `EXT_INTERCEPTOR_FAILED`, кроме `ERR_ABORTED` / `ERR_TIMEOUT`, которые дают `NET_ABORTED` / `NET_TIMEOUT`; прочие сбои Fetch → `NET_UNREACHABLE`. Отмена после того, как сервер принял запись, **не** доказывает, что запись откатилась.

## Credentials и XSRF

`withCredentials(true)` ставит Fetch `credentials: 'include'` для HTTP и SSE. Он не создаёт `Authorization` и не настраивает auth WebSocket. `false` оставляет credentials незаданными.

`withXSRF(...)` — только HTTP. По умолчанию: `cookieName: 'XSRF-TOKEN'`, `headerName: 'X-XSRF-TOKEN'`. Заголовок добавляется только для небезопасных методов и только если вызывающий его ещё не задал. При наличии `location`, в том числе в Worker, разрешённый URL запроса должен соответствовать `location.origin`; для запроса к другому origin `tokenProvider` не вызывается. Для поиска cookie отдельно требуется `document`. Пропускаются `GET`, `HEAD`, `OPTIONS`, `TRACE`. В Worker или на сервере передай синхронный `tokenProvider` в области текущего запроса, если нужна подстановка токена.

Держи credentials, XSRF-токены и query-строки подальше от обычных логов. Не используй query params как общий канал для credentials.

## Progress и граница Fetch

`onDownloadProgress` вызывается, пока читается объявленное тело ответа. `loaded` считает байты, прочитанные из потока ответа, который Fetch уже мог распаковать. `lengthComputable` равен true только при положительном `Content-Length` и отсутствующем `Content-Encoding` либо значении `identity`. При других кодировках, включая gzip и br, сообщаются `total: 0` и `lengthComputable: false`, поэтому распакованные байты никогда не сравниваются с длиной сжатых данных на проводе. Нет struct для этой стороны → тело не читают → нет progress чтения тела.

`onUploadProgress` сообщает о прогрессе передачи тела `ReadableStream<Uint8Array>` по мере того, как Fetch его читает, а не когда сервер подтверждает получение. Прогресс выгрузки сообщается только в средах выполнения, поддерживающих потоковую отправку тела запроса: в Bun и Node Defjs также преобразует в поток тела типа `Blob` / `File`, `ArrayBuffer` и `FormData`, поэтому для них тоже сообщается прогресс. В серверных средах FormData с `onUploadProgress` использует сериализованный поток напрямую, сохраняет multipart-разделитель и отправляется без сгенерированного библиотекой `Content-Length` (chunked по HTTP/1.1), поэтому прогресс, тайм-аут и отмена работают без буферизации всего тела. Его общая длина неизвестна, если её не задаёт корректный явный `Content-Length`. Для эндпоинта, которому нужен `Content-Length`, например некоторых целей предварительной подписи, опусти `onUploadProgress`; тогда платформенный Fetch отправит FormData с её длиной. Отмена освобождает обёрнутый поток. Браузеры, включая Workers, исключены, потому что Chromium поддерживает потоковую отправку тела запроса только по HTTP/2 или более поздним версиям, а Firefox не поддерживает её вовсе; в браузерах эти тела отправляются без изменений, и `onUploadProgress` не вызывается. JSON, текст, `URLSearchParams` и типизированные массивы отправляются целиком и не вызывают событий прогресса. Для потока неизвестной длины `total` равен `0` (поэтому `lengthComputable` имеет значение `false`). Запрос с телом `ReadableStream` в среде выполнения без поддержки потоковой отправки запросов, например в Firefox, завершается с ошибкой `ENV_UNSUPPORTED` до отправки каких-либо данных; сообщение исходной ошибки — `ERR_STREAMING_REQUEST_UNSUPPORTED`. В Chromium тело `ReadableStream` требует HTTP/2 или более поздней версии; по HTTP/1.1 вызов завершается с ошибкой `NET_UNREACHABLE`. `onDownloadProgress` работает одинаково во всех средах выполнения.

Если колбэк прогресса выбрасывает исключение или возвращает отклонённый промис, вызов завершается с ошибкой `EXT_OBSERVER_FAILED`, а выброшенное значение передаётся в `cause`. Это относится как к загрузке, так и к выгрузке. Отмена со стороны вызывающего кода и `timeout` по-прежнему возвращают `NET_ABORTED` / `NET_TIMEOUT`.

`fetchHandler(httpRequest, fetchImpl?)` — низкоуровневая граница Fetch: разрешает URL, вызывает Fetch, читает представление и возвращает `HttpResponse`. Стандартные handles HTTP и SSE определяют `globalThis.fetch` при каждом вызове, поэтому замена, установленная после импорта, используется. HTTP вызывает `(url, init)` только для неизменённого Fetch платформы; заменённый глобальный Fetch или пользовательский handle получает нативный `Request`. Импорт Core без Fetch допустим; если Fetch всё ещё отсутствует, выполнение HTTP/SSE через стандартный handle завершается с `ENV_UNSUPPORTED`, а пользовательские handles остаются пригодны. Эта граница **не** проверяет input команды, не выполняет диспатч `output` и не запускает интерцепторы. Она полезна для тестов с подставленным транспортом, но не заменяет `client.execute`.

## Пределы replay

Defjs **не** auto-retry HTTP. Ретрай чтения всё равно нуждается в проверенной политике timeout/сети/дубликатов. Ретрай мутации нуждается в воспроизводимых байтах, поддержке сервера, ключе идемпотентности, привязанном к auth scope + байтам запроса, и политике дубликатов на приёмнике.

Граница client/command/Fetch не может знать, закоммитилась ли упавшая запись. Решения о replay держи в приложении или в проверенном interceptor. Interceptors могут short-circuit или заменить низкоуровневый запрос; итоговые status и тело всё равно должны удовлетворять контракту команды.
