# HTTP-операции

SDK определяет каждую HTTP-операцию с помощью `defineRequest`: её HTTP-метод, шаблон пути, схему входных данных `input`, синхронную функцию `builder` и схемы ответов `output` / `error`. Использующие приложения импортируют операцию, передают настроенный `Client` и обрабатывают возвращаемый кортеж `[error, data, response]`.

## 1. Объявление операции и её вызов

### Лучшие практики проектирования SDK

- **Одна операция на каждое определение**: держите каждый метод, путь и контракт в отдельном определении, чтобы приложения могли применять tree-shaking к неиспользуемым операциям.
- **Указывайте статическое имя `operation`**: используйте идентификаторы с низкой кардинальностью, например `"orders.read"`. Плагины телеметрии (`@defjs/opentelemetry-server`) и логирующие перехватчики используют это имя без риска утечки URL или ID пользователей.
- **Никогда не встраивайте клиент в SDK**: экспортируйте только определения, схемы `struct` и типы.

## 2. Разрешение URL и параметры пути

Для `withEndpoint(...)` требуется валидный абсолютный URL. Его путь (pathname) служит базовым каталогом (любые query-параметры или хеш из базового эндпоинта отбрасываются).

<include cwd>examples/http/resolve-url.ts#example</include>

- **Плейсхолдеры пути (`:name`)**: кодируются ровно один раз как одиночный сегмент пути. Слэши, `?`, `#`, `%`, пробелы и символы Unicode остаются внутри этого сегмента — не кодируйте значения заранее. Пустые строки, `.` и `..` приводят к ошибке `REQ_BUILD_FAILED`.
- **Ограничение origin и каталога**: пути в определении не могут быть абсолютными URL, начинаться с `//`, содержать управляющие символы C0, обратные слэши, `?`, `#` или выходить за пределы базового каталога через `../`. Любое нарушение завершается ошибкой `REQ_BUILD_FAILED` ещё до запуска перехватчиков и транспорта.

## 3. Размещение входных данных с помощью `builder`

Если операция объявляет `input`, она **обязана** предоставить синхронную и чистую функцию `builder`, возвращающую `{ path?, query?, headers?, body? }`. Опускать `builder` разрешено только в операциях без `input`.

### Как `builder` кодирует алиасы полей

| Выражение в `builder`                          | Результат при сетевой передаче                                           |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| `body: input.profile`                          | Типизированный struct: применяются `.alias()` и кодеки `Date` / `bigint` |
| `body: { profile: input.profile }`             | Внешний ключ `profile` литерален; внутренний объект сохраняет алиасы     |
| `body: { ...input.profile, role: "admin" }`    | Spread сохраняет алиасы структуры; ключ `role` литерален                 |
| `body: { name: input.profile.customerName }`   | Анонимный объект: ключи передаются буквально                             |
| `query: input.filter` / `headers: input.trace` | Плоские объекты struct: поле `.alias()` становится сетевым ключом        |

### Пользовательская сериализация query-параметров

По умолчанию скаляры query и массивы скаляров (повторяющиеся ключи) сериализуются напрямую, а вложенные объекты query приводят к ошибке `REQ_BUILD_FAILED`. Если ваш бэкенд ожидает синтаксис вложенных параметров (`filter[status]=paid`), настройте `withQuerySerializer` на клиенте:

### Форматы тела запроса

Запросы с методами `GET` и `HEAD` не могут содержать тело. Для остальных методов формат тела определяется значением, которое вернул `builder`:

| Значение `body`                                                           | Способ сетевой отправки                        | `Content-Type` по умолчанию                |
| ------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------ |
| `undefined` / не указано                                                  | Без тела                                       | —                                          |
| Корневой struct с кодеком `urlencoded` или `formData`                     | `URLSearchParams` / `FormData` (алиасы учтены) | Форма / multipart boundary                 |
| Нативный `FormData` или `URLSearchParams`                                 | Передаётся напрямую как есть                   | Multipart boundary / urlencoded            |
| `Blob` / `File`                                                           | Передаётся напрямую как есть                   | `blob.type` или `application/octet-stream` |
| `ArrayBuffer`, typed array, `DataView`, `ReadableStream`                  | Сырые байты / поток                            | `application/octet-stream`                 |
| `string`                                                                  | Текст UTF-8                                    | `text/plain;charset=UTF-8`                 |
| Обычный объект, массив, конечное число, boolean, `null`, `Date`, `bigint` | JSON, закодированный через struct              | `application/json`                         |

<include cwd lang="typescript">
  examples/http/body.ts#example
</include>

Значения, которые невозможно корректно представить в JSON (`NaN`, `±Infinity`, `Map`, `Set`, функции, экземпляры классов без `toJSON()` или сырые итерируемые объекты), немедленно завершают вызов ошибкой `REQ_BUILD_FAILED` вместо неявного превращения в `{}` или `null`.

## 4. Как декодируются ответы

Схема `output` валидирует ответы `2xx`, а `error` валидирует ответы вне `2xx` (`3xx`, `4xx`, `5xx`). Тип структуры определяет, как читается поток ответа (`struct.string()` → текст, `struct.blob()` / `struct.file()` → `Blob`, `struct.arrayBuffer()` → `ArrayBuffer`, всё остальное → JSON):

1. **Выбор стороны по признаку `ok` (`200..299`)**: `output` для `2xx`, `error` для остальных кодов.
2. **Отказ от чтения при отсутствии схемы**: если для соответствующей стороны схема не объявлена, тело ответа вообще не читается (`2xx` возвращает `data: undefined` + `HttpMeta`; не-`2xx` возвращает `HTTP_STATUS` с `data: undefined`).
3. **Проверка media type для JSON в первую очередь**: для JSON-структур заголовок `Content-Type`, отличный от JSON, сразу приводит к ошибке `RES_MEDIA_TYPE_INVALID` ещё до чтения потока тела.
4. **Чтение и парсинг**: ошибки чтения потока или невалидный JSON приводят к ошибке `RES_DECODE_FAILED` (или `NET_BODY_INCOMPLETE`, если поток оборвался на середине).
5. **Валидация через `struct`**: несоответствие схеме возвращает `RES_STRUCT_MISMATCH`.

## 5. Отмена работы и установка дедлайнов [#cancel-the-work]

Передавайте `signal` через производный клиент для конкретного вызова: `client({ signal })`.

- **Дедлайны (`NET_TIMEOUT`)**: используйте `AbortSignal.timeout(ms)`.
- **Ручная отмена (`NET_ABORTED`)**: используйте `AbortController`.
- **Комбинированные сигналы**: используйте `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`.

## 6. Учётные данные, XSRF и отслеживание прогресса

- **`withCredentials(true)`**: устанавливает `credentials: "include"` в Fetch для HTTP и SSE.
- **`withXSRF(options?)`**: читает cookie XSRF (по умолчанию `XSRF-TOKEN`) и устанавливает заголовок (`X-XSRF-TOKEN`) для мутирующих HTTP-методов одного origin (`POST`, `PUT`, `PATCH`, `DELETE`).
- **`onDownloadProgress` / `onUploadProgress`**: передавайте через `client({ onDownloadProgress, onUploadProgress })`. Прогресс скачивания возвращает `lengthComputable: true`, только если заголовок `Content-Length` положителен, а `Content-Encoding` отсутствует или равен `identity`. Прогресс загрузки потоково передаёт тело на серверных средах (Bun, Node.js). Выброс ошибки в колбэке прогресса завершает вызов сбоем `EXT_OBSERVER_FAILED`.
