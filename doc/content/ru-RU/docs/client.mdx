# Клиент

`Client` — это настройка выполнения приложения-потребителя. `createClient(...)` возвращает [`DerivableClient`](/ru-RU/api/core/derivableclient-type). Вызов фабрики с опциями запроса возвращает значение `Client`, и именно `Client` принимают операции. Оно не вызываемое. Импортируй операции из SDK, выбери адрес сервиса, учётные данные, перехватчики и транспорт, затем вызови операцию с клиентом. `getOrder(client({ signal }), { id: 1 })` начинает вызов, у которого объявлен input. `health(client)` начинает вызов без input. Когда весь входной struct необязателен, допустимы и `search(client)`, и `search(client, input)`. Третьего аргумента с опциями нет. Вызов операции её начинает. `await` только ждёт кортеж error-first.

Определения SDK не привязаны к этому экземпляру. Браузер, серверный запрос и локальный тест могут использовать одну экспортированную операцию с разными клиентами. Все по-прежнему следуют одному контракту Defjs и совместимым версиям Core. Настрой адрес сервиса каждого клиента для операций, которые через него вызываешь.

Одно и то же значение клиента можно передать многим операциям. Кеш и политику повторов выбирает приложение, и оно владеет работой, которую начинает. При ошибках соединения HTTP есть ограниченный failover для безопасных методов, он описан ниже. Переподключение потока включается явно.

Фабрика — функция и одновременно `Client` без опций запроса. Не передавай фабрику в setter состояния React: `setState(factory)` вызовет её как updater. Не используй её как источник Vue `watch` или `computed`: они вызывают функцию. Выведенное значение клиента — обычный объект.

## Несколько эндпоинтов [#multiple-endpoints]

`withEndpoint` принимает один или несколько базовых URL. Аргументы копируются по порядку, а более поздняя копия той же строки отбрасывается. Более поздний `withEndpoint` заменяет список; он его не сливает. Здесь URL не проверяются. Некорректная база завершает вызов с `REQ_BUILD_FAILED`. Пустой список допустим и завершается так же, с [`ERR_NO_ENDPOINT`](/ru-RU/api/core/err-no-endpoint) в `cause`.

<include cwd lang="typescript">

</include>

Без `withEndpointBalancer` каждый клиент получает свой [`pickFirstBalancer`](/ru-RU/api/core/pickfirstbalancer). Он остаётся на первом эндпоинте, пока не случится сбой соединения (`NET_UNREACHABLE`) или ответ со статусом 502, 503 или 504, затем сдвигается и по концу настроенного списка возвращается к началу. Результат с fault-`code` игнорирует свой статус: `NET_BODY_INCOMPLETE` с 503 не сдвигает. Другие ответы, таймауты и отмены его не сдвигают.

HTTP также включает **failover в том же вызове по умолчанию**: сбой соединения на `GET`, `HEAD`, `OPTIONS` или `TRACE` может попробовать ещё один, ещё не испробованный эндпоинт, прежде чем вернуть кортеж последней попытки. Методы сравниваются без учёта регистра. Каждая попытка снова выполняет `pick`, builder, всю цепочку интерцепторов и транспорт; аутентификация, привязанная к эндпоинту, поэтому видит новый `baseEndpoint`. Каждый pick получает свой одноразовый `done`, а поздние pick’и исключают эндпоинты, уже испробованные в этом вызове.

[`withEndpointFailover`](/ru-RU/api/core/withendpointfailover) заменяет эту политику, не сливая её. Пропущенные поля берут свои значения по умолчанию. Поставь `attempts: 0` или `methods: []`, чтобы отключить failover. Тело запроса `ReadableStream` никогда не уходит в failover. Добавляй небезопасный метод в `methods`, только если приложение может безопасно послать его дважды: сбой соединения не доказывает, что сервер не выполнил первый запрос.

`retryOn: ["connect-failure", "gateway-error", "attempt-timeout"]` также разрешает failover в том же вызове после 502/503/504 и после настроенного `attemptTimeoutMs`. Failover шлюза применяется и тогда, когда ответ 502/503/504 не смог декодировать объявленное тело ошибки с fault `RES_*`, например HTML-страница ошибки против JSON-struct. Интерцептор, который восстановился до успеха или упал с `EXT_*`, не запускает failover шлюза. Отброшенный ответ шлюза дренируется или отменяется, прежде чем идти дальше. Без `gateway-error` этот неудачный HTTP-вызов возвращается, а `pickFirstBalancer` сдвигается для следующего вызова. HTTP 500 не вызывает failover в том же вызове и не продвигает `pickFirstBalancer`.

Повторы того же вызова делят **retry budget Finagle/Linkerd** между всеми вызовами и производными значениями одного клиента: `percentCanRetry: 0.2`, `minRetriesPerSecond: 10`, `ttlMs: 10000`. Каждый исходный вызов вносит кредит; каждая дополнительная попытка эндпоинта его снимает. При исчерпании возвращается результат текущей попытки без нового pick. `retryBudget: false` снимает только этот лимит бюджета. Отношение конечно в `[0, 1000]`, минимум — неотрицательное безопасное целое, TTL конечен в `[1000, 60000]` мс. Масштаб токенов Finagle вносит 1000 токенов и списывает `min(2147483647, floor(1000 / ratio))` за retry (нулевое отношение ничего не вносит и списывает один). Резерв — `minimum × floor(ttlMs / 1000) × charge`; как в Finagle, TTL считает целые секунды. И кредиты, и списания лениво истекают в десяти фиксированных долях `ttlMs / 10`, вплоть до одной доли раньше; ни таймер, ни история на запрос не растут без границы. При масштабном сбое бюджет может провалить вызов, который удался бы на другом эндпоинте; именно для этого он и нужен: держать повторы около 20 % трафика. Если бэкенды выдерживают все повторы, увеличьте `percentCanRetry` или задайте `retryBudget: false`.

Defjs по умолчанию оставляет failover соединения безопасных методов включённым; Linkerd/Envoy обычно требуют явных retry, а прозрачный retry gRPC зависит от доказательства, что обработки не было. `gateway-error` в Defjs значит **только 502/503/504 без fault-`code`**; одноимённое условие Envoy включает ещё разрывы и reset без ответа.

Дедлайна по умолчанию и таймаута на попытку нет. `attemptTimeoutMs` — конечное положительное число, измеренное от вызова Fetch до чтения и декодирования тела этой попытки; его истечение сообщает `NET_TIMEOUT`. `signal: AbortSignal.timeout(ms)` вызывающего покрывает **весь вызов**, через все попытки, и не может вызвать failover после истечения. Таймаут попытки разрешает failover, только если `retryOn` содержит `attempt-timeout`; сам он `pickFirstBalancer` не сдвигает.

Когда `navigator.onLine === false`, сбои соединения сообщаются балансировщику как `{ attempted: false }`, и HTTP не делает failover. Только строгое `false` подавляет атрибуцию; отсутствующий navigator или геттер, который бросает, считается online. Это подсказка offline, не проверка здоровья.

Настрой `pickFirstBalancer({ failbackMs: 30_000 })`, чтобы пробовать первый эндпоинт после того, как столько времени прошло в стороне от него. Первый подходящий pick делает пробу; одновременные pick’и продолжают использовать липкий fallback. Ответившая проба, которая не выполняет условие сдвига, восстанавливает первый эндпоинт, неудачная проба перезапускает интервал, а проба без атрибуции оставляет состояние неизменным. Фоновый таймер не работает. С `shuffle: true` «первый» значит перемешанный порядок.

[`roundRobinBalancer`](/ru-RU/api/core/roundrobinbalancer) идёт по списку со случайного начального индекса. Его необязательная карта `weights` использует конечные положительные числа; у неперечисленного кандидата вес 1, а веса отсутствующих кандидатов игнорируются. Веса 2 и 1 повторяются как более тяжёлый, более лёгкий, более тяжёлый. Оставь default для упорядоченных региональных primary/backup браузера; используй round robin для равных peer’ов сервера.

### Фильтрация здоровья и p2c [#health-filtering-and-p2c]

`roundRobinBalancer()` и [`p2cBalancer`](/ru-RU/api/core/p2cbalancer) включают пассивную фильтрацию здоровья по умолчанию. В отличие от липкого pick-first, они распределяют трафик между peer’ами, поэтому остановленная или устойчиво сбоящая реплика не должна и дальше получать свою обычную долю. `pickFirstBalancer()` оставляет фильтрацию здоровья выключенной, пока не передашь объект `outlierDetection`. Приложение по-прежнему владеет обнаружением эндпоинтов.

Поставь `outlierDetection: false`, чтобы отключить фильтрацию. Объект, включая `{}`, включает её со значениями по умолчанию для пропущенных полей. Другие значения завершают вызовы с `REQ_OPTIONS_INVALID`. Round robin без фильтра опускает `done`; round robin по умолчанию возвращает его на каждый успешный pick. [`outlierDetection(child, options)`](/ru-RU/api/core/outlierdetection) оборачивает свою стратегию той же реализацией. Отключи фильтр внутренней фабрики, когда оборачиваешь её явно.

Пассивный критерий — **подряд идущие ошибки**, по умолчанию пять (как в Finagle). Не-ошибка сбрасывает серию; `attempted: false` её не увеличивает и не сбрасывает. Поставь `consecutiveFailures: 0`, чтобы отключить пассивный разрыв. Фильтрация здоровья по умолчанию включена, как в Finagle; настройки Linkerd, Envoy и gRPC отличаются.

По умолчанию `NET_UNREACHABLE` и статусы 500 и выше считаются ошибками. Fault-коды `NET_TIMEOUT` и `NET_BODY_INCOMPLETE` важнее статуса и ошибками не являются. `isFailure` фильтрации здоровья может настроить эту классификацию. Брошенный или не-boolean результат отбрасывает сэмпл. Каждая попытка failover учитывается отдельно; offline-сбои соединения уже без атрибуции. Offline-подсказка и `failbackMs` — браузерные адаптации Defjs.

Штрафы следуют breaker’у подряд идущих ошибок Linkerd: `minPenaltyMs: 1000`, `maxPenaltyMs: 60000` и `jitterRatio: 0.5`. База — `min(minPenaltyMs × 2^level, maxPenaltyMs)`, начиная с уровня ноль. Добавь равномерный положительный jitter до `base × jitterRatio`, с потолком `maxPenaltyMs`. В отличие от Envoy и gRPC A50 **нет квоты выброса и защиты последнего хоста**: разорваться может каждый эндпоинт. Нет сетки расчёта, процентного критерия, slow start и фонового таймера.

Истечение допускает **одну пробу**. Внутренняя стратегия, выбравшая другой хост, оставляет слот свободным. Проба решается на транспортном `end`: заголовки ответа HTTP/SSE или WebSocket `open`, по восстановлению response-future Finagle и границе завершения ответа tower. Не-ошибка возвращает обычный трафик и сбрасывает штраф на первый уровень; ошибка удваивает следующий штраф. Неатрибутированный результат освобождает слот. Если `end` не пришёл, решает `done`. Поздний `done` — обычный сэмпл. Другие сэмплы во время разрыва или пробы счётчики не меняют. Неверный терминальный классификатор освобождает слот, не решая здоровье. Нет таймаута пробы, который считает успех; долгий успешный handshake сразу возвращает трафик. Проба `failbackMs` у pick-first остаётся независимой.

Для **активных проверок** приложение делает пробы и кэширует результаты; `isHealthy` синхронно читает этот кэш один раз на эндпоинт при `pick`. Это должно быть дёшево и не должно делать I/O. Брошенный или не-boolean результат отклоняет только этот pick с `REQ_OPTIONS_INVALID`. Возврат true никогда не отменяет пассивный выброс. Чтобы использовать только активные проверки, поставь `consecutiveFailures: 0`

Если фильтрация убирает всех кандидатов, балансировщик сначала игнорирует активные проверки и сохраняет пассивные выбросы; если всё ещё пусто, он берёт исходный текущий список. Это fail-open в panic mode по Finagle, а не политика ожидания/503 у Linkerd. Он никогда не приносит эндпоинты из списка другого клиента.

Выбирай round robin для равных серверных реплик; выбирай p2c, когда меняется нагрузка или задержка. p2c по умолчанию сэмплирует двух разных кандидатов и сравнивает затухающий RTT × (pending + 1) PeakEwma tower; при равенстве побеждает первый розыгрыш. В отличие от Envoy и gRPC A48 сэмплирование **без возвращения**. `choiceCount` — целое не меньше 2, потолок 10. Значения по умолчанию `defaultRttMs: 30` и `decayMs: 10000` взяты из Linkerd. Оба конечные и положительные. Оценки простоя затухают к нулю ради исследования. `load: "pending"` сравнивает попытки в полёте; это глобальный least-connections, только если сэмплирован каждый кандидат.

Pending начинается в `start` непосредственно перед Fetch или созданием сокета и заканчивается в `end`, не после post-интерцепторов и не при закрытии сессии. RTT — это `Date.now() - startTime` на этой границе для **всех транспортов и результатов**, включая быстрые ошибки. Нет синтетического штрафа и p2c `isFailure`; быстрые сбои эндпоинтов обрабатывает фильтрация здоровья. Больший сэмпл сразу заменяет оценку; иначе обновление tower — `old × exp(-Δt/decayMs) + sample × (1-exp(-Δt/decayMs))`. `done` без `end` отпускает pending без сэмпла RTT. Неначатые попытки pending не меняют.

Это следует tower `CompleteOnResponse` и разделению Linkerd между завершением нагрузки и итоговой классификацией здоровья. Fetch показывает заголовки, WebSocket показывает `open`; Defjs не видит границу первого body-frame Linkerd и завершение на уровне стрима Envoy. Сбои чтения тела HTTP и отказы чтения тела ответа SSE после заголовков влияют на `done`, не на уже выданный `end`. Транспортные сбои WebSocket после `open` точно так же влияют только на `done`. p2c предпочитает более лёгких сэмплированных кандидатов, не обязательно глобально самый быстрый хост.

SSE и WebSocket выбирают снова при reconnect, не внутри установленного соединения. Их opt-in политики reconnect принимают `connectTimeoutMs`, чтобы ограничить handshake. Здоровое долгоживущее соединение после деплоя не перебалансируется. Поставь на сервере максимальное время жизни соединения, чтобы клиенты переподключались и выбирали снова. Обычный EOF SSE терминален; идущая подписка должна наблюдать `closed` и сделать новый вызов со своим курсором приложения.

В отличие от HTTP failover, переподключения стрима не запускают builder и интерцепторы заново. Они повторно используют уже собранный запрос, а переподключение с атрибуцией может выбрать другой базовый URL или origin. Учётные данные, привязанные к эндпоинту, должны быть действительны или обновлены для **каждой физической попытки**, а не захвачены только для первой базы: используй [границу Fetch SSE](/ru-RU/docs/sse#reconnect) или [границу транспорта и authentication WebSocket](/ru-RU/docs/web-socket#protocols-и-authentication).

Свой балансировщик — объект с `pick`. Верни кортеж error-first. Не бросай исключение из-за того, что список пуст.

`pick`, необязательный `start`, необязательный `end` и необязательный `done` синхронны. `start` выполняется не больше одного раза непосредственно перед Fetch или созданием сокета. Ошибки сборки, short-circuit интерцептора (включая `makeResponse`), заменённые базы и отмена до транспорта не вызывают ни `start`, ни `end`. `end(info)` выполняется не больше одного раза после `start`, синхронно, когда Fetch возвращает заголовки, когда сокет открывается или когда транспорт падает до этой границы. Он получает `{ attempted: true, status }` для заголовков HTTP/SSE, `{ attempted: true }` для открытия сокета, fault этой фазы при сбое до ответа и `{ attempted: false }` при отмене вызывающим. Фильтрация здоровья передаёт оба сигнала своему потомку. Используй их для учёта попыток в полёте, а не для счёта при выборе. Если интерцептор вызывает `next()` несколько раз в одной попытке, дополнительные вызовы Fetch используют тот же выбор, поэтому `start`, `end` и `done` по-прежнему выполняются не более одного раза; чтобы попробовать другой эндпоинт, используйте `withEndpointFailover`.

`done` выполняется ровно один раз на успешный pick, после окончания HTTP-вызова или физической попытки stream/socket. Он делит форму `EndpointDoneInfo` с `end` (поля длительности нет) и хранит итоговую классификацию здоровья, включая сбой чтения тела или отмену после заголовков. Броски и отклонённые thenable всех хуков сдерживаются. Promise из `pick` по-прежнему недействителен; искажённые исходы и броски становятся `REQ_BUILD_FAILED`, неверная встроенная конфигурация становится `REQ_OPTIONS_INVALID`, и ни то ни другое не бросает на месте вызова операции. Опусти хуки, если учёт не нужен. Интерцепторы видят выбранный `baseEndpoint`, а не список кандидатов.

| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Тело ответа HTTP обрывается раньше времени                                                                                                                              | `{ attempted: true, code: "NET_BODY_INCOMPLETE", status }`                         |
| Успешный handshake SSE, затем обычный отказ чтения тела ответа                                                                                                          | `{ attempted: true, code: "NET_UNREACHABLE" }`, без `status`                       |
| Обычный EOF SSE, сбой декодирования тела handshake для media или объявленного тела, предел parser или queue, ошибка transform, hook или observer, либо сбой `getReader` | Полученный `{ attempted: true, status }`; нового сетевого кода нет                 |
| Открытый WebSocket, нет нативной cause, наблюдаемый код 1006 или `wasClean === false`                                                                                   | `{ attempted: true, code: "NET_UNREACHABLE" }`, даже без нативного события `error` |
| Открытый WebSocket, нет нативной cause и нет признака аномального close                                                                                                 | `{ attempted: true }`                                                              |
| Отмена вызывающим или ручное закрытие стрима или сокета                                                                                                                 | `{ attempted: false }`                                                             |
| Дедлайн вызывающего после старта попытки                                                                                                                                | `{ attempted: true, code: "NET_TIMEOUT" }`, без `status`                           |

Существующее сопоставление причин timeout и abort важнее новых сигналов чтения и close, а подсказка offline по-прежнему подавляет атрибутированный `NET_UNREACHABLE`. Отсутствующий `wasClean` не является false; чистые close 1000, 1001, 1005, 1011, 1012, 1013 и приватные 4xxx сами по себе не ошибки. Ошибки приложения и политики reconnect сами не создают сэмплы сетевого сбоя. Реальный физический сбой остаётся одним сэмплом, даже если политика позже откажется или бросит. Сэмпл сбоя чтения SSE намеренно заменяет прежний статус, отражавший только handshake; обычный EOF и сбои приложения сохраняют этот статус. Подставленные провайдеры Fetch для SSE владеют своими ошибками чтения: это сигнал здоровья, а не доказательство, что удалённый эндпоинт вызвал fault.

Эти сэмплы сдвигают pick-first по умолчанию или питают существующие пороги здоровья; они **не** включают reconnect, не меняют его бюджет, не разрешают прикладной replay, не синтезируют нативное событие `error` и не переписывают логические `closed.kind`/`cause` WebSocket. Без reconnect новый выбор эндпоинта действует при следующем явном вызове.

## Выведи клиент

`client(options?)` возвращает значение `Client` для одного вызова. `client()` и `client(undefined)` не сохраняют опции запроса. `client({})` оставляет пустой снимок; Defjs не отбрасывает его проверкой ключей. При вызове `client(options)` каждое поле запроса верхнего уровня читается один раз и кладётся в новый объект опций. Массив `protocols` копируется. `heartbeat` копирует `intervalMs`, `isAck`, `message` и `timeoutMs`. `reconnect` копирует `attempts`, `delayMs`, `factor`, `jitter`, `maxDelayMs` и `shouldReconnect`. Отсутствующие вложенные блоки остаются отсутствующими, поэтому не включают heartbeat или повторные попытки. `signal`, `beforeConnect` и каждый колбэк сохраняют свою идентичность. Тот же объект опций можно передать снова; каждый вызов захватывает собственные контейнеры. Вывод не делает I/O. Геттер на этих фиксированных полях выполняется во время `client(options)`. Если он бросает, исключение выходит из этого вызова и оставляет фабрику рабочей. Оно не превращается в fault. Числа вне диапазона по-прежнему проверяются, когда выполняется операция, и по-прежнему возвращают `REQ_OPTIONS_INVALID`. Значение клиента не вызываемое; создавай его на каждый вызов.

`signal` не объединяется. Повторное использование значения клиента с `signal` делит этот сигнал между вызовами, поэтому создавай значение клиента на каждый вызов. Объединяй сигналы через `AbortSignal.any` в коде приложения.

Базовая конфигурация из `createClient` общая для каждого значения клиента и во время выполнения не заморожена. Она фиксирована по соглашению: библиотека её не меняет, и приложению тоже не следует. Стандартные хелперы, такие как `withWebSocketHeartbeat`, `withWebSocketReconnect`, `withSSEReconnect` и `withWebSocketProtocols`, копируют свои фиксированные records, когда хелпер применяется. Свой client option всё ещё может хранить собственную ссылку. `withInterceptors` добавляет для каждого элемента свежий record `{ kind, fn }` и оставляет сам `fn`. Выведенный клиент несёт захваченный объект [`RequestOptions`](/ru-RU/api/core/requestoptions-type) только если опции были переданы. У фабрики, `client()` и `client(undefined)` его нет. Код приложения передаёт клиент операции. Это внутреннее состояние он не читает.

## Опции запроса

У [`RequestOptions`](/ru-RU/api/core/requestoptions-type) семь плоских полей. Каждый протокол читает только известные ему поля и игнорирует остальные. Передать `heartbeat` в HTTP-операцию — значит, что поле игнорируется, а не что это fault. SSE читает из опций запроса только `signal`. Переподключение SSE берётся из конфигурации клиента (`withSSEReconnect`), поэтому `client({ reconnect })` влияет только на WebSocket. Фильтра протокола на этапе компиляции нет.

| Поле                 | Кто использует       | Правило                                                                                             |
| -------------------- | -------------------- | --------------------------------------------------------------------------------------------------- |
| `signal`             | HTTP, SSE, WebSocket | Прерывает вызов. Дедлайн — `AbortSignal.timeout(ms)` (`NET_TIMEOUT`). Ручной abort — `NET_ABORTED`. |
| `onUploadProgress`   | HTTP                 | SSE и WebSocket игнорируют.                                                                         |
| `onDownloadProgress` | HTTP                 | SSE и WebSocket игнорируют.                                                                         |
| `beforeConnect`      | WebSocket            | Заменяет настройку клиента для этого вызова.                                                        |
| `protocols`          | WebSocket            | Заменяет список клиента. Он не дописывается.                                                        |
| `heartbeat`          | WebSocket            | Заменяется целиком. `timeoutMs` — ожидание подтверждения heartbeat, а не дедлайн запроса.           |
| `reconnect`          | WebSocket            | Заменяется целиком.                                                                                 |

Поля `timeout` нет, поля `abort` нет, и дедлайна по умолчанию на уровне клиента нет. Для SSE и WebSocket `signal` покрывает всё соединение, в том числе после открытия. Дедлайна только на старт нет. Приложение, которому он нужен, создаёт свой `AbortController`, прерывает его через `new DOMException("...", "TimeoutError")` из таймера и сбрасывает таймер после того, как `await` вернулся. См. [SSE](/ru-RU/docs/sse#close-and-dispose).

`HttpExecuteOptions` — срез HTTP: `signal` плюс колбэки прогресса. `EventStreamExecuteOptions` — это `{ signal? }`. `WebSocketExecuteOptions` — срез WebSocket плюс `signal`.

## Результаты по транспорту

- HTTP → `[error, data, response]`
- SSE → `[error, stream, open]`. `open` — снимок первого успешного handshake возвращённого соединения для нативных handle Defjs или обёрток, передающих тот же живой объект `open`; пользовательские handle или обёртки, переопределяющие `open`, используют свой текущий публичный `open` даже после переподключения, а `stream.open` остаётся живым (см. [SSE](/ru-RU/docs/sse)).
- WebSocket → `[error, session, connection]`

Вернись до использования успешного значения, если задан `error`.

Очистка на тебе: abort HTTP, close SSE + `await stream.closed`, close WebSocket + `await session.closed`.

## Scope на сервере и в браузере

На сервере создавай клиент внутри границы запроса, когда опции или замыкания interceptor’ов захватывают auth, cookies, пользователей или tenants. Идентичность клиента сама по себе — не security boundary.
