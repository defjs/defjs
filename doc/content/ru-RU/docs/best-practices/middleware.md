---
title: "Промежуточное ПО"
description: "Собирай интерцепторы в небольшие упорядоченные политики, которые остаются на границе приложения."
---

## Одна задача на интерцептор [#one-concern]

Давай каждому интерцептору одну задачу: прикрепить аутентификацию, добавить заголовок трассировки, замерить время или сделать short-circuit для заранее одобренного случая. Промежуточное ПО, которое аутентифицирует, переписывает тело, повторяет запрос и логирует, трудно тестировать и трудно понимать.

Предпочитай:

```ts
const auth = createHttpInterceptor(async (request, next) => {
  const response = await next(request);
  return response;
});
```

Избегай одного интерцептора, который меняет несколько несвязанных частей запроса.

## Порядок — это политика [#order]

Интерцепторы выполняются в порядке регистрации. Первый зарегистрированный — самый внешний: он первым видит запрос и последним — ответ. Политику, которая должна оборачивать всю попытку, ставь снаружи; политику, которая должна быть ближе всего к транспорту, — внутри.

```ts
const client = createClient(
  withEndpoint("https://api.example.com"),
  withInterceptors(trace, auth),
);
```

`trace` оборачивает `auth`; `auth` выполняется до транспорта.

## Делай short-circuit осознанно [#short-circuit]

Интерцептор может вернуть ответ через `makeResponse`, не вызывая `next`. Используй это для заранее одобренного кеша, ответа окна обслуживания или локального теста. Ответ всё равно должен удовлетворять объявленному `output` операции; не превращай провал в успех.

## Не переписывай контракт [#contract]

Промежуточное ПО может корректировать заголовки, контекст трассировки или URL запроса в пределах правил валидации библиотеки. Оно не должно менять смысл объявленных `input` или `output`. Аутентификация и трассировка относятся сюда, а не в `builder`.

## Оставайся без состояния [#stateless]

Не храни данные отдельного запроса в общем клиенте или модуле. Передавай значение через запрос, конфигурацию клиента или замыкание, созданное для этого клиента. Промежуточное ПО, которое изменяет общее состояние, смешивает данные параллельных вызовов.

## Обрабатывай провалы на границе [#failures]

Бросок из промежуточного ПО — это провал; возвращай ответ, только если промежуточное ПО намеренно обработало запрос. Не перехватывай fault только ради записи в лог, чтобы продолжить с `undefined`. Для логирования используй хук телеметрии приложения или интерцептор, а определение держи свободным от обоих.
