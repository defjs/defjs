<ApiReference identity="@defjs/core:withSSEReconnect" />

```ts
function withSSEReconnect(options: ClientSSEOptions['reconnect']): ClientOption
```

Настраивает автоматический reconnect после сбоя SSE-потока. Reconnect включается явно: без этой опции упавший поток не повторяется. Передача `undefined` сбрасывает ранее заданное значение.

```ts
type SSEReconnect = {
  attempts?: number
  delayMs?: number
  factor?: number
  jitter?: number
  maxDelayMs?: number
  shouldReconnect?: (context: {
    attempt: number
    cause?: unknown
    lastEventId: string
    method: string
    open?: { response: { status: number; statusText: string; url: string }; url: string }
  }) => boolean | Promise<boolean>
}
```

- `attempts` — бюджет повторов для каждого периода недоступности соединения. Когда `reconnect` задан, по умолчанию `3`, а `0` отключает повторы. Успешный handshake сбрасывает бюджет, `attempt` в колбэке и показатель степени в расчёте задержки. Отсутствие `attempts` не даёт неограниченных повторов в пределах одного периода недоступности. Повторяющиеся успешные открытия, за которыми сразу следуют повторяемые сбои стрима, могут продолжать reconnect с текущей базовой задержкой (с учётом jitter и пределов), потому что каждое открытие сбрасывает бюджет; останови их через `shouldReconnect`. Обычный EOF остаётся терминальным.
- Без `shouldReconnect` переподключение выполняется только для запросов `GET`, `HEAD`, `OPTIONS`, `PUT` и `DELETE`. Если колбэк задан, его результат определяет, переподключаться ли для каждого метода, включая `POST`; поле `method` в контексте позволяет различать эндпоинты. Верни `false`, чтобы прекратить повторы после этого сбоя. Колбэк вызывается до проверки лимита попыток.
- Запрос с телом `ReadableStream` никогда не переподключается, и `shouldReconnect` для него не вызывается.
- `delayMs`, `factor`, `jitter` (от 0 до 1) и `maxDelayMs` задают backoff. `factor` по умолчанию `1`, `jitter` — `0`. `maxDelayMs` ограничивает итоговую задержку после jitter и округления. Если предел не задан, всё равно действует ограничение платформенного таймера в `2_147_483_647` мс. Нулевая базовая задержка остаётся нулевой; при переполнении вычислений с допустимыми числами задержка ограничивается этими пределами.
- `delayMs` — лишь начальная базовая задержка (по умолчанию `1000`). Поле `retry:` от сервера (только цифры, в миллисекундах) заменяет её для последующих попыток.
- Последний id события при следующей попытке снова отправляется в `Last-Event-ID` как байты UTF-8. Пустое поле `id:` очищает его; ID, содержащий NUL, игнорируется.
- Опции reconnect проверяются до interceptor’ов и Fetch: `attempts` должен быть неотрицательным безопасным целым числом; `delayMs` и явно заданный `maxDelayMs` должны быть конечными и неотрицательными; `factor` — конечным и положительным; `jitter` — конечным и в пределах 0–1. Недопустимые значения возвращают `REQ_OPTIONS_INVALID` при выполнении команды.
