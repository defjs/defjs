# SSE

Объявите поток событий, вызовите операцию с клиентом, прочитайте события, затем закройте поток.

## defineEventStream()

<ApiSignature name="defineEventStream" />

- **definition** — `path` и карта `events`; необязательные `method` (по умолчанию `'GET'`), `operation`, `input`, `error`, `maxBufferSize` (по умолчанию `64 * 1024`) и `maxQueueSize` (по умолчанию `1024`). При объявленном `input` всегда нужен явный `builder`. `input` только описывает параметры; куда пойдёт каждое значение, решает только builder. Опустить `builder` можно только в определениях без `input`. Эти члены `definition` описаны в [`EventStreamDefinition`](/ru-RU/api/core/eventstreamdefinition-type). `error` обязателен только когда задан тип error-struct, а `builder` — ровно тогда, когда объявлен `input`.
- **Возвращает** операцию. Первый аргумент — [`Client`](/ru-RU/api/core/client-type). Дальше идёт только input. Вызов начинает поток.

<include cwd>examples/api/define-event-stream.ts#example</include>

Вызов возвращает `[null, stream, open]` или `[error, undefined, open?]`. Если объявлен `error`, сбой — это `Fault` этого struct; иначе `Fault<undefined>`. Передавайте `signal`, выводя клиент из [`RequestOptions`](/ru-RU/api/core/requestoptions-type). SSE читает только `signal` и игнорирует прогресс и поля WebSocket.

## EventStreamExecuteOptions

<ApiSignature name="EventStreamExecuteOptions" />

`EventStreamExecuteOptions` — это `{ signal? }`. Полей `timeout` или `abort` нет, и колбэка прогресса нет. `signal` покрывает весь поток, в том числе после открытия. Дедлайн — `AbortSignal.timeout(ms)`, и он классифицируется как `NET_TIMEOUT`. Ручная отмена — `NET_ABORTED`. Дедлайна только на старт нет, и дедлайна по умолчанию на уровне клиента нет. Приложение, которому нужен дедлайн только на старт, создаёт свой `AbortController`, прерывает его через `new DOMException("...", "TimeoutError")` из таймера и сбрасывает таймер после того, как `await` вернулся.

## EventStreamHandle

<ApiSignature name="EventStreamHandle" />

Третий слот кортежа — снимок `open` на момент старта; `stream.open` после переподключения отражает последнее соединение. Этот третий слот является снимком первого успешного хэндшейка только для нативного хэндла Defjs или обёртки, передающей тот же живой объект `open`; пользовательские хэндлы и обёртки, переопределяющие `open`, сохраняют свой текущий публичный `open` даже после переподключения, поэтому общий `closed` не позволяет обойти очистку URL или фильтрацию заголовков, а Defjs не восстанавливает метаданные первого хэндшейка из произвольных преобразований. Для освобождения ресурсов, принадлежащих области видимости, предпочитайте `await using stream = handle`. Асинхронное освобождение останавливает чтение Defjs и переподключения и ждёт освобождения блокировки reader; оно не гарантирует завершение зависшего Promise `ReadableStream.cancel()`, которым управляет провайдер. Ручные `close()` / `closed` остаются доступны.

### EventStreamCloseInfo

<ApiSignature name="EventStreamCloseInfo" />

`kind` — это `eof`, `aborted` или `error`. Каждый вариант может нести `reason` и `cause`. `code` есть только у `error`, одно из [`EventStreamFaultCode`](/ru-RU/api/core/eventstreamfaultcode-type): `'CAP_BUFFER_EXCEEDED' | 'CAP_QUEUE_OVERFLOW' | 'EXT_HOOK_FAILED' | 'EXT_OBSERVER_FAILED' | 'HTTP_STATUS' | 'NET_TIMEOUT' | 'NET_UNREACHABLE' | 'REQ_BUILD_FAILED' | 'REQ_OPTIONS_INVALID' | 'RES_DECODE_FAILED' | 'RES_MEDIA_TYPE_INVALID'`. `REQ_BUILD_FAILED` и `REQ_OPTIONS_INVALID` значат, что выбор эндпоинта при переподключении не удался после открытия потока. `HTTP_STATUS` значит, что хэндшейк переподключения завершился не-2xx статусом.

## EventStructs

<ApiSignature name="EventStructs" />

Ключ — имя SSE-события; сообщение без поля `event:` называется `message`. Если ни один ключ не подошёл, используется struct `default`. Event struct `string` оставляет сырой текст `data`. Любой другой вид struct — это JSON-текст: `JSON.parse`, затем struct. Голый `struct.literal` поэтому ждёт JSON-текст, а не незакавыченный токен. Тела ответа хэндшейка `error` следуют тому же правилу вида struct, что HTTP: `string` — текст, `blob` / `file` — blob, `arrayBuffer` — байты, всё остальное — JSON.

Reconnect живёт на клиенте (`withSSEReconnect`). SSE `jitter` — **мультипликативный коэффициент 0–1**, как у WebSocket.

Бюджет повторов и показатель степени задержки сбрасываются после каждого успешного хэндшейка и действуют на каждый обрыв отдельно, поэтому `attempts: 1` всё равно может создать много соединений за длительную сессию. Штатный EOF от сервера не запускает переподключение, а незавершённое событие при EOF не фиксирует свой ID. Хэндшейк с ответом 502, 503 или 504 повторяется как отказ в соединении по тем же правилам переподключения (метод, `shouldReconnect`, `attempts`, тело `ReadableStream`); остальные не-2xx хэндшейки фатальны. Исчерпанные повторы и фатальные хэндшейки переподключения завершаются с `HTTP_STATUS`; проверяйте живое значение `stream.open.response.status`, чтобы увидеть статус. Недопустимые числовые настройки возвращают `REQ_OPTIONS_INVALID` до открытия потока, а `maxDelayMs` ограничивает итоговую задержку после случайного отклонения. Правила проверки, значения по умолчанию и обработку `Last-Event-ID` в UTF-8 см. в [`withSSEReconnect`](/ru-RU/api/core/withssereconnect).

Парсер следует правилам строк и полей WHATWG SSE и удаляет только один начальный UTF-8 BOM в начале каждого физического потока. U+FEFF в данных и значениях ID сохраняется; имя поля с BOM в начале, появившееся позже, игнорируется как неизвестное. Несколько строк данных соединяются через `\n`, пустая строка выдаёт событие с данными, а незавершённое событие в конце потока (EOF) отбрасывается.

См. [руководство по SSE](/ru-RU/docs/sse) и [Чтение SSE-потока](/ru-RU/recipes/consume-sse).

## EventStreamDefinition

`path`, `events`, необязательные `method` / `operation` / `input` / `error` / `maxBufferSize` / `maxQueueSize`. Форма запроса совпадает с HTTP, включая `body`. `GET` и `HEAD` не могут нести тело. При объявленном `input` всегда нужен явный `builder`. `input` только описывает параметры; куда пойдёт каждое значение, решает только builder. Опустить `builder` можно только в определениях без `input`.

## EventStreamEndpoint

То, что возвращает `defineEventStream`. Первый аргумент — клиент. Дальше идёт только `input`.

## EventStreamRequestShape

Те же поля, что у `HttpRequestShape`, для метода и пути потока.

## StreamAwaitResult

`[null, stream, open]` или `[error, undefined, open?]`.

## EventStreamData

Разобранная полезная нагрузка события, выведенная из карты `EventStructs`.
