# OpenTelemetry на сервере

Middleware-плагин: инструментация исходящих HTTP / SSE / WebSocket через перехватчики Core. Этот пакет не инициализирует OpenTelemetry SDK и не инструментирует входящие серверные запросы.

См. [руководство по OpenTelemetry server](/ru-RU/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

Добавляет по одному перехватчику на каждый включённый транспорт в порядке HTTP, SSE, WebSocket. Применяйте при создании клиента через `createClient`. `options` обязателен; передайте `{}`, чтобы установить перехватчики только с распространением контекста.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter` и `logger` необязательны. Нет `propagator` → W3C Trace Context + Baggage.

Без `tracer` плагин не создаёт локальные спаны и не вызывает `trace.getTracer(...)`, `startSpanHook`, `requestHook` и `responseHook`. Переданные `meter` и `logger` работают независимо. Извлечённый родительский контекст передаётся дальше; `queryPropagation` WebSocket по умолчанию равен `false`. При наличии `tracer` опция `requireParentSpan: true` без активного родительского спана пропускает всю инструментацию, включая логи. Без `tracer` она не блокирует метрики и логи.

HTTP, SSE и WebSocket по умолчанию включены. `{ enabled: false }` пропускает транспорт.

## OpenTelemetryServerOptions

| Поле                | По умолчанию                | Эффект                                                                                                             |
| ------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `tracer`            | нет                         | Без него нет локальных спанов и хуков спанов.                                                                      |

| `webSocket`         | `{}`                        | Опции транспорта WebSocket.                                                                                        |

`enabled` по умолчанию `true`; транспорт отключает только `enabled: false`. Старый булев переключатель (`http: false`) и хуки верхнего уровня отвергаются только типами TypeScript. Проверки во время выполнения нет, поэтому `http: false` оставляет транспорт включённым, а хук верхнего уровня молча игнорируется.

Хуки спанов вызываются только при переданном `tracer`. `startSpanHook` выполняется синхронно до создания спана для своего транспорта HTTP, SSE или WebSocket. Возвращённые атрибуты применяются после встроенных, поэтому приложение может переопределить `url.full` или другое начальное значение. Если хук выбрасывает ошибку, Defjs создаёт спан со встроенными атрибутами и продолжает запрос; `requestHook` и `responseHook` выполняются после создания спана. Ни один из них не ожидается через await: брошенная ошибка или отклонение promise не блокируют операцию и не приводят к её сбою.

Пока `span.isRecording()` возвращает true, ошибки хуков записывают события `defjs.otel.hook.error` и `exception`. Если span не записывает данные (завершён или не выбран при сэмплировании), ошибки передаются диагностическому логгеру OpenTelemetry через `diag.error`. Для их получения приложение должно настроить `diag.setLogger(...)` из `@opentelemetry/api`; по умолчанию автоматического вывода нет. Пакет не инициализирует SDK, а эта диагностика не является отдельным SDK `LogRecord`.

`responseHook` получает то, что вернул транспорт: `HttpResponse` для HTTP, хэндл потока для SSE после успешного старта и сессию для WebSocket после открытия. Третий аргумент — исходный запрос.

По умолчанию `url.full` разрешает только `request.endpoint` относительно необязательного `request.baseEndpoint`; отдельный `request.queryString` не добавляется. Эта граница не является маскированием, а у пакета нет встроенного средства маскирования или политики чувствительных ключей. Явно составьте URL, принадлежащий приложению, и при необходимости удалите чувствительные параметры:

## Диагностика через Logger

Опция верхнего уровня `logger?: Logger` принимает интерфейс из `@opentelemetry/api-logs`, а не логгер приложения. Она необязательна и может использоваться отдельно. Defjs не получает глобальный логгер и не управляет провайдером. Он отправляет не более одной записи LogRecord уровня `WARN` (severity number 13) на запрос или логическое соединение, с фиксированным сообщением и атрибутами `server.address` и `server.port` (когда известны), `defjs.phase`, `exception.type`, а также `http.request.method` для HTTP, `defjs.sse.fault.code` при завершении SSE-потока с ошибкой и `websocket.close.code`, когда информация о закрытии WebSocket содержит числовой код:

| Исход                                                                   | Событие                                                           | `defjs.phase` |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------- |
| HTTP `next()` отклоняется, кроме отмены и публичного сбоя `HTTP_STATUS` | `http.client.request.exception`                                   | `request`     |
| Соединение SSE или WebSocket не удалось                                 | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `connect`     |
| SSE или WebSocket завершается ошибкой, включая отклонённый `closed`     | то же событие транспорта                                          | `connection`  |

Ответы с обычным статусом (включая 4xx/5xx, чьё объявленное тело `error` декодируется), успех, нормальное закрытие, EOF и отмена вызывающим не создают LogRecord. Отмена по дедлайну HTTP логируется один раз, только если отклонение promise из-за таймаута достигает границы `next()` / транспорта перехватчика OTel (отмена с причиной `TimeoutError`, например `AbortSignal.timeout()`, считается таймаутом, а не обычной отменой). Если дедлайн замечает только вызов операции — при разборе input, работе builder, работе прикладного перехватчика после `next()` или преобразовании тела после цепочки, — LogRecord не отправляется; наблюдай вызов операции. Ошибки чтения объявленного тела `output` / `error` внутри HTTP-обработчика логируются для любого представления; ошибки типа медиа и `JSON.parse` — только для JSON-представлений, при любом HTTP-статусе. Текст, blob-значения и байты в не-JSON формате не считаются ошибкой лишь потому, что их тип медиа не JSON. Необъявленное тело никогда не читается и не может вызвать запись в лог. Валидация struct, отсутствующее объявленное тело (например, 204) и последующее преобразование в `HTTP_STATUS` происходят после перехватчика и не логируются. Хэндшейк SSE со статусом вне `2xx` логируется всегда и один раз; кадр закрытия WebSocket от сервера не логируется никогда, каким бы ни был код. Резкий обрыв без кадра закрытия (1006) зависит от среды выполнения: там, где WebSocket платформы вызывает `error` перед `close`, сессия завершается ошибкой и логируется один раз; там, где нет (Bun), обрыв — обычное закрытие, и ничего не логируется.

`exception.type` — имя класса того, что увидел перехватчик, а не код сбоя Defjs: например `BodyFailure` (тело HTTP), `EventStreamFatalError` (хэндшейк SSE, завершившийся по причине, отличной от статуса не 2xx, например ответ не `text/event-stream`), `DefjsFault` (старт WebSocket, а также хэндшейк SSE со статусом не 2xx), `TypeError` (сетевой сбой) или `Error` (таймаут). Фильтрами, экспортёрами, flush и завершением работы управляет приложение.

Полные примеры логирования и интеграции со сторонними библиотеками см. в [руководстве по OpenTelemetry](/ru-RU/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
