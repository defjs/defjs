# OpenTelemetry на сервере

Middleware-плагин: инструментация исходящих вызовов каждой операции и её транспорта HTTP / SSE / WebSocket через перехватчики Core. Этот пакет не инициализирует OpenTelemetry SDK и не инструментирует входящие серверные запросы.

См. [руководство по OpenTelemetry server](/ru-RU/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

Добавляет перехватчик операции, если передан `tracer`, `meter` или `logger`, а затем по одному перехватчику на каждый включённый транспорт в порядке HTTP, SSE, WebSocket. Применяйте при создании клиента через `createClient`, один раз на клиента. `options` обязателен; передайте `{}`, чтобы установить транспортные перехватчики только с распространением контекста.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter` и `logger` необязательны. Нет `propagator` → W3C Trace Context + Baggage.

Каждый вызов операции наблюдается от самого вызова до его кортежа: спан операции вида `INTERNAL` с именем `defjs.operation.name` (например, `GET /orders/:id`), где при сбое `error.type` равен коду сбоя, один замер `defjs.client.operation.duration` и одна запись `WARN` в логе при сбое. Каждая попытка HTTP и каждое соединение SSE или WebSocket получает под ним транспортный спан вида `CLIENT`. Вызов без активного родительского спана начинает собственную трассу; что сохранить, решает сэмплер SDK.

Без `tracer` плагин не создаёт локальные спаны и не вызывает `trace.getTracer(...)`, `startSpanHook`, `requestHook` и `responseHook`. Переданные `meter` и `logger` работают независимо. Извлечённый родительский контекст передаётся дальше; `queryPropagation` WebSocket по умолчанию равен `false`.

HTTP, SSE и WebSocket по умолчанию включены. `{ enabled: false }` пропускает транспорт.

## OpenTelemetryServerOptions

| Поле                      | По умолчанию                | Эффект                                                                                     |
| ------------------------- | --------------------------- | ------------------------------------------------------------------------------------------ |
| `tracer`                  | нет                         | Без него нет локальных спанов и хуков спанов.                                              |

| `sse`                     | `{}`                        | Опции транспорта SSE.                                                                      |

`enabled` по умолчанию `true`; только `enabled: false` отключает транспорт вместе с телеметрией операций его вызовов.

Хуки спанов вызываются только при переданном `tracer`. `startSpanHook` выполняется синхронно до создания спана для своего транспорта HTTP, SSE или WebSocket. Возвращённые атрибуты применяются после встроенных, поэтому приложение может переопределить `url.full` или другое начальное значение. Если хук выбрасывает ошибку, Defjs создаёт спан со встроенными атрибутами и продолжает запрос; `requestHook` и `responseHook` выполняются после создания спана. Ни один из них не ожидается через await: брошенная ошибка или отклонение promise не блокируют операцию и не приводят к её сбою.

Хуки формируют транспортный спан; у спана операции хуков нет. Пока `span.isRecording()` возвращает true, ошибки хуков записывают события `defjs.otel.hook.error` и `exception`. Событие `exception` несёт только `exception.type` (имя класса, а не код сбоя Defjs), а `exception.message` и `exception.stacktrace` только при включённом `includeErrorDiagnostics`, потому что текст ошибки среды выполнения может включать полный URL запроса или фрагмент тела ответа; то же правило относится к событию `exception`, которое записывается при сбое транспорта. Если span не записывает данные (завершён или не выбран при сэмплировании), ошибки передаются диагностическому логгеру OpenTelemetry через `diag.error`. Для их получения приложение должно настроить `diag.setLogger(...)` из `@opentelemetry/api`; по умолчанию автоматического вывода нет. Пакет не инициализирует SDK, а эта диагностика не является отдельным SDK `LogRecord`.

`responseHook` получает то, что вернул транспорт: `HttpResponse` для HTTP, хэндл потока для SSE после успешного старта и сессию для WebSocket после открытия. Третий аргумент — исходный запрос.

По умолчанию `url.full` разрешает только `request.endpoint` относительно необязательного `request.baseEndpoint`; `request.query` не добавляется. Эта граница не является маскированием query. Как требуют семантические соглашения OpenTelemetry, учётные данные в userinfo эндпоинта заменяются на `REDACTED:REDACTED`, а значения чувствительных query-ключей по умолчанию (`sig`, `Signature`, `AWSAccessKeyId`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `X-Goog-Signature`) заменяются на `REDACTED`, но другого встроенного средства маскирования или политики чувствительных ключей у пакета нет. `url.full`, возвращённый `startSpanHook`, маскируется так же, но URL, который приложение записывает через объект `Span` в `requestHook` или `responseHook`, не перехватывается, поэтому составьте его явно и при необходимости замаскируйте:

## Диагностика через Logger

Опция верхнего уровня `logger?: Logger` принимает интерфейс из `@opentelemetry/api-logs`, а не логгер приложения. Она необязательна и может использоваться отдельно. Defjs не получает глобальный логгер и не управляет провайдером. Он отправляет одну запись LogRecord уровня `WARN` (severity number 13) на каждый неудавшийся вызов операции и по одной на каждый SSE-поток или сессию WebSocket, завершившиеся сбоем после открытия, каждую с фиксированным сообщением:

| Исход                                                                            | Событие                                                           | Атрибуты                                                                                                             |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Вызов операции завершается сбоем, кроме `NET_ABORTED`                            | `defjs.client.operation.exception`                                | `defjs.operation.name`, `error.type` (код сбоя), `exception.type`, `defjs.meta.*`                                    |
| SSE-поток или сессия WebSocket завершается ошибкой, включая отклонённый `closed` | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address`, `server.port`, `exception.type`, `defjs.meta.*`, `defjs.sse.fault.code` или `websocket.close.code` |

Успех, повторная попытка, которую восстанавливает следующая попытка, нормальное закрытие, EOF, кадр закрытия WebSocket от сервера с любым кодом и отмена вызывающим не создают LogRecord. Резкий обрыв WebSocket без кадра закрытия (1006) завершает сессию ошибкой и логируется один раз, в любой среде выполнения. Запись операции отправляется в контексте спана операции.

При `includeErrorDiagnostics: true` каждая запись также несёт `exception.message` и `exception.stacktrace`; для вызова операции это `message` и `stack` сбоя. Цепочка причин и перечисляемые поля ошибки никогда не экспортируются, но сообщение не фильтруется: сообщение сбоя часто совпадает с сообщением его причины, а текст ошибок платформы может цитировать URL запроса. Фильтрами, экспортёрами, flush и завершением работы управляет приложение.

Полные примеры логирования и интеграции со сторонними библиотеками см. в [руководстве по OpenTelemetry](/ru-RU/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
