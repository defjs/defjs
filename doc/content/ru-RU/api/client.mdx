# Клиент

Собери клиент, наложи опции слева направо, потом `execute` команды HTTP / SSE / WebSocket.

## createClient()

```ts
function createClient(...options: ClientOption[]): Client
```

Опции применяются по порядку. Клиент лучше собирать внутри границы запроса, если interceptors замыкают auth или tenants.

- **options** — хелперы вроде `withEndpoint`.
- **Возвращает** клиент, у которого `execute` перегружен под каждый транспорт.

## Хелперы option

Все хелперы возвращают `ClientOption`. Более поздний вызов заменяет более ранний для той же настройки, кроме `withInterceptors`: он дописывает.

### withEndpoint()

```ts
function withEndpoint(endpoint: string): ClientOption
```

Ставит base URL, который дописывается к относительным path.

### withInterceptors()

```ts
function withInterceptors(...interceptors: Interceptor[]): ClientOption
```

Дописывает interceptors в порядке регистрации. Смешанные kind фильтруются по транспорту в момент execute.

### withQuerySerializer()

```ts
function withQuerySerializer(serializer: QuerySerializer): ClientOption
```

Заменяет кодирование query для HTTP, SSE и WebSocket. `serializer(query)` получает **уже закодированный wire-объект** (алиасы применены, `Date` как ISO, `bigint` как string) и должен вернуть query-строку без ведущего `?`. Его не зовут, когда у запроса нет query. Builder, который возвращает `URLSearchParams`, его пропускает.

### withHeaders()

```ts
function withHeaders(headers: HeadersInit): ClientOption
```

Задаёт статические заголовки по умолчанию для HTTP- и SSE-запросов. WebSocket-запросы их не используют. Init копируется в момент применения опции, поэтому последующие правки объекта до клиента не доходят. Второй `withHeaders` заменяет первый, а не сливается с ним.

Приоритет для одного запроса:

1. Значения по умолчанию — начальный набор заголовков.
2. `headers`, которые вернул builder запроса, заменяют заголовок по умолчанию с тем же именем, если значение — скаляр или экземпляр `Headers`. Значение-массив (запись record вроде `{ 'x-a': ['one', 'two'] }` или `HeadersInit` в виде массива кортежей) добавляется к значению по умолчанию, а не заменяет его.
3. Interceptors получают объединённые заголовки и могут их менять.
4. В транспорте HTTP по умолчанию XSRF-заголовок добавляется последним и только если его ещё нет (см. `withXSRF`).

Для значений, которые меняются от запроса к запросу, используй interceptor: обновлённый Bearer-токен или HMAC по сериализованному телу.

### withTimeout()

```ts
function withTimeout(ms: number): ClientOption
```

Задаёт таймаут по умолчанию в миллисекундах только для **HTTP** `execute`. SSE и WebSocket его игнорируют: их execute-`timeout` — отдельный дедлайн запуска на каждый вызов. `ms` должен быть положительным safe integer не больше `2_147_483_647`, иначе `withTimeout` бросает `RangeError` сразу при вызове. Второй `withTimeout` заменяет первый.

Дедлайн охватывает разбор input, builder, interceptors, транспорт и чтение объявленного тела. Он сочетается с execute-опциями каждого вызова:

| Execute-опции                | Эффект                                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| нет                          | Действует значение клиента; истечение даёт `NET_TIMEOUT`.                                            |
| `{ timeout }`                | Заменяет значение клиента для этого вызова.                                                          |
| `{ abort }` или `{ signal }` | Сочетается со значением по умолчанию: сигнал вызывающего даёт `NET_ABORTED`, таймер — `NET_TIMEOUT`. |
| `{ abort, timeout }`         | По-прежнему недопустимо: `REQ_OPTIONS_INVALID`. Значение клиента конфликтом не считается.            |

### withCredentials()

```ts
function withCredentials(value: boolean): ClientOption
```

Если `true`, Fetch ставит `credentials: 'include'` для HTTP и SSE. По умолчанию выключено. Соединения WebSocket это не затрагивает.

### withXSRF()

```ts
function withXSRF(options?: {
  cookieName?: string
  headerName?: string
  tokenProvider?: (context: { request: HttpRequest }) => string | null | undefined
}): ClientOption
```

Добавляет в HTTP-запросы заголовок с XSRF-токеном. По умолчанию: cookie `XSRF-TOKEN`, header `X-XSRF-TOKEN`. Запросы SSE и WebSocket это не затрагивает.

Транспорт HTTP по умолчанию добавляет заголовок, когда выполняется всё перечисленное: метод не `GET`, `HEAD`, `OPTIONS` и не `TRACE`; у запроса ещё нет такого заголовка; запрос same-origin (вне браузера подходит любой запрос с `baseEndpoint`); найден непустой токен. Токен берётся из `tokenProvider`, если он задан, иначе из cookie, которую читают только в браузере.

## Типы

### Client

```ts
type Client = {
  execute(command: EventStreamCommand, options?: EventStreamExecuteOptions): Promise<StreamAwaitResult>
  execute(command: WebSocketCommand, options?: WebSocketExecuteOptions): Promise<SocketAwaitResult>
  execute(command: HttpCommand, options?: HttpExecuteOptions): Promise<HttpAwaitResult>
}
```

Параметры типов здесь опущены: каждая перегрузка выводит результат из команды.

### ClientOption

```ts
type ClientOption = (config: ClientConfig) => void
```

Мутирует `ClientConfig`, который собирает `createClient`. Пиши свою опцию, когда ни один хелпер `with*` не подходит.

### QuerySerializer

```ts
type QuerySerializer = (query: { [key: string]: unknown }) => string
```

### FetchHandle

```ts
type FetchHandle = (input: RequestInfo | URL, init?: RequestInit) => Promise<Response>
```

Сигнатура вызова, которая нужна Defjs от реализации Fetch. Это не `typeof fetch`, поэтому моку не нужны хостовые добавки вроде `preconnect`.

### ClientSSEOptions

### ClientWebSocketOptions

```ts
interface ClientSSEOptions {
  handle?: FetchHandle
  onInvalidEvent?: (context: {
    reason: 'missing-struct' | 'validation-failed'
    message: { id: string; event: string; data: string }
    cause?: unknown
    signal: AbortSignal
  }) => unknown
  reconnect?: {
    attempts?: number
    delayMs?: number
    factor?: number
    jitter?: number
    maxDelayMs?: number
    shouldReconnect?: (context: {
      attempt: number
      cause?: unknown
      lastEventId: string
      method: string
      open?: { response: { status: number; statusText: string; url: string }; url: string }
    }) => boolean | Promise<boolean>
  }
}

interface ClientWebSocketOptions {
  handle?: WebSocketHandleConstructor
  beforeConnect?: (context: { attempt: number; signal: AbortSignal }) => void | Promise<void>
  heartbeat?: {
    intervalMs: number
    isAck?: (message: unknown) => boolean
    message?: <T = unknown>() => T | unknown
    timeoutMs?: number
  }
  protocols?: readonly string[]
  reconnect?: {
    attempts?: number
    delayMs?: number
    factor?: number
    jitter?: number
    maxDelayMs?: number
    shouldReconnect?: (context: { attempt: number; cause?: unknown; code?: number; reason?: string; wasClean?: boolean }) => boolean
  }
}
```

Reconnect включается явно для обоих транспортов: без `withSSEReconnect` / `withWebSocketReconnect` повторов нет. Когда `reconnect` задан, действуют такие значения по умолчанию:

| Поле         | SSE        | WebSocket |
| ------------ | ---------- | --------- |
| `attempts`   | `3`        | `3`       |
| `delayMs`    | `1000`     | `1000`    |
| `factor`     | `1`        | `2`       |
| `jitter`     | `0`        | `0`       |
| `maxDelayMs` | без лимита | `30000`   |

Для SSE `delayMs` — лишь начальная базовая задержка: поле `retry:` от сервера заменяет её для последующих попыток. `attempts: 0` отключает повторы; опустить `attempts` — это не «без лимита». `jitter` должен лежать в пределах 0–1: каждая задержка случайно сдвигается не более чем на эту долю в обе стороны. Если `shouldReconnect` возвращает `false`, повторы прекращаются. Колбэк SSE дополнительно получает `lastEventId`, `method` запроса и последнюю информацию `open` и может быть асинхронным. Без этого колбэка SSE переподключается только для запросов `GET`, `HEAD`, `OPTIONS`, `PUT` и `DELETE`; если колбэк задан, его результат определяет, переподключаться ли для каждого метода. Колбэк WebSocket вместо этого получает сведения о закрытии: `code`, `reason` и `wasClean`.

SSE `onInvalidEvent` обрабатывает событие, для которого нет подходящего struct, включая отсутствие `default` (`missing-struct`), или чьи данные не проходят свой struct (`validation-failed`). Событие всегда отбрасывается; возвращаемое значение обработчика игнорируется, а брошенная им ошибка поток не закрывает.

Для WebSocket `beforeConnect`, `heartbeat`, `protocols` и `reconnect` можно также передать в `execute` на конкретный вызов; значение из execute заменяет значение клиента на этот вызов. `heartbeat.message` строит каждый ping; если он не задан или возвращает `undefined`, ничего не отправляется.

### ClientOptions

```ts
interface ClientOptions extends HttpClientOptions {
  sse?: ClientSSEOptions
  webSocket?: ClientWebSocketOptions
}
```

Описание клиента во входной форме: `endpoint`, `headers`, `http`, `interceptors`, `querySerializer`, `timeout`, `xsrf`, `withCredentials`, `sse` и `webSocket`. `createClient` его не принимает; он принимает хелперы option.

### ClientConfig

Готовый снимок, который мутируют хелперы option и читает `execute`: `ClientOptions` после применения значений по умолчанию, где `http.handle`, `interceptors`, `sse` (`ClientSSEConfig`) и `webSocket` присутствуют всегда.

### ClientSSEConfig

```ts
interface ClientSSEConfig extends ClientSSEOptions {
  handle: FetchHandle
}
```

Готовый SSE config на `ClientConfig.sse`: `ClientSSEOptions` с обязательным `handle`.

### WebSocketHandle

Поверхность WebSocket-инстанса, которую использует транспорт: `WebSocket` без `binaryType`, констант состояния готовности, `dispatchEvent` и свойств-обработчиков `on*`, зато с `readyState: number` только для чтения.

### WebSocketHandleConstructor

```ts
type WebSocketHandleConstructor = { readonly OPEN: number } & (new (...args: never[]) => WebSocketHandle)
```

Конструктор, который отдаёшь в `withWebSocketHandle`. Он должен экспортировать константу состояния готовности `OPEN`.
