# Клиент

`createClient(...)` возвращает [`DerivableClient`](/ru-RU/api/core/derivableclient-type). Составляйте опции клиента слева направо, затем вызывайте `client(options?)`, чтобы получить значение [`Client`](/ru-RU/api/core/client-type), и передай его операции: `getOrder(client(options), input)`.

## createClient()

<ApiSignature name="createClient" />

Опции применяются по порядку. Клиент лучше создавать внутри границы запроса, если перехватчики захватывают учётные данные аутентификации или контекст арендаторов. Возвращённая фабрика — функция. Её вызов возвращает значение `Client` и не делает I/O. Сама фабрика тоже является `Client` и не несёт опций запроса.

- **options** — хелперы вроде `withEndpoint`.
- **Возвращает** вызываемую фабрику. Базовая конфигурация общая для каждого значения клиента и во время выполнения не заморожена. Она фиксирована по соглашению: библиотека её не меняет, и приложению тоже не следует.

## Хелперы опций

Все хелперы возвращают `ClientOption`. Более поздний вызов заменяет более ранний для той же настройки, кроме `withInterceptors`: он дописывает.

### withEndpoint()

<ApiSignature name="withEndpoint" />

Копирует базовые URL-кандидаты в порядке первого появления и отбрасывает более позднюю копию той же строки. Более поздний `withEndpoint` заменяет список. Он не проверяет URL и не заменяет балансировщик. Пустой список допустим и завершает вызов с `REQ_BUILD_FAILED`.

### withBalancer()

<ApiSignature name="withBalancer" />

Заменяет балансировщик для последующих вызовов. Объект хранится по ссылке. Без этой опции каждый клиент получает свой `pickFirstBalancer()`.

### withInterceptors()

<ApiSignature name="withInterceptors" />

Добавляет перехватчики в порядке регистрации. Перехватчики разных видов фильтруются по транспорту, когда выполняется операция.

### withQuerySerializer()

<ApiSignature name="withQuerySerializer" />

Заменяет кодирование query для HTTP, SSE и WebSocket. `serializer(query)` получает **уже закодированный сетевой объект** (алиасы применены, `Date` как ISO, `bigint` как строка) и должен вернуть строку запроса без ведущего `?`. Строка разбирается в `query` запроса, поэтому запрос отправляет `query.toString()`, сериализацию application/x-www-form-urlencoded из URL Standard: пробел превращается в `+`, `[` — в `%5B`, а байты, которые записала функция, не сохраняются. Он не вызывается, когда у запроса нет query. Builder, возвращающий `URLSearchParams`, его пропускает.

### withHeaders()

<ApiSignature name="withHeaders" />

Задаёт статические заголовки по умолчанию для HTTP- и SSE-запросов. WebSocket-запросы их не используют. `headers` копируется в момент применения опции, поэтому последующие правки объекта до клиента не доходят. Второй `withHeaders` заменяет первый, а не сливается с ним.

Приоритет для одного запроса:

1. Значения по умолчанию — начальный набор заголовков.
2. `headers`, которые вернул builder запроса, заменяют заголовок по умолчанию с тем же именем. Первое значение этого имени заменяет значение по умолчанию, а последующие значения этого имени — из массива `[name, value]` или экземпляра `Headers` — добавляются к нему. Значение record — это одно значение: массив соединяется запятой так, как это делает JavaScript. Остальные имена по умолчанию остаются.
3. Перехватчики получают объединённые заголовки и могут их менять.
4. С `@defjs/core/xsrf` XSRF-заголовок добавляется последним и только если его ещё нет (см. `withXSRF`).

Для значений, которые меняются от запроса к запросу, используйте перехватчик: обновлённый Bearer-токен или HMAC по сериализованному телу.

Дедлайна по умолчанию на уровне клиента нет. Передайте `signal: AbortSignal.timeout(ms)` через производный клиент, когда он нужен одному вызову. Ручной abort — `NET_ABORTED`. `AbortSignal.timeout` классифицируется как `NET_TIMEOUT`.

### withXSRF()

<ApiSignature name="withXSRF" />

Добавляет в браузерные HTTP-запросы заголовок с XSRF-токеном. Импортируйте его из `@defjs/core/xsrf`. `options` — это значение `XSRFOptions`: `cookieName` (по умолчанию `XSRF-TOKEN`) и `headerName` (по умолчанию `X-XSRF-TOKEN`). Вызов `withXSRF()` без аргумента включает эти значения по умолчанию и бросает ошибку, если нет `location` или `document`, в том числе в Worker. Изоморфный код добавляет этот параметр только в браузере. Токен из другого источника задаётся интерцептором. Запросы SSE и WebSocket это не затрагивает.

Заголовок устанавливается, когда выполняется всё перечисленное: метод не `GET`, `HEAD`, `OPTIONS` и не `TRACE`; у запроса ещё нет такого заголовка; origin итогового URL запроса равен origin страницы; и в `document.cookie` есть непустой токен. Запросы с другим origin не читают cookie. Исключение при чтении cookie считается отсутствием токена. Пустой токен не задаёт заголовок. Недопустимое `headerName` или значение cookie, которое не является допустимым значением заголовка, завершает вызов с `EXT_HOOK_FAILED` до отправки любого запроса.

Проверка origin покрывает URL, который строит библиотека. Fetch сам следует редиректам, и после редиректа на другой origin удаляет только `Authorization`, поэтому XSRF-заголовок уходит вместе с запросом. Цель получает токен, если разрешает этот заголовок в своём CORS preflight. Чтобы отказаться от этого, передайте в `withHTTPHandle` функцию, которая вызывает `fetch(new Request(request, { mode: "same-origin" }))` для запросов к origin страницы, несущих этот заголовок. Не применяйте этот режим к кросс-origin API, чей заголовок приходит из интерцептора: Fetch отвергает любой запрос к другому origin в этом режиме. Такой запрос завершается с `NET_UNREACHABLE`, когда редирект покидает origin, и всё ещё следует редиректу того же origin. При `Referrer-Policy: no-referrer` Fetch отправляет `Origin: null` для POST того же origin в этом режиме, тогда как режим по умолчанию отправляет сериализованный origin, поэтому сервер, который проверяет `Origin`, может его отвергнуть. Некоторые движки реализуют это иначе.

## Типы

### DerivableClient

<ApiSignature name="DerivableClient" />

Корневой клиент, который возвращает `createClient`, в двух видах. Фабрика — функция и одновременно `Client` без опций запроса, поэтому `getOrder(client, input)` работает напрямую. Её вызов с [`RequestOptions`](/ru-RU/api/core/requestoptions-type) возвращает обычное значение `Client` для одного вызова. Это значение не вызываемое: `client()()` не компилируется. Вывод происходит один раз, из фабрики; цепочки нет. Записывайте тип как `DerivableClient`, а не `ReturnType<typeof createClient>`.

### Client

<ApiSignature name="Client" />

`Client` — значение, а не функция. Его возвращает вызов [`DerivableClient`](/ru-RU/api/core/derivableclient-type) с [`RequestOptions`](/ru-RU/api/core/requestoptions-type). `client()` и `client(undefined)` не сохраняют опции запроса. `client({})` оставляет пустой снимок. Вызов читает каждое поле верхнего уровня один раз. Массив `protocols` копируется. `heartbeat` и `retry` копируют свои известные поля, и копия `retry` включает массив `methods`. Отсутствующие вложенные блоки остаются отсутствующими. `signal`, `beforeConnect` и колбэки сохраняют свою идентичность. Геттер на захваченном поле выполняется во время этого вызова и, если бросает, выходит из вызова. Вывод не делает I/O. Значение клиента не вызываемое: его вызов не компилируется. Создавайте значение клиента на каждый вызов. Одно и то же значение можно передать многим операциям, но повторное использование значения с `signal` делит этот сигнал между вызовами. `signal` не объединяется; объединяйте сигналы через `AbortSignal.any` в коде приложения. Базовая конфигурация фабрики остаётся общей и не заморожена. Стандартные хелперы `with*` копируют принадлежащие им фиксированные записи при применении.

Не передавайте фабрику в сеттер состояния React (`setState(factory)` вызовет её как функцию-обновление) и не используйте её как источник Vue `watch` или `computed` (они вызывают функцию).

### RequestOptions

<ApiSignature name="RequestOptions" />

Семь плоских полей. Каждый протокол читает поля, которые понимает, и игнорирует остальные. Передача `heartbeat` в HTTP означает, что поле игнорируется, а не что это сбой. `client(options)` при этом вызове копирует массив `protocols` и известные поля `heartbeat` и `retry`. Отсутствующие вложенные блоки остаются отсутствующими. `signal`, `beforeConnect` и колбэки сохраняют свою идентичность. `retry` относится к HTTP, SSE и WebSocket одинаково и целиком заменяет политику повторов клиента для этого вызова. Фильтра протокола на этапе компиляции нет, и полей `timeout` или `abort` нет.

| Поле                 | Протокол              | Замена                                                                                     |
| -------------------- | --------------------- | ------------------------------------------------------------------------------------------ |
| `signal`             | HTTP, SSE и WebSocket | Прерывает вызов. Для SSE и WebSocket покрывает всё соединение, в том числе после открытия. |
| `onUploadProgress`   | HTTP                  | Другие протоколы игнорируют.                                                               |
| `onDownloadProgress` | HTTP                  | Другие протоколы игнорируют.                                                               |
| `beforeConnect`      | WebSocket             | Заменяет настройку клиента для этого вызова.                                               |
| `protocols`          | WebSocket             | Заменяет список клиента.                                                                   |
| `heartbeat`          | WebSocket             | Заменяется целиком. `timeoutMs` — ожидание подтверждения, а не дедлайн запроса.            |
| `retry`              | HTTP, SSE и WebSocket | Заменяет политику клиента целиком. HTTP `budget` остаётся у клиента.                       |

[`HttpExecuteOptions`](/ru-RU/api/core/httpexecuteoptions-type) — срез HTTP (`signal`, прогресс и `retry`). [`EventStreamExecuteOptions`](/ru-RU/api/core/eventstreamexecuteoptions-type) — это `{ signal?, retry? }`. [`WebSocketExecuteOptions`](/ru-RU/api/core/websocketexecuteoptions-type) — срез WebSocket плюс `signal` и `retry`.

### FetchHandle

<ApiSignature name="FetchHandle" />

Сигнатура вызова, которая нужна Defjs от реализации Fetch. Это не `typeof fetch`, поэтому моку не нужны хостовые добавки вроде `preconnect`. Обработчики HTTP/SSE по умолчанию получают `globalThis.fetch` при каждом вызове. HTTP передаёт `(url, init)` только неизменённой платформенной реализации Fetch; заменённая глобальная функция и пользовательские обработчики получают `Request`. SSE всегда передаёт `Request`. Core можно импортировать без Fetch; если Fetch отсутствует и при выполнении, обработчик по умолчанию возвращает `ENV_UNSUPPORTED`, а пользовательские обработчики по-прежнему доступны.

### ClientSSEOptions

### ClientWebSocketOptions

<ApiSignature name="ClientSSEOptions, ClientWebSocketOptions" />

Ни один из интерфейсов не хранит политику повторов. Повторы SSE и WebSocket берутся из общей для клиента политики [`withRetry`](/ru-RU/api/core/withretry), и без неё оборванный поток или закрытый сокет завершает вызов. Их значения по умолчанию, порядок решения после сбоя и то, что каждый транспорт повторяет по умолчанию, описаны в [withRetry()](#withretry).

SSE `onInvalidEvent` обрабатывает событие, для которого нет подходящего struct, включая отсутствие `default` (`missing-struct`), или чьи данные не проходят свой struct (`validation-failed`). Событие всегда отбрасывается; возвращаемое значение обработчика игнорируется, а брошенная им ошибка поток не закрывает.

Для WebSocket `beforeConnect`, `heartbeat` и `protocols` можно также передать на выведенном клиенте; каждое значение целиком заменяет соответствующую настройку клиента для этого вызова. `heartbeat.message` строит каждый ping; когда он возвращает `undefined`, ничего не отправляется. `heartbeat.timeoutMs` ждёт подтверждения и требует `isAck`. Это не дедлайн запроса. Heartbeat без ответа закрывает сокет и входит в поток повторов, как любое закрытие, которого не запрашивал `session.close()`.

### ClientOptions

<ApiSignature name="ClientOptions" />

`endpoints` — это `readonly string[]`. Готовое значение по умолчанию — `[]`. Пустой массив допустим и завершает вызов с `REQ_BUILD_FAILED`. `timeout` на уровне клиента нет. `createClient` этот объект не принимает; он принимает хелперы опций.

### ClientConfig

Готовый снимок, который изменяют хелперы опций и читает операция: `ClientOptions` после применения значений по умолчанию, где `http.handle`, `interceptors`, `sse` (`ClientSSEConfig`), `webSocket` и `balancer` присутствуют всегда. `retry` необязателен и по умолчанию `undefined` (одна попытка, без бюджета); `withRetry(options?)` задаёт его для каждого транспорта. `balancer` по умолчанию — новый `pickFirstBalancer()` для этого клиента. Это не поле [`RequestOptions`](/ru-RU/api/core/requestoptions-type).

### ClientSSEConfig

<ApiSignature name="ClientSSEConfig" />

Готовый конфиг SSE на `ClientConfig.sse`: `ClientSSEOptions` с обязательным `handle`.

### WebSocketHandle

Поверхность экземпляра WebSocket, которую использует транспорт: `WebSocket` без `binaryType`, константы состояния готовности, `dispatchEvent` и свойства-обработчики `on*`, а также `readyState: number` только для чтения.

### WebSocketHandleConstructor

<ApiSignature name="WebSocketHandleConstructor" />

Конструктор, который вы передаёте в `withWebSocketHandle`. Он должен предоставлять константу состояния готовности `OPEN`.

## Балансировщики

### pickFirstBalancer()

### roundRobinBalancer()

<ApiSignature name="pickFirstBalancer, roundRobinBalancer" />

`pickFirstBalancer` сдвигается на `NET_UNREACHABLE` или `NET_UNAVAILABLE` (HTTP 502, 503 или 504). Повтор выбирает заново из всех эндпоинтов и поэтому следует тому же правилу: после отказа в соединении он доходит до следующего эндпоинта, а после таймаута, который не сдвигает pick-first, снова пробует тот же эндпоинт. Порядок следует `members` — полному списку эндпоинтов клиента. Его необязательный `failbackMs` возвращает к первому эндпоинту только по времени: когда закреплённый эндпоинт не был первым в течение этого срока, следующий выбор, чьи кандидаты включают первый, выбирает его снова, без оценки того, восстановился ли он; если он снова даёт сбой, действует обычное правило сдвига, и время начинается заново. Повторы — отдельная политика клиента, её задаёт `withRetry`. `roundRobinBalancer` идёт по списку. `weights` необязателен. См. [Несколько эндпоинтов](/ru-RU/docs/client#multiple-endpoints).

### p2cBalancer()

<ApiSignature name="p2cBalancer" />

Выбирает разных кандидатов без повторного выбора (в отличие от Envoy/gRPC A48), сравнивая PeakEwma из tower или нагрузку pending. Значения по умолчанию Linkerd — RTT 30 мс и decay 10 с. Pending резервируется, когда `pick` выбирает эндпоинт, а `end` отпускает его на заголовках или при открытии сокета и записывает настоящий RTT для каждого транспорта, включая ошибки. `done` без `end` отпускает pending без сэмпла RTT. Нет классификатора ошибок p2c и штрафа. `choiceCount` по умолчанию 2 и ограничен 10.

### outlierDetection()

<ApiSignature name="outlierDetection, OutlierDetectionOptions" />

Считает классифицированные сбои и исключает эндпоинт по времени, а также пропускает эндпоинт, который отвергает переданная приложением функция `isHealthy`. Defjs не решает, что значит «здоровый». Он выключен, пока не передан объект: pick-first, round robin и p2c принимают его через свою опцию `outlierDetection` (`{}` для значений по умолчанию), либо он напрямую оборачивает пользовательский дочерний балансировщик. `isFailure` по умолчанию считает любой исход с кодом, включая `NET_TIMEOUT` и `NET_BODY_INCOMPLETE`; он только решает, что засчитывается в исключение, и его можно заменить. После пяти сбоев штрафы начинаются с 1000 мс, растут на 1000 мс с каждым исключением, добавляют положительный jitter до 0,5 базы и ограничены 60000 мс. Когда время истекает, эндпоинт снова можно выбрать, без пробного запроса и без оценки того, восстановился ли он; уровень штрафа сохраняется, и каждые 10 секунд без исключения он снижается на единицу (как в gRPC A50). Поздний результат попытки, начатой до исключения или пока эндпоинт был исключён, игнорируется. Нет квоты, защиты последнего хоста, сетки расчёта, процентного критерия и slow start. `isHealthy` — единственное суждение о здоровье; она сочетается с исключением через AND, поэтому `true` никогда не завершает штраф, а бросок из неё сообщается как `REQ_BUILD_FAILED`. Разорваться может любой хост; локальный для списка fail-open в стиле Finagle всё равно отправляет запросы. См. [Фильтрация здоровья и p2c](/ru-RU/docs/client#health-filtering-and-p2c).

### withRetry()

<ApiSignature name="withRetry, RetryOptions, RetryContext, HttpRetryContext, SSERetryContext, WebSocketRetryContext" />

Включает повторы для HTTP, SSE и WebSocket одной политикой, которая хранится в `config.retry`. Без `withRetry` каждый вызов делает одну попытку, простую и без backoff. `withRetry()` и `withRetry(undefined)` эквивалентны `withRetry({})`. Более поздний `withRetry` заменяет политику; `withRetry({ maxRetries: 0 })` выключает повторы после того, как они были включены. Опция фиксирует собственные поля, массив `methods` и вложенный бюджет в момент применения. Опции не проверяются во время выполнения; значение, которое TypeScript отверг бы, ведёт себя так, как с ним обращается JavaScript.

Значения по умолчанию — `maxRetries: 3` (повторы после первой попытки; `0` никогда не повторяет), `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000` (`Infinity` снимает предел, а предел платформенного таймера `2_147_483_647` мс всё равно действует) и `jitter: 0.2` (мультипликативный коэффициент от 0 до 1). Повтор _n_ ждёт `delayMs * factor^(n-1)` с ограничением; затем следуют jitter и округление, после чего итоговая задержка ограничивается снова. Нулевая база остаётся нулевой. `methods` по умолчанию — `GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT` и `DELETE`, сравнение без учёта регистра. `attemptTimeoutMs` ограничивает одну попытку: HTTP считает до конца тела ответа, SSE — до заголовков ответа, а WebSocket — до `open`. Попытка, у которой время вышло, — сбой, как и отказ в соединении. Для ограничения по времени без повторов используйте `withRetry({ maxRetries: 0, attemptTimeoutMs })`.

После каждой неудачной попытки на каждом транспорте выполняется одна и та же последовательность, в таком порядке:

1. Отмена вызывающим кодом, ручной `close()`, фатальная ошибка вроде несовпадающего media type, WebSocket, чей конструктор бросает исключение, и тело запроса `ReadableStream` завершают вызов. `shouldRetry` не вызывается.
2. Когда сделано `maxRetries` повторов, вызов завершается. `shouldRetry` не вызывается.
3. Решает `shouldRetry(context)`; без него решает `context.retryable`. Он может вернуть промис, и сигнал вызывающего его отменяет. Если он бросает, вызов завершается с `EXT_HOOK_FAILED` и брошенным значением как `cause`. Поток SSE, который уже был открыт, сообщает `EXT_HOOK_FAILED` в `closed.code`, а ошибку, чей `cause` — брошенное значение, — в `closed.cause`. Сессия WebSocket, которая уже была открыта, завершается с `closed.kind: "error"` и брошенным значением как `closed.cause`.
4. Только HTTP: бюджет должен оплатить повтор, иначе вызов завершается.
5. Вызов ждёт задержку backoff, затем балансировщик выбирает заново из всех эндпоинтов, включая тот, который только что дал сбой. Один эндпоинт пробуется снова после задержки. Для HTTP каждый повтор заново строит запрос и заново прогоняет всю цепочку перехватчиков; SSE и WebSocket переиспользуют свой запрос и заново разрешают только URL.

`context` — это [`RetryContext`](/ru-RU/api/core/retrycontext-type), суженный по `transport`. У каждого контекста есть `attempt` (номер повтора, который вот-вот начнётся, начиная с 1), `cause` (сбой, ошибка или причина закрытия) и `retryable` (то, что решает политика по умолчанию). HTTP добавляет `method`, `endpoint` и `status`; SSE добавляет `method`, `lastEventId`, `open` и `status`; WebSocket добавляет `code`, `reason` и `wasClean`. Верните `context.retryable`, чтобы сохранить решение по умолчанию и добавить правило поверх, или верните собственный вердикт, чтобы заменить его.

Что повторяемо по умолчанию, отличается только тем, какие сбои засчитываются:

| Транспорт | `retryable` по умолчанию                                                                                                                                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| HTTP      | Метод входит в `methods`, и попытка не получила ответа, получила 502, 503 или 504 либо исчерпала `attemptTimeoutMs`. Любой другой статус передаётся `shouldRetry` с `retryable: false`. Локальные сбои до старта Fetch до него не доходят. |
| SSE       | Метод входит в `methods`, и хэндшейк не удался по сети, хэндшейк ответил 502, 503 или 504, попытка исчерпала `attemptTimeoutMs`, либо открытый поток не удался по сети. Обычное завершение потока никогда не повторяется.                  |
| WebSocket | Каждое закрытие, которого не запрашивал `session.close()`, включая соединение, которое так и не открылось, и heartbeat без ответа.                                                                                                         |

Для SSE поле `retry:` сервера, состоящее только из цифр, заменяет `delayMs` для последующих попыток, зафиксированный ID события отправляется байтами UTF-8 в `Last-Event-ID`, а успешный хэндшейк сбрасывает счётчик. Для WebSocket успешный `open` сбрасывает счётчик. Сервер, который принимает соединение и сразу его закрывает, поэтому продолжает повторяться; остановите это через `shouldRetry`. У SSE и WebSocket нет бюджета. Офлайн-сбои HTTP никогда не повторяются.

Бюджет HTTP принадлежит клиенту и устроен в стиле Finagle. По умолчанию это 20 % плюс резерв 10 повторов в секунду на TTL 10 с, кредиты и списания лениво истекают в десяти срезах по TTL/10, а `budget: false` снимает лимит. Производные клиенты с одной конфигурацией делят её бюджет; разные клиенты — нет, даже с одним общим балансировщиком. Если раунд повтора не может использовать ни один эндпоинт (выбор балансировщика не удался или URL следующего эндпоинта не разрешается), вызов возвращает сбой предыдущей попытки. Сигнал вызывающего покрывает весь вызов, включая ожидания backoff. Опция запроса `retry` заменяет политику для одного вызова. У балансировщиков и обёрток здоровья нет настроек повтора. См. [Балансировка нагрузки и отказоустойчивость](/ru-RU/docs/load-balancing).

### Balancer

<ApiSignature name="Balancer, PickOutcome, PickInfo, PickResult, PickFaultCode, DoneInfo, ERR_NO_CANDIDATE, isNoCandidateCause" />

`pick` возвращает кортеж error-first. Необязательный `start` выполняется синхронно не больше одного раза непосредственно перед стартом выбранного транспорта; необязательный `end` выполняется один раз после `start` когда начинается ответ узла (или при сбое до ответа), а необязательный `done` — один раз при завершении. Fetch не может показать первый body-frame Linkerd или границы стрима Envoy. Броски всех хуков сдерживаются и сообщаются через `reportError` там, где среда выполнения его определяет (необработанный отчёт может завершить процесс Bun или Deno, у которого нет обработчика ошибок); возвращённый промис не ожидается. `ERR_NO_CANDIDATE` — только `cause` у `REQ_BUILD_FAILED`. Это не `FaultCode`. [`isNoCandidateCause`](/ru-RU/api/core/isnocandidatecause) распознаёт его и из другой копии Core.

Балансировщик видит только нейтральные исходы; каждый транспорт переводит свои факты в `DoneInfo.code`. Обнаружение выбросов по умолчанию считает сбоем любой исход с кодом, включая `NET_TIMEOUT` и `NET_BODY_INCOMPLETE`. Сырой `DoneInfo.status` сохраняется только для пользовательских балансировщиков, и встроенные стратегии его не читают. `PickInfo` содержит кандидатов `endpoints` для одного выбора, `members` (полный список эндпоинтов клиента, одинаковый для всех попыток) и необязательный `meta`, без дискриминатора транспорта.

См. [руководство по клиенту](/ru-RU/docs/client).
