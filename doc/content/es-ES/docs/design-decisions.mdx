# Arquitectura central

Defjs se construye sobre una frontera fundamental: **el SDK define el contrato de red; la aplicación consumidora es dueña de la ejecución.** Cada una de las reglas de diseño en `@defjs/core` se deriva de esta separación.

## 1. Definición frente a ejecución

Un paquete de SDK exporta operaciones (`defineRequest`, `defineEventStream`, `defineWebSocket`) y contratos de datos (`struct`). Nunca llama a `createClient`, no guarda clientes singleton ni lee variables de entorno.

<Tabs items={["sdk/orders.ts", "app/consumers.ts"]}>
<Tab value="sdk/orders.ts">

```ts
import { defineRequest, struct } from "@defjs/core";

export const Order = struct.object({
  id: struct.number(),
  status: struct.string(),
});

export const getOrder = defineRequest({
  method: "GET",
  path: "/orders/:id",
  operation: "orders.read",
  input: struct.object({ id: struct.number() }),
  builder: (input) => ({ path: input }),
  output: Order,
});
```

Dado que `getOrder` no captura ningún estado del cliente:

- Una interfaz de navegador, una tarea en segundo plano, un manejador de peticiones en SSR y una prueba unitaria pueden invocar la misma definición `getOrder` con diferentes configuraciones de `Client`.
- Los plugins para frameworks (`@defjs/react`, `@defjs/vue`) y el middleware de observabilidad (`@defjs/opentelemetry-server`) se conectan al `Client` de la aplicación, manteniendo el paquete publicado del SDK completamente libre de dependencias.

## 2. Ubicación explícita de entradas y alias bidireccionales

En Defjs, `input` declara lo que pasa quien llama, `struct` controla cómo se codifican y decodifican los valores, y `builder` coloca cada valor en la petición (`path`, `query`, `headers`, `body`).

- **Sin inferencias mágicas**: si una operación declara `input`, debe proporcionar un `builder` explícito, síncrono y puro. La ubicación de los campos nunca se deduce a partir de nombres de parámetros.
- **`.alias(wireName)` bidireccional**: declarar `.alias("customer_name")` en un campo del struct mantiene `customerName` en TypeScript mientras mapea automáticamente hacia y desde `"customer_name"` en la red.

Cuando el builder pasa un objeto struct tipado a `body`, `query` o `headers`, sus alias de campo y códecs de `Date` / `bigint` se aplican automáticamente. Las claves que escribas en un objeto contenedor anónimo (como `account_id` o `x-api-version` en el ejemplo anterior) se mantienen literales.

## 3. Declarar es asegurar [#declaration-is-an-assertion]

Seis reglas estrictas rigen cómo lee Defjs las respuestas HTTP:

### Regla 1: Lo que declaras es lo que aseguras

`output` asegura la forma del cuerpo en respuestas `2xx`. `error` asegura la forma del cuerpo en respuestas no `2xx`. Una declaración es una garantía en tiempo de ejecución, no una simple sugerencia.

### Regla 2: `ok` (`200..299`) es la única bifurcación

Una respuesta `2xx` se decodifica únicamente con `output`. Cualquier otro código de estado (`3xx`, `4xx`, `5xx`) se decodifica únicamente con `error`. Defjs nunca recurre de una opción a la otra como alternativa.

### Regla 3: Cualquier desviación respecto a lo declarado es un fallo explícito

Si se declara un `output` en JSON, una pasarela que devuelva una página de error en HTML o JSON malformado provocará un fallo inmediato (`RES_MEDIA_TYPE_INVALID` o `RES_DECODE_FAILED`). Para representaciones JSON, la cabecera `Content-Type` se verifica **antes** de leer los bytes del cuerpo.

| Qué falló durante la lectura de la respuesta                      | Fallo devuelto                                                     |
| ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| El tipo de medio no coincide con la representación JSON declarada | `RES_MEDIA_TYPE_INVALID` (el cuerpo nunca se lee)                  |
| Los bytes no pueden decodificarse según lo declarado              | `RES_DECODE_FAILED`                                                |
| El valor decodificado no supera la validación del `struct`        | `RES_STRUCT_MISMATCH` (HTTP) / `RES_DECODE_FAILED` (handshake SSE) |
| Código no `2xx` con struct de `error` decodificado                | `HTTP_STATUS` con `error.data` tipado                              |
| Código no `2xx` habiendo omitido `error`                          | `HTTP_STATUS` con `error.data: undefined`                          |

### Regla 4: Una decodificación fallida no tiene cuerpo

Un cuerpo solo existe tras haber superado la decodificación y la validación. Cuando la decodificación falla, la propiedad `response` del fallo está tipada como `HttpMeta` (que carece de la propiedad `body`), y el error de análisis o validación se adjunta en `fault.cause`.

### Regla 5: Omitir una parte descarta su lectura

Omitir `output` significa que los cuerpos `2xx` nunca se leen. Omitir `error` significa que los cuerpos no `2xx` nunca se leen, incluso si el servidor envió un JSON no válido junto a un `500`.

### Regla 6: `3xx` no es un estado de éxito

`ok` significa `200 <= status < 300`. Un `304 Not Modified` no es `2xx`: deja `error` sin declarar y maneja `HTTP_STATUS` (o intercepta `304` en un interceptor ETag), o declara `struct.string()` cuando esperes un cuerpo de texto vacío.

## 4. Tuplas de resultado específicas de cada transporte

Los tres transportes devuelven una tupla de tres elementos con el error en primer lugar en vez de lanzar excepciones en el punto de llamada:

- **HTTP** → `[error, data, response]` — carga decodificada + `DecodedResponse<T>` (`HttpMeta` cuando se omite `output`).
- **SSE** → `[error, stream, open]` — `EventStreamHandle` + instantánea del handshake inicial.
- **WebSocket** → `[error, session, connection]` — `WebSocketSession` + instantánea de conexión inicial.

Los clientes almacenan configuración, no conexiones activas. Quien inicia una petición HTTP, flujo SSE o sesión WebSocket es responsable de cancelarla o cerrarla (`AbortSignal` para HTTP; `await using` o `.close()` + `await .closed` para SSE y WebSocket).
