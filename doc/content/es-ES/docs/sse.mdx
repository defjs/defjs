# Flujos de eventos SSE

Un SDK declara un endpoint de Server-Sent Events con `defineEventStream`, indicando la ruta, entrada y builder opcionales, un diccionario `events` de structs y límites de búfer y cola. La aplicación consumidora configura la autenticación y la reconexión opcional en su cliente, abre el flujo, itera sobre los eventos tipados y se encarga de cerrarlo.

## 1. Definir el flujo de eventos y consumirlo

Libera siempre un `EventStreamHandle` abierto mediante `await using` (o con `stream.close()` + `await stream.closed` en un bloque `finally`):

<Tabs items={["sdk/orders-stream.ts", "app/watch-orders.ts", "Single-file quick look"]}>
<Tab value="sdk/orders-stream.ts">

```ts
import { defineEventStream, struct } from "@defjs/core";

export const watchOrders = defineEventStream({
  path: "/orders/events",
  operation: "orders.watch",
  events: {
    updated: struct.object({
      id: struct.number(),
      status: struct.string(),
    }),
  },
});
```

</Tab>
<Tab value="app/watch-orders.ts">

```ts
import { createClient, withEndpoint } from "@defjs/core";
import { watchOrders } from "../sdk/orders-stream.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
  const [error, stream] = await watchOrders(client);
  if (error) {
    console.error(error.code);
    return;
  }

  await using active = stream;
  for await (const event of active) {
    console.log(event.event, event.data.id, event.data.status);
    break;
  }
}

void main();
```

## 2. Handshake inicial y estructura de la tupla

Llamar a la operación resuelve `[error, stream, startupOpen]` solo después de que la respuesta HTTP inicial sea `2xx`, tenga tipo de medio `text/event-stream` y posea un cuerpo legible:

- **Handshake no `2xx`**: devuelve `HTTP_STATUS` (con `error.data` decodificado cuando se declara un struct de `error` en la definición).
- **Tipo de contenido incorrecto o cuerpo ilegible**: devuelve `RES_MEDIA_TYPE_INVALID` o `RES_DECODE_FAILED`.
- **`startupOpen` frente a `stream.open`**: el tercer elemento de la tupla (`startupOpen`) captura la respuesta del handshake inicial; `stream.open` se actualiza dinámicamente si el flujo se reconecta más adelante.

## 3. Despacho y decodificación de eventos

Cuando llega una trama SSE (delimitada por una línea en blanco según la especificación WHATWG):

1. **Enrutamiento de eventos**: el campo de red `event:` selecciona `events[eventName]`, recurriendo a `events.default` si se declaró. Si el campo `event:` se omite, se asume `"message"`. Los eventos no declarados sin `events.default` se descartan.
2. **Decodificación de la carga**: un esquema `struct.string()` recibe el texto sin procesar de `data:`. Cualquier otro tipo de struct analiza primero `data:` como JSON y luego lo valida contra el struct.
3. **Observar eventos no válidos**: los eventos no válidos o no declarados se descartan sin interrumpir el flujo. Conecta `withSSEOnInvalidEvent(...)` en el cliente para diagnósticos controlados:

## 4. Reconexión y `Last-Event-ID` [#reconnect]

La reconexión SSE es **opcional (opt-in)**. Sin `withSSEReconnect(...)`, cualquier caída de red o error de lectura da por terminado el flujo.

<include cwd>examples/sse/reconnect.ts#example</include>

- **Presupuesto de reintentos (`attempts`)**: por defecto es `3` cuando se pasa un objeto de opciones a `withSSEReconnect`. Un handshake exitoso restablece el contador de intentos y el exponente del backoff. Un fin de fichero normal del servidor (EOF) **no** es un fallo y no activa la reconexión.
- **Seguimiento del cursor (`Last-Event-ID`)**: se confirma cuando se procesa la línea en blanco que termina el evento y se envía automáticamente como `Last-Event-ID` en la reconexión.
- **Seguridad e idempotencia**: por defecto, solo los métodos idempotentes (`GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`) se reconectan automáticamente. Los métodos no idempotentes (`POST`, `PATCH`, como en peticiones de streaming de LLMs) solo se reconectan cuando un callback personalizado `shouldReconnect` devuelve explícitamente `true`. Cuerpos de petición con `ReadableStream` se consumen en el primer intento y nunca se reconectan.
- **Tiempo límite del handshake (`connectTimeoutMs`)**: limita cada handshake desde la invocación de Fetch hasta las cabeceras de respuesta, sin limitar el tiempo que un flujo establecido puede permanecer abierto.

## 5. Límites de búfer y cola

Ambos límites deben ser enteros seguros positivos. Superar cualquiera de ellos es fatal (`stream.closed` se resuelve con `kind: "error"` y el iterador rechaza; los eventos nunca se descartan en silencio):

| Opción en la definición | Qué limita                                                  | Código de fallo terminal |
| ----------------------- | ----------------------------------------------------------- | ------------------------ |
| `maxBufferSize`         | Bytes de tramas SSE incompletas o excesivas antes del salto | `CAP_BUFFER_EXCEEDED`    |
| `maxQueueSize`          | Eventos validados esperando al consumidor del `for await`   | `CAP_QUEUE_OVERFLOW`     |

## 6. Cierre y liberación de recursos [#close-and-dispose]

Quien abre un flujo es responsable de su limpieza. Salir de un bucle `for await` con `break`, `return` o una excepción cierra automáticamente el flujo, o puedes usar `await using` / `stream.close()`:

Para limitar solo el handshake de conexión inicial sin cancelar un flujo ya abierto, limpia el temporizador una vez que `await watchOrders(...)` retorne (como se muestra en la segunda pestaña superior) o usa `connectTimeoutMs` en `withSSEReconnect`.
