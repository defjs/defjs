# Server-Sent Events

Un SDK exporta una operación de event-stream con entrada, contratos de evento y límites de búfer. Las aplicaciones configuran la autenticación y la reconexión opcional en sus propios clientes, y llaman a la operación importada cuando necesitan un stream.

Abre un stream, itéralo y libera el handle propio con `await using`. Siguen disponibles `close()` y `closed` manuales; los clientes y los plugins no disponen por ti un stream devuelto.

## Definir el stream

`defineEventStream(...)` necesita `events` y un `path` relativo. El método es `GET` por defecto. La llamada copia los campos de definición conocidos. El contenedor del diccionario `events` se copia con sus propiedades propias, incluidas las no enumerables y una propiedad `__proto__` definida mediante un nombre de propiedad calculado. Los nombres heredados no se copian. Los valores struct siguen siendo los mismos objetos. Un accessor de ese diccionario sigue ejecutándose cuando llega un mensaje, con el diccionario original como `this`. Un diccionario ausente se deja tal como se dio y se sigue informando cuando se resuelve un evento.

La forma de la solicitud coincide con HTTP: `builder` que devuelve `path`, `query`, `headers` y `body`. `GET` / `HEAD` no pueden devolver un body. Un struct `error` declarado tipa el fault de arranque y decodifica un cuerpo de handshake no-2xx según el kind del struct (`string` texto, `blob` / `file` blob, `arrayBuffer` bytes, si no JSON). Defjs envía `Accept: text/event-stream` cuando tú no pusiste ya `Accept`. Un `input` declarado exige siempre un `builder` explícito. `input` solo define los parámetros; solo el builder decide dónde va cada valor. Solo las definiciones sin `input` pueden omitir `builder`. Un cuerpo `ReadableStream` sigue las reglas de HTTP: en un runtime que no puede hacer stream de cuerpos de solicitud, como Firefox, el arranque falla con `ENV_UNSUPPORTED` antes de enviar nada. En Chromium necesita HTTP/2 o posterior; sobre HTTP/1.1 el arranque falla con `NET_UNREACHABLE`. Un cuerpo stream se envía una vez y nunca se reconecta (consulta Reconexión).

Un stream lógico puede abarcar varios intentos Fetch físicos **cuando** activas la reconexión. Sin `withSSEReconnect`, los fallos transitorios de red y de lectura del stream terminan el stream lógico. Sigues obteniendo un handle y un iterador async cuando la apertura tiene éxito.

## Abrir e inspeccionar

La operación se resuelve solo después de que pasen las comprobaciones de estado, content-type y cuerpo:

<include cwd lang="typescript">
  examples/sse/open-and-inspect.ts#example
</include>

La respuesta debe ser correcta, con esencia de media type `text/event-stream`, y tener un cuerpo. Un arranque no-2xx → `HTTP_STATUS`. Cuando se declara `error`, ese fault lleva el cuerpo de handshake decodificado; un media type malo es `RES_MEDIA_TYPE_INVALID` y un cuerpo que no se puede leer como el kind declarado es `RES_DECODE_FAILED`. Una instantánea de respuesta puede seguir en el tercer hueco de la tupla cuando la validación falla después de que llega la respuesta.

Un endpoint base ausente, relativo o no válido, o un path ilegal, falla con `REQ_BUILD_FAILED` durante la construcción, antes de cualquier interceptor o transporte, incluso si un interceptor cortocircuitaría. La URL resuelta debe conservar el origen base y permanecer bajo su directorio; se rechazan caracteres de control C0 (incluidos tab, CR y LF), barras invertidas, `?`, `#` y escapes de directorio en el path. Las formas similares a un esquema y las relativas al protocolo se rechazan incluso con espacios iniciales; se permite un espacio ordinario en el interior y se envía como `%20`. El `req.endpoint` final de un interceptor se comprueba contra su `req.baseEndpoint` final con la misma regla; sustituir deliberadamente la base por otra URL absoluta válida está permitido. Los errores de URL deterministas nunca se reintentan.

`startupOpen` es la instantánea inicial de esa llamada; una llamada nueva nunca reutiliza la instantánea de una llamada anterior, aunque falle antes de que llegue una respuesta. `stream.open` está en vivo y cambia en aperturas físicas posteriores. Conserva el valor de la tupla cuando importa la primera respuesta. `startupOpen` es la instantánea del primer handshake correcto de la conexión devuelta solo para un handle nativo de Defjs o un wrapper que reenvía el mismo objeto `open` en vivo; los handles personalizados y los wrappers que sustituyen `open` conservan su `open` público actual incluso después de reconectar, así que un `closed` compartido no puede saltarse la sanitización de URL ni el filtrado de cabeceras, y Defjs no reconstruye los metadatos del primer handshake a partir de transformaciones arbitrarias.

## Decodificar eventos

Nombre de evento de cable → `events[eventName]`; si no, `events.default`. Sin Struct coincidente → el evento no se entrega. Si falta el campo SSE `event` → el nombre lógico es `message`.

El `data` de SSE empieza como texto. Un struct `string` conserva ese texto. Cualquier otro kind es JSON: parsea el texto y luego decodifica con el struct. `struct.object`, `struct.number`, `struct.boolean`, `struct.any` y `struct.unknown` son JSON, no texto recortado. Un token desnudo como `ping` no satisface `struct.literal('ping')`; los datos tienen que ser JSON. Un servidor que envía el string JSON `"abc"` sigue satisfaciendo `struct.string()`: el valor entregado es ese texto en bruto, comillas incluidas, y no se decodifica como JSON a `abc`.

El parseo sigue las reglas de línea y de campo SSE de WHATWG: CR, LF y CRLF terminan las líneas; una línea en blanco despacha un evento que lleva data; varias líneas `data:` se unen con `\n`. Los comentarios y los campos desconocidos se ignoran, y un evento inacabado en EOF no se despacha. Solo se quita un BOM UTF-8 inicial al principio de cada stream físico. U+FEFF dentro de valores `data` o `id` se conserva; un nombre de campo posterior con prefijo BOM, como `﻿data`, es desconocido y se ignora.

Valor emitido: `event`, `data` decodificado, `id` opcional no vacío. Con `default`, los nombres de evento desconocidos son `string` en la unión inferida.

## Observar eventos inválidos

Los eventos inválidos o no declarados se descartan, no se encolan. `withSSEOnInvalidEvent(...)` puede observar el ID en bruto, el nombre, los datos de texto, más `missing-struct` o `validation-failed` y una cause opcional.

El observador corre en el límite de transformación. Su fallo queda aislado salvo que el signal del intento activo esté abortado. Mantenlo corto; no trates los datos de evento en bruto como de confianza.

## Reconexión

Pon `connectTimeoutMs` dentro de la política de reconexión para acotar cada handshake desde la invocación de Fetch hasta las cabeceras de respuesta. Debe ser finito y positivo; los valores no válidos devuelven `REQ_OPTIONS_INVALID`. No tiene valor por defecto y se borra después del handshake, así que las sesiones establecidas no se ven afectadas. Un handshake que expira informa `NET_UNREACHABLE` al balanceador y sigue el presupuesto de reconexión existente; los reintentos agotados terminan con `NET_TIMEOUT`.

**Cambio de comportamiento:** la reconexión SSE es opt-in. Sin `withSSEReconnect(...)`, los fallos de red y de lectura del stream **no** se reintentan (igual que `attempts: 0`). Pasa `withSSEReconnect({ attempts: 3 })` (u otro presupuesto revisado) para reintentar esos fallos. Un EOF normal no se reintenta. Para una suscripción en curso, observa `stream.closed` y empieza una operación nueva con el último cursor de la aplicación; la reconexión no convierte el EOF en una suscripción sin fin. La validación de estado/content-type, los límites del parser, los fallos de transformación de mensajes, el desbordamiento de cola y el EOF normal siguen siendo terminales para el stream lógico.

<include cwd>examples/sse/reconnect.ts#example</include>

`attempts` es el presupuesto de reintento de cada interrupción; vale `3` por defecto cuando hay un objeto de reconexión. Un handshake correcto reinicia el presupuesto, el intento del callback y el exponente de backoff, así que las interrupciones distintas no gastan un presupuesto de por vida. `attempts: 0` desactiva el reintento. Omitir `withSSEReconnect` también lo desactiva. `delayMs` es el intervalo inicial (por defecto `1000`); `factor` lo hace crecer (por defecto `1`, un retraso constante); `maxDelayMs` es un tope duro del retraso final, después del jitter y el redondeo (por defecto: sin tope configurado). El `jitter` de SSE es un **factor multiplicativo 0–1**, igual que en WebSocket. El límite de temporizador de la plataforma es `2_147_483_647` ms incluso sin tope configurado. Una base cero se queda en cero; el desbordamiento de números por lo demás válidos se satura en los topes. Un campo `retry:` del stream que sea solo dígitos actualiza el intervalo base actual, también después de recuperarse. Que el callback de política devuelva false, lance o rechace termina el stream lógico. Aperturas correctas repetidas seguidas de inmediato por fallos de stream reintentables pueden seguir reconectando al retraso base actual (sujeto a jitter y topes), porque cada apertura reinicia el presupuesto; usa `shouldReconnect` para detenerlas. El EOF normal sigue siendo terminal.

Las opciones de reconexión se comprueban antes de los interceptores o de Fetch: `attempts` debe ser un entero seguro no negativo; `delayMs` debe ser finito y no negativo; `maxDelayMs` debe ser un número finito no negativo o `Infinity` positivo, que quita el tope configurado pero no el límite de plataforma de `2_147_483_647` ms; `factor` debe ser finito y positivo; `jitter` debe ser finito y estar entre 0 y 1. Los valores inválidos devuelven `REQ_OPTIONS_INVALID` sin abrir un stream.

Un campo `id:` solo actualiza un búfer; el cursor de reconexión se confirma únicamente al procesar la línea vacía final, incluso en una trama que solo contiene un ID y no entrega ningún mensaje. Si el stream termina antes de esa línea vacía, el cursor no cambia. El ID confirmado se convierte en `Last-Event-ID` en un intento posterior, codificado como bytes UTF-8 en el cable, incluidos los ID no ASCII. Un `id:` vacío borra la cabecera en esa línea vacía; un ID que contiene NUL se ignora. Aparte de esa cabecera, un intento posterior reenvía la solicitud construida para el primero: el builder y los interceptores corren una vez por llamada, así que el método, la URL, las cabeceras y el cuerpo se quedan igual. Una cabecera que deba ser fresca en cada intento, como un token de corta duración, va en el Fetch pasado a `withSSEHandle`, que corre una vez por intento. Si una credencial sigue caducando, un handshake de reconexión no-2xx después de que el stream se ha abierto lo termina con `RES_DECODE_FAILED`; inspecciona `stream.open.response.status` para el estado. Un handshake inicial no-2xx devuelve en cambio un fault de arranque `HTTP_STATUS` cuando su cuerpo de error declarado decodifica.

La reconexión reenvía una solicitud solo cuando eso es seguro:

- `GET`, `HEAD`, `OPTIONS`, `PUT` y `DELETE` son idempotentes (RFC 9110 §9.2.2) y reconectan dentro del presupuesto.
- Cualquier otro método, como `POST` o `PATCH`, reconecta solo cuando `shouldReconnect` devuelve `true`. Una conexión fallida no puede decir si el servidor ya actuó: un `POST` que arranca una generación de LLM volvería a ejecutarse, y a cobrarse, y sus eventos nuevos seguirían a los viejos en el mismo stream. Pasar `shouldReconnect` sustituye este valor por defecto para todos los métodos, así que comprueba `method` en su contexto cuando un cliente sirve a los dos kinds de endpoint.
- Un cuerpo `ReadableStream` lo consume el primer intento. Cualquier fallo, antes o después de que el stream se abra, termina el stream con el error original; no se llama a `shouldReconnect` y no se gasta ningún retraso. Usa un string, bytes, `Blob`, formulario o cuerpo JSON cuando la solicitud deba reconectar.

## Límites de búfer y de cola

Los dos deben ser enteros seguros positivos. El desbordamiento es fatal — no hay descarte silencioso de eventos más viejos.

| Límite          | Protege                                                         | Código terminal       |
| --------------- | --------------------------------------------------------------- | --------------------- |
| `maxBufferSize` | Línea/evento SSE incompleto o demasiado grande al parsear       | `CAP_BUFFER_EXCEEDED` |
| `maxQueueSize`  | Eventos producidos más rápido de lo que lee el único consumidor | `CAP_QUEUE_OVERFLOW`  |

Un stream fatal también limpia los eventos en búfer, cancela el cuerpo activo, rechaza el iterador y resuelve `stream.closed` con `kind: 'error'`.

## Cierra y dispone [#close-and-dispose]

`EventStreamHandle`: una instantánea de apertura en vivo, una promesa terminal, un `close`, un iterador async y un disposer async estándar.

<include cwd lang="typescript">
  examples/sse/close-and-dispose.ts#example
</include>

Kinds terminales (`closed.kind`): `eof`, `aborted` o `error`. Un resultado `error` también lleva `closed.code`, un `EventStreamFaultCode`: `CAP_BUFFER_EXCEEDED`, `CAP_QUEUE_OVERFLOW`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `REQ_BUILD_FAILED`, `REQ_OPTIONS_INVALID`, `RES_DECODE_FAILED` o `RES_MEDIA_TYPE_INVALID`. `REQ_BUILD_FAILED` y `REQ_OPTIONS_INVALID` significan que un pick de reconexión falló después de abrir el stream. No se reescriben a `NET_UNREACHABLE`.

`close(reason)` aborta el intento activo, cierra la cola y se asienta como `aborted`, incluso cuando el motivo es un `TimeoutError`. El `signal` pasado a la operación sigue enganchado después de que el stream está abierto y cubre toda la conexión. Abortarlo con normalidad termina el iterador e informa `aborted`. Si el motivo del abort es un `TimeoutError` o `ERR_TIMEOUT` (por ejemplo `AbortSignal.timeout(...)`), el iterador lanza `ERR_TIMEOUT` y `closed` informa `kind: 'error'` con `code: 'NET_TIMEOUT'`. No hay un plazo solo de arranque en el cliente. Una aplicación que quiera uno crea su propio `AbortController`, lo aborta con `new DOMException("...", "TimeoutError")` desde un temporizador y limpia el temporizador cuando el await regresa:

<include cwd>examples/sse/startup-deadline.ts#example</include>

Un `break` / `return` / throw del bucle invoca el return del iterador y cierra con `iterator-return`. El código que arranca la operación es dueño del cierre.

`await using` llama al mismo camino de cierre propio y espera hasta que el trabajo de lectura/reconexión de Defjs se ha detenido y se ha soltado el lock del reader activo. Está acotado a propósito alrededor de una promesa `ReadableStream.cancel()` controlada por el proveedor que nunca se asienta, así que no garantiza que esa promesa del proveedor haya terminado. `stream.close(reason)` explícito más `await stream.closed` sigue siendo válido cuando necesitas un motivo o el resultado terminal.

Las implementaciones estructurales personalizadas de `EventStreamHandle` deben aportar `[Symbol.asyncDispose](): PromiseLike<void>` y conectarlo al mismo ciclo de vida.

El conjunto mínimo de lib admitido es `ES2022`, `ESNext.Disposable`, `DOM` y `DOM.Iterable`. El tooling de declaraciones del repositorio usa TypeScript 7, pero no hay una puerta automática de verificación del consumidor empaquetado ni de la lib mínima, y no se prometen compiladores más viejos. Este conjunto aporta tipos, no polyfills de Web API en runtime. Un `Client` no es `AsyncDisposable`; gestiona cada solicitud con su `AbortSignal`.

Mantén credenciales, datos de evento, ID de evento, causes y URL de stream fuera de los logs rutinarios. `withCredentials(true)` afecta a las cookies de Fetch para SSE; no configura la auth de WebSocket.
