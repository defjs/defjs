# Primeros pasos: tu primera operación de SDK [#getting-started-one-http-request]

Escribirás dos archivos: un módulo de SDK que exporta `GET /orders/:id` y una aplicación que lo importa y es dueña del cliente. El handle Fetch local mantiene la primera ejecución sin red. La misma definición de API funcionará después con un cliente apuntando a tu servicio.

## Práctica recomendada

Una definición permanece independiente del cliente. Llama a la operación con el cliente de la aplicación, como en `getOrder(client, { id: 7 })`. No hay un tercer argumento de opciones. Llamar a la operación la arranca; `await` solo espera. La aplicación también es dueña de la dirección del servicio y de las credenciales. Inspecciona primero la tupla error-first. Si `error` está presente, informa `error.code` y sal de la función antes de leer el valor de éxito.

## Paso 1 — Instalar

`@defjs/core` es ESM y funciona en Node.js o Bun. Node.js 22.18+ (o 24+) ejecuta el archivo `.ts` directamente mediante type stripping; las versiones 22.x anteriores necesitan `--experimental-strip-types`. Mantén `"type": "module"` en package.json. En el navegador sigues necesitando tu bundler y Fetch.

```sh
bun add @defjs/core
```

## Paso 2 — Definir la solicitud

Crea `src/define-request.ts`. Este es el módulo del autor del SDK: exporta `getOrder` sin crear un cliente. El struct de entrada es el valor de quien llama. `builder` coloca ese valor en la solicitud. Aquí toda la entrada es el objeto de path, así que los campos escalares sin alias rellenan `:id`.

<include cwd meta="define-request.ts">
  examples/start/define-request.ts#example
</include>

`output` es el cuerpo 2xx. `error` es cualquier otro estado. Un struct cada uno. Usa `struct.or(...)` o una unión discriminada cuando esos cuerpos difieran.

`defineRequest(...)` devuelve una operación. Llamar a `getOrder(client, input)` arranca la solicitud. El `builder` de arriba es la función que coloca el input; no es la operación. Donde se declara `input`, `builder` es obligatorio, síncrono y puro.

## Paso 3 — Llámalo en local

Crea `src/execute-locally.ts` junto a la definición. Esta es la aplicación consumidora: importa `getOrder`, crea su propio cliente y aporta un handle Fetch local. Defjs sigue validando la entrada, construyendo el `Request`, despachando por estado y parseando el cuerpo.

<include cwd meta="execute-locally.ts">
  examples/start/execute-locally.ts#example
</include>

Ejecútalo:

```sh
bun src/execute-locally.ts
```

```txt
Loaded paid from 200
```

Prueba un pedido que falta — cambia el id del path a `8` y vuelve a ejecutar:

```txt
Order not found
```

En éxito: `error` es `null`, `order` es la salida Struct del `200`, `response` es un `DecodedResponse<Order>`. En un `404` declarado: `error.code` es `'HTTP_STATUS'`, `error.status` es `404` y `error.data` está tipado como `NotFound`. El segundo elemento de la tupla es `undefined` en fallo.

## Paso 4 — Apuntar a una API real

En `src/real-api.ts`, importa el mismo `getOrder` y crea un cliente con la URL base de tu servicio. Ejecuta esta versión solo después de sustituir la dirección de ejemplo por un servicio que implemente `GET /v1/orders/:id` con esos cuerpos.

<include cwd>examples/start/real-api.ts#example</include>

La definición de API se queda en el módulo del SDK. Las direcciones del servicio, las credenciales, los interceptores y el tiempo de vida de la ejecución se quedan en la aplicación. Los dos clientes usan el mismo contrato de endpoint de Defjs.

## Publica la definición

Mueve la definición a un paquete de SDK cuando más aplicaciones la necesiten. Exporta `getOrder`, incluye sus declaraciones de TypeScript y declara la versión compatible de Core. Los consumidores importan entonces desde el paquete en lugar de `./define-request.ts`; la configuración de su cliente sigue siendo suya. Sigue [Crear y publicar un SDK](/es-ES/recipes/publish-http-sdk) para el montaje completo del paquete.

## Cuando el resultado cambia

- Entrada mala → `REQ_INPUT_INVALID`; un `builder` que falla → `REQ_BUILD_FAILED`
- Un estado no-2xx → `HTTP_STATUS`, con `error.data` tipado cuando se declaró `error` y su cuerpo decodifica
- Un cuerpo JSON declarado con otro media type → `RES_MEDIA_TYPE_INVALID`, avisado antes de leer el cuerpo
- Un cuerpo declarado (`output` para 2xx, `error` en el resto) que no decodifica → `RES_DECODE_FAILED` o `RES_STRUCT_MISMATCH`, sea cual sea el estado
- Fallo de Fetch / cancelación / plazo → `NET_UNREACHABLE` / `NET_ABORTED` / `NET_TIMEOUT`

Un plazo es `client({ signal: AbortSignal.timeout(ms) })` y se clasifica como `NET_TIMEOUT`. Un abort manual es `NET_ABORTED`. No hay un plazo por defecto a nivel de cliente. Deriva un cliente cuando una llamada necesita su propio `signal`; consulta [Cliente](/es-ES/docs/client). La cancelación te dice lo que vio quien llama — no si una escritura en el servidor se confirmó.
