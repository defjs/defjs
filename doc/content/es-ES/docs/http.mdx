# Operaciones HTTP

Un SDK define cada operación HTTP con `defineRequest`: su método, plantilla de ruta, esquema de `input`, `builder` síncrono y los esquemas de respuesta `output` / `error`. Las aplicaciones consumidoras importan la operación, pasan su `Client` configurado y tratan la tupla devuelta `[error, data, response]`.

### Buenas prácticas en el diseño de SDKs

- **Una operación por definición**: mantén cada método, ruta y contrato en su propia definición para que las aplicaciones puedan aplicar _tree-shaking_ a las operaciones que no usen.
- **Asigna un nombre estático a `operation`**: utiliza un identificador de baja cardinalidad como `"orders.read"`. Los plugins de telemetría (`@defjs/opentelemetry-server`) y los interceptores de registro lo usarán sin filtrar URLs ni identificadores de usuario.
- **Nunca incrustes un cliente en el SDK**: exporta únicamente definiciones, esquemas `struct` y tipos.

## 2. Resolución de URLs y parámetros de ruta

`withEndpoint(...)` requiere una URL absoluta válida. Su pathname actúa como directorio base (cualquier query string o hash en el endpoint base se descarta).

<include cwd>examples/http/resolve-url.ts#example</include>

- **Marcadores de posición en la ruta (`:name`)**: se codifican exactamente una vez como un único segmento de ruta. Las barras, `?`, `#`, `%`, los espacios y caracteres Unicode permanecen dentro de ese segmento; no codifiques los valores de antemano. Cadenas vacías, `.` y `..` fallan con `REQ_BUILD_FAILED`.
- **Confinamiento de origen y directorio**: las rutas de definición no pueden ser URLs absolutas, relativas al protocolo (`//...`), ni contener caracteres de control C0, barras invertidas, `?`, `#`, ni escapar del directorio del endpoint base (`../`). Cualquier infracción falla con `REQ_BUILD_FAILED` antes de que se ejecuten interceptores o transportes.

## 3. Ubicar entradas con `builder`

Siempre que una operación declare `input`, **debe** proporcionar un `builder` síncrono y puro que devuelva `{ path?, query?, headers?, body? }`. Solo las operaciones sin `input` pueden omitir el `builder`.

### Cómo codifica `builder` los alias de campos

| Expresión en el builder                        | Salida en la red                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| `body: input.profile`                          | Struct tipado: se aplican `.alias()` y códecs de `Date` / `bigint`                    |
| `body: { profile: input.profile }`             | La clave externa `profile` es literal; el objeto interno conserva sus alias de struct |
| `body: { ...input.profile, role: "admin" }`    | El spread preserva los alias del struct; `role` es literal                            |
| `body: { name: input.profile.customerName }`   | Objeto anónimo: las claves son literales                                              |
| `query: input.filter` / `headers: input.trace` | Objetos tipados planos: el `.alias()` del campo se convierte en clave de red          |

### Serialización personalizada de query strings

Por defecto, los escalares de consulta y los arrays escalares (claves repetidas) se codifican directamente, mientras que los objetos anidados en query fallan con `REQ_BUILD_FAILED`. Si tu backend espera sintaxis de objetos anidados (`filter[status]=paid`), configura `withQuerySerializer` en el cliente:

### Formatos del cuerpo de la petición

Las peticiones `GET` y `HEAD` no pueden llevar cuerpo. Para otros métodos, el formato del cuerpo se selecciona a partir del valor devuelto por `builder`:

| Valor devuelto en `body`                                               | Enviado en la red como                           | `Content-Type` predeterminado            |
| ---------------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| `undefined` / omitido                                                  | Sin cuerpo                                       | —                                        |
| Struct raíz con códec `urlencoded` o `formData`                        | `URLSearchParams` / `FormData` (alias aplicados) | Tipo de formulario / límite multipart    |
| `FormData` o `URLSearchParams` nativos                                 | Se pasan tal cual                                | Límite multipart / urlencoded            |
| `Blob` / `File`                                                        | Se pasan tal cual                                | `blob.type` o `application/octet-stream` |
| `ArrayBuffer`, typed array, `DataView`, `ReadableStream`               | Bytes directos / stream                          | `application/octet-stream`               |
| `string`                                                               | Texto UTF-8                                      | `text/plain;charset=UTF-8`               |
| Objeto plano, array, número finito, booleano, `null`, `Date`, `bigint` | JSON codificado con struct                       | `application/json`                       |

Los valores que no pueden representarse en JSON (`NaN`, `±Infinity`, `Map`, `Set`, funciones, instancias de clases sin `toJSON()` o iterables sin procesar) fallan de inmediato con `REQ_BUILD_FAILED` en lugar de serializarse silenciosamente como `{}` o `null`.

## 4. Cómo se decodifican las respuestas

`output` valida las respuestas `2xx`; `error` valida las respuestas no `2xx` (`3xx`, `4xx`, `5xx`). El tipo de struct determina cómo se lee el flujo de la respuesta (`struct.string()` → texto, `struct.blob()` / `struct.file()` → `Blob`, `struct.arrayBuffer()` → `ArrayBuffer`, todo lo demás → JSON):

1. **Seleccionar rama según `ok` (`200..299`)**: `output` para `2xx`, `error` para no `2xx`.
2. **Descarte si se omite**: si no se declara un struct para esa rama, el cuerpo de la respuesta nunca se lee (`2xx` resuelve `data: undefined` + `HttpMeta`; no `2xx` resuelve `HTTP_STATUS` con `data: undefined`).
3. **Verificar primero el tipo de medio JSON**: para structs JSON, un `Content-Type` que no sea JSON falla con `RES_MEDIA_TYPE_INVALID` antes de que el cuerpo se lea o se busque. Una respuesta sin contenido (`HEAD`, `204`, `205`, `304`) se somete a la declaración como cualquier otra.
4. **Leer y analizar**: los flujos ilegibles o JSON malformados fallan con `RES_DECODE_FAILED` (o `NET_BODY_INCOMPLETE` si se truncan a mitad del flujo).
   Una respuesta sin contenido (`HEAD`, `204`, `205`, `304`) no tiene cuerpo que leer: `struct.string()` obtiene `''`, `struct.arrayBuffer()` un `ArrayBuffer` vacío y `struct.blob()` un `Blob` vacío. Un struct JSON que superó el paso 3 analiza los bytes vacíos, lo que falla con `RES_DECODE_FAILED`.
5. **Validar con `struct`**: las discrepancias con el esquema fallan con `RES_STRUCT_MISMATCH`.

## 5. Cancelar el trabajo y definir límites de tiempo [#cancel-the-work]

Pasa la señal `signal` derivando el cliente para cada llamada concreta: `client({ signal })`.

- **Límites de tiempo (`NET_TIMEOUT`)**: utiliza `AbortSignal.timeout(ms)`.
- **Cancelación manual (`NET_ABORTED`)**: utiliza `AbortController`.
- **Señales combinadas**: utiliza `AbortSignal.any([controller.signal, AbortSignal.timeout(ms)])`.

## 6. Credenciales, XSRF y progreso de transferencia

- **`withCredentials(true)`**: establece `credentials: "include"` en Fetch para peticiones HTTP y SSE.
- **`withXSRF(options?)`**: Desde `@defjs/core/xsrf`. En un navegador, lee la cookie de XSRF (`XSRF-TOKEN` por defecto) e inyecta la cabecera (`X-XSRF-TOKEN`) en métodos HTTP mutantes de mismo origen (`POST`, `PUT`, `PATCH`, `DELETE`). `withXSRF()` lanza si faltan `location` o `document`, también en un Worker. El código isomórfico añade esta opción solo en el navegador. Un token de otra fuente se establece con un interceptor. La comprobación de mismo origen se aplica a la URL que construye la biblioteca; Fetch sigue los redirects por su cuenta y conserva esta cabecera tras un redirect a otro origen (solo elimina `Authorization`). Para rechazar eso, consulta [`withXSRF`](/es-ES/api/core/withxsrf).
- **`onDownloadProgress` / `onUploadProgress`**: pásalos en `client({ onDownloadProgress, onUploadProgress })`. El progreso de descarga reporta `lengthComputable: true` solo cuando `Content-Length` es positivo y `Content-Encoding` está ausente o es `identity`. El progreso de subida se informa solo cuando el cuerpo de la petición es un `ReadableStream` que tú pasas; cualquier otro cuerpo (`Blob`, `File`, `ArrayBuffer`, `FormData`, un string, `URLSearchParams`) se envía tal como se construyó y `onUploadProgress` no se llama, en todos los runtimes. Un cuerpo `ReadableStream` sigue las reglas de Fetch para cuerpos de petición en streaming, con o sin `onUploadProgress`: Chromium y WebKit lo aceptan solo sobre HTTP/2 o posterior, así que la llamada falla con `NET_UNREACHABLE` en HTTP/1.1 (Node.js y Bun aceptan HTTP/1.1); Firefox no puede hacer streaming de cuerpos de petición y falla con `ENV_UNSUPPORTED`; en los navegadores, una petición cross-origin necesita un preflight CORS salvo que el navegador conserve un resultado de preflight en caché; y un redirect 301, 302, 307 o 308 falla. Los navegadores no envían `Content-Length`. El balanceador de carga recibe `{ attempted: false }` para estos fallos, y para un stream de origen que lanza, porque `fetch` los informa como el mismo error de red que un endpoint inalcanzable; una subida en streaming por sí sola no puede detectar un endpoint caído. Consulta la entrada `HttpProgressFn` en la referencia de API para los detalles. Si la función de callback de progreso lanza una excepción, la llamada falla con `EXT_OBSERVER_FAILED`.
