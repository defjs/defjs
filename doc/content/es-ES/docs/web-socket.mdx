# WebSocket

Start → receive → send → suelta con `await using`. Tú gestionas el unsubscribe y la liberación. `close()` / `closed` manuales siguen disponibles; clientes, providers e interceptores no cierran sesiones solos.

## Un struct por dirección

`incoming` es un struct para cada frame de texto. `outgoing` es un struct para `session.send(...)`. Modela varios kinds con `struct.discriminatedUnion`. El alias de esos campos es el nombre de cable en ambas direcciones. No hay un envelope de tipo aparte ni un normalizer.

```json
{ "type": "message", "text": "Hello" }
```

Los frames entrantes de texto, `ArrayBuffer`, typed-array y `Blob` se leen como UTF-8, se parsean como JSON y luego se comprueban contra `incoming`. El JSON malformado y los fallos de struct van a `session.onRuntimeError` y no se encolan. La sesión sigue en pie. Los frames que no son texto, bytes o un `Blob` se ignoran. No hay `withWebSocketOnInvalidEvent`.

`session.send(...)` valida y serializa de forma síncrona: encode del struct y luego `JSON.stringify`. Envía de inmediato cuando está open, encola durante `reconnecting` cuando hay cola outgoing habilitada y lanza `InvalidStateError` cuando no es escribible. También lanza cuando no hay struct outgoing, el payload falla el struct, la cola outgoing está deshabilitada o llena, o falla el send nativo. Una lista `protocols` estática en la definición es el contrato del endpoint (por ejemplo `graphql-transport-ws`). Las opciones de execute y `withWebSocketProtocols` aún pueden sobrescribirla. Solo esas opciones eligen subprotocolos: el builder, `beforeConnect` y los interceptores no pueden cambiarlos, así que un token en el subprotocolo se pasa como la opción `protocols` de execute para esa llamada. El builder solo puede devolver `path` y `query`.

`receive` es de un solo consumidor. Pedir un segundo iterador lanza un `TypeError`.

## Snapshots de estado

| Miembro                    | Significado                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| `state`                    | `idle`, `connecting`, `open`, `reconnecting`, `closing`, `closed`, `aborted` o `error`               |
| `connection`               | Última conexión física: `generation`, URL, protocolo negociado, extensiones cuando están disponibles |
| `bufferedAmount`           | Conteo nativo de bytes no enviados, o `0` sin socket físico                                          |
| `receive`                  | Iterable async de un solo consumidor de mensajes entrantes validados                                 |
| `onStateChange(listener)`  | Suscribirse a transiciones de estado lógico; devuelve unsubscribe                                    |
| `onRuntimeError(listener)` | Suscribirse a errores de runtime no de arranque; devuelve unsubscribe                                |
| `closed`                   | Promesa del resultado de cierre terminal lógico                                                      |

`open` = socket físico abierto. `reconnecting` incluye preparación + delay antes de un reemplazo. `connection.generation` incrementa con cada socket físico que llega a `open`. La tupla `startupConnection` se queda en el primer snapshot con éxito; `session.connection` avanza.

Fallo de arranque → `[error, undefined, connection?]`. Un fallo del constructor pre-open puede no tener conexión; timeout/cierre durante el arranque aún puede proporcionar un snapshot. Tras devolver la sesión, los errores de runtime viajan por observadores, `receive` y `closed` — no por una segunda tupla de execute.

## Reconnect

El reconnect es opt-in. Sin objeto `reconnect` → el cierre físico termina la sesión lógica. Cuando está configurado, los defaults son `attempts: 3`, `delayMs: 1000`, `factor: 2`, `maxDelayMs: 30000`, `jitter: 0`. `attempts` cuenta reintentos tras el intento inicial; `attempts: 0` desactiva. El predicado por defecto acepta todo resultado de cierre.

<include cwd>examples/web-socket/reconnect.ts#example</include>

`shouldReconnect` recibe el siguiente intento de retry, cause de cierre, code, reason y `wasClean`. Un `session.close(...)` manual no entra en el predicado. Lanzar en preparación/política termina la sesión lógica con error.

El jitter de backoff de WebSocket es **multiplicativo** (`jitter: 0.2` → delay entre `0.8x` y `1.2x`). El jitter de SSE es un factor multiplicativo 0–1, igual que WebSocket. Los valores de delay/factor/jitter/attempt se validan antes del constructor; los delays del timer no pueden superar `2_147_483_647` ms.

`beforeConnect({ attempt, signal })` corre antes del constructor inicial y de cada reconnect. Pasa su signal al refresh de token para que cancel detenga tanto la prep como el connect.

## Heartbeat

Opt-in en execute o en el ámbito del cliente. El intervalo envía `message()` a través del struct outgoing. Un `isAck(message)` opcional reconoce un ack — ese mensaje limpia el timeout y **no** se entrega a `receive`.

<include cwd>examples/web-socket/heartbeat.ts#example</include>

`intervalMs` y `timeoutMs` deben ser timers finitos positivos ≤ `2_147_483_647`. El mensaje de heartbeat debe ser válido para el struct outgoing. Fallos de serialización, send nativo, clasificación de ack y timeout son fatales para la sesión lógica — no se convierten en reconnects ordinarios.

## Colas

| Ajuste                 | Valor requerido                                 | Comportamiento                                                                                                       |
| ---------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `maxIncomingQueueSize` | Entero seguro positivo                          | Acota mensajes parseados esperando `receive` y frames en bruto esperando transformación. Overflow → `state: 'error'` |
| `maxOutgoingQueueSize` | Entero seguro no negativo opcional; default `0` | FIFO solo mientras `state === 'reconnecting'`. Llena/deshabilitada → `send(...)` lanza                               |

Los frames outgoing encolados se vacían antes de que el socket de reemplazo publique `open`. Los frames ya enviados en un socket anterior nunca se reenvían solos. Las colas de reconnect son para mensajes que envías mientras reconectas — no para reconstruir el estado de la app.

El overflow entrante limpia la secuencia pendiente, falla `receive`, detiene la sesión y resuelve `session.closed` con `kind: 'error'`. Mantén el consumidor lo bastante rápido o sube el tope desde tamaño/memoria medidos.

## Protocolos y autenticación

`protocols` de la definición, `withWebSocketProtocols(...)` del cliente y `protocols` de execute fijan la lista de subprotocolos del constructor. Precedencia: ejecución → cliente → definición. La primera lista definida se copia para la sesión lógica y se reutiliza en reconnect.

Los constructores WebSocket del navegador no aceptan cabeceras arbitrarias de handshake, y el builder no puede devolver `headers` ni `body`. Defjs convierte `http:` → `ws:` y `https:` → `wss:`, codifica placeholders de path una vez y usa las mismas reglas de query que HTTP: escalares y claves repetidas por defecto, `withQuerySerializer` para objetos anidados, y sin llamada al serializador cuando no hay query.

`withCredentials(true)` son credenciales Fetch para HTTP/SSE — no auth de WebSocket. Usa política revisada de cookie/sesión, subprotocolo o un ticket de conexión de corta duración. No pongas credenciales generales ni secretos de larga duración en el query string.

## Cierre y ownership

`session.close(code?, reason?)` pide cierre terminal y detiene el heartbeat. El code debe ser `1000` o `3000..4999`; reason ≤ 123 bytes UTF-8. Args de cierre inválidos lanzan antes de cambiar el estado. Úsalo con `await session.closed` cuando necesites un motivo de cierre manual o el resultado terminal lógico.

El `signal` o `abort` pasado a `execute` sigue vinculado a la sesión abierta: abortarlo más tarde termina la sesión como `'aborted'` y rechaza `receive` con un `AbortError`. `timeout` es solo un plazo de arranque.

</include>

`session.closed` es el snapshot terminal lógico: `'closed'`, `'aborted'` o `'error'`, con `code` / `reason` / `wasClean` nativos opcionales y un `cause` para aborted/error. Los campos de cierre nativo observados ganan sobre el fallback pedido por el dueño.

El disposer async estándar pide un close nativo best-effort y luego espera el teardown que posee Defjs: ciclo de vida, message pump, timers, listeners, colas y referencias al socket. Si no se observa un evento close en un segundo, el teardown se fuerza y el disposer puede rechazar con una `DOMException` llamada `TimeoutError`; esto no demuestra que la conexión TCP física se cerró. Las llamadas repetidas al disposer comparten el mismo teardown. Las implementaciones estructurales propias de sesión ahora deben proporcionar el mismo contrato `[Symbol.asyncDispose](): PromiseLike<void>`.

## Límite GraphQL

Defjs aporta un struct incoming, un struct outgoing y un ciclo de vida de sesión lógica. **No** implementa un protocolo de aplicación WebSocket. Las features GraphQL-over-WebSocket — connection init, IDs de operación, `next`/`error`/`complete`, liberación, replay de suscripción — quedan fuera del contrato core.

Usa un cliente de protocolo como `graphql-ws` cuando el servidor exija ese protocolo, o modela los frames con `defineWebSocket(...)`. Pon un subprotocolo estático como `graphql-transport-ws` en `protocols`. Un struct solo no negocia la semántica GraphQL.
