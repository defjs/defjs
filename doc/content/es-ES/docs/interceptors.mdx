# Middleware e interceptores

Los interceptores conectan políticas transversales de ejecución —cabeceras de autenticación, firma de peticiones, respuestas inmediatas por mantenimiento o reintentos en lecturas seguras— al `Client` de la aplicación sin modificar las definiciones de operación del SDK.

La validación de entrada y el mapeo en `builder` se ejecutan **antes** de la cadena de interceptores; el despacho de código HTTP y la validación de structs de `output` / `error` se ejecutan **después** de la cadena.

### Reglas del flujo de interceptores

- **Orden en capas de cebolla**: los interceptores se ejecutan en el orden de registro en la fase de salida (`antes de next(req)`) y en orden inverso en la fase de retorno (`después de await next(req)`). Coloca los interceptores generales de registro o trazado por fuera de los interceptores más específicos de autenticación o reintentos.
- **Convención de petición inmutable**: clona siempre `req.headers` (`new Headers(req.headers)`) y pasa un nuevo objeto de petición (`{ ...req, headers }`) a `next(...)` para que los reintentos externos vean cabeceras limpias.
- **`content-type` y `bodyContentType`**: Defjs almacena el tipo de contenido inferido para el cuerpo en `req.bodyContentType` sin mutar `req.headers`. Los firmadores de peticiones deben leer `req.headers.get("content-type") ?? req.bodyContentType`. Si un interceptor reemplaza `req.body` con un nuevo formato, establece explícitamente una cabecera `content-type`.

## 3. Reintentar lecturas HTTP seguras

Defjs no reintenta automáticamente códigos de estado HTTP de la aplicación. Cuando necesites reintentar según el código de respuesta (por ejemplo `429`, `502`, `503`, `504` en llamadas idempotentes `GET` / `HEAD` / `OPTIONS`), implementa un bucle acotado dentro de un interceptor HTTP:

<include cwd lang="typescript">
  examples/interceptors/retry-safe-reads.ts#example
</include>

- **Tratamiento de rechazos de transporte**: `next(request)` rechaza cuando ocurre un error de red (no existe una respuesta con estado 0). Capturar y relanzar ese rechazo preserva el código de fallo original `NET_*`.
- **Lanzar excepciones dentro de un interceptor**: una excepción no capturada (o devolver un valor que no sea una respuesta) resuelve la tupla de la operación con `EXT_INTERCEPTOR_FAILED` y asigna `fault.cause`. Lanzar `ERR_ABORTED` o `ERR_TIMEOUT` resuelve con `NET_ABORTED` o `NET_TIMEOUT`.

## 4. Envolver sesiones WebSocket

Un interceptor WebSocket puede llamar a `next(req)` **como máximo una vez**. Al envolver el objeto devuelto `WebSocketSessionLike`, delega los getters activos (`state`, `connection`, `bufferedAmount`), `close`, `closed`, `receive` y `[Symbol.asyncDispose]()` en lugar de copiar una instantánea puntual con spread de objeto:

## 5. Factorías integradas y utilidades

| Export                                         | Transporte | Descripción                                                                  |
| ---------------------------------------------- | ---------- | ---------------------------------------------------------------------------- |
| `createHttpInterceptor(fn)`                    | HTTP       | Envuelve `(req, next) => Promise<HttpResponse<unknown>>`                     |
| `createSSEInterceptor(fn)`                     | SSE        | Envuelve `(req, next) => Promise<EventStreamHandle<unknown>>`                |
| `createWebSocketInterceptor(fn)`               | WebSocket  | Envuelve `(req, next) => Promise<WebSocketSessionLike>`                      |
| `basicAuthHttpInterceptor(provider, options?)` | HTTP       | Inyecta `Authorization: Basic ...` desde un proveedor sincrónico o asíncrono |
| `basicAuthSSEInterceptor(provider, options?)`  | SSE        | Inyecta `Authorization: Basic ...` en los handshakes de SSE                  |
