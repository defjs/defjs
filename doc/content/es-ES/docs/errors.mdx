# Tratamiento de errores

En Defjs, los fallos de petición, transporte y decodificación no lanzan excepciones en el punto de llamada. Cada operación devuelve una tupla con el error por delante (`[error, ...]`) donde `error` es `null` o bien una instancia tipada de `Fault` (una instancia nativa de `Error` discriminada por `error.code`).

El mal uso de programación es la excepción. Suele rechazar con `TypeError` en lugar de devolver un `Fault`: una opción `signal` que no es un `AbortSignal`, una operación HTTP cuyo `output` o `error` no es un `struct`, y llamar a una operación sin un cliente.

### Por qué `error` transporta los metadatos de respuesta en fallos HTTP

En un fallo HTTP, la tupla es `[error, undefined, undefined]`. Cualquier metadato de respuesta recibido (`status`, `statusText`, `headers`, `url`) se adjunta directamente a `error.response`, lo que permite pasar el objeto `error` directamente a un logger o gestor de errores sin perder contexto.

## 2. Clases de fallos y conjunto cerrado de códigos

El prefijo antes del primer guion bajo `_` identifica la clase del fallo (`HTTP`, `REQ`, `NET`, `RES`, `EXT`, `CAP`, `ENV`), mientras que el `code` completo forma una unión cerrada para sentencias `switch` exhaustivas:

| Clase  | Códigos de fallo                                                       | Significado y resolución                                                                                                                                                                                                                                                                                                                                      |
| ------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HTTP` | `HTTP_STATUS`                                                          | El servidor respondió con un estado no `2xx` (`3xx`, `4xx`, `5xx`) y se decodificó el struct de `error` declarado.                                                                                                                                                                                                                                            |
| `REQ`  | `REQ_INPUT_INVALID`, `REQ_BUILD_FAILED`                                | La entrada de quien llama no superó la validación, la URL o la ruta no era válida, el `builder` lanzó, o la petición no se pudo construir (HTTP: stream de cuerpo ya usado, método no válido o prohibido, cuerpo en GET/HEAD, `Content-Type` no válido; HTTP y SSE: una URL con credenciales, un valor de cabecera que la plataforma rechaza). No reintentar. |
| `RES`  | `RES_MEDIA_TYPE_INVALID`, `RES_DECODE_FAILED`, `RES_STRUCT_MISMATCH`   | La respuesta del servidor violó el tipo de medio, la representación o el contrato de `struct` declarados.                                                                                                                                                                                                                                                     |
| `NET`  | `NET_ABORTED`, `NET_TIMEOUT`, `NET_UNREACHABLE`, `NET_BODY_INCOMPLETE` | Quien llama canceló (`NET_ABORTED`), venció el plazo (`NET_TIMEOUT`), falló la conexión o el flujo se truncó.                                                                                                                                                                                                                                                 |
| `EXT`  | `EXT_INTERCEPTOR_FAILED`, `EXT_HOOK_FAILED`, `EXT_OBSERVER_FAILED`     | Un interceptor, hook u observador de progreso o de estado de la aplicación lanzó su propio error, o un interceptor pasó a `next()` una `signal` que no es un `AbortSignal`.                                                                                                                                                                                   |
| `CAP`  | `CAP_BUFFER_EXCEEDED`                                                  | El búfer de tramas SSE superó el límite configurado.                                                                                                                                                                                                                                                                                                          |
| `ENV`  | `ENV_UNSUPPORTED`                                                      | El runtime anfitrión carece de APIs Web requeridas (p. ej., cuerpo de petición en streaming en Firefox).                                                                                                                                                                                                                                                      |

El código nombra qué falló, no quién aportó el valor. En HTTP, una petición que la plataforma no puede construir es `REQ_BUILD_FAILED` tanto si el valor malo vino del `builder`, de la configuración del cliente o de un interceptor. SSE aplica la misma regla a los valores de cabecera, una URL no válida y una URL con credenciales, en el primer intento y en cada reconexión. La biblioteca comprueba esta última por sí misma porque Bun acepta esa URL y enviaría la petición. Otros valores que la plataforma puede rechazar no los comprueba la biblioteca en SSE y WebSocket (un método no válido en SSE; una URL con credenciales, un subprotocolo no válido o un esquema no admitido en WebSocket), así que un rechazo ahí se informa como `NET_UNREACHABLE` con el error de la plataforma como `cause`, y un runtime que acepta el valor (Bun, para un método SSE no válido) envía la petición. `EXT_INTERCEPTOR_FAILED` cubre el comportamiento propio del interceptor: un error que lanza, o una `signal` que no es un `AbortSignal` (el canal de cancelación, no el contenido de la petición).

### Propiedades de Fault según el código

| Código de fallo | `status` | `response`                                      | `data`                                       | `cause`                              |
| --------------- | -------- | ----------------------------------------------- | -------------------------------------------- | ------------------------------------ |
| `HTTP_STATUS`   | `number` | `DecodedResponse<TErr>` o `HttpMeta`            | Struct de `error` decodificado o `undefined` | Causa subyacente si la hay           |
| `RES_*`         | `number` | `HttpMeta` (**sin campo `body`**)               | Ausente                                      | `StructError` o error del parser     |
| Otros códigos   | Ausente  | `HttpMeta` si llegaron cabeceras, o `undefined` | Ausente                                      | `Error` subyacente / motivo de abort |

## 4. Errores de inicio frente a errores posteriores en SSE y WebSocket

En conexiones de larga duración, la tupla de la operación notifica los fallos de **inicio** (antes de abrir el flujo o el socket). Una vez abiertos, los fallos en tiempo de ejecución se transmiten a través del ciclo de vida del handle o la sesión:

| Transporte    | Fallo en el inicio (devuelto en la tupla)                                                                                                                                                               | Fallo posterior al inicio (tras resolverse la tupla)                                                                                                                                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HTTP**      | Todos los fallos resuelven la tupla de la operación una única vez.                                                                                                                                      | N/A                                                                                                                                                                                                                                                                              |
| **SSE**       | No `2xx` (`HTTP_STATUS`, o el fallo de decodificación cuando el cuerpo `error` declarado no se puede decodificar), o un handshake `2xx` con un tipo de contenido incorrecto (`RES_MEDIA_TYPE_INVALID`). | El iterador asíncrono rechaza; `stream.closed` se resuelve con `{ kind: 'error', code }`.                                                                                                                                                                                        |
| **WebSocket** | Cierre previo a la apertura, fallo en el constructor o abort durante el handshake.                                                                                                                      | Los fallos de trama no fatales disparan `session.onRuntimeError`; los errores fatales rechazan `session.receive` y resuelven `session.closed` con `{ kind: 'error', cause }`. Un timeout de heartbeat y los reintentos agotados conservan causas `Error` ordinarias del runtime. |
