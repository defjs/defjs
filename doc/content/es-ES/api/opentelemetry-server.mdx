# OpenTelemetry en el servidor

Un plugin de middleware: instrumentación saliente de cada llamada de operación y de su transporte HTTP / SSE / WebSocket, como interceptores de core. Este paquete no inicializa un SDK de OpenTelemetry y no es instrumentación entrante de servidor.

Consulta la [guía de OpenTelemetry en el servidor](/es-ES/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

Añade un interceptor de operación cuando se aporta un `tracer`, un `meter` o un `logger`, y después un interceptor por transporte habilitado, en el orden HTTP, SSE, WebSocket. Aplícalo al crear el cliente con `createClient`, una vez por cliente. `options` es obligatorio; pasa `{}` para instalar los interceptores de transporte solo con propagación.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter` y `logger` son opcionales cada uno. Sin `propagator` → W3C Trace Context + Baggage.

Cada llamada de operación se observa desde la llamada hasta su tupla: un span de operación `INTERNAL` llamado `defjs.operation.name` (como `GET /orders/:id`) con `error.type` establecido al código de fallo cuando falla, una muestra de `defjs.client.operation.duration` y un log `WARN` si falla. Cada intento HTTP y cada conexión SSE o WebSocket recibe debajo un span de transporte `CLIENT`. Una llamada sin span padre activo inicia su propia traza; el sampler del SDK decide qué se conserva.

Sin `tracer`, el plugin no crea spans locales, nunca llama a `trace.getTracer(...)` y se salta `startSpanHook`, `requestHook` y `responseHook`. Las instancias de `meter` y `logger` que aportes funcionan de forma independiente. La propagación sigue reenviando el contexto padre extraído; `queryPropagation` de WebSocket sigue en `false` por defecto.

HTTP, SSE y WebSocket están activos por defecto. Pasa `{ enabled: false }` en un transporte para saltártelo.

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| Campo                     | Por defecto                 | Efecto                                                                                                         |
| ------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `tracer`                  | ninguno                     | Sin él no hay spans locales ni hooks de span.                                                                  |
| `meter`                   | ninguno                     | Sin él no se registran métricas del paquete.                                                                   |
| `logger`                  | ninguno                     | Un `Logger` de `@opentelemetry/api-logs`. Sin él no se emiten LogRecords de diagnóstico.                       |
| `propagator`              | W3C Trace Context + Baggage | Extrae el contexto padre e inyecta el contexto saliente.                                                       |
| `includeErrorDiagnostics` | `false`                     | Exporta mensajes y trazas de pila de error en los spans fallidos, los eventos `exception` y los logs de fallo. |
| `http`                    | `{}`                        | Opciones del transporte HTTP.                                                                                  |
| `sse`                     | `{}`                        | Opciones del transporte SSE.                                                                                   |
| `webSocket`               | `{}`                        | Opciones del transporte WebSocket.                                                                             |

<ApiSignature name="OpenTelemetryServerTransportOptions, OpenTelemetryServerHttpOptions, OpenTelemetryServerSSEOptions, OpenTelemetryServerWebSocketOptions" />

`enabled` vale `true` por defecto; solo `enabled: false` apaga un transporte, junto con la telemetría de operación de sus llamadas.

Los hooks de span solo se ejecutan cuando se aporta un `tracer`. `startSpanHook` se ejecuta de forma síncrona antes de crear el span de su propio transporte HTTP, SSE o WebSocket. Sus atributos se aplican después de los atributos integrados, así que la aplicación puede sustituir `url.full` u otro valor inicial. Si lanza, Defjs crea el span con los atributos integrados y continúa la solicitud; `requestHook` y `responseHook` se ejecutan después de crear el span. Ninguno se espera: un throw o un rechazo nunca bloquea ni falla la operación.

Los hooks dan forma al span de transporte; el span de operación no tiene hooks. Mientras `span.isRecording()` es true, los fallos de hook registran los eventos `defjs.otel.hook.error` y `exception`. El evento `exception` lleva solo `exception.type` (el nombre de la clase, no un código de fallo de Defjs), y ni `exception.message` ni `exception.stacktrace` salvo que `includeErrorDiagnostics` esté activado, porque el texto de error del runtime puede incluir la URL completa de la solicitud o un fragmento del cuerpo de la respuesta; la misma regla se aplica al evento `exception` que se registra cuando falla un transporte. En spans que no graban (terminados o no muestreados), los fallos van al logger de diagnóstico de OpenTelemetry mediante `diag.error`. Las aplicaciones deben configurar `diag.setLogger(...)` de `@opentelemetry/api` para recibirlos; no hay salida automática por defecto. El paquete no inicializa el SDK, y este diagnóstico no es un `LogRecord` aparte del SDK.

`responseHook` recibe lo que devolvió el transporte: el `HttpResponse` de HTTP, el handle del stream de SSE una vez que el arranque tuvo éxito y la sesión de WebSocket una vez abierta. Su tercer argumento es la solicitud original.

Por defecto, `url.full` resuelve solo `request.endpoint` contra un `request.baseEndpoint` opcional; `request.query` no se añade. Ese límite no es la ocultación de la query. Como exigen las convenciones semánticas de OpenTelemetry, las credenciales del userinfo del endpoint se sustituyen por `REDACTED:REDACTED`, y los valores de las claves de query sensibles por defecto (`sig`, `Signature`, `AWSAccessKeyId`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `X-Goog-Signature`) se sustituyen por `REDACTED`, pero el paquete no tiene ningún otro redactor integrado ni política de claves sensibles. Un `url.full` devuelto por `startSpanHook` se oculta del mismo modo, pero una URL que la aplicación escribe a través del objeto `Span` en `requestHook` o `responseHook` no se intercepta, así que constrúyela y, si hace falta, ocúltala de forma explícita:

`webSocket.queryPropagation` (solo WebSocket) vale `false` por defecto. Actívalo solo después de aceptar contexto de traza en la URL de WebSocket.

## Diagnósticos del logger

La opción de nivel superior `logger?: Logger` usa `@opentelemetry/api-logs`, no un Logger de aplicación. Es opcional y puede usarse sola. Defjs nunca obtiene un logger global ni es dueño de su proveedor. Emite un LogRecord `WARN` (número de severidad 13) por cada llamada de operación fallida, y uno por cada stream SSE o sesión WebSocket que falla después de abrirse, cada uno con un mensaje fijo:

| Resultado                                                                             | Evento                                                            | Atributos                                                                                                          |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Una llamada de operación se resuelve con un fallo distinto de `NET_ABORTED`           | `defjs.client.operation.exception`                                | `defjs.operation.name`, `error.type` (el código de fallo), `exception.type`, `defjs.meta.*`                        |
| Un stream SSE o una sesión WebSocket termina en error, incluido un `closed` rechazado | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `server.address`, `server.port`, `exception.type`, `defjs.meta.*`, `defjs.sse.fault.code` o `websocket.close.code` |

El éxito, un intento reintentado que un intento posterior recupera, el cierre normal, el EOF, una trama de cierre WebSocket del servidor sea cual sea su código y la cancelación de quien llama no producen ningún LogRecord. Una caída brusca de WebSocket sin trama de cierre (1006) termina la sesión en error y registra una vez, en todos los runtimes. El registro de operación se emite con el contexto del span de operación.

Con `includeErrorDiagnostics: true`, cada registro lleva además `exception.message` y `exception.stacktrace`; en una llamada de operación son el `message` y el `stack` del fallo. La cadena de causas y los campos enumerables de un error nunca se exportan, pero el mensaje no se filtra: el mensaje de un fallo suele ser el de su causa, y el texto de error de la plataforma puede citar la URL de la solicitud. Las aplicaciones son dueñas del filtrado, los exportadores, el vaciado y el apagado.

Consulta los ejemplos completos de logging e integración con terceros en la [guía de OpenTelemetry](/es-ES/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
