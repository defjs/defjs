# Servidor de OpenTelemetry

Instrumentación de salida HTTP / SSE / WebSocket como interceptores del core. Este paquete no inicializa un SDK de OpenTelemetry, y no es instrumentación de servidor de entrada.

Mira la [guía de OpenTelemetry server](/es-ES/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

```ts
function withOpenTelemetryServer(options: OpenTelemetryServerOptions): ClientOption
```

Añade un interceptor por transporte habilitado, en el orden HTTP, SSE, WebSocket. Aplícalo al llamar a `createClient`. `options` es obligatorio; pasa `{}` para instalar los interceptores solo con propagación.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter` y `logger` son opcionales cada uno. Sin `propagator` → W3C Trace Context + Baggage.

Sin `tracer`, el adaptador no crea spans locales, nunca llama a `trace.getTracer(...)` y omite `startSpanHook`, `requestHook` y `responseHook`. Las instancias de `meter` y `logger` que se proporcionen funcionan de forma independiente. La propagación sigue reenviando el contexto padre extraído; `queryPropagation` de WebSocket sigue siendo `false` por defecto. Con un tracer, `requireParentSpan: true` omite toda la instrumentación, incluidos los logs, cuando no existe un padre activo; sin tracer no bloquea ni las métricas ni los logs.

HTTP, SSE y WebSocket están activados por defecto. Pasa `{ enabled: false }` en un transporte para omitirlo.

## OpenTelemetryServerOptions

```ts
interface OpenTelemetryServerOptions {
  tracer?: Tracer
  meter?: Meter
  logger?: Logger
  propagator?: TextMapPropagator
  requireParentSpan?: boolean
  http?: OpenTelemetryServerHttpOptions
  sse?: OpenTelemetryServerSSEOptions
  webSocket?: OpenTelemetryServerWebSocketOptions
}
```

| Campo               | Por defecto                 | Efecto                                                                                                |
| ------------------- | --------------------------- | ----------------------------------------------------------------------------------------------------- |
| `tracer`            | ninguno                     | Sin él no hay spans locales ni span hooks.                                                            |
| `meter`             | ninguno                     | Sin él no se registran métricas del paquete.                                                          |
| `logger`            | ninguno                     | Un `Logger` de `@opentelemetry/api-logs`. Sin él no se emiten LogRecords de diagnóstico.              |
| `propagator`        | W3C Trace Context + Baggage | Extrae el contexto padre e inyecta el contexto saliente.                                              |
| `requireParentSpan` | `false`                     | Con un `tracer`, omite la instrumentación cuando no hay un span padre activo. Se ignora sin `tracer`. |
| `http`              | `{}`                        | Opciones del transporte HTTP.                                                                         |
| `sse`               | `{}`                        | Opciones del transporte SSE.                                                                          |
| `webSocket`         | `{}`                        | Opciones del transporte WebSocket.                                                                    |

### OpenTelemetryServerWebSocketOptions

```ts
interface OpenTelemetryServerTransportOptions<TResponse> {
  enabled?: boolean
  startSpanHook?: (request: HttpRequest) => Attributes
  requestHook?: (span: Span, req: HttpRequest) => Promise<void> | void
  responseHook?: (span: Span, res: TResponse, req: HttpRequest) => Promise<void> | void
}

type OpenTelemetryServerHttpOptions = OpenTelemetryServerTransportOptions<HttpResponse<unknown>>
type OpenTelemetryServerSSEOptions = OpenTelemetryServerTransportOptions<EventStreamHandle<unknown>>
interface OpenTelemetryServerWebSocketOptions extends OpenTelemetryServerTransportOptions<WebSocketSessionLike> {
  queryPropagation?: boolean
}
```

`enabled` vale `true` por defecto; solo `enabled: false` apaga un transporte. El antiguo interruptor booleano (`http: false`) y los hooks de nivel superior los rechazan únicamente los tipos de TypeScript. No hay comprobación en runtime, así que en runtime `http: false` deja el transporte habilitado y un hook de nivel superior se ignora en silencio.

Los span hooks solo se ejecutan cuando se proporciona un `tracer`. `startSpanHook` se ejecuta de forma síncrona antes de crear el span de su propio transporte HTTP, SSE o WebSocket. Sus atributos se aplican después de los atributos integrados, así que la aplicación puede sustituir `url.full` u otro valor inicial. Si lanza, Defjs crea el span con los atributos integrados y continúa la solicitud; `requestHook` y `responseHook` se ejecutan tras crear el span. Ninguno se espera (await): un throw o un rechazo no bloquea ni hace fallar la operación.

Mientras `span.isRecording()` sea true, los fallos de hooks registran los eventos `defjs.otel.hook.error` y `exception`. Si el span no está grabando (ha terminado o no fue muestreado), los fallos se envían al logger de diagnóstico de OpenTelemetry mediante `diag.error`. La aplicación debe configurar `diag.setLogger(...)` de `@opentelemetry/api` para recibirlos; no hay salida automática por defecto. El paquete no inicializa el SDK y este diagnóstico no es un `LogRecord` independiente del SDK.

`responseHook` recibe lo que devolvió el transporte: el `HttpResponse` en HTTP, el handle del stream en SSE una vez que el arranque tuvo éxito y la sesión en WebSocket una vez abierta. Su tercer argumento es la solicitud original.

Por defecto, `url.full` resuelve únicamente `request.endpoint` contra el `request.baseEndpoint` opcional; un `request.queryString` independiente no se añade. Ese límite no es redacción (ocultación de datos sensibles), y el paquete no incluye ningún redactor ni política de claves sensibles. Construye y, si hace falta, redacta explícitamente una URL propia de la aplicación:

`queryPropagation` vale `false` por defecto. Actívalo solo después de aceptar el trace context en la URL de WebSocket.

## Diagnósticos del logger

La opción de nivel superior `logger?: Logger` usa `@opentelemetry/api-logs`, no un Logger de Winston/Pino. Es opcional y puede usarse sola. Defjs nunca obtiene un logger global ni es dueño de su provider. Emite como máximo un LogRecord `WARN` (número de severidad 13) por solicitud o conexión lógica, con un mensaje fijo y los atributos `server.address` y `server.port` (cuando se conocen), `defjs.phase`, `exception.type`, además de `http.request.method` en HTTP, `defjs.sse.fault.code` cuando un stream SSE termina en error y `websocket.close.code` cuando la información de cierre del WebSocket tiene un código numérico:

| Resultado                                                                         | Evento                                                            | `defjs.phase` |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------- |
| `next()` de HTTP se rechaza, excluyendo la cancelación y el `HTTP_STATUS` público | `http.client.request.exception`                                   | `request`     |
| Falla la conexión SSE o WebSocket                                                 | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `connect`     |
| SSE o WebSocket terminan en error, incluido un `closed` rechazado                 | el mismo evento del transporte                                    | `connection`  |

Las respuestas con un status ordinario (incluidos 4xx/5xx cuyo body `error` declarado se decodifica), el éxito, el cierre normal, el EOF y la cancelación del llamador no producen ningún LogRecord. Un timeout de execute HTTP registra una vez solo si un rechazo por timeout llega al límite `next()` / transporte del interceptor de OTel (un abort cuyo motivo es un `TimeoutError`, como `AbortSignal.timeout()`, cuenta como timeout, no como cancelación). Si solo la ejecución exterior observa el plazo durante el parseo del input, la construcción, el trabajo de un interceptor de aplicación después de `next()` o la conversión del body posterior a la cadena, no se emite ningún LogRecord; observa `client.execute(...)` en el límite exterior del comando. Los fallos de lectura de un body `output` / `error` declarado dentro del límite del handler HTTP registran para cualquier representación; los fallos de media type y de `JSON.parse` registran solo para representaciones JSON, con cualquier status HTTP. El texto, los blobs y los bytes que no son JSON no son fallos solo porque su media type no sea JSON. Un body que no está declarado nunca se lee y no puede registrar. La validación de structs, un body declarado ausente como un 204 y la posterior conversión a `HTTP_STATUS` ocurren después del interceptor y no registran. Un handshake SSE no 2xx siempre registra una vez; un frame de cierre de WebSocket del servidor nunca registra, sea cual sea su código. Una caída abrupta sin frame de cierre (1006) depende del runtime: donde el WebSocket de la plataforma dispara `error` antes de `close` (Node.js), la sesión termina en error y registra una vez; donde no (Bun), la caída es un cierre normal y no se registra nada.

`exception.type` es el nombre de clase de lo que observó el interceptor, no un código de fault de Defjs: por ejemplo `BodyFailure` (body HTTP), `EventStreamFatalError` (handshake SSE), `DefjsFault` (arranque de WebSocket), `TypeError` (fallo de red) o `Error` (timeout). La aplicación se encarga del filtrado, los exporters, el flush y el shutdown.

Consulta los ejemplos completos de logging y de integración con bibliotecas de terceros en la [guía de OpenTelemetry](/es-ES/docs/integrations/opentelemetry-server#logs-y-loggers-de-terceros).
