# OpenTelemetry en el servidor

Un plugin de middleware: instrumentación saliente HTTP / SSE / WebSocket como interceptores de core. Este paquete no inicializa un SDK de OpenTelemetry y no es instrumentación entrante de servidor.

Consulta la [guía de OpenTelemetry en el servidor](/es-ES/docs/integrations/opentelemetry-server).

## withOpenTelemetryServer()

<ApiSignature name="withOpenTelemetryServer" />

Añade un interceptor por transporte habilitado, en el orden HTTP, SSE, WebSocket. Aplícalo al crear el cliente con `createClient`. `options` es obligatorio; pasa `{}` para instalar los interceptores solo con propagación.

<include cwd>examples/api/with-opentelemetry-server.ts#example</include>

`tracer`, `meter` y `logger` son opcionales cada uno. Sin `propagator` → W3C Trace Context + Baggage.

Sin `tracer`, el plugin no crea spans locales, nunca llama a `trace.getTracer(...)` y se salta `startSpanHook`, `requestHook` y `responseHook`. Las instancias de `meter` y `logger` que aportes funcionan de forma independiente. La propagación sigue reenviando el contexto padre extraído; `queryPropagation` de WebSocket sigue en `false` por defecto. Con un tracer, `requireParentSpan: true` evita toda la instrumentación, incluidos los logs, cuando no hay un padre activo; sin tracer no bloquea ni las métricas ni los logs.

HTTP, SSE y WebSocket están activos por defecto. Pasa `{ enabled: false }` en un transporte para saltártelo.

## OpenTelemetryServerOptions

<ApiSignature name="OpenTelemetryServerOptions" />

| Campo               | Por defecto                 | Efecto                                                                                                |
| ------------------- | --------------------------- | ----------------------------------------------------------------------------------------------------- |
| `tracer`            | ninguno                     | Sin él no hay spans locales ni hooks de span.                                                         |
| `meter`             | ninguno                     | Sin él no se registran métricas del paquete.                                                          |
| `logger`            | ninguno                     | Un `Logger` de `@opentelemetry/api-logs`. Sin él no se emiten LogRecords de diagnóstico.              |
| `propagator`        | W3C Trace Context + Baggage | Extrae el contexto padre e inyecta el contexto saliente.                                              |
| `requireParentSpan` | `false`                     | Con un `tracer`, evita la instrumentación cuando no hay un span padre activo. Se ignora sin `tracer`. |
| `http`              | `{}`                        | Opciones del transporte HTTP.                                                                         |
| `sse`               | `{}`                        | Opciones del transporte SSE.                                                                          |
| `webSocket`         | `{}`                        | Opciones del transporte WebSocket.                                                                    |

`enabled` vale `true` por defecto; solo `enabled: false` apaga un transporte. El interruptor booleano antiguo (`http: false`) y los hooks de nivel superior los rechazan solo los tipos de TypeScript. No hay comprobación en runtime, así que en runtime `http: false` deja el transporte habilitado y un hook de nivel superior se ignora en silencio.

Los hooks de span solo se ejecutan cuando se aporta un `tracer`. `startSpanHook` se ejecuta de forma síncrona antes de crear el span de su propio transporte HTTP, SSE o WebSocket. Sus atributos se aplican después de los atributos integrados, así que la aplicación puede sustituir `url.full` u otro valor inicial. Si lanza, Defjs crea el span con los atributos integrados y continúa la solicitud; `requestHook` y `responseHook` se ejecutan después de crear el span. Ninguno se espera: un throw o un rechazo nunca bloquea ni falla la operación.

Mientras `span.isRecording()` es `true`, los fallos de hook registran los eventos `defjs.otel.hook.error` y `exception`. En spans que no graban (terminados o no muestreados), los fallos van al logger de diagnóstico de OpenTelemetry mediante `diag.error`. Las aplicaciones deben configurar `diag.setLogger(...)` de `@opentelemetry/api` para recibirlos; no hay salida automática por defecto. El paquete no inicializa el SDK, y este diagnóstico no es un `LogRecord` aparte del SDK.

`responseHook` recibe lo que devolvió el transporte: el `HttpResponse` de HTTP, el handle del stream de SSE una vez que el arranque tuvo éxito y la sesión de WebSocket una vez abierta. Su tercer argumento es la solicitud original.

Por defecto, `url.full` resuelve solo `request.endpoint` contra un `request.baseEndpoint` opcional; un `request.queryString` independiente no se añade. Ese límite no es ocultación de datos sensibles, y el paquete no tiene un mecanismo integrado para ocultarlos ni una política de claves sensibles. Construye y, si hace falta, oculta de forma explícita los datos sensibles de una URL que posea la aplicación:

</include>

`webSocket.queryPropagation` (solo WebSocket) vale `false` por defecto. Actívalo solo después de aceptar contexto de traza en la URL de WebSocket.

## Diagnósticos del logger

La opción de nivel superior `logger?: Logger` usa `@opentelemetry/api-logs`, no un Logger de aplicación. Es opcional y puede usarse sola. Defjs nunca obtiene un logger global ni es dueño de su proveedor. Emite como mucho un LogRecord `WARN` (número de severidad 13) por solicitud o conexión lógica, con un mensaje fijo y los atributos `server.address` y `server.port` (cuando se conocen), `defjs.phase`, `exception.type`, más `http.request.method` para HTTP, `defjs.sse.fault.code` cuando un stream SSE termina en error y `websocket.close.code` cuando la información de cierre de WebSocket tiene un código numérico:

| Resultado                                                           | Evento                                                            | `defjs.phase` |
| ------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------- |
| `next()` de HTTP rechaza, salvo cancelación y `HTTP_STATUS` público | `http.client.request.exception`                                   | `request`     |
| Falla la conexión SSE o WebSocket                                   | `defjs.client.sse.exception` / `defjs.client.websocket.exception` | `connect`     |
| SSE o WebSocket termina en error, incluido un `closed` rechazado    | el mismo evento de transporte                                     | `connection`  |

Las respuestas con un estado ordinario (incluidos 4xx/5xx cuyo cuerpo `error` declarado decodifica), el éxito, el cierre normal, el EOF y la cancelación de quien llama no producen ningún LogRecord. Un aborto por plazo de HTTP registra una vez solo si un rechazo por timeout llega al límite `next()` / transporte del interceptor de OTel (un abort cuyo motivo es un `TimeoutError`, como `AbortSignal.timeout()`, cuenta como timeout, no como cancelación). Si solo la llamada a la operación observa el plazo durante el análisis de la entrada, la construcción, el trabajo de un interceptor de aplicación después de `next()` o la conversión del cuerpo posterior a la cadena, no se emite ningún LogRecord; observa la llamada a la operación. Los fallos de lectura de un cuerpo `output` / `error` declarado dentro del límite del handler HTTP registran para cualquier representación; los fallos de media type y de `JSON.parse` registran solo para representaciones JSON, con cualquier estado HTTP. El texto, los blobs y los bytes que no son JSON no son fallos solo porque su media type no sea JSON. Un cuerpo que no está declarado nunca se lee y no puede registrar. La validación del Struct, un cuerpo declarado ausente como un 204 y la conversión posterior a `HTTP_STATUS` ocurren después del interceptor y no registran. Un handshake SSE no-2xx siempre registra una vez; una trama de cierre WebSocket del servidor nunca registra, sea cual sea su código. Una caída brusca sin trama de cierre (1006) depende del runtime: donde el WebSocket de la plataforma dispara `error` antes de `close` (Node.js), la sesión termina en error y registra una vez; donde no lo hace (Bun), la caída es un cierre normal y no se registra nada.

`exception.type` es el nombre de clase de lo que observó el interceptor, no un código de fallo de Defjs: por ejemplo `BodyFailure` (cuerpo HTTP), `EventStreamFatalError` (handshake SSE), `DefjsFault` (arranque WebSocket), `TypeError` (fallo de red) o `Error` (timeout). Las aplicaciones son dueñas del filtrado, los exportadores, el vaciado y el apagado.

Consulta los ejemplos completos de logging e integración con terceros en la [guía de OpenTelemetry](/es-ES/docs/integrations/opentelemetry-server#logs-and-third-party-loggers).
