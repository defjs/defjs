# Cliente

`createClient(...)` devuelve un [`Client`](/es-ES/api/core/client-type) invocable. Compón las opciones del cliente de izquierda a derecha, luego llama a `client(options?)` para derivar un cliente y pásalo a una operación: `getUser(client(options), input)`.

## createClient()

<ApiSignature name="createClient" />

Las opciones se aplican en orden. Prefiere crear el cliente dentro del límite de la solicitud cuando los interceptores cierran sobre auth o tenants. El cliente devuelto es una función. Llamarla devuelve un cliente nuevo y no hace E/S.

- **options** — Helpers de opción como `withEndpoint`.
- **Devuelve** un cliente invocable. La configuración base la comparte cada cliente derivado y no está congelada en tiempo de ejecución. Queda fija por convención: nada en la biblioteca la cambia, y las aplicaciones tampoco deberían.

## Helpers de opción

Todos los helpers devuelven `ClientOption`. Una llamada posterior sustituye a una anterior para el mismo ajuste, excepto `withInterceptors`, que añade.

### withEndpoint()

<ApiSignature name="withEndpoint" />

Fija la URL base que se antepone a los paths relativos.

### withInterceptors()

<ApiSignature name="withInterceptors" />

Añade interceptores en el orden de registro. Los kinds mixtos se filtran por transporte cuando corre la operación.

### withQuerySerializer()

<ApiSignature name="withQuerySerializer" />

Sustituye la codificación de query para HTTP, SSE y WebSocket. `serializer(query)` recibe el **objeto de cable ya codificado** (alias aplicados, `Date` como ISO, `bigint` como string) y debe devolver el query string sin `?` inicial. No se llama cuando la solicitud no tiene query. Un builder que devuelve `URLSearchParams` se lo salta.

### withHeaders()

<ApiSignature name="withHeaders" />

Fija cabeceras estáticas por defecto para las solicitudes HTTP y SSE. Las solicitudes WebSocket no las usan. `headers` se copia cuando se aplica la opción, así que los cambios posteriores del objeto no llegan al cliente. Un segundo `withHeaders` sustituye al primero; no fusiona.

Precedencia para una solicitud:

1. Los valores por defecto son el conjunto inicial de cabeceras.
2. Las `headers` que devuelve el builder de la solicitud sustituyen un valor por defecto del mismo nombre. El primer valor de ese nombre sustituye al valor por defecto; los valores posteriores del mismo array solo se añaden a esa sustitución. Un escalar o una instancia de `Headers` también sustituye. Los demás nombres por defecto se quedan.
3. Los interceptores reciben las cabeceras fusionadas y pueden cambiarlas.
4. Con el transporte HTTP por defecto, la cabecera XSRF se añade al final, solo cuando sigue ausente (consulta `withXSRF`).

Usa un interceptor para valores que cambian por solicitud: un Bearer token renovado, o un HMAC sobre el cuerpo serializado.

No hay un plazo por defecto a nivel de cliente. Pasa `abort: AbortSignal.timeout(ms)` en un cliente derivado cuando una llamada lo necesita. Un abort manual es `NET_ABORTED`. `AbortSignal.timeout` se clasifica como `NET_TIMEOUT`.

### withCredentials()

<ApiSignature name="withCredentials" />

Cuando es `true`, Fetch usa `credentials: 'include'` para HTTP y SSE. Por defecto está apagado. Las conexiones WebSocket no se ven afectadas.

### withXSRF()

<ApiSignature name="withXSRF" />

Añade una cabecera de token XSRF a las solicitudes HTTP. `options` es el ajuste `xsrf`, la misma forma que `xsrf` en [`ClientOptions`](/es-ES/api/core/clientoptions-type): `cookieName` (por defecto `XSRF-TOKEN`), `headerName` (por defecto `X-XSRF-TOKEN`) y `tokenProvider({ request })`. Llamar a `withXSRF()` sin argumento activa esos valores por defecto. Las solicitudes SSE y WebSocket no se ven afectadas.

El transporte HTTP por defecto añade la cabecera cuando se cumple todo esto: el método no es `GET`, `HEAD`, `OPTIONS` ni `TRACE`; la solicitud no tiene ya esa cabecera; la solicitud es del mismo origen; y se encuentra un token no vacío. Siempre que exista `location`, incluso en un Worker, el origen resuelto de la solicitud debe coincidir con `location.origin`; sin él, una solicitud con `baseEndpoint` cuenta como mismo origen. Las solicitudes de origen cruzado no llaman a `tokenProvider`. El token sale de ese provider cuando se da, y si no de `document.cookie`, que solo se lee cuando existe `document`.

## Tipos

### Client

<ApiSignature name="Client" />

Un `Client` es una función. Llamarla con [`RequestOptions`](/es-ES/api/core/requestoptions-type) devuelve un cliente nuevo. Los siete campos conocidos se copian del argumento en un objeto nuevo superpuesto a las opciones actuales. Un campo posterior gana. Un campo cuyo valor es `undefined` se trata como no proporcionado y conserva el valor del padre. Un cliente derivado no puede quitar un ajuste que su padre tiene. Para volver a no tener ese ajuste, deriva otra vez desde el cliente que no lo tenía (conserva el cliente raíz). Los valores anidados `heartbeat`, `protocols` y `reconnect` se conservan por referencia, no se clonan, y sustituyen el valor del padre como un entero, no se fusionan. WebSocket los lee cuando se ejecuta la operación (entonces copia los campos de heartbeat y la lista protocols), así que mutar esos objetos después de derivar todavía puede afectar a una llamada posterior. Las aplicaciones deben tratarlos como inmutables después de pasarlos. El cliente original no se muta. `client()`, `client(undefined)` y `client({})` copian las opciones actuales. Derivar no hace E/S. El mismo valor de cliente puede pasarse a muchas operaciones. `abort` se sustituye, no se combina; combina signals con `AbortSignal.any` en el código de la aplicación.

No pases un cliente a un setter de estado de React (`setState(client)` lo llamaría como updater) ni lo uses como fuente de `watch` o `computed` de Vue (esos llaman a una función).

### RequestOptions

<ApiSignature name="RequestOptions" />

Siete campos planos. Cada protocolo lee los campos que entiende e ignora el resto. Pasar `heartbeat` a HTTP se ignora, no es un fault. SSE solo lee `abort` de las opciones de la solicitud. La reconexión de SSE viene de la configuración del cliente (`withSSEReconnect`), así que `client({ reconnect })` afecta solo a WebSocket. No hay un filtro de protocolo en tiempo de compilación ni un campo `timeout` o `signal`.

| Campo                | Protocolo             | Sustitución                                                                                        |
| -------------------- | --------------------- | -------------------------------------------------------------------------------------------------- |
| `abort`              | HTTP, SSE y WebSocket | Sustituye al signal anterior. En SSE y WebSocket cubre toda la conexión, también después de abrir. |
| `onUploadProgress`   | HTTP                  | Lo ignoran los demás protocolos.                                                                   |
| `onDownloadProgress` | HTTP                  | Lo ignoran los demás protocolos.                                                                   |
| `beforeConnect`      | WebSocket             | Sustituye el ajuste del cliente para esa llamada.                                                  |
| `protocols`          | WebSocket             | Sustituye la lista del cliente.                                                                    |
| `heartbeat`          | WebSocket             | Se sustituye entero. `timeoutMs` es la espera del acuse, no un plazo de la solicitud.              |
| `reconnect`          | WebSocket             | Se sustituye entero.                                                                               |

[`HttpExecuteOptions`](/es-ES/api/core/httpexecuteoptions-type) es el recorte HTTP (`abort` más progreso). [`EventStreamExecuteOptions`](/es-ES/api/core/eventstreamexecuteoptions-type) es `{ abort? }`. [`WebSocketExecuteOptions`](/es-ES/api/core/websocketexecuteoptions-type) es el recorte WebSocket más `abort`.

### FetchHandle

<ApiSignature name="FetchHandle" />

La firma de llamada que Defjs necesita de una implementación de Fetch. No es `typeof fetch`, así que un mock no necesita extras del host como `preconnect`. Los handles HTTP/SSE por defecto resuelven `globalThis.fetch` en cada llamada. HTTP usa `(url, init)` solo para el Fetch de la plataforma sin sustituir; los globales reemplazados y los handles personalizados reciben un `Request`. SSE siempre pasa un `Request`. Importar Core sin Fetch es válido; una ejecución por defecto informa `ENV_UNSUPPORTED` si Fetch sigue ausente, mientras que los handles personalizados siguen siendo utilizables.

### ClientWebSocketOptions

<ApiSignature name="ClientSSEOptions, ClientWebSocketOptions" />

La reconexión es opt-in en los dos transportes: sin `withSSEReconnect` / `withWebSocketReconnect` no hay reintento. Una vez definido `reconnect`, se aplican estos valores por defecto:

| Campo        | SSE                  | WebSocket            |
| ------------ | -------------------- | -------------------- |
| `attempts`   | `3` por interrupción | `3` por interrupción |
| `delayMs`    | `1000`               | `1000`               |
| `factor`     | `1`                  | `2`                  |
| `jitter`     | `0`                  | `0`                  |
| `maxDelayMs` | sin tope             | `30000`              |

En los dos transportes, un handshake correcto reinicia el presupuesto de reintento por interrupción, el intento del callback y el exponente de backoff. `attempts: 0` desactiva el reintento; omitir `attempts` no da reintentos ilimitados dentro de una interrupción. `maxDelayMs` limita el retraso final después del jitter y el redondeo; el límite de temporizador de la plataforma, `2_147_483_647` ms, también se aplica, incluso cuando SSE no tiene tope configurado. Una base cero se queda en cero; el desbordamiento de números válidos se satura en los topes.

Las opciones de reconexión se validan antes del transporte: `attempts` debe ser un entero seguro no negativo; `delayMs` debe ser finito y no negativo; `maxDelayMs` debe ser un número finito no negativo o `Infinity` positivo, que quita el tope configurado pero no el límite de plataforma de `2_147_483_647` ms; `factor` debe ser finito y positivo; `jitter` debe ser finito y estar entre 0 y 1. Los valores inválidos devuelven `REQ_OPTIONS_INVALID`. `attempts: 0` de WebSocket desactiva los reintentos posteriores, pero todos los campos de reconexión aportados de forma explícita se validan igualmente antes de la conexión inicial, igual que en SSE. El jitter escala la base ya limitada en cualquiera de las dos direcciones antes de aplicar el tope final.

Para SSE, `delayMs` es solo el retraso base inicial: un campo `retry:` del servidor que sea solo dígitos lo sustituye en los intentos posteriores, también después de recuperarse. Que `shouldReconnect` devuelva `false` detiene el reintento. El callback de SSE también recibe `lastEventId`, el `method` de la solicitud y la info `open` más reciente, y puede ser async. Sin él, SSE solo reconecta solicitudes `GET`, `HEAD`, `OPTIONS`, `PUT` y `DELETE`; con él, su resultado decide para todos los métodos. El ID de evento más reciente se envía como bytes UTF-8 en `Last-Event-ID`; un ID vacío lo borra y un ID que contiene NUL se ignora. El callback de WebSocket recibe en su lugar el `code`, el `reason` y `wasClean` del cierre.

`onInvalidEvent` de SSE trata un evento sin struct coincidente, incluido sin `default` (`missing-struct`), o cuyos datos fallan su struct (`validation-failed`). El evento siempre se descarta; el valor de retorno del handler se ignora, y un error que lance no cierra el stream.

Para WebSocket, `beforeConnect`, `heartbeat`, `protocols` y `reconnect` también pueden pasarse en un cliente derivado; cada uno sustituye el valor del cliente para esa llamada como un todo. `heartbeat.message` construye cada ping; no se envía nada cuando se omite o devuelve `undefined`. `heartbeat.timeoutMs` espera un acuse. No es un plazo de la solicitud.

### ClientOptions

<ApiSignature name="ClientOptions" />

Los campos mostrados son `sse` y `webSocket`. Los otros siete — `endpoint`, `headers`, `http`, `interceptors`, `querySerializer`, `xsrf` y `withCredentials` — se heredan de la base HTTP no exportada, y `endpoint` es obligatorio. No hay un `timeout` a nivel de cliente. `createClient` no recibe este objeto; recibe helpers de opción.

### ClientConfig

La instantánea resuelta que mutan los helpers de opción y lee una operación: `ClientOptions` después de los valores por defecto, con `http.handle`, `interceptors`, `sse` (un `ClientSSEConfig`) y `webSocket` siempre presentes.

### ClientSSEConfig

<ApiSignature name="ClientSSEConfig" />

La config SSE resuelta en `ClientConfig.sse`: `ClientSSEOptions` con un `handle` obligatorio.

### WebSocketHandle

La superficie de instancia de WebSocket que usa el transporte: `WebSocket` sin `binaryType`, las constantes de ready-state, `dispatchEvent` y las propiedades de handler `on*`, y con un `readyState: number` de solo lectura.

### WebSocketHandleConstructor

<ApiSignature name="WebSocketHandleConstructor" />

El constructor que se pasa a `withWebSocketHandle`. Debe exponer la constante de ready-state `OPEN`.
