# SSE

Declara un stream de eventos, llama a la operación con un cliente, itera los eventos y luego ciérralo.

## defineEventStream()

<ApiSignature name="defineEventStream" />

- **definition** — `path` y mapa `events`; `method` opcional (por defecto `'GET'`), `operation`, `input`, `error`, `maxBufferSize` (por defecto `64 * 1024`) y `maxQueueSize` (por defecto `1024`). Un `input` declarado exige siempre un `builder` explícito. `input` solo define los parámetros; solo el builder decide dónde va cada valor. Solo las definiciones sin `input` pueden omitir `builder`. Estos miembros de `definition` están documentados en [`EventStreamDefinition`](/es-ES/api/core/eventstreamdefinition-type). `error` solo es obligatorio cuando se da un tipo de struct de error, y `builder` es obligatorio exactamente cuando se declara `input`.
- **Devuelve** una operación. El primer argumento es un [`Client`](/es-ES/api/core/client-type). Los demás argumentos son solo la entrada. Llamarla arranca el stream.

<include cwd>examples/api/define-event-stream.ts#example</include>

La llamada devuelve `[null, stream, open]` o `[error, undefined, open?]`. Cuando se declara `error`, el fault es `Fault` de ese struct; si no, es `Fault<undefined>`. Pasa `signal` derivando un cliente a partir de [`RequestOptions`](/es-ES/api/core/requestoptions-type). SSE solo lee `signal` e ignora los campos de progreso y de WebSocket.

## EventStreamExecuteOptions

<ApiSignature name="EventStreamExecuteOptions" />

`EventStreamExecuteOptions` es `{ signal? }`. No hay campo `timeout` ni `abort`, ni callback de progreso. `signal` cubre todo el stream, también después de abrirse. Un plazo es `AbortSignal.timeout(ms)` y se clasifica como `NET_TIMEOUT`. Un abort manual es `NET_ABORTED`. No hay un plazo solo de arranque ni un plazo por defecto a nivel de cliente. Una aplicación que quiera un plazo solo de arranque crea su propio `AbortController`, lo aborta con `new DOMException("...", "TimeoutError")` desde un temporizador y limpia el temporizador cuando el await regresa.

## EventStreamHandle

<ApiSignature name="EventStreamHandle" />

El tercer hueco de la tupla es la instantánea de arranque de `open`; `stream.open` sigue la conexión más reciente tras una reconexión. Ese tercer hueco es la instantánea del primer handshake correcto de la conexión devuelta solo para un handle nativo de Defjs o un wrapper que reenvía el mismo objeto `open` en vivo; los handles personalizados y los wrappers que sustituyen `open` conservan su `open` público actual incluso después de reconectar, así que un `closed` compartido no puede saltarse la sanitización de URL ni el filtrado de cabeceras, y Defjs no reconstruye los metadatos del primer handshake a partir de transformaciones arbitrarias. Prefiere `await using stream = handle` para la limpieza de un ámbito propio. El disposer detiene la lectura y la reconexión de Defjs y espera a que se suelte el lock del reader; no promete que termine una promesa `ReadableStream.cancel()` atascada y controlada por el proveedor. Siguen disponibles `close()` / `closed` manuales.

```ts
async function consume(handle: EventStreamHandle<unknown>): Promise<void> {
  await using stream = handle;
  for await (const event of stream) console.log(event);
}
```

Las implementaciones estructurales de `EventStreamHandle` deben implementar `[Symbol.asyncDispose]()` y devolver el mismo camino de teardown propio.

## EventStructs

<ApiSignature name="EventStructs" />

La clave es el nombre del evento SSE; un mensaje sin campo `event:` se llama `message`. Cuando ninguna clave coincide, se usa el struct `default`. Un struct de evento `string` conserva el texto `data` en bruto. Cualquier otro kind es texto JSON: `JSON.parse` y luego el struct. Un `struct.literal` desnudo necesita por tanto texto JSON, no un token sin comillas. Los cuerpos `error` del handshake usan la misma regla de kind que HTTP: `string` es texto, `blob` / `file` son blobs, `arrayBuffer` son bytes y todo lo demás es JSON.

La reconexión vive en el cliente (`withSSEReconnect`). El `jitter` de SSE es un **factor multiplicativo 0–1**, igual que en WebSocket.

El presupuesto de reintento y el exponente de backoff se reinician tras un handshake correcto; se aplican por interrupción. Las opciones numéricas inválidas devuelven `REQ_OPTIONS_INVALID` antes de abrir un stream, y `maxDelayMs` limita el retraso final después del jitter. Consulta [`withSSEReconnect`](/es-ES/api/core/withssereconnect) para las reglas de validación, los valores por defecto y el manejo UTF-8 de `Last-Event-ID`.

El parser sigue las reglas de línea y de campo SSE de WHATWG y quita solo un BOM UTF-8 inicial al principio de cada stream físico. U+FEFF en valores de data o de ID se conserva; un nombre de campo posterior con prefijo BOM se ignora como desconocido. Los datos multilínea se unen con `\n`, una línea en blanco despacha un evento que lleva data y un evento inacabado en EOF se descarta.

Consulta la [guía de SSE](/es-ES/docs/sse) y [Consumir un stream SSE](/es-ES/recipes/consume-sse).

## EventStreamDefinition

`path`, `events`, `method` / `operation` / `input` / `error` / `maxBufferSize` / `maxQueueSize` opcionales. La forma de la solicitud coincide con HTTP, incluido `body`. `GET` y `HEAD` no pueden devolver un body. Un `input` declarado exige siempre un `builder` explícito. `input` solo define los parámetros; solo el builder decide dónde va cada valor. Solo las definiciones sin `input` pueden omitir `builder`.

## EventStreamEndpoint

Lo devuelve `defineEventStream`. El primer argumento es un cliente. Los demás argumentos son solo la entrada.

## EventStreamRequestShape

Los mismos campos que `HttpRequestShape` para el método y el path del stream.

## StreamAwaitResult

`[null, stream, open]` o `[error, undefined, open?]`.

## EventStreamData

Payload de evento parseado, inferido de un mapa `EventStructs`.
