```ts
interface ClientSSEOptions {
  handle?: FetchHandle
  onInvalidEvent?: (context: {
    reason: 'missing-struct' | 'validation-failed'
    message: { id: string; event: string; data: string }
    cause?: unknown
    signal: AbortSignal
  }) => unknown
  reconnect?: {
    attempts?: number
    delayMs?: number
    factor?: number
    jitter?: number
    maxDelayMs?: number
    shouldReconnect?: (context: {
      attempt: number
      cause?: unknown
      lastEventId: string
      method: string
      open?: { response: { status: number; statusText: string; url: string }; url: string }
    }) => boolean | Promise<boolean>
  }
}
```

- **handle** — Implementación de fetch que abre el stream. El valor por defecto resuelve `globalThis.fetch` en cada intento, incluidas las sustituciones instaladas después del import. Todo handle SSE recibe un `Request`. Si falta el Fetch global, la ejecución por defecto falla con `ENV_UNSUPPORTED`; un handle personalizado sigue siendo utilizable.
- **onInvalidEvent** — Se llama cuando un evento no tiene un struct que le corresponda ni un struct `default` (`'missing-struct'`), o cuando la validación de sus datos falla (`'validation-failed'`). El evento se omite. Un error lanzado por el hook no cierra el stream.
- **reconnect** — Debe activarse explícitamente. Sin esta opción, el stream nunca se reconecta. `attempts` vale por defecto **3** por interrupción; `attempts: 0` desactiva el reintento. Un handshake correcto reinicia el presupuesto, el `attempt` del callback y el exponente de backoff. `delayMs` es el primer retardo base, 1000 por defecto, y un valor `retry:` enviado por el servidor lo reemplaza. `factor` vale 1 por defecto. `jitter` es un factor multiplicativo de 0 a 1 y vale 0 por defecto. `maxDelayMs` limita el retardo final tras el jitter y el redondeo; sin tope configurado, sigue aplicando el límite de la plataforma de `2_147_483_647` ms. Una base cero sigue siendo cero; el desbordamiento de números válidos se satura en los topes. Sin `shouldReconnect`, solo se reconectan las solicitudes `GET`, `HEAD`, `OPTIONS`, `PUT` y `DELETE`; si se proporciona, su resultado determina si se reconecta para cada método y su contexto incluye `method`. Las solicitudes con un cuerpo `ReadableStream` nunca se reconectan. La reconexión envía el último ID como bytes UTF-8 en `Last-Event-ID`; un ID vacío lo borra y un ID que contiene NUL se ignora.

Las opciones de reconexión se validan antes de los interceptores o de Fetch: `attempts` es un entero seguro no negativo; `delayMs` y un `maxDelayMs` explícito son finitos y no negativos; `factor` es finito y positivo; `jitter` es finito y está entre 0 y 1. Los valores no válidos devuelven `REQ_OPTIONS_INVALID` en el momento de execute.

Configúralos con `withSSEHandle`, `withSSEOnInvalidEvent` y `withSSEReconnect`. Omitir `withSSEReconnect` desactiva el reintento.
