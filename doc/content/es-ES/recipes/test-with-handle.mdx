### Tres detalles clave al escribir pruebas

- **Por qué envolver `(input, init)` en `new Request(input, init)`**: `withHTTPHandle` recibe la firma estándar `fetch(input, init)`. Envolverla en `new Request(input, init)` ofrece una vista única de `method`, `url`, `headers` y `await request.json()`.
- **Por qué usar `withEndpoint("https://fixture.invalid")`**: `createClient` valida la URL base antes de invocar `withHTTPHandle`; `.invalid` está reservado por RFC para no resolver DNS real.
- **Cómo simular los tres resultados HTTP habituales**:
  - Éxito `2xx`: devolver `Response.json(...)` -> `[null, data, response]`
  - Error `4xx` / `5xx`: devolver `Response.json(..., { status: 422 })` -> `err.code === "HTTP_STATUS"`
  - Fallo de red: rechazar o lanzar (`Promise.reject(new TypeError("fetch failed"))`) -> `err.code === "NET_UNREACHABLE"`. **No** devuelvas `Response.error()`, porque cualquier `Response` (incluso con estado `0`) se trata como respuesta HTTP (`HTTP_STATUS`).

En producción, llama a la misma operación `getOrder` con un cliente configurado con `withEndpoint(...)`. Consulta [Pruebas](/es-ES/docs/testing) y [Cliente](/es-ES/docs/client).
