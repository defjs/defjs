# Consumir un flujo SSE

Cada `EventStreamHandle` expone un único iterador asíncrono. Coloca siempre `stream.close(...)` y `await stream.closed` dentro de un bloque `finally` para que una salida temprana con `break` o `return` nunca deje escapar el flujo Fetch subyacente:

<Tabs items={["sdk/deployments.ts", "app/main.ts", "deploy-events.ts"]}>
  <Tab value="sdk/deployments.ts">
```ts
import { defineEventStream, struct } from "@defjs/core";

export const deployEvents = defineEventStream({
  path: "/deployments/events",
  events: {
    line: struct.object({ text: struct.string() }),
  },
});
```
  </Tab>
  <Tab value="app/main.ts">
```ts
import { createClient, withEndpoint } from "@defjs/core";
import { deployEvents } from "../sdk/deployments.ts";

const client = createClient(withEndpoint("https://api.example.com"));

async function main() {
const [error, stream] = await deployEvents(client);
if (error) {
console.error(error.code);
return;
}
try {
for await (const event of stream) {
if (event.event === "line") {
console.log(event.data.text);
break;
}
}
} finally {
stream.close("consumer-finished");
await stream.closed;
}
}

void main();

````

Con un servidor cuyo primer evento sea `line` con datos `{ "text": "build started" }`, el script imprime:

```txt
build started
````

- SSE no se reconecta automáticamente ante fallos de red o de lectura a menos que configures [`withSSEReconnect(...)`](/es-ES/api/core/withssereconnect) en el cliente.
- Cuando `withSSEReconnect` se habilita con un objeto de opciones, `attempts` se establece por defecto en `3` por interrupción y se reinicia tras un handshake exitoso (`attempts: 0` desactiva la reconexión). Sin un callback `shouldReconnect` personalizado, solo las peticiones `GET`, `HEAD`, `OPTIONS`, `PUT` y `DELETE` con cuerpos reproducibles se reconectan. Consulta [Flujos de eventos SSE](/es-ES/docs/sse).
