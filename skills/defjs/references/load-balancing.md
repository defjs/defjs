# Multiple endpoints, balancing, and retry

## Endpoint selection

Configure replicas of one service with `withEndpoint(...urls)`. URLs are deduplicated in first-seen order; a later option replaces the list. Different services still need separate clients.

```ts
import {
  createClient,
  pickFirstBalancer,
  withBalancer,
  withEndpoint,
  withRetry,
} from "@defjs/core";

export const client = createClient(
  withEndpoint("https://primary.example.com", "https://backup.example.com"),
  withBalancer(pickFirstBalancer()),
  withRetry({ maxRetries: 2 }),
);
```

The client above is configuration, not an operation call. Pass it to an SDK operation and check the error-first tuple before using a result.

| Strategy                            | Defaults and intended use                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pickFirstBalancer(options?)`       | Default client strategy. Sticky ordered primary/backup; advances after attributed `NET_UNREACHABLE` or `NET_UNAVAILABLE`, not a timeout, so a retry after a timeout picks the same endpoint again. Order follows `PickInfo.members`. Health filtering and `shuffle` are off. Optional positive `failbackMs` returns to the primary by time alone: after that long away from it, the next pick whose candidates include it selects it again, with no judgement of recovery. If it fails again the advance rule applies and the time restarts. Pick a `failbackMs` longer than the time between picks, such as a reconnect delay.                                                                                                                                                                                       |
| `roundRobinBalancer(options?)`      | Counter starts at a random `uint32`, then selects cyclically. Every pick, including a retry's or a stream reconnect's, advances it; without `outlierDetection`, with serial calls, a persistently failing endpoint gets more than 1/n of first attempts, all of them with two endpoints and retries on (concurrent calls break this). Optional `weights: ReadonlyMap<string, number>` uses smooth weighted round-robin; weights must be finite and positive; missing weights are 1. Health filtering is off unless `outlierDetection` is passed.                                                                                                                                                                                                                                                                      |
| `p2cBalancer(options?)`             | Samples two distinct candidates, choosing lower PeakEwma RTT × (pending + 1). Defaults: `load: "peakEwma"`, `choiceCount: 2`, `defaultRttMs: 30`, `decayMs: 10000`. `load: "pending"` compares in-flight counts, reserved at `pick` and released at `end` (or `done` if no response began). Load history keeps at least 256 endpoints and at least the current member count. Health filtering is off unless `outlierDetection` is passed.                                                                                                                                                                                                                                                                                                                                                                             |
| `outlierDetection(child, options?)` | Wraps a strategy. Defaults: `consecutiveFailures: 5`, `minPenaltyMs: 1000`, `maxPenaltyMs: 60000`, `jitterRatio: 0.5`. Every coded outcome is a failure (`NET_UNREACHABLE`, `NET_UNAVAILABLE`, `NET_SERVER_ERROR`, `NET_TIMEOUT`, `NET_BODY_INCOMPLETE`); an attempted outcome without a code resets the streak, while unattributed attempts and discarded samples leave it unchanged. History keeps at least 256 endpoints and at least the current member count. Each ejection adds a step to the next penalty; 10 s without an ejection lowers it a step. When an ejection ends the endpoint is selectable again, with no trial request and no recovery judgement; a late result from an attempt that began before the ejection, or during it, is ignored. All-unhealthy falls back to the current candidate list. |

Health filtering is off in every built-in balancer; `outlierDetection: {}` enables it with the defaults, and `false` is the same as omitting it. Defjs does not decide what healthy means: only the optional synchronous `isHealthy(endpoint)` does. It reads an application-owned cached health result and is not an async health-check runner; it is called for each endpoint on every pick, `false` skips the endpoint, `true` does not end an ejection, and a throw is not caught: the pick fails with `REQ_BUILD_FAILED` and the thrown value as `cause`. Optional `isFailure(info)` replaces the default rule for what counts toward ejection. Share a balancer instance only when its endpoint-health/load state should be shared.

## Retries: one policy for HTTP, SSE, and WebSocket

No `withRetry` means one attempt per call and, for HTTP, no retry budget. `withRetry()`, `withRetry(undefined)`, and `withRetry({})` enable the defaults below. A later option replaces the whole policy; `{ maxRetries: 0 }` disables retries. `client({ retry })` replaces the policy for one call; the HTTP `budget` stays with the client. Options are not validated at runtime.

| Option                                      | Default / boundary                                                                                                                                                                                                                                                                                                |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxRetries`                                | 3 retries after the first attempt; `0` never retries. SSE and WebSocket reset the count when a connection is established again.                                                                                                                                                                                   |
| `methods`                                   | `["GET", "HEAD", "OPTIONS", "TRACE", "PUT", "DELETE"]`, case-insensitive. Every method actually sent after interceptor rewrites must qualify for HTTP. `[]` retries nothing by default. WebSocket ignores it.                                                                                                     |
| `attemptTimeoutMs`                          | Unset. Time limit of one attempt: HTTP from invocation until its response body is read, SSE until the response headers, WebSocket until `open`. Interceptor work around an HTTP send and struct decoding are not timed. It no longer enables retries by itself: `withRetry({ maxRetries: 0, attemptTimeoutMs })`. |
| `delayMs`, `factor`, `jitter`, `maxDelayMs` | 1000 ms, 2, 0.2, 30000 ms. Multiplicative ±jitter, capped after jitter and rounding; zero delay skips waiting. `maxDelayMs` also accepts `Infinity`, with the platform timer cap still applying. An SSE server `retry:` field replaces `delayMs`.                                                                 |
| `shouldRetry(context)`                      | Optional, may return a promise. Called after the `maxRetries` check, so it replaces `context.retryable`; return that to keep the default. Not called for a caller abort, a manual close, a fatal error, or a `ReadableStream` body. A throw ends the call with that error as the cause.                           |
| `budget`                                    | HTTP only. `{ percentCanRetry: 0.2, minRetriesPerSecond: 10, ttlMs: 10000 }`. 20% of original traffic plus reserve; credits expire in ten slices of `ttlMs / 10`. `false` removes the cap.                                                                                                                        |

After a failure, in this order: a caller stop, a fatal error, or a `ReadableStream` body ends the call; spent `maxRetries` ends it; `shouldRetry` (or `context.retryable`) decides; for HTTP the budget must pay; then the backoff runs and the balancer picks again from **every** endpoint, including the one that just failed, so a single endpoint is tried again after the delay. `context` is a `RetryContext` narrowed by `transport`: `attempt`, `cause`, and `retryable` everywhere; HTTP adds `method`, `endpoint`, `status`; SSE adds `method`, `lastEventId`, `open`, `status`; WebSocket adds `code`, `reason`, `wasClean`.

Default `retryable`: HTTP, a method in `methods` and no response, a 502/503/504, or an `attemptTimeoutMs` timeout (other statuses reach `shouldRetry` with `retryable: false`); SSE, a method in `methods` and a handshake or stream network failure, a 502/503/504 handshake, or an attempt timeout (clean EOF ends the stream); WebSocket, every close that `session.close()` did not request, a never-opened connection and an unanswered heartbeat included.

Each HTTP retry re-picks, rebuilds, and reruns the complete interceptor chain, including auth. The retry budget belongs to the client configuration: derived `client({ signal })` values share it; separately created clients do not, even if their balancer is shared. Balancer state (sticky endpoint, ejections, load) also belongs to the client: create the client once and derive per-call values to keep both the balancer state and the retry budget; sharing one balancer through `withBalancer` keeps the balancer state only, and a client created per request starts both fresh. An exhausted budget returns the current failure without another wait or attempt. If an HTTP retry round cannot use any endpoint (the pick fails or the next URL does not resolve), the call returns the previous attempt's fault, not `REQ_BUILD_FAILED`; interceptor work after the send and decoding are not timed by `attemptTimeoutMs`, and a caller deadline that expires there is not reported to the balancer as `NET_TIMEOUT`.

- `ReadableStream` bodies are never replayed. Explicit browser offline state (`navigator.onLine === false`) suppresses endpoint attribution and HTTP connection-failure retry; it does not prove Fetch was never invoked.
- Core does not read `Retry-After`. That header is an application interceptor policy. An interceptor's `next()` loop stays on its current endpoint and does not rerun the builder or outer auth. It can multiply physical sends beyond `maxRetries` (three primary sends plus one backup send with one outer retry).
- A JSON POST auth-refresh replay is still two HTTP deliveries. Require auth rejection before business handling and a stable idempotency key with server-side deduplication, or return the 401. Cross-region write retries need shared, atomic server-side deduplication; a header alone is not exactly-once execution.
- Migration: the separate SSE and WebSocket reconnect helpers are gone; use `withRetry`, and the request option `reconnect` is now `retry`. `attempts: N` becomes `maxRetries: N` and `shouldReconnect` becomes `shouldRetry`. SSE `factor` goes from `1` to `2`, SSE `maxDelayMs` from unlimited to `30000`, and `jitter` from `0` to `0.2`. `withRetry` also retries HTTP; to keep HTTP calls to one attempt, return `false` for `context.transport === "http"`.

## SSE and WebSocket retries

SSE and WebSocket use the same `withRetry` policy, opt-in, with `maxRetries` counted per outage, not per session. Every successful open resets the count and backoff, so `maxRetries: 1` can produce many connections in a long session; stop a flapping server with `shouldRetry`. A managed reconnect re-picks from the configured endpoints and may revisit an endpoint. There is no budget for them.

- SSE: clean server EOF ends the stream; it does not retry. Read failures may retry. A 502/503/504 handshake (initial or reconnect) is retried like a refused connection under the same rules (method, `shouldRetry`, `maxRetries`, `ReadableStream` body); other non-2xx handshakes reach `shouldRetry` with `retryable: false` and end the stream by default. Exhausted and declined retries end with `HTTP_STATUS`; a later operation can pick the backup. SSE commits `id:` only at the terminating blank line (including ID-only frames); a partial frame does not advance the cursor. A retry sends the committed ID as `Last-Event-ID`; an empty ID clears it. The server must implement resumption/deduplication. After a reconnect handshake ends the stream, read the live `stream.open.response.status`; the iterator/`closed` fault is `HTTP_STATUS`.
- WebSocket: `wasClean` describes the close handshake, not application success. A server 1011 can have `wasClean: true`; decide on `context.code` in `shouldRetry`, e.g. stop on 1008. Reconnection restores transport, not application subscriptions or acknowledgments. A heartbeat acknowledgement timeout is a connection failure: it reports `NET_UNREACHABLE` to the balancer and enters the retry flow (a heartbeat that cannot be sent is local, neutral, and not retried). For an opened socket the balancer sees the close code only, whatever `wasClean` reports: 1006 or 1015 (no close frame) is `NET_UNREACHABLE`, 1012 or 1013 is `NET_UNAVAILABLE`, other codes are not failures.
- WebSocket input, builder output, and selected subprotocols are captured once for the session. The URL is resolved before each `beforeConnect` call; a retry can replace the selected base endpoint, not the captured path/query. `beforeConnect` runs per attempt but cannot refresh a captured query token or subprotocol by changing a closure variable. Obtain new credentials and call the operation again when those values must change.
- Keep owning the logical handle/session through reconnects. Handle runtime errors, close it, and await `closed` (or use `await using`).

## Custom balancer contract and faults

Implement synchronous `Balancer.pick(info)` returning `[error, undefined]` or `[null, result]`. `info` contains the candidate `endpoints` and optional static `operation`, not a transport discriminator. Never mutate the candidates, invent an endpoint, return a promise, or throw for ordinary no-candidate outcomes.

```ts
import { ERR_NO_CANDIDATE, type Balancer } from "@defjs/core";

export const first: Balancer = {
  pick({ endpoints }) {
    const endpoint = endpoints[0];
    if (endpoint === undefined) return [ERR_NO_CANDIDATE, undefined];
    return [null, { endpoint }];
  },
};
```

The selected string must belong to that pick's candidate list; foreign selections become `REQ_BUILD_FAILED` before I/O, and their `done` runs with `{ attempted: false }`. `PickInfo.endpoints` is one pick's candidates (shrinking when a wrapper filters); `PickInfo.members` is the client's whole list, the same for every attempt, which stateful balancers key on. `ERR_NO_CANDIDATE` is a cause sentinel, not a fault code: inspect `fault.code === "REQ_BUILD_FAILED"` and `isNoCandidateCause(fault.cause)` (also works across Core copies).

Optional callbacks follow `pick → start → end → done`: `start()` runs immediately before transport; `end(info)` runs when the peer response begins or a pre-response transport failure occurs; `done(info)` runs once on completion, including pre-transport exits after a valid pick. A later body failure can differ from the earlier `end` sample. All callbacks must be synchronous and are called without a receiver (`this` is `undefined`; use closures or bound functions). Core contains a synchronous throw and reports it with `reportError` where the runtime defines it (not Node.js), and an unhandled report can end a Bun or Deno process that has no error handler; it ignores rejected thenables. Custom code should still not throw. `attempted: false` is not a health sample (local build/short-circuit/cancellation/explicit close/offline attribution/network error on a streamed request body). Neutral `DoneInfo.code` values are not the operation's public tuple fault codes; custom strategies may also read raw `status`.

## Observability limits

Current `@defjs/opentelemetry-server` HTTP spans observe individual attempts. They are siblings under an active application parent; core creates no logical-call parent or attempt number/retry reason/budget attributes. SSE/WS use one logical-session span across reconnects, retaining initial endpoint URL/metric attributes; active metrics count logical sessions, not physical sockets. There are no dedicated endpoint ejection/recovery or retry-budget events. Add application-level outcome accounting rather than inferring those decisions from span counts.
